# Performance audit, November 2026

- Date: 2026-11-17
- Base: `main` at `c4974cb`
- Requested by: Salih (owner)
- Status: findings to be measured and scheduled. Nothing in this audit changes code.
- Rules proposed from it: [ADR-0143](../adr/0143-performance-rules-for-every-change.md) (Proposed)

## Why this audit

Until now the project put working features first. Most of them now work, so the next step is to make RBS produce the best output with the least CPU, GPU, memory and power, and to turn what we learn into rules that new features follow ([ADR-0143](../adr/0143-performance-rules-for-every-change.md)).

The scope covers runtime cost (compositing, capture, encode, audio, UI, idle cost), startup, binary size and, briefly, the developer loop. The aim was to find every optimization, from a single loop to "do this differently". Runtime speed has priority over the developer loop (owner, 2026-11-17).

## Method and limits

- Seven independent reviews of the code, one per area. Each was told to quote the code it relies on and to verify line numbers. The full findings are in the area files listed under [Area reports](#area-reports).
- **Every benefit is an estimate unless it says "measured".** Estimates show their arithmetic, such as bytes per frame times frame rate. Nothing was built or benchmarked for this audit. Measured numbers come from earlier work recorded in the specs and ADRs.
- Spot checks by the lead auditor against the code confirmed every claim checked: C-01 (2 ms park), G-05 (`MAX_WAIT` 50 ms), C-03 (scalar un-premultiply), U-01 (`appearance.toml` and theme files read per sync), E-07 (hardware encoders advertise 0 B-frames), D-02 (`Backends::PRIMARY` on Windows), R-16 (`timeBeginPeriod(1)`), R-02 (virtual camera converts before it knows a consumer exists), R-04 and A-11 (preview and meter sink are "essential" nodes).
- Line numbers are from `c4974cb`. They drift; the function names stay searchable.
- A [measurement plan](#measurement-plan) lists short device runs (at most 2 minutes each) that settle the uncertain numbers before work starts.

### Reference hardware and scenario

Agreed with the owner on 2026-11-17:

| Tier | Machine |
| --- | --- |
| Low | 4-core laptop with an integrated GPU (shared memory bandwidth of about 50-100 GB/s) |
| Mid | 6-8 cores, a mid-range discrete GPU |
| High | Mac M4 Pro; Windows with an RTX 4090 and an AMD iGPU |

Reference scenario: 1080p60 stream and recording at the same time, with 3-4 sources (display capture, camera, image, text). Bandwidth findings matter most on the low tier, where every GB/s of copies is a visible share of the whole machine.

### Labels used

- **Effort:** S under a day, M 1-3 days, L more than 3 days.
- **P15:** the code is on a [hot path](../architecture/hot-paths.md) and needs before/after numbers, the `hot-path-review` checklist and the owner's sign-off.
- **ADR:** the change needs a new ADR or supersedes one, with an independent review (ADR-0014).
- **Visual:** the user can see the change, so it needs the owner's approval with dark and light screenshots (CLAUDE.md rule 16).

## Summary

There are 149 findings across seven areas. Most of the cost does not come from slow loops. It comes from **work nobody needs**: pictures read back that no encoder uses, frames rendered that nobody sees, captures at four times the size and rate that are drawn, and a control plane that rebuilds everything for a small edit. The biggest wins are therefore structural, and most of them are medium effort.

Ten themes carry almost all of the benefit:

| # | Theme | Main findings | Typical gain (estimate) |
| --- | --- | --- | --- |
| 1 | **Stop reading frames back to the CPU for encoding** (exit ADR-0038, macOS first) | R-10, E-03, E-05, E-06 | 1080p60: about 400 MB/s of CPU copies and about 58 MB RAM per encoder chain; 4K60: about 1.5 GB/s and 224 MB. On the RTX 4090 also about 200 MB/s each way over PCIe |
| 2 | **Do not work when nobody is watching or listening** | R-02, R-04, R-22, U-09, A-11, C-06, C-01 | Minimised and not live: render and audio cost to near zero. Virtual camera without a reader: one full conversion and readback per frame removed |
| 3 | **Do each piece of work once and share it** | R-01, E-04, E-01, A-13 | Record + stream at the same size: one conversion and readback instead of two (about 200 MB/s of DMA and CPU copy each at 1080p60). Replay buffer: one encoder session and about 58 MB less |
| 4 | **Render and encode only what changed** | R-03, E-02 | Static scene: about 100 MB of GPU traffic per tick skipped at 1080p. ISO file of a 30 fps camera on a 60 fps canvas: half its export work |
| 5 | **Capture at the size and rate that is drawn** | C-02, C-05, C-21, C-13, C-11, C-12 | 5K display on a 1080p canvas: 7x less capture bandwidth and memory (413 MB to 58 MB of surfaces). 240 Hz display on a 60 fps canvas: 4x fewer frames |
| 6 | **Make edits cost what they change** | G-01, G-02, G-03, G-04, U-04, U-06, U-07, U-11 | A drag step from about 1-20 ms to about 20-100 µs. Autosave fsyncs during a drag down about 99 % |
| 7 | **A quiet UI** | U-01, U-02, U-03, U-05, A-10 | Silent meters: 30 full-window redraws per second to 0. Native meter layers: measured 8.4-9.2 % to 2.5 % CPU at 16 meters (ADR-0035) |
| 8 | **Wait for events instead of polling** | C-01, G-05, G-09, C-19, A-21, E-11, E-16, R-16, A-12 | Media source: 500 wake-ups/s to under 100. Control thread at idle: 20/s to 0-4/s. Browser source: 120-200/s to about 4/s when static |
| 9 | **Smaller pixel formats and buffers** | R-11, C-08, R-15, C-10, C-17, R-17, E-09, R-21 | NV12 cameras and videos no longer expanded to 16-bit float RGBA (up to 4 GB/s of GPU traffic at 4K60). 4K media: about 300 MB to 100 MB of VRAM per source |
| 10 | **Vectorised and skipped audio work** | A-01, A-02, A-03, A-04, A-07 | Mixer 13 µs to about 3 µs; loudness 19.7 µs to about 3-5 µs; input and output nodes 27-32 µs to about 3 µs at matched rates |

Better output per bit is part of "best output with the least resources". Two findings give better pictures for the same bitrate at almost no CPU cost: hardware encoders never use B-frames (E-07, about 10-15 % fewer bits for the same quality) and the NVENC and AMF defaults leave quality on the table (E-08, about 5-10 %).

### First results (Mac M4 Pro, 2026-11-17)

These are runs M1 to M3, made on a release build of `main` at `ab90f270` (the Mac's checkout of main at the time; the measured paths have not changed since). The owner's normal scene collection was loaded: two ScreenCaptureKit display or window captures, nothing on air, Mixer shown. Each run was under 70 s. Release build: 301 s with 6 jobs.

| Run | Result | What it shows |
| --- | --- | --- |
| M1 idle, `top` 45 × 1 s after a 10 s settle | Process CPU median **26.9 %** (max 31.0 %); 18-20 threads; RSS 427-429 MB, flat; about 6 idle wake-ups per second | Idle is far from the "0.0 % when nothing animates" UI budget |
| `sample` 10 s, samples outside a wait (of about 2068 per thread) | Main thread about 214 (**about 10 % of a core**), almost all CADisplayLink → Slint `draw` → `SkiaRenderer::render` of the main window. `rbs-partition-1` (audio) 15, `rbs-render` 12, `rbs-studio` 10, each SCK cursor thread 3-4, each SCK queue 6-7 | The largest single cost is the UI redrawing the whole window while nothing changes, not a spinning engine thread |
| M3 `RBS_MEASURE_UI=12`, idle phase | **365 frames in 12 s (about 30 fps)**, render p50 2.45 ms, p95 4.22 ms, frame interval p50 33.3 ms | The idle window redraws at the 33 ms meter timer rate, which fits U-02 (every meter row pushed every tick even when silent). One hover frame took 48.6 ms |

Other phases of the same run: hover 533 frames (render p50 2.34 ms, max 48.6 ms), resize 1440 frames (p50 1.07 ms), sweep 451 frames (p50 3.59 ms), redraw 1006 frames (p50 1.91 ms).

Consequences for the ranking: U-02 (meter rows only on change) and U-03 (native meter layers) move to the top of wave 1 and wave 3. The rest of the 27 % (two display captures at native size and rate, render, audio input alignment) is what C-02, C-05, R-03 and A-03 address. The cause of the 30 fps redraw is inferred from the 33 ms interval and the code; a run with the Mixer hidden would confirm it.

## Documentation drift found

- `docs/architecture/overview.md` says transports run on a `tokio` runtime. No crate uses tokio; transports use their own threads (E-16).
- `docs/architecture/overview.md` lists `rbs-transport-whip`, which does not exist in the tree.
- ADR-0109 decision 9 says the browser picture is never converted with a per-frame CPU pass, but the helper un-premultiplies every pixel on the CPU (C-03).
- ADR-0035 (native meter layers) is accepted, but the app does not use the layers and `docs/status.md` does not mention the gap (U-03).
- The idle-cost checks in `docs/specs/performance-budgets.md` compare "loaded" with "baseline", so a wake-up that both runs share, such as the control thread's 20/s (G-05), can never fail them. ADR-0143 adds an absolute idle check.

These are recorded here and fixed by the changes that implement the findings, so that each spec is corrected next to its code.

## How to use this audit

1. Run the [measurement plan](#measurement-plan) first and write the numbers into the area reports, replacing estimates.
2. Take items wave by wave, one concern per PR. Each PR cites its finding ID and follows [ADR-0143](../adr/0143-performance-rules-for-every-change.md).
3. After each wave, add the measured result to `docs/specs/performance-budgets.md`. Budgets are set from what the optimizations achieve, not fixed in advance (owner, 2026-11-17).
4. Repeat the audit after a large feature phase, and keep the thread inventory in [engine-core.md](audit-2026-11/engine-core.md) current.
