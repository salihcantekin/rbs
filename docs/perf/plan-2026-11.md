# Performance work plan, November 2026

- Date: 2026-11-17
- Source: [performance audit 2026-11](audit-2026-11.md) (finding IDs below point there)
- Order agreed with the owner: low risk and high impact first, test each package quickly, then structural work, then changes that need an ADR.

## How every package is done

1. **One package = one PR = one concern**, mostly within one crate. Packages that touch different crates can run in parallel threads; packages that touch the same files run one after another (noted under "Conflicts").
2. **Tests:** `cargo xtask affected clippy` and `cargo xtask affected test` in the cloud (changed crates and their dependents only, CLAUDE.md rule 14 and the project testing rule). A new test proves the behaviour the package changes, for example "an unchanged meter does not write its row".
3. **Numbers:** each package names its before/after measurement.
   - Off the hot path: one Mac run of at most 2 minutes (slot from the coordinator), compared with the 2026-11-17 baseline: idle CPU 26.9 %, about 30 UI frames/s at idle, RSS 428 MB (audit, "First results").
   - On a hot path (P15): a criterion bench before and after, the `hot-path-review` checklist, and the owner's sign-off before merge.
4. **Visual changes:** none of packages P1-P8 should change what the user sees. If one does, it stops for the owner's approval with dark and light screenshots (CLAUDE.md rule 16).
5. **Merge:** one at a time through the coordinator, after the owner's OK.

## Order and parallelism

- Now: P1 (this thread), then P2 in the same thread because both edit `rbs-app`. P3 and P5 can start in parallel threads since they touch other crates.
- P4 and P6 need P15 sign-offs, so they go in once their benches are ready.
- P7's Windows half and P8 wait for an SC-PC slot.
- After phase A: repeat the Mac baseline run and update the audit's "First results" table, then start phase B in the order S1, S2, S3/S4, S5.
- ADR-0143 (the rules) is reviewed in parallel; it does not block phase A.
