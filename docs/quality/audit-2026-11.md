# Code quality and structure audit, November 2026

- Date: 2026-11-17
- Base: `main` at `ab90f27`
- Requested by: Salih (owner)
- Companion to: [performance audit 2026-11](../perf/audit-2026-11.md) (PR #518, ADR-0143). Structural changes are planned once, across both audits ([Plan](#plan-aligned-with-the-performance-waves)).
- Rules proposed from it: [ADR-0144](../adr/0144-code-quality-rules-and-their-enforcement.md) (Proposed)
- Status: findings to be scheduled. Nothing in this audit changes code, except the removal of merge-conflict markers that main contained ([QD-01](#qd-01-main-contains-merge-conflict-markers)).

## Why this audit

RBS is now about 437,000 lines of Rust in 90 crates and 22,700 lines of Slint, written mostly by AI agents working in parallel. The owner asked (2026-11-17) to measure how easy the code is to read and change, how well crates and tests are split for fast builds and tests, and whether the project's standards and principles are actually enforced, not only written down. The performance audit will move code too, so both are planned together.

## Method and limits

- Every number below was measured on `ab90f27` with scripts over the tree (`cargo metadata --no-deps`, line counts, brace-matched function lengths, `grep` counts), unless it says "estimate". Function lengths count lines between the signature and its closing brace; generated FFI bindings (`*/src/sys/*`) are left out.
- Nothing was built or benchmarked for this audit. Build and link times quoted come from earlier measurements recorded in project notes and in the performance audit's [devloop report](../perf/audit-2026-11/devloop.md).
- One reviewer read the whole tree; there were no separate area reviews. Findings that need a deeper read before work starts say so.

### Labels

- **Effort:** S under a day, M 1-3 days, L more than 3 days.
- **Risk:** of the change itself (Low, Med, High).
- **ADR:** changes crate layering, a contract or a rule, so it needs a new ADR and an independent review (ADR-0014).
- **Perf:** overlaps a finding of the performance audit; the IDs are listed and the work is planned once.

## Summary

The foundations are good: ports have consistent typed errors, `check-layers` and `check-ui` turn rules into counts, unsafe blocks must document themselves, library code has almost no `unwrap`, nextest refuses retries and kills hangs. The problems are concentrated in a few places and in one missing habit:

1. **Three god files carry most of the app.** `rbs-app` has 72,900 lines of Rust: `studio_host.rs` (16,732 lines, one 1,659-line function, a 97-field `Host`), `studio_ui.rs` (9,739) and the binary's `main.rs` (6,368, `install_studio` 942 lines). They are edited by 17-20 of the last 50 merged PRs, so parallel agents collide there, and every change to them rebuilds and relinks the heaviest test binaries in the workspace.
2. **The studio host is toolkit-free but lives in the toolkit crate.** Its 23,000 lines and the 18 settings-file modules it uses never name Slint, yet its 13 test binaries link Slint and Skia because they are `rbs-app` tests. Moving it into its own crate is the biggest structural win for build and test time ([QS-01](#qs-01-move-the-studio-host-out-of-rbs-app)).
3. **Two command paths.** The window uses `studio_host::Command` (147 variants, a 942-line dispatcher) and the API uses `rbs_api::Command` (155 variants, a 1,659-line dispatcher). Every feature is wired twice, and principle U20 (every UI command maps to an API command) has no test.
4. **Little enforces the rules automatically between CI runs.** CI is set to run by hand (`workflow_dispatch`) for now; the owner will make it automatic again (2026-11-17). Until then agents merge locally, and the toolchain floats on `stable`. Proof: main at `ab90f27` contains unresolved merge-conflict markers in the control API spec and the ADR index, and new clippy lints from a newer stable already turned main red twice without a code change. One local gate command ([QN-01](#qn-01-one-verify-command-and-a-recorded-result-before-every-merge)) and a pinned toolchain ([QN-02](#qn-02-pin-the-toolchain)) fix most of this.
5. **Tests copy their helpers.** The GPU-or-skip helper exists in 20+ files and its `RBS_REQUIRE_GPU` check in 77 places, there are no property tests at all, no Miri or loom for the hand-written lock-free code, and 9 screenshot tools are compiled as full `rbs-app` test binaries.
6. **Docs are large and drift.** The control API spec is 243 KB with lines up to 7,900 characters, the UI design system spec 276 KB, and `status.md` has table cells over 4 KB. Three Proposed ADRs (0103, 0104, 0105) are implemented and shipped, against the rule that Proposed ADRs are not implemented.

## Findings

IDs: QS structure, QT tests, QN enforcement, QR errors and robustness, QD docs and ADR drift.

### Structure: crates, modules, boundaries

#### QS-01 Move the studio host out of rbs-app
- Location: `crates/rbs-app/src/studio_host.rs` (16,732 lines) and `studio_host/` (15 files, 6,202 lines); the settings-file modules it uses: `record_profile` (2,081), `user_session` (1,256), `stream_profile` (762), `calibration_file` (628), `stream_destinations` (604), `edit_history` (454), `remote_control` (350), `device_sync_file` (323) and 10 smaller ones. None of them uses `slint`. Tests: `crates/rbs-app/tests/studio_*.rs` (13 binaries, none uses `slint`).
- Problem: the control thread is engine-side logic, but it is compiled inside the desktop shell. Its tests link the whole `rbs-app` with Slint and Skia (earlier measurement: `rbs-app` test binaries are 230-560 MB each, and its test and example units cost about 153 s of CPU, mostly linking). `cargo test -p rbs-app` for a host change also builds the five UI crates. The host cannot be reused by a headless studio process (ADR-0099, Proposed) or `rbs-cli`.
- Proposal: a new toolkit-free crate (working name `rbs-studio-host`, class App-support in `check-layers`) holding the host and its settings files. `rbs-app` keeps windows, bindings and platform glue. The host's tests move with it and become one or two binaries (see QT-04). Do it as a pure move PR (no behaviour change) on a day with no other open PR in `rbs-app`, then split the file (QS-02).
- Benefit: estimate. Host tests no longer link Slint/Skia: much smaller binaries and seconds less link per binary; iterating on the host (`cargo test -p rbs-studio-host`) needs no UI build at all. The host gets a public boundary that the window and the API both go through.
- Effort: L. Risk: Med (large move; mechanical). Needs: ADR (crate layering). Perf: G-01 to G-08, U-06, D-14.

#### QS-02 Split studio_host.rs by concern
- Location: `crates/rbs-app/src/studio_host.rs`: `struct Host` (line 3550, 97 fields), `Host::command` (line 4430, 942 lines), `ApiTarget::run` (line 13279, 1,659 lines), `Host::start` (244), `start_recording_with_tracks` (236), `round` (234), 202 top-level items.
- Problem: one file holds recording, streaming, scenes, sources, filters, outputs, projectors, the API adapter and their state. A reader needs the whole file to find one behaviour; every feature PR edits it (17 of the last 50 merges), so parallel agents collide; a 1,659-line `match` cannot be reviewed.
- Proposal: per-concern modules (`recording`, `stream`, `scenes`, `sources`, `outputs`, `projector`, `api`), each with its own state struct inside `Host` and its own handler function that the dispatchers call (`Command::Record*(..) => self.recording.handle(..)`). Target: no file over 2,000 lines, no function over 200 (QN-04).
- Benefit: reviewable units; fewer merge conflicts; perf work (G-02 layers-only edits, G-04 revision counter, G-08 targeted publish) lands in one module instead of a giant function.
- Effort: M-L. Risk: Low-Med (mechanical, covered by 13 test binaries). Perf: G-02, G-04, G-08, U-06.

#### QS-03 One command path for the window and the API
- Location: `studio_host::Command` (147 variants, `studio_host.rs:640`) and `rbs_api::Command` (155 variants, `rbs-api/src/request.rs:1759`); two dispatchers (QS-02). `docs/status.md`: "JSON Schema, `stats`, `ui.*` routing, U20 command parity: Not started". Principle U20 asks for a test that every UI command maps to an API command.
- Problem: a feature is wired twice (window command and API command, often with separate validation), the two drift, and remote control or AI tools cannot do what the window does until someone adds the second path.
- Proposal: the window sends `rbs_api::Command` for every operation the API has; `studio_host::Command` keeps only window-only operations (pickers, live drags until G-02 lands) and each of those is listed in a test as "window only, because ...". Add the U20 parity test from `rbs-ui`'s command registry. Plan it with G-02 (the layers-only edit path), so drags get one design.
- Benefit: one place to validate and test each operation; API parity by construction (Stream Deck, MCP).
- Effort: L. Risk: Med. Needs: ADR or a spec change to the control API and `ui-design-system` command registry. Perf: G-02, U-11.

#### QS-04 The binary's main.rs is 6,368 lines of untestable wiring
- Location: `crates/rbs-app/src/main.rs`: 28 modules declared only in the binary (`app_menu`, `appearance`, `menu_bar` 2,387 lines, `look`, ...), `install_studio` (942 lines), `run` (436), `sync` (299), `sync_studio` (199). Edited by 20 of the last 50 merged PRs.
- Problem: modules declared in `main.rs` cannot be reached from `tests/`, so they are tested only through screenshots or by hand; one 942-line function installs every callback of every window.
- Proposal: move the modules into the library (`lib.rs`) and split `install_studio` and `sync` into per-window or per-panel binding modules (`bind::scenes`, `bind::mixer`, `bind::outputs`, ...). Combine with the performance audit's U-04 and U-05 (targeted UI updates, model reuse), which rewrite the same sync code.
- Benefit: testable bindings; smaller, parallel-safe edits.
- Effort: M. Risk: Low-Med. Perf: U-04, U-05, U-08, U-11, U-12.

#### QS-05 studio_ui.rs applies every update in one function
- Location: `crates/rbs-app/src/studio_ui.rs` (9,739 lines): `apply` (519 lines), `push` (270), `set_rows` (203); a 214-line test inside the file.
- Problem: as QS-04; the performance audit's U-04 wants one handler per update kind, which this layout makes hard.
- Proposal: one module per update kind (scenes, sources, mixer, outputs, recording, stream, filters) with `apply` as a short router. Do it in the same PRs as QS-04 and U-04.
- Effort: M. Risk: Low. Perf: U-04, U-05.

#### QS-06 rbs-record's Studio is the second god object
- Location: `crates/rbs-record/src/studio.rs` (5,377 lines; `struct Studio` line 1149 with 76 fields; `reconcile` 615 lines, `start_with` 295, `add_output` 293), plus `studio/transition.rs` (1,957).
- Problem: output planning, partitions, encoders and transitions share one struct; `reconcile` handles every output kind in one body.
- Proposal: split `reconcile` per output kind and give outputs, encoders and canvases their own state types. Do it as the first step of the performance audit's shared-producer work (R-01 = E-04, E-01), which rewrites the same code.
- Effort: M. Risk: Med (hot-path adjacent: P15 applies where the render tick is touched). Perf: R-01, E-04, E-01, G-01, G-07.

#### QS-07 Two composition roots list the same adapters by hand
- Location: `crates/rbs-app/src/platform.rs` (224 lines) and `crates/rbs-cli/src/platform.rs` (158 lines): the same registrations per platform, 98 differing lines after whitespace.
- Problem: a new adapter is added in two places; the CLI and the app silently differ (which encoders, muxers and decoders each registers). `rbs-mcp` will need a third copy.
- Proposal: one support crate (working name `rbs-platform`) that both roots call, with explicit flags for what differs (for example demo sources). `check-layers` gives it the App class.
- Benefit: one list; the CLI tests what the app ships.
- Effort: S-M. Risk: Low. Needs: ADR note (new crate in the layer table).

#### QS-08 Orphan crates and leftovers
- Location: `rbs-mux-flv` (no workspace crate depends on it, no root registers it); `rbs-plugin-host` (no dependent; status "Started"); `prototypes/` (552 KB, outside the workspace).
- Problem: they build and test with every workspace run and look like shipped features to readers.
- Proposal: register `rbs-mux-flv` (FLV recording) or remove it; keep `rbs-plugin-host` and say "not wired" in its crate doc; give `prototypes/` a README saying what is kept and why, or move it out.
- Effort: S. Risk: Low.

#### QS-09 A test adapter ships in the app
- Location: `crates/rbs-app/Cargo.toml`: `rbs-media-decode-test` is a normal dependency ("stand-in until FFmpeg ships"), registered last for every other file.
- Problem: a crate meant as a test double is part of the product. Its behaviour (a scripted picture) is what a user sees for an unsupported file.
- Proposal: a real "unsupported file" decoder in a product crate (an error the source shows in one sentence), and the test crate back to dev-only.
- Effort: S. Risk: Low.

#### QS-10 Shared numbers cause merge conflicts
- Location: `rbs-api/src/session.rs:116` `PROTOCOL_VERSION`, the scene format number, `docs/status.md`, `docs/adr/README.md`. Rule today: "whoever merges takes main + 1".
- Problem: every API change edits the same lines in four places; parallel branches always conflict there, and the last merge (#511) left conflict markers on main (QD-01).
- Proposal: change fragments (`docs/changes/api/<slug>.md`, `docs/changes/scene-format/<slug>.md`) and a `cargo xtask bump` run by the merger that assigns the next number, writes the constant and appends the spec section. ADR numbers keep being taken by hand but are checked (QN-05).
- Effort: S-M. Risk: Low.

#### QS-11 rbs-core is the root of almost everything
- Location: `rbs-core` (5,064 lines: media types, time and timing, pause, registry, capabilities). Its reverse closure is 69 packages.
- Problem: any edit to it selects almost the whole workspace in `cargo xtask affected`. Today it changes rarely, which is right.
- Proposal: no split now. Keep it stable: new shared helpers go into small helper crates (as `rbs-media-format` and `rbs-params` already do), not into `rbs-core`. Recheck its churn in the next audit.
- Effort: none now. Risk: none.

### Tests

#### QT-01 Copied test helpers
- Location: `fn gpu()` with the same body in 20+ test files (13 in `rbs-app/tests/studio_*.rs`, 6 in `rbs-nodes/tests/*_gpu.rs`, more in `rbs-gpu`, `rbs-capture-test`); the `RBS_REQUIRE_GPU` check in 77 places; `host_with`, `start`, `next`, `next_while` repeated across `rbs-app` tests.
- Problem: a fix to the helper (for example the lavapipe exit crash fixed in `rbs-gpu/src/exit.rs`) has to be found in every copy; copies drift.
- Proposal: a dev-only crate `rbs-test-support` (class Tool) with `gpu_or_skip()`, `require_env!`, update-waiting helpers with hang guards, and studio host builders. The host builders follow QS-01.
- Benefit: one helper to fix; shorter tests. Effort: S-M. Risk: Low.

#### QT-02 About 370 boilerplate allows in tests
- Location: 188 `#[allow(clippy::unwrap_used, ...)]` on `#[cfg(test)]` modules in `src/`, 178 crate-level allows in `tests/`.
- Proposal: a workspace `clippy.toml` with `allow-unwrap-in-tests = true`, `allow-expect-in-tests = true`, `allow-panic-in-tests = true`, then delete the allows. Check with clippy whether integration-test helpers outside `#[test]` functions still need a crate-level allow; keep it only where they do.
- Benefit: less noise in every test file. Effort: S. Risk: Low.

#### QT-03 Screenshot tools are compiled as test binaries
- Location: 9 `#[ignore = "a tool: writes screenshots for the owner's approval"]` tests in `rbs-app/tests/*_shots.rs` and `menus.rs`.
- Problem: each is a full `rbs-app` test binary (hundreds of MB, linked by every `cargo test -p rbs-app` and `affected test`) that never runs as a test.
- Proposal: one example or `cargo xtask shots <name>` that renders every shot set from one binary.
- Benefit: 9 fewer large links per `rbs-app` test build. Effort: S. Risk: Low. Perf: D-14.

#### QT-04 Too many rbs-app test binaries
- Location: 35 integration-test files in `rbs-app/tests`, 20 examples.
- Proposal: as the performance audit's D-14, group them into a few binaries (`tests/studio/main.rs` with one module per current file, `tests/ui/main.rs`). After QS-01 the studio ones live in the host crate.
- Effort: S-M. Risk: Low. Perf: D-14.

#### QT-05 Engine crates test adapters
- Location: dev-dependencies: `rbs-nodes` on `rbs-capture-mf`, `rbs-capture-wgc`, `rbs-codec-amf`, `rbs-codec-nvenc`, `rbs-transport-file`, `rbs-mux-matroska`; `rbs-sources` on `rbs-audio-io-wasapi`, `rbs-capture-mf`, `rbs-capture-wgc`; `rbs-record` on `rbs-codec-mf`.
- Problem: `cargo xtask affected` follows dev-dependencies, so an adapter change reruns engine tests, and engine tests break when an adapter changes. Tests about an adapter's behaviour belong with the adapter.
- Proposal: move adapter-specific tests to the adapter crate (using the engine as a dev-dependency there) or to one integration crate (`rbs-it`) that only the full run builds.
- Benefit: smaller affected sets for adapter work. Effort: M. Risk: Low.

#### QT-06 No property tests
- Location: no `proptest` or `quickcheck` anywhere, although CLAUDE.md asks for "property tests for pure logic".
- Proposal: add `proptest` (dev-only, fixed seed, case counts that keep each test in milliseconds) for: scene collection operations with undo (`rbs-scene` `perform`), time and rate arithmetic (`rbs-core` `time`, `timing`), bitstream conversion (`rbs-media-format`), muxer round trips, user-data format upgrades (`rbs-user-data`), layout (`rbs-ui` `layout`).
- Benefit: finds edge cases that example tests miss in exactly the code that parses, converts and undoes. Effort: M. Risk: Low (ADR-0032 fast-test rules still apply).

#### QT-07 Lock-free code without Miri or loom
- Location: `rbs-vcam/src/mailbox.rs` (`unsafe impl Sync`, slot `UnsafeCell`), `rbs-core/src/media/lease.rs`, `rbs-vcam-ring`, `rbs-capture/src/handoff/ring.rs`, `rbs-browser-shm`.
- Problem: their soundness rests on comments and example tests; a data race shows up as a rare crash on one machine.
- Proposal: a slow-tier job that runs `cargo +nightly miri test` on the pure crates (`rbs-vcam`, `rbs-vcam-ring`, `rbs-core`) and `loom` models for the mailbox and rings.
- Effort: M. Risk: none.

#### QT-08 Test tiers written for the future CI
- Location: `docs/specs/testing-strategy.md` (fast and slow tiers, hardware via `RBS_REQUIRE_*`).
- Proposal: name five tiers and what runs where, so the CI can be switched on later without new decisions: T0 while editing (`cargo test -p <crate>`), T1 before a push (`cargo xtask verify`, QN-01), T2 after a batch of merges (whole fast tier on Linux in the cloud), T3 nightly (slow tier, Miri, interop, GPU hardware on the owner's machines on request), T4 before a release (soak). Each tier lists its time budget.
- Effort: S (docs). Risk: none.

#### QT-09 Skipped GPU tests look like passes
- Location: every `gpu()` helper returns `None` without an adapter, and the test returns early unless `RBS_REQUIRE_GPU` is set.
- Problem: on a machine without a working adapter, a green run may have tested nothing on the GPU.
- Proposal: `cargo xtask affected test` sets `RBS_REQUIRE_GPU=1` where an adapter is known to exist (cloud containers with lavapipe, the owner's machines), and the shared helper (QT-01) counts skips and prints them at the end.
- Effort: S. Risk: Low.

#### QT-10 Benchmarks never run
- Location: 50 bench files; `docs/status.md`: "Performance budgets in CI: Not enforced".
- Proposal: covered by ADR-0143 R11 (measure, then budget). Here only: `clippy --all-targets` keeps them compiling; run them in tier T3.
- Perf: ADR-0143 R11.

#### QN-01 One verify command and a recorded result before every merge
- Location: `.github/workflows/ci.yml` runs only on `workflow_dispatch` for now (it becomes automatic again later, owner 2026-11-17); merges happen locally; CLAUDE.md lists seven separate commands.
- Problem: whether a rule holds depends on each agent remembering every command. Main at `ab90f27` has conflict markers that any check would have caught.
- Proposal: `cargo xtask verify`: `fmt --check`, `check-layers`, `check-ui`, `check-docs` (QN-05), and `affected clippy`, `affected test`, `affected doc`, `cargo deny` when the lock file changed. It prints one summary line with the commit hash and the selected crates, which goes into the PR body; the merger checks that the line matches the head commit. An opt-in `pre-push` hook (`git config core.hooksPath .githooks`) runs the quick part. When CI returns, CI runs the same command.
- Benefit: the rules hold without relying on memory; the PR shows what ran. Effort: S-M. Risk: Low.

#### QN-02 Pin the toolchain
- Location: `rust-toolchain.toml` `channel = "stable"`; `rust-version = "1.87"` (workspace), `"1.92"` (UI crates), never built.
- Problem: a new stable adds lints and turns main red without a code change (recorded: `rbs-cli` `function_casts_as_integer` at `interrupt.rs:89`, Windows `chunks_exact_to_as_chunks` at `rbs-app/src/thumbnail.rs:109`). Machines on different stables disagree.
- Proposal: pin an exact version (`1.97.0` today) and move it in its own PR that also fixes new lints. Either test the declared MSRV in tier T3 or set `rust-version` to the pinned version.
- Effort: S. Risk: Low.

#### QN-03 Lints to add
- Location: `Cargo.toml` `[workspace.lints]`.
- Proposal:
  - `#![forbid(unsafe_code)]` (or `unsafe_code = "forbid"` per crate lints) in every crate without unsafe today (46 of 90), so unsafe cannot appear in a pure crate unnoticed.
  - `clippy::allow_attributes_without_reason = "warn"`, and `#[expect(..., reason = "...")]` instead of `#[allow]` (0 uses today), so stale allows are reported.
  - `clippy::dbg_macro`, `clippy::todo`, `clippy::print_stdout` and `clippy::print_stderr` as warnings in library crates (13 `eprintln!` today; see QR-02).
- Effort: S each. Risk: Low.

#### QN-04 A size ratchet like check-ui
- Location: 11 files over 2,000 lines, 41 functions over 200 lines (non-generated).
- Proposal: `cargo xtask check-size` with a baseline file: counts of files over 2,000 lines and functions over 200 lines may only fall (`--lower`), a rise needs the owner's approval, as `check-ui` does. Generated code and `sys/` bindings are excluded. Runs in `verify`.
- Benefit: the god files stop growing while they are split. Effort: S. Risk: Low.

#### QN-05 check-docs
- Location: today: 3 broken relative links (`docs/adr/0078-...md` to `0065-global-sources.md`; `docs/architecture/hot-paths.md` lines 11 and 28 link `adr/...` instead of `../adr/...`), ADR-0076 missing from the ADR index, conflict markers in two docs (QD-01), 16 crates missing from the layer table in `docs/architecture/overview.md` and `rbs-transport-whip` listed but absent, CODEOWNERS hot-path list kept "in sync" with `hot-paths.md` by hand.
- Proposal: `cargo xtask check-docs`: relative links resolve; no conflict markers anywhere in the tree; every ADR file is in the index with the status of its header; every workspace crate is in the layer table and no absent crate is; CODEOWNERS covers every path in `hot-paths.md`; a Proposed ADR is not named as built in `status.md` or a spec's "As built" lines (see QD-03).
- Effort: S. Risk: Low.

#### QN-06 Say when a change touches a hot path
- Location: `docs/architecture/hot-paths.md` lists paths (`crates/rbs-audio`, `crates/rbs-gpu/src/download.rs`, ...).
- Proposal: `cargo xtask affected` and `verify` print "hot path: <path> (P15: numbers, hot-path-review, owner)" for changed files under those paths.
- Effort: S. Risk: none. Perf: ADR-0143 "How the rules are checked".

#### QN-07 One source for crate layers
- Location: the layer class of each crate is a `match` in `xtask/src/main.rs:443` and again a table in `overview.md`.
- Proposal: `[package.metadata.rbs] layer = "core"` in each `Cargo.toml`; `check-layers` reads it; `check-docs` compares the overview table with it.
- Effort: S-M. Risk: Low. Needs: ADR note (changes how layering is declared).

#### QN-08 Count unmarked visual literals in check-ui
- Location: rule 15 literals are already marked with `// literal: <why>`; only a few px literals are unmarked (`source_settings.slint:343`, `main_window.slint:1341,1343` `100000px`), apart from the colour picker's fixed palette in `components.slint`.
- Proposal: a sixth `check-ui` count, `literal`: a px, phx or hex colour literal in `crates/rbs-app/ui` outside token files without a `// literal:` comment on its line. Baseline from today's count.
- Effort: S. Risk: Low. Needs: owner OK for a new check-ui count (rule 18).

#### QN-09 Turn repeated procedures into skills

- Proposal: skills `add-api-method`, `add-setting` (settings file, row, API, settings search index), `add-source-type`, each listing the files in order and the checks. They shrink after QS-03.
- Effort: S each. Risk: none.

#### QN-10 A repeatable quality report
- Proposal: `cargo xtask quality-report` prints the numbers of this audit (sizes, long functions, allows, unsafe per crate, test binaries, copied helpers, reverse closures), so the next audit is a diff.
- Effort: S. Risk: none.

### Errors, robustness and unsafe

#### QR-01 Text errors in library crates
- Location: `rbs-user-data/src/document.rs` (`upgrade`, `from_body`, `to_body`, `body_of` return `Result<_, String>`; 34 in the crate), `rbs-ui` (17), `rbs-app` (131: 39 in `studio_host.rs`, 23 in `user_session.rs`).
- Problem: rule 8 asks for typed errors across boundaries; a caller cannot tell a parse error from a newer file format from an I/O error, and the API maps them all to `failed`.
- Proposal: typed errors in `rbs-user-data` (`DocumentError { Parse, Upgrade { from }, Io, ... }`) and `rbs-ui`; in the host (after QS-01), refusals with kinds that map to `ApiError` kinds. Text stays at the UI and CLI edge.
- Effort: M. Risk: Low.

#### QR-02 No diagnostics log
- Location: no `log` or `tracing` dependency; `rbs-app` reports with `eprintln!` (`main.rs:5562`, `5897`, `5903`, `5910`, `studio_host/protection.rs:35`, `text_live.rs:132`, ...).
- Problem: a desktop app started from Finder or the Start menu has no visible stderr, so these messages are lost; support has only crash reports.
- Proposal: a small diagnostics facility: levels, a fixed-size ring in memory and a rotating file in the user data folder, with zero cost when a level is off (P13) and nothing on real-time threads (a lock-free hand-off). Needs an ADR (a new cross-crate facility).
- Effort: M. Risk: Low.

#### QR-03 Unsafe outside adapters
- Location: `rbs-app` has 105 unsafe sites in `win/` and `native/` (Win32 caption, tray, Core Animation meter layer). Port crates `rbs-vcam` (mailbox) and `rbs-core` (lease) have a few, documented.
- Proposal: no move needed now (rule 7 allows marked low-level modules). Mark `win/` and `native/` as such in their module docs, and cover the port-crate unsafe with QT-07.
- Effort: S. Risk: none.

### Docs and ADR drift

#### QD-01 Main contains merge-conflict markers
- Location: `docs/specs/control-api.md:546-561` (protocol 1.88 and 1.89 sections) and `docs/adr/README.md:150-155` (rows 0140 to 0142), left by the merge of #511.
- Problem: readers see both versions; `rbs-mcp` compiles the control API spec into its tool catalogue, so the markers reach it.
- Proposal: fixed in the first commit of this PR (both sides kept). QN-05 prevents it.
- Effort: done. Risk: none.

#### QD-02 Specs and status are too large to read
- Location: `docs/specs/control-api.md` 243 KB (913 lines, the longest 7,899 characters), `ui-design-system.md` 276 KB, `recording.md` 171 KB; `docs/status.md` 22 KB with single cells over 4 KB; CLAUDE.md 12 KB. `ui-design-system.md` was edited by 20 of the last 50 merged PRs.
- Problem: every agent session reads them (context cost and slower work); people cannot skim them; large shared files are merge hotspots.
- Proposal: split the control API spec by namespace (`control-api/scene.md`, `source.md`, `record.md`, ...) with the index and versioning rules in the main file; split the design system spec by component group; one sentence per paragraph line; `status.md` rows at most two lines that link to the spec's "Implementation status" section (QD-04).
- Effort: M. Risk: Low (links need care; QN-05 checks them).

#### QD-03 Proposed ADRs implemented
- Location: ADR-0103 (source region), ADR-0104 (display chrome insets), ADR-0105 (timed show) are `Proposed` in their headers and the index; `status.md` lists them as "Partial", and the API has `source.set_region`, `source.set_chrome` and `item.show`.
- Problem: CLAUDE.md says a Proposed ADR is not implemented until reviewed and approved. Either the rule was skipped or the headers are stale.
- Proposal: the owner decides per ADR: record the review and accept, or mark the built parts experimental. `check-docs` flags it in future (QN-05).
- Effort: S. Risk: none.

#### QD-04 Accepted but not built, and where status lives
- Location: accepted ADRs with decisions not built, from `status.md` and the performance audit: ADR-0035 (native meter layers; only an example uses them), ADR-0088 decision 2 (replay buffer reuses the running encoder), ADR-0009 (budgets in CI), ADR-0038 exit criteria, ADR-0044 follow-up (JSON Schema), U20 parity, ADR-0006 (plugin loading: manifests only). 28 of 33 specs have no "Implementation status" section, although CLAUDE.md says that section wins over indexes.
- Proposal: an `Implementation:` line in every ADR header (`not started`, `partial: <what is missing>`, `done`) next to `Status:`, kept by the PR that builds it and checked by `check-docs`; an "Implementation status" section in every spec; `status.md` becomes a short table that links to both.
- Effort: M. Risk: none. Perf: U-03, E-01.

#### QD-05 Small drift
- CLAUDE.md calls `rbs-mcp` "planned, ADR-0052"; it exists and ships (ADR-0134).
- `status.md` calls ADR-0090 Proposed in one row and Accepted in another; the header says Accepted.
- `overview.md`: see QN-05; the performance audit adds tokio and `rbs-transport-whip`.
- Effort: S, in the `check-docs` PR.

## Already good

Keep these; do not redo them.

- Ports share one style: each has its own typed error (`CaptureError`, `EncodeError`, `MuxError`, `TransportError`, `AudioIoError`, `VcamError`, `DecodeError`, `TextError`), capabilities instead of vendor names, and a conformance suite behind a `conformance` feature that only dev-dependencies enable.
- `check-layers` classifies every crate and fails on an unclassified one; `check-ui` turns UI rules into counts with an owner-approved exceptions file; `affected` keeps per-change runs small; the edit hook runs `check-ui` for agents.
- Library code has 19 `unwrap`/`expect` outside tests; every `unsafe` block must carry `// SAFETY:` (deny lint); `unsafe_op_in_unsafe_fn` is denied.
- nextest: no retries, report at 15 s, kill at 60 s, GPU groups per platform with written reasons.
- `cargo deny` bans encode ADRs (no web views, CEF only in the browser runner, Slint only in the shell, rustls on ring).
- The UI crate split (ADR-0138) and live preview already cut the slowest edit loop; UI code uses tokens almost everywhere, with literals marked.
- English-only holds: the only non-English text found is test data.
