# ADR-0181: One RBS at a time, on every system

- Status: Accepted (2026-11-24)
- Date: 2026-11-24
- Deciders: Salih (owner)
- Amends: [ADR-0056](0056-keep-running-after-the-main-window-closes.md) decisions 6 and 9 (the second-launch event exists with either close setting), [ADR-0051](0051-user-data-profiles-and-scene-collections.md) decision 8 (the app no longer opens a read-only second instance), [ADR-0156](0156-ask-before-quitting-while-recording-and-stop-off-the-ui-thread.md) decision 7 (a launch while RBS is closing)

## Context

Whether a second launch opens a second RBS depends on the system and a setting today:

- Windows with Keep RBS running: the running RBS owns `Local\RBS.Show.<SID>` and comes forward (ADR-0056 decision 6).
- Windows with Quit RBS (the Windows default): a second RBS starts, read-only for user data (ADR-0051 decision 8).
- macOS: a Finder, Dock or Spotlight launch of the bundle reaches the running process (Launch Services). A binary started directly, or `open -n`, starts a second RBS.

Two copies collide beyond user data: remote control's fixed port (4456), the per-user control channel (ADR-0044), the global shortcuts (Ctrl/Cmd+1..9), cameras that one process may open at a time, and the virtual camera. RBS already does in one copy what other tools need two copies for (a vertical canvas, several outputs).

The owner decided on 2026-11-24: RBS runs as one copy for now; running several copies is parked. The analysis is in the project thread "Find app behaviour that differs by OS".

## Decision

1. **One RBS per settings folder, on Windows and macOS, with either close setting.** The settings folder is `config_dir()` (`RBS_CONFIG_DIR` included). First thing in `main`, before the diagnostics log, the crash marker and any user data, `rbs` creates the folder if needed, opens `instance.lock` there without truncating it and takes an exclusive lock (`File::try_lock`), held until the process ends; the system releases it however the process ends. `rbs-cli` and `rbs-mcp` do not take it. A lock that fails for another reason than another holder (a network home without locks, a read-only folder) is logged as a `warn` once the log runs, and RBS starts as today.
2. **macOS: the running RBS says what it is doing in `instance.state`**, a small file beside the lock that is never locked. Right after taking the lock it deletes any leftover state. It writes `running <pid> <executable path>` only after `route_show` succeeded (the reopen handler exists and AppKit receives events), and `closing <pid> <executable path>` on the UI thread when Quit is decided, before the windows hide (ADR-0156 decision 4; outside the budgeted `shutdown::STEPS`), each written whole through a temporary file and a rename; a failed write is logged and ignored. A missing, empty, partial or unreadable state, or one whose pid does not run the same executable path, means "starting". Windows does not need the file: a missing event already tells it apart (decision 3).
3. **A launch that cannot take the lock asks the running RBS to show its main window and ends.** It starts no log file, reads or writes no user data, writes no crash marker and opens no device. Exit code 0 when the running RBS answered.
   - Windows: the running RBS creates the named event `Local\RBS.Show.<SID>.<folder>` right after taking the lock, in every mode, waited on in the system wait pool (no thread, no polling). A signal that arrives before the main window exists needs nothing more: RBS never starts hidden, so the window is about to show. `<folder>` is the 64-bit FNV-1a hash of the canonical settings folder path (`fs::canonicalize` after the folder exists), lower-cased, as 16 hex digits. The launch calls `AllowSetForegroundWindow(ASFW_ANY)` and sets the event.
   - macOS: a bundled RBS started from Finder, the Dock or Spotlight never gets here, because Launch Services already turns that launch into a reopen of the running app. Only `open -n` and a binary started directly do. Such a launch reads `instance.state`; when it says `running`, it asks the running app to reopen: `NSWorkspace openURL:` with the running app's bundle URL (no consent needed), or, for an unbundled development build, the reopen Apple event (`kAEReopenApplication`) to the pid. macOS may attribute that event to Terminal and ask once or refuse it (-1743); a refusal falls through to the wait of decision 4 (development only). Either reaches `applicationShouldHandleReopen:`, which shows a hidden main window (ADR-0056 decision 6) and, when the window is shown, brings it to the front. The Apple event is never used by a signed, hardened build, so no Automation entitlement or consent prompt is needed. Activation by `NSRunningApplication` is not relied on: since macOS 14 another process may be refused it.
4. **When the running RBS is closing or does not answer yet**, the launch waits for the lock for at most 15 s (the shutdown budget, the sum of `shutdown::STEPS`, is 12 s). While it waits it tries the signal of decision 3 again every 500 ms (Windows: the event exists again; macOS: the state reads `running`) and ends with exit code 0 at the first signal that was delivered; a closing RBS is not signalled. This loop runs only in a launch that is about to end or start, never in a running RBS, so P13 is not touched. When the lock comes free, RBS starts normally. On timeout the launch shows a system message box through `rfd::MessageDialog` (already used for file dialogs; `MessageBoxW` on Windows, an alert on macOS), "RBS is already running but did not respond. Try again in a moment.", in English like the app's other texts made in Rust until those have a translation catalog (U8), and ends with exit code 1. The message box is a visible change and goes to the owner with the implementation (rule 16).
5. **Linux keeps today's behaviour** (a second, read-only instance, ADR-0051 decision 8) until there is a way to reach the running RBS there. Known limit.
6. **The tray icon is unchanged:** it exists only while Keep RBS running is set (ADR-0056 decision 9). The event of decision 3 is dropped when closing starts, as today; it costs one kernel event and one wait registration and runs nothing until signalled.
7. **Running several copies is parked.** Two settings folders (`RBS_CONFIG_DIR`) are a developer-only, unsupported setup: remote control's port, the control channel (`rbs-control-<SID>` on Windows, `$TMPDIR/rbs/control.sock` on macOS) and the global shortcuts are not per folder and still collide. An older build that is still running during an upgrade holds no `instance.lock`; the new launch then starts and works read-only through `user-data.lock`, as today.

Known limits: for up to 15 s before that message box the user sees nothing. On Windows a launch that signals just before Quit drops the event (ADR-0156 decision 4) ends with exit code 0 and no window; launching again after RBS has ended starts it. On macOS a Finder, Dock or Spotlight launch while RBS is closing reaches the closing process as a reopen, which ADR-0156 decision 3 ignores, so no new RBS starts until the user launches again. On Windows the same user signed in to two sessions shares `%APPDATA%` but not `Local\` events, so the second session gets the message box of decision 4.

## Consequences

- One behaviour on Windows and macOS: a second launch brings the running RBS forward, and never leaves the user without either a window or a message.
- Ports, the control channel, shortcuts, cameras and the virtual camera no longer meet a second copy of the app on the same settings folder.
- `cargo xtask device-check app` reports "another RBS is running" instead of a passing run when the lock is held.
- Tests (milliseconds, no device, no sleeps): a second `claim` of the same folder is refused while the first is held and succeeds after it is dropped; a lock error other than contention starts normally; the folder key is the same for different spellings of one folder and stable across builds; the state file round-trips `running`, `closing`, empty and partial content (partial = starting); the wait of decision 4 ends when the first claim is dropped, driven by a channel, not by time.
- Device check on the Mac (macOS 14 or later, the signed hardened bundle started with `open -n` as well as `target/debug/rbs`) and SC-PC: with Quit RBS set and with Keep RBS running set, a second launch brings the window forward (hidden and shown); a launch during Quit starts RBS once the first has ended.
- Specs: `ui-design-system.md` "Bring an open window forward" and `user-data.md` (second instance) are updated in the implementation change.

## Alternatives considered

- **Use the user-data writer lock (`user-data.lock`) as the instance lock.** The app takes and drops it for short writes (`reset_appearance`, `forget_deleted_themes`), and on Unix two `flock`s of one file in one process conflict, so holding it for the whole session would break those paths. A separate file keeps both meanings clear.
- **Use the control API's IPC to ask the running copy** (as ADR-0056 already rejected): it exists only while remote control is on and needs a token.
- **Activate the running app with `NSRunningApplication` on macOS:** may be refused since macOS 14 (cooperative activation), and does not show a window hidden while RBS is the active app.
- **A named mutex on Windows and nothing on macOS.** Leaves the systems different, which is what this ADR removes.
- **Allow several copies with a warning, as OBS does.** The owner parked it; the collisions in Context would each need their own answer.

## Review

- 2026-11-24, independent AI session (ADR, specs, code): changes requested, 4 blocking and 6 minor concerns. Resolved in this text: a closing RBS is told apart by `instance.state` (decision 2), not by a missing process; the event is created right after the lock, a signal before the event loop is kept, the folder key hashes the canonical path, the launch signals again while it waits and shows a message box on timeout instead of ending silently (decisions 3 and 4); macOS uses the reopen Apple event instead of activation (decision 3); Linux keeps today's read-only second instance (decision 5); lock errors other than contention, folder creation, no truncation and why the state is a separate file (decisions 1 and 2); Finder launches while closing and two Windows sessions are known limits; the launch starts no log file; developer-only second folder and the upgrade case (decision 7); tests for the state file and path spellings.
- 2026-11-24, same independent AI session, round 2: changes requested, 3 blocking and 3 minor. Resolved in this text: stale state is deleted after the lock and `running` is written only once the reopen handler exists, with the executable path checked against the pid (decision 2); a bundled build uses `NSWorkspace openApplicationAtURL:` and the Apple event only for unbundled development builds, so no Automation consent (decision 3); the wait ends at the first delivered signal (decision 4); message box APIs and translation, the state file is macOS-only and its failed writes are ignored, the closing write moves to the shutdown thread, the late-signal case on Windows is a known limit.
- 2026-11-24, same independent AI session, round 3: approve, with 4 minor points, all fixed in this text: `closing` is written on the UI thread when Quit is decided and outside the budgeted steps; the development-only consent prompt falls through to the wait; the device check includes the signed bundle with `open -n`.
- 2026-11-24: Accepted by the owner (Salih) on a decision card, after the review above.
- 2026-11-24, implementation: two facts corrected in place (D1): the message box goes through `rfd::MessageDialog`, and a signal before the main window exists is not kept, because the window is about to show anyway.
- 2026-11-24, implementation risky review (independent AI session): no blocking findings. One fact corrected in place (D1): the bundle path calls `NSWorkspace openURL:` (synchronous, the same Launch Services reopen) instead of `openApplicationAtURL:`, which needs a completion block; whether it can pick the `open -n` caller itself is part of the Mac device check. Code fixes: an autorelease pool per try, canonical executable paths, a 0.5 s Apple event timeout, the Windows show event kept when its name already exists, and the set-up warnings logged once the log runs.
- 2026-11-24, Mac check: a hidden or minimized RBS did not come back after `open -n`, because opening the bundle URL can reach the new launch itself. Corrected in place (D1): the launch sends the reopen Apple event to the running RBS's pid first, for a bundle too; only if that is refused does it unhide the app (no consent needed) and open the bundle URL. The second Mac check found the hidden or minimized RBS came back behind the app in front: a reopen Apple event brings no activation, so the reopen handler now also activates RBS (best effort; macOS 14 may decline it).
