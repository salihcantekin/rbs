# ADR-0117: Record still sources separately as images, not video

- Status: Accepted (2026-11-14)
- Date: 2026-11-14
- Deciders: Salih (owner)
- Amends: [ADR-0086](0086-recording-sources-separately-iso.md) decisions 2, 3, 6 and 7 (separate files), without changing what it says about moving sources
- Related: [ADR-0087](0087-output-cost-estimate-and-hardware-limits.md) (cost estimate), [ADR-0038](0038-io-graph-nodes.md) (readback, the P4 exception), [ADR-0039](0039-scene-source-types.md) (source types), [ADR-0062](0062-built-in-video-filters-and-properties-tabs.md) (filter chains), [ADR-0074](0074-still-image-and-colour-sources.md) (image sources)
- Spec: [recording](../specs/recording.md), [io-nodes](../specs/io-nodes.md), [scene-model](../specs/scene-model.md), [control-api](../specs/control-api.md)

## Context

ADR-0086 gives every source marked *Record separately* for its picture a video file at the canvas frame rate. That fits a camera or a screen capture. It does not fit a source whose picture does not change on its own: an image, a colour or gradient card, and later text or a shape. Step 3.2 of ADR-0086 showed the problem directly:

- The first Mac measurement (2026-11-14, M4 Pro) wrote a one-frame file for each colour source, because the export took a canvas only when it changed. After the fix that repeats the picture on every tick, a still source costs what a camera costs: a GPU conversion and readback, an encoder session, and one identical frame per canvas tick (1,800 per 30 s at 60 fps). On the M4 Pro the hardware encoder is shared, so four such files made the master skip about 20 % of its frames before the yield rule of step 3.2 (see the 3.2 measurements in the PR).
- An editor gains nothing from that video. A logo, a lower-third card or a background is used in an edit as a single image layer, usually with transparency. A video file loses the transparency: the encoders carry no alpha, so ADR-0086 decision 3 composites alpha over black.
- The built-in types already know which sources are still: `rbs_sources::SourceClass::Still` (image and colour). Video filters cannot animate on their own: `FilterType::uniforms` takes the values and the input size, never the time, so a still source's chain tail changes only when its settings, its filters or its input change.
- But nothing on the link says *that* it changed: a still source stamps its frame `Timestamp::ZERO` with sequence 0 (`rbs-nodes` `still.rs`), and the filter node passes the input's timestamp on and sets no sequence. A change in a colour or a filter value gives the same `(timestamp, sequence)` as before.
- `RecordSeparately` today holds only `video` and `audio`; the per-track options of ADR-0086 decision 2 (`exclude_filters`, `size`, `max_height`, `frame_rate`) are not built yet.

Forces: zero cost when unused and as little cost as possible when used (P13, rule 17); capabilities, not type names, in engine code (P3); no I/O, encoding or allocation on the render thread (P6); the master is never degraded (ADR-0086 decision 9); the owner wants per-source choices exposed as settings.

## Decision

1. **A picture track has a form: video or image.** `RecordSeparately` gains `video_as: auto | video | image`, next to the per-track options of ADR-0086 decision 2 when those are built. The default is `auto`. A scene file that holds a value other than `auto` is written with the next free scene format number (18 at the time of writing; assigned at merge), as other optional fields are; a file without one keeps its number, and an older build refuses a newer file with the usual upgrade error rather than a parse error. `auto` resolves at the start of each take: `image` when the source is still (decision 2), otherwise `video`. `video` always gives a video file (ADR-0086 unchanged). `image` is accepted only for a still source; for any other source it is refused (`IsoError::ImageOnMovingSource`, `invalid_params` in the control API; `IsoError` becomes `#[non_exhaustive]` in the same change, a breaking change of `rbs-record` noted in the changelog), because a camera written as images would be a slideshow at a capped rate, not a track.
2. **What counts as still.** A source is still when its type is still and nothing else in its chain makes the picture move. The type must declare it: for built-in types, `SourceClass::Still`. The rule for that class (written into its spec): the type has no time input and no decoder clock, so its picture changes only when its settings or files change. Image and colour qualify; an animated image (GIF, APNG) and a text source with a clock or ticker never do, and a later text or shape type qualifies only in its static form. A plugin type is not still until the plugin SDK can declare it (a later SDK minor with its own review); until then `auto` gives a plugin source a video file. Engine and record code ask the class, never compare type ids. Every built-in video filter keeps a still source still, since filters take no time input. `FilterType` is also the plugin filter trait, so a future time-dependent filter is declared by a new trait method with a default of "no time input" (not a breaking change); a chain with such a filter enabled is not still.
3. **What an image track writes.** The source's picture after its filters (the same chain tail as a video track, ADR-0086 decision 3), at the source's own size. The images are PNG, 8-bit sRGB, with straight (not premultiplied) alpha, so the transparency of a logo or a keyed picture is kept. This applies to image tracks only. `exclude_filters` applies as for video. `size: master` gives an image of the master recording's size with the picture fitted and centred and the area around it transparent, not black. `max_height` caps the size as for video. `frame_rate` does not apply.
   - The first image is the picture at the start of the take, named `<name>.png`.
   - When the picture changes during the take (a setting, a filter, a new file behind an image source, a size change), a new image is written, named `<name>-<n>.png` with `n` counting from 2. There is no fixed size to keep, so a size change needs no scaler.
   - Changes are coalesced: at most one image per 100 ms (`MIN_IMAGE_INTERVAL`). A change inside that window is written at the window's end, showing the picture as it is then. The number of images per track per take is capped at `MAX_IMAGES_PER_TRACK` (1,000). Changes past the cap are not written; they are counted, and the manifest says so.
4. **How a change is seen.** A video frame's `sequence` becomes a generation for these two producers, unique across node instances: each time the still source node uploads (a new instance after a colour or file change, or a warm) and each time the filter node re-renders (a new input, new values, a new size), the node takes its frame's sequence from one process-wide counter (`rbs_core::media::next_generation()`, beside `VideoFrame::with_sequence`, so `rbs-nodes` and `rbs-filters` need no new dependency; one relaxed `fetch_add` on an `AtomicU64`: lock-free and allocation-free, P6). A node built anew by the binder therefore never repeats a key an earlier instance published. The image track compares `(timestamp, sequence)` as the master's export does, and with that contract the pair changes exactly when the picture does. This is a contract change in `io-nodes.md` and needs no new field.
   - When the binder rebuilds the chain (a filter added or removed, a new source instance), the image track node itself is kept and keeps its last key. The rebuilt chain's first frame has a new generation, so it is written as a new image. A rebuild that changed nothing visible therefore writes one duplicate image; that is acceptable and counted (`rebuilt`).
5. **Where the work runs.** On the render partition the image track is one node after the chain tail. On a tick where the key is the one it last took, it does nothing more: one compare. When the key changed, the interval allows it and the previous image's readback has finished, the node converts the picture and starts one readback. A change that finds the readback busy, or falls inside the interval, is kept pending and taken on a later tick (counted in `coalesced`, never lost unless the take ends first). The track also obeys the give-way rules of ADR-0086 decision 9 (a long render tick, or a drop on the way into a master encoder): a change is then retried on the next tick, since an image track has no frame to lose.
   - **A new readback path, `RgbaDownload`** in `rbs-gpu`, beside `YuvDownload`: one pass that un-premultiplies the chain tail's premultiplied linear `Rgba16Float`, encodes sRGB and writes RGBA8, then a non-blocking readback. An unfiltered still source's output is already `Rgba8` sRGB with straight alpha: it is read back directly, with no conversion pass and no normalisation pass. It is a new hot-path item (`hot-paths.md`) with its own P15 sign-off, and it widens the ADR-0038 readback exception to "once per picture change" for image tracks.
   - **One staging buffer per track**, sized when the track starts, in `prepare`, for the picture's size then. A larger picture during the take gets a new buffer under the ADR-0062 decision 5 exception (at most one buffer creation per size change, never on a steady tick); a smaller one reuses the buffer. The memory (4 bytes per pixel per track: 33 MB for a 4K picture) is part of the ADR-0087 estimate.
   - A completed readback goes as a frame to a writer node on `ISO_OUTPUT`, which encodes the PNG and writes the file through the transport, as the audio and video files do. Encoding and file I/O never run on the render thread.
   - **The writer lives in `rbs-record`** and uses the pure-Rust `png` crate already in the tree for image sources (ADR-0074). It is not behind a port in the first version: PNG is one format with no vendor or OS code, and the writer is one module, so swapping it means replacing that module. If a second image format is wanted (lossless WebP, 16-bit PNG for HDR), an image-writer port comes with it, with its own ADR.
   - An image track adds no encoder session and no encoder partition, and it is not counted in `MAX_ISO_VIDEO`. It has its own limit, `MAX_ISO_IMAGES` (32 tracks).
6. **Manifest.** An image track is a file entry with `role = "image"`, its `source` and `source_name`, and an `images` list. Each element has its file `name`, `width`, `height` and `at_ns`: the time from `t0` of the render tick on which that picture was taken (the tick's time, never the frame's timestamp, which is zero for a still). The first is the first tick at or after `t0`. When changes were coalesced, the image shows the picture as it was on that tick. At stop the entry gets `coalesced` and `over_cap` counters. Editors and the project export of ADR-0089 place each image as a still from its `at_ns` to the next image's `at_ns`, or to the end of the take.
7. **Cost estimate.** ADR-0087 counts an image track by what it holds and does: its staging buffer in memory, no encoder, one conversion and readback per change, and a PNG write on the output worker. Per tick it is one compare, so its CPU and GPU share is near zero for a picture that does not change. The estimate shows image tracks on their own line, so the user sees that marking a logo costs nothing like marking a camera.
8. **Control API and UI.** `source.set_record_separately` gains `video_as` (same patch rules as the other per-track fields of ADR-0086 decision 11; next free minor at merge). In Properties, a still source's *Record separately* row shows a compact dropdown next to the toggle, *Automatic (image)*, *Image* and *Video*. A moving source shows no such control, since it has only one choice. The Separate files card and the Outputs card name image tracks as images. The visual design follows the UI approval rule before it is built.
9. **Zero cost (P13).** No image track: no node, no staging buffer and no writer state. While one runs, a tick on which the picture did not change costs one compare on the render thread and nothing elsewhere.

## Consequences

- A marked logo, card or background costs almost nothing during a take, instead of a video encode at the canvas rate. The editor gets a transparent PNG layer, which an encoded video file cannot carry. This is something OBS cannot give at all.
- Image tracks change ADR-0086's manifest (a new role and the `images` list) and the scene format (`video_as`, written only when it is not `auto`). Both need the usual compatibility notes.
- A new node pair (image export on render, PNG writer on `ISO_OUTPUT`) and `RgbaDownload` are hot-path additions. They need the P15 measurements: 0, 1 and 4 image tracks against the 3.2 video numbers, a still source and a source whose settings change every frame (to show coalescing).
- The filter node's and the still node's output gain a generation sequence. The master's export reads the canvas, which the compositor stamps with the tick index, so it is unaffected.
- `rbs-record` gains a direct `png` dependency (pure Rust, already in the tree).
- Follow-ups: `recording.md` (image tracks, manifest), `io-nodes.md` (image export and writer nodes, the filter node's output sequence), the GPU spec (`RgbaDownload`), `hot-paths.md`, the source types spec (the `Still` rule), `scene-model.md` (`video_as`), `control-api.md`, ADR-0087's estimate table, the UI proposal, and a plugin SDK minor for declaring a still type.
- Until this is accepted and built, a still source marked for its picture gets a video file, as ADR-0086 says.

## Alternatives considered

- **Keep video for every source (ADR-0086 as is).** Simple and uniform, but it spends an encoder session and a per-tick conversion on pictures that never change, and the transparency is lost.
- **Video for still sources, written only when the picture changes (variable frame rate).** Saves encode time, but many editors handle VFR files badly, alpha is still lost, and the file is still a video where an image is wanted.
- **Encode video with alpha (ProRes 4444, VP9 with alpha).** Keeps the transparency, but it needs encoders the platforms do not all offer, the files are large, and it still encodes repeated frames.
- **Decide by type id in the record code.** Rejected by P3. The class lives in the source registry, and plugins get a declaration, not a list of names.
- **Encode from the decoded pixels on the CPU** for an image source with no enabled filter (the still node holds them): no GPU pass at all. A good later optimisation for that one case, but it needs a second path for colour sources and for any filter, so the first version uses the chain tail for every image track.
- **Allow `image` on any source (snapshots of a camera).** A rate-capped slideshow is not a useful track and would surprise users. A snapshot feature, if wanted, is a different decision.

## Review

- 2026-11-14, independent AI session (round 1, given only the ADR, the referenced ADRs, specs and code): changes requested, 4 major (no change signal on still chains, no RGBA readback path, staging buffer size and memory undefined, the writer's layering left open) and 5 minor plus 2 nits (scene format number, `IsoError` semver, give-way rule, CPU fast path, the `Still` rule and the filter trait, frame counts at 60 fps, `at_ns` under coalescing). All resolved in the text above: decisions 4 and 5 (change signal, `RgbaDownload`, buffers, writer in `rbs-record`), decision 1 (format number, `non_exhaustive`), decision 2 (`Still` rule, trait default), decision 6 (`at_ns` is the capture tick), the fast path under Alternatives. 
- 2026-11-14, same reviewer (round 2): changes requested, 1 major (a per-instance count repeats after the binder rebuilds a node), 1 minor (the unfiltered `Rgba8` input), 1 nit, and one wrong sentence in Consequences about the master export. Resolved: decision 4 takes generations from one process-wide counter and says what a rebuild does; decision 5 reads unfiltered input back directly; Consequences corrected.
- 2026-11-14, same reviewer (round 3): approve with one minor change (the counter must live in `rbs-core`, since `rbs-filters` does not depend on `rbs-nodes`); applied in decision 4. Verdict: approve. Waiting for the owner's acceptance.
- 2026-11-14, owner (Salih) approved acceptance after the review. Status: Accepted.
- 2026-11-14, implementation (ADR-0119 step (b3)): the owner chose to write the PNG files directly into the take folder, as the manifest is written, instead of through a transport (decision 5 says "through the transport"). Transports carry container streams; a transport for single images would need a new `ContainerId` and its own review. The writer still runs on `ISO_OUTPUT`, never on the render thread.
- 2026-11-18, render on change (R-03 of the November 2026 performance audit, ADR-0143 R5): the Consequences line "the compositor stamps with the tick index" no longer holds. The compositor now draws only when its inputs change and stamps each drawn canvas with `next_generation()`, the counter of decision 4; an unchanged canvas keeps its timestamp and sequence. The master's export repeats an unchanged canvas as a new frame stamped with the tick's time and a new sequence, so the encoder still gets one frame per tick (`gpu-compositor.md`, "Render on change"; `io-nodes.md`, video export). Decision 4 itself is unchanged.
