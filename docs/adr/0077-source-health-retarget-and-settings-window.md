# ADR-0077: Source health, re-picking a source's target, and the Source settings window

- Status: Accepted
- Date: 2026-11-08
- Deciders: Salih (owner)
- Builds on: ADR-0039 (scene source types), ADR-0038 (I/O nodes, `prepare` finds a lost target), ADR-0062 (filters survive a settings change), ADR-0049 (workspace, floating windows), ADR-0057 (themes), ADR-0013 (zero cost when unused)

## Context

The owner added a Window capture of a terminal and closed the terminal. Today the source row then shows red text ("Not running: ..."), nothing says in plain words that the window is gone, and there is no way to point the source at another window: the only option is to delete it and add a new one, which loses its name, layout, filters and place in other scenes. The same holds for every source: a camera that was unplugged, a microphone that changed, a display that was removed.

OBS Studio has a Properties dialog per source (window, camera, microphone, ...), where the target is changed and device-specific options live (a camera's resolution, frame rate and format, its device controls). RBS has the pieces (settings keys `adapter`/`target`/`width`/`height`/`fps`, the binder keeps filters when settings change, `Command::ListTargets`, OS pickers) but no UI or control API that edits an existing source's settings.

Forces: rule 15 and U6 (tokens only), rule 16 (visual change approved before merge), P13 (a source that is not shown is not opened, and nothing may poll for a lost source without need), U20 (every UI action has a control API command), the preview must never disappear when a dialog opens.

## Decision

1. **Source health is a state, not a message, and it is typed end to end.** Today the reason is a string: `rbs-nodes` capture collapses capture errors into `NodeError::Permanent(&'static str)` and the app keeps `Failed(String)`. This ADR adds a typed carrier, `SourceFault { TargetGone, PermissionDenied, Busy, Other }` (non-exhaustive), defined in `rbs-core` next to the capability model, produced by `rbs-nodes` through a change of `NodeError` in `rbs-graph` (a core API change that needs the rule 11 review: `Permanent` and the recoverable `Backend` error both gain an optional fault). Full mapping of `CaptureError`: `TargetNotFound` and `TargetLost` -> `TargetGone`; `PermissionDenied` and `PermissionNotDetermined` -> `PermissionDenied`; `DeviceBusy` -> `Busy`; every other variant -> `Other`. **Retry rule:** the port spec says `TargetLost` and `DeviceBusy` are recoverable with engine back-off retry. That stays, with one change: after three failed retries (back-off as today) the node reports its fault and the source becomes `Unavailable`; the engine then stops retrying until the user acts or the source is shown again (P13). A closed window therefore reaches `TargetGone` after the retries, with no endless polling. The port spec (invariant on `TargetLost`) is updated in the same change, by `rbs-sources::instantiate` for audio endpoints (`SourceError::Audio(EndpointNotFound)` -> `TargetGone`), and read by the studio state into `SourceStatus::Unavailable { fault, detail: String }` next to `Running`, `Idle` and `Failed`. `detail` is the adapter's own text for display and logs only; no code branches on it (P3). An audio source that failed at `instantiate` has no node: the host keeps it in the scene with status `Unavailable` and tries `instantiate` again on every settings change of that source (decision 3), which is the same path as a new source. Adapters that cannot tell the cause report `Other`. Phase (b) therefore touches `rbs-graph`, `rbs-core`, `rbs-nodes`, `rbs-sources`, `rbs-api` and `rbs-app`, and the capture port spec gets a short note on which errors map to which fault.
   The reason text is never fixed: it comes from the reason and the source type, in plain words. For example: window "Window closed"; display "Display disconnected"; camera "Camera unplugged", "Camera in use by another app" or "Camera access denied"; microphone "Microphone not found" or "Microphone access denied"; application audio "Application not running"; image "File not found". A reason with no known wording shows the adapter's own message (`Other`).
2. **How an unavailable source looks.** In the Sources panel the row is dimmed (`Theme.text-disabled` name) and shows a small warning icon (`Theme.state-warning`, a library icon, 16 px token size) in front of the type icon, with the reason as a tooltip and accessible label, and a one-line second row with that reason and a text button "Choose another..." The coloured sentence is removed. Colour is never the only signal (U-rules): the icon shape and the text carry it. In the picture panel the item keeps its frame and handles (dashed outline, token) and shows a centred icon and the reason, drawn by the UI layer, not the compositor, so the compositor gets no new per-frame branch (P6, rule 10). Audio rows show the same icon in place of the level meter. High-contrast uses `state-warning` as defined by the theme.
3. **Re-pick for every source type.** "Source" is the first tab of Properties (before Transform), shown for every source with a device or file: a target list for the type (displays, windows, cameras, input devices, output devices, applications; an image's file; a colour is edited there too) with a Refresh button and the adapter's "Choose..." entries (OS pickers). Choosing a target sets the `adapter` and `target` settings of the same `Source`. Name, id, items in every scene, layout, filters, volume and global flag stay. The binder already treats a settings change as a replaced source with break-before-make (scene-sources spec, step 6), so an exclusive camera works. One re-pick is one undo step (`EditKind::Retarget`).
3a. **The target list is built for finding things.** It has a search field (case-insensitive match on the target's name and application, as you type, no work beyond filtering the already listed targets), a "Recent" group first (the last targets the user picked for this source type, up to five, kept in the user's settings, newest first, listed only while they still exist; a lost target is not shown there), groups ("Same application", then by application), and for windows and displays a small preview picture in front of each name, at a token size (`size.target.thumb-w` and `-h`, not themeable, about 96 x 54). A thumbnail is one frame grabbed on demand, one per visible row, only while the list is open, kept until it closes, and fetched off the control thread; nothing is captured when the list is closed (P13). It needs a new method on `CaptureFactory` (so it works without opening a session): `thumbnail(&self, target: &TargetId, max: Size) -> Result<Thumbnail, CaptureError>`, default `Unsupported`, a minor port version with its own spec change, conformance tests in `rbs-capture-test` and the architecture review of rule 11, as a separate change before phase (c2b). `Thumbnail` is a small owned RGBA8 CPU image, at most 192 x 108 (about 80 KiB): a bounded, deliberate exception to P4 because it is never on the frame path and is a one-off picture for browsing. The host runs at most two grabs at a time off the control thread, each with a 1 s timeout and cancelled when the list closes or the row scrolls away (the list is virtualised, so 50 windows cost only the visible rows), and drops all thumbnails on close. Thumbnails are UI-only: not in the control API, not logged, not in crash dumps, never stored, and RBS's own windows are skipped. Adapters implement it in this order: ScreenCaptureKit, Windows Graphics Capture; the PipeWire portal lists nothing, so it returns `Unsupported`. On macOS a grab needs the screen-recording permission the user already gave for capture; with no permission the list shows icons and no prompt is triggered by browsing; rows of adapters that return `Unsupported`, or whose frame is not ready, show the type icon. Cameras and microphones get no preview: grabbing a camera frame would open the device and light its privacy LED just to browse a list. Minimised or hidden windows may have no frame; they show the icon too. Thumbnails need the same screen-capture permission as the source itself and are never stored or sent anywhere.
4. **Suggestions for a lost window or device.** For an unavailable window source, the list opens with "Same application" first: windows of the application that the old target belonged to, found by the application name stored with the target (`target_app` and `target_title`, written when a window is added or picked, for the label "was: zsh - Terminal"). These two are **hints, not settings**: they are stored in `Source.hints` (a new optional map in the scene document, format version bump, older builds drop it on save), so the binder's comparison of settings does not see them and updating them never restarts a device. A re-pick replaces both with the new target's. Display, camera and audio sources store `target_title` only, and "Same application" applies to windows and application audio. Matching is by application name, case-insensitive, never by process id. Other types list the current targets as usual. The suggestions use the adapter's `enumerate`, on the control thread, only while the Source tab is open or the user presses Refresh: no polling (P13).
5. **No automatic reconnect in this ADR.** OBS and others re-find windows by title in the background. That needs polling or OS notifications and a matching rule that can pick the wrong window. It is left as a later opt-in setting ("Reconnect when the window comes back", off by default), event-driven where an adapter can say so (capture port addition) and otherwise a slow poll that exists only while a source is unavailable and shown. It needs its own decision.
6. **The Source settings window.** A floating window (ADR-0049, one per source, reused if open) opened by double-click on a source row, by "Source settings..." in the row's context menu and by a button on the Source tab. It is never modal and never covers the preview by design: it opens beside the main window's centre of attention, placed by the same window placement rule as the Settings window, so the picture panel stays visible. It has the sections that apply to the source type, in a fixed order, built from a declarative description (`SettingsSchema`: sections of typed fields: choice, number with unit, toggle, text, file, colour) provided by `rbs-sources` per type, so a plugin source type can describe its own fields later (plugin SDK; this ADR defines the schema for built-in types only):
   - **Source**: target, as in decision 3.
   - **Video** (display, window, camera): size and frame rate (`width`, `height`, `fps`), for cameras the list of modes the device offers (`CameraMode` of the capture port: size, pixel format, rate range; the app's list of modes per target already comes from `enumerate`, so no port change), "Draw cursor" for display and window.
   - **Audio** (microphone, system, application): device and the sync offset (already a setting).
   - **Device controls** (cameras: exposure, white balance, focus, zoom ...): not in this ADR; it needs a capture port extension (capabilities per control, P3) and its own ADR. The section is absent, not disabled, until then.
   Edits are held in the window and applied with **Apply** or **OK** as one undo step (`EditKind::Retarget`; filters, volume and mute are untouched, and values changed live in Properties while the window is open are not part of the step); **Cancel** drops them. If the new target fails to open, the settings stay applied and the source shows `Unavailable` with the reason, and Undo restores the previous settings; the window says so in plain words. The window follows ADR-0049 floating windows (one per source, placement as the Settings window, position remembered in the workspace), is fully keyboard operable with the library components, and all reason text is composed from translatable strings per fault and source type (no string building from fragments). Applying restarts the device when a field needs it, with break-before-make. Fields that never need a restart (cursor, volume, sync offset) stay in Properties and are not duplicated as live-only fields here.
7. **Control API (U20), version 1.13.** `source.set_settings` (scope `control`): a patch of the stored settings keys; a key set to `null` removes it; validated strictly like `source.add`; one undo step; refused with a typed error if the new settings fail validation. `source.get_settings` (scope `control`, because it returns file paths and window titles): the stored settings and hints. `status` on `source.list`, `source.changed` and `scene.sources` gets the new `unavailable` variant with `fault` and `detail`; the handshake only tells a client the server's minor version, so the rule is additive: the spec states that a client must treat an unknown `state` as `failed` and show its `detail` (the tolerant decoder is part of the 1.13 change), and the server sends `unavailable` for these cases from 1.13 on. The recent targets are a user setting with a `settings.recent_targets` read and clear command (`control` scope), capped at five per source type. Browsing and thumbnails are UI-only; `source.targets` is the API counterpart of the list. The UI uses the same commands.
8. **Zero cost when unused (P13).** An unavailable source holds no device and no node work. The settings window instantiates nothing until it is opened; closing it frees its model. Listing targets runs on demand.
9. **Phases.** (a) This ADR, then the spec updates in the same change as each code step: scene-sources (`hints`, `SettingsSchema` as a new public contract, which moves "settings schema per type" out of the open questions for built-in types only), control-api 1.13, capture-port (fault mapping, later `thumbnail`). (b) `SourceStatus::Unavailable`, the row and picture indicators, API status. (c) The Source tab, re-pick, `source.set_settings`, undo. (c2) The search field and groups (no port change); thumbnails after the capture port addition. (d) The Source settings window with Video and Audio sections. (e) Later, each with its own decision: device controls, opt-in auto reconnect.

## Consequences

- A source whose window or device disappeared is recoverable in two clicks without losing layout, filters or scene placement.
- All source types use one path to change their target, tested once in the conformance suite of the host (settings patch, break-before-make, undo).
- `rbs-sources` gains a settings schema per built-in type and `rbs-app` a new floating window; the scene document gets an optional `hints` map per source (format version bump; excluded from the binder's settings comparison, so it never restarts a device; older builds drop it on save), and `NodeError` in `rbs-graph` gains an optional fault.
- Specs to update with the code: scene-sources (hints, schema), capture-port (fault mapping, retry rule), graph spec (`NodeError`), control-api (1.13), ui-design-system (state-warning usage, Source settings window component), glossary ("Source settings", "Unavailable").

## Reference tools (CLAUDE.md rule 17)

- **OBS Studio**: a per-source Properties dialog with device-specific options and a "Deactivate" toggle; a closed window shows a black picture with no indicator in the Sources list. It matches windows by `title:class:exe` and can re-find them by title, which fails when the title changes.
- **Where this falls short today (RBS)**: no way to edit a source after adding it; a lost source is only red text.
- **What RBS does better by design**: search and thumbnails in the window list (OBS shows a plain drop-down of titles); an explicit unavailable state with a reason and a fix action in the row; "same application" suggestions rather than title matching; one undo step for a re-pick; the same operation through the control API; nothing polls while the source is healthy or hidden.

## Alternatives considered

- **Keep delete and re-add as the way to change a target.** Loses name, layout, filters and placement in other scenes. Rejected.
- **A modal OK/Cancel dialog like OBS.** Hides the picture the user wants to look at while choosing a camera mode. A floating, non-modal window keeps the preview visible.
- **Only a Properties tab, no window.** Enough for the target, too cramped for camera modes and later device controls.
- **Automatic reconnect now.** Needs background polling and a wrong-window risk; deferred to an opt-in (decision 5).
- **Draw the unavailable state in the compositor.** A new per-frame branch for a rare state (rule 10). The UI layer draws it.

## Review

Reviewer: independent AI session (round 1), 2026-11-08. Verdict: changes requested. Concerns and resolutions:
1. Typed reasons did not exist (string errors). -> Decision 1 now specifies `SourceFault`, who produces it, and the crates touched.
2. Per-type mapping and `can_retry` undefined. -> `can_retry` dropped; text by fault and source type (decision 1, 6).
3. Control API gaps (scopes, old clients, patch semantics, recent list). -> Decision 7.
4. `thumbnail` contract (factory, image type, P4, limits). -> Decision 3a.
5. Thumbnail privacy and platforms. -> Decision 3a (UI-only, not logged, skipped on PipeWire, no prompt on browsing).
6. `target_app`/`target_title` inside compared settings would restart devices. -> Moved to `Source.hints` (decision 4).
7. Audio endpoint gone at `instantiate`. -> Decision 1 (source stays, retried on settings change).
8. Sequencing and `SettingsSchema` as a new contract, `CameraMode`. -> Decision 9, 6.
9. Recent list and application matching. -> Decision 4, 7 (capped at five, per type, API command).
10. Undo and failed apply. -> Decision 6.
11. Placement, accessibility, i18n, token. -> Decision 6, 2.
Round 2 (independent AI session, 2026-11-08): changes requested (minor): fault mapping must cover `TargetLost` and `DeviceBusy`, retry rule versus P13, `rbs-graph` in the crate list, Consequences out of date, API version negotiation. All fixed in this revision (decisions 1 and 7, Consequences).
Round 2 reviewer: "once items 1-4 are fixed, I would approve"; they are fixed. The owner approved the direction and the additions (search, thumbnails, recent targets) on 2026-11-08. Accepted. The capture port `thumbnail` method and the `NodeError` change still need their own rule 11 review in their PRs.
