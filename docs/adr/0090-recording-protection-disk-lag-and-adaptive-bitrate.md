# ADR-0090: Recording protection: early warnings for disk and encoder trouble, ordered load shedding, and adaptive bitrate

- Status: Proposed
- Date: 2026-11-09
- Deciders: Salih (owner)
- Builds on: [ADR-0013](0013-zero-cost-when-unused.md), [ADR-0024](0024-node-restart-with-back-off.md), [ADR-0032](0032-fast-deterministic-tests.md), [ADR-0045](0045-recording-tail-on-stop.md), [ADR-0047](0047-several-outputs-per-canvas.md), [ADR-0055](0055-crash-resilience.md), [ADR-0086](0086-recording-sources-separately-iso.md), [ADR-0087](0087-output-cost-estimate-and-hardware-limits.md), [ADR-0088](0088-replay-buffer-and-retroactive-recording.md), [ADR-0089](0089-recording-markers-and-editor-project-export.md)
- Spec: [recording](../specs/recording.md), [recording protection](../specs/recording-protection.md), [output-ports](../specs/output-ports.md) (`codec.reconfigure`), [control-api](../specs/control-api.md), [performance-budgets](../specs/performance-budgets.md)

## Context

The worst outcomes in live production are silent: a disk that fills at hour three, a recording that falls behind because the encoder or the disk cannot keep up, a stream that stutters because the uplink is worse than at the test. ADR-0055 makes the app survive faults and ADR-0087 (Proposed) would predict cost before the start; neither reacts to what happens during the take. The owner approved a protection feature: warn early when the disk is about to fill or an encoder lags, and lower the bit rate automatically when needed.

What exists to build on (checked against the code on 2026-11-14):

- `rbs_record::Studio::output_counters(OutputId) -> Option<Progress>` (`crates/rbs-record/src/studio.rs`), counted from the output's start. The fields this ADR reads: `export_drops`, `encoder_skipped`, `encoder_drops` and, for a stream, `transport_drops`, `reconnect_attempts` and `connected`. `late_render_ticks` and `late_audio_ticks` belong to the render and audio workers, so they are studio-wide, not per output. `backlog_peak` is a high-water mark for the whole run (`fetch_max`, never reset), and the output's backlog limit is private to the output node; neither gives a per-interval value. There is no queue-depth counter and no bytes-written counter.
- The studio host's control loop in `rbs-app` (`studio_host::round`), which calls `Studio::service` and already runs once-a-second work (the Stats panel's counters, the replay state) through its `wait` value, so nothing runs while nothing is due.
- `codec.reconfigure` (a running encoder may accept a bitrate change; the capability lists which adapters do, and a CBR change must keep the rate-control mode), fragmented containers that stay playable after an abrupt end, the clean end of a recording (`Studio::end_output`, ADR-0045), and the ISO isolation rules (ADR-0086) that already say the master comes first.

Constraints: no new work in hot paths (P15; reading existing counters is fine, adding counters to a node's `process` is a hot-path edit that needs measurement), nothing running when no output runs (P13), deterministic tests with no sleeping (ADR-0032), every threshold and action a user setting with a plain explanation (owner's standing rule), and an automatic quality change must never surprise the user silently.

## Decision

The decisions below are the whole feature. **Phase one** is the part that depends on no Proposed ADR, no hot-path change and no visual change: decisions 1 to 4 (with shedding step 1 inert, see decision 4), the memory warning of decision 6, the status and event of decision 9, and the existing error notice of decision 7. Everything else is named as a later phase where it appears.

1. **A protection guard per running take.** When the first recording or stream output starts (main or vertical canvas, `Studio::outputs`), the studio host creates a *guard*; it is dropped when the last of them ends. The replay buffer and the virtual camera do not create a guard in phase one (the replay buffer joins with decision 6's second phase). With no guard there is no thread, timer or polling. The guard is sampled once per second through the host loop's existing `wait` path (as the Stats panel is). Disk and memory are read every five seconds on **one probe worker thread**, created with the guard. Dropping the guard closes the worker's request channel and joins it only when no request is unanswered; a worker stuck in a call ends when that call returns, so ending a take never waits on a hung drive (a test drops a worker over a hanging fake probe and checks that the drop returns); the host loop sends it a request and takes the answer without waiting. A probe call that has not answered within `probe_timeout` (default 10 s; a network drive can hang) marks disk and memory *unknown*, no further request is sent until it answers, and skipped requests are counted; no thread is created per sample. The guard reads the counters of decision 4; it never writes a hot-path structure.
2. **A pure state machine.** The decision logic is one pure type, `rbs_record::protection::Guard`, with `Guard::step(now, &Sample) -> Vec<Action>` and explicit hysteresis state. It is tested with synthetic samples and explicit timestamps (no real disk, no sleeping; ADR-0032). The sampling layer (the probe worker and its timeout) takes the master clock and a fake probe that can be made to hang, so the five-second cadence and the timeout are tested by moving a `TestClock`; real time bounds tests only as a hang guard.
3. **Disk, per volume.** Each recording output's target folder is mapped to its *volume* by the probe (outputs and ISO files on one volume share it). The guard estimates the volume's write rate from the **fall of its free space** between probe samples over a sliding window (default 60 s, at least three samples), which needs no bytes-written counter and also sees other programs that write there. *Time left* is free space above the reserve divided by that rate (unbounded when free space does not fall). Levels: `notice` below `notice_minutes` (default 30), `warning` below `warning_minutes` (default 3), `critical` when free space reaches `reserve` (default 1 GiB). A level falls back only when the condition clears by a margin (20 % more time left, or free space above the reserve plus 10 %), so it does not flicker. At `critical`, the configured action runs for every recording on that volume, the master included: **stop cleanly** (default on: the recording ends through the host's normal stop, `end_recording` and then `stop_recording` once the tail is in, ADR-0045, before the disk is full, so the files are complete; the host keeps the protection reason through the ending and passes it as the recording summary's `failure` text) or *warn only*. A recording never runs the disk to zero by default. Separate files (ADR-0086) on that volume end with their master; shedding them first at `critical` waits for decision 4's step 1. In phase one the separate audio files the app writes (ADR-0086, protocol 1.46) live beside the master and end with it in the host's stop (`stop_iso_audio`). If ADR-0087 is accepted, its preflight checks free space before the start and uses the same probe.
4. **Lag.** Per output, the guard reads the change per second of `export_drops + encoder_skipped + encoder_drops`, plus `transport_drops` for a stream. An output *lags* when that rate is above `lag_limit` (default 1 per second) for `lag_seconds` in a row (default 3), and stops lagging after `lag_seconds` in a row at or below it. `late_render_ticks` and `late_audio_ticks` are studio-wide: they raise a separate `render` and `audio` lag with the same rule, not one per output. `backlog_peak` is not used (a run-long maximum); a per-interval backlog counter is a separate hot-path PR (decision 10). A lagging output escalates through an **ordered list of shedding steps the user can edit** (each with a switch; defaults in this order): (1) *stop separate tracks* (ISO video tracks, newest first, ADR-0086; their files end cleanly and the manifest records why in a new `ended_reason` field next to the `ended_at` that ADR-0086 plans), (2) *lower the bit rate* of the lagging output (decision 5), (3) *warn only*. Step 1 is inert until ISO video tracks and a per-track stop exist (today only `Studio::stop_iso_audio`, which stops all ISO audio, and ISO video is not built); step 2 is inert until phase two. In phase one every lag is therefore *warn only*. Stopping the master is never a shedding step; only decision 3's disk rule can stop it.
5. **Adaptive bit rate (opt-in, second phase).** The encoder node has no parameter channel today, and ADR-0047 calls adding one a hot-path change and forbids per-output bit rate changes on a shared encoder. Adaptive bit rate is therefore a **second phase** that first adds that channel (before/after numbers, `hot-path-review`, Salih's sign-off, P15). It then applies only to CBR sessions of adapters that list `bitrate` in `codec.reconfigure` (whether padded CBR counts is checked against the `RateControl` of the output-ports spec in that PR), on an encoder that is not shared (it is shown unavailable, with the reason, for VBR, constant quality and shared encoders), lowers the bit rate by `step` percent (default 20 %) down to `floor` (default 40 % of the configured value), raises it back after `recover_seconds` (default 30) without lag, at most one change per `hold_seconds` (default 10). The current step per output is reported on `protection.status`. It helps a slow disk or network; it does not help a CPU-bound encoder, which the text says. The default is **off**.
6. **Memory.** When available system memory falls below `min_memory` (default 1 GiB), the guard raises a `warning`; it clears above `min_memory` plus 10 %. It never allocates in response. *Second phase:* the guard first makes the replay buffer (ADR-0088) evict earlier. The replay ring cannot change its limits while it runs today (`ReplayRingNode::new` fixes them), and a new control value read in its `process` is a hot-path change; it is its own PR under decision 10, and with it an armed replay buffer creates a guard. Where the probe cannot read available memory (decision 11), memory is reported *unavailable*.
7. **Telling the user (never modal, never silent).** Each change of level is a log entry and an update of decision 9's state. In phase one, `warning` and `critical` changes and a protection stop also use the app's existing error notice with a plain sentence ("Recording stopped before the disk was full: 1.0 GiB left on the disk."); that adds no new visual element. *Second phase (visual, rules 15 and 16: proposal first, then screenshots):* a toast for every level, a line in the live indicator area following U4/U12 without hiding the On air state, `warning` and `critical` staying visible in Live controls until the user acknowledges them (`protection.acknowledge {kind}`, scope `control`, for API parity) or the condition ends, and the guard's events listed in the recording's finish report. If ADR-0089 is accepted, each change can also be an automatic marker. All text uses glossary terms; it is English until the app has localisation.
8. **Settings (second phase; user-visible and saved, none hard-coded).** *Open for the owner:* phase one has no switch, so stop-cleanly at `critical` is on with no way to choose warn only until this phase; the owner either accepts that for phase one or asks for the action switch to move into phase one. Section `[protection]` of the output profile (ADR-0051, `format_version = 1`; adaptive bit rate in `[protection.stream]` and `[protection.recording]`): `notice_minutes`, `warning_minutes`, `reserve`, the action at critical (stop cleanly / warn only), the ordered shedding list with switches, `lag_limit` and `lag_seconds` in an advanced section, adaptive bit rate (on/off, step, floor, recover time), `min_memory`. Settings › Recording › Protection shows each with a one-line effect text and the default; reset per card. Phase one runs the defaults above, which are named constants of `ProtectionSettings::default()`, not literals spread through the code.
9. **Control API** (the next free minor at merge). `protection.status` (scope `read`) answers a snapshot (`seq` of `protection.changed`) of `{guarded, level, disks: [{volume, level, free_bytes?, seconds_left?}], outputs: [{canvas, output, level}], render: level, audio: level, memory: {level, available_bytes?}, alerts: [{kind, level, text, canvas?, output?}]}`. `level` is `"ok"`, `"notice"`, `"warning"`, `"critical"` or `"unavailable"` (nothing could be read); the top-level `level` is the highest of the disks, outputs, render, audio and memory in the order ok < notice < warning < critical, and `unavailable` never raises it. `alerts` lists every item at `notice` or above, most severe first, plus a disk whose reading is `unavailable` while a recording runs. `seconds_left` is in seconds, rounded to whole minutes. `kind` is `"disk"`, `"lag"`, `"render"`, `"audio"` or `"memory"`; `output` is `"record"` or `"stream"` and `canvas` `"main"` or `"vertical"`, as in the other output methods. `guarded` is false and the lists empty while no guard runs. `protection.changed` (state topic, scope `read`, no object id) carries the same object and is published when a level, the alerts or a rounded value (free space to 0.1 GiB, time left to the minute) changes, so a late subscriber catches up from the snapshot. The settings of decision 8 join `settings.get/set/changed` as `protection` in the second phase: thresholds apply to a running guard at once (the pure function takes them on each step) and are exempt from the running-output `conflict` of `settings.set`; the action at critical and the shedding list apply to the next take. There is no method that turns the guard off during a take.
10. **Hot paths.** Phase one reads existing counters only. A missing counter (a per-interval backlog, a queue depth), the replay buffer's earlier eviction (decision 6) and the bit rate change of decision 5 are each a separate PR that is a hot-path change (before/after numbers, `hot-path-review`, Salih's sign-off, P15).
11. **Probes and platforms.** The pure guard and the `SystemProbe` trait (free space and volume of a folder, available memory) live in `rbs-record`, which uses no OS API, so `rbs-cli` can use the guard later (phase one wires `rbs-app` only). The OS calls live in a small adapter crate, `rbs-system-probe` (class `Adapter` in `cargo xtask check-layers` and the overview's layer table; its `unsafe` FFI with `// SAFETY:` comments), which exposes plain functions and depends on no other RBS crate; a small type in each composition root implements `SystemProbe` over them. Windows: `GetDiskFreeSpaceExW`, `GetVolumePathNameW`, `GlobalMemoryStatusEx`. macOS: `statvfs` and the folder's device id; available memory is *unavailable* in phase one (free pages alone understate what macOS can give back, so a warning from them would be wrong), and a correct reading (`host_statistics64`, counting inactive and purgeable pages) is a follow-up. Other Unix: `statvfs`, and `MemAvailable` from `/proc/meminfo`, so the guard's real probe also runs on the Linux test machines. A platform with no reading reports *unavailable*, never a guess. If ADR-0087 is accepted, its preflight uses the same probe.

## Consequences

- Disk-full and slow-disk disasters become a planned, explained stop or a clean shedding of the least important files, with the master protected.
- Streams can ride out a weak uplink if the user opts in; the quality change is visible and bounded.
- The logic is deterministic and unit-testable without sleeping, so it will not become a flaky test (rule 14).
- Defaults are conservative: warnings on, stop-before-disk-full on, adaptive bitrate off. A user who wants more automation turns it on knowingly.
- A guard that mis-measures could stop a recording early; that is why the stop is on a reserve with a time-left estimate, the notice and warning come first, and the thresholds are settings.
- Phase one adds one probe thread per take and one pass per second on the control thread; no thread or timer when nothing records or streams.
- Spec follow-ups: `recording.md` (guard, `ended_reason` in the ISO manifest when step 1 is built), `control-api.md` (decision 9), `performance-budgets.md` (guard cost: one pass per second, one probe thread per take), `user-data.md` (the `[protection]` section, second phase), `ui-design-system.md` and the glossary (second phase).

## Alternatives considered

- **Warn only, never act.** Safe and simple, but cannot prevent a corrupted or truncated take when nobody is watching the screen.
- **Always adapt bit rate.** Surprises people who chose a quality; opt-in with explanation is the project's pattern for quality parameters.
- **Let each output decide for itself.** Duplicates logic, cannot protect the master by shedding other outputs, and cannot be tested in one place.
- **Run the checks in the encoder or muxer nodes.** Puts work on hot paths for a control-rate concern.
- **Lower resolution or frame rate when lagging.** Changes the session parameters, which no `EncoderChange` allows (output-ports spec: the stream parameters are fixed for the session).
- **A bytes-written counter per output for the write rate.** Exact for RBS's own files, but it is a new counter in the transport's send loop (a hot path), it misses other programs filling the same disk, and two outputs on one volume would each overestimate their time left. The fall of free space per volume has none of these problems.
- **A general system-information crate (for example `sysinfo`) instead of an adapter crate.** It would cover macOS memory today, but it is a large dependency that enumerates processes, disks and networks; three OS calls per platform do not justify it.

## Review

- 2026-11-09, independent AI session (round 1, reviewing only the ADRs, specs and code): changes requested. Concerns covered contract details, claims about existing code, hot-path and zero-cost rules, and number allocation across these ADRs; each was resolved in the text above (the numbers of protocol minors and scene formats are now assigned at merge time, not claimed by ADRs).
- 2026-11-14, independent AI session (round 2, a fresh reviewer given only the ADR, the specs and the code): changes requested, 13 findings. Three were blocking: the counters named in the text do not exist as written (no queue depth; `backlog_peak` is a run-long maximum and the backlog limit is private), the replay buffer cannot shrink without a hot-path change, and decision 9 said both "new takes" and "applies to the running guard". The others: no settings section or API shapes, lag counted per worker rather than per output, ISO shedding has no per-track stop yet, no bytes-written counter for the write rate, dependencies on Proposed ADRs 0087 and 0089, the probe's place in the layers and on macOS, the guard's lifetime and threads, tests for the sampler's timeout, padded CBR, and two tied thresholds. All were addressed in the text above on the same day: phase one is defined, counters are named, the write rate comes from free space per volume, memory shrink and backlog are later hot-path PRs, the API shapes and scopes are written out, settings live in `[protection]`, the probe is an adapter crate behind a trait in `rbs-record`, and `warning_minutes` is its own setting. A third, verifying review of this revision and the owner's approval are still needed before the status can become Accepted (ADR-0014).
- 2026-11-14, independent AI session (round 3, a third fresh reviewer verifying the revision): approve with changes. All round-2 concerns resolved. Ten remaining findings, none blocking, addressed the same day: the probe crate's layer class and where the `SystemProbe` glue lives, a drop that never joins a hung probe, the stop path through the host's `end_recording`/`stop_recording` carrying the reason, the top-level `level`, `unavailable` and `alerts` defined, an `audio` lag next to `render`, `ended_at` as planned by ADR-0086, separate files ending with their master, no provisional minor in the text, and phase one wiring `rbs-app` only. One item needs the owner: phase one ships stop-cleanly on with no switch (decision 8). The owner's approval is still needed before the status can become Accepted (ADR-0014).
