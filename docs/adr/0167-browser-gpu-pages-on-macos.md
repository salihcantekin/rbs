# ADR-0167: Browser pages on macOS paint into studio-owned IOSurfaces

- Status: Accepted (owner, 2026-11-21)
- Date: 2026-11-21
- Deciders: Salih (owner)
- Extends: [ADR-0157](0157-browser-gpu-pages-sync-on-a-shared-fence.md) to macOS. It supersedes nothing: ADR-0157 says "macOS (IOSurface) is unchanged by this decision and still paints in software", and this ADR is that missing decision. ADR-0109 decision 8 ("the studio owns the textures ... a texture goes back only after the studio's GPU work that reads it has finished") holds unchanged.

## Context

On macOS a browser page still paints in software: the browser process gets `disable-gpu` and `disable-gpu-compositing` (`rbs-browser-cef` `gpu_switches`), `OnPaint` swizzles BGRA into the frame section, `take_latest` copies the slot into a `Vec` and `publish_at` copies it into `Bytes` before the upload (F-03 in `docs/research/resource-and-structure-audit-2026-11.md`). A 1920x1080 picture is 8.3 MB, so at 30 fps each copy moves about 250 MB/s.

Device spike on the owner's Mac (Apple M4 Pro, CEF 156.0.30, release build, a 1920x1080 canvas page redrawn every frame, 30 fps, 20 s runs; spike code not committed):

- With `shared_texture_enabled` and no GPU switches in the browser process, CEF 156 calls `OnAcceleratedPaint` with an `IOSurfaceRef` at the page rate (about 30 per second). The surface is `BGRA` (`'BGRA'`, `CEF_COLOR_TYPE_BGRA_8888`), 1920x1080, 7,680 bytes per row, `IOSurfaceIsInUse` false. CEF rotates a pool of three surfaces. CEF's header says the surface returns to its pool when the callback returns.
- A Metal blit of that surface on the helper's own `MTLDevice`, committed without a wait: callback time (texture from the surface, command buffer, blit, commit) mean 0.5 to 0.8 ms per 120-frame window, max about 1.2 ms after warm-up (32 ms once at device creation). The copy completed on the GPU 0.55 ms after commit on average, max 2.3 ms.
- CPU of the runner processes and the test supervisor (sum of `%cpu` over three samples): GPU path about 20 %, software path 23 to 29 % of one core, before the studio's `Vec` and `Bytes` copies and the upload, which the GPU path removes as well.

The studio already shares IOSurfaces with another process over a Mach service (ADR-0028, `rbs-gpu` `share`), and the Metal importer already takes `NativeSurface::IoSurface` frames and keeps them retained while cached (`rbs-gpu/src/interop/metal.rs`).

## Decision

1. **Same model as Windows, with one writer.** ADR-0157 decisions 1 (the helper never waits on the CPU in a CEF callback), 4 (the slot state words, the CAS claim, the latest published slot never overwritten; the same `rbs-browser-shm` `gpu_slots` code), 5 (slot count from the holders, default 4), 9 (fallback is a restart without the GPU block, visible as one Warn line), 10 (versioned section and `Configure` block) and 12 (every spawn is fresh) apply on macOS. Every claim, publish and abandon of a slot runs on CEF's UI thread, which is also the runner's paint loop (WP-J pump), so `gpu_slots` keeps exactly one writer as on Windows. Only what differs is decided below.
2. **The GPU path needs one Metal device.** The helper takes the GPU path only when `MTLCopyAllDevices` returns one device and its `registryID` equals the one in the `Configure` block; otherwise the studio's block is refused and the page uses shared memory (reason `adapter`). That is a capability check (one GPU, so CEF's GPU process and the helper's copy run on the same GPU), not a model check (P3). Systems with two GPUs keep software paint until a later decision pins CEF's GPU process.
3. **The studio owns the surfaces and hands them over once, on an authenticated Mach service.** For each spawn the studio creates the slot IOSurfaces (`BGRA`, the page size) and checks in a Mach service with a fresh random name. The `Configure` GPU block gets a macOS variant (its own tag, a version byte, the service name, a 128-bit random token, the studio's `MTLDevice` registry id, the slot count); it travels over the private pipe the studio already uses. The helper looks the service up right after it reads `Configure`, sends one request with the token and a reply port, and waits for the reply at most 2 s, outside any CEF callback. The studio receives requests with `MACH_RCV_TRAILER_AUDIT` (a buffer sized for that trailer), drains at most 8 queued messages per supervisor pass with zero-timeout calls, and answers only when the token matches and the audit-token pid is the spawned helper's (the studio spawns the runner directly). It then removes the service (also the `bootstrap_register` path's send right). The service is removed after that one reply or 5 s after the supervisor's first pass that sees the helper's first heartbeat, whichever is first, so a slow first engine start does not count; no handover in time is fallback `open`. The studio's Mach server lives in `rbs-app` and is handed to the supervisor as a non-blocking hook, as `FenceView` is, so `rbs-browser-runner` gains no OS dependency. No pixels and no per-frame Mach message cross the boundary. The message layout and the check-in, look-up and port helpers move from `rbs-gpu` `share/mach.rs` into a small low-level crate without wgpu (`rbs-mach`), used by `rbs-gpu`, `rbs-app` and the helper, so the two sides cannot drift. `rbs-mach` is a macOS-only target dependency, a marked low-level `unsafe` crate (rule 7), and gets a row in the layers table of `overview.md`. The browser handover has its own message ids and version, distinct from ADR-0028's preview messages, so neither service parses the other's messages.
4. **The copy is recorded in the callback; its completion is collected on the UI thread.** In `OnAcceleratedPaint` the helper claims a slot, records a blit from CEF's surface into the slot surface on its own device and command queue, adds a completed handler, commits and returns. The copy region is the slot size; a CEF surface of another size is not copied and counts as a failed copy (the runner forces device scale 1, as today). The completed handler only stores the command buffer's status into the slot's per-slot "copy done" word (ok or error, Release) and wakes the pump (`pump::PUMP.wake()`, any thread, never waits; not `schedule(0)`, which would add a CEF work pass per picture). It holds an `Arc` of the mapping and slot set and does not allocate, log or panic (an infallible body). Teardown never waits for it, and the UI thread keeps its own reference until the process exits, so a handler never drops the last one (no unmap or free on Metal's thread). On the UI thread, at the start of each callback and each loop pass, the helper takes the done slots in claim order (each claim takes the next value of a per-helper claim sequence; the helper keeps the order in its own memory and only writes the value into the slot's fence word, never reading it back from the section): an ok slot is published in ADR-0157 decision 4's order and orderings; an error slot is abandoned. A done slot whose earlier claim is still in flight waits for it, so pictures are published in claim order. `waitUntilCompleted`, `waitUntilScheduled` and semaphore waits are in `clippy::disallowed_methods` for the crate, as the Windows waits are.
5. **Failure counting.** ADR-0157 decision 6 applies when the UI thread collects a slot: a published slot resets the count to 0, an error or size mismatch adds one, "no free slot" leaves it; at 60 the helper falls back with `copy`. The repaint request (`invalidate(PET_VIEW)`) is posted from the UI thread as on Windows. A copy still not done 30 page frames after its commit, measured on the paint loop's clock, is fallback `copy`: a GPU that stops completing ends the GPU path, while the heartbeat (which keeps beating then) does not.
6. **No fence on macOS; the gate runs in a fence-less mode.** A slot is published only after its copy completed, so the studio's frame carries `SurfaceSync::Ready`. `GpuGate` gets an explicit fence-less mode (no `FenceView`): it keeps the leases, `failed_imports` and the `import` fallback, and passes a picture through on its first pass. The slot's fence word is the claim sequence; in `pass` the gate requires it to be strictly higher than the newest value seen (otherwise fallback `fence`); `again` may return the same value. Ordering between the helper's slot write and the studio's read is the completed command buffer followed by a later submission on the same GPU (decision 2). Rule (c) of ADR-0157 decision 2 stays: the helper writes a slot only after the studio's hand-back (the lease reaches zero after `Importer::retire`).
7. **CEF's surface.** The helper calls `IOSurfaceIncrementUseCount` on CEF's surface in the callback and `IOSurfaceDecrementUseCount` when it collects the copy; the device check (decision 10) records whether CEF's pool skips a surface in use. The textures made from CEF's surfaces are per callback (ADR-0157 decision 7); the slot surfaces and their textures are opened once at start. Whether Chromium's write into the surface has finished before the callback, and whether its pool honours the use count, are measured by the tear test of decision 10 before the path is turned on by default; if pictures tear, the path stays off on macOS and this ADR is revisited.
8. **Studio import and lifetime.** A picture is `NativeSurface::IoSurface` of the studio's own slot surface, imported by the existing Metal importer. ADR-0157 decision 13's handle grave is not needed on macOS: the importer's cached texture retains the surface, so its address cannot be reused while cached (`interop/metal.rs`). A stopped spawn's importer entries are closed by its per-spawn identity, as on Windows, so its surfaces are freed when no frame holds them instead of after `SURFACE_IDLE`. The first import of each slot (`alias_plane`, allocates) happens once per spawn; it is measured.
9. **Switches.** The GPU path is the default once the tests and the device check pass; `RBS_BROWSER_SHARED_MEMORY=1` forces software paint as on Windows. Without a GPU block the browser process keeps `disable-gpu` and `disable-gpu-compositing`.
10. **Tests and numbers.** Without CEF: the macOS `Configure` block round-trips and an unknown version gives shared memory; the Mach exchange hands over all slot surfaces between two processes, refuses a wrong token and a wrong pid, and removes the service after one reply and after the deadline; a supervisor pass with the service checked in does not block; `loom` models with the claim on one thread and completions arriving on others, out of order, keep "the latest published slot is never overwritten" and publish order equal to claim order; the 30-frame copy timeout with an injected clock; the gate's fence-less mode (pass-through, `import` fallback, a falling sequence). On the device (ignored, `slow_*`): a page that alternates full-frame solid colours each frame, every published slot checked uniform (no tear) and the colour sequence in order, for 20 s with no fallback; callback, completion and import times, and CPU against `RBS_BROWSER_SHARED_MEMORY=1`, written into `docs/architecture/hot-paths.md`. `BrowserSourceNode::process` takes the native branch on macOS for the first time: the `browser_import.rs` allocation guard gets the IOSurface case, hot-path review, before/after numbers and the owner's approval (P15).

## Consequences

- macOS pages stop paying the swizzle, the two studio copies and the upload (F-03) on the normal path; the spike shows less CPU in the runner already.
- The callback costs about 0.5 ms on CEF's UI thread at 1080p (spike). If the implementation measures the per-callback texture creation as the larger part, a cache of textures for retained CEF surfaces, bounded to CEF's pool size, needs a new decision (it holds CEF's memory alive).
- A new low-level crate `rbs-mach` (ADR-0028's Mach helpers moved out of `rbs-gpu`), a macOS variant of the `Configure` GPU block, and a fence-less `GpuGate` mode.
- Macs with two GPUs keep software paint (decision 2).
- Follow-up: scene-sources spec ("Frames cross ...") gets the macOS paragraph when the code lands; `docs/status.md` row for browser GPU pages; WP-H fault injection covers a helper whose copies never complete (decision 5).

## Alternatives considered

- **Send CEF's own surface to the studio each frame.** Zero copies, but CEF takes the surface back when the callback returns, and holding it would starve CEF's three-surface pool; it would also need a Mach message per frame.
- **Wait for the copy in the callback (`waitUntilCompleted`).** Simple, but it stalls CEF's UI thread, which also takes Interact input: the freeze ADR-0157 removed on Windows.
- **A shared `MTLSharedEvent` as the fence, as on Windows.** Its handle crosses processes only through XPC, which the helper does not use; publishing from the completed handler gives the same ordering with nothing shared.
- **Global IOSurfaces looked up by id.** `kIOSurfaceIsGlobal` is deprecated and lets any process open the surfaces.
- **Keep software paint on macOS.** Works, but keeps F-03's three copies per picture, which the owner's stability plan lists as open.

## Review

Round 1: independent AI session (given only this ADR, the principles, ADR-0157, ADR-0109, ADR-0028, the specs and the code), 2026-11-21. Verdict: changes requested. Concerns and resolutions by the author, written into the decisions above:
1. (Blocking) Publishing from Metal's completed handler made two writers of `gpu_slots`, so a claim could overwrite the slot just published, and handlers could publish out of order. -> Decision 4: the handler only marks the slot done; the UI thread publishes in claim order; `loom` models with completions on other threads (decision 10).
2. (Blocking) A GPU that stops completing had no fallback; the heartbeat keeps beating. -> Decision 5: 30 page frames on the paint loop's clock, then fallback `copy`.
3. (Blocking) The gate bypass was not specified. -> Decision 6: an explicit fence-less mode that keeps leases and the `import` fallback; the fence word is the claim sequence.
4. (Blocking) Completion then later submission was not shown for reading CEF's surface, and on two GPUs it may not hold. -> Decision 2 limits the path to one Metal device (capability); decisions 7 and 10 add the use count and a tear test before the path is on by default.
5. (Blocking) The Mach handover had no token, pid check or deadline. -> Decision 3. Passing the port without the namespace (`posix_spawnattr_setspecialport_np`) was weighed: the helper's own children need the real bootstrap port (Chromium's Mach port rendezvous looks services up there), and a spare special port is not a documented contract, so the namespace stays with the token, pid check and 5 s removal.
6. Handler lifetime and panics. -> Decision 4.
7. CEF pool reuse was asserted. -> Decision 7 and the tear test.
8. Size and scale. -> Decision 4.
9. A stopped spawn's surfaces stayed alive up to `SURFACE_IDLE`. -> Decision 8.
10. Duplicated Mach code would drift. -> Decision 3: `rbs-mach`.
11. First-import cost and the allocation guard. -> Decisions 8 and 10.
12. Asynchronous failure counting. -> Decision 5.

Round 2 (confirm): a fresh independent AI session (same inputs), 2026-11-21. Verdict: approve with notes, none blocking. All round-1 concerns resolved in the Decision text; the single writer holds because the loop that calls `do_message_loop_work` is CEF's UI thread (`external_message_pump`). Notes, all written into decisions 3, 4 and 6 by the author: (1) receive with the audit trailer; (2) the handover deadline starts at the first heartbeat, not the spawn; (3) the UI thread owns the last reference to the slot set; (4) `rbs-mach` is macOS-only, low-level, in the layers table, with its own message ids; (5) the studio's Mach server is injected into the supervisor from `rbs-app`; (6) `PUMP.wake()` instead of `schedule(0)`; (7) the claim order lives in helper memory; (8) drain a bounded number of queued requests per pass; (9) the gate's rising check is strict in `pass`, equal in `again`.

Owner's acceptance, 2026-11-21 22:11 UTC: Salih accepted this ADR in the project thread ("ADR-0167 kabul"), after round 2.

Implementation notes, 2026-11-21 (author; factual, the decisions stand):
1. Decision 8 said a stopped spawn's importer entries are "closed by its per-spawn identity, as on Windows". The importer has no per-spawn close on either platform (Windows holds the handles in a grave for 10 s, ADR-0157 decision 13); a stopped macOS page's surfaces are freed when the Metal importer drops its cached textures after `SURFACE_IDLE` (8 s), at most four page-sized surfaces per stopped page. This hold is what the round-1 review (concern 9) offered to accept; it is stated here instead of the wrong sentence.
2. The device check of decision 10 ran on the owner's Mac (Apple M4 Pro, CEF 156.0.30, release builds, a 1280x720 page that paints a new solid colour every frame at 30 fps, 20 s, `rbs-app` `browser_metal::device_tests`): 571 and 597 pictures, every published slot uniform (64 sampled pixels; no torn picture) and every picture new, no fallback. Helper processes' CPU (sum of `%cpu`, three samples): GPU path 1.7-3.7 %, shared memory with the same page and size 4.2-8.6 %.
3. Hot-path numbers (`rbs-sources` `tests/browser_import.rs` `slow_tick_times_bytes_against_io_surface`, same Mac, a 1920x1080 page picture each tick, the tick plus the GPU wait): bytes upload (macOS before) p50 551 us, p99 1,028 us; cached IOSurface import (after) p50 21 us, p99 34 us. A tick that takes an IOSurface picture allocates at most 25 times against 4 for the upload: the extra allocations are wgpu's command encoder and submit in `Importer::retire`'s hand-back submission, which every imported native frame already pays (ScreenCaptureKit captures, Windows pages). They are outside `BrowserSourceNode::process` and are a follow-up for the importer, not part of this change.
