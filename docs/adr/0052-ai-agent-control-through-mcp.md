# ADR-0052: AI agents control RBS through an MCP server that is a plain control API client

- Status: Accepted
- Date: 2026-11-06
- Deciders: Salih (owner)
- Amends: ADR-0044 decisions 9 and 10 (additive: token narrowing on IPC, a per-token "irreversible actions" permission)

## Context

The owner wants users to hand RBS work to an AI agent: not only "start recording", but building scenes, adding and placing sources, switching and editing output profiles and scene collections, and reading and changing settings. Agents such as Claude, Cursor or VS Code reach outside tools through the Model Context Protocol (MCP): a server lists typed tools (name, description, JSON Schema for the input, annotations), prompts and resources, and the agent calls them, usually over stdio.

What exists:

- The control API (ADR-0044, ADR-0046, [control API spec](../specs/control-api.md)) is a versioned JSON-RPC protocol with scoped tokens over local IPC and WebSocket, served while remote control is on. Its Rust types are the schema; `api.describe` lists methods with their scopes; the generated JSON Schema is an open follow-up. Stream server and key, token values and token hashes never appear in any answer, event or log, and no API method can set the stream server.
- UI rule U20 and ADR-0008 say every UI command is a control API command, but the API covers only a first slice: program-scene sources, undo and redo, recording, streaming and part of the settings. Scenes, canvases, transitions, audio mixing, profiles and scene collections (ADR-0051) are not reachable.
- On IPC, a same-user peer is authenticated by `session.hello` with all scopes; a later `session.authenticate` is refused as "already authenticated" (`rbs-api` `session.rs`). On loopback WebSocket the client cannot check which OS user serves the port, so another local user who binds it first would receive the token; IPC checks the server's user.
- `control` covers both undoable scene edits and live actions (record and stream start and stop, program switch). Audit records (`AuditEvent::Privileged`) cover only `admin`, `plugins` and `tokens` calls.
- Scene edits go through one shared undo stack; each API request is at most one undo step.

Forces: an agent can be wrong or be steered by text it reads (prompt injection through a window title, a file name or a source name). What an agent may do through its RBS tools must therefore be bounded by RBS, not by the agent's good behaviour. That bound covers the agent's RBS connection only: any program running as the same OS user can still open IPC with all scopes, so an agent that is also allowed to run shell commands is bounded by what the user grants in the agent. Live actions and some deletions are not undoable. Agents start each task without knowledge of RBS and pay context for every tool they see. P1 and P2 keep protocol libraries out of core crates; P13 forbids cost for users who never use an agent; P9 requires clients to keep working across versions.

## Decision

1. **API parity is a rule.** Everything a user can do in the desktop app must be doable through `rbs-api`, with the same validation and undo behaviour, except a short list kept for the local user: entering the stream server and key, the remote control and network access settings (including "Allow remote admin"), and turning the irreversible-actions permission on for an existing token (decision 4). The U20 test allows exactly that list and enumerates the other gaps until it can require none; a PR that adds a UI action adds its request. Before agents are offered as a feature, the scene model's operations get `scene.*`, `canvas.*` and `source.*` methods, and, once ADR-0051 is merged, profiles and collections get methods with these scopes and effects (decision 4):

   | Methods | Scope | Effect |
   | --- | --- | --- |
   | `collection.list`, `collection.get`, `profile.list`, `profile.get` | `read` | `read` |
   | `collection.create`, `collection.rename`, `collection.duplicate` | `control` | `edit` |
   | `collection.switch` (gets the on-air check of decision 4) | `control` | `edit` |
   | `collection.delete` | `control` | `destructive` |
   | `profile.create`, `profile.rename`, `profile.duplicate` | `admin` | `edit` |
   | `profile.switch` (changes where the next stream goes) | `admin` | `live` |
   | `profile.delete` (removes the profile's stream key) | `admin` | `destructive` |
   | `collection.import`, `collection.export`, `profile.import`, `profile.export` (explicit paths; an export to a path that exists is refused with `file_exists`, as for every explicit file; an import error gives the error kind, line and column, never text from the file) | `admin` | `destructive` |

   Switching either is refused with `conflict` while recording or streaming, as in the app. No API method sets a stream server (control API spec, stream settings), and these do not open a way around that: `profile.create` and `profile.duplicate` take a name and a source profile only, `profile.import` drops the stream server of the imported file, so an imported profile has none until the local user enters one in the app, and `profile.export` through the API always leaves the server out of the file (the server address may carry a key, and the agent could read the file). Conformance tests import a profile with a server and check it has none, and check that an API export holds none.
2. **`rbs-mcp` is a separate application and a plain API client.** A new binary crate, `rbs-mcp`, speaks MCP to the agent and `rbs-api` to RBS. It holds no RBS state, has no rights of its own and no path into RBS except the control API; RBS does not know MCP exists. It is a composition root like `rbs-app` and `rbs-cli`: it depends on `rbs-api`, the `rbs-api-ipc` transport adapter (its client), `rbs-remote-settings` (the config directory) and an MCP library chosen and justified in its own PR; no engine, port, other adapter or toolkit crate. Toward the agent it speaks stdio (the agent starts it); toward RBS, local IPC, which verifies the server's OS user. A WebSocket client for RBS on another computer (TLS with a pinned key, ADR-0046) and MCP over HTTP each need their own review.
3. **Agents use their own token, also on IPC.** `rbs-mcp` must authenticate with a token and refuses to start without one. It reads the token from `RBS_TOKEN` when that is set, otherwise from a file (`--token-file`, by default `agent-token` in the config directory, mode 0600 on Unix); never from the command line, and it never writes it to a tool result or log. Agent applications keep environment variables in plain-text configuration files, so the token file is the documented way. Protocol addition (minor): a same-user IPC peer may send `session.authenticate {token}` as its first request after `session.hello`; the session then has exactly the token's scopes and permission for its lifetime (narrowing, never widening), and the answer (`AuthResult`) reports both. `authenticate` is refused once any other request was admitted, and a second one is refused, so nothing runs with all scopes before the narrowing. A wrong token gets `auth_failed` and close (no back-off on IPC: the peer is the same user and tokens have 256 bits); revoking the token closes the session. Narrowing is voluntary: a same-user peer that does not authenticate keeps all scopes, as `rbs-cli` does. `rbs-mcp` fails closed: it sends nothing after `session.hello` until the `session.authenticate` answer arrives, stops unless the server's protocol minor supports narrowing and that call succeeds (an older server's "already authenticated" refusal is a failure), and builds its tools only from the scopes and permission in that answer, never from the hello answer; a test runs it against a server one minor older. `rbs-mcp` never lists `session.*`, `tokens.*`, `events.*` or plugin methods.
4. **Every method declares an effect, and irreversible effects need a token permission.** Next to its scope, every method, without exception, declares an `effect` in `rbs-api`: `read`; `edit` (undoable, or reversed by another call with nothing lost; `edit.undo`, `edit.redo`, `canvas.set`, program switch, mute, volume and transitions included); `live` (record and stream start and stop, `profile.switch`); `destructive` (removes something outside the undo history). Tokens gain one permission, **"Allow actions that cannot be undone"** (amends ADR-0044 decisions 9 and 10, additively). Without it the server refuses, with a new error kind `not_permitted` (reason `irreversible`, `on_air` or `network`):
   - every `live` and `destructive` method, checked on the API thread from the method's effect;
   - every `edit` that changes what is on air, `edit.undo`, `edit.redo`, program switch, `collection.switch` and each operation of `edit.apply` included, checked on the control thread (so an agent can build a scene and switch to it while nothing is running, but not change a running show). A canvas is *on air* while it has any active output (recording, streaming, and later outputs such as a virtual camera). On air is: that canvas's format (`canvas.set`), everything reachable from its program scene (items, nested scenes, the sources they show, also where a source is shared with other scenes, and their filters), and the audio mix of that canvas (mute, volume and routing of the sources in it). Reachability is one pure function over the scene model in `rbs-scene`, which tests drive directly; the target applies it, and checks the canvas format and the mixer (which `rbs-scene` does not own) with it. A test per part runs through the real target;
   - anything that would make RBS open a connection to a host: adding a source of a type that opens network connections (a network media or browser source; the source type registry marks such types) or changing its address, and any *location* value that is not a local absolute file system path. Every path or URL field in a request (source settings such as an image or media file, recording folders, `record.start_to_file`, import and export paths) is marked as a location in the schema and checked by its value: without the permission, URL schemes, UNC and `\\?\UNC` paths and device paths are refused, so an agent cannot reach a host of its choosing through a "file" (an SMB path would also leak the user's credentials). The check fails closed: a source type (built in or from a plugin) counts as network unless it declares itself local-only and names its location fields, and a local-only type must open local files only (for media sources, a protocol allow list, so a local playlist or SDP file cannot make the demuxer contact a host; the detail belongs in the scene sources spec). These methods also carry `openWorldHint`.
   - `settings.set` has effect `edit`; its `canvas` field gets the on-air canvas-format check above.

   `tokens.create` passes on only what its caller holds and can never give a token more: scopes beyond the caller's, or the permission when the caller lacks it, are refused with `not_permitted`. `tokens.create` and `tokens.revoke` have effect `destructive`.

   For this, `ControlTarget::handle` receives a caller context: the token name (or a fixed label, `local user (IPC)` or `desktop app`) and whether the permission is held. This changes a public trait of `rbs-api`; its crates are not published, and every implementation changes in the same PR. A token store entry without the field has the permission, so existing tokens and same-user IPC peers keep today's behaviour. `tokens.create` takes an optional `irreversible` field (default `true` for a caller that holds the permission, as tokens behave today, for panels); `rbs-cli token create --agent` and the app's Agents page make tokens without it, and the agent's token file. Effects are fixed in code and covered by the schema snapshot test.
5. **Audit.** An audit record, with the caller label, is written for every `live` and `destructive` call and every `not_permitted` refusal, besides the existing privileged calls. The API thread writes all of them; for a refusal made on the control thread, it writes the record when it forwards that answer.
6. **Tools come from the schema of built-in methods.** At connect time `rbs-mcp` reads `api.describe` and makes one tool per method the session can call: the method name with `.` replaced by `_` (a collision or a name outside MCP's name pattern fails a test), the description from the method's doc comment, the input schema from the generated JSON Schema. Only methods built into `rbs-api` become tools; `api.describe` and the schema must not contain text taken from state or from plugins: enum values come from code, a source's `type` is a free string whose valid values a read method lists as data, and plugin and user-defined settings are opaque objects. Annotations come from the effect: `read` gives `readOnlyHint`; `edit` gives `destructiveHint: false`; `live` and `destructive` give `destructiveHint: true`, and `stream.start` also `openWorldHint`. A missing or unknown effect (an older or newer server) is treated as `destructive`. `--tools <namespaces>` limits the list so an agent's context holds only what its task needs. `edit.undo` and `edit.redo` are not listed, because the shared stack would let an agent undo the user's own edit; an undo of the agent's own step waits for an `edit.undo {step}` addition.
7. **Few high-level tools, each one undo step.** `rbs-mcp` adds a small fixed set of task tools, such as `studio_summary` (canvases, scenes, sources, profile, collection and output state in one value) and `scene_build`. Each is built from ordinary API requests, so it has no more rights than the session, and each requires the protocol minor it was written for (hidden otherwise). An editing task tool must be one undo step: the API gets `edit.apply {label, operations}`, scope `control`, effect `edit`, which takes only undoable scene operations, validates the list as a whole, applies all or none, and records one undo step named `label`. It depends on the serialisable scene operation type (ADR-0044 decision 14), which comes with the scene document format (ADR-0051).
8. **Undo covers the agent.** Agent edits go on the user's shared undo stack, so Ctrl+Z in the app undoes them. The undo history shows the caller label of each step (an addition to the undo record and, when undo history is exposed, to the API).
9. **RBS text is data.** Tool results carry RBS state as structured JSON. Strings from users or the system (source and scene names, window titles from `source.targets`, file names) are returned as values, never placed into tool descriptions, prompts, resources' fixed text or the server's instructions, which come only from the `rbs-mcp` build and `rbs-api` doc comments.
10. **A usage guide ships with the server.** Domain knowledge (canvas sizes for vertical channels, build in a scene that is not on air and then switch, never change the profile while live, typical workflows) is written once as Markdown in `rbs-mcp` and served as the server's short `instructions`, as MCP prompts for workflows and as resources (`rbs://guide/...`), and published as an agent skill for agents without MCP prompts. The guide advises; every rule that matters is enforced by the API (decisions 3 and 4).
11. **Connection lifecycle.** `rbs-mcp` declares the MCP `tools.listChanged` capability. When RBS cannot be reached, it lists only `studio_summary`, which answers with how to turn on remote control. Every (re)connection runs the fail-closed handshake of decision 3: if it fails, every tool call returns a tool error and no RBS tool is listed; if it succeeds, it reads `api.describe` and sends `notifications/tools/list_changed`, also after RBS restarts with another instance id.
12. **Zero cost when unused** (P13). Nothing of this runs inside RBS: `rbs-mcp` is started by the agent and ends with it. RBS needs remote control on, which costs nothing without a session (ADR-0044 decision 15). The effect check is a table lookup per request on the API thread, and the on-air check one query of the scene model per edit on the control thread; neither is on a hot path. Events are not used in the first version; mapping subscriptions to MCP resource updates is a later, separately reviewed addition.

## Consequences

- Any MCP-capable agent can operate RBS within its token, and every capability added to the API reaches agents, Stream Deck, scripts and `rbs-cli` with no extra work.
- The parity rule makes the API the first thing built for every feature, and the U20 test becomes a gate.
- Protocol additions (minor, each with its spec change and review): IPC narrowing, `effect`, the irreversible-actions permission, the `not_permitted` error kind, the caller context of `ControlTarget`, audit of `live` and `destructive` calls, `edit.apply`, `scene.*`, `canvas.*`, `profile.*`, `collection.*`, token names in undo records, later `edit.undo {step}`. The token file format gains the permission with a default that keeps existing tokens' behaviour.
- Blocking prerequisites for shipping `rbs-mcp`: the generated JSON Schema (ADR-0044 follow-up), the serialisable scene operation type, and ADR-0051 merged for `profile.*` and `collection.*`.
- With `read`, an agent sees source and scene names, window titles and file names, and its agent application sends them to its model provider. The Agents settings page says so when a token is made.
- An agent without the permission cannot help during a live show beyond reading and editing scenes not on air; the user can allow more per token.
- A third-party dependency (the MCP library) in an application crate. Since `rbs-mcp` is a thin client, replacing it or adding another agent protocol touches only that crate.
- CLAUDE.md rule 3 names `rbs-mcp` among the composition roots.
- Follow-ups: [MCP server spec](../specs/mcp-server.md) (Draft, in this change), the API additions above, an "Agents" entry in Settings, Remote control (make an agent token and its file, show the line to add RBS to an agent), the guide content, the WebSocket client and MCP over HTTP reviews.

## Alternatives considered

- **Only an agent.md / skill file, with the agent calling `rbs-cli`.** Cheapest to write, but the agent needs shell access (all scopes over IPC, and far more than RBS), commands are parsed from text without a schema, every feature needs a CLI command too, and nothing is enforced. Kept as the guide's second channel (decision 10).
- **Loopback WebSocket with a token, no protocol change.** Works today with scopes and revocation. But the client cannot verify which OS user serves the port, so another local user could take it first and collect the agent's token; IPC checks the server. It stays possible for agents on another computer once the WebSocket client is reviewed.
- **An MCP server inside `rbs-app`.** No extra program, but it brings an MCP library and probably an HTTP server and async runtime into the app, opens a second protocol with its own security, and costs something while unused.
- **A separate `live` scope split out of `control`.** Clear, but changes the meaning of every existing Control token and panel setup (ADR-0044 decision 10). A permission with a keeping default gives the same bound without breaking them.
- **RBS asks the local user to confirm each irreversible request** from a token without the permission. Also enforced by RBS, and it would let an agent help during a live show. Not chosen for now: headless `rbs-cli` setups have nobody to ask, and a dialog in the middle of a show interrupts the person running it. A later ADR can add it as a third choice per token. MCP elicitation is not the same, since the agent application answers it.
- **Only a client-side flag in `rbs-mcp` to hide live tools.** The agent's own configuration sets it, so it bounds nothing against a steered agent. Superseded by decision 4.
- **Hand-written tools per method.** Better descriptions per tool, but they drift from the API and double the work. Doc comments in `rbs-api` carry the descriptions; only task tools are written by hand.
- **One generic `call(method, params)` tool.** Smallest context, but no per-method schemas or annotations. Namespace selection limits context instead.
- **Only high-level task tools.** Simple for agents, but every feature needs a new task tool and agents cannot do what the tools did not foresee.
- **Client libraries for agents that run code (Python, TypeScript).** Possible later from the same schema; MCP is what agent applications support directly.

## Review

Reviewer: independent AI sessions (a fresh session per round, given only the proposal, specs, principles, related ADRs and code)
Date: 2026-11-06
Verdict: five rounds; round 5 approved with minor changes, applied in the same change. Owner approval: Salih, 2026-11-06 (project thread: approved the MCP plus usage guide approach and asked for this ADR; ADRs may be accepted in the early phase).
Concerns and resolutions:
1. Round 1, changes requested, 13 concerns. A client-side `--no-live` flag bounded nothing: replaced by a server-enforced token permission (decision 4). Missing or unknown effects now count as `destructive`. `edit.apply` is limited to undoable `control` operations and waits for the operation type. `profile.*` and `collection.*` got scopes and effects. Audit now covers `live` and `destructive` calls. The loopback WebSocket alternative was added, with the reason IPC is preferred (server identity), and the narrowing was stated as voluntary. Tool text comes only from built-in methods. Narrowing semantics, undo exclusion, the connection lifecycle, layering (`rbs-mcp` is a composition root; CLAUDE.md rule 3), the token file, the privacy note and tests were added.
2. Round 2, changes requested, 10 concerns. `profile.import` could bring in an attacker's stream server: API import drops it. `ControlTarget` gets a caller context (a public trait change). `rbs-mcp` fails closed against servers without narrowing. Every method declares an effect, undo and redo get the on-air check, and "on air" is defined. New error kind `not_permitted`; defaults for new tokens; labels for tokenless callers; token source precedence; the on-air check is a pure `rbs-scene` function also tested through the real target.
3. Round 3, changes requested, 9 concerns. API export leaves the server out, and exports never overwrite (`file_exists`). The fail-closed check now uses the authenticate answer, which reports the permission. Narrowing must be the first request after hello. On air means any active output, including the canvas format and the audio mix. Network source types are refused without the permission. Plugin source types are free strings. The connection rules no longer contradict each other. IPC has no back-off.
4. Round 4, changes requested, 5 concerns. Location values (paths and URLs) are checked by value, so a UNC or URL "file" cannot reach a host. `settings.set` got its effect and the on-air check. `tokens.create` cannot give more than its caller holds. The parity rule lists its local-only exceptions. Import errors never echo file text.
5. Round 5, approve with minor changes. Source types count as network unless they declare themselves local-only (fail closed). Program switch and `collection.switch` are `edit` with the on-air check, so an agent can finish a scene while nothing runs. The exception wording for the permission was fixed. The "RBS asks the local user" alternative was added. Tests were added for plugin source types and for `edit.apply`.
