# ADR-0046: Network access to the control API: TLS on the remote control port, a generated certificate the client pins

- Status: Proposed
- Date: 2026-11-04
- Deciders: Salih (owner)

## Context

[ADR-0044](0044-control-api-protocol-and-security.md) decision 11 keeps the control API on loopback unless the user turns on network access, a separate setting, and requires TLS for every connection that is not loopback. Decision 9 lets a client send its bearer token only over loopback, IPC, or TLS whose certificate it verified, either through a CA or through a pinned fingerprint. The [control API spec](../specs/control-api.md) leaves the certificate open: "a generated self-signed certificate with a fingerprint the user pins, or a user-supplied one".

What exists today:

- `rbs-api-ws` serves WebSocket on loopback only. It has its own RFC 6455 framing and one I/O thread on the OS readiness poller (`polling`), with non-blocking sockets. It refuses a non-loopback address at `start`.
- `rbs-api` already has what remote peers need:
  - `PeerInfo` tells loopback and remote peers apart.
  - Scopes are limited per channel (`ScopeSet::for_channel`: `plugins` and `tokens` are never given to remote peers, and `admin` only with `allow_remote_admin`).
  - Pending-handshake and per-address caps, and authentication back-off per address.
  - The `Host` check accepts configured names and the addresses of bound interfaces (`UpgradePolicy`).
- `rbs-app` has the Remote control settings: on or off, the port, and access tokens (`rbs-remote-settings`, `remote-control.toml`).

Who connects from another computer: a Stream Deck or Companion host on the network, a tablet with a browser panel, or a script on another machine. Most of these users have no CA of their own. A design that needs one would leave network access unused, or push users towards turning security off.

Forces:

- **The token must not be sent to an unverified server** (ADR-0044 decision 9). Plain `ws://` on the network would expose it to anyone on the path.
- **Zero cost when unused** (ADR-0013). When network access is off, no TLS state, certificate or extra listener may exist. Loopback users pay nothing.
- **Layers** (P1). TLS and certificate code live in the adapter (`rbs-api-ws`). `rbs-api` stays free of it. Only `rbs-app` decides where files are and what is on.
- **Licences and builds** (ADR-0010). Dependencies must be GPL-3.0-compatible and must build on Windows, macOS and Linux without extra system tools.
- **No new latency or threads on the I/O path.** The I/O thread is not a hot path (hot-paths.md), but it serves every connection and must not block.

## Decision

1. **TLS library: `rustls` with the `ring` crypto provider, in `rbs-api-ws` only.**
   - `rustls` is a memory-safe library. Its `ServerConnection` does no I/O of its own, so it fits the existing non-blocking poll loop: the I/O thread passes socket bytes through `read_tls`/`process_new_packets`/`write_tls`, and the WebSocket code reads and writes plaintext as it does now. No new thread is added.
   - The `ring` provider is used because rustls' default provider (`aws-lc-rs`) needs CMake and, on Windows, NASM to build.
   - TLS 1.2 and 1.3 are offered, with rustls' default cipher suites. The ALPN protocol is `http/1.1`.
   - Licences: rustls is Apache-2.0, ISC or MIT; ring is Apache-2.0 AND ISC. Both are allowed by `deny.toml`.

2. **One port, the protocol detected per connection.**
   - With network access on, the WebSocket transport listens on all interfaces (`0.0.0.0` and `::`) at the remote control port, instead of `127.0.0.1` and `::1`.
   - It reads the first byte of each connection. `0x16` (a TLS handshake record) starts TLS. Anything else is plain HTTP, and plain HTTP is accepted only from a loopback peer.
   - A plain request from a non-loopback peer gets one fixed answer, `426 Upgrade Required` ("use wss://"), and is closed. Nothing it sent is used.
   - Loopback clients keep working unchanged, with `ws://localhost:<port>`, and may also use `wss://`.
   - The decision is made on the peer address the OS reports, never on headers.

3. **The certificate: generated by RBS, or the user's own.**
   - **Generated (the default).** When network access is first turned on, RBS makes a self-signed certificate:
     - An ECDSA P-256 key, valid for 10 years. Pinning, not expiry, is what protects it.
     - Subject alternative names `localhost`, the computer's host name, and the addresses of its interfaces at that moment. A client that pins does not depend on them; they help clients that check the name after pinning.
     - It is generated with `rcgen` (MIT or Apache-2.0) on its `ring` backend.
     - The certificate and key are stored as PEM next to `remote-control.toml`: `remote-control-cert.pem` and `remote-control-key.pem`. On Unix the key is mode 0600, and a key file that others can read or write is refused, like the settings file.
     - Settings shows the certificate's SHA-256 fingerprint (of its DER encoding, colon-separated hex, as browsers and Node show it) and the address `wss://<host name>:<port>`. The user enters or confirms the fingerprint once in the client.
     - "New certificate" in Settings replaces the certificate. Clients must then pin the new fingerprint; connected sessions are closed.
   - **The user's own.** Settings can instead point to a PEM certificate chain and key, for example from a CA the user runs. RBS uses them as they are, does not copy them, and reads them again when network access starts. A key file that others can read is refused, on Unix.
   - In both cases, ADR-0044 decision 9 applies to clients: they send the token only after the certificate verified, through a CA or the pinned fingerprint, and never after a mismatch. A client library RBS ships must implement pinning.

4. **Settings and defaults.**
   - "Allow access from other computers" sits under Remote control, is off by default, and needs remote control on.
   - When on, the section shows:
     - that RBS is reachable from the network, and at which address;
     - the fingerprint;
     - "Allow remote admin", off by default (`ServerConfig::allow_remote_admin`). Remote sessions get `read` and `control`, plus `admin` only with this setting. `plugins` and `tokens` stay local-only (already enforced by `ScopeSet::for_channel`).
   - Host names the user adds for `Host` checks are stored with these settings.
   - The settings live in `remote-control.toml` (new fields, with defaults, so existing files still load). `rbs-cli` keeps managing tokens only.

5. **Checks on the network path are unchanged, plus TLS limits.**
   - `Origin` and `Host` checks run after TLS, before the upgrade completes.
   - "An address of a bound interface" is the local address of the accepted socket (`getsockname`), so no interface listing is needed.
   - The TLS handshake counts as part of the upgrade:
     - The same deadline applies (10 s).
     - The same cap on connections still upgrading applies; it counts non-loopback peers only, as now.
     - The same per-address caps and authentication back-off apply.
   - rustls' buffer limits are set so that a peer cannot make the server hold more than its message limits allow (4 KiB of plaintext before authentication). Records over the TLS maximum are rejected by rustls.

6. **Zero cost.**
   - Off: nothing changes from today. The transport binds loopback and builds no TLS configuration, and no certificate is read or generated.
   - On: the TLS configuration is built once at start. Per connection, only TLS state is added, and only for connections that start TLS. The I/O thread still sleeps until the OS reports activity.

## Consequences

- Stream Deck hosts, tablets and scripts on other computers can control RBS without the user running a CA. The token never leaves the computer in clear.
- `rbs-api-ws` gains `rustls`, `ring` (through rustls) and `rcgen`. It becomes the workspace's only TLS stack. `ring` has a C and assembly part, built by `cc` with the platform compiler that the workspace already needs.
- The transport conformance suite runs a second time over TLS, with a test certificate. New tests:
  - a plain request from a non-loopback peer gets 426;
  - a TLS handshake that never finishes hits the upgrade deadline;
  - a byte-at-a-time TLS client works;
  - a wrong-fingerprint client never gets as far as sending a token (client-side test helper).
- On Windows, the first listen on all interfaces triggers the firewall prompt. That happens only when the user turns network access on, and the section says so.
- Users must pin the fingerprint once per client, and again after "New certificate". The Settings text and the docs explain it.
- No mutual authentication of clients by certificate. Tokens remain the client credential (ADR-0044); mTLS stays a later option.
- `rbs-app` gains a second settings area (network access) to design under the UI rules (U1–U21, design system tokens, glossary terms).

## Alternatives considered

- **Only a user-supplied certificate.** Most users have no CA, so network access would stay unused or be bypassed. Kept as an option, not the only way.
- **A separate TLS port next to the loopback port.** Two ports to explain and to open in firewalls, and loopback `wss://` would need yet another port. Per-connection detection on one port is simple, because the first byte of TLS and of HTTP never collide.
- **Plain `ws://` on the network with SCRAM or challenge-response authentication.** It protects the token, but not the commands, events or window titles that follow, and it allows tampering in transit. ADR-0044 already chose TLS.
- **`native-tls` / OpenSSL / SChannel / Secure Transport.** Three platform stacks with different behaviour and certificate stores, and OpenSSL is a system dependency on Linux. rustls is one implementation everywhere.
- **`aws-lc-rs` provider.** It is rustls' default, but needs CMake (and NASM on Windows) to build. `ring` needs only the C compiler already required.
- **An async runtime (tokio-rustls).** The transport has no async runtime (ADR-0044 decision 4 leaves that to adapters); adding one only for TLS would bring threads and dependencies that the sans-I/O API makes unnecessary.
- **Let's Encrypt or other ACME certificates.** They need a public domain name pointing at a home or studio network, which most users do not have.
