# ADR-0159: The studio host in its own toolkit-free crate, then split by concern

- Status: Proposed
- Date: 2026-11-20
- Deciders: salihcantekin

## Context

The studio host is the control thread that owns the `Studio`, the adapter registries and the scene collection, and answers the window's `studio_host::Command`s and the control API (ADR-0041 decision 7, ADR-0044). Today it lives inside the desktop shell crate `rbs-app`:

- `crates/rbs-app/src/studio_host.rs` is 18,516 lines, with `studio_host/` (20 files, 7,553 lines). `ApiTarget::run` is 1,797 lines, `Host::command` 1,056, `round` 264, `start` 247 (`docs/quality/size-baseline.toml`).
- The host uses 22 more `rbs-app` modules: the settings files (`record_profile`, `stream_profile`, `stream_destinations`, `calibration_file`, `canvas_profile`, `device_sync_file`, `loudness_settings`, `monitor_settings`, `replay_settings`, `recent_targets`, `text_timers`, `vertical_outputs`, `browser_profiles`), `user_session`, `edit_history`, `obs_import`, `levels`, `ui_thread`, and parts of `stream_key`, `add_ons`, `remote_control` and `browser_tree`. None of them names Slint.
- Its 15 test files (`crates/rbs-app/tests/studio_*.rs`, 14,364 lines) use no Slint, yet each is its own binary that links all of `rbs-app` with Slint and Skia (230 to 560 MB per binary, about 153 s of CPU for `rbs-app`'s test and example units, mostly linking; quality audit QS-01, `docs/quality/audit-2026-11.md`). A host change rebuilds the five UI crates. In the cloud, `rbs-app`'s affected tests run into the 30-minute limit.
- Every feature edits `studio_host.rs` (17 of 50 merges in the audit), so parallel work collides there, and a 1,800-line `match` cannot be reviewed.
- The host also calls adapters directly, which only composition roots may do (P1): `rbs_capture_sck::main_display` (macOS screen size at start), `rbs_mux_matroska::append_chapters` (markers into a finished MKV), `rbs_transport_file::file_url`, `rbs_browser_runner` and `rbs_browser_shm` through `browser_tree`, `rbs_add_ons_sys` through `AddOnsSetup::system`, `keyring` through `stream_key::SystemKeyStore`, and `rbs_api_ws`/`rbs_api_ipc` through `remote_control` (it needs only `ApiTokens` from there).

ADR-0144 accepted the direction (quality plan WP-12 to WP-14) and asked for this ADR before the move. The stability plan (WP-L) schedules it after the browser GPU work (ADR-0157) and the shutdown and control-thread changes (ADR-0156, `ControlOut`), which edit the same file.

## Decision

1. **A new crate `rbs-studio-host`** (library `rbs_studio_host`) holds the studio host and the modules it needs (decision 2). It contains no windowing, toolkit or OS binding code. The process model does not change: `rbs-app` still runs the host in its own process on the `rbs-studio` control thread (ADR-0041 decision 7), and the UI still talks to it only through `Command` and `Update`. This ADR decides where the code is compiled and what it may depend on; it does not decide ADR-0099 (the studio in its own process), which it only makes easier.
2. **What moves and what stays.** Moves: `studio_host.rs` and `studio_host/`, the settings-file modules listed in Context, `user_session`, `edit_history`, `obs_import`, `levels`, `ui_thread`, and from the four mixed modules only their toolkit- and adapter-free part: `stream_key`'s `KeyStore`, `MemoryKeyStore`, `ACCOUNT`, `account`, `vertical_account` and `hint`; `add_ons`' `AddOnsSetup`, catalog and constants; `remote_control`'s `ApiTokens` and `SlotFlags` (with a public constructor `ApiTokens::new`); `browser_tree`'s `EngineSlot` and `EngineRuntime`. Stays in `rbs-app`: windows and bindings (`main.rs`, `studio_ui.rs`, the pages), the platform adapter list (`platform.rs`), `browser_tree`'s runner and trees and `browser_gpu`, the `RemoteServer` and `network_access`, `SystemKeyStore` and `stream_key::system`, `AddOnsSetup::system` (as a free function in `rbs-app`), hotkeys, tray and the other OS glue.
3. **A layer class of its own, enforced.** `rbs-studio-host` gets the xtask class `StudioHost` and a row "Studio host" in the overview's layer table. It may depend on workspace crates of the classes Core (foundation and ports), Helper, Engine, Control (`rbs-api`), UI model (`rbs-ui`), Settings (`rbs-remote-settings`), User data, Add-ons, Importers, Recording model and Editor projects, on `rbs-system-probe` from the adapter support class, and on the external crates `serde`, `serde_json`, `toml` and `chrono`. It must not depend on an adapter, a control transport (`rbs-api-ws`, `rbs-api-ipc`), `rbs-log`, an app UI crate, a composition root, or any toolkit, windowing or OS binding crate. Only composition roots (class App) may depend on it. `cargo xtask check-layers` enforces this with a test for an allowed and a denied edge; another external crate needs an xtask change, reviewed like any layering change. Dev-dependencies may name the reference adapters (`rbs-capture-test`, `rbs-audio-io-test`, `rbs-vcam-test`, `rbs-text-test`, `rbs-browser-runner`), as the class is not one check-layers watches for test adapters.
4. **Adapters reach the host only through `HostConfig` or the registry.** The host keeps getting its adapters from the `RecordAdapters` closure of `StudioHost::spawn`. Each direct use in Context becomes a field of `HostConfig` that the composition root fills, with a trait or function type defined in the host crate:
   - `main_display: Option<fn() -> Option<MainDisplay>>`: `rbs-app` passes the ScreenCaptureKit probe on macOS; `None` keeps the current non-macOS path (the default screen target).
   - `chapters: Option<Arc<dyn ChapterWriter>>`: writes markers into a finished file; `rbs-app` implements it with `rbs-mux-matroska`. `None`: no chapters are written and the manifest keeps the markers, as today for a file another muxer wrote.
   - `browser: Option<Arc<dyn BrowserTrees>>`: creates the browser tree for a start, given the engine slot and the profiles folder, and returns it as an `rbs_sources::BrowserTree` plus the two questions the add-ons code asks (`in_use`, `needs_engine`). `rbs-app` implements it with `RunnerBrowserTree` and `resolve_runner` and sets the adapter LUID there (ADR-0157 decision 8); the `browser_runner` field goes away. `None`: no browser tree, so browser sources show as unavailable.
   - `file_url` moves to the port crate `rbs-transport` as a pure function; `rbs-transport-file` uses and re-exports it, so its callers do not change.
   - The key store and the add-ons setup are already `HostConfig` fields with trait objects; only their system implementations stay in `rbs-app` (decision 2).
   These seams are made in `rbs-app` first, one behaviour-neutral commit each, before the move.
5. **The public boundary is what `rbs-app` uses.** Public: `StudioHost` and its methods, `Command`, `Update` and the types they carry, `HostConfig` and its seam traits, the settings modules' file types and their read and write functions, `UserSession`, `ApiTokens`, `SlotFlags`, `levels` and `ui_thread`. Every other item stays `pub(crate)` or private; an item becomes public only when a composition root needs it. `Command` and `Update` are an in-process interface between the host and its roots, not a versioned contract: the control API (`rbs_api::Command`) stays the only external contract, and the one-command-path work (quality WP-20) shrinks `Command` later. `rbs-app`'s `lib.rs` re-exports the moved modules under their old names (`pub use rbs_studio_host::record_profile;`), so no `rbs-app` path changes in the move; the re-exports are removed when `main.rs` and `studio_ui.rs` are split (quality WP-15).
6. **The move is a pure move.** One commit moves the files with `git mv` and changes only paths, `use` lines, visibility (decision 5), `Cargo.toml` files and the feature `fault-injection` (it moves to the host crate; `rbs-app`'s feature forwards to it). No behaviour, name or signature changes. `cargo xtask check-size --lower --moved <old> <new>` (ADR-0144, implemented before the move) carries each ceiling to its new path. The crate keeps `rbs-app`'s `rust-version` (1.92) at the move; a lower one is a later change. The move lands when no other open change edits `studio_host.rs` or the moved modules, announced ahead through the coordinator.
7. **Tests move with the code, as one binary.** The unit tests move with their modules. The `studio_*.rs` files become modules of one test binary `crates/rbs-studio-host/tests/studio/main.rs`, which keeps the `fault-injection` feature on through a dev-dependency on the crate itself, as `rbs-app` does today. A test that needs something that stays in `rbs-app` (a real browser runner, a window) stays in `rbs-app`. The move commit records, as its measurement note, the host test build time, link time and binary sizes before and after on the same machine.
8. **Then the host is split by concern, inside the crate.** Modules `recording`, `stream`, `scenes`, `sources`, `outputs`, `projector` and `api` (the control API answers, one file per API namespace), each owning a state struct that is a field of `Host` and handler functions that `Host::command` and `ApiTarget::run` call; the dispatchers keep only the match that routes to them. The existing `studio_host/` modules keep their names. Each concern is its own commit, a move with no behaviour change, checked by the moved tests, and lowers `check-size`. Target: no file in the crate over 2,000 lines and no function over 200 (`record_profile.rs` is split too). Split commits do not wait for each other's review, but only one is open at a time.
9. **Order.** (a) The studio host's log lines (ADR-0158 follow-ups) land first. (b) The seams of decision 4, after the browser GPU work (ADR-0157) is on main, since the browser seam wraps its code. (c) `check-size --moved`. (d) The move. (e) The split. Work that only touches a moved module, such as making `UserSession::run` and `flush` asynchronous for import, export, new, rename and delete (stability plan WP-I follow-up, `docs/architecture/threads.md`), is done after the move in the new crate.

## Consequences

- Host tests build and link without Slint, Skia or the UI crates; `cargo test -p rbs-studio-host` iterates on the host alone, and `cargo xtask affected` no longer pulls `rbs-app`'s UI for a host-only change. The 15 test binaries become one.
- The host can no longer call an adapter or a toolkit by accident: check-layers fails. Adapter choices stay in the composition roots (P1), and `rbs-cli` or a later studio process (ADR-0099) can use the same host.
- New xtask class and test, overview row, `docs/architecture/threads.md` file paths, `docs/architecture/hot-paths.md` paths if any, size-baseline paths (`--moved`), `docs/status.md` and the quality audit's numbers are updated in the move commit. A short spec `docs/specs/studio-host.md` (boundary, `HostConfig` seams, threads, tests, implementation status) is written with the seams, before the move.
- `HostConfig` gets three fields and loses one; every test that builds a `HostConfig` uses `HostConfig::canvas`, so only the tests that pass a browser runner change.
- Costs: one large move commit that every open `rbs-app` branch must rebase over; re-exports in `rbs-app` for a while; one more crate to build. `rbs-app` keeps its other tests (UI, shots), which still link Slint.
- `rbs-transport` gains `file_url` (a pure function, std only), a port change covered by this ADR's review.
- Not changed: ADR-0041 decision 7 (process and thread model), the control API, the scene format, the user data formats, the hot paths (the host holds no code listed in `hot-paths.md`; a split commit that touches code called from a hot path follows rule 12).

## Alternatives considered

- **Split `studio_host.rs` but leave it in `rbs-app`.** Fixes review size and merge collisions but not the build and test cost, and keeps the host able to call any adapter.
- **Move without seams, with the host allowed to depend on adapters.** A smaller first step, but it breaks P1 (only composition roots name adapters), puts OS-specific adapters and `cfg` blocks in a toolkit-free crate, and makes its tests link vendor code.
- **Move `browser_tree` into the host with `rbs-browser-runner`.** Keeps one more file together, but brings an adapter and the Windows D3D interop of ADR-0157 into the host.
- **Put the host into `rbs-record` or another engine crate.** Engine crates may not see the control API, user data or settings files; it would mix layers.
- **Two crates at once (settings files, then the host).** The settings files are used only by the host and `rbs-app`; one crate is one boundary to review. They can be split out later if another root needs them alone.
- **Do it inside ADR-0099's separate studio process.** That ADR is Proposed with open blocking concerns; the crate is useful now and does not depend on it.
