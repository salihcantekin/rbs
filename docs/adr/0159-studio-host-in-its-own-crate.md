# ADR-0159: The studio host in its own toolkit-free crate, then split by concern

- Status: Accepted (three independent review rounds and the owner's approval 2026-11-20, see Review)
- Date: 2026-11-20
- Deciders: salihcantekin

## Context

The studio host is the control thread that owns the `Studio`, the adapter registries and the scene collection, and answers the window's `studio_host::Command`s and the control API (ADR-0041 decision 7, ADR-0044). Today it lives inside the desktop shell crate `rbs-app`:

- `crates/rbs-app/src/studio_host.rs` is 18,516 lines, with `studio_host/` (20 files, 7,553 lines). `ApiTarget::run` is 1,797 lines, `Host::command` 1,056, `round` 264, `start` 247 (`docs/quality/size-baseline.toml`).
- The host uses 22 more `rbs-app` modules: the settings files (`record_profile`, `stream_profile`, `stream_destinations`, `calibration_file`, `canvas_profile`, `device_sync_file`, `loudness_settings`, `monitor_settings`, `replay_settings`, `recent_targets`, `text_timers`, `vertical_outputs`, `browser_profiles`), `user_session`, `edit_history`, `obs_import`, `levels`, `ui_thread`, and parts of `stream_key`, `add_ons`, `remote_control` and `browser_tree`. None of them names Slint.
- Its 15 test files (`crates/rbs-app/tests/studio_*.rs`, 14,364 lines) use no Slint, yet each is its own binary that links all of `rbs-app` with Slint and Skia (230 to 560 MB per binary, about 153 s of CPU for `rbs-app`'s test and example units, mostly linking; quality audit QS-01, `docs/quality/audit-2026-11.md`). A host change relinks every one of them against the UI crates. In the cloud, `rbs-app`'s affected tests run into the 30-minute limit.
- Every feature edits `studio_host.rs` (17 of 50 merges in the audit), so parallel work collides there, and a 1,800-line `match` cannot be reviewed.
- The host also calls adapters directly, which only composition roots may do (P1): `rbs_capture_sck::main_display` (macOS screen size at start), `rbs_mux_matroska::append_chapters` (markers into a finished MKV), `rbs_transport_file::file_url`, `rbs_browser_runner` and `rbs_browser_shm` through `browser_tree`, `rbs_add_ons_sys` through `AddOnsSetup::system`, `rbs_system_probe` (free space, memory and OS version for recording protection, `studio_host/protection.rs`, `studio_host.rs:8329`), `keyring` through `stream_key::SystemKeyStore`, and `rbs_api_ws`/`rbs_api_ipc` through `remote_control` (it needs only `ApiTokens` from there).

ADR-0144 accepted the direction (quality plan WP-12 to WP-14) and asked for this ADR before the move. The stability plan (WP-L) schedules it after the browser GPU work (ADR-0157) and the shutdown and control-thread changes (ADR-0156, `ControlOut`), which edit the same file.

## Decision

1. **A new crate `rbs-studio-host`** (library `rbs_studio_host`) holds the studio host and the modules it needs (decision 2). It contains no windowing, toolkit or OS binding code. The process model does not change: `rbs-app` still runs the host in its own process on the `rbs-studio` control thread (ADR-0041 decision 7), and the UI still talks to it only through `Command` and `Update`. This ADR decides where the code is compiled and what it may depend on; it does not decide ADR-0099 (the studio in its own process), which it only makes easier.
2. **What moves and what stays.** Moves: `studio_host.rs` and `studio_host/`, the settings-file modules listed in Context, `user_session`, `edit_history`, `obs_import`, `levels`, `ui_thread`, and from the four mixed modules only their toolkit- and adapter-free part: `stream_key`'s `KeyStore`, `MemoryKeyStore`, `ACCOUNT`, `account`, `vertical_account` and `hint`; `add_ons`' `AddOnsSetup`, catalog, `target()` and constants; `remote_control`'s `ApiTokens` and `SlotFlags` (with a public constructor `ApiTokens::new`); `browser_tree`'s `EngineSlot`, `EngineRuntime` and the runner-less tree of decision 4. Stays in `rbs-app`: windows and bindings (`main.rs`, `studio_ui.rs`, the pages), the platform adapter list (`platform.rs`), `browser_tree`'s runner and trees and `browser_gpu`, the `RemoteServer` and `network_access`, `SystemKeyStore` and `stream_key::system`, `AddOnsSetup::system` (as a free function in `rbs-app`), `OsProbe` and `SystemProbeFactory::os` (as a free function `system_probe::factory` in `rbs-app`, from `studio_host/protection.rs`) and the call of `rbs_system_probe::os_version`, hotkeys, tray and the other OS glue.
3. **A layer class of its own, enforced.** `rbs-studio-host` gets the xtask class `StudioHost` and a row "Studio host" in the overview's layer table. It may depend on workspace crates of the classes Core (foundation and ports), Helper, Engine, Control (`rbs-api`), UI model (`rbs-ui`), Settings (`rbs-remote-settings`), User data, Add-ons, Importers, Recording model and Editor projects, and on the external crates `serde`, `serde_json`, `toml` and `chrono`. It must not depend on an adapter, an adapter support crate, a control transport (`rbs-api-ws`, `rbs-api-ipc`), `rbs-log`, an app UI crate, a composition root, or any toolkit, windowing or OS binding crate. Only composition roots (class App) may depend on it; the crate's own dev-dependency on itself (decision 7) is exempt. `cargo xtask check-layers` enforces this with a test for an allowed and a denied edge; another external crate needs an xtask change, reviewed like any layering change. Dev-dependencies are checked too: they may name adapters for tests (today `rbs-capture-test`, `rbs-audio-io-test`, `rbs-vcam-test`, `rbs-text-test`, `rbs-media-decode-test`, `rbs-mux-matroska`, `rbs-mux-wav`, `rbs-codec-pcm`, `rbs-codec-mf` with `testing`, `rbs-transport-file`, `rbs-add-ons-sys`), but never a composition root, an app UI crate or a toolkit crate, so the tests cannot bring the Slint link back. `denied()` in xtask today watches dev edges only for the Core, Helper, Support and Engine classes, so it gets a `StudioHost` branch of its own, placed before the early return for targets that are not adapter-like (the ordinary `deny()` rules would also refuse the allowed adapter dev edges), and its test covers an allowed adapter dev edge, the exempt self edge and a denied `slint` dev edge. The host depends on `rbs-gpu` without the `preview-layer` feature (P8: no window code below the roots); a seam commit makes `rbs_gpu::share::DEFAULT_RETIRE_POLL` and `DEFAULT_RETIRE_AFTER` (plain `Duration`s that `preview_hold` reads) available without that feature, and `cargo xtask device-check` builds `-p rbs-studio-host` alone on macOS and Windows, because a workspace build turns the feature on through `rbs-app` and would hide the gap.
4. **Adapters reach the host only through `HostConfig` or the registry.** The host keeps getting its adapters from the `RecordAdapters` closure of `StudioHost::spawn`. Each direct use in Context becomes a field of `HostConfig` that the composition root fills, with a trait or function type defined in the host crate:
   - `main_display: Option<fn(&SourceTypes) -> Option<MainDisplay>>`. `None` means no main display is known. The host offers today's non-macOS behaviour as a public function `display_from_default_screen`, which `rbs-app` passes on Windows and Linux; on macOS it passes the ScreenCaptureKit probe. A root that forgets the field therefore never opens a screen listing by accident (on macOS that would open ScreenCaptureKit shareable content).
   - `chapters: Option<Arc<dyn ChapterWriter>>` with `fn append(&self, file: &mut File, chapters: &[Chapter]) -> Result<Applied, String>`, where `Chapter` (start in ns, title) is the host's own type and `Applied` is `Written` or `NotSupported` (the file takes no chapters: another muxer wrote it, or it could not seek). The three outcomes of today's `write_chapters` stay: written, `Ok` with markers only in the manifest, and an I/O error. `rbs-app` implements it with `rbs-mux-matroska`; the chapter test (`slow_a_matroska_master_gets_its_markers_as_chapters`, cited by the recording spec) passes a writer built from its `rbs-mux-matroska` dev-dependency. `None`: no chapters are written and the manifest keeps the markers.
   - `browser: Option<Arc<dyn BrowserTrees>>`, whose `create(&self, engine: Arc<EngineSlot>, profiles: Option<PathBuf>, gpu: &Arc<GpuContext>)` returns `Arc<dyn HostBrowserTree>`, where `trait HostBrowserTree: rbs_sources::BrowserTree { fn in_use(&self) -> bool; fn needs_engine(&self) -> bool; }` holds the two questions the add-ons code asks; the host upcasts it to `Arc<dyn BrowserTree>` for the sources (trait upcasting is stable at the crate's `rust-version`). It is called where `start` builds the tree today, after the GPU context exists, so an implementation can read what it needs from the context (the adapter LUID of ADR-0157 decision 8) without another seam change. `rbs-app` implements it with `RunnerBrowserTree` and `resolve_runner`; the `browser_runner` field goes away. `None` installs the host's own runner-less tree, which behaves as `RunnerBrowserTree` without a runner does today: `unavailable()` answers `HELPER_MISSING`, so the source releases its slot and shows Unavailable with `helper_missing` (add-ons spec), `in_use` and `needs_engine` are false, and the profiles folder is kept. `RBS_BROWSER_HELPER` is then read only by `rbs-app`'s `resolve_runner`: host tests always get the runner-less tree unless they pass a fake, which is more deterministic (ADR-0032) and is a change for a developer who sets that variable. The add-ons test that needs a runner that needs the engine uses a fake `BrowserTrees` whose `needs_engine` is true.
   - `file_url`, its escaping and its round-trip tests move to the port crate `rbs-transport` as pure functions (std only); `rbs-transport-file` uses and re-exports them, so its callers do not change.
   - The key store, the add-ons setup and the system probe (free space and memory) are already `HostConfig` fields with trait objects; only their system implementations stay in `rbs-app` (decision 2).
   - `os_version: Option<String>`, filled by the root from `rbs_system_probe::os_version()`, for the calibration key (`Host::this_computer`). `None` gives `""`, today's fallback when the OS name cannot be read; entries saved with an OS name do not match a key without one, so a root must always pass it.
   - Tests: `HostConfig::canvas` leaves `main_display` at `None`; a host test passes `display_from_default_screen` and checks the test screen's size reaches the canvas choice, since no test asserts it today.
   These seams, the renames that leave the system parts in `rbs-app` (`AddOnsSetup::system` and `SystemProbeFactory::os` become free functions there), and the new public items they need (such as `ApiTokens::new`), are made in `rbs-app` first, one behaviour-neutral commit each, before the move. The seams do not depend on ADR-0157: if that ADR lands later, it changes only `rbs-app`'s `BrowserTrees` implementation.
5. **The public boundary is what `rbs-app` uses.** Public: `StudioHost` and its methods, `Command`, `Update` and the types they carry, `HostConfig` and its seam traits, the settings modules' file types and their read and write functions, `UserSession`, `ApiTokens`, `SlotFlags`, `levels` and `ui_thread`. Every other item stays `pub(crate)` or private; an item becomes public only when a composition root or the crate's own integration tests need it (today, for example, `protection::SystemProbeFactory`, `ExportRigMaker`, `CalibrationSetup`, `OutputCanvas`, `attributes_browser_size`, `replay::ReplayState`). `Command` and `Update` are an in-process interface between the host and its roots, not a versioned contract: the control API (`rbs_api::Command`) stays the only external contract, and the one-command-path work (quality WP-20) shrinks `Command` later. `rbs-app`'s `lib.rs` re-exports the moved modules under their old names (`pub use rbs_studio_host::record_profile;`), so no `rbs-app` path changes in the move. The four mixed modules (`add_ons`, `stream_key`, `remote_control`, `browser_tree`) stay as `rbs-app` modules that re-export the moved part (`pub use rbs_studio_host::add_ons::*;`) beside their local items; the re-exports are removed when `main.rs` and `studio_ui.rs` are split (quality WP-15).
6. **The move is a pure move.** One commit moves the files with `git mv` and changes only paths, `use` lines, visibility (decision 5), `Cargo.toml` files, a crate `clippy.toml` and the feature `fault-injection` (it moves to the host crate; `rbs-app`'s feature forwards to it). No behaviour, name or signature changes. The crate's `clippy.toml` repeats the root's test allowances and every `rbs-app` entry that does not name a toolkit or dialog crate (`std::thread::sleep`, the `println!` family and `dbg!`, ADR-0055), since clippy reads only the nearest file and these lints would otherwise go silent. `src/add_ons.rs` reads `../../rbs-browser-cef/cef-pin.toml` through a relative `include_str!`; the new crate sits at the same depth under `crates/`, so the path still resolves, and the move commit checks it. `cargo xtask check-size --lower --moved <old> <new>` (ADR-0144, implemented before the move) carries each ceiling to its new path. The crate keeps `rbs-app`'s `rust-version` (1.92) at the move; a lower one is a later change. The move lands when no other open change edits `studio_host.rs` or the moved modules, announced ahead through the coordinator.
7. **Tests move with the code, as one binary.** The unit tests move with their modules. The `studio_*.rs` files become modules of one test binary `crates/rbs-studio-host/tests/studio/main.rs`, which keeps the `fault-injection` feature on through a dev-dependency on the crate itself, as `rbs-app` does today. Each file keeps its own helpers in the move; a shared `common` module (one `GpuContext` per process instead of one per old file) follows in its own commit. A test that needs something that stays in `rbs-app` (a real browser runner, a window) stays in `rbs-app`. The move commit records, as its measurement note, the host test build time, link time and binary sizes before and after on the same machine.
8. **Then the host is split by concern, inside the crate.** Modules `recording`, `stream`, `scenes`, `sources`, `outputs`, `projector` and `api` (the control API answers, one file per API namespace), each owning a state struct that is a field of `Host` and handler functions that `Host::command` and `ApiTarget::run` call; the dispatchers keep only the match that routes to them. The existing `studio_host/` modules keep their names. Each concern is its own commit, a move with no behaviour change, checked by the moved tests, and lowers `check-size`. Target: no file in the crate over 2,000 lines and no function over 200 (`record_profile.rs` is split too). Split commits do not wait for each other's review, but only one is open at a time.
9. **Order.** (a) The studio host's log lines (ADR-0158 follow-ups) land first. (b) The seams of decision 4, once no other open change edits `start` or `browser_tree.rs` (the browser GPU work, stability plan WP-A, does today). (c) `check-size --moved`. (d) The move. (e) The split, followed by performance packages G-02, G-04 and G-08, which edit the same code and are written in the new modules. Work that only touches a moved module, such as making `UserSession::run` and `flush` asynchronous for import, export, new, rename and delete (stability plan WP-I follow-up, `docs/architecture/threads.md`), is done after the move in the new crate.

## Consequences

- The 15 host test binaries become one that links no Slint, Skia or UI crate, and `cargo test -p rbs-studio-host` iterates on the host alone. `cargo xtask affected` still selects `rbs-app` for a host change, since it depends on the host, so `xtask verify` keeps building and running `rbs-app`'s tests then; the gain there is the 15 binaries that no longer link the UI.
- The host can no longer call an adapter or a toolkit by accident: check-layers fails. Adapter choices stay in the composition roots (P1), and `rbs-cli` or a later studio process (ADR-0099) can use the same host.
- New xtask class and test, overview row, `docs/architecture/threads.md` file paths, `docs/architecture/hot-paths.md` paths if any, size-baseline paths (`--moved`), `docs/status.md` and the quality audit's numbers are updated in the move commit. The specs that name the moved code are updated with the seams or the move: `add-ons.md` (no runner means `helper_missing`), `scene-sources.md` (`resolve_runner`), `recording.md` (chapters through `ChapterWriter`). A short spec `docs/specs/studio-host.md` (boundary, `HostConfig` seams, threads, tests, implementation status) is written with the seams, before the move.
- `HostConfig` gets three fields and loses one; every test builds it from `HostConfig::canvas`. Tests that change: the add-ons test that passes a runner (a fake `BrowserTrees`) and the Matroska chapter test (passes a `ChapterWriter`).
- Layer metadata in `Cargo.toml` (quality audit QN-07) is not adopted here; the class is one more arm of the xtask `match` until QN-07 (quality wave Q3) replaces the `match` for every crate.
- Costs: one large move commit that every open `rbs-app` branch must rebase over; re-exports in `rbs-app` for a while; one more crate to build. `rbs-app` keeps its other tests (UI, shots), which still link Slint.
- `rbs-transport` gains `file_url` (a pure function, std only), a port change covered by this ADR's review.
- Not changed: ADR-0041 decision 7 (process and thread model), the control API, the scene format, the user data formats, the hot paths (the host holds no code listed in `hot-paths.md`; a split commit that touches code called from a hot path follows rule 12).

## Alternatives considered

- **Split `studio_host.rs` but leave it in `rbs-app`.** Fixes review size and merge collisions but not the build and test cost, and keeps the host able to call any adapter.
- **Move without seams, with the host allowed to depend on adapters.** A smaller first step, but it breaks P1 (only composition roots name adapters), puts OS-specific adapters and `cfg` blocks in a toolkit-free crate, and makes its tests link vendor code.
- **Move `browser_tree` into the host with `rbs-browser-runner`.** Keeps one more file together, but brings an adapter and the Windows D3D interop of ADR-0157 into the host.
- **Put the host into `rbs-record` or another engine crate.** Engine crates may not see the control API, user data or settings files; it would mix layers.
- **Two crates at once (settings files, then the host).** The settings files are used only by the host and `rbs-app`; one crate is one boundary to review. They can be split out later if another root needs them alone.
- **Do it inside ADR-0099's separate studio process.** That ADR is Proposed with open blocking concerns; the crate is useful now and does not depend on it.

## Review

- **Round 1: independent AI session, 2026-11-20, changes requested (10 concerns).** -> resolution in this revision:
  1. A `None` browser seam would fail browser sources instead of answering `helper_missing` (add-ons spec) -> `None` installs a runner-less tree with today's behaviour; the runner test uses a fake `BrowserTrees`.
  2. The browser seam could not carry the adapter LUID of ADR-0157, and tying the order to that Proposed ADR blocked the move on hardware -> `create` gets the `GpuContext` and runs after it exists; the order waits only for no other open change on `start`/`browser_tree.rs`.
  3. A `None` chapters seam breaks the chapter test and the outcomes were unspecified -> `ChapterWriter::append` with host-owned `Chapter` and `Applied`; the test passes a writer; Consequences corrected.
  4. A `None` main display ran the screen listing (ScreenCaptureKit on macOS) -> `None` means no display; `display_from_default_screen` is passed explicitly off macOS.
  5. Build gains overstated (`affected` still selects `rbs-app`; the UI crates are relinked, not rebuilt) -> Context and Consequences restated.
  6. The host's ADR-0055 lints live in `rbs-app/clippy.toml` -> the crate gets its own `clippy.toml` (decision 6).
  7. `rbs-system-probe` contradicted "no OS binding code" -> dropped from the allow-list; the system probe stays in the root behind the existing `system_probe` field (and, after round 2, `os_version` through its own field).
  8. Dev-dependencies unchecked and listed incompletely -> class's dev edges deny roots, app UI and toolkit crates; list completed, `rbs-browser-runner` dropped.
  9. Specs naming moved code and QN-07 -> specs listed; QN-07 deferred; G-02/G-04/G-08 ordered after the split.
  10. Nits -> shared test `common` module as a follow-up, `ApiTokens::new` in a seam commit, `rbs-gpu` without `preview-layer`, `file_url` escaping and tests move with it, `include_str!` path noted.
- **Round 2: independent AI session, 2026-11-20, changes requested (1 blocking, 4 should-fix, 3 nits).** Items 1-6 and 8-10 of round 1 confirmed against the code. -> resolution in this revision:
  1. Blocking: `os_version` (`studio_host.rs:8329`) and `OsProbe`/`SystemProbeFactory::os` (`studio_host/protection.rs`) still named `rbs-system-probe` -> `HostConfig::os_version` seam; `OsProbe` and the factory move to `rbs-app`; a root must always pass the OS name.
  2. The pure move needed renames it forbids -> listed among the seam commits of decision 4.
  3. Re-exports collide for the four mixed modules -> they stay `rbs-app` modules that re-export the moved part (decision 5).
  4. `BrowserTrees::create`'s return type unnamed -> `Arc<dyn HostBrowserTree>`, trait named.
  5. The dev-edge rule is not in xtask and the self edge needs an exemption -> `StudioHost` arm in `denied()`, self edge exempt, both in the xtask test.
  6-8. Nits -> `include_str!` citation fixed; `RBS_BROWSER_HELPER` change stated; a test passes `display_from_default_screen`.
- **Round 3: independent AI session, 2026-11-20, changes requested (1 should-fix, 2 nits); all round-2 items confirmed, no contradictions, the moved code's dependencies all inside the decision-3 allow-list.** -> resolution in this revision:
  1. `preview_hold` reads two `rbs-gpu` constants exported only under `preview-layer`, so the crate alone would not build on macOS and Windows -> seam commit exports them without the feature; `device-check` builds the crate alone on both.
  2. The xtask dev-edge rule must be its own branch before the early return -> stated in decision 3.
  3. Public items the integration tests and `main.rs` need, and `add_ons::target()` -> decisions 2 and 5.
