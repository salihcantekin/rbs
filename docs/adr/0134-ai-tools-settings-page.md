# ADR-0134: Start AI tools from Settings and hand the user a ready connection line

- Status: Accepted
- Date: 2026-11-16
- Deciders: Salih (owner)
- Owner decision: 2026-11-16, approved after the round-4 independent review (project thread).
- Owner direction: 2026-11-16, project thread: a Settings page where the user starts MCP, can have it start when RBS opens, it stops when RBS closes, and starting it produces the configuration the user pastes into their AI tools. Of the two ways offered (an MCP server inside RBS, or this page in front of the separate `rbs-mcp`), the owner chose the page with `rbs-mcp` over stdio.
- Builds on: [ADR-0013](0013-zero-cost-when-unused.md), [ADR-0044](0044-control-api-protocol-and-security.md), [ADR-0052](0052-ai-agent-control-through-mcp.md), [ADR-0056](0056-keep-running-after-the-main-window-closes.md), [ADR-0113](0113-experience-level-and-first-run.md)
- Amends: ADR-0052 decision 3 (additions: a token kind and a refusal reason; changes: an explicit `--token-file` wins over `RBS_TOKEN`, and `rbs-mcp` without a usable token waits in a hint state instead of refusing to start) and decision 11 (the hint text); ADR-0044 decision 5 (when the API thread exists), decision 9 (one non-uniform refusal, same-user IPC only), decision 10 (no hello scopes on IPC while only AI tools are started) and decision 15 (when the IPC endpoint is served); replaces ADR-0052's "Agents" settings follow-up and its `rbs-cli token create --agent` writing the default token file
- Spec: [mcp-server](../specs/mcp-server.md), [control-api](../specs/control-api.md), [ui-design-system](../specs/ui-design-system.md) (follow-up with the UI proposal)

## Context

ADR-0052 (Accepted) makes `rbs-mcp` a separate program that an AI tool (Claude Desktop, Claude Code, Cursor, VS Code and other MCP clients) starts over stdio; `rbs-mcp` reaches RBS through the control API over local IPC with its own token, narrowed on IPC, and the API enforces scopes, effects and the "Allow actions that cannot be undone" permission. Its follow-ups name "an Agents entry in Settings" that makes the agent token and its file and shows the line to add RBS to an agent, but do not say how it behaves.

Today the API thread and the IPC endpoint exist only while "Allow remote control" is on: `rbs-app` `RemoteServer` always starts the loopback WebSocket transport and adds IPC as an optional extra whose failure is not fatal, and a network or certificate change restarts the server and drops every session. A user who only wants an AI tool must therefore open a port they do not need, make a token by hand, save it to a file with the right mode and write an MCP client configuration (JSON whose shape differs per AI tool, with escaped Windows paths). Each step is a place to fail or to leak the token. `rbs-mcp` exists as a crate, answers stdio and has no IPC session yet (docs/status.md).

Forces: P13 (nothing runs while unused); the token must never appear in configuration text; the API, not the page, bounds what `rbs-mcp` can do; the user expects one button and a line to copy.

Threat model (unchanged from ADR-0052): the bound holds for the `rbs-mcp` connection only. Any program running as the same OS user, including an AI tool allowed to run shell commands, can run `rbs-cli` over IPC with all scopes or read the token file. Stop ends what `rbs-mcp` can do; it is not a boundary against same-user programs, and the page says so in its help.

## Decision

1. **A Settings section, "AI tools".** In the Control group, after Remote control, an advanced section (ADR-0113: drawn with the `standard` and `pro` experience). It holds a status line, a **Start** / **Stop** button, a Toggle **"Start when RBS opens"** (off by default), the access of the AI tools token, the Toggle "Allow actions that cannot be undone" (off by default; ADR-0052 decision 4; local-only per its decision 1), the connection line (decision 5), "New token" and a list of recent actions (decision 7). Access is View only, Control or Full control, the existing `Access::scopes` (`read`; `read` + `control`; `read` + `control` + `admin`), Control by default; the token never gets `plugins` or `tokens`. The exact layout, icon and texts come with a UI proposal (dark and light screenshots) approved by the owner before implementation (CLAUDE.md rule 16); the page uses only library components and tokens.

2. **Server states.** The API thread exists, and the IPC transport is served, while remote control is on **or** AI tools are started (amends ADR-0044 decisions 5 and 15); the WebSocket transport only while remote control is on.

   | Remote control | AI tools | WebSocket | IPC | API thread | AI tools token |
   | --- | --- | --- | --- | --- | --- |
   | off | stopped | no | no | no | not accepted (no endpoint) |
   | off | started | no | yes, token sessions only | yes | accepted on IPC |
   | on | stopped | yes | yes (optional, as today) | yes | refused on IPC with `ai_tools_off` once the hash matches; otherwise `auth_failed` |
   | on | started | yes | yes | yes | accepted on IPC |

   - **Remote control off, AI tools started:** IPC accepts only sessions that send `session.authenticate` with a token; `session.hello` there grants no scopes (amends ADR-0044 decision 10 for this state). The `tokenless_ipc` flag in the token slot says which. With it off, a same-user IPC `session.hello` leaves the session waiting for authentication, as on WebSocket (`HelloResult.scopes` null, the handshake timeout applies), and `session.authenticate` then grants the token's scopes: the one case where it grants rather than narrows. When the flag turns off (remote control off while AI tools stay started), tokenless sessions are closed; a state-machine test covers both directions. Panel tokens from `remote-control.toml` are then also accepted on IPC (new, harmless for a same-user peer). `rbs-cli`, which has no token option, answers a `not_authenticated` there with "turn on remote control, or stop AI tools", and its `token` commands refuse with the same text rather than editing files under a running server. So starting AI tools gives other same-user programs nothing they could not already get by reading the token file. `rbs-cli` uses a token in this state, or remote control.
   - **Start** makes sure the token file and entry exist (decision 3), then starts the server with IPC required: if IPC cannot be served (a second RBS holds the lock, the socket directory is unsafe, the pipe name is taken), or the config directory cannot be written, Start fails as a whole, nothing is served for AI tools, and the status line says why. With remote control on, Start adds IPC to the running server if it is missing, without dropping WebSocket sessions.
   - **Stop and Start** change an "AI tools started" flag carried in the same shared slot as the token store (`TokenHandle`), applied atomically with it. The slot value is `{store, ai_tools_started, tokenless_ipc}`, where `store` is the union of both files; one composer in `rbs-app` builds it under the settings lock, and every writer goes through it (`rbs_remote_settings::token_command` reads and writes both files and never sets the slot from `remote-control.toml` alone), so a `tokens.create` or `tokens.revoke` while AI tools are started keeps their entry, flag and sessions. Because the flag rides that slot, Start and Stop are ordered against every `session.authenticate` exactly as a revocation is today (no new inbox input; ADR-0044 decision 5's three inputs stay). Stop closes every session of the AI tools token (a new `CloseReason` beside `Revoked`): a request already forwarded to the control thread finishes and is audited, its answer is discarded; requests queued behind it are dropped; the IPC connection is closed with the close frame code 1001 ("going away", IPC framing). With remote control off the API thread and the IPC transport stop and the socket file is removed (Windows: the pipe is closed).
   - Turning remote control on or off while AI tools are started keeps the AI tools sessions (only the WebSocket transport starts or stops). A network or certificate change (`restart_remote`) restarts only the WebSocket transport. Both need `RemoteServer` split into the API thread and optional, separately started and stopped transports, with a settable `allow_remote_admin`: a prerequisite (decision 9).
   - **Start when RBS opens:** once the studio host is running, RBS starts AI tools as by Start. If the host does not start, or stops later, AI tools stop with it and the status line says why; when the host comes back, they start again while the Toggle is on. Headless runs (`rbs-cli`, no desktop app) do not read it. Quitting RBS stops AI tools; closing the window while RBS keeps running (ADR-0056) does not.
   - Saved in a file of its own, `ai-tools.toml` in the config directory (`format_version = 1`, `start_on_open`, and the AI tools token entry: name, hash, access, irreversible permission), written with the same private write and lock as `remote-control.toml`. `remote-control.toml` does not change, so an older RBS never sees the entry and never refuses or rewrites the remote control file. The server's `TokenStore` is the union of both files, each entry with its `kind`. A test runs an older reader on a profile written by the new one.

3. **One AI tools token, made by RBS, kept in a file.**
   - The token is a token store entry with `kind = "ai_tools"` and the reserved name `AI tools`, which the name check refuses for user tokens. RBS's own operations on it go by `kind` and hash, never by name; `tokens.revoke` with the reserved name revokes every `ai_tools` entry, and `tokens.list` shows each entry with its `kind` (a test revokes in the middle of a rotation). A user token already named `AI tools` is renamed to the first free `AI tools (n)` on the first Start (written to `remote-control.toml` in its current format, and said on the page); its panel reconnects, as after any rename. At most one such entry is current; an entry being rotated out is revoked by its hash. Audit events carry the caller's `kind`. `kind` is never written to `remote-control.toml`, so an older RBS reading that file is safe by construction. `rbs-api` `TokenStore` and the session state machine gain the kind and an "AI tools started" flag; the check is in the pure session state machine and tested on `TestClock`. An `ai_tools` token is accepted only on a same-user IPC session (as ADR-0052 narrowing); on WebSocket it gets `auth_failed`, uniform as before. On IPC, after the hash matched and only then, a stopped AI tools gives `not_permitted` with `data.reason: "ai_tools_off"` and closes; this is the one exception to ADR-0044 decision 9's uniform failure, limited to same-user IPC peers, who could read the token file anyway.
   - Only the local user makes or changes it: no API method creates an `ai_tools` entry, sets or changes `kind`, or changes its access or permission (`tokens.create` takes no `kind`). Changing the access or the Toggle on the page is a local store update (new in `rbs-remote-settings`): it saves the file, then closes the token's sessions, as any token change (`set_tokens` compares `kind` and the permission too, not only name, hash and scopes); `rbs-mcp` reconnects with what the token allows now. `tokens.list` shows the entry with its `kind`; `tokens.revoke` of it removes the entry and leaves the file; while started, the status line then says "The AI tools token was revoked" with "New token", and the next Start makes a new pair. The Remote control page's token list does not show it.
   - **File:** `agent-token` in the config directory (ADR-0052 decision 3 default). Order for a first Start and for "New token": make the token, add its hash and save `ai-tools.toml`, write the token file, then revoke the old entry; a crash leaves at worst an extra valid entry, never a file without one. The file is written to a new temporary file in the same directory created exclusively with its final permissions (Unix `O_CREAT | O_EXCL`, mode 0600 at creation; Windows inheriting the user-only folder ACL), flushed and synced, then renamed over the old one, and the directory synced. On Windows a replace refused because `rbs-mcp` holds the file open is retried a few times, then Start or "New token" fails with the reason shown and the new entry is revoked again. **Start checks the file:** missing, unreadable, or a token whose hash is not the current `ai_tools` entry's (including a token of another kind) leads to "New token"; the page says when the file held a token of another kind. Start then revokes every `ai_tools` entry except the one matching the file, which settles a crash in the middle of a rotation.
   - **One writer of `agent-token`.** Only this routine writes the default file. `rbs-cli token create --agent` (ADR-0052 decision 4) makes or rotates the same `ai_tools` entry through the same local routine and refuses another path as default; a token of another kind is never written there. While the IPC endpoint lock is held (an RBS, desktop or headless, serves remote control or AI tools), `--agent` refuses and points to Settings, AI tools, because the running server would keep the old store; and Start always re-reads `ai-tools.toml`, so a change made while nothing served is picked up.
   - The page never shows the token, and no generated line contains it.

4. **What `rbs-mcp` reads.** It reads the token file again on every (re)connection, so a rotation needs no restart of the AI tool. It opens the file only to read it and closes it at once (on Windows with `FILE_SHARE_DELETE`), so a replace rarely needs the retry of decision 3. An explicit `--token-file` wins over `RBS_TOKEN` (amends ADR-0052 decision 3's precedence), so a stray environment variable cannot defeat rotation or the hint mode; the generated line always passes it.

5. **The connection line is generated, never edited by hand.** For the AI tool the user picks (a drop-down: Claude Desktop, Claude Code, Cursor, VS Code, Other), the page shows the text to paste, a Copy button and where it goes (file name or command). It names `rbs-mcp` by its absolute path and passes `--token-file <absolute path>`, nothing else. `rbs-mcp` ships in the same package as `rbs` (macOS: in the app bundle beside the main executable, signed like it; Windows and Linux: beside `rbs`), found from the app's own executable path. When it is missing, or RBS runs from a location other programs cannot start it from (an AppImage mount, a Flatpak or Snap sandbox), the page says so and shows no line. The templates are fixed text in `rbs-app`; paths are inserted by code with JSON escaping, or with quoting for the shell the line is pasted into (POSIX `sh` on macOS and Linux, PowerShell on Windows); tests parse every generated JSON line, and every command line by that shell's rules, for paths with spaces, quotes, backslashes, `$`, `%` and non-ASCII characters. The page says to copy the line again after RBS is moved. RBS never writes another application's configuration file.

6. **`rbs-mcp` tells the user what to do** (amends ADR-0052 decision 11 and the mcp-server spec's exits). When IPC is unreachable, the token file is missing, or authentication answers `ai_tools_off` or `auth_failed` (after a rotation or revocation), `rbs-mcp` stays running and lists only `studio_summary`, which answers "Open RBS and press Start in Settings, AI tools". No RBS tool is listed and nothing else is sent, so this stays fail-closed. It tries again on a tool call at most once every 2 seconds (an injected clock in tests), so an AI tool's loop cannot flood the audit log, and sends `notifications/tools/list_changed` when the handshake succeeds. An older server without narrowing still ends it (ADR-0052 decision 3).

7. **The page shows what AI tools are doing.** The status line says whether AI tools are started, why not when Start failed, and how many AI tools are connected, each with the name it reports (`session.hello` `client.name`). That name is untrusted: cut to 64 characters, with control, line break and bidirectional characters removed, shown after "reported as", and never used as a caller label, in audit identity or in anything `rbs-mcp` returns. "Recent actions" shows the last 20 audit records whose caller is the AI tools token (ADR-0052 decision 5: `live` and `destructive` calls and `not_permitted` refusals): time, method, allowed or refused. The audit sink `rbs-app` passes to the server (`RemoteOptions.audit`) is fixed when the server starts, so it forwards records whose caller `kind` is `ai_tools` to a shared slot; Start puts a new bounded ring there; after Stop the ring is kept, with no new records, until the Settings window closes or the next Start, so the user can still check what the AI tool just did (with no ring, the forward is one load and nothing else). The page reads the ring on the UI thread when it opens and on a change signal; it is not saved. The `ai_tools_off` refusal happens only while stopped, when the ring takes no records, so it goes only to the general audit log, like other `not_permitted` refusals. Listing `edit` calls too would need a new `rbs-api` event and is left to a later change.

8. **Zero cost when unused** (P13). Never started: no thread, no endpoint (when remote control is also off), no token entry, no file, no ring. After Stop: the entry and the file remain, nothing runs. Started with no AI tool connected: the IPC accept thread and the API thread asleep, as in remote control's Standby. Connected: the per-request costs of ADR-0052 decision 12 and one ring push per audited call. Nothing on a hot path. `rbs-mcp` is a separate process that the AI tool starts and ends.

9. **Prerequisites.** The page ships only once ADR-0052's IPC narrowing, the `effect` table, the irreversible-actions permission, the split of `RemoteServer` into an API thread with optional transports (decision 2), the `not_permitted` error kind, the audit of decision 5 (`live`, `destructive` and refusals) and `rbs-mcp`'s IPC session are merged; before that, an AI tools token on IPC would have all scopes.

## Consequences

- Turning AI tools on is one button and one copied line; no port opens, the token is never typed or pasted, and what `rbs-mcp` may do is bounded by the API.
- One token for every AI tool: "New token" disconnects all of them. Tokens per AI tool are a possible later addition.
- The generated lines follow other applications' configuration formats, which can change; the templates are small, tested and updated in place.
- Contract changes: `rbs-api` `TokenStore` and session state machine (token `kind`; the token slot value becomes `{store, ai_tools_started, tokenless_ipc}`); `rbs-remote-settings` (token kind, reserved name, local access update, `ai-tools.toml`); protocol minor (the next free at merge) adding `not_permitted` reason `ai_tools_off` and `kind` in `tokens.list`. The `rbs-api` crates are not published; every implementation changes in the same PR.
- Packaging: `rbs-mcp` is built and shipped with `rbs` on all platforms.
- Follow-ups: UI proposal with dark and light screenshots and the owner's approval; spec changes in mcp-server (Settings start, hint state, file re-read), control-api (server states, the new reason, token `kind`, IPC-only acceptance), ui-design-system (AI tools section), settings-search and the glossary ("AI tools").
- Tests: never started means no thread, endpoint, file or `[[tokens]]` entry; Start with remote control off opens no WebSocket port; Stop with remote control off removes the socket (Windows: closes the pipe); Stop racing `session.authenticate` and an in-flight request (state machine on `TestClock`); `ai_tools_off` only after a hash match on IPC, `auth_failed` for the same token on WebSocket; `restart_remote` while started; Start failing when IPC or the config directory is unavailable; file created with 0600 and no window where it is readable by others; the crash order of decision 3; Start rotating a missing or mismatched file; the token in no generated line, log or page text; `rbs-mcp` in hint mode while stopped, after a rotation and with no file, then listing tools after Start without a restart; `client.name` sanitising; generated lines parse for awkward paths; an older RBS reading the remote control file unchanged; `rbs-cli token create --agent` rotating the `ai_tools` entry; a non-`ai_tools` token in `agent-token` treated as a mismatch; IPC hello granting no scopes while only AI tools are started, and tokenless sessions closed when remote control turns off; `tokens.create` from `rbs-cli` with remote control on and AI tools started keeping the AI tools session; `--agent` refusing while RBS runs; an existing user token named `AI tools` renamed; `--token-file` winning over `RBS_TOKEN`; `rbs-mcp` retry spacing.

## Alternatives considered

- **An MCP server (Streamable HTTP) inside RBS.** One less program, but brings an HTTP server and async runtime into the app, and a loopback port that another local user could take first (IPC checks the server's user); already rejected in ADR-0052. The owner chose this ADR's approach.
- **Reuse "Allow remote control".** No new setting, but it opens the WebSocket port and mixes AI tokens with panel tokens; the user who wants only an AI tool would turn on more than needed.
- **Show the token and let the user paste it into the AI tool's configuration.** Simpler, but the token would sit in another application's plain-text file and in the clipboard; a file in RBS's own config directory, named by path, keeps it out of both.
- **Write the AI tool's configuration file for the user.** Saves a paste, but RBS would edit files of other applications whose formats and locations it does not own; a later addition with its own review if wanted.
- **Plain same-user IPC (hello with all scopes) while only AI tools are started.** Keeps `rbs-cli` tokenless, but turning on AI tools would turn on full control for every same-user program, more than the user asked for; the same reason that rejected reusing remote control.
- **Keep the AI tools token valid while stopped.** Simpler, but "Stop" would then not stop an AI tool already configured while remote control is on.

## Review

Independent review per ADR-0014.

1. Round 1 (independent AI session, 2026-11-16), changes requested, 14 concerns (some resolutions below were replaced in later rounds: the inbox messages by the token slot flag in round 2). Server lifecycle was undefined and ADR-0044 decision 5 not amended: a state table, Start failing as a whole, and remote control changes were added. The refusal moved into the session state machine with Start and Stop through the API inbox and defined in-flight handling. The AI tools token is accepted on IPC only, and `ai_tools_off` follows a hash match (ADR-0044 decision 9 amended for IPC). Token file order, exclusive creation, Windows replace and rotation on a missing or mismatched file were specified. `rbs-mcp` re-reads the file and shows the Start hint instead of exiting. Access levels, local-only changes, the threat model, `client.name` sanitising, the audit ring's source (edit calls dropped), start-on-open with a failing host, sandboxed packages, downgrade, IPC close and testable cases were added.
2. Round 2 (independent AI session, 2026-11-16), changes requested, 11 concerns. A new `remote-control.toml` version would make an older RBS move the file aside and lose panel tokens: AI tools moved to their own `ai-tools.toml`. `rbs-cli --agent` and Start both wrote `agent-token`: one routine now owns it, and a token of another kind there is a mismatch. The entry got a reserved name, revocation by hash and cleanup on Start; the started flag rides the token store slot instead of a new inbox input, and `set_tokens` compares kind and permission. IPC with only AI tools started accepts token sessions only (ADR-0044 decision 10 amended). Prerequisites now name the audit and `not_permitted`; the audit sink swap is defined. Shells are named per OS and tested, `rbs-mcp` retries are spaced, `restart_remote` keeps IPC once the server is split, external revocation shows on the page, and the section level uses ADR-0113 terms.
3. Round 3 (independent AI session, 2026-11-16), changes requested, 10 concerns. Leftover text named `remote-control.toml` and inbox messages: fixed. The token slot value is now `{store, ai_tools_started, tokenless_ipc}`, composed in one place from both files, so `rbs-cli` token changes keep the AI tools entry. `--agent` refuses while RBS runs. The transport split is a prerequisite for both remote control switches and `restart_remote`. Tokenless IPC switches at runtime with sessions closed. It opens the file only to read it and closes it at once (on Windows with `FILE_SHARE_DELETE`), so a replace rarely needs the retry of decision 3. An explicit `--token-file` wins over `RBS_TOKEN`. An existing `AI tools` user token is renamed; all operations go by kind and hash. `ai_tools_off` goes only to the audit log; state after Stop stated.
4. Round 4 (independent AI session, 2026-11-16), approve with nits, 4 should and 7 nits, all applied: `tokens.revoke` by the reserved name revokes every AI tools entry; with tokenless IPC off, hello waits for authentication, which then grants; `rbs-cli` token commands refuse in that state; the `--agent` guard uses the IPC endpoint lock and Start re-reads the file; garbled sentences, the Amends line, the table qualifier, the rename, Windows file sharing and keeping the recent actions after Stop were fixed.
