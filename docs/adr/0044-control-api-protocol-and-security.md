# ADR-0044: Control API: one typed request layer, JSON-RPC over swappable transports, scoped token authentication

- Status: Accepted
- Date: 2026-11-04
- Deciders: Salih (owner)

## Context

[ADR-0008](0008-ui-as-api-client.md) decided that every user interface is a client of a versioned control API (commands, queries, events, metrics), with local IPC for the desktop app and WebSocket for remote clients. The [control API spec](../specs/control-api.md) names its users: the desktop UI, `rbs-cli`, Stream Deck and other hardware panels, scripts, user-built apps and tests. UI rule U20 requires that every UI command is a control API command. The roadmap lists "Control API schema technology" as an open decision, and Phase 1 lists "headless engine with control API".

Nothing of it exists yet. `rbs-app` drives the studio through a private `Command`/`Update` pair in `crates/rbs-app/src/studio_host.rs` on its own control thread (ADR-0041 decision 7); recording settings (folder, container, bitrates) and canvas settings live in UI-side files (`record_profile.rs`, `canvas_profile.rs`), and the UI sends an absolute path with each recording. `rbs-cli` calls `rbs-record` directly. Each new UI action adds another private command that no outside app can reach.

Forces:

- **Layering (P1, P2).** Control logic must not name a network, IPC or async-runtime library. Transports must be swappable behind a port with a conformance suite.
- **Zero cost when unused (P13, ADR-0013 rule 4).** Most users never connect an outside app: no thread, socket, timer or event production unless enabled and used.
- **Real-time paths (P6).** No control API work in `Node::process`, audio callbacks or the render tick. A slow or hostile client must not stall the control thread or lock the local user out.
- **Security.** The API can start recordings, write files and, later, load plugins. Known failure modes of comparable APIs: unauthenticated localhost services, browser pages reaching `ws://localhost` (cross-site WebSocket hijacking, DNS rebinding), secrets sent in clear, and remote clients with full power.
- **Contracts are versioned (P9).** User-written clients must keep working across releases.
- **Clients in any language.** Stream Deck plugins and browser panels are JavaScript; scripts are often Python.

## Decision

1. **One request layer, `rbs-api`.** It defines requests (commands and queries), responses, typed errors and events by namespace (`studio.*`, `scene.*`, `source.*`, `audio.*`, `record.*`, `stream.*`, `output.*`, `settings.*`, `edit.*`, `ui.*`, `session.*`, `events.*`, `api.*`, `tokens.*`), and the session state machine (handshake, authentication, scopes, subscriptions, limits). Its dependencies are exactly: `rbs-core`, `serde`, `serde_json` (the JSON codec module, behind a `Codec` trait so other encodings can be added), `sha2` and `subtle` (token hashing and constant-time comparison), `getrandom` (token and instance ids), and `schemars` behind an off-by-default `schema` feature used only by the schema generator and its CI test. It must not depend on an engine crate, an adapter, or a network, IPC, async-runtime or UI crate.
2. **Commands are handled by a `ControlTarget` the composition root supplies**, on the control thread that owns the studio and scene collection (today `studio_host`, later an engine-layer crate). All requests from all clients and the desktop UI are applied there, one at a time. Recording profiles, output destinations and canvas settings move from UI-side files to state the control thread owns and serves through `output.*` and `settings.*`, so a remote client and the UI start a recording the same way.
3. **The desktop UI uses the same types, all serializable.** Every request, response and event type is `Serialize + Deserialize`; a round-trip test passes every request and event through JSON. The UI sends them in process without serializing. Things that cannot cross a process boundary (the preview endpoint, the shared level meters drawn as native layers per ADR-0035) are handed to the local UI through a separate local-only attachment, not through `rbs-api` types. A UI action that has no `rbs-api` request must not exist (U20, enumerated by a test).
4. **Transports are a port.** `ControlTransport` adapters accept connections, exchange whole UTF-8 messages and report the peer (transport kind, loopback or not, `Origin`/`Host` headers, OS peer identity for IPC). Adapters run their own I/O (threads or an async runtime) and push transport events into a bounded inbox that `rbs-api` gives them. Adapters: `rbs-api-ws` (WebSocket, TLS) and `rbs-api-ipc` (Unix domain socket, named pipe). Every adapter passes one conformance suite. Only `rbs-app` and `rbs-cli` choose which run.
5. **Threads.** One API thread, existing only while remote control is on, owns all sessions. The session logic is a pure state machine (`handle(event, now)`, `next_deadline()`) that tests drive directly on `TestClock`; the thread is a thin wrapper that sleeps on one shared wake primitive until the next deadline, with no periodic wake-up. Three separate inputs sit behind that wake primitive: the bounded transport inbox, the response channel, and the event slots. Adapters apply back-pressure per connection: a connection whose queue quota is used stops being read, so one client cannot fill the transport inbox. Each session keeps at most one request in flight to the control thread and a small bounded queue behind it; the API thread forwards in round-robin order. The control thread has two request queues, local UI and API, behind one wake-up, and always drains the UI queue first. The control thread never blocks on API output: responses go into their own channel sized by the number of requests that can be in flight (one per connection under the connection cap; a closed session's in-flight request stays counted, and its connection slot stays taken, until its response is drained and discarded), so a send never fails; events go into per-state-key latest-value slots that a newer event overwrites, and an `events pending` flag avoids one message per write: the API thread atomically swaps the flag to clear before it reads the slots, and a writer that changes it from clear to set signals the wake primitive. The wake primitive is permit-based, so a signal sent before the API thread sleeps is not lost; pushes to the transport inbox and the response channel signal it the same way. Events are serialized once per event on the API thread. Latest-value topics are sampled on the API thread from read-only, lock-free meter and statistics handles the composition root provides; sampling never wakes the control thread.
6. **Events and `seq`.** A state event carries the whole current state of its state key, never a delta, so a newer event for a state key replaces an older one without loss; topics are kept small for this. A state key is a topic name plus an optional object id (for example one key per source); `seq`, the slots, per-session coalescing and the `seq` maps in queries and subscribe all use the state key, while subscriptions and the subscriber mask are per topic name. The first slice's topics have no object id. Every state key has a change counter `seq` that the control thread increments on every change of that state, whether or not anyone subscribed (an integer, not event production). The control thread builds event payloads only for topics in a subscriber mask. The in-process UI is a permanent subscriber registered on the control thread and gets the same event types and `seq`; the API thread sets its sessions' bits before it forwards `events.subscribe`, and the control thread answers with the `seq` read after that.
7. **Wire format: JSON-RPC 2.0** over UTF-8 JSON text messages, `namespace.verb` methods, events as notifications. Batches are refused in protocol version 1. WebSocket subprotocol `rbs.v<major>`.
8. **The Rust types are the schema.** A JSON Schema document is generated from them, checked in, served by `api.describe`, and used to generate clients (TypeScript first). Protocol version `major.minor`, independent of crate semver. A CI tool classifies schema differences: additive changes (new methods, topics, optional request fields, response fields, enum values in responses, error kinds) need a minor bump; removals, renames, type changes and new required request fields need a major bump. Clients must ignore unknown response fields and treat unknown enum values and error kinds generically. The server supports the current and the previous major for at least one release cycle (P9).
9. **Authentication: bearer tokens over protected channels only.** Tokens are `rbs1_` followed by 64 lowercase hex digits of OS randomness (256 bits). The server stores only `SHA-256(token)` and compares in constant time; a stolen store does not reveal tokens. A token may be sent only over loopback, IPC, or TLS whose certificate the client verified (CA or a pinned fingerprint); clients must not send it after a certificate mismatch. Failures are uniform (`auth_failed`, no hint whether the token exists). Before authentication the server reveals only the protocol version and an instance id. Tokens are named, created by the UI or `rbs-cli token create`, shown once, and revocable; revoking closes their sessions.
10. **Scopes.** `read` (state, queries, events), `control` (scene and source changes including capture-target lists, mute and volume, transitions, program switch, record and stream start/stop with configured profiles and destinations, undo and redo, `ui.*`), `admin` (settings, explicit file paths and destinations; an explicit file is never overwritten and its path is logged), `plugins` (plugin management), `tokens` (token management). Every method declares one scope in the schema; where a parameter would need a different scope, it is a separate method (for example `record.start` and `record.start_to_file`). `admin`, `plugins` and `tokens` are accepted only from loopback or IPC peers; a separate, visible setting allows remote `admin`; `plugins` and `tokens` are never remote in version 1. IPC peers of the same OS user and the in-process UI have all scopes, since they could edit the settings files anyway; on IPC, `session.hello` authenticates a verified same-user peer and returns its scopes.
11. **Exposure.** Off by default. When on, WebSocket binds to loopback; network access is a separate setting shown in the app, and non-loopback connections require TLS. Origin and Host checks run before the WebSocket upgrade completes: an `Origin` header is refused unless on the user's allow list, and `null` can never be put on it; `Host` must be a loopback name or address, a configured name, or an address of a bound interface. The IPC endpoint is current-user only (socket mode 0600 in a user-private directory; named pipe with a DACL for the current user and `PIPE_REJECT_REMOTE_CLIENTS`).
12. **Limits.** Caps on total connections, pending handshakes and connections per peer address (not applied to loopback, where all clients share one address); a small pre-authentication message size; a handshake timeout; back-off after failed authentication (per connection on loopback, per address otherwise); per-session message size, request rate and queue length (`busy` when full). Responses on a connection come in request order, so a long command (for example `canvas.set`, which restarts the studio) delays that session's later requests; while it runs on the single control thread, other sessions' and the UI's requests also wait for it.
13. **Consistent state.** Events carry the `seq` of their state key. `session.hello` returns a server instance id; `seq` counters restart with the instance. State queries and `events.subscribe` return the current `seq` per state key; a client applies an event only when its `seq` is higher than what it holds. Skipped `seq` values are normal (coalescing) and need no re-query. Per session, the outgoing queue also keeps only the latest event per state key, so it is bounded by the number of live state keys and never overflows; there is no `events.lost`.
14. **Undo.** One user undo stack for the scene collection, shared by all clients like a shared document. An out-of-order undo returns `undo_conflict`. The serialisable operation type joins the schema (minor addition) with the scene document format ADR.
15. **Zero cost.** Off: nothing constructed. On, no session: the adapter's accept and the API thread asleep on its wake primitive, no wake-ups, no event production. A sampling timer for latest-value topics (levels capped at 30 Hz, statistics at 1 Hz) exists only while a session subscribes to one. Nothing in `Node::process`, audio callbacks or the render tick.
16. **Out of scope.** Remote preview video (control API spec open question, U5). The OBS WebSocket compatibility layer is a separate optional adapter crate that speaks obs-websocket v5 on its own endpoint and turns its calls into `rbs-api` requests in process, under the same channel rules. obs-websocket's salted password challenge cannot use the token store, so the adapter keeps its own secret store, decided in its own review; each entry carries scopes applied the same way, and the remote limits on `admin`, `plugins` and `tokens` apply unchanged; packaging it as a plugin waits for the plugin SDK, whose host call for submitting requests needs its own review.

## Consequences

- Every UI action becomes reachable from Stream Deck, panels, scripts and user apps as soon as it exists, through one code path.
- `rbs-app` must move its studio commands onto `rbs-api` requests and move recording and canvas settings to the control thread; until then the U20 test lists the gaps.
- New crates: `rbs-api` (Control layer), `rbs-api-ws` and `rbs-api-ipc` (adapters). The PR adding `rbs-api` justifies its dependencies (decision 1). The overview's layer table changes: `rbs-api` no longer depends on engine crates.
- JSON is larger and slower than a binary format; control traffic is small and high-rate topics are capped. A binary codec can be negotiated later.
- Bearer tokens rely on the channel (loopback, IPC, verified TLS); there is no mutual authentication of the server beyond TLS. Accepted for version 1; SCRAM can be added as another `session.authenticate` mechanism in a minor version.
- Tests: transport conformance (framing, size limits, close reasons, peer info, Origin/Host cases); session tests on `TestClock` (handshake timeout, auth success and uniform failure, token vector, scopes and remote-scope refusal, connection and handshake caps, back-off, rate limit, `busy`, round-robin fairness, UI priority, a transport inbox full of messages while responses and events are still delivered, event coalescing, `seq` and instance id); JSON round-trip test; schema snapshot with diff classification; U20 test; idle-cost check (thread count and wake-ups when off and when on without sessions).
- Follow-ups: TypeScript client generation, `rbs-cli call` and `rbs-cli token create|list|revoke`, a "Remote control" settings page (UI rules apply), the OBS compatibility adapter, channel binding (RFC 9266) if certificate pinning proves insufficient.

## Alternatives considered

- **Protobuf with gRPC.** Strong evolution rules and generators, but needs a code generator in the build, gRPC-Web plus a proxy for browsers, and a higher barrier for panel and script authors. Can be added as another codec later.
- **An existing JSON-RPC framework (for example `jsonrpsee`).** Brings its own transports and async runtime into the request layer, which breaks the transport port and decision 1. An adapter may still use such a library internally.
- **Own JSON envelope (op codes).** Every client writes its own framing; JSON-RPC 2.0 has libraries in every common language.
- **HTTP REST plus polling.** No push events, which meters and state changes need. A REST bridge can be added as a transport.
- **Speak obs-websocket natively.** Ties the API to OBS's model. Kept as a compatibility adapter.
- **A message broker (MQTT).** Adds a service users must run. Possible later as a transport.
- **Salted challenge-response with a stored key.** Keeps the secret off the wire, but the stored key is itself the credential, so it protects nothing on disk, and adds client complexity. Rejected for the bearer scheme with channel rules.
- **SCRAM-SHA-256.** Protects against a stolen verifier and authenticates the server, but is harder for panel and script authors to implement. Deferred as an optional mechanism.
- **mTLS for network clients.** Strong, but certificate handling is a high barrier for users. Possible later for managed setups.
- **OS peer credentials only, no tokens.** Right for IPC (decision 10), not available over WebSocket.
- **Command handling inside `rbs-api` with a direct engine dependency (the overview's original plan).** Couples the protocol crate to engine internals; the `ControlTarget` trait keeps it testable with a fake target.

## Review

Reviewer: independent AI sessions (a fresh session per round, given only the ADR, specs, principles, related ADRs and code)
Date: 2026-11-04
Verdict: six rounds; round 6 left only a wording fix, applied in the following commit. Owner approval: Salih, 2026-11-04 (in the project thread).
Concerns and resolutions:
1. Round 1, changes requested, 20 concerns. The salted challenge stored the real credential: replaced by bearer tokens stored as SHA-256, constant-time comparison, channel rules and a test vector. `record.start` needed settings the UI owned: profiles and settings move to the control thread, and `record.start_to_file` needs `admin`. Other fixes: the dependency list is now exact; a Threads section and decision 5 were added; per-session queues serve the UI first; instance id and `seq` come with queries and subscribe; connection, handshake and size caps and back-off were added; new `plugins` and `tokens` scopes, local-only by default; the IPC endpoint is user-only and uses peer credentials; schema changes are classified by kind; all types are serializable, with a round-trip test. Undo, the `source.targets` scope, Origin/Host, bootstrap, the OBS adapter and the missing alternatives were addressed too.
2. Round 2, changes requested, 12 concerns, all resolved. They were: a shared inbox and blocking output from the control thread; `seq` against the subscriber mask; the UI event path; scopes that depended on parameters; the IPC handshake; OBS secrets; where sampling reads; loopback lock-out; the `null` origin; overwrites through explicit paths; `TestClock` testability (now a pure state machine); and wording.
3. Round 3, changes requested. The ADR and spec disagreed on the control-thread output path, and responses could be dropped; the wording on long commands and the OBS scopes were also wrong. Resolved.
4. Round 4, changes requested. One inbox could still lose responses or wake-ups, and single-value slots made `events.lost` the normal case. Resolved: separate inputs sit behind one wake primitive, and events carry full state, so `events.lost` is gone.
5. Round 5, changes requested. The pending flag could lose a wake-up; the state key was undefined; the response channel was too small once a session closed with a request in flight; some text was stale. Resolved: the flag is swapped before read, the wake primitive is permit-based, state keys are defined, and the channel is sized by in-flight requests.
6. Round 6: the only remaining item was per-topic wording for slots and `seq`, which was changed to per state key.
7. Implementation review (`rbs-api`, PR #104), a fresh session given the ADR, specs and code: changes requested, 2 major and 8 minor concerns, all resolved in the PR. Recorded clarifications of this ADR, without changing its decisions: protective refusals (`busy`, `rate_limited`, `message_too_large`, and errors for messages without a readable id) are sent at once and can overtake an earlier in-flight answer, since queueing them would make the per-session queue unbounded (decision 12's ordering holds for every other answer); the pending-handshake cap applies to non-loopback peers only (decision 12, no loopback lock-out); before authentication any non-handshake method gets `not_authenticated` (decision 9); transports enforce the per-connection message limit while reading; IPv6 peers are grouped by /64 for caps and back-off; `settings.changed` needs `admin` (decision 10). Round 2 of that review: approve with minor changes; its two notes (clients wait for the authenticate answer before larger messages; a reserve of connection slots for loopback and IPC peers so a refused remote flood cannot fill the cap) were applied.
