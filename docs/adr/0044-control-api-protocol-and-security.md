# ADR-0044: Control API: one typed request layer, JSON-RPC over swappable transports, scoped token authentication

- Status: Proposed
- Date: 2026-11-04
- Deciders: Salih (owner)

## Context

[ADR-0008](0008-ui-as-api-client.md) decided that every user interface is a client of a versioned control API (commands, queries, events, metrics), with local IPC for the desktop app and WebSocket for remote clients. The [control API spec](../specs/control-api.md) names its users: the desktop UI, `rbs-cli`, Stream Deck and other hardware panels, scripts, user-built apps and tests. UI rule U20 requires that every UI command is a control API command. The roadmap lists "Control API schema technology" as an open decision, and Phase 1 lists "headless engine with control API".

Nothing of it exists yet. `rbs-app` drives the studio through a private `Command`/`Update` pair in `crates/rbs-app/src/studio_host.rs` on its own control thread (ADR-0041 decision 7); recording settings (folder, container, bitrates) and canvas settings live in UI-side files (`record_profile.rs`, `canvas_profile.rs`), and the UI sends an absolute path with each recording. `rbs-cli` calls `rbs-record` directly. Each new UI action adds another private command that no outside app can reach.

Forces:

- **Layering (P1, P2).** Control logic must not name a network, IPC or async-runtime library. Transports must be swappable behind a port with a conformance suite.
- **Zero cost when unused (P13, ADR-0013 rule 4).** Most users never connect an outside app: no thread, socket, timer or event production unless enabled and used.
- **Real-time paths (P6).** No control API work in `Node::process`, audio callbacks or the render tick. A slow or hostile client must not stall the control thread or lock the local user out.
- **Security.** The API can start recordings, write files and, later, load plugins. Known failure modes of comparable APIs: unauthenticated localhost services, browser pages reaching `ws://localhost` (cross-site WebSocket hijacking, DNS rebinding), secrets sent in clear, and remote clients with full power.
- **Contracts are versioned (P9).** User-written clients must keep working across releases.
- **Clients in any language.** Stream Deck plugins and browser panels are JavaScript; scripts are often Python.

## Decision

1. **One request layer, `rbs-api`.** It defines requests (commands and queries), responses, typed errors and events by namespace (`studio.*`, `scene.*`, `source.*`, `audio.*`, `record.*`, `stream.*`, `output.*`, `settings.*`, `edit.*`, `ui.*`, `session.*`, `events.*`, `api.*`, `tokens.*`), and the session state machine (handshake, authentication, scopes, subscriptions, limits). Its dependencies are exactly: `rbs-core`, `serde`, `serde_json` (the JSON codec module, behind a `Codec` trait so other encodings can be added), `sha2` and `subtle` (token hashing and constant-time comparison), `getrandom` (token and instance ids), and `schemars` behind an off-by-default `schema` feature used only by the schema generator and its CI test. It must not depend on an engine crate, an adapter, or a network, IPC, async-runtime or UI crate.
2. **Commands are handled by a `ControlTarget` the composition root supplies**, on the control thread that owns the studio and scene collection (today `studio_host`, later an engine-layer crate). All requests from all clients and the desktop UI are applied there, one at a time. Recording profiles, output destinations and canvas settings move from UI-side files to state the control thread owns and serves through `output.*` and `settings.*`, so a remote client and the UI start a recording the same way.
3. **The desktop UI uses the same types, all serializable.** Every request, response and event type is `Serialize + Deserialize`; a round-trip test passes every request and event through JSON. The UI sends them in process without serializing. Things that cannot cross a process boundary (the preview endpoint, the shared level meters drawn as native layers per ADR-0035) are handed to the local UI through a separate local-only attachment, not through `rbs-api` types. A UI action that has no `rbs-api` request must not exist (U20, enumerated by a test).
4. **Transports are a port.** `ControlTransport` adapters accept connections, exchange whole UTF-8 messages and report the peer (transport kind, loopback or not, `Origin`/`Host` headers, OS peer identity for IPC). Adapters run their own I/O (threads or an async runtime) and push transport events into a bounded inbox that `rbs-api` gives them. Adapters: `rbs-api-ws` (WebSocket, TLS) and `rbs-api-ipc` (Unix domain socket, named pipe). Every adapter passes one conformance suite. Only `rbs-app` and `rbs-cli` choose which run.
5. **Threads.** One API thread, existing only while remote control is on, owns all sessions. It blocks on its inbox with a deadline computed from an injected `rbs-core` clock (`TestClock` in tests); it has no periodic wake-up. Each session keeps at most one request in flight to the control thread and a small bounded queue behind it; the API thread forwards in round-robin order. The control thread reads the local UI's channel and the API channel separately and serves the UI first, so remote clients cannot crowd out the local user. Responses and events go back to the API thread's inbox tagged with session and request ids. Events are serialized once per event on the API thread. Which topics have subscribers is published as an atomic topic mask the control thread reads when state changes.
6. **Wire format: JSON-RPC 2.0** over UTF-8 JSON text messages, `namespace.verb` methods, events as notifications. Batches are refused in protocol version 1. WebSocket subprotocol `rbs.v<major>`.
7. **The Rust types are the schema.** A JSON Schema document is generated from them, checked in, served by `api.describe`, and used to generate clients (TypeScript first). Protocol version `major.minor`, independent of crate semver. A CI tool classifies schema differences: additive changes (new methods, topics, optional request fields, response fields, enum values in responses, error kinds) need a minor bump; removals, renames, type changes and new required request fields need a major bump. Clients must ignore unknown response fields and treat unknown enum values and error kinds generically. The server supports the current and the previous major.
8. **Authentication: bearer tokens over protected channels only.** Tokens are `rbs1_` followed by 64 lowercase hex digits of OS randomness (256 bits). The server stores only `SHA-256(token)` and compares in constant time; a stolen store does not reveal tokens. A token may be sent only over loopback, IPC, or TLS whose certificate the client verified (CA or a pinned fingerprint); clients must not send it after a certificate mismatch. Failures are uniform (`auth_failed`, no hint whether the token exists). Before authentication the server reveals only the protocol version and an instance id. Tokens are named, created by the UI or `rbs-cli token create`, shown once, and revocable; revoking closes their sessions.
9. **Scopes.** `read` (state, queries, events), `control` (scene and source changes including capture-target lists, mute and volume, transitions, record and stream start/stop with configured profiles and destinations, undo, `ui.*`), `admin` (settings, explicit file paths and destinations), `plugins` (plugin management), `tokens` (token management). Every method declares its scope in the schema. `admin`, `plugins` and `tokens` are accepted only from loopback or IPC peers; a separate, visible setting allows remote `admin`; `plugins` and `tokens` are never remote in version 1. IPC peers of the same OS user and the in-process UI have all scopes, since they could edit the settings files anyway.
10. **Exposure.** Off by default. When on, WebSocket binds to loopback; network access is a separate setting shown in the app, and non-loopback connections require TLS. Origin and Host checks run before the WebSocket upgrade completes: an `Origin` header (including `null`) is refused unless on the user's allow list; `Host` must be a loopback name or address, a configured name, or an address of a bound interface. The IPC endpoint is current-user only (socket mode 0600 in a user-private directory; named pipe with a DACL for the current user and `PIPE_REJECT_REMOTE_CLIENTS`).
11. **Limits.** Caps on total connections, pending handshakes and connections per peer address; a small pre-authentication message size; a handshake timeout; back-off after failed authentication; per-session message size, request rate and queue length (`busy` when full). Long commands (for example `canvas.set`, which restarts the studio) block only their own session's later requests; clients can open more connections.
12. **Consistent state after gaps.** Events carry a per-topic `seq`. `session.hello` returns a server instance id; `seq` counters restart with the instance. State queries and `events.subscribe` return the current `seq` per topic, so a client can tell which events its snapshot already contains. `events.lost` carries a map from topic to last sent `seq`.
13. **Undo.** One user undo stack for the scene collection, shared by all clients like a shared document. An out-of-order undo returns `undo_conflict`. The serialisable operation type joins the schema (minor addition) with the scene document format ADR.
14. **Zero cost.** Off: nothing constructed. On, no session: the adapter's accept and the API thread blocked on its inbox, no wake-ups, no event production. A sampling timer for latest-value topics (levels capped at 30 Hz, statistics at 1 Hz) exists only while a session subscribes to one. Nothing in `Node::process`, audio callbacks or the render tick.
15. **Out of scope.** Remote preview video (control API spec open question, U5). The OBS WebSocket compatibility layer is a separate optional adapter crate that speaks obs-websocket v5 on its own endpoint and turns its calls into `rbs-api` requests in process, under a token's scopes; packaging it as a plugin waits for the plugin SDK, whose host call for submitting requests needs its own review.

## Consequences

- Every UI action becomes reachable from Stream Deck, panels, scripts and user apps as soon as it exists, through one code path.
- `rbs-app` must move its studio commands onto `rbs-api` requests and move recording and canvas settings to the control thread; until then the U20 test lists the gaps.
- New crates: `rbs-api` (Control layer), `rbs-api-ws` and `rbs-api-ipc` (adapters). The PR adding `rbs-api` justifies its dependencies (decision 1). The overview's layer table changes: `rbs-api` no longer depends on engine crates.
- JSON is larger and slower than a binary format; control traffic is small and high-rate topics are capped. A binary codec can be negotiated later.
- Bearer tokens rely on the channel (loopback, IPC, verified TLS); there is no mutual authentication of the server beyond TLS. Accepted for version 1; SCRAM can be added as another `session.authenticate` mechanism in a minor version.
- Tests: transport conformance (framing, size limits, close reasons, peer info, Origin/Host cases); session tests on `TestClock` (handshake timeout, auth success and uniform failure, token vector, scopes and remote-scope refusal, connection and handshake caps, back-off, rate limit, `busy`, round-robin fairness, UI priority, overflow, `events.lost`, `seq` and instance id); JSON round-trip test; schema snapshot with diff classification; U20 test; idle-cost check (thread count and wake-ups when off and when on without sessions).
- Follow-ups: TypeScript client generation, `rbs-cli call` and `rbs-cli token create|list|revoke`, a "Remote control" settings page (UI rules apply), the OBS compatibility adapter, channel binding (RFC 9266) if certificate pinning proves insufficient.

## Alternatives considered

- **Protobuf with gRPC.** Strong evolution rules and generators, but needs a code generator in the build, gRPC-Web plus a proxy for browsers, and a higher barrier for panel and script authors. Can be added as another codec later.
- **An existing JSON-RPC framework (for example `jsonrpsee`).** Brings its own transports and async runtime into the request layer, which breaks the transport port and decision 1. An adapter may still use such a library internally.
- **Own JSON envelope (op codes).** Every client writes its own framing; JSON-RPC 2.0 has libraries in every common language.
- **HTTP REST plus polling.** No push events, which meters and state changes need. A REST bridge can be added as a transport.
- **Speak obs-websocket natively.** Ties the API to OBS's model. Kept as a compatibility adapter.
- **A message broker (MQTT).** Adds a service users must run. Possible later as a transport.
- **Salted challenge-response with a stored key.** Keeps the secret off the wire, but the stored key is itself the credential, so it protects nothing on disk, and adds client complexity. Rejected for the bearer scheme with channel rules.
- **SCRAM-SHA-256.** Protects against a stolen verifier and authenticates the server, but is harder for panel and script authors to implement. Deferred as an optional mechanism.
- **mTLS for network clients.** Strong, but certificate handling is a high barrier for users. Possible later for managed setups.
- **OS peer credentials only, no tokens.** Right for IPC (decision 9), not available over WebSocket.
- **Command handling inside `rbs-api` with a direct engine dependency (the overview's original plan).** Couples the protocol crate to engine internals; the `ControlTarget` trait keeps it testable with a fake target.
