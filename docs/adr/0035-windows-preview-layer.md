# ADR-0035: Cross-process preview on Windows: shared D3D12 textures, a named pipe and a composition swapchain layer

- Status: Proposed
- Date: 2026-11-03
- Deciders: Salih (owner)
- Builds on: ADR-0028 (preview surfaces shared as native handles, decision 8), ADR-0034 (preview as a native compositor layer, decision 6), ADR-0013 (zero cost when unused)

## Context

ADR-0028 shares the engine's preview with the UI process as native surfaces and ADR-0034 shows them as a native compositor layer so the toolkit never redraws for preview frames; both are implemented on macOS only. ADR-0028 decision 8 says Windows follows with shared NT handles and the same messages, ADR-0034 decision 6 names a DirectComposition visual as the Windows layer. Until then the Windows UI has no preview at all.

Windows constraints:

- **Surfaces.** The engine renders with `wgpu` on D3D12. A committed resource created with `D3D12_HEAP_FLAG_SHARED` gets an NT handle (`CreateSharedHandle`); another process opens it with `OpenSharedHandle` (D3D12) or `OpenSharedResource1` (D3D11) on the same adapter. Flip-model swapchains and the composition swapchain accept no sRGB formats, so a texture that the desktop compositor shows directly is `R8G8B8A8_UNORM` (or BGRA), not `_SRGB`.
- **Handle transport.** NT handles are per process. The owner duplicates them into the other process (`DuplicateHandle` with a `PROCESS_DUP_HANDLE` handle to it). Named handles (`CreateSharedHandle` with a name) would let any process of the session that guesses the name open the surface.
- **IPC.** Windows has no Mach ports. Named pipes give a per-connection channel with kernel-reported end of the peer (broken pipe), message framing, the peer's process id (`GetNamedPipeClientProcessId`) and overlapped (asynchronous) I/O that can be polled without a system call.
- **Showing a shared texture without the toolkit.** DirectComposition visuals take a swapchain or a composition surface as content; a plain DXGI swapchain needs a copy per frame into its back buffer. The composition swapchain API (`presentation.h`, `IPresentationManager`, Windows 10 1809 and later, driver support reported by `IsPresentationSupported`) presents application-owned textures directly (`AddBufferFromResource`, `SetBuffer`, `Present`) into a composition surface that a DirectComposition visual shows, and reports per buffer when the system stops using it (`IPresentationBuffer::IsAvailable`).
- **Adapter.** `wgpu` enumerates Vulkan before D3D12, so on a Windows GPU with both drivers the engine and the UI could open Vulkan devices, which have no D3D12 shared handles.

## Decision

1. **Surfaces.** On Windows `PreviewPublisher` owns a fixed ring (2 to 8) of committed `R8G8B8A8_UNORM` textures of the preview size, created on the render device's D3D12 device with `D3D12_HEAP_FLAG_SHARED` and `ALLOW_RENDER_TARGET | ALLOW_SIMULTANEOUS_ACCESS` (they decay to `COMMON` after each submission, so another device may read them without a transition), each with one NT handle (`CreateSharedHandle`, unnamed, `GENERIC_ALL`). They are wrapped as `Rgba8Unorm` render targets for `wgpu`. The preview pass writes sRGB-encoded values itself (`fs_preview_encode`), so the bytes are the same as the macOS `'RGBA'` surfaces. Same pass otherwise: one render pass, one submission, no copy, no readback.
2. **Pipe, name and token.** The engine creates a message-mode named pipe `\\.\pipe\org.rbs.preview.<pid>.<n>.<nonce>` with one instance, `FILE_FLAG_FIRST_PIPE_INSTANCE` (a squatter makes creation fail), `PIPE_REJECT_REMOTE_CLIENTS` and the default security descriptor (only the creating user, SYSTEM and administrators may write), and a 64-bit token from the system CSPRNG (`BCryptGenRandom`). The endpoint is `service#token` as on macOS. The UI opens the pipe with identification-level impersonation only and checks that the pipe's server process id (`GetNamedPipeServerProcessId`) is the pid in the name.
3. **Same four messages.** `SUBSCRIBE` (id, version, token), `SURFACES` (id, version, generation, width, height, count, adapter LUID, one 64-bit handle value per surface), `FRAME` (id, generation, slot, sequence, timestamp) and `RELEASE` (id, generation, slot), as fixed arrays of little-endian 32-bit words, version 1. The first message on a connection must be a valid `SUBSCRIBE`; anything else disconnects the client, so a stranger cannot keep the single instance. On `SUBSCRIBE` the engine opens the client process (`PROCESS_DUP_HANDLE`, by the pid the pipe reports) and duplicates every surface handle into it; the values in `SURFACES` are valid in the UI process, which owns and closes them. If `SURFACES` cannot be sent, the engine closes the duplicates in the UI process (`DUPLICATE_CLOSE_SOURCE`).
4. **The engine never waits.** Every engine-side pipe operation is overlapped and polled: the connect, one read, and a fixed set of ring size + 2 boxed writes, each with its own `OVERLAPPED` and event. Whether an operation has finished is a memory read (`HasOverlappedIoCompleted`); only a finished one is collected (`GetOverlappedResult` without waiting). Per tick: at most ring size + 1 messages read; one write per delivered frame. A frame with no free write buffer is dropped and counted, as a timed-out Mach send is on macOS. This is the same accepted exception to "no I/O on hot paths" (P6) as ADR-0028 decision 4.
5. **End of a subscription.** A subscription ends when the engine's read fails (the UI closed its end: it dropped the subscriber and every frame, which share the pipe, or exited, also while holding every surface) or a write finds the pipe closed. Then the UI holds no surface any more and every surface is free; the next tick listens again. One UI at a time (one pipe instance). The UI learns that the engine is gone from its read failing (`GpuError::Disconnected`).
6. **Layer.** `PreviewLayer` on Windows (feature `preview-layer`) creates a D3D11 device on the engine's adapter (the LUID from `SURFACES`), opens the shared textures there, registers them as presentation buffers of a composition swapchain (`IPresentationManager`) whose surface is the content of a DirectComposition visual in a topmost target of the window (`CreateTargetForHwnd(hwnd, true)`, above the toolkit's own swapchain). A frame costs `SetBuffer` and `Present`; placement is the visual's offset and scale (aspect fit, physical pixels), committed only when the rectangle changes. It takes only an `HWND` and a rectangle, so it does not depend on the toolkit.
7. **Release rule: the system's signal.** A replaced frame goes back to the engine once its buffer reports `IsAvailable`, which the desktop compositor sets when it no longer reads the buffer, not after a timing guess as on macOS (ADR-0034 decision 3). The UI checks on every `show` and, while any frame waits, with a one-shot timer `DEFAULT_RETIRE_POLL` (4 ms) after the last check. The ring needs `surfaces_needed` (5 at 60 fps; the demo engine keeps 6).
8. **Fallback.** Where the composition swapchain is missing (`IsPresentationSupported` false, for example in a remote desktop session or on WARP) `PreviewLayer::new` returns `GpuError::Unsupported` and the UI shows the surfaces through the toolkit: `PreviewSubscriber::textures` opens them on the UI's D3D12 device (same adapter, checked by LUID) as `Rgba8Unorm` textures, the ADR-0028 path.
9. **D3D12 first on Windows.** Among adapters of the same kind, `GpuContext::new` prefers the D3D12 backend on Windows, because every native interop there (import, encoder export, this preview) is D3D12.
10. **Zero cost when unused (P13).** As ADR-0028 decision 7 and ADR-0034 decision 8: the publisher exists only while a preview output is Active; with no UI connected `publish` does no GPU work and `tick` reads one `OVERLAPPED` field; the layer adds no thread and its timer runs only while a frame waits. Layer code is behind `preview-layer`, so engine binaries carry no DirectComposition code.

## Consequences

- The Windows UI can show the engine's preview across processes without copies; the same `PreviewPublisher` / `PreviewSubscriber` / `PreviewLayer` names and the same message semantics as macOS, so the shell's preview panel wires one API on both.
- Unlike macOS, the layer's release is a completion signal from the system, so the Windows layer cannot tear a monitoring frame by releasing too early, and needs a smaller ring.
- `rbs-gpu` gains Windows features of the `windows` crate it already depends on (pipes, overlapped I/O, threading, security, cryptography; with `preview-layer` also Direct3D 11, DXGI, DirectComposition and the composition swapchain) and, with `preview-layer`, `windows-numerics` (already in the lockfile through `windows`). No new crate is built.
- The preview's UI-side textures are `Rgba8Unorm` holding sRGB-encoded values on Windows and `Rgba8UnormSrgb` on macOS (`PREVIEW_TEXTURE_FORMAT` per platform). A toolkit path that samples them must treat the Windows values as already encoded.
- The engine needs `PROCESS_DUP_HANDLE` on the UI process. Same user and integrity level is enough; a UI running elevated while the engine is not cannot be served (the open fails and the subscription is refused).
- One subscriber per publisher, as on macOS. Same-user denial of service (connecting first and never subscribing) is limited to one failed connection: the first message must subscribe.
- The hot-path row of the preview export grows by the Windows publisher (overlapped pipe calls instead of Mach sends).
- Residual risk: the composition swapchain is not available on CI (WARP has no presentation support), so the layer is verified on the owner's Windows machine only; the pipe protocol and the shared textures run on CI.

## Alternatives considered

- **DXGI swapchain in a DirectComposition visual, copy per frame.** Works everywhere DirectComposition does, but costs a GPU copy and a present per frame in the UI and gives no buffer release signal beyond the copy; kept in mind as a fallback if the composition swapchain proves unreliable on some drivers.
- **Named shared handles (`CreateSharedHandle` with a name, `OpenSharedHandleByName`).** No duplication step, but any process of the session that learns the name opens the surface; duplication gives the handles to the subscribed process only.
- **UI duplicates the handles from the engine.** Needs `PROCESS_DUP_HANDLE` on the engine process, which gives the UI the power to take any of the engine's handles; pushing from the engine gives the UI only what it needs.
- **ALPC or COM out-of-process server.** Heavier, allocates per call, and not needed for four fixed-size messages.
- **Waiting on the buffers' available events in a thread.** Exact without a poll timer, but adds a thread while the preview shows; the 4 ms poll runs only while a frame waits.
- **Keyed mutex or shared fence between engine and compositor.** The desktop compositor does not take the engine's fence; the engine already waits for its own GPU work before sending `FRAME`, and `IsAvailable` covers the read side.
