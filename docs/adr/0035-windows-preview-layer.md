# ADR-0035: Cross-process preview on Windows: shared D3D12 textures, a named pipe and a composition swapchain layer

- Status: Proposed
- Date: 2026-11-03
- Deciders: Salih (owner)
- Builds on: ADR-0028 (preview surfaces shared as native handles, decision 8), ADR-0034 (preview as a native compositor layer, decision 6), ADR-0013 (zero cost when unused)

## Context

ADR-0028 shares the engine's preview with the UI process as native surfaces and ADR-0034 shows them as a native compositor layer so the toolkit never redraws for preview frames; both are implemented on macOS only. ADR-0028 decision 8 says Windows follows with shared NT handles and the same messages, ADR-0034 decision 6 names a DirectComposition visual as the Windows layer. Until then the Windows UI has no preview at all.

Windows constraints:

- **Surfaces.** The engine renders with `wgpu` on D3D12. A committed resource created with `D3D12_HEAP_FLAG_SHARED` gets an NT handle (`CreateSharedHandle`); another process opens it with `OpenSharedHandle` (D3D12) or `OpenSharedResource1` (D3D11) on the same adapter. Flip-model swapchains and the composition swapchain accept no sRGB formats, so a texture that the desktop compositor shows directly is `R8G8B8A8_UNORM` (or BGRA), not `_SRGB`.
- **Handle transport.** NT handles are per process. The owner duplicates them into the other process (`DuplicateHandle` with a `PROCESS_DUP_HANDLE` handle to it). Named handles (`CreateSharedHandle` with a name) would let any process of the session that guesses the name open the surface.
- **IPC.** Windows has no Mach ports. Named pipes give a per-connection channel with kernel-reported end of the peer (broken pipe), message framing, the peer's process id (`GetNamedPipeClientProcessId`) and overlapped (asynchronous) I/O that can be polled without a system call.
- **Showing a shared texture without the toolkit.** DirectComposition visuals take a swapchain or a composition surface as content; a plain DXGI swapchain needs a copy per frame into its back buffer. The composition swapchain API (`presentation.h`, `IPresentationManager`, Windows 10 1809 and later, driver support reported by `IsPresentationSupported`) presents application-owned textures directly (`AddBufferFromResource`, `SetBuffer`, `Present`) into a composition surface that a DirectComposition visual shows, and reports per buffer when the system stops using it (`IPresentationBuffer::IsAvailable`).
- **Adapter.** `wgpu` enumerates Vulkan before D3D12, so on a Windows GPU with both drivers the engine and the UI could open Vulkan devices, which have no D3D12 shared handles.

## Decision

1. **Surfaces.** On Windows `PreviewPublisher` owns a fixed ring (2 to 8) of committed `R8G8B8A8_UNORM` textures of the preview size, created on the render device's D3D12 device with `D3D12_HEAP_FLAG_SHARED` and `ALLOW_RENDER_TARGET | ALLOW_SIMULTANEOUS_ACCESS` (they decay to `COMMON` after each submission, so another device may read them without a transition), each with one NT handle (`CreateSharedHandle`, unnamed, `GENERIC_ALL`). They are wrapped as `Rgba8Unorm` render targets for `wgpu`. The preview pass writes sRGB-encoded values itself (`fs_preview_encode`), so the bytes are the same as the macOS `'RGBA'` surfaces. Same pass otherwise: one render pass, one submission, no copy, no readback.
2. **Pipe, name and token.** The engine creates a message-mode named pipe `\\.\pipe\org.rbs.preview.<pid>.<n>.<nonce>` with one instance, `FILE_FLAG_FIRST_PIPE_INSTANCE` (a squatter makes creation fail), `PIPE_REJECT_REMOTE_CLIENTS` and an explicit protected DACL that grants the engine process's user, and nobody else, access (`D:P(A;;GA;;;<user SID>)`; the default descriptor would let Everyone connect for reading and so occupy the single instance) and a medium mandatory label with no read up and no write up (`S:(ML;;NWNR;;;ME)`), so a low-integrity sandbox of the same user cannot open it either, and a 64-bit token from the system CSPRNG (`BCryptGenRandom`). The endpoint is `service#token` as on macOS. The UI opens the pipe with identification-level impersonation only and checks that the pipe's server process id (`GetNamedPipeServerProcessId`) is the pid in the name.
3. **The four messages plus a handle handshake.** `SUBSCRIBE` (id, version, token), `SURFACES` (id, version, generation, width, height, count, adapter LUID, one 64-bit handle value per surface), `FRAME` (id, generation, slot, sequence, timestamp) and `RELEASE` (id, generation, slot), as fixed arrays of little-endian 32-bit words, version 1, and one Windows-only message, `ACCEPT` (id, generation). The first message on a connection must be a valid `SUBSCRIBE`; a wrong one disconnects the client. On `SUBSCRIBE` the engine opens the client process (`PROCESS_DUP_HANDLE`, by the pid the pipe reports) and duplicates every surface handle into it; the values in `SURFACES` are valid in the UI process. **Ownership rule:** the duplicates stay the engine's until the UI's `ACCEPT` arrives. A UI that gives up before writing `ACCEPT` (timeout, invalid message) never closes the values. The engine closes them in the UI process (`DUPLICATE_CLOSE_SOURCE`) only on a decisive signal that no `ACCEPT` can follow: its read fails because the UI closed its end (messages are ordered, so a written `ACCEPT` would have been read first), or `SURFACES` could not be sent. When the engine itself ends an offered connection (the publisher is dropped, or a message other than `ACCEPT` arrives) an `ACCEPT` may already be queued, so it leaves the values to the client: a bounded leak of at most one ring until that process exits, never a close of a value the client may own. After `ACCEPT` the UI owns them and closes them with its subscriber. So a slow or failed connect leaks no texture in the normal case, and the engine can never close an unrelated handle in the UI. Frames are sent only after `ACCEPT`.
4. **The engine never waits.** Every engine-side pipe operation is overlapped and polled: the connect, one read, and a fixed set of ring size + 2 boxed writes, each with its own `OVERLAPPED` and event. Whether an operation has finished is a memory read (`HasOverlappedIoCompleted`); only a finished one is collected (`GetOverlappedResult` without waiting). Per tick: at most ring size + 2 messages read (one `RELEASE` per surface, `SUBSCRIBE` or `ACCEPT`, and one more); one write per delivered frame. A frame with no free write buffer is dropped and counted, as a timed-out Mach send is on macOS. This is the same accepted exception to "no I/O on hot paths" (P6) as ADR-0028 decision 4.
5. **End of a subscription.** A subscription ends when the engine's read fails with a broken or unconnected pipe (the UI closed its end: it dropped the subscriber and every frame, which share the pipe, or exited, also while holding every surface) or a write finds the pipe closed. A message too long for the protocol (`ERROR_MORE_DATA`) or one that does not decode is counted in `rejected` and ignored: the UI may be alive and showing a surface, so it does not end the subscription. Then the UI holds no surface any more and every surface is free; the next tick listens again. One UI at a time (one pipe instance). The UI learns that the engine is gone from its read failing (`GpuError::Disconnected`).
6. **Layer.** `PreviewLayer` on Windows (feature `preview-layer`) creates a D3D11 device on the engine's adapter (the LUID from `SURFACES`), opens the shared textures there, registers them as presentation buffers of a composition swapchain (`IPresentationManager`) whose surface is the content of a DirectComposition visual in a topmost target of the window (`CreateTargetForHwnd(hwnd, true)`, above the toolkit's own swapchain). A frame costs `SetBuffer` and `Present`; placement is one transform on the visual (aspect-fit scale and translation, physical pixels, zero offset), committed only when the rectangle changes. It takes only an `HWND` and a rectangle, so it does not depend on the toolkit.
7. **Release rule: the system's signal.** A replaced frame goes back to the engine once its buffer reports `IsAvailable`, which the desktop compositor sets when it no longer reads the buffer, not after a timing guess as on macOS (ADR-0034 decision 3). The UI checks on every `show` and, while any frame waits, with a one-shot timer `DEFAULT_RETIRE_POLL` (4 ms) after the last check. The ring needs `surfaces_needed` (5 at 60 fps; the demo engine keeps 6). The frame shown at `detach` stays the presentation surface's current buffer, so it never reports available: `detach` removes the visual and waits for the compositor to apply that (`WaitForCommitCompletion`, UI thread), and the layer keeps that frame (outside the retiring set) until a later `show` replaces it, after which it retires by `IsAvailable` like any other, or until the layer is lost or dropped. A re-attached layer adds its visual only at its first `show`, so it never shows the stale frame. The engine has one surface fewer while the layer is detached. When the presentation manager is lost (its lost event, checked on every `show`, or a failed `Present`), the system reads none of the buffers and every frame goes back at once; the UI recreates the layer or falls back (decision 8).
8. **Fallback.** Where the composition swapchain is missing (`IsPresentationSupported` false, for example in a remote desktop session or on WARP) `PreviewLayer::new` returns `GpuError::Unsupported` and the UI shows the surfaces through the toolkit: `PreviewSubscriber::textures` opens them on the UI's D3D12 device (same adapter, checked by LUID) as `Rgba8Unorm` textures, the ADR-0028 path.
9. **D3D12 first on Windows.** Among adapters of the same kind, `GpuContext::new` prefers the D3D12 backend on Windows, because every native interop there (import, encoder export, this preview) is D3D12.
10. **Zero cost when unused (P13).** As ADR-0028 decision 7 and ADR-0034 decision 8: the publisher exists only while a preview output is Active; with no UI connected `publish` does no GPU work and `tick` reads one `OVERLAPPED` field; the layer adds no thread and its timer runs only while a frame waits. Layer code is behind `preview-layer`, so engine binaries carry no DirectComposition code.

## Consequences

- The Windows UI can show the engine's preview across processes without copies; the same `PreviewPublisher` / `PreviewSubscriber` / `PreviewLayer` names and the same message semantics as macOS, so the shell's preview panel wires one API on both.
- Unlike macOS, the layer's release of replaced frames is a completion signal from the system, so they cannot tear a monitoring frame by going back too early, and the ring is smaller. `detach` keeps the last shown frame until it is replaced; dropping the layer waits for commit completion and then releases everything, so dropping it while the window stays open can show one torn frame at worst, as on macOS.
- `rbs-gpu` gains Windows features of the `windows` crate it already depends on (pipes, overlapped I/O, threading, security, cryptography; with `preview-layer` also Direct3D 11, DXGI, DirectComposition and the composition swapchain) and, with `preview-layer`, `windows-numerics` (already in the lockfile through `windows`). No new crate is built.
- The preview's UI-side textures are `Rgba8Unorm` holding sRGB-encoded values on Windows and `Rgba8UnormSrgb` on macOS (`PREVIEW_TEXTURE_FORMAT` per platform). A toolkit path that samples them must treat the Windows values as already encoded.
- The engine needs `PROCESS_DUP_HANDLE` on the UI process. Same user and integrity level is enough; a UI running elevated while the engine is not cannot be served (the open fails and the subscription is refused). The pipe's DACL names the user SID, which an elevated and a non-elevated process of the same user share, so a non-elevated UI can still open the pipe of an elevated engine.
- One subscriber per publisher, as on macOS. Other accounts cannot open the pipe (DACL). A process of the same user at medium integrity or above can occupy the single instance by connecting and never subscribing, without knowing the token; the engine then serves no UI until that process closes its end. This is weaker than macOS, where the bootstrap name and token gate every subscription and a silent client holds nothing. Accepted: as in ADR-0028, same-user denial of service is out of scope (such a process can already suspend or kill the engine), and a tick-based kick would make the in-process tests timing dependent.
- The hot-path row of the preview export grows by the Windows publisher (overlapped pipe calls instead of Mach sends). `benches/preview.rs` and the allocation test `share_alloc_metal.rs` (name kept from macOS) also run on Windows.
- Residual risk: the composition swapchain is not available on CI (WARP has no presentation support), so the layer is verified on the owner's Windows machine only; the pipe protocol and the shared textures run on CI.

## Alternatives considered

- **DXGI swapchain in a DirectComposition visual, copy per frame.** Works everywhere DirectComposition does, but costs a GPU copy and a present per frame in the UI and gives no buffer release signal beyond the copy; kept in mind as a fallback if the composition swapchain proves unreliable on some drivers.
- **Named shared handles (`CreateSharedHandle` with a name, `OpenSharedHandleByName`).** No duplication step, but any process of the session that learns the name opens the surface; duplication gives the handles to the subscribed process only.
- **UI duplicates the handles from the engine.** Needs `PROCESS_DUP_HANDLE` on the engine process, which gives the UI the power to take any of the engine's handles; pushing from the engine gives the UI only what it needs.
- **ALPC or COM out-of-process server.** Heavier, allocates per call, and not needed for four fixed-size messages.
- **Waiting on the buffers' available events in a thread.** Exact without a poll timer, but adds a thread while the preview shows; the 4 ms poll runs only while a frame waits.
- **Keyed mutex or shared fence between engine and compositor.** The desktop compositor does not take the engine's fence; the engine already waits for its own GPU work before sending `FRAME`, and `IsAvailable` covers the read side.

## Review

- 2026-11-03, independent AI session (fresh context: proposal, specs and code only), round 1: changes requested. Findings and resolution:
  1. High: the default pipe DACL lets every local account connect for reading and occupy the single instance; the ADR's "one failed connection" claim was wrong for a client that sends nothing. Fixed: explicit user-only DACL; wording corrected; same-user denial of service stays out of scope as on macOS (no tick-based kick, which would make in-process tests timing dependent).
  2. Medium: a UI that timed out after `SUBSCRIBE` could leave duplicated handles (and textures) in its process. Fixed: `ACCEPT` handshake; the engine closes un-accepted duplicates.
  3. Medium: the UI wrapped handle values before checking the message id and version. Fixed: nothing is wrapped before `ACCEPT` is written.
  4. Medium: no Windows hot-path numbers, bench or allocation test. Fixed: bench and allocation test run on Windows; numbers below.
  5. Medium: after `detach` the shown buffer never reports available. Fixed: wait for commit completion, then the 34 ms rule.
  6. Medium: layer arithmetic untested; spec test list. Fixed: `share::geometry` (fit, ring size) with unit tests on every platform; spec Testing entries.
  7. Low: any read error ended the subscription. Fixed: only broken or unconnected pipe; `MORE_DATA` is rejected and ignored.
  8. Low: kernel-written `OVERLAPPED` and buffers without `UnsafeCell`, no acquire ordering. Fixed: `UnsafeCell`, raw pointers while issued, `fence(Acquire)` after completion.
  9. Low: dropping the layer could tear a frame, contradicting the ADR. Fixed: drop waits for commit completion; Consequences state the remaining one-frame worst case.
  10. Low: lost manager detected only by a failed call. Fixed: lost event checked per `show`; every frame goes back on loss.
  11. Low: placement depended on offset/transform order. Fixed: one matrix, zero offset.
  12. Low: Slint fallback colours unverified. Open: checked in the hardware run.
  13. Low: re-subscription after a held exit untested. Fixed: the test runs a second child.
- 2026-11-03, independent AI session (fresh context), round 2: changes requested. Findings and resolution:
  1. High: dropping the publisher, or an engine-side disconnect while `Offered`, closed duplicates the UI might already own (an `ACCEPT` in flight), so the UI could later close reused handle values. Fixed: the engine closes un-accepted duplicates only on decisive signals (UI closed its end, `SURFACES` not sent); otherwise a bounded leak until the client exits (decision 3).
  2. Medium: same-user denial of service is weaker than on macOS. Accepted and documented (Consequences); low-integrity processes are now excluded by a mandatory label.
  3. Medium: no P15 numbers yet. Open: the owner's Windows hardware run.
  4. Medium: a detached then re-attached layer could show stale content, and the 34 ms rule after `detach` could release a frame the compositor still showed. Fixed: the detached frame is kept until replaced; the visual is added at the first `show` after attach.
  5. Low: the subscriber's connect documentation omitted the 1 s `ACCEPT` grace. Fixed.
  6. Low: wording (reads per tick are ring size + 2; decision 6 said offset and scale). Fixed.
  7. Low: the macOS layer did not use the shared ring arithmetic. Fixed: `share::geometry::ring_needed` on both.
