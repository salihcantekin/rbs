# ADR-0148: Streaming follows its destinations: every destination can be removed, and Go live shows only while one is on

- Status: Accepted (independent review resolved, owner approved 2026-11-18)
- Date: 2026-11-18
- Deciders: Salih (owner)
- Amends: [ADR-0127](0127-multistreaming-to-several-destinations.md) decisions 1 ("First destination", ids) and 17 (Settings, Stream); [ADR-0050](0050-command-registry-menus-and-toolbar.md) decision 6 (the Go live core flow before first setup); [ADR-0073](0073-pictures-area-and-studio-mode-switch.md) decision 8 (Go live always in the frame's fixed group)
- Builds on: [ADR-0013](0013-zero-cost-when-unused.md), [ADR-0050](0050-command-registry-menus-and-toolbar.md), [ADR-0093](0093-vertical-second-canvas-from-the-same-sources.md), [ADR-0111](0111-vertical-outputs-start-with-the-main-ones.md)
- Spec: [ui-design-system](../specs/ui-design-system.md) (Settings, Stream; frame; U1 core flow "Go live"), [control-api](../specs/control-api.md) (`stream.*`), [ui glossary](../ui/glossary.md)

## Context

ADR-0127 made a canvas's stream a list of destinations. Its first destination is the old `stream` (or `stream-vertical`) section, so ADR-0127 decision 1 says it "cannot be removed or reordered, only cleared or disabled", to keep the old fields meaning the same in old and new builds. The owner found this in use (2026-11-18): the first row has no Remove, while every other row has one, and the user cannot tell why. The owner asked that every destination be removable, each row have a switch to turn it off instead of removing it, and that streaming as a whole follow the list: adding a destination turns streaming on and shows Go live; removing or turning off the last one turns streaming off, after a warning, and hides what belongs to streaming.

Today Go live, Hold stream and the stream commands show for every user, also for one who only records; ADR-0073 decision 8 puts Go live in the frame's fixed group that "cannot be removed". RBS is not released yet, so a profile written by this version and read by an older development build is a minor concern, but it is stated below.

Moving the next destination into the first slot when the first is removed was considered and rejected (Alternatives): it moves a key between credential store accounts, changes the destination's API id, and has no answer when every destination is removed.

## Decision

1. **Streaming is available on a canvas while at least one of its existing destinations is on.** "On" is the existing `enabled` flag (Use on Go live); "existing" is defined in decision 2. Availability is derived from the saved destinations, never a separate setting. A destination that is on but has no key yet still counts: Go live shows and its refusal names what is missing, as today. The main and the vertical canvas are decided separately. While the `stream`, `stream-vertical` or `stream-destinations` section is newer than this build or failed to load, that canvas counts as available and Add, Remove and the switch are refused with the load error, so a load error never looks like "streaming is off" and never lets Add delete a real key. One function in `rbs-app` (`stream_destinations`) computes availability from the sections and their load state; the window and the control thread both use it (the host is sent the load state with the stream settings, as it is sent the settings today), so the API and the window never disagree.

2. **A first destination exists while its `stream` section has a server.** The key flag does not decide it (it is reset by the NoKey answer to a failed Go live and by the Linux restart reset in `studio_ui.rs`, which must not make a row vanish). Every Save of a destination needs a server (the editor's Add and Save are disabled until the Server field holds one), so the only way a first destination stops existing is Remove. Paths that change the server or `enabled` (editor Save, Remove, the row switch, `stream.destination.set_enabled`, profile load and switch, OBS import) recompute availability; an OBS import that brings a key and no server (OBS's service list, in `obs_import.rs`) fills the server from the matching preset, or leaves the slot not existing and says so in the import report. The limit of six destinations per canvas, the "N of 6" count and the limit of own encodings count existing destinations only. A leftover `stream-destinations` entry for id 0 or 1 whose slot does not exist is ignored by the checks (`problem()`) and the list (`of()`), and replaced on Add. A `stream-vertical` section that is absent means the vertical first slot does not exist.

3. **Every destination can be removed.** Removing one that is not first is as today. Removing a first destination, in this order: delete its key from the credential store and wait for the answer; on failure stop and show the error with nothing changed; on success empty the `stream` section's server, `key_saved`, `reconnect` (back to on) and SRT latency, and delete its `stream-destinations` entry (name, service, enabled, encoding). Removal of a non-first destination also deletes the key before the entry, with the same failure rule. Removing is refused while that canvas's stream runs (as editing is today).

4. **Add fills the empty first slot, at the end of the list.** "Add destination" on a canvas whose first destination does not exist works on a draft; nothing is written and no key is saved until Save (Cancel writes nothing). Save into the empty slot (id 0 or 1, the `stream` section, the existing key account), in this order: delete any key in that account and wait for the answer (on failure stop and show it, nothing changed); write the server and the other fields; then save the typed key, if any. So a key the flag did not know about can never reach the new destination, whether or not a new key is given. Independently, the stream request builder (decision 6) reads a destination's key only when its `key_saved` is true. Add is refused while a section has a load error (decision 1). The fixed first ids are the only ids that can come back; every other id is never reused, as ADR-0127 says.

5. **Order.** The list shows the existing destinations in a saved order: a new optional `order` value per entry in `stream-destinations`. Sorting: entries with `order` by it; entries without by id after them, except an existing first slot without an entry, which sorts as order 0 (today's order for every current profile). A new destination, including one added into the empty first slot, gets `order` = the largest order or count on the canvas + 1 (an entry is written for the first slot when it gets an order), so it is listed last and nobody is renumbered. An older development build that re-saves the section drops `order`; the list then falls back to id order (decision 11). Each row shows its number; while more than one destination is on, a line over the list says "Go live sends to all N at the same time." Every destination that is on starts in the same apply (ADR-0127 decision 3), so the number is not a start order or a priority; the list, the live chip and `stream.destinations` use the same order. Reordering by the user is not offered yet. `order` is an optional field and the section does not deny unknown fields (`stream_destinations.rs` `Destination` has no `deny_unknown_fields`), so `format_version` stays 1 and an older build ignores `order`.

6. **Go live does not need the first destination.** The stream request is built from the canvas's `stream` section for the shared settings (encoding, output size, hold, auto-record) and from each existing, enabled destination for server and key; an empty first slot is skipped. The paths that refuse today when the first destination has no server use the same function: the window's Go live and `would_start` in `studio_ui.rs`, the vertical stream checks (`vertical_stream_set_up` and the vertical Go live), and `api_stream_request` in `studio_host.rs`. The `stream.start` refusal texts in the control-api spec are amended: "no server" names the destination.

7. **The switch is at the end of the row.** Turning off or removing the last destination that is on asks first, in a callout under the row: "This is the last destination that is on. Streaming turns off and Go live leaves the main window. You can add or turn on a destination at any time." Remove itself always asks first. While the canvas's stream runs, the switch and Remove are disabled in Settings (as today) and `stream.destination.set_enabled` keeps working on a live stream (ADR-0127 decision 8), but availability for the UI is decision 8's rule.

8. **What shows.** A canvas's stream items show while the canvas is available **or its stream is not off** (live, starting, reconnecting, ending, held). End stream, Hold stream and Resume are never hidden or refused because of availability; only Go live / start is.
    - **Frame's fixed group:** Go live shows while either canvas shows stream items; it keeps its ▾ for the vertical choice as today. With both canvases unavailable and no stream running, the group has Record only. This amends ADR-0073 decision 8: the group cannot be removed by the user, but it shows only the outputs that exist. The four cases: main and vertical available: as today; main only: Go live starts the main stream, no vertical stream choice; vertical only: Go live starts the vertical stream (its title stays "Go live", the ▾ names the canvas); neither: no Go live. `canvas: "all"` and the "Main + vertical" with-main flag (ADR-0111) start the available canvases only, and the with-main choice for streams is offered only while both are available.
    - **Commands:** they stay registered (ADR-0050). Hiding uses the existing `CommandState::applies` (`rbs-ui` `command.rs` 2255), exactly as the vertical output commands do today (`menu_bar.rs` 1328): `stream.toggle`, `stream.main.toggle`, `stream.vertical.toggle`, `stream.hold_toggle` and the stream choice of `output.with_vertical` do not apply while their canvas shows no stream items; `stream.toggle` (the frame's Go live and its shortcut) applies while either canvas shows stream items and starts the available canvases, as the frame button does, so button and shortcut never disagree. Surfaces that honour it: app menu, Mac menu bar, command palette, context menus, toolbar picker; a toolbar item the user placed stays saved but is not drawn. Their `enabled` check answers "Streaming is off. Add a destination or turn one on in Settings, Stream." and a shortcut press shows that text in the status bar. `ui.command.list` lists them with `enabled: false` and that reason.
    - Break (`output.break_toggle`) stays; with no stream it only pauses recordings.
    - **Settings, Stream** stays in the sidebar and in search. With no destination: an empty state ("Streaming is off. Add a destination and Go live shows in the main window.") and Add destination; with destinations that are all off, the list and a note "Every destination is off, so Go live is hidden." The Connection, While live and Encoding cards are hidden while the canvas picked in Settings is not available and its stream is off. Settings, Recording hides "Mark stream start and end" while no canvas shows stream items.
    - **Shortcuts** lists the stream commands with their bindings, dimmed, with "Streaming is off" as their note.
    - **Status bar and live indicator:** the U4 status text drops its stream part while no canvas is available ("Not recording" instead of "Not live · not recording"); the live indicator is unchanged (it only shows while something runs).
    - Nothing of this is per frame: availability is computed on the changes listed in decision 2 (rule 10).

9. **First-time setup.** A new profile has no destination, so a first-time user sees Record and no Go live until they add one in Settings, Stream. This changes the U1 core flow "Go live" in the design system spec ("Go live button (first time only: pick service, ...)"): first-time setup starts in Settings, Stream; after setup Go live is one interaction as before. ADR-0050 decision 6 still holds for Go live once streaming is available. The owner approved this change of the U1 flow in writing on 2026-11-18 (CLAUDE.md rule 18), choosing "Only Settings › Stream" over keeping a "Set up streaming" button in the frame; the spec's core-flow row is amended in the same change. An existing profile whose `stream` section has a server reads as today.

10. **Control API** (next free minor version at merge):
    - `stream.status`, `stream.state` and `stream.canvas_state` add `available: bool` (absent from an older server: read as true). A change of `available` publishes a new `stream.state` / `stream.canvas_state` event.
    - `stream.start` on a canvas that is not available is refused as `failed` with the text of decision 8, before any key is read. `canvas: "all"` starts the available canvases and is refused only when none is.
    - `stream.destinations` lists existing destinations only, in the order of decision 5; id 0 or 1 may be absent. `stream.destination.start|stop|set_enabled` with the id of a first slot that does not exist answer `not_found` and never create an entry.
    - `rbs-mcp` reports `available` in its stream tools' answers. The release notes say that id 0 may be absent.

11. **Old builds.** A development build from before this ADR reads a removed first slot as a stream with no server: its Go live refuses with "no server" and does not go live to the other destinations either. It ignores the order. A profile from before this ADR with a saved key and no server (the first slot never set up) loses its first row on upgrade, and the next Add into that slot deletes the old key. Stated in the release notes; no migration, since RBS is not released.

## Consequences

- A user who only records never sees Go live, Hold stream or stream menu items; a streamer adds a destination once and sees everything; a live stream can always be ended and held.
- `rbs-app`: destinations gain `exists`/`available` per canvas, an `order`, removal of a first destination (key first, then clear), Add into the empty slot, and one stream request builder used by Go live, `would_start` and the API; Settings, Stream's empty state and last-destination callout; the shell's `applies` and the frame group follow decision 8. No new `rbs-ui` contract.
- Control API minor version with `available`, `not_found` for absent first ids, and events on availability changes; `rbs-mcp` follows.
- Specs: control-api (`stream.*`), ui-design-system (frame group, Settings, Stream, U1 Go live flow), glossary if needed, status.
- Tests (ADR-0032, no sleeps): removing the first destination deletes the key before clearing and changes nothing when the delete fails; a failed Go live (NoKey) and the Linux restart do not hide the first row; Save without a server is refused; Add into the empty slot deletes a stale key before saving, is listed last and leaves others' numbers; Go live and `stream.start` work with the first slot empty and other destinations on; all-off and none are not available, a load error is available with edits refused; turning off the last destination while live keeps End stream and Hold; the four main/vertical cases of the frame group; `canvas: "all"` with one available canvas; `stream.start` refused before any key read; `stream.destination.*` on an absent first id answers `not_found`; `available` changes publish an event; OBS import with key and no server; old profiles with a server list their first destination unchanged.
- UI: mock-ups (empty state, last-destination callout, frame without Go live) in dark and light before code, screenshots after, owner approval before merge (rule 16).

## Alternatives considered

- **Keep the first destination fixed** (ADR-0127 as is): no change, but the user sees one row they cannot remove and cannot turn streaming off. Rejected by the owner.
- **Move the next destination into the first slot on remove:** keeps the first slot always filled, but moves a key between credential store accounts (a step that can fail half way), changes that destination's API id under Stream Deck buttons and scripts, and has no answer when every destination is removed. Rejected.
- **A separate "Streaming" on/off setting:** can disagree with the list (on with no destination, off with five), and adds a step. Rejected for availability derived from the list.
- **A `removed` flag in the first destination's entry:** explicit, but a new field in a section older builds read strictly, and a format version bump, for what "no server and no key" already says. Rejected.
- **Hide Settings, Stream while streaming is off:** leaves no place to turn it on. Rejected.
