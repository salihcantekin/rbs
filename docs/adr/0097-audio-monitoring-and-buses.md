# ADR-0097: Audio monitoring and buses

- Status: Proposed
- Date: 2026-11-10
- Deciders: Salih (owner)
- Spec: [audio-graph](../specs/audio-graph.md), [audio-io-port](../specs/audio-io-port.md), [scene-model](../specs/scene-model.md), [control-api](../specs/control-api.md)
- Builds on: [ADR-0037](0037-audio-graph.md), [ADR-0081](0081-master-strip-in-the-mixer.md), [ADR-0082](0082-audio-filter-chains-on-sources.md), [ADR-0095](0095-audio-ducker-and-key-tap.md), [ADR-0013](0013-zero-cost-when-unused.md)

## Context

Every audio source goes to one mix, `main`, whose master strip feeds the encoders. Two everyday needs are missing: hearing a source or the mix in headphones without sending it to the stream (monitoring), and sending different sources to different outputs, for example a stream mix and a recording or "VOD safe" mix without music (buses). The audio-graph spec lists both as out of scope; audio-io-port.md reserves `AudioBackend::open_output` as a later minor version. The owner approved the proposal (2026-11-10): monitoring first, send levels (not only on/off), and an output picks one bus for now.

## Decision

### Part 1: monitoring (F1)

1. **Audio output in the port** (signatures go into audio-io-port.md in the F1 change). `AudioBackend::open_output(&self, req: OutputRequest) -> Result<Box<dyn AudioOutput>, AudioIoError>`, default `Unsupported`. `EndpointKind::Output` lists render endpoints for playback (`OutputLoopback` stays the capture of a render endpoint); `AudioEndpoint` gains an opaque `device_key` that is equal for a render endpoint and its loopback endpoint (decision 8). `OutputRequest { endpoint: EndpointId, channels: ChannelLayout, ring_frames: usize }`; the adapter picks the device's shared-mode mix rate and reports it (no OS resampling, as for input). `AudioOutput` has `format()`, `start()`, `stop()`, `latency_ns()`, `stats() -> OutputStats { written, played, silence_frames, dropped_frames }` and `producer() -> OutputProducer`, a wait-free single-producer ring writer the engine pushes interleaved f32 into; the OS render callback is the consumer (the reverse of the input ring, so a new support module, not `ring.rs`). The callback allocates, locks and blocks nothing (P6); an empty ring plays silence and counts it; a full ring drops the newest and counts it. Capabilities: `audio.output` (Flag), `audio.output.enumerate` (Flag), `audio.output.latency_ns` (Int, estimate). Invariant "zero cost before start" holds for output: `open_output` opens no stream until `start`. Linux/PipeWire has no output adapter in this change, so the feature is hidden there by capability (CI has no output hardware). WASAPI render (shared mode) and CoreAudio output are the adapters.
2. **Conformance** (the input suite's equivalents): listing, open and start, `written == played + silence + dropped`, underrun and overrun accounting, no allocation in the callback, release on stop and drop, device loss (`EndpointLost`, `DeviceBusy` recoverable as in ADR-0024), honest `latency_ns`, plus negative wrappers like the input suite. The reference output (`rbs-audio-io-test`) simulates a drifting device clock.
3. **Clock, rate and latency.** The graph runs at its own rate with `block_time = tick - latency`; the output device runs on its own clock. An `OutputNode` in `rbs-audio` (placed there, not in `rbs-app`, so headless composition roots use it) resamples to the device rate and steers drift the way `InputNode` does for input, writes into the ring and tolerates both over- and underrun. Monitoring therefore has the graph's latency plus the ring, not a low-latency path; the UI shows the figure next to the device and the help says so (live performers keep using their interface's direct monitoring). A low-latency tap is a separate later ADR.
4. **Monitor device and failure containment.** One monitor device is app state of the machine that runs the engine, chosen in Settings; "System default" follows the OS default output, a named device stays. Opening and closing happen on the host side, never in the engine thread's `apply`. `EndpointLost` and `DeviceBusy` reopen with back-off; a monitor failure is contained: the mix and the encoders never wait for it.
5. **Per-strip monitor mode and solo.** A source has `monitor: Off | Only | Also` (default Off), stored in the source record (a new field: round-trip and loader tests decide whether the scene format number is bumped, recorded in the F1 PR). The monitor mix is the sum of monitored strips after the strip fader and before the master, so it does not pass through the master. `Only` leaves the mix by ramping its `main` send to 0 over the existing mixer ramp (the strip stays linked, so there is no hard cut on the stream; the "inputs that leave stop at once" rule is not used here). Solo is session state, not saved: while any strip is soloed, the monitor plays only soloed strips (including `Also` strips); the mix and the encoders are unchanged. Once buses exist, a bus can be monitored (post its fader). Monitor volume is one saved setting. All monitor and send changes are ramped (declick).
6. **One mixer, extra outputs.** Strip gain, mute and ramps live in the `MixerNode`, so the monitor is a second output of that mixer (and each bus a further output), not separate nodes that re-apply gains. The meter of a strip records once per block whatever the number of outputs. This is the hot-path change of F1 (P15: before/after numbers, human approval, `hot-paths.md` updated: monitor output, output ring producer, render callbacks).
7. **Zero cost (P13).** With every strip Off and no solo, no monitor device is opened, no ring or output node exists and the mixer has no monitor output. The first monitored strip builds them and opens the device (Standby to Active); the last one tears them down. Output enumeration runs only while the Settings picker is open.
8. **Feedback.** Display companions already leave RBS's sound out (ADR-0096 `exclude_own_process`). The real risk is another `OutputLoopback` source (or a PipeWire sink monitor, which lacks the capability) on the monitor's device. `device_key` makes the comparison possible; the UI warns exactly when the monitor's `device_key` equals the key of an active loopback source that cannot exclude RBS's own process. The engine does not block it.

### Part 2: buses (F2)

9. **Buses belong to a canvas.** The master is per canvas (ADR-0081, ADR-0093 decision 5), so buses are too. Each canvas keeps an ordered bus list; `main` always exists, cannot be removed and is the canvas's existing master (volume, mute, meter), so there is no migration of master values and two canvases never share a bus. A bus has a `BusId` (never reused, as source ids), a name, volume, mute and a chain of audio filters (ADR-0082 `Filter` model, unchanged). Sends are stored per canvas: for a source, a level per bus (linear gain, 0 means none); the default is `main` at 1.0 and every other bus at 0, and an absent entry means the default. Sends are post-fader and before the bus's own fader. Per-scene levels (ADR-0091) keep changing a source's fader and mute, which sends follow; they do not change sends. The ducker key (ADR-0095) is untouched. `MAX_BUSES` is 8 per canvas (the mixer has a fixed per-block cost in it).
10. **Graph.** The one mixer of a canvas (decision 6) gets one output per bus that has a non-zero send or is used by an output; `main` is unchanged for a project that never adds a bus and its per-block work must not grow (numbers prove it, rule 12). Send level changes ramp.
11. **Outputs choose a bus.** A recording or stream output (Output profile, ADR-0051) names one `(canvas, bus)`; the default is `(its canvas, main)`. Multi-track containers (one bus per track) are a later change.
12. **Removal and dangling references.** Removing a bus is refused while an output uses it (the message names the output); otherwise it deletes the bus, its filters and every send to it in one undo record of the collection (outputs are not in the collection, so none is touched). A profile that names a bus that does not exist (profile used with another collection, or an older save) makes that output silent with a visible error; it never falls back to `main`, so music cannot leak into a "VOD safe" recording.
13. **Scene format and control API.** Sends and buses are new data: scene format bump, with a loader migration that gives every canvas its `main` bus and keeps masters as they are (decided and recorded in the F2 PR with the round-trip test). Control API: `bus.list/add/remove/set`, `source.set_sends`, `source.set_monitor`, topics `bus.changed` and `monitor.changed`, each the next free minor at merge. New fields in existing payloads are additive and optional; decoders from older minors ignore unknown fields (the control-api note that some decoders reject an unknown `state` is respected by adding no new `state` values).
14. **UI and staging.** Monitoring first, then buses; each has a visual proposal and screenshots in the three themes before merge (rule 16). Order: (a) this ADR, independently reviewed; (b) F1: port and reference output with conformance suite, CoreAudio and WASAPI adapters (device tests on the Mac and the Windows machine, one device slot, numbered steps), `OutputNode` and mixer output (bench, P15), host and API, UI; (c) F2: scene model and migration, mixer outputs (bench, P15), API, UI. The binder part lives in the crate that owns the audio binder today, not in `rbs-app`.

## Consequences

- Headphone monitoring and per-output mixes arrive without changing how a single-mix project behaves or costs.
- The port gains audio output once; it also serves a later virtual microphone output.
- The mixer changes twice (a second output in F1, N outputs in F2): both need measurements and a human maintainer's approval.
- Monitoring has the graph's latency; it is not a live-performer path.
- The scene format and control API grow; round-trip, migration and dangling-bus tests are required.
- Monitoring through a device that a loopback source captures can echo; the UI warns, the engine does not block.

## Alternatives considered

- **Monitoring as a bus.** Couples headphone latency and device handling to bus mixing; the monitor has a different consumer (a device callback) and must stay absent when unused.
- **A separate monitor node that re-applies gains.** Can drift from the stream and duplicates the ramps and meters.
- **Collection-wide buses.** Contradicts the per-canvas master and leaves the migration of two masters undefined.
- **Send on/off only (like OBS tracks).** Cannot sit a strip lower in one mix; the level costs one multiply per active send and nothing at 0.
- **Per-output mixes without buses (a mask per output).** No bus fader or filters, so "limiter only on the stream" is impossible.
- **Both parts in one change.** The port and device work (F1) and the bus work (F2) carry different risks.
