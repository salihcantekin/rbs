# ADR-0097: Audio monitoring and buses

- Status: Accepted
- Date: 2026-11-10
- Deciders: Salih (owner)
- Spec: [audio-graph](../specs/audio-graph.md), [audio-io-port](../specs/audio-io-port.md), [scene-model](../specs/scene-model.md), [control-api](../specs/control-api.md)
- Builds on: [ADR-0037](0037-audio-graph.md), [ADR-0081](0081-master-strip-in-the-mixer.md), [ADR-0082](0082-audio-filter-chains-on-sources.md), [ADR-0095](0095-audio-ducker-and-key-tap.md), [ADR-0013](0013-zero-cost-when-unused.md)

## Context

Every audio source goes to one mix, `main`, whose master strip feeds the encoders. Two everyday needs are missing: hearing a source or the mix in headphones without sending it to the stream (monitoring), and sending different sources to different outputs, for example a stream mix and a recording or "VOD safe" mix without music (buses). The audio-graph spec lists both as out of scope; audio-io-port.md reserves `AudioBackend::open_output` as a later minor version. The owner approved the proposal (2026-11-10): monitoring first, send levels (not only on/off), and an output picks one bus for now.

## Decision

### Part 1: monitoring (F1)

1. **Audio output in the port** (signatures go into audio-io-port.md in the F1 change). `AudioBackend::open_output(&self, req: OutputRequest) -> Result<Box<dyn AudioOutput>, AudioIoError>`, default `Unsupported`. `EndpointKind::Output` lists render endpoints for playback (`OutputLoopback` stays the capture of a render endpoint); `AudioEndpoint` gains an opaque `device_key` that is equal for a render endpoint and its loopback endpoint (decision 8). `OutputRequest { endpoint: EndpointId, channels: ChannelLayout, ring_frames: usize }`; the adapter picks the device's shared-mode mix rate and reports it (no OS resampling, as for input). `AudioOutput` has `format()`, `start()`, `stop()`, `latency_ns()`, `stats() -> OutputStats { written, played, silence_frames, dropped_frames }` and `producer() -> OutputProducer`, a wait-free single-producer ring writer the engine pushes interleaved f32 into; the OS render callback is the consumer (the reverse of the input ring, so a new support module, not `ring.rs`). The callback allocates, locks and blocks nothing (P6); an empty ring plays silence and counts it; a full ring drops the newest and counts it. Capabilities: `audio.output` (Flag), `audio.output.enumerate` (Flag), `audio.output.latency_ns` (Int, estimate). Invariant "zero cost before start" holds for output: `open_output` opens no stream until `start`. Linux/PipeWire has no output adapter in this change, so the feature is hidden there by capability (CI has no output hardware). WASAPI render (shared mode) and CoreAudio output are the adapters.
2. **Conformance** (the input suite's equivalents): listing, open and start, `written == played + silence + dropped`, underrun and overrun accounting, no allocation in the callback, release on stop and drop, device loss (`EndpointLost`, `DeviceBusy` recoverable as in ADR-0024), honest `latency_ns`, plus negative wrappers like the input suite. The reference output (`rbs-audio-io-test`) simulates a drifting device clock.
3. **Clock, rate and latency.** The graph runs at its own rate with `block_time = tick - latency`; the output device runs on its own clock. An `OutputNode` in `rbs-audio` (placed there, not in `rbs-app`, so headless composition roots use it) resamples to the device rate and steers drift the way `InputNode` does for input, writes into the ring and tolerates both over- and underrun. Monitoring therefore has the graph's latency plus the ring, not a low-latency path; the UI shows the figure next to the device and the help says so (live performers keep using their interface's direct monitoring). A low-latency tap is a separate later ADR.
4. **Monitor device and failure containment.** One monitor device is app state of the machine that runs the engine, chosen in Settings; "System default" follows the OS default output, a named device stays. Opening and closing happen on the host side, never in the engine thread's `apply`. `EndpointLost` and `DeviceBusy` reopen with back-off; a monitor failure is contained: the mix and the encoders never wait for it.
5. **Per-strip monitor mode and solo.** A source has `monitor: Off | Only | Also` (default Off), stored in the source record (a new field: round-trip and loader tests decide whether the scene format number is bumped, recorded in the F1 PR). The monitor mix is the sum of monitored strips after the strip fader and strip mute (a source muted for the stream is silent in the headphones too) and before the master, so it does not pass through the master. `Only` takes the strip off the stream by ramping its effective send to 0 over the existing mixer ramp; the effective send is the stored send times (Only ? 0 : 1), so stored levels survive, and `Only` leaves every bus, not only `main`. The strip stays linked, so there is no hard cut. `Only` degrades to `Off` whenever no monitor is active (no output capability, no device, device failed): a collection opened on another machine never loses a source from the stream because of a device it does not have. Audio strips exist only for program scenes (the binder), so monitoring covers sources in the scene on air; cueing a source in the preview scene is out of scope here and noted as a follow-up. With two canvases, the monitor output belongs to the main canvas's mixer only (the vertical canvas shares that mix, ADR-0093), so a shared source is never summed twice. Solo is session state, not saved: while any strip is soloed, the monitor plays only soloed strips (including `Also` strips); the mix and the encoders are unchanged. Once buses exist, a bus can be monitored (post its fader). Monitor volume is one saved setting. All monitor and send changes are ramped (declick).
6. **One mixer, extra output pins.** Strip gain, mute and ramps live in the `MixerNode`, so the monitor is a further output of that mixer (and each bus another), not separate nodes that re-apply gains. The mixer declares its monitor and bus pins always; an unlinked pin does no accumulation, so linking one is a schedule swap (ADR-0020) that keeps the node and therefore every strip ramp: enabling monitoring on air must not glitch the stream, and a test proves ramp state survives the swap. The master applies to `main` only; filter chains of a bus run as nodes after that bus's pin; `main` has its master and may carry a chain like any bus. A strip's meter records once per block whatever the number of outputs. This is the hot-path change of F1 (P15: before/after numbers, human approval, `hot-paths.md` updated: monitor pin, output ring producer, render callbacks).
7. **Zero cost (P13).** With every strip Off and no solo, no monitor device is opened, no ring or output node exists and the mixer has no monitor output. The first monitored strip builds them and opens the device (Standby to Active); the last one tears them down. Output enumeration runs only while the Settings picker is open.
8. **Feedback.** Display companions already leave RBS's sound out (ADR-0096 `exclude_own_process`). The real risk is another `OutputLoopback` source (or a PipeWire sink monitor, which lacks the capability) on the monitor's device. `device_key` makes the comparison possible (WASAPI: the IMMDevice id shared by a render endpoint and its loopback; CoreAudio: the device UID); aggregate and virtual devices will not compare equal, so the warning is best effort; the UI warns exactly when the monitor's `device_key` equals the key of an active loopback source that cannot exclude RBS's own process. The engine does not block it.

### Part 2: buses (F2)

9. **Buses belong to the main canvas.** The master is per canvas (ADR-0081), and a canvas with `audio_from = main` (the vertical canvas, ADR-0093 decision 5) has no mixer or buses of its own: it resolves to the main canvas's. So the bus list lives on the main canvas; `main` always exists, cannot be removed and is that canvas's existing master (volume, mute, meter), so no master value migrates. A bus has a `BusId` (never reused inside the collection, as source ids), a unique name, volume, mute and a chain of audio filters (ADR-0082 `Filter` model, unchanged). Sends are stored on the canvas: `sends: source -> (bus -> level)` in linear gain, 0 meaning none; the default is `main` at 1.0 and every other bus at 0, an absent entry meaning the default. Send edits are live ops with narrow undo records like ADR-0081 and ADR-0091 level edits (no `undo_conflict` for others); removing a source, a canvas or a bus removes the matching sends in that op's own undo record. Sends are post-fader and before the bus's own fader. Per-scene levels (ADR-0091) keep changing a source's fader and mute; sends are unchanged by them. The ducker key (ADR-0095) is untouched. `MAX_BUSES` is 4 (a fixed per-block cost; outputs are capped at two anyway, the rest serve monitoring).
10. **Graph.** The one mixer of a canvas (decision 6) gets one output per bus that has a non-zero send or is used by an output; `main` is unchanged for a project that never adds a bus and its per-block work must not grow (numbers prove it, rule 12). Send level changes ramp.
11. **Outputs choose a bus by name.** A recording or stream output (Output profile, ADR-0051) stores a bus *name*, never ids: ADR-0051 keeps canvas ids out of profiles, and a profile is shared across collections where ids would mean different buses. The default is `main`. Audio encoders are shared between outputs only when their settings match (ADR-0047 decision 3); the bus is part of that key, so two outputs on different buses get separate encoders (the per-canvas two-output limit stands, ADR-0093 decision 6). Multi-track containers (one bus per track) are a later change.
12. **Removal and dangling references.** Removing a bus is refused while an output of the loaded profile uses it (the message names the output); otherwise it deletes the bus, its filters and every send to it in one undo record of the collection. A saved profile that names a bus the current collection does not have cannot be checked while it is not loaded, so the safeguard is at start: that output refuses to start with a visible reason ("bus 'VOD safe' does not exist"); it never falls back to `main`, so music cannot leak into a "VOD safe" recording, and it does not record silence. Renaming a bus updates the loaded profile's references in the same step.
13. **Scene format and control API.** Sends and buses are new data: scene format bump, with a loader migration that gives the main canvas its `main` bus and keeps masters as they are (decided and recorded in the F2 PR with the round-trip test). Control API: `bus.list/add/remove/set`, `source.set_sends`, `source.set_monitor`, topics `bus.changed` and `monitor.changed`, each the next free minor at merge. New fields in existing payloads are additive and optional; decoders from older minors ignore unknown fields (the control-api note that some decoders reject an unknown `state` is respected by adding no new `state` values).
14. **UI and staging.** Monitoring first, then buses; each has a visual proposal and screenshots in the three themes before merge (rule 16). Order: (a) this ADR, independently reviewed; (b) F1: port and reference output with conformance suite, CoreAudio and WASAPI adapters (device tests on the Mac and the Windows machine, one device slot, numbered steps), `OutputNode` and mixer output (bench, P15), host and API, UI; (c) F2: scene model and migration, mixer outputs (bench, P15), API, UI. The binder part lives in the crate that owns the audio binder today, not in `rbs-app`.

## Consequences

- Headphone monitoring and per-output mixes arrive without changing how a single-mix project behaves or costs.
- The port gains audio output once; it also serves a later virtual microphone output.
- The mixer changes twice (a second output in F1, N outputs in F2): both need measurements and a human maintainer's approval.
- Monitoring has the graph's latency; it is not a live-performer path.
- The scene format and control API grow; round-trip, migration and dangling-bus tests are required.
- Monitoring through a device that a loopback source captures can echo; the UI warns, the engine does not block.

## Alternatives considered

- **Monitoring as a bus.** Couples headphone latency and device handling to bus mixing; the monitor has a different consumer (a device callback) and must stay absent when unused.
- **A separate monitor node that re-applies gains.** Can drift from the stream and duplicates the ramps and meters.
- **Collection-wide buses.** Contradicts the per-canvas master and leaves the migration of two masters undefined.
- **Send on/off only (like OBS tracks).** Cannot sit a strip lower in one mix; the level costs one multiply per active send and nothing at 0.
- **Per-output mixes without buses (a mask per output).** No bus fader or filters, so "limiter only on the stream" is impossible.
- **Both parts in one change.** The port and device work (F1) and the bus work (F2) carry different risks.

## Review

Round 1, independent AI session (2026-11-10): changes requested (8 blocking: buses vs per-canvas masters, monitor sum cannot be post-fader without the mixer, hard cut on `Only` and sends, missing output clock and latency, thin port contract, thin conformance, removal and profiles not atomic, wrong feedback model; 6 non-blocking). All addressed in the round 2 text. Owner approval of the shape: Salih, 2026-11-10 ("olur göster", "önerini uygula"); acceptance waits for the review.

Round 2, independent AI session (2026-11-10): changes requested (4 high: buses vs ADR-0093's shared mix, profile references vs ADR-0051, encoder sharing key vs ADR-0047, fixed mixer pin vs schedule swap; 5 medium/low: `Only` without sends, `Only` on a machine without a device, preview and two-canvas monitoring, where sends live and undo, muted strips in the monitor). All addressed in this text.

Round 3, independent AI session (2026-11-10): approve, no blocking problems. Notes for the implementation PRs: (1) mixer ramp state is keyed by producer today; sends and `Only` need ramp state per (producer, bus) with fixed capacity, sized in the F2 design and bench; (2) the F2 PR pins whether `main` is a stored record or implicit (one source of truth for its volume and mute); (3) a canvas with `audio_from = main` keeps its own `master` field, which is ignored for audio (the UI hides it); (4) the start-time refusal for a missing bus offers a one-click fix (choose another bus); (5) a test that no stored send or `Only` entry for a removed source or bus survives load. Owner approval of the shape: see above; owner acceptance: Salih, 2026-11-10 ("ADR-0097'yi kabul ediyorum").

Implementation note (F1 mixer monitor output, 2026-11-10): decisions 6 and 7 read together. The mixer always declares its `monitor` pin (decision 6); "no monitor output" in decision 7 means the pin is not linked, so the mixer does no monitor work. "No monitor is active" in decision 5 is read in the engine as "the monitor pin is not read by a node with an instance" (`Outputs::is_linked`): an output node held after a failed `prepare` or waiting for a restart does not count. An independent AI review of that PR found this case and it is fixed and tested there.

Implementation note (F1 host and scene format, #305, 2026-11-10): decision 5's round-trip and loader tests decided the bump. The loader refuses unknown keys, so the source `monitor` key needs scene format 10; formats 1 to 9 load unchanged and an older document that carries `monitor` is refused (`rbs-user-data` tests `a_collection_round_trips_exactly_with_its_counters`, `a_monitor_in_a_format_before_10_is_refused`).

Implementation note (F1 control API, protocol 1.30, 2026-11-10): decision 13 names `source.set_monitor` and `monitor.changed`. Decisions 4, 5 and 7 also need a way to read the monitor's state, list devices, choose the device and volume, and solo, so 1.30 adds `monitor.status` (`read`, snapshot of `monitor.changed`), `monitor.devices` (`read`; the API's form of "enumeration only while the picker is open": clients call it when they show a picker), `monitor.set_device` (`admin`, a saved setting of the computer that decides which speaker hears the program), `monitor.set_volume` (`control`, like a source's volume) and `monitor.set_solo` (`control`, session state). An independent AI review of the 1.30 change (2026-11-10) asked for the `admin` scope on `monitor.set_device` and for this note; both are in that PR.
