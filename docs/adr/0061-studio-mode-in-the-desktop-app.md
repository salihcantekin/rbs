# ADR-0061: Studio mode in the desktop app

- Status: Accepted
- Date: 2026-11-07
- Deciders: Salih (owner)
- Builds on: ADR-0021 (scene collection model: program and preview per canvas), ADR-0034 and ADR-0036 (preview layer), ADR-0041 (studio on a running engine), ADR-0048 (preview handles), ADR-0049 (studio split, `rbs.transition`), ADR-0054 (the picture never disappears), ADR-0059 (scenes in the studio), ADR-0013 (zero cost when unused), ADR-0052 (API parity and effects)

## Context

The owner tested ADR-0059 on the Mac (2026-11-07) and asked where studio mode is: a Preview of the next scene beside the Program on air, and a way to move it to air. The pieces exist only in parts:

- **Model.** A canvas has `program` and an optional `preview` scene; `set_preview` is a live edit, and `wanted_sources` already includes the preview scene's sources (scene model spec). "Studio mode" is defined as engine state: a canvas is in studio mode while it has a preview scene (UI design system spec, Studio mode).
- **Binder.** `SceneBinder` already makes a second compositor per canvas for the preview scene (`Role::Preview`), with its layers, and retires it when the preview is cleared.
- **Studio.** `rbs_record::Studio` adopts only the program compositor and links one `PreviewNode` (one surface ring, one endpoint) to it. A preview compositor the binder makes is never instantiated, so it would be a node without a runtime.
- **App.** One picture layer (`rbs_app::preview`, a thread-local singleton) shows the program on the Program panel, else on Preview. The Live workspace already has the studio split (Preview, the `rbs.transition` rail, Program), but the rail has no content, nothing enters studio mode, and the host and the control API have no preview-scene commands.
- **Transitions.** Only a cut exists. A fade needs both scenes drawn into textures and blended for the length of the transition; that is new GPU work on the render path.

## Decision

1. **Studio mode is the canvas's preview scene.** Entering studio mode sets the preview to the program scene (`set_preview(canvas, Some(program))`); leaving it clears the preview. Both are live actions, never on the undo stack (ADR-0021). The preview scene is saved with the collection like the program, so the app starts in the mode it was left in. The app runs one canvas; the rules below are for the studio's canvas.
2. **The studio renders the preview scene only in studio mode, and only for a UI.** When the canvas has a preview scene and the studio has a preview description (`StudioSettings::preview`, set only by the desktop app on platforms with a picture layer), `Studio::update` (and `Studio::start`) instantiates the preview compositor the binder made (`Role::Preview`, same `CompositorNode` type and layer limit as the program's, on `RENDER`) and links a second `PreviewNode` to it with its own surface ring and endpoint (`Studio::scene_preview() -> Option<PreviewEndpoint>`). Without a preview description (headless recording, `rbs-cli`, Linux) the binder's preview compositor has no consumer, so the schedule plan leaves it and the preview-only sources out (`SkipReason::NoSink`): nothing of studio mode runs or opens, and a strict recording only checks the program scene, as before. Leaving studio mode retires both nodes; they leave the graph and are taken back after the apply, through the pending takes with no source when their partition is still swapping. Neither node is essential: a failure of either is reported as the Preview panel's picture failing and never stops the studio or its outputs. Outputs (recording, stream) and the mixer stay on the program compositor and the program scene: what goes out never depends on studio mode. Without studio mode nothing of this exists (P13). In studio mode the cost is one more compositor pass and one more preview publish per frame, plus the preview scene's sources running (Active), which is what studio mode is for.
3. **Transition is a cut, and it swaps.** `Transition` sets the program to the preview scene and the preview to the old program scene (the usual "swap after transition"), in one step before the studio updates, so the outputs change on the next frame. The binder keeps the compositor node ids by role and gives them new layers and links, so no node is added or removed by a cut. The cut is one schedule swap: as for any layer change (ADR-0023, recording spec), the layers are sent before the apply and the compositor draws only layers whose producer is linked in the schedule it runs, so no program frame ever shows a layer of the old scene after the cut's first frame and no frame mixes the two scenes' boxes; for at most one frame the new scene may lack a layer whose source was not yet linked to the program compositor (in studio mode the preview scene's sources are already running, so its picture is ready). A later transition decision may make the swap frame-exact. A transition with the same scene in both does nothing. It is a live action, not undoable. Fade and other transitions (a T-bar, a duration) are a later decision: they need render-to-texture of both scenes and a blend node on the render path (hot path, P15).
4. **In studio mode the user edits the preview scene.** The host keeps two scenes apart: `program` (on air; ADR-0059's rules) and the *edited* scene (the preview scene in studio mode, else the program). The Sources panel, Properties, the picture handles (ADR-0048) and the app's source and item commands act on the edited scene, so the next scene is prepared without touching what is on air. A click in the Scenes panel, and `scene.select` / `scene.position?n` from the command registry, set the preview scene; Transition puts it on air. Handles are drawn only on the Preview panel's picture; a press on the Program picture selects nothing and the Program panel shows no marks. The Mixer lists what is heard: the program scene's audio (the binder mixes only the program scene). Outside studio mode everything acts on the program scene, as in ADR-0059.
5. **Host rules (extending ADR-0059 decision 4).**
   - Undo and redo never change the program or the preview scene, and never turn studio mode on or off: "the mode is on" means the canvas had a preview scene before the step. The host remembers both scenes before applying a record and puts them back (outside the undo stack); a remembered preview scene that no longer exists is replaced by the program scene, and a preview a record brought back while the mode was off is cleared.
   - There is always a preview scene in studio mode: removing the preview scene first sets the preview to the program scene (if the removed scene is also on air, after the program has been switched as ADR-0059 says, to the new program), outside the undo stack, because the model's removal would otherwise clear the preview and end the mode.
   - Scene numbers, names and the program rules are unchanged.
6. **The app shows two pictures in studio mode.** `rbs_app::preview` keeps one layer per role (Program, Preview), each with its own connection, area, covers and marks; everything ADR-0054 says about covers applies to each. In studio mode the Program panel shows the program endpoint and the Preview panel the preview endpoint; a panel that is not shown has no layer attached and its frames are not shown (and the subscriber is dropped as ADR-0056 decision 5 does for a hidden window). Outside studio mode there is one layer and the routing of ADR-0059 is unchanged (Program if shown, else Preview). A Preview panel in studio mode never shows the program picture, and the reverse, so the two are never confused. On Windows a window has a single DirectComposition target (ADR-0036), so a second layer cannot attach yet: there the studio is started without `scene_preview` and the Preview panel says in words that this platform cannot show the preview scene; Program keeps the program picture. A target shared by both pictures is a follow-up with its own hardware check.
7. **UI.**
   - Studio mode is switched from the toolbar (Studio mode, a toggle, as the UI spec's Live workspace has it) and the Scene menu (`canvas.studio_mode.toggle`); the registry also has `canvas.transition` (enabled only in studio mode) for the menu, the toolbar and shortcuts (the UI spec's Ctrl/Cmd+Enter, and Space while Preview or Program has the focus, through the shortcuts work, ADR-0060).
   - The `rbs.transition` panel gets its first content, per its width as the UI spec says: from 40 px a rail with the transition's name ("Cut", the only one for now) and, in studio mode, a primary **Transition** button (Auto and the T-bar come with fades); below 40 px only the button, as a floating control over the bottom edge of the two views; outside studio mode only the name. As an ordinary panel it shows the same at its size. Keyboard: the button is reachable and activates with Return or Space.
   - Entering studio mode opens a closed Preview panel where it opens by default, as the UI spec says (the only layout change studio mode makes).
   - Scenes panel in studio mode: the preview scene is marked like a selected row (`accent.subtle`, `accent` border, accessible "in preview"); the program scene carries a neutral "Program" badge (`surface.overlay`, `text.secondary`, accessible "program"), which becomes the live badge of ADR-0059 in `state.live` while streaming or recording. One scene in both shows both marks.
   - Toolbar and menus: the registry commands `canvas.studio_mode.toggle` and `canvas.transition` (owned by the command registry, ADR-0050) call the same host commands; the Live workspace's toolbar shows Studio mode as in the UI spec.
8. **Control API 1.9** (a minor version: nothing earlier changes meaning; numbered 1.7 when proposed, renumbered because the filters of ADR-0062 shipped first as 1.8).
   - `scene.list` and `scene.changed` gain `preview` (a scene id, absent outside studio mode); `scene.changed` is also sent when the preview scene changes or studio mode starts or ends.
   - `canvas.set_preview {scene}` (`control`; the method name the UI spec planned): a scene id enters studio mode with that scene in preview, or changes the preview scene; `null` leaves studio mode (the preview choice is not kept: entering again starts from the program scene). `not_found` for an unknown scene, `invalid_params` for a scene the canvas may not show (scope), like `scene.switch`.
   - `canvas.transition {}` (`control`): the cut of decision 3; `conflict` outside studio mode; a preview scene that is the program changes nothing.
   - Both are live and not undoable. An optional `canvas` parameter joins them when the app runs several canvases (a minor addition).
   - `source.list`, `source.changed`, `source.add` and `item.add` keep meaning the program scene. `source.list {scene?}`, `source.add {..., scene?}` and `item.add {source, scene?}` take an optional scene (a minor addition), so a client can list and fill the preview scene; `source.changed` stays the program scene's list. Item methods take global item ids and are unchanged.
   - Effects (ADR-0052): `canvas.set_preview` `edit` without the on-air check (nothing on air changes), `canvas.transition` `edit` with the on-air check; `source.add` and `item.add` with a scene other than the program without it.
9. **Zero cost.** Off: no preview compositor instance, no second preview node, no second layer, no second subscriber, no per-frame check. On: costs as decision 2, in the same `RENDER` partition as the program, so it shares the program's frame deadline. The hot-path code (compositor, preview publisher) is not changed; it runs a second instance. Measurements (P15) on the Mac before merge or right after, with the owner: the render worker's tick time (p50, p99), late program frames and dropped frames of a recording, and the app's CPU and GPU, studio mode off and on, at 1920x1080 60 fps with two screen sources and a camera, and at the largest canvas the app offers. If the program's deadline suffers, the preview compositor renders at the preview's size, a follow-up inside this decision.

## Consequences

- `rbs_record::Studio` gains the preview compositor and `scene_preview()`; its spec (recording) says when they exist. Tests: entering and leaving studio mode creates and retires them, a cut changes only layers (no node added or removed), outputs stay on the program compositor.
- `rbs-app`: host commands `SetStudioMode`, `Transition` (and `SwitchScene` sets the preview in studio mode); `SceneList` gains `preview`; the "edited scene" is the preview scene in studio mode; a new `Update::ScenePreview(Option<PreviewEndpoint>)` carries the second endpoint each time it appears or goes. Tests cover removing the preview scene, undo across a cut, and that a cut is not undone.
- `rbs_app::preview` becomes per role; the UI sends two areas.
- Specs: scene model (none), recording, control API 1.9, UI design system (Transition panel, Scenes marks, two pictures), user data (none: `preview` is already saved).
- Follow-ups: fade and other transitions with T-bar and duration (own ADR, hot path); "duplicate scene into preview" and "swap off" options; studio mode per canvas when the app runs several canvases.

## Alternatives considered

- **Render the preview scene into the same picture as the program, side by side.** One layer, but a canvas twice as wide on the render path and the output would need cropping; it mixes what goes out with what is prepared.
- **Studio mode as UI state only (the preview scene not saved, not in the engine).** The model and the UI spec already define it as canvas state shared by every client; an API client must see and drive it.
- **Edit the program scene in studio mode too.** Simpler, but every edit would hit what is on air, which is what studio mode exists to avoid.
- **No swap after a cut (preview keeps the new program).** Both are common; swap lets the user go back and forth with one button and keeps the old scene's sources Active, which makes the way back instant.
- **Fade now.** Needs render-to-texture and a blend node on the render path, with measurements and the owner's hot-path sign-off; it would delay the mode itself.

## Review

Independent review per ADR-0014.

- Reviewer: independent AI session (given only the ADR, principles, specs and code). Date: 2026-11-07. Verdict: changes requested; all resolved in this revision (first numbered 0060; renumbered because the shortcuts ADR took 0060).
- Concerns and resolutions:
  1. 1.7 changed the meaning of 1.6 `source.list`, `source.changed`, `source.add`, `item.add`: they keep meaning the program scene; an optional `scene` parameter is the addition (decision 8).
  2. Studio mode not opt-in for headless use: the preview compositor and its sources run only with a preview description, which only the desktop app sets; without a consumer the plan drops them (decision 2).
  3. A preview failure could end the studio: neither node is essential (decision 2).
  4. Cut atomicity unspecified: stated what a cut frame can and cannot show (decision 3).
  5. The host conflated program and edited scene: two scenes named in decision 4; "mode on" defined as "preview before the step" (decision 5).
  6. Measurement plan too narrow: render tick time, late and dropped program frames, at 1080p60 and the largest canvas (decision 9).
  7. Method names conflicted with the specs: `canvas.set_preview` and `canvas.transition`; `scene.changed` on preview changes; scope refusal stated (decision 8).
  8. UI conflicts with the design system spec: toggle in the toolbar and menu, rail per width, shortcuts, auto-open of Preview, Program picture presses and the Mixer stated (decisions 4 and 7).
  9. Endpoint lifecycle and per-role preview state: decision 6 and the host sends the second endpoint in its own update (Consequences).
  10. Leaving drops the preview choice: stated (decision 8).
- Owner: accepted under the standing project policy that threads may mark ADRs Accepted once the independent review is recorded and resolved (Salih, 2026-11-06); Salih may still reopen it.

Follow-up, 2026-11-10: the Windows limit of decision 6 is lifted. Every preview layer of the UI thread now uses one shared DirectComposition device and each window has one topmost target holding both pictures as child visuals (gpu-compositor spec, "Several layers in one window"), so the studio starts with `scene_preview` on Windows too and the Preview panel shows the preview scene. The hardware check on Windows is recorded in the implementing pull request. No decision changes; the Windows text of decision 6 is superseded by this record.
