## Context

A recording today is one file: the program scene composited, with one mixed audio track. An editor often needs the pieces: the screen capture, the camera and each microphone as their own files, so a scene can be recut, a camera reframed, a microphone cleaned up, without re-recording. The owner (2026-11-09) calls this his biggest complaint with OBS and wants it: a master file *and* the sources recorded separately, with a warning about the cost, and the least possible performance loss.

What the architecture gives (verified in the specs):

- Every source has its own node and its own picture before the compositor; the graph lets one output pin feed several consumers (ADR-0047), so a tap costs no capture. OBS has no such tap: it encodes only the composited output (plugins record a source by re-rendering it).
- A video output chain is *export* (GPU conversion to the encoder format, then a readback to system memory; the one P4 exception, ADR-0038, or a native surface for hardware encoders, ADR-0025), *encoder*, *muxer*, *file transport*. Each ISO video track is one more such chain, with nothing shared with the master: the cost is a conversion, an export and an encoder session per track, plus the disk writes. This is the real price of the feature and is why ADR-0087 exists.
- Audio sources are separate nodes (a source has video or audio, never both: `AudioOnVideoSource`), each feeding the mixer through its own filter chain (ADR-0082).
- `Studio` allows `MAX_OUTPUTS = 4` outputs: a recording and a stream for each of two canvases (`MAX_OUTPUTS_PER_CANVAS = 2`, ADR-0047, ADR-0093 decision 6; `crates/rbs-record/src/studio.rs`), a number sized for "record and stream", not for N tracks.
- Partitions each have a worker thread (ADR-0027); one thread per track would not scale.

Forces: the master recording and stream must never degrade because of ISO (P7, ADR-0055); all files must line up in an editor with no manual sync (P5); the cost must be shown *before* the recording starts (owner); zero cost when unused (P13); the user's quality choices are settings.

## Decision

1. **A new output kind: the *ISO set*.** A recording can carry an ISO set: a group of tracks started and stopped together with the master recording (or on its own). It is one `Studio` output of a new kind, not N outputs, so `MAX_OUTPUTS` keeps its meaning (record + stream per canvas) and the ISO set does not count toward it. In the first version only the main canvas's recording carries an ISO set; the vertical canvas's recording (ADR-0093, ADR-0111) never does, so `record.start {canvas: "all"}` gives one ISO set, attached to the main recording. An ISO set per canvas is a later decision. The set is bounded by what the machine can do (ADR-0087), with a fixed ceiling of 16 video tracks and 32 audio tracks in the first version.
2. **What is a track, and where its options live.** Per source, the user turns on *Record separately*: one switch, whose meaning follows the source's media kind (a source has video or audio, never both: `AudioOnVideoSource`), so a video source gives a video track and an audio source an audio track. The setting lives on the source in the scene collection, so it follows the source across scenes, not in an output profile (a profile holds no scenes, ADR-0051). It is an optional table `record_separately` on `Source`; absent means off. For a video source it holds `exclude_filters: bool?`, `size: "native" | "master"?`, `max_height: u32?` (`0` means no cap, even when the profile sets one) and `frame_rate: "canvas" | "source"?`; for an audio source `raw: bool?`. Each absent field means "use the profile default" (decision 4), so the table may be empty (`record_separately = {}` means "on, all defaults"); fields of the other media kind are refused by validation. A collection that never sets it is unchanged on disk, and the scene format number is raised (next free value at merge time) only in files that contain the table; `scene-model.md` and `user-data.md` record the fields. A video track is one file with one video stream; an audio track is one audio-only file (`Wav` or `Flac`, ADR-0085; WAV is written as RF64-capable from the start with a periodically refreshed header, so neither the 4 GiB limit nor a crash truncates it).
3. **What is recorded.**
   - **Video: the source's own picture, with its filters.** By default a track takes the tail of the source's filter chain (ADR-0062): the source's picture with its filters applied (colour correction, chroma key, LUT and so on) and its source region (ADR-0103, if that ADR is accepted: a region is part of the source, so the track shows what the source shows, and the crop is done by the track's scaled converter), but before the item's position, crop, style and rotation and before the scene's mix, so the file is that source alone, not the scene. The option *Exclude filters* (`exclude_filters`) takes the source node's output instead (the picture before any filter), for an editor who wants to redo the filtering later; a source with no filters gives the same picture either way. Any transparency in the recorded picture (a chroma key, a browser or image source with alpha, a window with alpha) is composited over black, filtered or not, because the encoders carry no alpha; the option's help says so. Tracks are tagged Rec. 709, like the master. `P010` SDR sources (BT.709 or BT.2020, not PQ or HLG) go through the same decode as the master; PQ and HLG sources are unsupported until HDR sources land, as on the canvas. Recording a source in its own colour space is a later decision.
   - **Video size: native or master size.** A per-track setting `size: native | master` (default `native`).
     - `native`: the source's own size at the start of the recording (its first frame at or after `t0`, or its known `picture_size`, ADR-0058, when that is known earlier), rounded up to even, with an optional cap (`max_height`, for example 2160) that adds a scaling pass.
     - `master`: the track is written at the size of the master recording's file, that is the recording's output size (ADR-0102), which is the canvas size unless the user set a different output size. The source is scaled to fit inside it with its aspect ratio kept, centred, the rest black (no crop, no stretch). This is the full-screen version of each source: a scene with a screen capture and a camera gives a full-screen screen-capture file and a full-screen camera file next to the master, all the same size and frame rate as the master, so an editor can cut between them or rebuild the layout without rescaling. It always uses the scaled converter; `max_height` does not apply. (The UI calls it *Same size as the recording*; the output size, not the canvas size, is used because that is the size of the master file the editor cuts against.)
     - **A track's size is fixed for the whole file.** A source whose size changes during the recording (a resized window, a camera that switches mode; ADR-0062 decision 5) is fitted into the track's fixed size by the same letterbox scaler, so the file stays valid and the encoder is never reopened. The track's converter re-binds its input view once per size change; this is a real-time exception (P6) of exactly the kind ADR-0062 decision 5 states for filters (at most one texture acquire or view creation per size change on the render thread, never on a steady tick), and it is part of the P15 sign-off of step 3. Each size change is recorded in the manifest (time and new source size).
   - **Frame rate:** the **canvas frame rate** in the first version (constant frame rate, the latest picture is repeated when the source delivered no new one, like the compositor does). Recording at the source's own detected constant rate is a second phase with its own pacing and measurements; the setting `frame_rate: canvas | source` exists from the start with `source` disabled until then.
   - **Audio: the source's sound before the fader and mute, after its filters**, taken from the tail of the source's chain (the source node when its chain is empty), the same read-only tap ADR-0095 decision 4 defines for the ducker's key, so no new graph tap is needed (the named tap ADR-0082 decision 7 asked for) (default; gate and noise filters apply, a muted strip still records, because muting on air must not remove it from the edit), or *Raw* (`raw`: the source node's output, before the filters), per track. Format: the audio graph's, as float, encoded as PCM or FLAC (ADR-0085) in `Wav`/`Flac`; a lossy codec is allowed.
4. **Quality settings.** The ISO video encoder settings are a section of the output profile (`recording.iso.video`, ADR-0051): either *Match the master* (the master's codec and a bit rate scaled by the pixel rate so the quality per pixel is the same; the default) or a full `VideoSettings` of their own. Audio likewise. Container: the master's by default, or any container valid for the codec (ADR-0085). The profile also holds the defaults of the per-source options of decision 2 (`recording.iso.defaults`: `exclude_filters = false`, `size = "native"`, `max_height` unset, `frame_rate = "canvas"`, `raw = false`); a source's own value wins. All of it is user-visible and saved; nothing is hard-coded.
5. **One start, one clock, honest offsets.** When Record is pressed, the studio (a) checks the cost and limits (ADR-0087) and shows the warning if needed, (b) opens **every** encoder, muxer and file first and reports every failure before anything is written (by default one failure aborts the whole start; the user may choose *continue without failed tracks*, recorded in the report), and (c) fixes a common start time `t0` on the master clock a few ticks ahead (never more than 300 ms), asks the master's video encoder for a keyframe at `t0` (so a shared encoder joins there, ADR-0047) and starts every track at the first tick at or after `t0`. **No synthetic padding and no timestamp origin override:** the muxers keep their rule that media time 0 is the file's earliest sample, with no edit list (fMP4 sign-off, P15; an edit list is read as AAC priming by FFmpeg), so the muxer crates are not changed by this ADR. Each file therefore starts at its own first sample, within about one frame (video) or one block (audio) of `t0`, and the **manifest records each file's exact start offset from `t0` in nanoseconds** (`start_offset_ns`); the editor project (ADR-0089) places every clip at that offset, so a project is sample-exact. A user who drags raw files into an editor by hand sees offsets of a few milliseconds up to about a frame; the manifest and the project are the exact path, which the UI says. Timestamps in every file come from the same master clock (ADR-0004); audio sync offsets (ADR-0062) apply as in the master. All tracks end at the same end time (ADR-0045 tail rules per chain).
6. **Manifest.** Next to the files the recording writes `recording.rbs.toml` (the recording manifest, a TOML document with `format` and `kind`, written atomically like other documents, ADR-0051; it is specified once, in `recording.md`, and ADR-0089 and ADR-0092 add fields to it; it is also written for plain recordings): `t0` as wall-clock UTC and master nanoseconds, each file's role (master, video, audio), source name and id, codec, size, frame rate, `first_real_ns`, `start_offset_ns`, end time, counters for dropped frames and gaps, whether filters were excluded, and for video tracks each source size change (time from `t0` and the new size, decision 3). It is written when the recording starts, rewritten at stop, and contains no secret and no absolute path. ADR-0089 builds the editor project from it; users and scripts can read it.
7. **Files.** One folder per recording, named by the profile's file name template; inside, `master.<ext>` and one file per track named after the source, made safe for the file system; names that collide after that get a numeric suffix; a source without a usable name uses `source-<id>`. Existing files are never overwritten.
8. **Sources that are not on air.** A source with a track is kept Active for the whole recording even when no program scene shows it (the binder's active set gains "ISO-recorded sources"), so a scene switch never interrupts a track. This is a cost (a camera nobody sees keeps running) and is part of the estimate (ADR-0087). When no recording runs, the flag costs nothing.
9. **Isolation and priority: the master first.** Partitions today are a fixed set (ADR-0047, ADR-0093: two output slots per canvas, `MAX_OUTPUTS = 4`). ISO needs more, so this ADR amends ADR-0026/0027/0047 in one place: the ISO set draws its partitions from a separate pool, with a bounded number of encode workers (default 2, a setting; each runs its tracks' nodes serially, so a slow software encoder can delay sibling ISO tracks but never the master, whose partitions are not in the pool) and one output worker for all the files. The source-to-export input path has two cases, specified in `io-nodes.md`. (a) **Filter tail** (the default when the source has filters): the tail publishes a pooled `Rgba16Float` texture, linear BT.709, premultiplied (ADR-0062 decision 4), which is exactly the input the existing converter and `YuvDownload` take, so the track uses `VideoExportNode` unchanged, with its own converter instance and its own set of download buffers. (b) **Source output** (*Exclude filters*, or a source with no filters): the source node has already uploaded and decoded its frame (`SourceUpload` and the importer run inside the source node, `gpu-compositor.md`), so its output is a pool texture in one of two forms. A frame decoded from YUV (`Nv12`, `P010`) is already in the canvas format (`Rgba16Float`, linear) and goes straight to the converter as in (a). An 8-bit RGB frame (`Bgra8`, `Rgba8`, sRGB) first runs a **normalisation pass**: the compositor's own source-sampling shader, with its sRGB decode, draws it into a pooled canvas-format texture (the same conversion that puts the source on the canvas, so colours match the master), and the track then continues as in (a). Nothing is uploaded a second time. The normalisation pass, its texture, the scaling pass (`max_height` or `size: master`) and the download buffers are counted per track in the estimate (ADR-0087). All ISO exports run on the render thread after the master's, so their GPU and readback time is part of the render tick: the skip rule uses the previous tick's measured time (skip when it exceeded a share of the budget, a setting), because a late check after recording the work would limit only later ticks; measured N-track tick cost is part of step 3 below, and a separate GPU queue or partition is the alternative if the numbers demand it. In the render partition the ISO export nodes run after the master's export; if a tick is already late, the ISO exports of that tick are skipped, counted, and the manifest records the gap, rather than delaying the master (this is a lateness check inside the ISO export node, not a feature-enabled check, rule 10). A track whose encoder or disk fails ends its own file cleanly and is reported; the master and the other tracks continue (P7, ADR-0055). Timestamps stay truthful: a gap is a gap, a file never drifts.
10. **Changes during the recording.** The set of tracks is fixed at start. Flagging a source later does not add a track (the UI says "applies to the next recording"). Removing a source with a running track ends that track cleanly at that moment (valid file, manifest `ended_at`).
11. **Control API and UI.** Methods (next free minor version): `source.set_record_separately {source, enabled: bool, exclude_filters?, size?, max_height?, frame_rate?, raw?}` (a source setting, one undo step; the fields are those of decision 2; the call is a patch like `filter.set_settings`: an absent field keeps the source's current value, `null` resets it to the profile default, and a field of the other media kind is refused with `invalid_params`), `record.estimate {profile}` (ADR-0087), `record.start` accepts `iso: bool?` (default: the profile's setting; with `canvas: "all"` the ISO set goes with the main canvas's recording only, decision 1), `record.status` carries a `tracks` list (file, role, source id, size, bytes, dropped, state). UI (all visual parts need the owner's proposal and screenshots first, rules 15 and 16): the Source settings window and Properties get a *Record separately* row with a live cost hint; Settings › Recording gets a *Separate files* card (enable, quality mode, container, default video size, frame rate, audio tap, folder layout); the per-track *Exclude filters*, *Size* and *Raw* options sit with the *Record separately* row; pressing Record shows the ADR-0087 warning when it applies; Live controls shows per-track state while recording.
12. **Order of work.** (1) Spec updates, the manifest and the start rule (no muxer change); (2) audio tracks (cheapest: no GPU); (3) video tracks (filter tail and normalisation pass, `native` and `master` size, canvas frame rate, system-memory export); (4) native-surface hand-off to hardware encoders per ADR-0025 to remove the readback; (5) `frame_rate: source`. Each step has before/after measurements of the master's frame times and CPU/GPU with 0, 1, 2 and 4 tracks, on the Windows RTX 4090 machine and the M4 Pro Mac.
13. **Zero cost (P13).** No flag set, or no ISO recording running: no node, no partition worker, no file, no pooled buffers, no polling. The flag itself is a field.

## Consequences

- Editors get each source as its own file (with or without its filters, at its own size or the master's) with a project aligned at zero, and RBS can do what OBS cannot without a re-render per source.
- The cost is real and grows with the track count: each video track is a conversion, an export and an encoder session. ADR-0087 makes the user see this before pressing Record, and the first-version ceilings are conservative and measured.
- The master recording is protected by design, but under extreme load ISO tracks drop frames first, visibly.
- Kept-active hidden sources raise CPU/GPU for sources nobody sees on air; the estimate includes them.
- A scene-format change appears (optional field, format 16, written only when a file contains the flag), which needs the usual compatibility notes; the plugin SDK is not affected.
- Spec follow-ups: `recording.md`, `io-nodes.md` (ISO export, the normalisation pass, the fixed track size and the shared start), `scene-model.md`, `user-data.md`, `control-api.md`, `ui-design-system.md`, glossary ("Separate files", "Track").

## Alternatives considered

- **Raise `MAX_OUTPUTS` and treat each track as an output.** Reuses code but mixes record/stream limits with track limits, and gives every track its own partitions and threads.
- **Re-render each source through a second compositor.** Simple conceptually, expensive: a full render per track; the tap needs no render.
- **Record raw frames and encode after the take.** Lowest live CPU but enormous disk traffic (4K60 raw is gigabytes per second) and a long wait; not viable as the default.
- **Record only the composited master plus audio tracks (the OBS way).** Cheap, and still possible (one mixed track in the master file, ADR-0085); it does not give the editor the sources.
- **Audio tracks inside the master file** (one extra audio stream per source) instead of separate audio files, for editors that prefer one file. Closed by the owner (2026-11-13): not part of this ADR; the first version writes separate audio files only. The muxers can carry several audio streams (`StreamIndex`) and nothing here rules that layout out; it would need its own settings, tests and a later ADR.
- **Per-output-profile list of sources.** Profiles hold no scenes (ADR-0051), so the list would hold ids that mean nothing in another collection.
