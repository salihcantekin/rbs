# ADR-0165: Show mouse and keyboard input on the picture

- Status: Accepted (2026-11-21; phase 1 mouse only, keys later on the same port)
- Date: 2026-11-21
- Deciders: Salih (owner)
- Builds on: ADR-0013 (zero cost when unused), ADR-0023 (parameter channels), ADR-0060 (shortcuts), ADR-0129 (text source), ADR-0141 (OS permissions), ADR-0158 (diagnostics log), ADR-0162 (extension-ready registries)
- Touches when built: a new port (`rbs-input`), new adapters in `rbs-platform`'s list (ADR-0160), the video filter contract, the plugin SDK permissions, the Permissions page

## Context

Tutorial and demo videos need the viewer to see what the presenter does with the mouse and the keyboard: a ring on each click (left and right told apart), a halo that follows the pointer, and the keys pressed (`Ctrl+Shift+S`). The owner asked for the infrastructure analysis on 2026-11-21. Today RBS can only ask the OS to draw the cursor into a display or window capture (`CaptureRequest::cursor`, `capture.cursor`); it knows nothing about clicks or keys.

How OBS users do it today: the cursor comes from the capture as in RBS. Clicks and keys come from a third-party plugin (most often *Input Overlay*, which uses the `libuiohook` global hook library and draws a configured texture atlas, with an optional network mode for input from another PC), from Lua scripts that poll the cursor through FFI (zoom-to-mouse scripts), or from separate desktop tools that draw on the screen itself (PowerToys Mouse Highlighter, KeyCastr, Carnac), which the display capture then films. The weak points: an effect drawn on the screen also shows in every other capture and on the presenter's own screen; plugin hooks run for the whole session even when no overlay is on air; there is no sync between an event's time and the captured frame, so rings appear a frame or two ahead of the captured cursor; mapping breaks with mixed DPI, cropped or moved windows; and keystroke tools show passwords as readily as shortcuts.

### Mapping a point to the captured picture

Events arrive in desktop coordinates; effects are drawn in the captured picture's pixels.

- **Displays.** Windows (per-monitor DPI aware process): physical pixels in the virtual desktop, which can be negative left of or above the primary monitor; subtract the monitor rectangle (`GetMonitorInfoW`) of the captured `HMONITOR`. macOS: points in the global Quartz space (top-left of the main display); subtract `CGDisplayBounds` of the captured display and multiply by its pixels per point (`DisplayScale` already reads it). Mixed scales across monitors are handled because each display has its own origin and scale.
- **Windows (captured windows).** The window moves and resizes. Windows: WGC captures the DWM extended frame bounds (`DWMWA_EXTENDED_FRAME_BOUNDS`), read again on `EVENT_OBJECT_LOCATIONCHANGE` for that window (a `SetWinEventHook` owned by the WGC adapter that exists only while a mapping is requested), not per event. macOS: the window's global frame comes from the `CGWindowList` bounds, read by the ScreenCaptureKit adapter's watcher thread (the existing `rbs-sck-cursor` watcher, 50 ms poll, generalised); ScreenCaptureKit's per-frame `contentRect`, `contentScale` and `scaleFactor` (`SCStreamFrameInfo`, already read in `mac.rs`) only place the content inside the output buffer (offset and fit scaling), so they are combined with that frame. The mapping is exact only up to the refresh time of the window frame. Effects show only while the point is inside the window and the window is not covered at that point: on macOS the `rbs-sck-cursor` test, on Windows `WindowFromPoint` plus `GetAncestor(GA_ROOT)`. Both run in the capture adapter, on its own thread, and the result travels in the mapping (decision 5); the input adapter only delivers points (P1), and no window-server query runs on the macOS tap's run loop.
- **Crop, scale, rotation, scene placement.** If the effects are drawn into the source's own picture before the compositor, the item's crop and transform apply to them for free. If they are drawn as a separate layer, the layer must copy the item's transform and crop exactly, also while the item is dragged or animated.
- **Time.** Capture frames arrive one or two frames after the OS composed them, and both capture adapters deliver only changed frames (WGC sends nothing on a still screen; ScreenCaptureKit drops idle frames). Events carry a timestamp read when they arrive (QPC on Windows, since `GetMessageTime` has millisecond resolution; `CGEventGetTimestamp` on macOS), and brought to the engine clock by the monitor's own `EdgeClock` over the same OS clock the capture adapters use (QPC on Windows, mach time for both CoreGraphics and ScreenCaptureKit); `EdgeClock` is a per-session estimator and is not shared across threads. `EdgeClock` lives in `rbs-capture/src/edge.rs` today; it moves to `rbs-core::timing` (re-exported from `rbs-capture`, no behaviour change) so `rbs-input` does not depend on another port crate. An effect starts once its event time is at or before the capture time of the newest frame, or, when no new frame has come for about one frame interval, at render time; it then animates on render time (`ctx.tick().time`). So a ring neither runs ahead of the captured cursor nor waits for the screen to change.

### Where the feature fits (ADR-0162, rule 19)

Three shapes were analysed:

- **A. Filter on display and window capture** (`org.rbs.filter.pointer`). The effects are drawn in source pixels, so crop, transform and every scene that shows the source are right with no extra mapping. But the filter contract is pure today (`FilterType::uniforms` runs only when values or size change and gets no outside data), and a filter writes a new full-size texture: a 4K halo costs a full-frame pass on every frame it is visible.
- **B. Separate sources** placed above the capture (`org.rbs.input.pointer`, `org.rbs.input.keys`). Keys fit a source well: they have their own position and style, like a text source. Pointer effects as a source must follow another item's transform and crop, which is a new cross-item binding and breaks when the user moves one of the two.
- **C. A compositor decoration of the layer.** Cheapest on the GPU (small quads drawn right after the layer, with its transform and crop as scissor), but it adds per-layer work in `Compositor::render`, a hot path, for one feature, and it is not something a plugin could add.

## Decision (proposed)

0. **Scope and phases (owner, 2026-11-21).** Phase 1 is the mouse only, on Windows and macOS: the input port with its pointer, button and wheel events, the adapters for them, the capture mapping and the pointer filters (decisions 1, 2, 3, 5, 8). Linux is not in phase 1: Wayland has no global input (decision 5), and X11 capture also goes through the PipeWire portal, which would need its own mapping producer and a `CLOCK_MONOTONIC` read per XInput2 event; that is a later phase with its own review. The port is designed for keys from the start (decision 1), but phase 1 builds no key adapter code, no keys source, no key permission and no key privacy UI. Phase 2, keys (decisions 4, 6 for keys, 7), needs the owner's go-ahead and its own review of the parts it adds.

1. **One input port, one shared monitor.** A new port crate `rbs-input` defines `InputMonitor` (open a subscription with an event mask: pointer, buttons, wheel, keys) and lock-free delivery per subscription: a single-producer ring of timestamped discrete events (button down and up, wheel), which drops the newest event and counts it when full, and a small timestamped history of pointer positions (the last 64 samples, about 64 ms at 1000 Hz, enough to cover capture latency; each slot carries a sequence number written before and after the sample, so a reader that sees the two differ reads the slot again and never uses a torn sample), so a reader can ask where the pointer was at a frame's capture time; moves at 1000 Hz never go into the event ring. Adapters: `rbs-input-win` (Raw Input with `RIDEV_INPUTSINK` on a message-only window thread that runs per-monitor DPI aware v2; no low-level hooks), `rbs-input-mac` (listen-only `CGEventTap` on its own run-loop thread, re-enabled when the system disables it). Linux later (`rbs-input-x11`, XInput2; decision 0). Capabilities: `input.pointer`, `input.buttons`, `input.wheel`; phase 2 adds `input.keys`, `input.secure_input` (the OS hides password input) and `input.permission.keys`. The event type and the subscription mask are `#[non_exhaustive]` and name keys from phase 1, so adding them is a minor change; until then a subscription that asks for keys gets `Unsupported`. On macOS, phase 1 taps mouse events only; if hardware shows that a mouse-only listen-only tap is gated by Input Monitoring, the Permissions row of decision 7 moves into phase 1. Adapters register in `rbs-platform`'s list (ADR-0160). Engine code checks capabilities, never the OS (P3).

2. **Zero cost when off (P13).** Installed: no thread, no hook, no tap, no window. The monitor thread starts when the first Active consumer subscribes and stops (hook removed, thread joined) when the last one leaves; it asks only for the event classes some consumer needs (no key events unless a keys overlay is Active). The subscription opens and closes on the consuming node's Active edge (ADR-0013 lifecycle) in `prepare` and `release`, or a host call on the control thread, never in `warm`, `cool` or `process`, which run on the executor thread, because subscribing can start a thread; on the same edge the host turns the source's mapping switch on or off (decision 5), so the WGC `SetWinEventHook` and the window-frame watchers run only while a pointer filter is Active. While Active the filter holds its pooled canvas textures (memory is kept, not trimmed), so the first click never allocates on the render thread. Standby items (not in preview or on air) hold no subscription.

3. **Pointer effects are video filters on display and window capture (shape A), with a filter contract extension.** Two filter types, so each fits `rbs_filters::MAX_FIELDS` (8) and the settings stay short, all as `rbs-params` schemas:
   - `org.rbs.filter.click-rings`: a ring on each click (7 fields). Colour for the left, right and middle button; **ring size** (the ring's line width); **ring radius** (how far the ring grows from the click point); **duration** (how long the ring stays on screen before it has faded out); which buttons show a ring.
   - `org.rbs.filter.pointer-halo`: a circle that follows the pointer (5 fields). **Size** (radius) and **colour** of the circle; optional dimming outside a spotlight (on or off, amount, spotlight radius).

   Size, radius and colour of both circles and the click duration are user settings, as the owner asked (2026-11-21). Sizes are in pixels of the captured picture, so a circle keeps its size relative to the captured content when the item is scaled. Ranges, defaults and units are set in the `rbs-params` schemas with the UI proposal (rule 16).

   The filter contract gains a declared host service: a filter type may declare `needs: pointer` and then receives, per frame, a read-only view of the pointer history and button events (decision 1) and the source's mapping (decision 5). Live effects (at most 16) go into a small per-frame buffer at bind group 2, reserved when the node becomes Active, not into the 15 type-owned `Uniforms` entries; the type's own full-screen fragment shader samples the input and loops over the live effects, so it stays one pipeline and one draw per pass, as filters are today, with no second blended pipeline. "An effect is alive" joins the inputs of `FilterNode::process`'s early return (today it returns when the input frame and values are unchanged), so a ring animates on a still screen. When no effect is alive the filter passes the input through with `VideoFrame::share`, in a branch of its own (the colour-correction `identity_skip` gate needs a linear canvas input and does not apply to capture frames), with no pass; the branch `touch`es the node's pool descriptions, as `identity_skip` does, so `TexturePool::trim_idle` keeps them. When one is alive it draws its pass into its pooled canvas output, as every filter does today (sRGB decode included); a copy is not possible (capture frames are `Bgra8` sRGB, filter outputs are `Rgba16Float` without `COPY_DST`) and frames are lent and shared, so drawing on them in place is not allowed. The published format therefore switches between the capture's `Bgra8` sRGB (idle) and linear `Rgba16Float` (drawing); this is allowed, because downstream nodes rewrite their uniforms on a decode change (the compositor reads `source_transfer` every frame). It contradicts `video-filters.md` items 4 and 6 and `conformance.rs` check 4 (every output linear `Rgba16Float`, never the input, except identity colour correction), so the spec and the conformance suite gain an exception for types that declare `needs: pointer`, with a test of the format switch. The exception also allows one effect-buffer `write_buffer` per drawn frame (`video-filters.md` step 3 allows one only when values, size or decode change), covered by conformance check 7 (bounded allocations per frame). After the last effect dies the filter renders one more pass-through frame, so the final ring does not stay on a still screen. The pointer filters must come before any filter that moves pixels in the chain (crop, transform-like filters); the chain editor keeps every type that declares `needs: pointer` first, from that declared property, never from a match on type ids (rule 19). This is a change to `FilterType` and to `FilterNode::process` (hot path, P15) and to the plugin SDK, each with its own review. The host enforces the subscription mask from the type's granted permissions, so a filter granted `input.pointer` never receives key events, whatever it asks for. `plugin-sdk.md` gains a "Host services" section listing `input.pointer` and reserving `input.keys` as a separate permission (ADR-0162 decision 8(d)). Sandbox filters are data-only (ADR-0162 decision 2a); for them the host would evaluate a manifest-declared mapping from the pointer view to uniforms, which is not in phase 1.

4. **Phase 2: keys are a source (shape B).** `org.rbs.input.keys` (extends `SourceClass` until the source registry exists, ADR-0162 decision 8a), drawn through the text port like the text source (ADR-0129): a new picture only when the shown keys change, one atomic load per frame otherwise. Settings (schema): **Shortcuts only** (default: keys with Ctrl, Alt, Win/Cmd, plus function, arrow and editing keys) or **All keys**, how long a combination stays, how many lines, grouping of repeats (`Ctrl+Z ×3`), mouse buttons shown as keys, and style. A mouse-diagram source and zoom-to-pointer can use the same port later; out of scope here.

5. **Mapping is made by the capture adapter and lent by the source node.** The capture port gains an optional "desktop to picture" mapping (origin, scale, and for windows the window frame, the buffer placement and the covered test), produced by the adapter that knows it (WGC: monitor rectangle, extended frame bounds; ScreenCaptureKit: display bounds or the `CGWindowList` window frame combined with the frame's `contentRect` and scale). The request opts in through a shared switch: `CaptureRequest::with_mapping(MappingSwitch)`, minor and non-breaking in `capture-port.md`. `MappingSwitch` (in `rbs-capture`) is an atomic flag plus a callback the adapter registers when the session starts; the host's source entry owns it (created once per entry with the mapping cell; `InstanceContext` carries both to the source builder, and `rbs-sources` `registry.rs` passes the switch into `CaptureRequest::with_mapping`, so a rebuilt instance keeps them) and sets it on the control thread to "any pointer filter of this source is scheduled", not per filter edge, so a second pointer filter leaving does not turn it off; the callback starts or stops the adapter's mapping thread there. Registering the callback applies the current state under the switch's own lock (control path only, never on a real-time thread); `register` returns a guard owned by the session that unregisters on `stop` or drop, and the switch holds no strong reference to adapter state. A test flips the switch while a session opens on the node's own thread. A running session is not restarted (a restart would re-pick windows), `reconfigure` is not used, and nothing reaches the executor thread. Off by default, so an adapter does none of this work unless a pointer filter is Active (P13). The mapping thread runs per-monitor DPI aware v2 on Windows (`SetThreadDpiAwarenessContext`), the same as the Raw Input thread, so both coordinate sets match; a display's monitor rectangle is read under the adapter's existing scoped per-monitor v2 context or on the mapping thread. The covered test answers for the pointer position at the thread's last poll, not for each click: on macOS the existing 50 ms poll; on Windows the same 50 ms poll of `GetCursorPos` with the same still-pointer skip, plus `EVENT_OBJECT_LOCATIONCHANGE` and `EVENT_SYSTEM_FOREGROUND` for the target window. The thread exists only while the switch is on. `CaptureSession` gains `latest_mapping()`, default `None`, filled in the same hand-off as `latest_frame` and tagged with that frame's timestamp, so a reader can tell when the two do not match. It is real-time like `latest_frame` (no allocation, no lock, no wait). `hot-paths.md` adds it to the capture hand-off row and gains an `rbs-input` row (event ring, pointer history, the filter's read of both); `EdgeClock` in `rbs-core/src/timing.rs` is already covered by the clock row. `VideoFrame` does not change: the capture source node publishes the mapping of its newest frame into a lock-free cell (one writer, readers never wait) that the host lends to the pointer filters of that source's own chain, as part of the decision 3 host service. The cell's `Arc` belongs to the host's source entry, not to the node instance, so a reopened capture node does not leave filters reading a dead cell. Two contract changes, each with its own review (P14): the capture port's mapping, and the host service. Wayland is out of phase 1: a halo there needs metadata cursor mode, chosen at portal session start when a pointer filter is on the source, RBS drawing the cursor bitmap itself, and possibly a new pick of the source; the filters are not offered on Wayland and the filter list says, in one sentence, that Wayland does not let apps see clicks.

6. **Privacy rules.** Phase 1 has the pause shortcut, the never-leaves-the-engine rule and the window rule; the key rules arrive with phase 2.
   - Keys default to **Shortcuts only**; **All keys** is opt-in with one warning sentence.
   - Where the OS has secure input (`input.secure_input`, macOS), the overlay shows nothing while it is on. On Windows, the keys adapter asks UI Automation, on a focus-change event on its own thread, whether the focused element is a password field (`UIA_IsPasswordPropertyId`) and suppresses keys while it is; this is best effort and the Settings text says so. X11 has neither, and the Linux settings say so.
   - A global shortcut command `input.overlay.pause` (ADR-0060) hides all input effects at once; the studio shows that they are paused.
   - Keys and pointer events never leave the engine: never logged (ADR-0158; only counts and faults), never sent through the control API, MCP or recording metadata. The overlay's text is not readable through the API.
   - Window captures show effects only while the pointer is over the uncovered target window; a keys source can be limited to "only while the captured window has focus" (default on when linked to a window capture).
   - Optional later: a list of apps that hide the overlay while focused (password managers).

7. **Permissions (phase 2, see decision 1 for macOS).** ADR-0141 gains a fifth kind, **Input monitoring** (macOS Input Monitoring; "No permission needed" on Windows and X11; "Not available" on Wayland), asked at the moment the first keys overlay is added (ADR-0141 decision 4). `Info.plist` needs no new usage key for Input Monitoring; the prompt is the system's own.

8. **Measurements before merge (P15).** Before/after numbers for `FilterNode::process` with the filter present and idle, present and drawing, and absent; at 4K, the copy plus quads against today's pass-through; a ring on a still screen (forced redraws); `CaptureSourceNode::process` with and without the mapping publish (`bench capture`, including `no_frame`); the monitor thread's CPU at 1000 Hz mouse polling; and the end-to-end delay from a click to the ring, with the check that event and frame times are in one clock domain. On the Mac and on SC-PC.

## Consequences

- Built in, timestamp-aligned and zero cost when off, which OBS plugins and desktop tools are not; effects appear only in RBS's picture, not on the presenter's screen.
- `EdgeClock` moves to `rbs-core::timing`.
- Four contract changes, each with its own independent review: the new input port, the filter contract's host-service extension (hot path), the capture port's mapping, and the plugin SDK's host services and permission names. `VideoFrame` stays unchanged.
- Linux (Wayland and X11) gets nothing in phase 1; Windows elevated windows and secure desktops show nothing. The UI states both.
- The keys overlay is a privacy risk by nature; the defaults above keep the risk low but cannot remove it on Windows and X11.
- The visible parts (filter settings, keys source look, Permissions row) need a proposal and dark and light screenshots before implementation (rule 16).

## Alternatives considered

- **Linux X11 in phase 1.** XInput2 needs no permission, but the portal capture has no mapping producer and X server times are not the frames' `CLOCK_MONOTONIC`; deferred to a later phase.
- **Low-level hooks (`WH_*_LL`) on Windows, or `libuiohook` on all OSes.** One code path, used by OBS's Input Overlay, but a hook slows everyone's input when the reader stalls, is removed silently after timeouts, and looks like a keylogger to security software. Raw Input does the same job from our own message queue.
- **Separate pointer source that copies the capture item's transform (B for pointer).** Cheaper per frame than a filter, but a cross-item binding that breaks when the user moves or crops one of the two, and it must be repeated in every scene that uses the capture.
- **Compositor layer decoration (C).** Cheapest GPU cost, but per-layer work in `Compositor::render` for one feature and not reachable by a plugin (rule 19).
- **Draw effects on the real screen (as PowerToys does).** Simple, but the presenter sees them too, every capture shows them, and RBS would own a top-most transparent window per monitor.
- **Read input from the browser source or a companion app.** Only sees input inside that app.
