# ADR-0170: Multi-track recording and six buses

- Status: Accepted
- Date: 2026-11-22
- Deciders: Salih (owner)
- Spec: [audio-graph](../specs/audio-graph.md), [recording](../specs/recording.md), [scene-model](../specs/scene-model.md), [user-data](../specs/user-data.md), [control-api](../specs/control-api.md)
- Amends: [ADR-0097](0097-audio-monitoring-and-buses.md) decisions 9 (`MAX_BUSES`), 10 (when a bus pin is linked) and 11 (multi-track containers)
- Builds on: [ADR-0047](0047-several-outputs-per-canvas.md), [ADR-0051](0051-user-data-profiles-and-scene-collections.md), [ADR-0013](0013-zero-cost-when-unused.md), [ADR-0162](0162-extension-ready-registries-and-plugin-order.md); [ADR-0127](0127-multistreaming-to-several-destinations.md); aligns with ADR-0169 (the audio branch rests while nothing reads it; Proposed on its branch when this was written)

## Context

ADR-0097 accepted buses (part 2, "F2"): named mixes on the main canvas with per-source send levels, a fader, mute and a filter chain each, and an output that picks one bus. F2 is not built yet (status.md: "Buses ... are not built"). Two things stop it from covering what people coming from OBS expect:

- **Multi-track recording.** OBS records up to six audio tracks into one file (for example track 1 the full mix, track 2 the microphone alone, track 3 the game) so an editor can rebalance later. ADR-0097 decision 11 left "multi-track containers (one bus per track)" for a later change.
- **Bus count.** ADR-0097 decision 9 caps buses at 4. Six tracks of separate mixes need six buses.

The mixer work and the scene model of F2 are unchanged by this ADR; it only adds what a multi-track recording needs on top.

## Decision

1. **Six buses, cost only when linked.** `MAX_BUSES` is 6, `main` included (amends ADR-0097 decision 9, which called the cap "a fixed per-block cost" and reasoned from a two-output cap that ADR-0127 has since lifted). The mixer keeps a list of *linked* bus pins and its per-strip block loop walks only that list, never `0..MAX_BUSES`; the cap only bounds the fixed-capacity ramp state per (producer, bus) (ADR-0097 review round 3 note 1). The F2 mixer bench (rule 12) has rows for `main` only, six buses declared and unlinked, `main` plus one linked bus, and six linked buses; "six unlinked equals `main` only" within noise is a pass condition.
2. **When a bus pin is linked** (amends ADR-0097 decision 10, stricter): only while a running output, a running track, the monitor or that bus's meter sink (below, while the branch is awake) reads it. A non-zero send alone links nothing. Aligned with ADR-0169 (the audio branch rests while nothing reads it): every reader of a bus pin is a graph output (a track or stream encoder chain ending in its output node, or the monitor), so it keeps the audio branch awake by itself with no flag or list of reader kinds; tracks and bus links are added and removed through the normal apply, sent like every studio graph through `Studio::send_graph`. The rule does not depend on ADR-0169: without it, a bus pin is still linked only by the chain or monitor that reads it. Bus meters in the Mixer: each bus with at least one non-zero send has a meter sink on its pin in the studio's model, handled exactly like the `main` sink (ADR-0169 decisions 1, 2 and 7): `send_graph` removes it from the engine's graph while the branch rests and `set_audio_awake(true)` brings it back, so a meters toggle applies nothing and the grace holds; adding the first send to a bus or removing its last goes through the normal apply. A bus without sends shows an idle meter. This replaces ADR-0097's "live while it has a send" and goes through the stage (d) UI proposal.
3. **A recording writes tracks.** A recording output stores `audio_tracks`: an ordered list of 1 to 6 distinct bus *names*, default `["main"]`; track 1 is the first entry. A stream output keeps one bus name, `audio_bus`, default `"main"`; destinations with their own encoding (ADR-0127) use the stream's `audio_bus` (a per-destination bus is a later change). RTMP/FLV carries one audio stream; multi-track streaming (enhanced RTMP, SRT) is a later ADR. Names, not ids, as in ADR-0097 decision 11.
4. **A multi-track recording owns one audio chain.** The tracks of one recording are one audio encoder chain (one `MAX_CHAINS` slot, one `NoEncoderSlot` check, one partition from `Partitions::audio_encoder_of(chain)`) holding one encoder per track, each fed from its bus pin, all with the output's one `AudioSettings`. So six tracks add no chain slot and no worker thread beyond today's one, and ADR-0127's limits are unchanged. Sharing (ADR-0047 decision 3) is unchanged for one-track outputs (key: settings plus bus); a chain with more than one track is never shared and never joins another output's chain.
5. **Sample-exact alignment.** The encoders of one chain start on the same audio block, are cut on the same block at pause and resume (sample-exact, as an owned encoder is today, ADR-0124) and stop together, so their packet grids are identical. The aligned start (`Progress::start_drops`) drops the same packets on every track: the output node's start hold (`START_HOLD` in `rbs-nodes` `output.rs`, one FIFO for all streams today) becomes one preallocated hold per stream, all built in the start path (none for the video stream), so `process` only pushes and pops preallocated rings and six tracks keep the same lead time as one. The holds drain merged by timestamp, ties broken by stream index, both when video arrives and in the flush when no video comes (the same merged order in both), and the abort path counts every hold in `finish_lost`, so the muxer sees today's interleaving. When any audio hold overflows, every audio hold of the chain drops its packets at or before that packet's timestamp, so drops stay equal by rule, not only because tracks arrive in step. `Progress::start_drops` keeps counting track 1 (and video) as today; each track's count is in `tracks`. A test with late video asserts equal per-track drops. This touches `output.rs` `process`, a hot path: staging (c) includes the hot-path review and before/after output-tick numbers. The required test asserts the same first-sample time and the same packet timestamps on every track, sample-exact, also after a pause.
6. **Mux contract (additive).** `StreamDescriptor` (rbs-core) gains `name: Option<String>` and `default: bool` (it is `#[non_exhaustive]`; additive, minor bump noted in `output-ports.md`). Matroska (`rbs-mux-matroska`) writes `Name` and `FlagDefault` (1 on track 1 only; it is omitted today, so every track counts as default). MP4 and MOV (`rbs-mux-fmp4`) write the name in both `hdlr` name and `udta`/`name` (editors that ignore `udta` read `hdlr`), put every audio track in `alternate_group` 1 and set the `tkhd` enabled flag on track 1 only, so players do not play all tracks at once. MPEG-TS carries no track name (only the ISO 639 descriptor); names are dropped there. A conformance case "several audio streams" in `rbs-mux` `conformance.rs` comes first, then ffprobe interop tests per container.
7. **How many tracks a format takes is a capability** (P3, ADR-0162): muxers declare `mux.audio_streams` (Int) beside `mux.codecs` in `rbs-mux/src/caps.rs`; a muxer that does not declare it (FLAC, WAV, FLV, a plugin muxer) takes 1. A recording with more tracks than its muxer declares is refused at start and in the API (`RecordError::TracksUnsupported { allowed }`, control-api error code `tracks_unsupported`, added to control-api.md with decision 11's API change), and the UI's track picker offers only that many. No list of format names is kept.
8. **Stream numbering.** With video, video is `s0` and track *n* is `s<n>`; without video, track *n* is `s<n-1>` (recording.md: audio alone starts at `s0`).
9. **Dangling names.** ADR-0097 decision 12 applies per track and to `audio_bus`: removing a bus that the loaded profile uses is refused naming the output and track; a saved profile naming a missing bus refuses to start that output with a visible reason and a one-click fix (choose another bus or drop the track). It never falls back to `main` and never records a silent track. Renaming a bus updates every reference in the loaded profile in the same step.
10. **Vertical canvas.** A recording of a canvas with `audio_from = main` (ADR-0093 decision 5) resolves its `audio_tracks` against the main canvas's buses; its chain is fed from those pins but belongs to the vertical canvas's output, so it takes the vertical canvas's `MAX_CHAINS_PER_CANVAS` slot and partition. A canvas with its own mix (later) has no buses, so it accepts only `["main"]`.
11. **Reports, data and API.** `Progress` and `StartReport` keep their single audio fields as track 1 and gain a `tracks` list (bus name, encoder name, packet drops, queue drops, flushes, tail lost per track; `shared` stays a chain-level field, always false for more than one track); additive, noted in recording.md. The ADR-0087 estimate counts every track's encoder, and stage (c) measures six encoders against one partition's block budget on the Mac. Output profile: the recording section gains `audio_tracks`, the stream section `audio_bus`; absent means the default, so older profiles load unchanged (round-trip and loader tests decide whether `SECTION_VERSION` rises, recorded in the PR). Control API, next free minor at merge: `settings.get/set` gains optional `audio_tracks` in `recording` and `audio_bus` in `stream`; `record.status` and topic `record.state` gain the optional `tracks` list. No new `state` values (ADR-0097 decision 13). Separate per-source files ([ADR-0086](0086-recording-sources-separately-iso.md)) keep their behaviour; an audio-only recording may write tracks when its muxer allows.
12. **Zero cost when unused (P13).** A recording with `["main"]` builds exactly today's graph and chain. Buses no running output reads cost nothing per block.
13. **Plugin-ready (ADR-0162).** A bus is collection data, addressed by name in profiles and by `BusId` inside the collection; bus filter chains use the existing filter registry; a plugin output type gets bus names through the same profile fields and its track count through `mux.audio_streams`. No closed list is added.
14. **Staging.** (a) This ADR, independent review, owner approval. (b) F2 as in ADR-0097 decision 14: scene model and migration, mixer bus outputs (bench, hot-path review, owner approval), API, UI proposal. (c) Mux contract and conformance, then the multi-track chain, alignment tests, reports, estimate, API, and the six-encoder measurement. (d) UI proposal for buses and tracks (Mixer bus strips, send levels per strip, Settings › Recording "Audio tracks"), screenshots in dark and light before merge (rule 16). (e) Later: OBS import maps OBS mixer track flags and `RecTracks` to buses and `audio_tracks`.

## Consequences

- An editor gets separate microphone, game and music tracks from one recording, and the stream can still use a different mix ("no music in the VOD").
- Unlike OBS tracks, each bus has a send level per source, its own fader and its own filters (for example a limiter only on the stream mix).
- More encoders per recording cost CPU only for the tracks chosen; a one-track recording costs what it costs today.
- A multi-track recording never shares its audio encoders with the stream, so a stream and track 1 on the same bus encode twice; that is the price of sample-exact tracks.
- The mux stream descriptor gains a name and a default flag; muxers need multi-audio conformance and interop tests.

## Alternatives considered

- **OBS-style track flags without buses.** Cannot sit a source lower in one mix and gives a track no fader or filter (rejected already in ADR-0097).
- **A separate file per bus.** Loses sample alignment in editors that expect one file; per-source files already exist (ADR-0086) for that workflow.
- **Different codec settings per track.** More profile and UI surface for a rare need; one `AudioSettings` per output keeps sharing simple. Can be added later as an optional override.
- **One chain per track.** Six tracks would use six of `MAX_CHAINS` and six threads, and a track shared with the stream would be out of phase by up to one AAC frame.
- **Keep four buses.** Leaves six-track OBS setups without an equivalent; the extra two cost nothing while unlinked.
