# ADR-0062: Built-in video filters: one filter node behind a filter type trait, settings through parameter channels, and the Properties tabs

- Status: Accepted
- Date: 2026-11-07
- Deciders: Salih (owner)
- Builds on: ADR-0053 (item style and video filter chains, decisions 6 to 10), ADR-0013 (zero cost when unused), ADR-0020 (node contract and schedule swap), ADR-0023 (parameter channels), ADR-0024 (restart with back-off), ADR-0044 (control API), ADR-0051 (user data documents), ADR-0052 (API parity), ADR-0058 (source crop and `picture_size`), ADR-0059 (source audio), ADR-0061 (studio mode, protocol 1.7)
- Supersedes: the input-size clause of ADR-0053 decision 6 ("`process` must not allocate" on a size change), replaced by decision 5 here

## Context

ADR-0053 decided that video filters are a per-source chain of GPU nodes of kind `VideoFilter` in a new crate `rbs-filters`, specified in `docs/specs/video-filters.md` before any code, that a filter's settings change through its parameter channel without rebuilding its node, and that the control API gains `filter.*` methods. It left open how a filter type is defined, how a filter node learns its input's size without allocating in `process`, how the settings reach the node, and where the user edits filters.

What exists today (checked in the code on 2026-11-07, `main` at e577560):

- The scene model has `Source::filters: Vec<Filter>` (`id`, `type_id`, `enabled`, `settings`) and the edits `add_filter`, `remove_filter`, `set_filter_enabled`, `move_filter`. There is no edit for a filter's settings. The scene collection document (format 3) already saves `filters = [{ id, type, enabled, settings }]`.
- The binder creates a node for each filter whose type is installed, links the enabled ones in order between the source and every compositor, and keeps disabled ones in the graph but out of the schedule (Standby, P13). It keeps a filter's node while the filter exists; a settings change is not noticed.
- No filter node type exists, `rbs_sources::SourceTypes::node_types` installs none, and `rbs_record::Studio` makes instances only for source nodes: a filter in a collection is reported as `UnknownFilterType` and skipped.
- `rbs_gpu`'s pooled textures carry a sampled bind group for the compositor's sampled-texture layout, but both are `pub(crate)`.
- The Properties panel shows one long column: name, sound, position and size, crop, shape and border. The design the owner picked (mockup E, ADR-0049) shows a segmented control at the top of Properties with three tabs: Transform, Filters and Audio. The UI design system says a feature that grows (filter chains) gets its own panel and Properties shows a one-line summary.
- The per-source audio sync offset (ADR-0037) exists in the engine and the CLI (`--mic-offset`), but not in the scene model, so the app cannot set or save it.

Forces: P4 (no readback), P6 (no allocation, blocking or locks in `process`), P13 and rule 10 (an unused filter costs nothing; no per-frame "is it enabled" test), P15 (`process` of a built-in node is a hot path: numbers and the owner's sign-off), U4 (undo, one step per user action), ADR-0052's API parity, ADR-0051 decision 6 (a document change older builds cannot read needs a new format).

## Decision

1. **A filter type is a trait; one node runs any filter type.** `rbs-filters` defines the object-safe trait `FilterType` (spec `video-filters.md`): a type id (`org.rbs.filter.<name>`), an English display name, a static list of fields (the settings schema: key, label, kind and range or default), the passes (WGSL fragment shaders and the scale of each pass's target, full or half size) and a pure function that turns validated values and the input size into each pass's uniform block. `FilterNode` is the one `Node<GpuRuntime>` of kind `VideoFilter` (input `in`, output `out`, both video) and runs any `FilterType` given as `Arc<dyn FilterType>`. A new filter, a plugin filter or a test double implements the trait; the node, the binder and the app do not change. A conformance suite in the crate (`rbs_filters::conformance`) runs against every `FilterType` and the built-in catalogue passes it. `rbs-filters` depends on `rbs-core`, `rbs-graph`, `rbs-gpu`, `wgpu` and `bytemuck`; never on adapters or `rbs-scene` (the conversion from scene settings lives in `rbs-sources`, as `layer_style` does for item styles). Evolution: `FieldKind` and `Value` are `#[non_exhaustive]`; the trait gains methods only with default bodies (a minor change); its `&'static` schema suits built-in types and a plugin host that keeps a loaded plugin's schema alive for the process (the plugin SDK decides how).
2. **Settings are validated values, never discovered in `process`.** `FilterType::fields` is the schema the app and the control API both use. `Values::from_pairs(type, pairs)` checks every key and value against it (unknown key, wrong kind, out of range, non-finite: refused with a typed `FilterError`) and fills missing keys with their defaults. Numbers are stored as `SettingValue::Float` (or `Int`) and colours as `SettingValue::Text("#rrggbb" | "#rrggbbaa")` in the scene model, so the scene document needs no new format for filters. An edit with values the type refuses is refused before it reaches the model (ADR-0053 decision 7).
3. **Settings reach the node through its parameter channel.** The model gains `SceneCollection::set_filter_settings(source, filter, settings) -> Undo` (one undo step, through the existing source record, `audio` untouched). The binder keeps a copy of each bound filter's settings and reports a filter whose node it kept but whose settings changed in `BindReport::changed_filters: Vec<(FilterId, NodeId)>`; it never rebuilds the node for it. `rbs_record::Studio` keeps the `ParamSender<Values>` of each filter instance and sends the new values on `update`. A slider drag must not make a step per frame: while dragging, the host sends values through `Studio::preview_filter(filter, values)`, which only sends to the node, and the release commits one `set_filter_settings` (U4); the UI sends at most one value per frame of its event loop.
4. **Rendering contract.** Each filter renders into textures of its input's size: `TextureDesc::canvas(w, h)` (`Rgba16Float`, linear light, premultiplied alpha), two output textures in turn (the one published last tick stays leased in the output slot while the next is drawn; filter outputs are read only by nodes of the same render tick, never queued) and, for a two-pass type, one intermediate at the first pass's scale. It samples its input like the compositor does (sRGB-encoded inputs decoded, premultiplied kept) and publishes frames with the input's timestamp and `ColorSpace::LINEAR_BT709`. Filters that work on perceived values (colour correction, keying) un-premultiply, encode to sRGB in the shader, work there, and decode back. Pipelines, samplers and uniform buffers are made in `prepare`; textures are acquired once in `warm` and released to the pool after each publish exactly as the compositor does with its canvas ring; `process` writes the uniform buffer only when the values or the input size changed, records the passes and submits. No readback (P4). At a steady size `process` makes no allocation of its own; the wgpu calls it shares with the compositor (recording, submit) are checked as `rbs-gpu`'s `alloc_per_frame` test does: the count per frame is bounded and does not grow.
5. **An input size change re-acquires textures in `process`, once (supersedes ADR-0053 decision 6's clause).** The node keeps its warm size in a shared `FilterStats` (atomics). Its first frame of another size (a camera that switched format, a window capture that was resized, or the first frame when the size was not known at creation) acquires the textures of the new size from the pool in that `process` call and draws the frame. That is the one allocation `process` may make, at most once per size change, exactly what `CompositorNode` already does when the pool has no free canvas of its size (`TexturePool::acquire` creates on a miss), and the input is never shown unfiltered. Considered and rejected in the first draft of this ADR: going through the restart path (ADR-0024), which in the code takes the failure limit (8 ticks) plus about three control rounds (250 ms each) with the layer blank on air, reports a failure and a restart to every event consumer, and repeats once per filter of a chain; and a new graph-level re-warm request, a node contract change bigger than the problem. **Textures of the old size are given back at once:** the node marks the output it published last with `TexturePool::forget_texture(id)` (dropped when its last reader lets go, never returned to the free list) and drops its free spares with `TexturePool::forget(desc, count)` (the rest of the output ring, one per intermediate). Other users of the same description keep their textures; only if this node's spares were already evicted or trimmed does `forget` take free textures someone else released, who then creates one once, which is accepted. So a window resized every frame costs one size's textures plus at most one frame still being read, not one set per size passed through (tested with a 120-frame sweep under a chain of two filters); no separate byte budget is needed, unlike replaced capture surfaces, whose old size the capture port cannot hand back this way. **A full pool evicts:** when every slot holds a texture, `create` and `insert_external` (native import) drop the free textures of the description acquired least recently, never the one asked for and never one asked for in the current tick (so two busy descriptions cannot take turns evicting each other), before they refuse with `PoolFull`, and a description whose last texture is dropped is removed, so the pool's list of descriptions stays bounded by what it holds and `acquire` stays O(live descriptions). **An unchanged input is not filtered again:** video slots keep their last frame, so a source that delivers nothing new (a still image, a window that did not change) keeps offering the same frame; when the input texture, its time, the values and the size are those of the frame published last, `process` keeps that frame in its output slot, records nothing and marks its descriptions used (`TexturePool::touch`), so they never turn idle while the source is quiet. **The pool frees what nobody uses (P13):** `TexturePool::trim_idle(idle_ticks)`, called by `GpuRuntime::end_tick` on the render thread once per tick, advances the pool's own clock and drops the free textures of every description no one acquired or touched in the last `POOL_IDLE_TICKS` (120) calls, so a removed or disabled filter, or a size no source has any more, gives its memory back within about two seconds; descriptions in use every tick are never touched. The studio passes the source's known picture size (`picture_size`, ADR-0058) to every filter of its chain when it creates them, so adding a filter while a source runs allocates in `warm`, not on the render thread; a source whose first frame comes more than `POOL_IDLE_TICKS` after `warm` (a camera slow to start) finds those textures freed and allocates once on its first frame, which is accepted. The pool's clock counts its own `trim_idle` calls, one per tick run, not tick indices (which jump after a stall and would make everything look idle at once); `acquire` and `touch` stamp descriptions with it, so acquires in `warm`, on the executor thread between ticks, count. **Real-time exception (P6), stated here and in `gpu-compositor.md`:** creating a texture (on a size change or a pool miss) and dropping one (`forget` on a size change, eviction on a full pool, `trim_idle` when a description turns idle) go through wgpu's device tracking and its locks on the render thread. Both happen only on those events, never on a steady tick; the benchmark measures a tick that creates and a tick that drops at 1920x1080. Sending dropped textures to the control thread, as retired schedules are, was considered: it adds a channel and a per-tick check for the same rare event, and the drop cost is measured. The resize allocation, the drops and `trim_idle` are part of this change's P15 sign-off.
6. **First catalogue.** Colour correction (`org.rbs.filter.color-correction`: brightness, contrast, saturation, gamma, hue), chroma key (`org.rbs.filter.chroma-key`: key colour, similarity, smoothness, spill reduction), blur (`org.rbs.filter.blur`: radius in source pixels; a separable Gaussian whose first pass downsamples to half size and whose second pass upsamples, so a radius up to 64 pixels costs two passes) and sharpen (`org.rbs.filter.sharpen`: amount). Each is one `FilterType`, one or two full-frame passes; fusing passes is a later decision on numbers (ADR-0053 decision 8). Colour key, LUT and image mask follow (they need resources sent through the channel as shared handles); the drop shadow is an item style drawn by the compositor (ADR-0053 decision 5), not a filter.
7. **Zero cost when unused.** A source without filters has no filter node and nothing changes for it. A filter disabled before it ever ran has a node in the graph out of the schedule and no instance. A filter disabled or removed while it runs leaves the schedule: its `cool` gives back what it kept exactly as on a size change (decision 5: its last output dropped when unread, its spares at once), so its memory goes even when the compositor uses the same texture description every tick (a 1920x1080 source on a 1920x1080 canvas), and the controller keeps the instance idle (released: no pipelines, no buffers) (P13, ADR-0013). Installing `rbs-filters` registers node descriptors only; pipelines are created in `prepare` of an instance. The compositor is unchanged.
8. **The studio makes filter instances.** `SourceTypes::node_types` installs the catalogue's descriptors. `rbs_record::Studio::reconcile` treats filter nodes as it treats source nodes: an entry per created filter, an instance (`FilterNode`) in the render partition for each scheduled one, instances taken back when retired. A filter whose type the catalogue does not have stays a binder problem (`UnknownFilterType`), shown to the user, and its source is drawn without it. **Settings read from a document are read leniently:** a collection can hold values a newer or older build wrote (a key the type no longer has, a value outside a narrowed range, the wrong kind), and the model does not check filter settings. The studio converts them with `filter_values_lenient`: unknown keys ignored, numbers clamped into range, wrong kinds and non-finite numbers replaced by the default; each adjustment is reported as a problem of the studio (`FilterSettingsAdjusted { filter, key }`), shown to the user like a binder problem, and the document is left as it is until the user edits that filter. **What is shown and patched is what is on air:** the Filters tab's fields, the API's `filters[].settings` rows and the base of a `filter.set_settings` patch are the lenient `Values` the node runs, never the raw stored settings. Every settings edit validates the patched set strictly (decision 2) and writes the full set of the type's keys; on a filter with adjustments it always writes, even when the patch resends the values on air, so the first settings edit of a filter repairs its stored settings, drops keys the type does not have and clears its `FilterSettingsAdjusted` problem; a patch is refused only for what it sends. A filter whose type is unknown can be moved, enabled, disabled and removed, keeps its stored settings untouched and is not drawn; `filter.set_settings` on it is refused (`invalid_params`, unknown filter type) and the Filters tab offers only Remove for it. The sync offset (decision 10) is not read leniently: its range is part of format 4, so a document with an offset out of range is refused as a whole with the model's reason (`InvalidSyncOffset`), as an out-of-range volume is (ADR-0059); a build that widens the range writes a new format, which older builds refuse safely.
9. **Properties gets the three tabs of the design; filters are edited in its Filters tab.** The Properties panel keeps its header (icon, the name as a TextField for every source, ADR-0059, and the type) and under it shows a `SegmentedControl` with Transform, Filters and Audio for the selected source (the last tab used is remembered per window). Transform holds position and size, crop, and shape and border. Filters holds the selected source's filter chain: one row per filter (enable Checkbox with the name, move up and down, remove), an Add filter menu listing the catalogue, and the fields of the selected filter under the list, generated from `FilterType::fields` (sliders with their value for numbers, the colour picker for colours), so new filter types need no UI code. Audio holds volume and mute (ADR-0059) and the sync offset. A source without a picture has no Transform or Filters tab; one without sound no Audio tab. The UI design system's rule "a growing feature gets its own panel and Properties shows a one-line summary" gets one stated exception: filter chains are edited only in the Filters tab (one place), and move to an `rbs.filters` panel only if the tab needs more than a screen. Filters and the sync offset belong to the source, not to a scene: an edit in the Filters or Audio tab changes that source wherever it is placed, also while studio mode shows a preview scene, so the tabs show the on-air mark whenever the source can be reached from the program scene (the check decision 11 uses for the API), as U4 asks for edits to the program. Volume and mute are mirrored live controls: the Audio tab and the Mixer row (and a Stream Deck key) show and change the same value, as on a hardware desk; that is not editing in two places, there is one value. Each confirmed filter change is one undo step: adding, removing, moving, enabling or disabling a filter, each slider release or typed value, and Reset to defaults. Two filters of the same type in one chain are named with a number from the second on ("Blur", "Blur 2"), in rows, accessible names and undo labels. A slider drag that is cancelled (Escape, focus lost before release) sends the model's values to the node again, so the picture never shows values the model does not have.
10. **Sync offset joins the source's audio.** `SourceAudio` gains `sync_offset_ms: i32` in `-MAX_SYNC_OFFSET_MS..=MAX_SYNC_OFFSET_MS` (200, equal to `rbs_sources::DEFAULT_MAX_AUDIO_OFFSET`, checked by a test); positive delays the sound, negative advances it. `SourceAudio::new(volume, muted)` keeps its signature (offset 0) and `with_sync_offset` sets it; `set_source_volume` and `set_source_muted` keep the offset (tested). It follows ADR-0059 decision 2: one value per source, changed by `set_source_sync_offset` through the `SetSourceAudio` record, ignored by the binder, and, like volume, a live control the app keeps off the undo stack (an exception to U4 stated here: it is tuned by ear while live, and an undo of a layout change must not shift the sound). One source of truth per composition root: the app builds `StudioSettings::audio_offsets` from the collection when the studio starts and calls the existing `Studio::set_audio_offset` when the value changes, which sends it to the running input; the CLI keeps its flags. The audio input clamps an advance to what its latency allows (audio graph spec); the Audio tab says so in its hint. The scene collection document becomes format 4 (`sync_offset_ms` on the source when not 0; format 3 bodies load unchanged), for the reason ADR-0059 gives; the app writes the current format always, the rule ADR-0053's review kept (one rule, and older builds refuse safely).
11. **Control API 1.8.** `filter.types` (`read`) lists the catalogue with each type's fields. `source.list` and `source.changed` rows carry the source's `filters` (`id`, `type`, `enabled`, `settings`) and `sync_offset_ms`. New `control` methods, each one undo step on the shared stack, publishing `source.changed`: `filter.add {source, type, settings?}` (answers `{filter}`), `filter.remove {filter}`, `filter.move {filter, index}`, `filter.set_enabled {filter, enabled}`, `filter.set_settings {filter, settings}` (a patch on the values on air, decision 8: the given keys replace, the others stay; the result is validated as a whole and written in full). `source.set_sync_offset {source, offset_ms}` is live and not undoable, like `source.set_volume`. Refusals: `not_found` for an unknown source or filter, `invalid_params` for an unknown type, unknown keys, wrong kinds, values out of range, an index past the end, a filter on a sound-only source, settings for a filter whose type is unknown, an offset out of range, or a sync offset on a source without sound. Effects (ADR-0052 decision 4): the filter methods and `source.set_sync_offset` `edit`, with the on-air check when the source is reachable from the program scene (nested scenes included, as `control-api.md` defines it); `filter.types` `read`. Identifiers and API values spell `color` (`key_color`, field kind `"color"`), as the scene document's `border.color` does; UI text says "colour".

## Consequences

- Filters work in the app, the CLI's scene files and the control API with one definition per filter type; adding a type is one `FilterType` implementation, its conformance run and a catalogue entry.
- `FilterNode::process`, the resize allocation in it (decision 5) and `TexturePool::trim_idle` in `GpuRuntime::end_tick` are hot-path changes (P15): the PR carries a benchmark per filter at 1920x1080 (container software Vulkan numbers, Mac and Windows numbers before the owner signs off), the compositor benchmark before and after `trim_idle`, the allocation test and the `hot-path-review` checklist, and waits for the owner's sign-off before merging. `docs/architecture/hot-paths.md` and `.github/CODEOWNERS` list `crates/rbs-filters`.
- `rbs_gpu` makes `PooledTexture::sampled_bind_group` and the context's sampled-texture layout public (`GpuContext::sampled_layout`), so filter pipelines bind pool textures as the compositor does, and gains `TexturePool::trim_idle`, `forget`, `touch` and eviction on a full pool (decision 5); `gpu-compositor.md` records them and the P6 exception.
- A source switching size costs one frame with an allocation on the render thread, never a gap or a wrong frame; the old size's textures go back at once; tested along a chain of two filters, including a 120-frame resize sweep.
- A source that delivers no new frame costs its filters nothing per tick but one `touch` per target.
- Public contracts that change: scene document format 4 (sync offset), control API 1.8 (additive), `BindReport` (non-exhaustive) gains `changed_filters`, `SourceAudio` (non-exhaustive) gains a field. Spec updates in the same change: `video-filters.md` (new), `scene-model.md`, `user-data.md`, `control-api.md`, `ui-design-system.md`, `scene-sources.md` and `recording.md` where they list node types and instances.
- Follow-ups: colour key, LUT and image mask (resource handles through the channel), looks (ADR-0053 decision 9), fusing per-pixel passes on numbers, a before/after toggle in the Filters tab, filters on nested scenes (needs render-to-texture for scenes), audio filters.

## Alternatives considered

- **One node type per filter** (`ColorCorrectionNode`, `ChromaKeyNode`, ...). Each would repeat the ring, warm, resize and channel logic, the part that is hard to get right on a hot path; the trait keeps that in one tested node and makes a filter a shader plus a schema.
- **Re-warm through the restart path (ADR-0024)** (this ADR's first draft). Keeps `process` free of allocation, but the layer is blank for 8 ticks plus about three control rounds, every resize is reported as a failure and a restart, a chain of filters repeats the gap per filter, and a warm that fails at the new size could be retried in a loop (review round 1). A one-frame allocation, as the compositor already makes on a pool miss, is the smaller harm on air.
- **A graph-level re-warm request** (the node asks the executor to cool and warm it at the next swap without a failure record). Cleaner in principle, but a change to the node contract of every runtime for one node type; worth it only if more node types need it.
- **Warm every possible size, or the canvas size, up front.** Memory for sizes never used, and a source larger than the canvas would still need a resize.
- **Pass the input through while resizing.** Reveals what a key or blur hides (ADR-0053 review round 2).
- **Filters in their own panel only** (the design system's rule as written). The design the owner chose puts Filters in the Properties tabs, the tab already keeps Properties short, and editing stays in one place; the separate panel remains the way out if the tab grows beyond a screen.
- **Filter settings as live, not undoable, like volume.** A filter change is an edit of how the scene looks, the kind of change U4 makes undoable; volume and mute are exempt only because an undo must never unmute a microphone (ADR-0059).
- **Sync offset as a source setting.** A settings change replaces the source node, which reopens the device (ADR-0059 alternative).

## Review

Reviewer: independent AI session (round 1)
Date: 2026-11-07
Verdict: changes requested
Concerns:
1. The restart-path resize leaves the layer blank for 8 ticks plus about three control rounds, reports failures, and the retry only saves the back-off; the rejected one-time allocation was stated unfairly (the compositor already creates on a pool miss). -> Decision 5 now re-acquires once in `process`; the restart path and a graph-level re-warm are listed as alternatives with their costs.
2. Immediate retries could loop with no back-off when `warm` fails at the new size. -> Gone with the restart path; a failing `acquire` in `process` is an ordinary node error with back-off.
3. Resizes cascade along a chain. -> No gap per filter now; the studio passes the known size to every filter of the chain; two-filter chain test.
4. Old-size textures are never freed; nothing calls `trim`. -> `TexturePool::trim_idle` in `GpuRuntime::end_tick` (decision 5), tested; output ring of two, justified (decision 4).
5. Blur radius 0 cannot be the identity; `smoothstep(e, e, x)` undefined. -> The spec drops the identity claim (the minimum blur is the half-size resample) and states the chroma key's smoothness floor.
6. "No allocation in `process`" untestable as written. -> Decision 4 and the spec use `alloc_per_frame`'s wording.
7. Settings from documents are never validated. -> Decision 8: lenient conversion on load with reported adjustments; strict on edits; tested.
8. Semver and evolution: `SourceAudio::new` would reset the offset; trait and enums not non-exhaustive; `colour`/`color` spelling; always writing format 4. -> Decision 10 keeps `new` and adds `with_sync_offset`, with tests; decision 1 states evolution rules and `#[non_exhaustive]`; identifiers say `color` (decision 11); always the current format, as ADR-0053's review decided.
9. Sync offset: negative values are clamped by latency, the limit is configurable, `audio_offsets` would override the model. -> Decision 10: one source of truth per root (the app derives `audio_offsets` from the model and uses `set_audio_offset`), the clamp is stated and hinted in the UI, the constant is tied to the input's default by a test.
10. Spec edits missing for `scene-sources.md`, `recording.md`, `gpu-compositor.md`. -> Added.
11. UI rule amendment contradicts itself; name in Transform; volume in two places; sync offset as a U4 exception; on-air wording. -> Decision 9 rewritten (name stays in the header, mirrored live controls stated), decision 10 states the U4 exception, decision 11 uses "reachable from the program scene".
12. Slider drag has no cancel. -> Decision 9: a cancel re-sends the model's values.
13. Conformance gaps. -> Spec's suite gains: naga compile of every pass without a GPU, a chain of two filters, pool memory after removal and resize, an sRGB input and a partly transparent input, odd sizes, format 3 to 4 round trip and the offset kept across volume changes, API patch semantics and `method_not_found` on 1.7, a disabled-then-enabled filter keeping its values.
