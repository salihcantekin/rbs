# ADR-0087: Show the cost of outputs before they start, and the limits of this hardware

- Status: Proposed
- Date: 2026-11-09
- Deciders: Salih (owner)
- Builds on: [ADR-0013](0013-zero-cost-when-unused.md), [ADR-0047](0047-several-outputs-per-canvas.md), [ADR-0051](0051-user-data-profiles-and-scene-collections.md), [ADR-0086](0086-recording-sources-separately-iso.md)
- Spec: [backend-ports](../specs/backend-ports.md) (capabilities), [output-ports](../specs/output-ports.md), [recording](../specs/recording.md), [performance-budgets](../specs/performance-budgets.md), [user-data](../specs/user-data.md), [control-api](../specs/control-api.md)

## Context

Outputs are not free, and the same settings do not work on every machine. Recording the master and three sources separately (ADR-0086) means four encoder sessions, four conversions and readbacks, four disk writers, and sources kept running that nobody sees on air. A recent desktop GPU may do that comfortably; a laptop may not, or may run out of hardware encoder sessions and silently fall to a CPU encoder. The owner (2026-11-09) asks for two things: an estimate of the load shown **before** recording starts, and a warning of the form "this hardware can export at most X sources", because every machine produces different output.

What exists: the capability model already declares `codec.sessions.max` (concurrent sessions, absent means unlimited), `codec.video.width`/`height`, `codec.video.fps.max`, `codec.video.rate_control` and whether an adapter is hardware (`adapter.hardware`). Adapter selection picks the best candidate whose `open` succeeds (`tried` lists the refusals). Progress counters (late ticks, drops, queue depth) exist at run time. What is missing: a way to say *before* the start what the plan will cost, how many tracks fit, and what happens to the track that does not fit.

Declared capabilities are upper bounds, not promises: a driver may allow 8 sessions yet not sustain 8 at 4K60, and disk, memory bandwidth and the CPU encoder fallback are not declared at all. A useful answer therefore combines declared limits with measurements taken on this machine.

## Decision

1. **An estimate for any plan.** A pure function in `rbs-record` (the layer that already sees every registry) takes a *plan* (the outputs: master, stream, the ISO tracks with their sizes, frame rates, codecs and rate control, the sources kept active, the target folder) and the probed registries, and returns an `Estimate`: per resource a *need*, a *limit* and a *level*, plus the reasons. Resources: **encoder sessions** (per adapter, from `codec.sessions.max`), **encoder throughput** (pixels per second per adapter and codec; measured or declared), **CPU encoder load** when a track would use a software adapter, **export and readback traffic** (bytes per second, and pooled memory: the export buffers times frame size per track), **disk write rate** (sum of the bit rates, compared with the folder's measured write speed) and **disk space** (bit rate times a planned duration, default 1 hour, against free space), **sources kept active** (count and their kind). The disk probes (free space, write speed) run on a worker with a timeout, because a network share can hang, never on the control thread. The function has no side effects and allocates only on the control thread; it runs when the UI opens the relevant card, when a setting changes, and when Record is pressed. Nothing runs in the background (P13).
2. **Levels.** `fits` (all needs below 70 % of their limits), `heavy` (any need between 70 % and 100 %, or any track that would fall to a CPU encoder), `over` (any need above its limit, or a track that has no adapter that can open it). The thresholds are constants in one place and are part of the spec, not user-facing settings.
3. **"At most N" for this hardware.** For a given plan shape, the estimate also returns `max_tracks`: how many more tracks of the same kind fit before the first resource becomes `over`, and **which resource is the limit** ("encoder sessions", "encoder throughput", "disk speed", "memory"). Because machines differ, the UI shows it as a sentence beside the setting: "This computer can record up to 6 separate 1080p60 video tracks with these settings. The limit is encoder throughput." The sentence says whether the number is *measured on this machine* (with the date) or *estimated from the declared capabilities*.
4. **Measurement on request (calibration).** Settings › Recording has a *Test this computer* button (also offered once, as a suggestion, the first time an estimate is `heavy`). It runs a short synthetic encode (about 10 seconds, no capture, no files kept) of a growing number of parallel sessions at the plan's codec, size and frame rate on each adapter the plan can use, and records the highest count and pixel rate that sustained real time with no late frames; it also writes a temporary file of a few hundred megabytes in the target folder to measure the write speed. It refuses to run while any output, recording, virtual camera or armed replay buffer is active; it also covers the native-surface path (ADR-0025) where the adapter has one; it (it would disturb it) and says so. Results are a per-machine user-data document (`kind = "calibration"`, ADR-0051: never part of a profile or collection, never synced, versioned), keyed by adapter id, the adapter's reported version (driver), codec, size class, frame rate and rate-control class, and are used by later estimates; a changed driver or adapter invalidates the entry. Without a measurement the estimate uses declared capabilities and says so.
5. **When the plan does not fit.** An adapter selection that would silently fall back to a CPU encoder is exactly what the user must not discover mid-take, so the policy is explicit and saved: `when hardware encoders run out` = *ask* (the default: the start dialog offers *use the CPU encoder for the extra tracks*, *skip those tracks* or *cancel*), *use the CPU encoder*, or *skip those tracks*. Over the hard limit (no adapter can open the track at all, disk full, a source that cannot be activated) the start is refused with the list of reasons and what to change; there is no "start anyway" for a hard limit.
6. **The warning before Record.** When the level is `heavy` or `over`, pressing Record (or Go live) shows a confirmation that lists the numbers per resource in plain words, the track list with the estimated cost of each, and the options of decision 5. `heavy` can be continued; the confirmation is remembered per exact plan (a hash of the settings and track set) so it is not repeated for an unchanged plan, and shown again when the plan changes. `fits` shows nothing. The same estimate is on screen, live, in Settings › Recording › Separate files and in the Source settings *Record separately* row (a small meter and the sentence of decision 3), so the user sees the effect while choosing. All wording uses glossary terms and is localised; all visual values are tokens. The dialog and cards are visual changes and follow rules 15 and 16.
7. **Same estimate for the API.** `record.estimate {profile?, plan?}` (read class) returns the structure of decision 1 and `max_tracks`; `record.start` refuses a plan that is `over` with a new code `output_over_limit` (number from the control-api error table at implementation) and the reasons, and starts a `heavy` plan only when the caller passes `acknowledge_heavy: true` (the UI does this after its confirmation), so scripts and remote panels cannot start an expensive take by accident. `calibration.run` (control class, refused while an output runs) and `calibration.status` complete the set.
8. **After the take.** The recording's final report (and ISO manifest, ADR-0086) includes the measured outcome: dropped and late counts per track, so the user can compare with the estimate; repeated disagreement is a reason to run the calibration.
9. **Not a hot path.** The estimate and calibration run on the control thread and in a throwaway graph that is not the live engine; they edit no hot-path code. The calibration creates real encoder sessions; it uses the same adapters and registry as a take, so a result also proves that the sessions can be opened.
10. **Limits of the method (stated, not hidden).** Estimates cannot see other programs using the GPU, thermal throttling or a slow external disk that changes mid-take; ADR-0090 handles run-time pressure. GPU utilisation percentages are not read (OS counters differ and are not portable); throughput is measured by what the encoder actually sustains. Windows and macOS only; on other platforms the estimate runs on declared capabilities and calibration is unavailable.

## Consequences

- The user sees what a take will cost, how many separate tracks fit, and what the limit is, before pressing Record, and a different machine gives a different, honest answer.
- Adapters must report `codec.sessions.max` honestly and a stable version string; the conformance suite checks that the number is not exceeded and that exceeding it fails with `Unsupported`, not a hang.
- A new capability (`codec.video.pixel_rate.max`, optional, declared throughput in pixels per second at the adapter's default settings) lets an adapter state what it knows; the measured value overrides it.
- A per-machine calibration document joins user data; its location, format version and eviction are specified in `user-data.md` in the implementing PR. The calibration needs a throwaway-graph helper in `rbs-record` and an automated test with fake adapters (`TestClock`, no sleeping; ADR-0032) for the arithmetic of levels and `max_tracks`.
- Spec follow-ups: `backend-ports.md` (capability), `output-ports.md`, `recording.md`, `user-data.md`, `control-api.md`, `ui-design-system.md`, `performance-budgets.md`, glossary.

## Alternatives considered

- **Only declared capabilities.** Cheap and deterministic, but wrong whenever the declared limit is higher than what the machine sustains; the "at most X" statement would mislead.
- **Measure automatically at first start.** More accurate by default, but a hidden load on the machine at the worst time and a surprise delay; an explicit button with an offer is predictable (P13).
- **Hard-code limits per GPU model.** Breaks P3 and ages immediately.
- **Start anyway and adapt (drop tracks live).** Dropping data after the user is on air is worse than a clear answer before; run-time adaptation is ADR-0090's job and complements this.
- **Show only an error when the encoder cannot open.** Misses the soft failures (CPU fallback, slow disk) that spoil a take without any error.
