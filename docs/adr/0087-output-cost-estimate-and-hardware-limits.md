# ADR-0087: Show the cost of outputs before they start, and the limits of this hardware

- Status: Proposed
- Date: 2026-11-09
- Deciders: Salih (owner)
- Builds on: [ADR-0013](0013-zero-cost-when-unused.md), [ADR-0047](0047-several-outputs-per-canvas.md), [ADR-0051](0051-user-data-profiles-and-scene-collections.md), [ADR-0086](0086-recording-sources-separately-iso.md)
- Amends: [ADR-0086](0086-recording-sources-separately-iso.md) decisions 5 (what happens when tracks cannot open, for starts with ISO video tracks), 6 (skipped tracks in the manifest) and 11 (`record.estimate` and the start parameters), and adds one requirement to decision 12's step 3 (publish the render partition's previous-tick time, decision 1: an engine statistic like the existing per-tick counters, stored only while the render partition runs, so ADR-0086 decision 13's zero cost holds); a `## Review` note is added there when this ADR is accepted
- Spec: [backend-ports](../specs/backend-ports.md) (capabilities), [output-ports](../specs/output-ports.md), [recording](../specs/recording.md), [performance-budgets](../specs/performance-budgets.md), [user-data](../specs/user-data.md), [control-api](../specs/control-api.md)

## Context

Outputs are not free, and the same settings do not work on every machine. Recording the master and three sources separately (ADR-0086) means four encoder sessions, four conversions and readbacks, four disk writers, and sources kept running that nobody sees on air. A recent desktop GPU may do that comfortably; a laptop may not, or may run out of hardware encoder sessions and silently fall to a CPU encoder. The owner (2026-11-09) asks for two things: an estimate of the load shown **before** recording starts, and a warning of the form "this hardware can export at most X sources", because every machine produces different output.

What exists: the capability model has the key `codec.sessions.max` (concurrent sessions, absent means unlimited, `output-ports.md`), but no adapter declares it today: NVENC does not report the GeForce session limit, so its spec leaves the key out. It also has `codec.video.width`/`height`, `codec.video.fps.max`, `codec.video.rate_control` and whether an adapter is hardware (`adapter.hardware`). Adapters report no version: `AdapterFactory` has `id`, `display_name` and `probe` only. Adapter selection picks the best candidate whose `open` succeeds (`tried` lists the refusals). Progress counters (late ticks, drops, queue depth) exist at run time. What is missing: a way to say *before* the start what the plan will cost, how many tracks fit, and what happens to the track that does not fit.

Declared capabilities are upper bounds, not promises: a driver may allow 8 sessions yet not sustain 8 at 4K60, and disk, memory bandwidth and the CPU encoder fallback are not declared at all. A useful answer therefore combines declared limits with measurements taken on this machine.

## Decision

1. **A plan, a probe and an estimate.** A *plan* is what a start would run, built by the studio from the output profile, the canvases and the collection (never from a caller's description): the master recording, the stream, the vertical canvas's outputs when they start with the main ones (ADR-0111), the ISO tracks of ADR-0086 with their sizes, frame rates, codecs and rate control, the sources kept active (ADR-0086 decision 8) and the profile's recording folder. Outputs that already run (a stream started before the recording, the vertical canvas's outputs) count toward sessions, throughput and disk like the ones the start adds. Encoders shared by several outputs (ADR-0047) count once. The work is split in two:
   - The **probe** reads the folder's free space and, from the last calibration (decision 4), its write speed. It runs on a short-lived worker, never on the control thread, with a timeout of 2 seconds (`PROBE_TIMEOUT`, in the spec) because a network share can hang; a result is cached per folder for 60 seconds. A probe that times out or fails gives *unknown* for free space, with a reason, never `over`. `calibration.toml` (decision 4) is read at app start together with `app.toml`, before the control thread serves any request, and kept until a calibration rewrites it, so no start waits for it. The folder's write speed comes from it; the probe gives only free space.
   - The **estimate** is a pure function in `rbs-record` (the layer that already sees every registry) of the plan, the probed registries, the probe result and the calibration document. It returns an `Estimate`: per resource a *need*, a *limit* (or *unknown*), a *unit*, a *level* and whether the limit was *measured* or *declared*, plus coded reasons (decision 7). Resources: **encoder sessions** per adapter; **encoder throughput** (pixels per second per adapter and codec); **ISO encode workers** (the measured encode time per frame of the ISO tracks on each of ADR-0086's encode workers, against the frame interval, so serial software encoders are counted); **ISO render share**: the render partition's previous-tick time, plus, per ISO video track, the calibrated export time of its size class (conversion, normalisation, scaling, readback), against ADR-0086 decision 9's share of the tick budget, so the same rule that skips ISO exports at run time is the one estimated. The previous-tick time comes from ADR-0086 step 3, which publishes it whenever the render partition runs, not only while an ISO set runs (one relaxed atomic store per tick of the `now` the worker already reads; that edit is part of step 3's hot-path measurements and P15 sign-off, not of this ADR); the control thread samples it when the estimate runs and uses the median of its last samples. Until step 3 lands, the live part is *unknown*; **CPU encoder load**: the software video tracks' pixel rate against the software video encoders' calibrated throughput (`pixels_per_second`), *unknown* without a calibration; audio encoding is listed per track and not limited, since one audio track costs a small fraction of a core; **export memory** (pooled export buffers times frame size per track; informational only, with no limit and no level, since no GPU adapter reports a memory budget); **disk write rate** (sum of the bit rates against the measured write speed); **disk space** (bit rate times a planned duration, default 1 hour, a profile setting, against free space); **ISO ceilings** (MAX_ISO_VIDEO 16 and MAX_ISO_AUDIO 32); **sources kept active** (count and kind, unit `sources`, informational).
   The estimate runs when the UI opens the Separate files card or the Record separately row, when one of their settings changes, and when Record or Go live is pressed. A start never waits for a probe: with no cached result for the folder, free space is *unknown* for that start and a probe is started for the next one, so the control thread is never blocked. Nothing runs in the background (P13).
2. **Levels.** Two kinds of resources, with exact bounds; the thresholds are constants in one place in the spec, not user settings:
   - *Count* resources (encoder sessions, ISO ceilings): `fits` when need ≤ limit, `over` when need > limit. Using every hardware session is normal.
   - *Rate* resources (throughput, ISO encode workers, ISO render share, CPU encoder load, disk write rate): `fits` when need < 0.7 × limit, `heavy` when 0.7 × limit ≤ need ≤ limit, `over` when need > limit.
   - *Disk space* is planned against a guessed duration, so it is shown (`fits` or `heavy`) and never refuses a start or needs an acknowledgement; only a disk with no room for the start itself (below one minute of the plan) is `over`, and that is checked when files open, not from the cached probe. So the first start after launch, with no probe cached, is judged like the next one.
   - *Unknown* limit: the resource is `unknown` and adds a reason; the advice "run Test this computer" is given only where a calibration can measure the resource (an unknown session count, CPU load without a calibration, disk write speed), and resources no calibration can measure (for example free space after a failed probe) say what is missing instead; it never makes a plan `over`. In declared-only mode an absent `codec.sessions.max` on a **hardware** adapter (`adapter.hardware`) is read by the estimate as *unknown*, not unlimited, because hardware session caps are common and often not reported; on a software adapter absent keeps its port meaning, unlimited. The port meaning of the key is unchanged, so no adapter changes.
   - A track that **falls to a CPU encoder** means: the plan wants a hardware encoder for that codec, every hardware candidate is exhausted or refuses, and a software one would be used. That makes the plan at least `heavy`. A software adapter the user picked on purpose, and audio encoding (always software), are counted only under CPU encoder load.
   - The plan's level is the worst resource level, with `unknown` reported beside it, never instead of it.
3. **"At most N" for this hardware.** For a given plan shape, the estimate also returns `max_tracks` per kind (`video`, `audio`): the total number of tracks of that kind (those already in the plan included) that fit before the first resource becomes `over`, and **which resource is the limit** (`encoder_sessions`, `encoder_throughput`, `iso_workers`, `iso_render_share`, `cpu_load`, `disk_speed`, `disk_space`, `iso_ceiling`). `max_tracks` is computed from the known resources; when a resource is unknown, the answer carries `partial: true` and the unknown resources, and the count is an upper bound that the UI words as "at most" with "not counting" the unknown ones. When no resource is known, the count is `null`. The UI shows it as a sentence beside the setting: "This computer can record up to 6 separate 1080p60 video tracks with these settings. The limit is encoder throughput." The sentence says whether the number is *measured on this machine* (with the date) or *estimated from the declared capabilities*, and says "Unknown until you test this computer" when that is the case.
4. **Measurement on request (calibration).** Settings › Recording has a *Test this computer* button (also offered once, as a suggestion, the first time an estimate is `heavy` or `unknown`).
   - **What it measures.** On each adapter the plan can use, a synthetic encode of a growing number of parallel sessions at the plan's codec, size class and frame rate (no capture, no files kept), stepping one session at a time and stopping at the first step with a late frame, an open that fails with `ResourceExhausted` or `Unsupported`, or the plan's ceiling. It records the highest session count and pixel rate that ran each step's 2 seconds with no late frame. It also runs the ISO export of ADR-0086 decision 9 on a pooled texture of each size class used (conversion, scaling when needed, readback), in a throwaway GPU context like the encode, and records the time per frame; and, when the adapter has one, the native-surface path (ADR-0025). Finally it writes a temporary file of 256 MiB in the profile's recording folder to measure the write speed, and deletes it.
   - **Classes.** *Size class*: the smallest of 720, 1080, 1440 and 2160 lines at or above the frame's height, else `above-2160`. *Frame-rate class*: 30, 60 or `above-60` (at or below). *Rate-control class*: `cbr`, `vbr` or `cq` (constant quality, QP and CRF). The steps run for each class the plan uses.
   - **Time.** At most 60 seconds in all (`CALIBRATION_LIMIT`, in the spec); a run that reaches it stops and keeps what it measured, marked partial.
   - **What it tests.** `calibration.run {profile, canvas?}` tests the plan shape of that profile and canvas (default the main one); the desktop button uses the profile in use.
   - **Lifecycle.** `calibration.run` answers at once with `{}` and the run continues on its own worker thread, created for the run and gone after it (Installed, then Active only while it runs, P13); it never runs on the control thread. Progress and the outcome go out on the topic `calibration.state` (`idle`, `running {step, steps, adapter}`, `done {partial}`, `failed {reason}`) and are read with `calibration.status`. `calibration.cancel` stops it. It is refused with `conflict` while any output, recording, virtual camera or armed replay buffer runs, because it would disturb them, and starting any of those while it runs, by hand, by a hotkey, by the API or automatically ("Record when the stream starts", an armed replay buffer), is refused with `conflict` ("Test this computer is running") until it ends or is cancelled; the UI offers to cancel it and says why an automatic start did not happen. A device loss ends it as `failed`.
   - **Temporary file.** It is named `.rbs-calibration-<process id>.tmp`; a crash leaves it behind, so the next calibration run removes any `.rbs-calibration-*.tmp` in that folder first (nothing is cleaned at app start, P13).
   - **Where results live.** A per-computer file `calibration.toml` beside `app.toml` in the config directory, outside the `UserData` library: never part of a profile or collection, never exported, imported or synced. `format = 1`, `kind = "calibration"`. Encoder entries are keyed by adapter id, the adapter's version when it reports one (the optional capability key `adapter.version`: a one-element `Set` holding the driver or library version string, so no new `CapabilityValue` variant is needed; an adapter reports it only when its OS or SDK call answers inside the probe budget of `backend-ports.md`, otherwise leaves it out), codec, size class, frame-rate class and rate-control class. An entry whose adapter no longer probes, or whose `adapter.version` changed, is dropped when the file is next written; an adapter without `adapter.version` keeps its entries until the RBS version changes. Write-speed entries are keyed by the recording folder's path, kept in this local file only, and dropped when the folder no longer exists. At most 64 entries of each kind, the oldest dropped first. Without a measurement the estimate uses declared capabilities and says so.
5. **When hardware encoders run out.** A silent fall to a CPU encoder is what the user must not discover mid-take, so the choice is a saved setting of the output profile: `recording.iso.on_hardware_limit` = `ask` (the default), `cpu` (use a CPU encoder for the extra tracks) or `skip` (skip those tracks). The same values are ADR-0086 decision 5's choice for tracks that cannot open: `skip` is its *continue without failed tracks*, so one setting covers both. For ISO video tracks whose plan wants a hardware encoder (decision 2), encoder selection stops before a software candidate unless the policy is `cpu`, even when the estimate did not see the limit coming (no calibration, an unknown session count): a hardware encoder that refuses another session while files open gives `software_fallback` under `ask` (the start is refused, with the reason) and skips the track under `skip`. When only some tracks fit, the tracks are kept in source id order (the plan's order, ADR-0086 decision 2) and the rest are skipped or sent to the CPU encoder. The policy applies only to starts with ISO video tracks whose request carries a new parameter (decision 7), to their audio tracks as well (under `skip` a failed audio file is skipped too; ADR-0086's *continue without failed tracks* for audio-only starts is left to a later minor); a start without ISO video tracks keeps 1.46's rule that any track that cannot open refuses the whole start. `cpu` applies only to encoder sessions: a track whose muxer or file cannot open is skipped under `skip` and refuses the start under `cpu` and `ask` (reason `open_failed`), including when the failure is found after the estimate, while files open (ADR-0086 decision 5 (b)). In the desktop app `ask` shows the start dialog (*use the CPU encoder for the extra tracks*, *skip those tracks* or *cancel*). For a start with ISO video tracks whose request carries a new parameter, over a hard limit (no adapter can open the track at all, disk full, a source that cannot be activated, an ISO ceiling) the start is refused with the list of reasons and what to change; there is no "start anyway" for a hard limit. Skipped tracks are never in `tracks` or in the manifest's `[[files]]`, which keep listing only files on disk. They are listed in the start's answer and in `record.status` under a separate `skipped: [{source, role, reason}]`, and in the manifest in a separate `[[skipped]]` table (source, role, reason), which manifest format 1 readers ignore as an unknown table; the manifest stays format 1.
6. **The warning before Record.** The desktop app gates the same starts as the API (decision 7), so a script and a click behave alike. For a start with ISO video tracks, when the level is `heavy` or `over`, or a track would fall to a CPU encoder with `ask`, pressing Record (or Go live, when it records with the stream) shows a confirmation that lists the numbers per resource in plain words, the track list with the estimated cost of each, and the options of decision 5. `heavy` can be continued. A Record or Go live press runs as a request with the new parameters: the answer to the confirmation becomes `acknowledge_heavy` and `on_hardware_limit`, and when no confirmation is shown the profile's `on_hardware_limit` applies, so decision 5's policy and hard-limit refusals apply to a click. The confirmation is remembered for the app's run only (memory, not saved) per plan: a hash of the plan, the calibration entries it used and the adapters' versions, so a new calibration result or a changed driver shows it again. An automatic or indirect recording start ("Record when the stream starts" from the desktop or after an API `stream.start`, a hotkey, a Stream Deck command) carries no new parameter, so it follows the rule of decision 7 for such requests: video tracks the gate would stop are skipped, never the recording; when the desktop's confirmation would have been shown, the recording starts without those tracks and the UI says which were skipped and why, in the Live controls and `record.status`. A recording that cannot start at all (a hard limit) is not started: the stream goes on, the recording is reported as not started with the reason, and the UI shows it, as for any recording that cannot start; the user starts it by hand after the confirmation. `fits` shows nothing, and a start without ISO video tracks shows nothing new: the estimate is only on screen for it, as below. The same estimate is on screen, live, in Settings › Recording › Separate files and in the Source settings *Record separately* row (a small meter and the sentence of decision 3), so the user sees the effect while choosing. All wording uses glossary terms and is localised; all visual values are tokens. The dialog and cards are visual changes and follow rules 15 and 16.
7. **Same estimate for the API.** Scopes are those of the control-api spec.
   - `record.estimate {profile, canvas?}` (`read`): the plan of decision 1 for that profile and canvas (`"main"` by default, `"all"` as for `record.start`); no path is accepted, the profile's folder is the only folder probed. Answer: `{level, resources: [{resource, need, limit | null, unit, level, measured}], reasons: [{code, resource?, track?}], max_tracks: {video: {count | null, limit, partial, unknown: [resource]}, audio: {count | null, limit, partial, unknown: [resource]}}, tracks: [{source, role, cost: {resource: need}}]}`. `resource` is one of `encoder_sessions`, `encoder_throughput`, `iso_workers`, `iso_render_share`, `cpu_load`, `memory`, `disk_speed`, `disk_space`, `iso_ceiling` and `active_sources`. `unit` is `sessions`, `pixels_per_second`, `ratio`, `bytes_per_second`, `bytes`, `tracks` or `sources`; `memory` and `active_sources` are informational rows with `limit: null` and no `level`; `code` is one of a closed list in the spec (`unknown` for a resource no calibration can measure, such as the live part of the ISO render share before step 3, `no_adapter`, `open_failed`, `sessions`, `sessions_unknown`, `throughput`, `software_fallback`, `cpu_load`, `workers`, `render_share`, `disk_unknown`, `disk_full`, `disk_slow`, `ceiling`, `source_inactive`), so clients localise it. ADR-0086 decision 11's `record.estimate {profile}` is this method.
   - **No change for existing starts.** 1.46 refuses a picture mark through the API (`source.set_record_separately`, control-api 1.46), but a collection saved by a later version or edited by hand can carry one, and 1.46 writes no picture file for it. The gate below applies only to a `record.start` whose plan has at least one ISO **video** track. A request that carries neither `acknowledge_heavy` nor `on_hardware_limit` (any client before the video minor) is never refused because of ISO video tracks: the video tracks the gate would stop (`heavy`, `over`, `ask`) are skipped and listed in `skipped`, and the rest of the start runs as in 1.46. It writes at least what 1.46 wrote, so no earlier request changes meaning; only a request that carries one of the new parameters gets the refusals below. This covers every refusal ISO video tracks could cause, decision 5's included: for a request with neither new parameter, a video track whose source cannot be activated, whose hardware encoder runs out of sessions while files open, or whose file cannot open is skipped and listed, whatever the policy; its audio tracks keep 1.46's all-or-nothing rule, also under `skip`. When every video track is skipped and no source is marked for its sound, the start writes one file, as 1.46 does, not a folder. A recording, stream or audio recording without them, including a 1.46 start with separate audio files, starts exactly as in earlier minors, whatever its level; its answer gains `estimate: {level}` for information. `record.start_to_file`, `stream.start` and `audio_record.start` never carry ISO tracks and are never refused by the estimate.
   - **With ISO video tracks and a new parameter.** `record.start` takes `acknowledge_heavy: bool?` and `on_hardware_limit: "cpu" | "skip"?` (absent: the profile's value; `ask` from the API without this parameter is refused). It refuses an `over` plan, a `heavy` plan without `acknowledge_heavy: true`, and an `ask` that needs an answer, with the existing code `failed`; an explicit `on_hardware_limit: "cpu"` answers the fallback, so a plan that is `heavy` only because of that fallback needs no `acknowledge_heavy`, while other `heavy` resources still do. The refusal carries `data: {reason: "over_limit" | "heavy" | "hardware_limit", estimate}`; no new error code. `acknowledge_heavy` and `on_hardware_limit` sent on a start without ISO video tracks are accepted and ignored. With `canvas: "all"` the gate looks at the main canvas's plan, which is the only one with ISO tracks (ADR-0086 decision 1).
   - `calibration.run {profile, canvas?}` (`admin`, because it writes a large file into a recording folder), `calibration.cancel` (`admin`), `calibration.status` (`read`) and the topic `calibration.state`, as in decision 4. Their effect (ADR-0052) is `live` for `calibration.run` and `calibration.cancel` and none for `calibration.status`.
8. **After the take.** The recording's final report (and ISO manifest, ADR-0086) includes the measured outcome per track from the counters that exist: dropped frames, gaps and skipped ISO ticks (ADR-0086 decisions 6 and 9), so the user can compare with the estimate; no new per-track counter is added. Repeated disagreement is a reason to run the calibration.
9. **Not a hot path.** The estimate runs on the control thread; the probe and the calibration on their own short-lived workers, the calibration in a throwaway graph and GPU context that are not the live engine. None of it edits hot-path code. The calibration creates real encoder sessions with the same adapters and registry as a take, so a result also proves that the sessions can be opened.
10. **Limits of the method (stated, not hidden).** Estimates cannot see other programs using the GPU, thermal throttling or a slow external disk that changes mid-take; ADR-0090 handles run-time pressure. GPU utilisation percentages are not read (OS counters differ and are not portable); throughput is measured by what the encoder actually sustains. The estimate and the calibration are portable code; they are built and tested on Windows and macOS, the owner's target platforms, and are not excluded elsewhere, but no Linux work is planned.

## Consequences

- The user sees what a take will cost, how many separate tracks fit, and what the limit is, before pressing Record, and a different machine gives a different, honest answer; an unknown limit is said to be unknown.
- Existing API clients are unaffected: only requests that carry the new parameters can be refused because of ISO video tracks; older requests may gain video files and a folder, as 1.46's `iso` default did, and are never refused because of video tracks, and 1.46's separate audio files are unchanged.
- Adapters may declare `codec.sessions.max` when they know it; the conformance suite checks that a declared number is not exceeded and that exceeding it fails with `Unsupported` or `ResourceExhausted`, not a hang. The port meaning of an absent key is unchanged.
- A new optional capability key `adapter.version` (a one-element `Set`, so `CapabilityValue` is unchanged) lets an adapter report its driver or library version; and `codec.video.pixel_rate.max` (optional, declared throughput in pixels per second at the adapter's default settings) lets it state what it knows; the measured value overrides it. Both are additive, minor port changes, listed in `backend-ports.md` in the implementing PR.
- A per-computer `calibration.toml` joins `app.toml` outside the library (`user-data.md`).
- `recording.md` states the manifest rule that readers ignore unknown tables such as `[[skipped]]`, before ADR-0089's reader ships; `backend-ports.md` notes that `adapter.version` is a one-element `Set` holding a version string, and each adapter's spec in `output-ports.md` says what it reports there or that it leaves it out.
- ADR-0086 step 3 gains one requirement: publish the render partition's previous-tick time (decision 1).
- The calibration needs a throwaway-graph helper in `rbs-record`. Its driver takes an injected clock and a fake encoder factory with a scripted throughput and session limit, so a `TestClock` test (no sleeping, ADR-0032) checks the found count, the stop at `ResourceExhausted`, that the first start after launch is judged like the next one, the 60-second limit, the refusal while an output runs, the invalidation on a version change and the removal of a left-over temporary file. The arithmetic of levels, `unknown` and `max_tracks` has its own unit tests.
- Spec follow-ups: `backend-ports.md` (capabilities), `output-ports.md`, `recording.md`, `user-data.md`, `control-api.md` (methods, topic, reason codes, constants), `ui-design-system.md`, `performance-budgets.md`, glossary.

## Alternatives considered

- **Only declared capabilities.** Cheap and deterministic, but wrong whenever the declared limit is higher than what the machine sustains; the "at most X" statement would mislead.
- **Measure automatically at first start.** More accurate by default, but a hidden load on the machine at the worst time and a surprise delay; an explicit button with an offer is predictable (P13).
- **Hard-code limits per GPU model.** Breaks P3 and ages immediately.
- **Start anyway and adapt (drop tracks live).** Dropping data after the user is on air is worse than a clear answer before; run-time adaptation is ADR-0090's job and complements this.
- **Show only an error when the encoder cannot open.** Misses the soft failures (CPU fallback, slow disk) that spoil a take without any error.
