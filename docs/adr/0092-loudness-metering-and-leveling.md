# ADR-0092: Loudness: BS.1770 metering first, then a slow leveler, and gain advice for editing

- Status: Proposed
- Date: 2026-11-09
- Deciders: Salih (owner)
- Builds on: [ADR-0037](0037-audio-graph.md), [ADR-0081](0081-master-strip-in-the-mixer.md), [ADR-0082](0082-audio-filter-chains-on-sources.md), [ADR-0086](0086-recording-sources-separately-iso.md), [ADR-0089](0089-recording-markers-and-editor-project-export.md), [ADR-0091](0091-per-scene-audio-levels.md)
- Spec: [audio-graph](../specs/audio-graph.md) ("Loudness meter"), [recording](../specs/recording.md) ("Loudness meter"), [audio-filters](../specs/audio-filters.md) (from ADR-0082), [control-api](../specs/control-api.md), [ui-design-system](../specs/ui-design-system.md)

## Context

Peak meters (dBFS) show clipping, not how loud a programme sounds. Platforms and broadcasters judge loudness in LUFS (ITU-R BS.1770, EBU R 128): YouTube and many streaming services reference about -14 LUFS, podcasts about -16, European broadcast -23. A live creator whose voice is quiet in one scene and loud in another is heard as inconsistent, and a recording that must be corrected later costs editing time. The owner approved scene-aware audio profiles and loudness normalization as ideas to pursue. Live normalization has a hard limit: the future of a live signal is unknown, so any real-time gain ride must be slow, bounded and gated, and a limiter that never clips needs look-ahead, which the graph cannot yet report (ADR-0082: filters add no latency today).

Facts: the master volume and mute are the last stage of the mix (ADR-0081); filters exist only on sources (ADR-0082); recorded files get a manifest (ADR-0086, ADR-0089); audio nodes are a hot path (P15).

## Decision

1. **Three stages, each useful alone.**
   - **Stage 1: Loudness meter.** Momentary (400 ms), short-term (3 s) and integrated loudness (LUFS), loudness range (LU) and true peak (dBTP), as defined by BS.1770-4 and EBU R 128 (decision 4 has the algorithm). It measures the main canvas's master mix at the master tap point (decision 2), and its first deliverable is the control API read-out (decision 8); the master-strip readouts and target mark (decision 7) follow as a visual change of their own. Per-source loudness is not part of stage 1.
   - **Stage 2: Loudness advice in the manifest and editor project.** True peak is measured before encoding; overs after a lossy encode can differ. **2a** (needs only ADR-0086, which is Accepted and already writes the manifest, also for plain recordings): when recording with *Measure loudness of recordings* on, a meter per recorded file accumulates integrated loudness, range and maximum true peak, and the manifest stores them per file when the recording stops. The master file's meter reads the master tap point; each separate audio file's meter reads that file's own tap (after the source's filters, before its fader, ADR-0086), so the master's processing never changes them. **2b** (needs ADR-0089 Accepted): the editor project export writes a clip gain that brings each file to the user's target, so the correction is exact, non-destructive and made in the edit where the future is known.
   - **Stage 3: Leveler (live gain ride).** A slow automatic gain on the master bus that moves the short-term loudness toward a target, then a ceiling (decision 6).
2. **Placement: a master chain, and a master tap point at its tail.** Audio filters so far exist on sources (ADR-0082). The master needs the same: an ordered filter chain between the mixer's output (after the master volume and mute, ADR-0081) and its consumers (the meter sink, the audio encoders and the replay buffer; the master *peak* meter is not a consumer but is computed inside `MixerNode::process`). The binder inserts processing filters into it like a source chain, which is **new binder work** for the master (the master volume is a mixer parameter today, ADR-0081, and each output's audio route is wired in `Studio`, ADR-0047); the ADR's implementation PR specifies how the chain interacts with encoder sharing (one chain per canvas, before the fan-out) and is a contract and hot-path change. The **master tap point** is the chain's tail, or the mixer's `main` output while the chain is empty: what the encoders get. The loudness **meter is not a chain filter but a parallel tap** there: a sink node (`LoudnessTapNode`, kind `Output`, one audio input, no output, in `rbs-audio` next to the meter sink) that reads the block and changes nothing, so *Show loudness* during a stream causes no dip. It is not in the filter catalogue and not part of any chain. When the chain's tail changes, the binder relinks the tap to the new tail in the same apply, as ADR-0095 relinks a ducker's key. Processing filters on the master (the leveler) use the same `AudioFilterType`/`AudioDsp` traits and nodes as source chains (ADR-0082); what each consumer (encoders, replay buffer, meter sink, loudness tap) receives on the tick a new tail joins (ADR-0020) is specified and measured in the stage-3 PR; a missing block must never become a timestamp gap in a file or stream, and any audible dip is stated in the UI. **Amendment of ADR-0081 decision 3** ("the master meter shows what the encoders get"): once a master chain has a filter, the in-mixer master peak meter would read before it, so the implementation that adds the chain also moves the master peak meter to the tap point (or labels it pre-chain); this ADR records that amendment. The chain is after the master volume and mute: with the master muted the leveler holds (it sees silence), and a lowered master fader is counteracted within *Max boost*, which the help text says; on a scene switch (ADR-0091 changes levels in steps) the leveler holds its gain for its settle time and then resumes. A canvas with an empty master chain has no node between the mixer and its consumers (P13). Separate audio files (ADR-0086) tap *before* this chain, so the master's processing never changes them; their own meters measure them.
3. **Node and filter types.** The meter is the tap node of decision 2 (`org.rbs.audio.loudness-tap`), publishing its values through a struct of atomics read by the UI, the control API and the recorder. The leveler is a filter type in `rbs-audio-filters` (ADR-0082), `org.rbs.audio-filter.leveler`, fields-from-schema (ADR-0082 `rbs-params`), so its controls come from the same generated editor. Metering is an opt-in: **off by default**; the Mixer's master menu has *Show loudness*, whose API twin is `loudness.set_enabled` (decision 8), and which connects the tap; recording loudness measurement is a profile setting (*Measure loudness of recordings*, default off, with a note that it costs CPU on the audio thread, measured and stated in the PR). Nothing runs unless enabled (P13, rule 10): with loudness off the graph has no loudness node and the schedule is the same as without this feature.
4. **Meter algorithm contract (testable).**
   - *K-weighting:* the two biquads of BS.1770-4 from their analogue prototypes (shelf f0 1681.97 Hz, Q 0.7072, +4.0 dB; high-pass f0 38.135 Hz, Q 0.5003) by the bilinear transform with prewarping, for the graph's rate; at 48 kHz they match the BS.1770 table to 1e-6.
   - *Channels:* mean square per channel with the BS.1770-4 weights: 1.0 for mono, stereo, front and discrete channels, 1.41 for side surrounds, LFE excluded. A mono graph is one loudspeaker and reads about 3 dB below the same signal on two; that is intended (BS.1770).
   - *Windows:* the signal is summed per 10 ms of samples, independent of `block_frames` (1 to 8192). Momentary (400 ms) and short-term (3 s) are ungated sliding windows updated every 10 ms.
   - *Integrated:* 400 ms gating blocks every 100 ms (75 % overlap), absolute gate -70 LUFS, relative gate -10 LU below the power mean of the blocks above the absolute gate.
   - *Range (Tech 3342):* short-term values every 100 ms; keep those above -70 LUFS, then those above their power mean minus 20 LU; LRA is the 95th minus the 10th percentile.
   - *True peak:* polyphase oversampling by 4 below 96 kHz, 2 from 96 kHz to below 192 kHz and 1 (the sample peak) from 192 kHz, so the interpolated rate stays at least 176.4 kHz; 12 taps per phase (48 at 4x, as the BS.1770 example filter).
   - *Bounded state:* integrated loudness and range need every block since the reset; they accumulate into fixed histograms (0.1 LU bins from -70 to +30 LUFS) that keep the count and the energy sum of each bin, so the power means are exact and only the bin holding a relative gate is decided by its mean. All state is sized when the meter is made; nothing allocates in `process` or `reset`.
   - *Conformance:* the EBU Tech 3341 and 3342 minimum-requirements signals that are defined by formula (3341 cases 1 to 6, 9, 11, 12, 14 and 15 to 23; 3342 cases 1 to 4), generated in the tests, read within the documents' tolerances: M, S and I ±0.1 LU, LRA ±1 LU, true peak +0.2/-0.4 dB; with graph blocks of 480 frames, and of 512 and 1 where the block size matters, and at 44.1 and 96 kHz besides 48 kHz. 3341 cases 7, 8, 10 and 13 and 3342 cases 5 and 6 need the EBU's signal files or one file per segment and are run when the files are available, not in the unit tests. Silence reads no value and does not move the integrated value (gated).
   - *When it restarts:* integrated loudness, range and maxima restart when the meter is turned on, on `loudness.reset` and when the audio graph restarts (a new studio); never on a scene switch, an output start or stop, or a master filter being added. The DSP and its conformance tests are platform-independent and run on every platform; shipping is Windows and macOS (decision 10).
5. **Settings (user-visible, saved; targets are not hard-coded).** *Target* is a user setting of the app (`user-data.md`), read through `settings.get`/`settings.set`; measuring recordings is the profile setting of decision 3; the leveler's controls are filter values of the leveler in the master chain (scene data per collection, decision 6a), edited in the master chain's filter editor and listed here only to define them. Settings › Audio › Loudness: *Target* (presets -14 streaming, -16 podcast, -23 broadcast EBU R 128, -24 ATSC A/85, or a custom value in LUFS), and, in the leveler's filter editor: *Leveler* on/off, *Max boost* (default 0 dB until a limiter exists; the user may raise it), *Max reduction* (default -12 dB), *Speed* (slow, medium, fast; each preset sets both the time constant of the detector and the gain slew limit: slow 10 s and 1 dB/s, medium 3 s and 3 dB/s, fast 1 s and 6 dB/s; default slow), *Gate* (below which short-term loudness the leveler holds its gain instead of raising it: default -50 LUFS, so silence and room noise are not pumped up), *Ceiling* (true-peak ceiling, default -1 dBTP; see decision 6). Each control has a one-line help and a reset. Per scene (ADR-0091) a target override may be added later with the same ramp rules; not in this decision.
6. **Leveler behaviour, honestly.** The leveler is a gain ride, not a compressor: it contains its own BS.1770 short-term estimator (the same code as the meter), smooths the gain error (target minus short-term loudness) with the *Speed* time constant, so a constant this short still moves on the 3 s estimate, and changes its gain never faster than the slew limit, never above *Max boost*, holds when the gate says "no programme", and interpolates the gain per sample, linear in dB (no steps, no clicks; a test bounds the per-sample gain change). It does **not** guarantee that peaks stay under the ceiling. A true-peak limiter needs look-ahead, therefore latency, which the node contract cannot report today (ADR-0082). The leveler is therefore delivered in two parts: first without a limiter (the UI says the ceiling is *monitored*, with a warning indicator when the true peak passes it), then, once a separate decision adds latency reporting to nodes, a look-ahead limiter filter that makes the ceiling a guarantee. Until then the meter and the manifest report overs, and a gain filter (ADR-0082) is the manual trim. Because the tap point is the chain's tail (decision 2), the meter sees overs that the leveler's boost creates.
   - **6a. Data model of the master chain.** `MasterAudio { volume, muted }` (ADR-0081) gains `filters: Vec<Filter>` like a source (ADR-0082), with undo records and `scene-model.md` changes; the scene format number is assigned when that PR merges. The stage-3 implementation PR specifies it; stages 1 and 2 need no model change.
7. **Live indicator on the master strip** (visual: proposal and screenshots first, rules 15 and 16): short-term LUFS as a number next to the peak meter, a target mark on a small loudness bar, a gain-reduction/boost readout when the leveler is on, and a true-peak "over" lamp. Colours and sizes are tokens.
8. **Control API** (one minor version per stage, numbered at merge). Stage 1, main canvas only: `loudness.status` (`read`) answers `{enabled, momentary?, short_term?, integrated?, range?, true_peak_max?, momentary_max?, short_term_max?}` (LUFS, LU, dBTP; a value without data is absent, never NaN or infinite); `loudness.set_enabled {on}` (`control`, the API twin of *Show loudness*; session state in stage 1, saved with the UI step); `loudness.reset` (`control`; restarts integrated loudness, range, maxima and windows of the master meter, never the per-file meters of stage 2; `conflict` while off). The target is read and written with `settings.get`/`settings.set` when the setting exists; `loudness.status` then adds `target`. `audio.levels` carries per-source rows only today; an optional `master: {short_term}` object, present only while the meter is on, is added with the master-strip UI (older clients ignore it). `leveler_gain` joins `loudness.status` in stage 3. The recording report and manifest carry per-file `loudness` objects (stage 2a).
9. **Hot-path review.** The meter and leveler are new audio nodes in the audio partition. Ceiling: the meter at most 50 µs per 10 ms block at 48 kHz stereo (0.5 % of the block), measured by `cargo bench -p rbs-audio --bench loudness`; the leveler's ceiling is set the same way in its PR. Each needs the allocation guard test, the `hot-path-review` checklist and Salih's sign-off (P15). The master-chain binder change is the same review as ADR-0082's.
10. **Order of work.** (1) the meter as a tap on the master tap point (the mixer's `main` while there is no master chain) with the control API read-out, then the master-strip UI; (2a) per-file measurement and manifest fields, (2b) editor clip gain (ADR-0089); (3) master chain and leveler; (4) look-ahead limiter after the latency decision. Shipping targets Windows and macOS; the DSP and its tests are platform-independent.

## Consequences

- Creators see loudness the way platforms judge it, can aim at a target, and get exact correction data for the edit; live gain ride is available but honest about its limits.
- The master chain adds a binder feature that other master effects (compressor, limiter, EQ) will also use.
- No cost unless the user enables a meter or the leveler.
- A guarantee against clipping needs a separate, later decision (latency reporting); this ADR does not pretend otherwise.
- Spec follow-ups: `audio-filters.md`, `audio-graph.md` (master chain), `control-api.md`, `user-data.md`, `ui-design-system.md`, glossary ("Loudness", "LUFS", "Target").

## Alternatives considered

- **Peak normalization only.** Simple, but peak level says little about perceived loudness.
- **A fast compressor/limiter as "normalization".** Changes the sound character and pumps; a slow leveler plus clip gain in the edit respects the material.
- **Normalize only after recording (offline).** Most accurate, and decision 1 stage 2 provides the data; live streaming has no "after", so the live stages remain.
- **Write the loudness meter into the mixer.** Touches the mixer hot path for everyone; a separate tap node costs nothing when absent (decision 3).
- **Look-ahead limiter now.** Needs node latency reporting; deciding that inside this ADR would change the node contract without its own review.
