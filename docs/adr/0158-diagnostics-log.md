# ADR-0158: A diagnostics log with levels, written to a rotating file off the calling thread

- Status: Accepted
- Date: 2026-11-20
- Deciders: Salih (owner; design approved 2026-11-20 in the logging thread); independent review pending

## Context

RBS has no logging facility (quality audit QR-02, quality plan WP-21). About 170 places report through `rbs_crash::errln!` or `studio_ui::log`, which write to standard error. A desktop app started from Finder or the Start menu has no visible standard error, so these lines are lost, and support only has crash reports (ADR-0055). The UI stall watch (`rbs-app` `ui_thread`, stability plan WP-F) adds more such lines. Libraries already in the build (`wgpu`, `naga`, `winit`, `rustls`) report through the `log` crate, which nobody listens to.

The owner asked (2026-11-20) for app-wide logs that show what the system does, with professional levels, never hundreds of lines per second; a Settings › Advanced section where a user sets the level; and a way for a user who hit a problem to switch to detailed logs, repeat it and share the files on GitHub.

Constraints: core crates know no external library (P1; `rbs-core`'s only external crate is `bytes`); nothing on the real-time paths may allocate, block or do I/O (P6, [hot paths](../architecture/hot-paths.md)); a level that is off must cost nothing measurable (P13); the UI thread never waits on a disk or another thread ([threads](../architecture/threads.md)); secrets never reach a file (ADR-0055 decision 4).

## Decision

1. **A facade in `rbs-core`, no dependency.** `rbs_core::log` holds `Level` (`Error`, `Warn`, `Info`, `Debug`, `Trace`), `Filter` (`Off` and the five levels: what an area lets through), `Area` (`#[non_exhaustive]`; `App`, `Ui`, `Studio`, `Engine`, `Gpu`, `Capture`, `Audio`, `Encode`, `Record`, `Stream`, `Browser`, `Remote`, `AddOns`, `Plugin`, `UserData`, `Lib`; a new area is an additive change), a `Record` (level, area, `fmt::Arguments`, file, line), a `Sink` trait, `install(&'static dyn Sink)`, which succeeds once per process, and `Filters`, a value with one `AtomicU8` per area that tests create for themselves; the process-wide filters are one static `Filters`, all `Off` until set. The macros are exported at the crate root and called by path (`rbs_core::info!(Area::Record, ...)`, never imported with `use`, so they do not clash with the `log` crate's): each must check its area's filter with one relaxed load before any argument is evaluated or formatted, and only then reads the sink. A crate used without raised filters (tests, a library user) pays that one load and nothing else.
2. **Levels mean the same everywhere.** Error: something the user asked for failed, or something running stopped. Warn: it goes on, degraded or on a fallback. Info (the default): life-cycle steps and user actions, a few lines a minute in a normal session. Debug: decisions and details (candidates tried, formats negotiated, graph rebuilds, stall entries over 100 ms, a stats summary every 10 s). Trace: every control command and IPC message, every settings write, a stats summary every second. No level logs per frame, per block or per packet. The table per area is in the [diagnostics log spec](../specs/diagnostics-log.md#what-is-logged).
3. **Nothing on the hot paths.** The macros must not be called in code listed in [hot-paths.md](../architecture/hot-paths.md). Hot code counts events in atomics it already has or adds; a thread that is not hot (the control thread) turns changes of those counters into lines, and its summary timer exists only while its level is on: a level change from Settings reaches the control thread as a studio command, which wakes it, and `RBS_LOG` is read before the studio starts. `cargo xtask check-layers` fails when a log macro appears in a file that is hot as a whole (the list is in xtask and the spec); mixed files are covered by the `hot-path-review` checklist.
4. **A file writer in a new crate, `rbs-log`.** It gets its own layer class in `cargo xtask check-layers`, *Diagnostics*: it may depend on `rbs-core`, `rbs-crash` and `log` only, and only composition roots (`rbs-app`, `rbs-cli`, `rbs-mcp`) and the browser helper executables (`rbs-browser-runner`; `rbs-browser-cef` outside the workspace) may depend on it. Its sink formats the line on the calling thread and hands it, with its file and line, to a bounded queue with a non-blocking send; when the queue is full the line is dropped and counted, and the next line written says how many were dropped. A thread named `rbs-log` writes the lines, blocks on the queue when idle (no polling; a bounded wait only while a repeat count is pending), flushes when the queue is empty, removes secrets (decision 6), collapses a message repeated from the same call site into one line and a count (kept across file flushes, written when another line comes, when no line came for 60 s, or at `Logger::flush`), and keeps the last 500 redacted lines in memory for crash reports, holding that lock only to push one line. A full disk or a failed write stops the file, never the app.
5. **Files.** macOS `~/Library/Logs/RBS/`, Windows `%LOCALAPPDATA%\RBS\logs\`, Linux `$XDG_STATE_HOME/rbs/logs/` (default `~/.local/state/rbs/logs/`); `RBS_LOG_DIR` overrides it. One file per run, named by its start time in UTC and the process id (`rbs-20261120T152735Z-4182.log`; a helper uses its own prefix, `rbs-browser-...`), created with `create_new`, plain text lines `2026-11-20T15:27:35.123Z INFO  record [rbs-control] ...`, opened by a header (version, commit, OS, CPU, GPUs, levels). A file that reaches 10 MB continues in a segment (`rbs-20261120T152735Z-4182.1.log`, `.2.log`, ...). A file being written is marked: on Unix with an advisory lock (`File::try_lock`, `flock`); on Windows by opening it without delete sharing, never with a Windows file lock, which would stop every other reader (a text editor, the logs export). Pruning considers only names that match its own prefix exactly, orders runs by the time in the name (process id breaks ties), skips any file still being written (locked on Unix, not removable on Windows), and keeps the 10 newest runs and at most 50 MB in total, at start and whenever a segment is added, removing the oldest run first and, when only the current run is left, its oldest segments after the first (which holds the header).
6. **Secrets never reach the file.** Every line passes through a new `rbs_crash::LogRedactor` on the writer thread. It keeps its own copy of the secrets list and takes the list's lock only to copy it again after a change, never while it scans a line, so the panic hook's non-waiting look at the list is not turned away by a busy writer, and the writer never skips the list: the home directory becomes `~`, every secret registered with `rbs_crash::add_secret` (stream keys, passphrases, tokens; the list grows to 64 distinct values, a re-added secret moves to the end, the least recently added is dropped first) becomes `<redacted>`, a stream URL (`rtmp`, `rtmps`, `srt`, `rist`, `whip`) keeps its scheme and host and loses its path and query, and an `http(s)` URL loses its query and fragment at every level. Secrets are matched before URLs are rewritten, so a secret registered as a whole URL (a WHIP endpoint with the key in its path) is replaced whole. Crash reports run their own `redact` over the ring's lines, which also removes the host. Known limit: the panic hook's non-waiting look at the list still skips it in the microseconds while `add_secret` or a redactor's copy holds the lock. Callers log commands and settings by name or kind, never their payload; never text sources' contents (ADR-0132); captured window titles and page paths only at Debug. Other paths that hold a user name (`/Volumes/<name>`, another user's folder) are not detected; that is a known limit, and the Save logs dialog asks the user to look the files over.
7. **Levels are set by the user, the environment and the command line.** The Settings level is one of Errors only, Warnings, Normal (Info, default), Detailed (Debug) and Everything (Trace), stored in `app.toml`; Detailed and Everything return to Normal at the next start unless the user keeps them. Pro users can set a level per area. `RBS_LOG` (`debug`, or `info,stream=trace`) and the CLI's `--log-level` win over the setting, and the page says so. A change applies at once (an atomic store), no restart. Third-party `log` records arrive in `Area::Lib`, default Warn; Apps set levels only through `rbs-log` (`set_filter`, and `apply_level` for the Settings level, which leaves `Lib` alone); it keeps `log::max_level` equal to `Lib`'s filter, capped at Debug. Before formatting, the bridge thins a call site that logs often (its first 10 lines, then one in 1000, counted per file, line and level in 256 slots; errors are never thinned), so a library warning on every frame costs an atomic add on that thread, not a format. The Settings levels never raise `Lib` (a library such as `wgpu` may log per frame at Debug); only the per-area list (Pro) and `RBS_LOG` do, as an explicit choice, and repeats are collapsed.
8. **Sharing.** Settings › Advanced has "Save logs…" (a zip of the last three runs, crash reports, a system summary and a settings summary without keys or paths), "Open the logs folder" and "Report a problem on GitHub" (opens an issue template with version and OS filled in; the user attaches the zip). The crash notice gains "Save logs". The page is a visual change and follows rule 16 (proposal, dark and light screenshots, owner approval) before it is merged.
9. **Existing output moves.** `studio_ui::log`, `protection::log` and the app's `errln!` lines become leveled macro calls in their area; `errln!` stays for the CLI's answers to its user. The UI stall watch's lines go to `Area::Ui`: an entry that returned after more than 100 ms at Debug (Warn from 1 s), "not answering" at 1 s and 2 s at Warn, at 4 s and longer at Error.

## Consequences

- Problems on a user's machine leave a trace that the user can share in two clicks, without a debugger or a terminal.
- One more thread (`rbs-log`) in the app, parked when there is nothing to write; one atomic load per call site whose level is off.
- `rbs-core` gains a small public module; `rbs-log` joins the layer table as a helper with three allowed dependencies; `log` (already in the lock file) becomes a direct dependency of `rbs-log` only.
- Follow-ups, in order: the facade and `rbs-log` with tests; wiring in `rbs-app` and `rbs-cli`, moving the existing lines; lines in each area (the studio host after stability WP-G and before WP-L, the browser after WP-A); the Settings › Advanced page with screenshots; later, control API commands `diagnostics.log_level` and `diagnostics.export` (a contract change of their own).
- `tracing` records (only `zbus` on Linux) are not collected yet.

## Alternatives considered

- **The `log` crate as the facade in `rbs-core`.** Ready made and tiny, but it puts an external crate in the core (P1) and has no per-area levels without string matching on targets at every call site.
- **A std-only helper crate for the facade instead of a module in `rbs-core`.** Engine and port crates may see only Foundation and ports, so a separate facade crate would need an exception in every layer rule; the module is about 300 lines with no dependency.
- **`tracing` with `tracing-subscriber` and `tracing-appender`.** Spans and structured fields we do not need yet, a larger dependency tree, and the same P1 problem.
- **Writing the file from the calling thread under a lock.** Simplest, but the UI thread and the control thread would wait on the disk, which the thread rules forbid.
- **Logging from hot paths with a rate limit.** Even a rate-limited check formats nothing but still adds a branch and a clock read to code measured in nanoseconds; counters and a summary from a cold thread give the same information.
- **One file for all runs.** Harder to share the run that failed, and harder to cap.

## Review

Independent AI sessions (ADR-0014), each given only the ADR, specs, principles and code, 2026-11-20.

- **Round 1, changes requested (15 concerns).** Secrets left in a line when the secrets lock was busy, and a 16-secret cap: the writer gets its own redaction that never skips the list, the cap is 64. The host-keeping redaction did not exist: named (`redact_for_log`) and specified. User content at Trace and Debug (command payloads, URL queries): commands and settings by name or kind only, `http(s)` queries removed at every level. No layer class: the Diagnostics class with its edges (decision 4). Filters before `install`, global state against deterministic tests: `Filters` values for tests, the globals tested in one file. Pruning (prefix collisions, live files of other instances, same-second names, order, a run past the total, segment names): exact names with the process id, `create_new`, in-use files skipped, segments named (decision 5). Repeat collapsing ended by every flush: kept across flushes. The `log` bridge's filter and per-frame library logs: one setter keeps `log::max_level` in step, `Lib` capped at Debug and never raised by the Settings levels. Waking the control thread for the summary timer: a studio command (decision 3). `Area` made `#[non_exhaustive]`, macros called by path, the ring lock held only to push, home-only redaction recorded as a known limit, the separate-crate alternative added.
- **Round 2, changes requested (10 concerns).** The writer holding the secrets lock while scanning turned the panic hook's `try_lock` away: `LogRedactor` copies the list on change only. Two filter setters: apps use `rbs_log::set_filter` and `apply_level` only. Bridge formatting per frame on hot threads: thinned per call site before formatting. A compile-time check of the area count; a re-added secret moves to the end; repeat flush wording; the `rbs-log` thread in threads.md, `rbs-filters/src/node.rs` in the hot list, status.md; tests for filters before install and the call site's file; `write` kept out of line; xtask rejects macro imports.
- **Round 3, changes requested (8 concerns).** A Windows file lock would stop every reader of the running log: Windows marks files in use by share mode instead (decision 5). Shared bridge slots could thin a later library error: errors are never thinned, slots are per file, line and level, 256 of them. Secrets matched after URL rewriting could miss a WHIP key: secrets first. The repeat wait restarted with every line: a 60 s deadline. Spec and code gaps (`home`, `echo`, the counted unbounded queue, two missing tests) closed; the xtask check also catches `crate::` calls in `rbs-core`, `pub use` and `as` imports and `use log` in hot files; the first file of a run, with the header, is never pruned; wording. The panic hook's skip during a microsecond copy is recorded as a known limit (decision 6).
