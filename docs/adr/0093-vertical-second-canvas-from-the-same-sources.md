# ADR-0093: A vertical (9:16) second canvas running at the same time as the main one

- Status: Proposed
- Date: 2026-11-09
- Deciders: Salih (owner)
- Builds on: [ADR-0021](0021-scene-collection-model.md), [ADR-0026](0026-partitions-and-queues.md), [ADR-0034](0034-preview-as-native-layer.md), [ADR-0039](0039-scene-source-types.md), [ADR-0041](0041-studio-recording-on-a-running-engine.md), [ADR-0047](0047-several-outputs-per-canvas.md), [ADR-0049](0049-main-window-areas-panel-states-and-sizes.md), [ADR-0061](0061-studio-mode-in-the-desktop-app.md), [ADR-0081](0081-master-strip-in-the-mixer.md), [ADR-0084](0084-source-transform-commands-and-source-context-menu.md), [ADR-0087](0087-output-cost-estimate-and-hardware-limits.md)
- Spec: [scene-model](../specs/scene-model.md), [recording](../specs/recording.md), [gpu-compositor](../specs/gpu-compositor.md), [engine](../specs/engine.md), [control-api](../specs/control-api.md), [ui-design-system](../specs/ui-design-system.md)

## Context

Creators publish the same live show to a horizontal destination (YouTube, Twitch) and a vertical one (Shorts, TikTok, Reels). With a classic tool that means a second program instance, a second capture of every source (double the cost, and some devices cannot be opened twice) and a second set of scenes. The product vision lists multiple canvases as a core difference, and the owner approved a vertical second canvas as a feature to pursue.

What the model already has: a collection holds several canvases (`Canvas`: name, size, frame rate, program and preview scenes, master); a scene item has a default layout plus `overrides: BTreeMap<CanvasId, Layout>`, so the same source can sit differently in each canvas; scene scope (`Canvas(id)` or `Shared`, U15) says which canvases may show a scene; the binder routes audio to a mixer **per canvas** (ADR-0039) and the master volume is per canvas (ADR-0081); outputs are per canvas (ADR-0047). What it does not have: a running studio that serves more than one canvas. `StudioSettings` names a single `canvas` and the engine builds one compositor, one export per encoder, one mixer.

Forces: sources must be captured once and shared (P4, rule 17); a second canvas costs a second compositor pass, a second export and encoder; nothing of it may cost anything when it is off (P13); the vertical layout must be quick to get right, since "same scene, different shape" is where users lose time.

## Decision

1. **A studio serves a set of canvases.** The change surface is: `StudioSettings` (one canvas, one `PreviewDesc`, `scene_preview`), the mixer and meters, the audio-offset and master maps, preview endpoints, studio mode and every API that says "the studio's canvas". `StudioSettings` gains `canvases: Vec<CanvasId>` (the first is the *main* canvas; at most `MAX_CANVASES`, 2 in the first version; the number is a constant and is also subject to the estimate, ADR-0087). The engine builds one compositor, one preview endpoint (while its panel is open), one set of outputs and one audio route per canvas. **Source nodes and their video filter chains are built once and feed every compositor** (fan-out of an output pin, as ADR-0047 already uses): a camera is opened once. A canvas that is not in the set is data in the document and costs nothing (Installed); adding it to the set is *Activate* (Standby to Active, P13), removing it releases its nodes.
2. **Same frame rate in the first version.** All canvases of a studio share the main canvas's frame rate, so one render tick drives all compositors; sizes and aspect ratios are independent. A canvas whose rate differs is refused for activation with the reason. A second pacing domain is a possible later change with its own review.
3. **What the second canvas shows (follow modes, saved on the canvas).** `follow = main` (the default for a new vertical canvas): its program scene is the main canvas's program scene, switching together with it (transitions are the main canvas's; the second canvas cuts, a simple limitation stated in the UI). If the main program scene is scoped to the main canvas alone (U15), the second canvas shows its **fallback** instead, a setting: a chosen scene, "keep the last scene", or black. `follow = none` (its own program scene, switched independently) is **not in the first version**, because its sources would need their own audio mix (decision 5). A vertical canvas has no studio mode in the first version. When the main canvas runs a timed transition the second canvas cuts when the transition completes (a cut today).
4. **Layouts: reuse, then help.** A shared scene shown on the vertical canvas uses each item's `overrides[canvas]` or, when none exists, its default layout. Because the default layout is shaped for the horizontal canvas, adding a canvas offers **Auto layout** (a command, `canvas.auto_layout {canvas, scene?, mode}`, one undo step, writes overrides for the chosen scene or all scenes it shows) with three modes built on the fit/fill/align operations of ADR-0084: *Fit* (each item scaled to fit within the canvas, letterboxed), *Fill* (each item scaled to cover the canvas, with a horizontal focus point per item, default centre, adjustable on the picture), and *Stack* (the scene's visible items placed in equal bands from top to bottom in layer order, each filling its band, the common game-over-camera Shorts layout). Automatic face or subject tracking is not part of this decision. The layout of a vertical canvas is then edited like any layout, per canvas (U15).
5. **Audio.** The first version shares the main canvas's mix (a source heard only in a vertical scene would be silent, which is why `follow = none` waits; per-scene levels, ADR-0091, are those of the main program scene): the second canvas's outputs use the main canvas's audio encoder where their audio settings match (shared, ADR-0047), so the second canvas adds no audio cost. A canvas with its **own mix** (its own mixer and master, which the binder already supports per canvas) is the option for later; the setting `audio_from` exists from the start with the value `main`.
6. **Outputs.** Outputs are per canvas (ADR-0047). `MAX_OUTPUTS` becomes a limit per canvas (the fixed array and the partition allocation of ADR-0047 are amended in the implementing PR; ADR-0086's ISO pool is separate), and the estimate (ADR-0087) is the real guard for the total. Settings › Stream and Record are organised per canvas (a canvas selector at the top of the card), each canvas with its own destination, profile, size-appropriate presets (a vertical H.264 profile at 1080x1920 or 720x1280, data in the output profile) and files. Separate-source recording (ADR-0086) is per source and unaffected by the number of canvases; the replay buffer (ADR-0088) belongs to the main canvas in the first version.
7. **Preview and program panels per canvas** (ADR-0049, U15): the vertical canvas's preview is a panel the user opens; a closed panel costs nothing (no preview export, ADR-0034). The main window can show the vertical canvas beside the horizontal one.
8. **Creating one.** A guided command *Add vertical output...* (registry: `canvas.add_vertical`): choose a size preset (1080x1920 default, 720x1280, custom), follow mode, Auto layout mode; it creates the canvas, activates it, writes the layouts and opens its preview. The same through the control API: `canvas.add {name, size}`, `canvas.activate`, `canvas.deactivate` (live), `canvas.set_follow`, `canvas.auto_layout`, `canvas.list`, and `canvas.*` methods that today act on the studio's canvas take an optional `canvas` argument (default: main), in the next free protocol minor version.
9. **Model and format.** `Canvas` gains `follow: Option<CanvasId>` (None: independent), `fallback` and `audio_from`; the document keeps them only for a canvas that sets them; the scene format number is raised at the next free value at merge time (older builds refuse such a file, ADR-0078 precedent). The set of activated canvases is session state saved with the workspace (a profile holds no canvas ids, ADR-0051), not part of the scene collection (a collection opened on another machine does not start a second encoder by surprise).
10. **Cost and safety.** The second canvas adds: one compositor pass per frame at its size, one export and one encoder per output, one preview export while its panel is open. Sources, filter chains and the audio mix are shared. The render partition gets a second compositor node instance; the executor, queues and the compositor code are unchanged, but the render tick is a hot path, so the implementation has before/after measurements of the render tick and GPU time with 1 and 2 canvases (1080p60 main plus 1080x1920 at 60 fps) on the Windows RTX 4090 machine and the M4 Pro Mac, the `hot-path-review` checklist and Salih's sign-off (P15). If the second canvas threatens the main one, the main canvas wins: when the previous tick ran over a share of its budget the secondary canvas's frame is skipped, counted and shown (the same rule as ISO tracks, ADR-0086), and ADR-0090's guard can switch the secondary canvas's outputs off first.
11. **Order of work.** (1) multi-canvas `Studio` with source sharing and a second compositor, headless, tests and measurements; (2) follow modes and fallback; (3) Auto layout; (4) per-canvas panels and settings; (5) the guided command and the control API. Visual parts (1 to 5 as applicable) follow rules 15 and 16.

## Consequences

- One show, two shapes, with every source opened once: a combination that is hard in tools built around a single canvas. Cost is explicit and bounded.
- The studio loses the assumption of a single canvas; every API, event and UI path that said "the studio's canvas" is reviewed (spec follow-ups list in the implementing PRs: `recording.md`, `engine.md`, `scene-model.md`, `control-api.md`, `ui-design-system.md`, `gpu-compositor.md` notes, glossary "Canvas", "Follow").
- A transition on the main canvas is a cut on the second one in the first version. Different frame rates, own mixes, studio mode on the vertical canvas and a per-canvas replay buffer are later changes, each stated here so they are not assumed.
- The estimate (ADR-0087) must model the second canvas; it is part of that ADR's plan input.

## Alternatives considered

- **Two studio instances (two engines).** Simple to build, but every source is captured twice, devices that cannot be opened twice fail, and the two programs drift apart.
- **Crop the horizontal output to vertical after encoding.** Cheap but poor: no layout of its own, lower quality, no separate scene.
- **Unlimited canvases from the start.** The vision allows it, but the cost model and the UI are proven with two first; the constant can grow with measurements.
- **Automatic reframing by subject detection.** Attractive, but needs a vision model and per-frame GPU/CPU work; not in this decision.
- **Own audio mix by default.** Duplicates mixing and encoding for the common case where both shows have the same sound.

- 2026-11-09, independent AI session (round 1, reviewing only the ADRs, specs and code): changes requested. Concerns covered contract details, claims about existing code, hot-path and zero-cost rules, and number allocation across these ADRs; each was resolved in the text above (the numbers of protocol minors and scene formats are now assigned at merge time, not claimed by ADRs).
- Round 2 was done on 2026-11-10 (next entry).
- 2026-11-10, independent AI session (round 2, a fresh reviewer given only this ADR, the specs and the code of steps 1 to 3): **changes requested**. Findings and how each was handled in the implementing PR (#269):
  - *Inactive canvases still bound by the binder (P13).* Checked by a test (`a_canvas_that_does_not_run_costs_nothing_and_its_sources_close_when_it_stops`): the binder creates the nodes of every canvas with a program, but the plan schedules only nodes that reach a consumer, so a canvas that does not run opens no source of its own and a canvas that stops releases them. No code change; the test pins the behaviour.
  - *Atomicity of `activate_canvas` and `deactivate_canvas`*: the checks of an update now run before anything changes; a canvas that cannot be attached no longer loses the sources the sync created; a failed picture gives the compositor back.
  - *Format 8 file with `follow`* is refused; a duplicate canvas has its own error (`DuplicateCanvas`); `last` is dropped when a canvas stops.
  - *Deferred, stated here so the text does not claim them as done* (each needs its own change and review): the secondary-frame skip rule and the ADR-0090 guard of decision 10; `MAX_OUTPUTS` per canvas of decision 6 (it stays 2 in total, so record plus stream on both canvases cannot run yet); `Fallback::Black` and the cut when the main canvas's transition ends (decision 3); saving the set of activated canvases with the workspace (decision 9: `extra_canvases` is a `StudioSettings` field only); `audio_from` is in the model but not in the document (only `main` exists). The Windows (RTX 4090) measurement of decision 10 is open; the M4 Pro measurement is in #269.
  - Test gaps: the picture tests run only on Windows and macOS (previews exist only there).
- The owner's explicit acceptance and a round-3 check of these amendments are still needed before the status can become Accepted (ADR-0014).
