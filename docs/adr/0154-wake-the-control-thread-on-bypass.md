# ADR-0154: Wake the control thread when a node is bypassed

- Status: Accepted
- Date: 2026-11-19
- Deciders: Salih (owner); independent review recorded below; owner approved the review 2026-11-19
- Supersedes: [ADR-0027](0027-engine-loop.md) decision 6, the clause that caps `service().wait` by `control_interval` while any worker runs, and the sentence "Bypasses are seen at the latest one interval later." The rest of ADR-0027 stays.

## Context

ADR-0027 decision 6 makes `Engine::service()` return a wait of at most `EngineConfig::control_interval` (250 ms) whenever a partition has a worker. The reason is the bypass counter. The executor increments `bypasses` when it bypasses a node (`executor.rs`, the tick-failure branch and the warm-failure branch) and nothing else tells the control thread. ADR-0024 requires that restart to happen without a scene edit: a node that drops out comes back on its own. The poll is how the control thread notices.

That poll also runs when every node is healthy. The studio adopts a mixer and the program compositor at start, so those workers exist on an empty scene. `service().wait` is then `Some(250 ms)` even though `next_due` is `None` and nothing is in flight. The studio control thread wakes four times a second for the life of the window (ADR-0143 R6: a thread waits on an event or a deadline it computed, not on a fixed poll). `EngineHandle` has the same cap.

On the toolchain this tree builds with, `mpsc::recv` and `recv_timeout` wait in `Thread::park` / `park_timeout`. The control thread has one park token. A bypass `unpark` can be consumed by a channel wait inside `service` or a later `settle`, and the loop's own `park` then does not see it. Both control loops sleep on a channel today (`handle.rs` `control_loop`, `studio_host.rs` `round`). The studio also samples `serviced.wait` and may settle again (`apply`, `collect_timeout`) before it sleeps. A wake that is only an `unpark`, with the sleep taken from a `wait` sampled before that settle, never reaches the loop.

Removing the cap without a wake fails ADR-0024. A test that calls `service()` itself still sees the counter; a thread that sleeps until the next command does not. That was observed on 2026-11-19: dropping `has_worker()` from the cap made `a_bypassed_node_restarts_through_the_control_loop` fail its "a worker runs, so the loop keeps looking" assertion, which is the poll this ADR retires.

The owner approved this direction on 2026-11-19 and approved the review the same day.

## Decision

1. **The bypass is the event.** On each existing increment, the worker first updates the bypass counter, then reads the bound thread and unparks it. The counter is the record. The unpark is only the edge. A healthy tick must not unpark. The unpark must not allocate, lock or block (P6). Writes that happen before the unpark are the ones a later `park` is guaranteed to see, so the counter update must not move to after the unpark. `Ordering::SeqCst` on the counter alone does not order the cell: `OnceLock::get` is an acquire load and `OnceLock::set` publishes with an acq-rel swap. The handshake is two `SeqCst` fences. The worker fences after the increment and before it reads the cell. The sleeper fences after the bind and before the load that decides whether to sleep (`restart_due`, and the load immediately before `park`). If that load does not observe the increment, the worker has not yet passed its fence, so its cell read still sees the bind and it still unparks. Without those fences a skipped unpark can be slept through.

2. **The sleeper binds itself first.** `Engine` shares the control thread's `std::thread::Thread` with every executor it starts, including one started after the bind, as an `Arc<OnceLock<Thread>>` or an equivalent whose read is wait-free after `set`. The worker must not take a mutex to read it. The thread that will sleep binds itself before it samples `wait` and before its first `park`. A bind is once, and it is that sleeper, not whichever thread happened to call `service()` earlier. A bypass that observes an empty cell does not unpark. That race is safe only because a `service()` still runs after the bind and before the first `park`, and that `service()` reads the counter. The loop must not park on a `wait` sampled while the cell was empty.

3. **The sleep is the loop's own park, on a fresh wait.** The value the loop sleeps for is the `wait` from a `service()` that ran after the last settle in that round (`apply`, `collect_timeout`, anything else that waits on a worker). The loop then loads the bypass counter, or a flag the worker stored before the unpark, and only then calls `thread::park` or `park_timeout`. No `park` may run between that load and this `park`, including a channel receive: on this toolchain a receive parks on the same token and would consume the unpark. The `EventSink` must not park. After enqueueing a command, the sender unparks through one helper per channel (every `StudioHost::post`, `Host::post`, API waker and direct `tx.send` of a control message). A bare `send` does not wake a `park`. One extra wake from a token that was already set is acceptable. A healthy engine must not spin.

4. **`service().wait` no longer watches workers.** A running worker does not cap the wait. The wait is still the soonest `next_due` (zero when a restart is already due, the back-off delay otherwise, absent when nothing is scheduled). It is still capped by `control_interval` while a swap is in flight, a part is dirty, a move is waiting, or a retired endpoint remains, because those are not yet signalled by an unpark. A fault record does not by itself cap the wait: its next time is `next_due`. `control_interval` stays in `EngineConfig` for the cases that still use it.

5. **No new dependency and no plugin change.** The wake target is `std::thread::Thread` inside `rbs-graph` and `rbs-engine`. `rbs-graph` must not depend on `rbs-engine`. The plugin ABI, the control API and scene documents do not change. `Serviced.wait` changes meaning for a healthy running worker, from "at most 250 ms" to "whatever is actually due, or `None`". This crate is pre-1.0. A caller that still sleeps in `recv` when `wait` is `None` does not implement decision 3.

## Consequences

- An idle studio whose workers are healthy and whose drivers have no deadline blocks the control thread until a command or a bypass. The four wakes a second from `has_worker()` stop. The audio cadence and the render cadence do not. This ADR does not stop those threads.
- A bypass reaches `service()` on the next wake of the control thread, not within 250 ms. The counter is what `service()` reads. The load immediately before `park` (decision 3) is what keeps a bypass that lands after that `service()` from being slept through. A command still causes a `service()`, so a bypass is also seen then.
- While a swap is in flight or a retired endpoint remains, the 250 ms cap stays. Replacing that cap with an unpark when a retired schedule is delivered is follow-up work, not this decision.
- During a recorded fault the wait is `next_due`, not a 250 ms poll. A permanent fault with no scheduled retry does not wake the thread.
- `docs/specs/engine.md` invariant 1 matches this decision. No thread-inventory entry named this 250 ms poll. Tests: a parked control thread wakes after a bypass without a command (`a_bypass_wakes_the_bound_control_thread`), a bypass during a channel wait stays visible on the counter (`a_bypass_during_a_channel_wait_stays_visible`), and a healthy running worker may return `wait == None` (`a_bypassed_node_restarts_through_the_control_loop`). The unpark sits on the tick thread's failure branch, so a hot-path review still has to be verified by someone other than the author (P15). The cost is the one above: no unpark on a healthy tick, one unpark per bypass. Do not claim a faster frame.
- When this ADR is Accepted, set ADR-0027's status line to record that decision 6 is superseded in that part. Do not do that while this ADR is Proposed.

## Alternatives considered

- **Keep the 250 ms poll** (ADR-0027 decision 6 as written). Correct, and it is what the code does today. It taxes every idle studio that has a worker. The owner rejected it for this change on 2026-11-19.
- **Drop the cap and do not wake.** The next command would notice the bypass. A node that fails with nobody editing stays down, which breaks ADR-0024. Rejected.
- **Send a command on the control channel from the worker.** `std::sync::mpsc::send` can allocate, and the worker must not. A bounded `try_send` needs a receive the control thread already waits on, which `recv` on a different channel is not, and `std` has no `select`. Rejected in favour of `unpark`, which allocates nothing and adds no crate.
- **An `eventfd` or a reactor.** OS-specific and a new dependency in the engine layer. Rejected.
- **Unpark on every failed tick, before the bypass.** The counter moves only when the node is actually bypassed. Waking earlier would run `service()` before there is anything to collect. Rejected.

## Review

Reviewer: independent AI session
Date: 2026-11-19
Verdict: approve
Concerns:
1. The bypass unpark and `mpsc` share one park token, and the studio sleeps on a stale `wait` -> resolved by decision 3. The slept `wait` is the result of a `service()` that ran after the last settle in the round, so a later `apply` / `collect_timeout` (including one that returns on `SwapTimeout` and leaves a swap in flight) is not slept on. The loop loads the counter or flag and only then parks, and no park, including a channel receive, runs between that load and the park. A bypass in that gap is one sticky token, so the park returns even though the load and the park are not one atomic step. A bypass during that last `service()` is either before its counter read, which is after every settle inside `service()`, so the returned `wait` includes it, or after that read, where this thread does not park again before its own `park`. The `EventSink` must not park. Every enqueue unparks through one helper per channel, and a bare `send` does not wake a `park`. Context now states the shared token. Consequences require the `collect_timeout` test and the test for a bypass after `wait` was sampled.
2. Binding once, and trusting the next `service` when the cell is empty, loses a bypass -> resolved by decision 1. The worker does a `SeqCst` fence after the increment and before `OnceLock::get`. The sleeper does a `SeqCst` fence after the bind and before the load that decides whether to sleep (`restart_due`, and the load immediately before `park`). `get` is an acquire load and `set` publishes with an acq-rel swap; neither is `SeqCst`, and neither needs to be. Both are atomic accesses to the cell, which is the coherence order those fences use. If that load misses the increment, the worker has not yet passed its fence, so the cell read still sees the bind and it unparks. The other way around: a worker that already observed an empty cell has passed its fence, so the load observes the increment and `wait` is not `None`. A skipped unpark is not slept through.
3. Idle studio still polls at 250 ms after `has_worker` is dropped -> resolved: it does not. The cap that remains is `in_flight`, a dirty part, a waiting move, or a retiring endpoint. Decision 4 also drops the `has_faults` term. On a settled healthy studio those are empty: the compositor, mixer, and meter workers exist, `next_due` is `None`, and nothing is in flight (`Engine::service` as written). `Studio::service` forwards that wait, and `round` blocks on the message channel when the engine wait is absent and no driver arms one. The four wakes a second from `has_worker` stop. Decision 3 closes the stale-wait window that used to bring them back.
4. A sticky unpark spins for a long back-off -> resolved. One `unpark` is one token. `park_timeout(next_due)` returns once, and the next park waits out the back-off. `process_all` skips a node once `health.bypassed` is set, so each `fetch_add` runs once per bypass, not on later ticks. A healthy tick does not unpark. Decision 3’s one extra wake is the whole effect.
5. A fault with no deadline, or an in-flight swap, sticks under the wait rules -> resolved for the rules themselves. A permanent fault or a fault that gave up stores `retry_at: None`. `gate` is `Closed(None)`, `next_deadline` skips it, and `next_due` is `None` once `restart_due` is false. The thread sleeps until a command (`retry`) or another bypass. ADR-0024 decision 6 already leaves that node for the user; the `Failed` event was emitted by the `service` that recorded it. While a swap is in flight, a part is dirty, a move is waiting, or an endpoint is retiring, `service` still caps `wait` by `control_interval` and collects on that wake. The cap is a maximum: `restart_due` makes `next_due` zero, so the loop runs again immediately, as it does today. A bypass not yet collected keeps `restart_due` via the counter. These rules do not strand the work. An empty cell does not lose that wake: decision 1's fences cover it.
6. Layering, the plugin ABI, and the deferred retired-schedule unpark -> resolved. `rbs-graph` does not depend on `rbs-engine`. Passing `Arc<OnceLock<Thread>>` into the executor keeps that direction. No new crate. The plugin surface is the versioned WIT world; `Executor` is outside it, so decision 5 holds. `Serviced.wait` for a healthy running worker changes meaning; the crate is pre-1.0 and the ADR says so. Callers that already poll (the CLI sleeps at most 50 ms) still observe a bypass.
   Darwin `Thread::unpark` is an atomic swap and, only when that thread is parked, one semaphore signal. No allocation and no mutex, which meets decision 1 on the failure branch. The branch is still the tick thread, so the implementation PR’s hot-path review stays required, as Consequences says.
   Unparking when a retired schedule is delivered stays follow-up. A successful `try_send` is not the whole cap: `TrySendError::Full` keeps the schedule in `pending`, and dirty parts, waiting moves, and retiring endpoints are separate signals. The idle-studio poll does not depend on them. Consequences already defers the work. Doing nothing leaves the idle 4 Hz wake. Putting the `has_worker` cap back and returning the loops to `recv` reverses the decision.
