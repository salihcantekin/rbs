# ADR-0061: Built-in video filters: one filter node behind a filter type trait, settings through parameter channels, and the Properties tabs

- Status: Proposed
- Date: 2026-11-07
- Deciders: Salih (owner)
- Builds on: ADR-0053 (item style and video filter chains, decisions 6 to 10), ADR-0013 (zero cost when unused), ADR-0020 (node contract and schedule swap), ADR-0023 (parameter channels), ADR-0024 (restart with back-off), ADR-0044 (control API), ADR-0051 (user data documents), ADR-0052 (API parity), ADR-0059 (source audio)

## Context

ADR-0053 decided that video filters are a per-source chain of GPU nodes of kind `VideoFilter` in a new crate `rbs-filters`, specified in `docs/specs/video-filters.md` before any code, that a filter's settings change through its parameter channel without rebuilding its node, and that the control API gains `filter.*` methods. It left open how a filter type is defined, how a filter node learns its input's size without allocating in `process`, how the settings reach the node, and where the user edits filters.

What exists today (checked in the code on 2026-11-07, `main` at e577560):

- The scene model has `Source::filters: Vec<Filter>` (`id`, `type_id`, `enabled`, `settings`) and the edits `add_filter`, `remove_filter`, `set_filter_enabled`, `move_filter`. There is no edit for a filter's settings. The scene collection document (format 3) already saves `filters = [{ id, type, enabled, settings }]`.
- The binder creates a node for each filter whose type is installed, links the enabled ones in order between the source and every compositor, and keeps disabled ones in the graph but out of the schedule (Standby, P13). It keeps a filter's node while the filter exists; a settings change is not noticed.
- No filter node type exists, `rbs_sources::SourceTypes::node_types` installs none, and `rbs_record::Studio` makes instances only for source nodes: a filter in a collection is reported as `UnknownFilterType` and skipped.
- `rbs_gpu`'s pooled textures carry a sampled bind group for the compositor's sampled-texture layout, but both are `pub(crate)`.
- The Properties panel shows one long column: name, sound, position and size, crop, shape and border. The design the owner picked (mockup E, ADR-0049) shows a segmented control at the top of Properties with three tabs: Transform, Filters and Audio. The UI design system says a feature that grows (filter chains) gets its own panel and Properties shows a one-line summary.
- The per-source audio sync offset (ADR-0037) exists in the engine and the CLI (`--mic-offset`), but not in the scene model, so the app cannot set or save it.

Forces: P4 (no readback), P6 (no allocation, blocking or locks in `process`), P13 and rule 10 (an unused filter costs nothing; no per-frame "is it enabled" test), P15 (`process` of a built-in node is a hot path: numbers and the owner's sign-off), U4 (undo, one step per user action), ADR-0052's API parity, ADR-0051 decision 6 (a document change older builds cannot read needs a new format).

## Decision

1. **A filter type is a trait; one node runs any filter type.** `rbs-filters` defines the object-safe trait `FilterType` (spec `video-filters.md`): a type id (`org.rbs.filter.<name>`), an English display name, a static list of fields (the settings schema: key, label, kind and range or default), the passes (WGSL fragment shaders and the scale of each pass's target, full or half size) and a pure function that turns validated values and the input size into each pass's uniform block. `FilterNode` is the one `Node<GpuRuntime>` of kind `VideoFilter` (input `in`, output `out`, both video) and runs any `FilterType` given as `Arc<dyn FilterType>`. A new filter, a plugin filter or a test double implements the trait; the node, the binder and the app do not change. A conformance suite in the crate (`rbs_filters::conformance`) runs against every `FilterType` and the built-in catalogue passes it. `rbs-filters` depends on `rbs-core`, `rbs-graph`, `rbs-gpu`, `wgpu` and `bytemuck`; never on adapters or `rbs-scene` (the conversion from scene settings lives in `rbs-sources`, as `layer_style` does for item styles).
2. **Settings are validated values, never discovered in `process`.** `FilterType::fields` is the schema the app and the control API both use. `Values::from_pairs(type, pairs)` checks every key and value against it (unknown key, wrong kind, out of range, non-finite: refused with a typed `FilterError`) and fills missing keys with their defaults. Numbers are stored as `SettingValue::Float` (or `Int`) and colours as `SettingValue::Text("#rrggbb" | "#rrggbbaa")` in the scene model, so the scene document needs no new format for filters. An edit with values the type refuses is refused before it reaches the model (ADR-0053 decision 7).
3. **Settings reach the node through its parameter channel.** The model gains `SceneCollection::set_filter_settings(source, filter, settings) -> Undo` (one undo step, through the existing source record, `audio` untouched). The binder keeps a copy of each bound filter's settings and reports a filter whose node it kept but whose settings changed in `BindReport::changed_filters: Vec<(FilterId, NodeId)>`; it never rebuilds the node for it. `rbs_record::Studio` keeps the `ParamSender<FilterParams>` of each filter instance and sends the new values on `update`. A slider drag must not make a step per frame: while dragging, the host sends values through `Studio::preview_filter(filter, values)`, which only sends to the node, and the release commits one `set_filter_settings` (U4); the UI sends at most one value per frame of its event loop.
4. **Rendering contract.** Each filter renders into textures of its input's size: `TextureDesc::canvas(w, h)` (`Rgba16Float`, linear light, premultiplied alpha), a ring of three output textures and, for multi-pass types, intermediates at the pass's scale. It samples its input like the compositor does (sRGB-encoded inputs decoded, premultiplied kept) and publishes frames with the input's timestamp and `ColorSpace::LINEAR_BT709`. Filters that work on perceived values (colour correction, keying) un-premultiply, encode to sRGB in the shader, work there, and decode back. Pipelines, samplers and uniform buffers are made in `prepare`; textures are acquired once in `warm` and released to the pool after each publish exactly as the compositor does with its canvas ring; `process` writes the uniform buffer only when the values or the input size changed, records the passes and submits. No readback (P4), no allocation (P6), checked by an allocation-counting test.
5. **Input size changes go through the restart path (ADR-0024), never through the input.** The node's warm size lives in a shared `FilterStats` (atomics, read on any thread). If a frame arrives at another size than the warmed one (the first frame when the size was not known, or a camera that switched format), `process` sets its output to nothing, stores the new size in `FilterStats`, and returns `NodeError::Backend(INPUT_RESIZED)`. The executor bypasses the node after its failure limit; the controller releases it and prepares and warms it again after the back-off, and `warm` acquires textures of the new size. Until then the compositor skips the layer (P7); the unfiltered input is never shown, because the node only ever publishes its own textures (ADR-0053 decision 6). A composition root that knows the reason (`FilterStats::resized`) calls `Engine::retry` at once so the gap is one control-loop round rather than the back-off, and does not report it as a failure to the user. When the studio adds a filter to a source whose picture size it already knows (`picture_size` of the capture node, ADR-0058), it creates the node with that size, so adding a filter while a source runs shows no gap. Textures of the old size go back to the pool on `release` and are reused or dropped by `TexturePool::trim`; while the node re-warms, both sizes may be held for one round.
6. **First catalogue.** Colour correction (`org.rbs.filter.color-correction`: brightness, contrast, saturation, gamma, hue), chroma key (`org.rbs.filter.chroma-key`: key colour, similarity, smoothness, spill reduction), blur (`org.rbs.filter.blur`: radius in source pixels; a separable Gaussian whose first pass downsamples to half size and whose second pass upsamples, so a radius up to 64 pixels costs two passes) and sharpen (`org.rbs.filter.sharpen`: amount). Each is one `FilterType`, one or two full-frame passes; fusing passes is a later decision on numbers (ADR-0053 decision 8). Colour key, LUT and image mask follow (they need resources sent through the channel as shared handles); the drop shadow is an item style drawn by the compositor (ADR-0053 decision 5), not a filter.
7. **Zero cost when unused.** A source without filters has no filter node and nothing changes for it. A disabled filter's node stays in the graph out of the schedule: no instance, no textures, no pipeline (P13, ADR-0013). Installing `rbs-filters` registers node descriptors only; pipelines are created in `prepare` of an instance. The compositor is unchanged.
8. **The studio makes filter instances.** `SourceTypes::node_types` installs the catalogue's descriptors. `rbs_record::Studio::reconcile` treats filter nodes as it treats source nodes: an entry per created filter, an instance (`FilterNode`) in the render partition for each scheduled one, instances taken back when retired. A filter whose type the catalogue does not have stays a binder problem (`UnknownFilterType`), shown to the user, and its source is drawn without it.
9. **Properties gets the three tabs of the design; filters are edited in its Filters tab.** The Properties panel shows a `SegmentedControl` with Transform, Filters and Audio for the selected source (the last tab used is remembered per window). Transform holds the name, position and size, crop, and shape and border (what is there today, minus sound). Filters holds the selected source's filter chain: one row per filter (enable switch, name, move up and down, remove), an Add filter menu listing the catalogue, and the fields of the selected filter under the list, generated from `FilterType::fields` (sliders with their value for numbers, the colour picker for colours), so new filter types need no UI code. Audio holds volume and mute (ADR-0059) and the sync offset. A source without a picture shows no Transform or Filters tab; one without sound shows no Audio tab. This amends the UI design system's rule that a growing feature gets its own panel: the Filters tab is the one place filters are edited, and a separate `rbs.filters` panel comes only if the tab outgrows one screen (the rule's own threshold). Each confirmed change is one undo step: adding, removing, moving, enabling or disabling a filter, and each slider release or typed value.
10. **Sync offset joins the source's audio.** `SourceAudio` gains `sync_offset_ms: i32` in `-200..=200` (the input's default limit, `rbs_sources::DEFAULT_MAX_AUDIO_OFFSET`); positive delays the sound, negative advances it. It follows ADR-0059 decision 2: one value per source, changed by `set_source_sync_offset` through the `SetSourceAudio` record, a live control that the app does not put on the undo stack, ignored by the binder, sent to a running input through its existing offset channel (`Studio::set_mix`). `StudioSettings::audio_offsets` (the CLI's flags) still wins for the sources it names. The scene collection document becomes format 4 (`sync_offset_ms` on the source when not 0; format 3 bodies load unchanged), for the reason ADR-0059 gives.
11. **Control API 1.7.** `filter.types` (`read`) lists the catalogue with each type's fields. `source.list` and `source.changed` rows carry the source's `filters` (`id`, `type`, `enabled`, `settings`) and `sync_offset_ms`. New `control` methods, each one undo step on the shared stack, publishing `source.changed`: `filter.add {source, type, settings?}` (answers `{filter}`), `filter.remove {filter}`, `filter.move {filter, index}`, `filter.set_enabled {filter, enabled}`, `filter.set_settings {filter, settings}` (a patch: the given keys replace, the others stay; the result is validated as a whole). `source.set_sync_offset {source, offset_ms}` is live and not undoable, like `source.set_volume`. Refusals: `not_found` for an unknown source or filter, `invalid_params` for an unknown type, unknown keys, wrong kinds, values out of range, an index past the end, a filter on a sound-only source, or an offset out of range. Effects (ADR-0052 decision 4): the filter methods `edit`, with the on-air check when the source is in the program scene; `filter.types` `read`.

## Consequences

- Filters work in the app, the CLI's scene files and the control API with one definition per filter type; adding a type is one `FilterType` implementation, its conformance run and a catalogue entry.
- `FilterNode::process` is a new hot path (P15): the PR carries a benchmark per filter at 1920x1080 (container software Vulkan numbers, Mac and Windows numbers before the owner signs off), the allocation test and the `hot-path-review` checklist, and waits for the owner's sign-off before merging. `docs/architecture/hot-paths.md` and `.github/CODEOWNERS` list `crates/rbs-filters`.
- `rbs_gpu` makes `PooledTexture::sampled_bind_group` and the context's sampled-texture layout public, so filter pipelines bind pool textures as the compositor does; no other change to `rbs-gpu`.
- A source switching size shows a short gap (one control-loop round with the root's retry) instead of a wrong frame; tested.
- Public contracts that change: scene document format 4 (sync offset), control API 1.7 (additive), `BindReport` (non-exhaustive) gains `changed_filters`, `SourceAudio` (non-exhaustive) gains a field. Spec updates in the same change: `video-filters.md` (new), `scene-model.md`, `user-data.md`, `control-api.md`, `ui-design-system.md`, `scene-sources.md` and `recording.md` where they list node types and instances.
- Follow-ups: colour key, LUT and image mask (resource handles through the channel), looks (ADR-0053 decision 9), fusing per-pixel passes on numbers, a before/after toggle in the Filters tab, filters on nested scenes (needs render-to-texture for scenes), audio filters.

## Alternatives considered

- **One node type per filter** (`ColorCorrectionNode`, `ChromaKeyNode`, ...). Each would repeat the ring, warm, resize and channel logic, the part that is hard to get right on a hot path; the trait keeps that in one tested node and makes a filter a shader plus a schema.
- **Allocate the new size in `process` once, as an accepted exception.** Simple and fast, but breaks P6 on the render thread at a moment (a camera switch while live) when a hitch is visible, and ADR-0053 rules it out.
- **Warm every possible size, or the canvas size, up front.** Memory for sizes never used, and a source larger than the canvas would still need a resize.
- **Pass the input through while resizing.** Reveals what a key or blur hides (ADR-0053 review round 2).
- **Filters in their own panel only** (the design system's rule as written). The design the owner chose puts Filters in the Properties tabs, the tab already keeps Properties short, and editing stays in one place; the separate panel remains the way out if the tab grows beyond a screen.
- **Filter settings as live, not undoable, like volume.** A filter change is an edit of how the scene looks, the kind of change U4 makes undoable; volume and mute are exempt only because an undo must never unmute a microphone (ADR-0059).
- **Sync offset as a source setting.** A settings change replaces the source node, which reopens the device (ADR-0059 alternative).
