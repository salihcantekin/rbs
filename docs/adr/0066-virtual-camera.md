# ADR-0066: Virtual camera on Windows: the program as a camera for meeting apps, off by default

- Status: Accepted (Windows scope)
- Date: 2026-11-07
- Deciders: Salih (owner)
- Builds on: ADR-0003 (ports and adapters), ADR-0013 (zero cost when unused), ADR-0025 (native surface export), ADR-0028 (non-blocking IPC exception), ADR-0031 (adapter support crates), ADR-0038 (graph nodes and the readback exception), ADR-0041 (studio on a running engine), ADR-0047 (several outputs per canvas), ADR-0050 (command registry), ADR-0052 (API parity and effects), ADR-0061 (studio mode)

## Context

The owner wants meeting apps (Google Meet in a browser, Zoom, Teams, FaceTime) to show what RBS produces, and to change what they show live from RBS, without the window-sharing trick: a pop-out window must stay on screen at full size (a minimised window stops being captured, a small one is shared small) and takes a screen of its own. He chose a virtual camera (2026-11-07): RBS appears as one more camera in every app's camera list. It must be off by default, and turning it on must tell the user what it does. A virtual display and a pop-out window are out of scope for now. The roadmap lists the virtual camera under phase 3; the glossary already names it as a kind of output.

The owner has no paid Apple Developer team, which macOS requires for a camera extension, and decided (2026-11-07) that the feature ships on Windows only for now; on Windows a one-time administrator approval when the camera is added is fine with him, as long as using it later asks nothing.

What the platforms offer:

- **macOS 12.3+: CoreMediaIO Camera Extensions.** A system extension (`CMIOExtensionProvider`, one device, streams) embedded in an app bundle in `/Applications`, activated with `OSSystemExtensionRequest` and approved by the user in System Settings; activation can also finish only after a restart. Every app that uses AVFoundation sees the device; the extension runs in its own sandboxed process, started by the system when an app opens the camera. An app feeds it through a *sink stream* of the same device, through the public CoreMediaIO C API (`CMIOStreamCopyBufferQueue`, `CMIODeviceStartStream`); IOSurface-backed sample buffers cross the process boundary without a pixel copy. Opening the device is camera access, so the feeding app needs the user's camera permission (TCC, `NSCameraUsageDescription`). Loading a system extension needs a Developer ID (or development) signature with the `com.apple.developer.system-extension.install` entitlement, which needs a paid Apple Developer team. The older DAL plug-ins are deprecated and refused by current macOS apps.
- **Windows 11: `MFCreateVirtualCamera`** (Media Foundation, build 22000+). The app registers a camera backed by a COM media source (a DLL); the Windows Camera Frame Server service loads that DLL in its own process (session 0, LocalService) and every Media Foundation and DirectShow camera app sees the camera. The DLL's class must be registered machine-wide once (administrator rights); creating and removing the camera itself does not need them. The source runs in another session, so frames reach it through a named shared-memory section that the source creates in the `Global\` namespace (creating `Global\` objects needs a privilege the user's process does not have; opening one with the right access does not). A crash in the source takes Frame Server down, and with it every camera of every app until the service restarts.
- **The consuming app picks the format** from the formats the source lists, and the source is installed once and runs before RBS sends anything.
- **Linux:** `v4l2loopback` (a kernel module). Parked: there is no Linux machine (owner, 2026-11-04).

What exists in RBS: the studio composes the program (and in studio mode a preview scene, ADR-0061, only for the UI's picture) on the render partition; ADR-0025's `SurfaceExporter` exports a canvas into IOSurfaces on unified-memory Macs (used by tests only so far); ADR-0038's `YuvDownload` reads NV12 back to system memory without waiting (the P4 exception, Windows), with `DOWNLOAD_BUFFERS` (6) recycled buffers. The YUV converter loads canvas pixels one to one (`textureLoad`), so it cannot scale.

Forces:

- **P13:** off by default; a user who never turns it on pays nothing, and one who turned it on but is not sending pays nothing in RBS.
- **P6, P7:** the render thread never waits for a camera consumer, another process or the OS; a slow or stuck consumer drops camera frames, never program frames, recordings or the stream.
- **P1, P3:** the engine sees a port, not CoreMediaIO or Media Foundation; the node chooses native or system memory from what the adapter declares, not from the platform.
- **P4:** the Windows path inherits ADR-0038's readback exception until a native path exists.
- **Owner's settings rule (2026-11-03):** what affects the picture (size, frame rate) is a user setting.
- **Privacy and trust:** a machine-wide camera outlives RBS's process; the user must know what is installed, how to remove it, and when RBS is sending. Code RBS puts into a Windows service must not widen what a user-level process can do, and must not take the user's real cameras down.

## Decision

1. **A new port, `rbs-vcam`** (Ports layer: depends on `rbs-core` only, no `unsafe`). A `VirtualCameraFactory` (registered in the adapter registry like other ports) reports the camera's state (`Unsupported { reason }`, `NotInstalled`, `NeedsUpdate { reason }`, `Installed`; macOS states come with the macOS ADR), installs and uninstalls it (`install`, `uninstall`: may show OS prompts and block, so they run on the control thread, never the UI thread), changes the format the camera announces (`set_format`), and opens a `VirtualCameraSession` for a `VirtualCameraConfig` (built with `VirtualCameraConfig::new`). A session takes frames with `send(frame)`, which never waits (decision 3). The adapter declares capabilities: `vcam.input.memory` (`system`; `metal` and native kinds for later adapters), `vcam.input.format` (`nv12`), `vcam.max_size`, `vcam.rates`, and `vcam.persistent` (the camera stays in the OS camera list while RBS is not sending). The crate holds the conformance suite. All of `rbs-vcam` is new and additive (semver: new crate, 0.x). Contract: [virtual camera spec](../specs/virtual-camera.md).
2. **A shared frame ring, `rbs-vcam-ring`**: a standalone crate that depends on `std` only (not even `rbs-core`), so the service DLL pulls in nothing else; a marked low-level module, every `unsafe` block with a `// SAFETY:` comment; no OS or vendor code. It is classed with the adapter support crates (ADR-0031) although one adapter uses it today, because it holds no vendor code and both sides of the process boundary (the adapter and its companion DLL) must share one layout; a later adapter with a consumer in another process (a `v4l2loopback` helper, for example) reuses it. It lays a header and three slots over a mapped byte slice, with slot states, sequence numbers, a writer heartbeat, a reader heartbeat and a generation in atomics. The writer never waits; the reader never sees a slot while it is written; a slot left `Reading` by a reader whose heartbeat is older than 1 s is taken back by the writer; the creator of the section writes a new generation, and a writer that sees the generation change starts over. Heartbeats are milliseconds of a system-wide monotonic clock that the caller passes in (`now_ms`; the adapter and DLL read `GetTickCount64`, tests pass their own), so the crate reads no clock and its tests are deterministic. **The reader never trusts the shared header:** it keeps the layout (size, stride, slot count, offsets) it computed itself from the format it announced, bounds every index by its own values, and treats a header that disagrees as "no frames" (the still picture). The header carries a layout version; a mismatch on either side means "no frames", and the app reports `NeedsUpdate`. Property tests and a fuzz target for the reader live in the crate.
3. **The hand-off.** The session holds three fixed slots, each a state word (`Empty`, `Full(seq)`, `Taken`) and room for one frame. Before any GPU work for a camera frame the node reserves a slot (`session.reserve()`, a compare-and-swap `Empty` -> `Reserved` returning a token); when none is free, the camera frame is skipped before conversion (counted as `consumer_busy`). A readback in flight keeps its token, so conversions in flight never compete for one slot; a failed readback drops its token and frees the slot. When the frame is ready, `send(token, frame)` fills the slot, marks it `Full(seq)` and rings the sender thread's doorbell: one non-blocking wake per camera frame, an accepted exception to "no system calls on hot paths" for the same reason as ADR-0028's non-blocking send. The sender thread takes the `Full` slot with the highest sequence number and drops every older `Full` slot itself (counted as `replaced`), so frames are only ever dropped on the sender thread, except a frame `send` refuses for breaking the config, which the node drops (a system frame: its buffer is recycled, no lease is held). The node's `YuvDownload` is created with enough buffers for the render slot, the three session slots and the frame the sender copies from (readbacks in flight hold reserved slots, so they are within this count) (a new constructor taking a buffer count; `DOWNLOAD_BUFFERS` stays the default), so recycling never falls back to allocating.
4. **A virtual camera node** (`org.rbs.virtual-camera`, kind `Output`, in `rbs-nodes`, on the `RENDER` partition, one input `canvas`). Each tick it takes the newest canvas frame only when the camera's cadence (`rbs_core::timing`, camera rate from canvas rate) says a camera frame is due, converts it to NV12 at the camera size, and sends it:
   - **Scaling** is folded into the YUV conversion: a sampler-based variant of `YuvConverter` (linear filtering, aspect ratio kept with black bars) used when the camera size differs from the canvas; the existing one-to-one path is unchanged for encoders. This and the `YuvDownload` buffer-count constructor change `rbs-gpu`'s hot-path API: both are named in hot-paths.md and the gpu-compositor spec, and both are in the measurement plan (P15: measurements and the owner's sign-off before merge).
   - With `vcam.input.memory = metal` (a later macOS adapter): through an ADR-0025 `SurfaceExporter`; the native frame goes straight to `send` (the adapter is its single consumer; it never travels on a link). Not built until such an adapter exists.
   - With `system`: through a `YuvDownload` (ADR-0038's readback, the same P4 exception and exit criteria, #83). This is two CPU copies per camera frame (staging buffer into the frame buffer on the render thread, frame buffer into a ring slot on the sender thread); a download that writes straight into a ring slot is a follow-up.
   - A full exporter or download ring drops the camera frame, counted; nothing waits. A frame `send` refuses is counted, never an error of the tick. Session failures (consumer gone, OS error) show in the node's stats and the adapter retries; the node is not essential, so the studio and its outputs never stop because of the camera.
5. **The camera shows the program.** What goes out never depends on studio mode (ADR-0061). Sending the studio-mode preview scene to the camera needs the preview compositor without a UI picture, which ADR-0061 decision 2 does not allow; it is left to a later decision that amends ADR-0061 (a picture node separate from the compositor's lifetime, and re-linking the camera to the program in the same apply that retires the preview compositor).
6. **Studio API** (additive, semver minor for `rbs-record`; `StudioSettings` unchanged). `Studio::start_virtual_camera(factory, VirtualCameraSettings) -> Result<(), VcamError>`, `stop_virtual_camera()`, `virtual_camera()` (state and stats). It is not one of the `MAX_OUTPUTS` outputs (ADR-0047): it has no encoder or output partition, and it runs alongside recording and streaming without touching them. `start` opens the session on the control thread, then adds the node with a plain swap. Stopping removes the node with a plain swap; the node comes back through the studio's pending takes (as every removed node does), and the session, whose drop joins the sender thread, is dropped on the control thread, never on `RENDER`. The canvas can change while the camera sends: the camera keeps its size and rate and the new canvas is scaled into it.
7. **Format.** The source announces exactly one format, the one in the user's settings (size, frame rate, NV12), so the app picks what RBS sends and nothing rescales outside RBS. The format is a property of the camera (`IMFVirtualCamera::AddProperty`), which the source reads when Frame Server activates it. `set_format` removes and creates the camera again with the same friendly name, source class and properties other than the format (no administrator rights); the hardware test checks that meeting apps keep the camera they picked (same symbolic link). If they do not, the setting says "Meeting apps need to pick the camera again" after a change. A format change applies when no app reads the camera; while one does, the setting says "Applies when no app is using the camera" and the session counts `format_pending`. RBS sends at the announced rate, or at the canvas rate when that is lower; the source repeats the last frame to keep the announced rate. A frame whose size differs from what the source announced is not shown: the source shows the still picture.
8. **macOS later, behind the same port.** No macOS adapter is built now (owner, 2026-11-07: no Apple Developer team). On macOS `rbs-app` registers no virtual camera factory, so Settings › Virtual camera says "Not available on macOS yet" and nothing else of the feature exists there. A later macOS adapter (a CoreMediaIO Camera Extension fed through its sink stream, native IOSurface frames, an `RBS.app` bundle with a signing team) needs its own ADR; this review's findings for it are kept in the Review below so they are not lost.
9. **Windows adapter: `rbs-vcam-mf`** (adapter crate, `windows` crate) and **the media source: `rbs-vcam-mf-source`** (a `cdylib`, an in-process COM server implementing a Media Foundation media source with one NV12 stream; depends on `rbs-vcam-ring` and `windows` only).
   - **Installation.** RBS is installed per machine for this feature: the DLL lives in `Program Files`, signed, and the machine-wide class registration points only there; a DLL in a user-writable folder is never registered (that would let any user-level process run code as LocalService). The registration is done by a separate elevated step (one UAC prompt), never by the engine process. Creating the camera (`MFCreateVirtualCamera`, software camera source, persistent lifetime, current-user access) and removing it need no elevation; RBS creates it from the user's own, non-elevated process, right after the elevated step, so the camera belongs to the user who added it even when an administrator typed their credentials into the UAC prompt. Turning the setting off removes the camera; the DLL registration stays until RBS is uninstalled or the user picks "Remove completely" in the section (a second UAC prompt), and the dialog says so.
   - **Containment.** Every COM entry point catches panics (`catch_unwind`, the crate builds with `panic = "unwind"`) and returns an `HRESULT`; the source allocates its buffers when a stream starts and nothing per sample; it is reviewed with the `risky-review` skill.
   - **Frames.** The source creates the ring section with `CreateFileMapping`; a section of that name it did not create is used only when its owner is the Frame Server account and its access list is the source's own (a squatted name is never read). The name is `Global\org.rbs.vcam.<user SID>`; the source creates it when an app starts reading, writing a new generation even if RBS still holds the old section open. Its access list grants write access only to the SID that RBS stored as a camera property when it created the camera from the user's non-elevated process (decision 7), so the elevated install step never decides who may write, and each user who added the camera has a section of their own. The adapter's sender thread opens it (retrying at most twice a second while sending and the ring is absent) and copies each NV12 frame into a slot. The source delivers the newest complete slot at the announced rate, repeats it when no new one came, and shows the still picture when the writer heartbeat is older than 1 s.
   - **Updates.** Frame Server keeps a DLL in use locked; an RBS update replaces it when no app reads the camera, and a version mismatch between app and DLL shows as `NeedsUpdate` with the reason, never as wrong pixels.
   - A zero-copy path (a shared D3D texture across sessions) is a follow-up with its own hardware check.
10. **Lifecycle (P13).**
    - **Off** (the default): no adapter call beyond a cheap status probe when Settings › Virtual camera is opened, nothing installed by RBS, no node, no thread.
    - **Turned on** (installed, not sending): the camera exists in Windows, so the user can pick "RBS Virtual Camera" in a meeting app before RBS sends; it shows the still picture, at its own cost in Frame Server's process. RBS holds no session, thread, GPU resource or device handle.
    - **Sending** (Active): the node, its converter, exporter or download, and the adapter's sender thread. Stopping returns RBS to the turned-on state with the threads and GPU resources of before (rule 5).
    - **Turning it off** removes the camera; an app reading it sees the stream end.
11. **Settings and the warning (desktop app).** Settings gets a **Virtual camera** section: a Toggle "Virtual camera" (off by default). Turning it on first shows a dialog that says what happens before anything is installed: RBS adds a camera named "RBS Virtual Camera" that every app on this computer can list; an app you allow to use cameras sees what RBS sends while it sends; Windows asks for administrator approval once, now, and never again while you use the camera; sending costs one more GPU pass and two copies of each camera frame; it is video only (meeting apps keep using your microphone); turning the setting off removes the camera (removing RBS's part from Windows completely asks for administrator approval once more, under "Remove completely"). Buttons: "Add the camera" and Cancel (focused). Then the section shows the state in words (Not added; Update needed; Added; Not available on this computer, with the reason: "Needs Windows 11", "Needs an administrator to add the camera", "Not available on macOS yet"), **Size** (1920 x 1080, 1280 x 720 (default), 640 x 360) and **Frame rate** (15, 24, 30 (default), 60). Kept in the app settings file `vcam.toml` (`format_version = 1`, `enabled`, `width`, `height`, `rate`), not in an output profile: the camera belongs to the computer.
12. **Start and stop.** A registry command `vcam.toggle` ("Start virtual camera" / "Stop virtual camera", icon `camera`; ADR-0050), in the Live controls panel under Record and Go live and in the Controls menu; not in the default toolbar (the user can add it). It is enabled only while the camera is added. While sending, the button and the live indicator say "Virtual camera on" in words (U12, U4: an app may be showing it to other people); stopping asks nothing, because the camera then shows the still picture rather than a frozen frame. Quitting RBS stops sending. RBS never starts sending by itself.
13. **Control API, next minor version** (1.11 if the global sources work ships 1.10 first): `vcam.status` (`read`: state, sending, size, rate, frame counters), `vcam.start`, `vcam.stop` (`control`, effect `live`, so a token without the irreversible-actions permission is refused, ADR-0052), and the topic `vcam.changed`. A start by an API client shows in the app exactly like the button's, and the live indicator names it. Adding and removing the camera and its format stay with the local user, like entering a stream key: they change the computer outside RBS and need OS approval (U20 exception, listed in the control API spec).

## Consequences

- Meeting apps can show RBS's program live; changing scenes in RBS changes what the meeting sees, with one camera frame of latency plus the platform's.
- New crates: `rbs-vcam` (port), `rbs-vcam-ring` (frame ring), `rbs-vcam-test` (in-process test adapter), `rbs-vcam-mf`, `rbs-vcam-mf-source`. The overview's layer table gains them. The companion binaries are not adapters and never depend on the engine.
- macOS has no virtual camera until a paid Apple Developer team exists; the port and node are ready for an adapter.
- Windows needs a per-machine install with one elevated registration; a standard user without administrator rights cannot add the camera, and the setting says so.
- RBS code runs inside a Windows service. Its failure would take every camera down, so the source is kept minimal, panic-free across COM and fuzzed on its only input (the ring).
- A camera that apps read while RBS is sending costs, per camera frame: one scaled NV12 conversion, and on Windows one readback plus two CPU copies (about 1.4 MB each at 1280 x 720). Measured before merge (P15): render worker tick time (p50, p99), late program frames and dropped frames of a recording, and process CPU and GPU, camera off and on, at a 1080p60 canvas with the camera at 720p30 and at 1080p30 on the owner's Windows PC (SC-PC). The converter's existing path and `YuvDownload` with its default buffer count are measured against main to show no change.
- Tests (ADR-0032): port conformance with a stalled test consumer (send returns under a hang guard, allocates nothing after warm-up, a full session skips before conversion, newest frame wins, replaced frames are dropped by the sender, refused configs, threads back to their number after drop); the ring as property tests and a fuzz target (no torn slot, the writer never waits, sequence numbers increase, a stale reader's slot is reclaimed, a new generation resets the writer, a corrupt header gives no frames) plus a two-process smoke test on the Windows and Linux CI runners; the node with the test adapter on `TestClock` (cadence 60 to 30 fps, drops when rings are full, a session error never fails the tick); the studio (start and stop leave outputs untouched; no node or thread while not sending; the session is dropped off `RENDER`). A CI test loads the source DLL in process through its COM class factory, runs a stream start, `RequestSample` against a test writer and stop, and checks for no allocation per sample and that a panic in a COM entry point becomes an `HRESULT`. Hardware tests on Windows 11 with a real meeting app (Meet in Chrome and Edge, the Windows Camera app): the camera listed before sending, the picture live, the still picture after stop and after RBS is killed, a format change keeping the picked camera, Frame Server still serving a real webcam afterwards.
- Specs: new virtual camera spec; io-nodes (the node), gpu-compositor (scaled conversion), recording (Studio), control API, UI design system (Settings section, Live controls, live indicator), overview and hot paths.

## Alternatives considered

- **Pop-out window shared by the meeting app.** Simple, but has the problems the owner named (must stay full size and visible on screen, minimising freezes it). Possible later as a fallback; not chosen now.
- **Virtual display.** Each OS needs a driver (Windows IddCx, macOS private API); out of scope (owner).
- **macOS now.** A CoreMediaIO Camera Extension needs a paid Apple Developer team to be signed; the owner has none and chose Windows only for now. (The DAL plug-ins of older virtual cameras are deprecated and refused by current macOS apps.)
- **DirectShow filter on Windows (OBS's way).** Works without administrator rights per user, but Media Foundation apps (the Windows Camera app, newer Chromium paths) do not see DirectShow filters, and a filter runs inside every consumer process. `MFCreateVirtualCamera` reaches both kinds of app with one source.
- **Session lifetime on Windows** (the camera exists only while RBS runs it). The user could not pick the camera in a meeting app before sending, and macOS behaves the other way. Kept as the fallback if the persistent lifetime fails on hardware.
- **The source lists several formats and scales on the CPU.** Lets the app pick, but costs a CPU scale per frame in another process, outside RBS's measurements. One announced format, chosen by the user, keeps all scaling on RBS's GPU.
- **Preview as a camera picture now.** Needs ADR-0061's preview compositor without a UI and a re-link on leaving studio mode; deferred to its own decision (decision 5).
- **A camera as an encoder output (encode, then decode in the source).** Saves bandwidth nobody needs on one machine and adds encoder latency and cost.
- **Send RGBA frames (reuse the preview publisher).** No change to the converter, but four bytes per pixel instead of 1.5 and a conversion in every consumer; NV12 is what camera consumers expect.
- **A separate scale pass before the converter.** No change to the encoder converter's shader, but an intermediate texture and a second pass per frame; folding the sampler into the converter is one pass.
- **Let the engine process write `Global\` objects.** Needs a privilege standard users lack; the source in the service creates them instead.
- **Start sending when the setting is turned on.** Simpler UI, but the picture would reach other people without a deliberate act each time.

## Review

- 2026-11-07, independent AI session (ADR-0014, `architecture-review` skill; given only the proposal, principles, specs and code). Verdict: changes requested (2 blockers, 5 major, 7 minor). All addressed in this revision:
  1. (blocker) The consuming app, not RBS, picks the format from what the extension or source lists. Resolved: one announced format from the user's settings, handed over with `set_format` (decision 7).
  2. (blocker) `IOSurfaceIsInUse` with a cached `CVPixelBuffer` per surface would read "in use" for ever. Resolved: a `CVPixelBuffer` per send, released after enqueue; reuse when the use count is back at RBS's own baseline; ring of 6 with the reasons; check frequency stated; hardware test and fallback before merge (decision 8).
  3. (major) Windows service security and containment. Resolved: DLL only in `Program Files`, signed; the reader keeps its own layout and bounds every index, fuzzed; `catch_unwind` on every COM entry, no per-sample allocation, minimal dependencies; access list for the installing user's SID only (decisions 2 and 9).
  4. (major) Ring recovery and lifetime. Resolved: reader heartbeat and slot take-back, a generation written by the creator, a named system-wide clock, layout version and `NeedsUpdate` (decisions 2 and 9).
  5. (major) Preview picture conflicts with ADR-0061 decision 2. Resolved by taking it out: the camera shows the program; Preview needs a later decision that amends ADR-0061 (decision 5).
  6. (major) `send` contradictions. Resolved: fixed triple buffer, replaced frames dropped by the sender, the doorbell stated as an exception like ADR-0028, download buffers sized for the frames the sender may hold (decision 3).
  7. (major) Incomplete macOS states. Resolved: `NeedsRestart`, `NeedsPermission`, `Unsupported` for location and signature, deactivation outcomes, install off the UI thread (decisions 1 and 8).
  8. (minor) Intel Macs. `Unsupported` for now; the exporter's first production use is noted (decisions 4 and 8).
  9. (minor) Two CPU copies on Windows. Stated; scaling folded into the converter (decision 4).
  10. (minor) Contract and semver details: `VirtualCameraConfig::new`, `VcamStats` non-exhaustive with an encoded last error (spec), semver stated (decisions 1 and 6), related ADRs added.
  11. (minor) Second UAC prompt, uninstall while in use, rate below the setting. Stated (decisions 7, 9, 10, 11).
  12. (minor) Session drop on stop. Through pending takes; dropped on the control thread (decision 6).
  13. (minor) Testability. Stalled consumer, hang guard, allocation check; two-process ring smoke test (Consequences).
  14. (minor) `unsafe` in a port crate, packaging, remote start. The ring moved to an adapter support crate; packaging gets its own ADR (decision 8); `vcam.start` is `live`, so it needs the irreversible-actions permission, and the app shows a remote start like a local one (decision 13).
- 2026-11-07, after the first round: the owner took macOS out of scope (no Apple Developer team). Decisions for macOS (findings 2 and 7, and 8) were removed from this ADR and are kept here for the later macOS ADR.
- 2026-11-07, re-check by the same independent session: findings 3, 4, 5, 7-14 resolved; 1, 2 and 6 partly; new findings, and what changed:
  1. (major) macOS `set_format` through app-group preferences may not reach an extension running as `_cmiodalassistants`. Moot: macOS is out of scope (owner, 2026-11-07); kept for the later macOS ADR: pass the format as a custom CMIO device or stream property.
  2. (major) Windows `set_format` recreating the camera may change its id and the section name. Resolved: same name, class and properties; the section is named by the user's SID, not the camera; the hardware test checks the picked camera survives, and the UI says so if it does not (decision 7).
  3. (major) The SID from the elevated step can be the wrong user under over-the-shoulder UAC. Resolved: the camera is created from the user's non-elevated process and carries the user's SID as a property; the source uses it (decision 9).
  4. (major) `IOSurfaceGetUseCount` is process-local. Moot for now (macOS out of scope); kept for the later macOS ADR: use `IOSurfaceIsInUse` with no own use held, or the sink queue's pixel buffer pool plus a blit, gated by a hardware test.
  5. (minor) A triple buffer returns replaced frames to the producer. Resolved: three state-tagged slots; the node skips a camera frame before conversion when no slot is empty; only the sender drops replaced frames (decision 3).
  6. (minor) `rbs-vcam-ring`'s dependencies and fit with ADR-0031. Resolved: `std` only, reason stated (decision 2).
  7. (minor) `rbs-gpu` hot-path API changes spread across the ADR. Resolved: both named, in hot-paths.md, the gpu-compositor spec and the measurement plan (decision 4, Consequences).
  8. (minor) The still picture on a size mismatch missing from the spec. Resolved in the spec (ring and stats).
- 2026-11-07, second re-check by the same session: verdict changes requested, minor only; all fixed in this revision:
  1. (minor) A readback that arrives ticks later could find its checked slot taken. Fixed: `reserve()` takes a slot by compare-and-swap before the GPU work; `send` fills it and cannot fail for lack of room; a dropped token frees the slot (decision 3, spec).
  2. (minor) `rbs-vcam-ring` was said to use `std` only but named `GetTickCount64`. Fixed: callers pass `now_ms` (decision 2).
  3. (minor) macOS states, errors, the `metal` memory kind and the native-frame invariant left in a Windows-only contract. Removed; they come with the macOS ADR (non-exhaustive enums).
  4. (minor) The predictable section name could be squatted by a holder of the global-object privilege. Fixed: an existing section is used only with the expected owner and access list (decision 9, spec).
  5. (minor) The source DLL was tested on hardware only. Added an in-process COM test on the Windows CI runner (Consequences, spec).
