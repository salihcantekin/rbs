# ADR-0066: Virtual camera: the program as a camera for meeting apps, off by default

- Status: Proposed
- Date: 2026-11-07
- Deciders: Salih (owner)
- Builds on: ADR-0003 (ports and adapters), ADR-0013 (zero cost when unused), ADR-0025 (native surface export), ADR-0038 (graph nodes and the readback exception), ADR-0041 (studio on a running engine), ADR-0047 (several outputs per canvas), ADR-0052 (API parity and effects), ADR-0061 (studio mode)

## Context

The owner wants meeting apps (Google Meet in a browser, Zoom, Teams, FaceTime) to show what RBS produces, and to change what they show live from RBS, without the window-sharing trick: a pop-out window must stay on screen at full size (a minimised window stops being captured, a small one is shared small) and takes a screen of its own. He chose a virtual camera (2026-11-07): RBS appears as one more camera in every app's camera list. It must be off by default, and turning it on must tell the user what it does. A virtual display and a pop-out window are out of scope for now. The roadmap lists the virtual camera under phase 3; the glossary already names it as a kind of output.

What the platforms offer:

- **macOS 12.3+: CoreMediaIO Camera Extensions.** A system extension (`CMIOExtensionProvider`, one device, streams) embedded in an app bundle, activated with `OSSystemExtensionRequest` and approved by the user in System Settings. Every app that uses AVFoundation sees the device; the extension runs in its own sandboxed process, started by the system when an app opens the camera. An app feeds it through a *sink stream* of the same device, through the public CoreMediaIO C API (`CMIOStreamCopyBufferQueue`, `CMIODeviceStartStream`); IOSurface-backed sample buffers cross the process boundary without a pixel copy. Loading a system extension needs a Developer ID (or development) signature with the `com.apple.developer.system-extension.install` entitlement, which needs a paid Apple Developer team. The older DAL plug-ins are deprecated and refused by current macOS apps.
- **Windows 11: `MFCreateVirtualCamera`** (Media Foundation, build 22000+). The app registers a camera backed by a COM media source (a DLL); the Windows Camera Frame Server service loads that DLL in its own process (session 0, LocalService) and every Media Foundation and DirectShow camera app sees the camera. The DLL's class must be registered machine-wide once (administrator rights). The source runs in another session, so frames reach it through a named shared-memory section that the source creates in the `Global\` namespace (creating `Global\` objects needs a privilege the user's process does not have; opening one with the right access does not).
- **Linux:** `v4l2loopback` (a kernel module). Parked: there is no Linux machine (owner, 2026-11-04).

What exists in RBS: the studio composes the program (and in studio mode a preview scene, ADR-0061) on the render partition; ADR-0025 exports a canvas into IOSurfaces (macOS, native frames, one consumer); ADR-0038's `YuvDownload` reads NV12 back to system memory without waiting (the P4 exception, Windows). The YUV converter loads canvas pixels one to one (`textureLoad`), so it cannot scale.

Forces:

- **P13:** off by default; a user who never turns it on pays nothing, and one who turned it on but is not sending pays nothing in RBS.
- **P6, P7:** the render thread never waits for a camera consumer, another process or the OS; a slow or stuck consumer drops camera frames, never program frames, recordings or the stream.
- **P1, P3:** the engine sees a port, not CoreMediaIO or Media Foundation; the node chooses native or system memory from what the adapter declares, not from the platform.
- **P4:** zero copy where the platform allows it (macOS); the Windows path inherits the readback exception until a native path exists.
- **Owner's settings rule (2026-11-03):** what affects the picture (size, frame rate, which picture) is a user setting.
- **Privacy and trust:** an installed system extension or a machine-wide camera outlives RBS's process; the user must know what is installed, how to remove it, and when RBS is sending.

## Decision

1. **A new port, `rbs-vcam`** (Ports layer: depends on `rbs-core` only). A `VirtualCameraFactory` (registered in the adapter registry like other ports) reports the camera's installation state (`Unsupported { reason }`, `NotInstalled`, `NeedsApproval`, `Installed`), installs and uninstalls it (`install`, `uninstall`: may show OS prompts and block, so they run on the control thread and never on the UI thread), and opens a `VirtualCameraSession` for a `VirtualCameraConfig` (size, frame rate, pixel format, memory kind). A session takes frames with `send(frame)`, which never blocks: it hands the frame to the adapter's own sender thread through a one-slot mailbox (the newest frame replaces an unsent one, counted as `replaced`) and returns. The adapter declares capabilities: `vcam.input.memory` (`metal`, `system`), `vcam.input.format` (`nv12`), the sizes and rates it can announce (`vcam.max_size`, `vcam.rates`), and `vcam.persistent` (the camera stays in the OS camera list while RBS is not sending). The port crate also holds a shared-memory frame ring (`rbs_vcam::ring`: header, slot states and sequence numbers in atomics over a byte slice, single writer, never waits) used by adapters whose consumer lives in another process, and the conformance suite. Contract: [virtual camera spec](../specs/virtual-camera.md).
2. **A virtual camera node** (`org.rbs.virtual-camera`, kind `Output`, in `rbs-nodes`, on the `RENDER` partition, one input `canvas`). Each tick it takes the newest canvas frame only when the camera's cadence (`rbs_core::timing`, camera rate from canvas rate) says a camera frame is due, scales it to the camera size with the aspect ratio kept (black bars), converts it to NV12, and sends it:
   - with `vcam.input.memory = metal`: through an ADR-0025 `SurfaceExporter` sized for the camera; the exported native frame goes straight to `send` (the adapter is its single consumer; it never travels on a link);
   - with `system`: through a `YuvDownload` (ADR-0038's readback, the same P4 exception and the same exit criteria, #83), the system frame to `send`.
   - A full exporter ring or download ring drops the camera frame, counted; nothing waits. A camera frame the adapter cannot take is counted, never an error of the tick. Session failures (consumer process gone, OS error) are reported in the node's stats and retried by the adapter, never as a failed tick: the node is not essential, so the studio and its outputs never stop because of the camera.
   - **Scaling** is new GPU code: a linear-filtered pass from the canvas into a pool texture at the camera size, before the existing converter, run only when the sizes differ. It and the node's `process` join the hot-path list (P15: measurements and the owner's sign-off before merge).
3. **The camera shows the program by default; the user may pick Preview.** Preview means the studio-mode preview scene (ADR-0061), and the program while studio mode is off, so the camera never goes black when studio mode ends. A camera on Preview is a consumer of the preview compositor, so the studio instantiates it in studio mode even without a UI preview description (ADR-0061 decision 2 counts consumers). Switching the choice while sending re-links the node in one schedule swap; the camera's format does not change.
4. **Studio API.** `Studio::start_virtual_camera(factory, VirtualCameraSettings) -> Result<(), VcamError>`, `stop_virtual_camera()`, `virtual_camera()` (state and stats). It is not one of the `MAX_OUTPUTS` outputs (ADR-0047): it has no encoder or output partition and does not count against them, and it runs alongside recording and streaming without touching them. Stopping removes the node with a plain swap and closes the session on the control thread. The canvas can change while the camera sends: the camera keeps its size and rate, and the new canvas is scaled into it.
5. **Lifecycle (P13).**
   - **Off** (the default): no adapter call beyond a cheap status probe when Settings › Virtual camera is opened, nothing installed by RBS, no node, no thread.
   - **Turned on** (installed, not sending): the OS camera exists (macOS extension activated; Windows camera registered with persistent lifetime where `vcam.persistent` holds), so the user can pick "RBS Virtual Camera" in a meeting app before RBS sends. RBS holds no session, thread, GPU resource or device handle. When an app reads the camera while RBS is not sending, the extension or source shows a still "RBS Virtual Camera is off" picture built into it, at its own cost in its own process.
   - **Sending** (Active): the node, its scaler, exporter or download, and the adapter's sender thread. Stopping returns RBS to the turned-on state with the threads and GPU resources of before (rule 5).
   - **Turning it off** uninstalls: the macOS extension is deactivated, the Windows camera removed. Nothing of the camera stays behind.
6. **macOS adapter: `rbs-vcam-cmio`** (adapter crate, `objc2` bindings) and **the extension: `rbs-vcam-cmio-extension`** (a separate binary crate built into `RBS.app/Contents/Library/SystemExtensions/org.rbs.app.camera.systemextension`). The extension exposes one device "RBS Virtual Camera" with a source stream (what apps read) and a sink stream (what RBS writes); it forwards each sink buffer to the source stream with the client's timing, repeats the last buffer when RBS falls behind and switches to the still picture after 1 s without frames (RBS stopped or crashed). The adapter finds the device by its UID, starts the sink stream and enqueues `CMSampleBuffer`s that wrap the exported IOSurfaces (`CVPixelBufferCreateWithIOSurface`, cached per surface). It holds each frame until `IOSurfaceIsInUse` reports that no process uses its surface any more, so the exporter never rewrites a surface a meeting app still reads; a ring that stays held shows as dropped camera frames. `install` submits the activation request and reports `NeedsApproval` until the user allows it in System Settings. The app gains a bundle (`RBS.app`), signed with a team that may install system extensions; without that signature `status` is `Unsupported` with a reason, and the setting says so.
7. **Windows adapter: `rbs-vcam-mf`** (adapter crate, `windows` crate) and **the media source: `rbs-vcam-mf-source`** (a `cdylib`, an in-process COM server implementing a Media Foundation media source with one NV12 stream). `install` registers the DLL's class machine-wide (one UAC prompt, run elevated as a separate step, never by the engine process) and creates the camera with `MFCreateVirtualCamera` (software camera source, persistent lifetime, current-user access); `uninstall` removes both. The source creates the shared frame ring (`rbs_vcam::ring`) as `Global\org.rbs.vcam.<camera id>` when an app starts reading, with an access list that lets interactive users write it; the adapter's sender thread opens it (retrying at most twice a second while sending and the ring is absent) and copies each NV12 frame into a free slot. The source delivers the newest complete slot at the camera's rate, repeats it when no new one came, and shows the still picture when the ring's writer heartbeat is older than 1 s. A zero-copy path (a shared D3D texture across sessions) is a follow-up with its own hardware check.
8. **Settings and the warning (desktop app).** Settings gets a **Virtual camera** section: a Toggle "Virtual camera" (off by default). Turning it on first shows a dialog that says what happens before anything is installed: RBS adds a camera named "RBS Virtual Camera" that every app on this computer can list; an app you allow to use cameras sees what RBS sends while it sends; macOS asks you to allow the extension in System Settings, Windows asks for administrator approval once; sending costs one more GPU pass per camera frame (and on Windows a copy of each frame); it is video only (meeting apps keep using your microphone); turning the setting off removes the camera. Buttons: "Add the camera" and Cancel (focused). Then the section shows the state in words (Not added, Waiting for your approval in System Settings with an "Open System Settings" button, Added, Not available on this computer with the reason), **Picture** (Program, Preview), **Size** (1920 x 1080, 1280 x 720 (default), 640 x 360), **Frame rate** (15, 24, 30 (default), 60; a rate above the canvas rate is sent at the canvas rate and says so). Changes apply at the next start; Picture applies at once. Kept in the app settings file `vcam.toml` (`format_version = 1`), not in an output profile: the camera belongs to the computer.
9. **Start and stop.** A registry command `vcam.toggle` ("Start virtual camera" / "Stop virtual camera", icon `camera`; ADR-0050), in the Live controls panel under Record and Go live and in the Controls menu; not in the default toolbar (the user can add it). It is enabled only while the camera is added. While sending, the button and the live indicator say "Virtual camera on" in words (U12, U4: an app may be showing it to other people); stopping asks nothing, because the camera then shows the still picture rather than a frozen frame. Quitting RBS stops sending. RBS never starts sending by itself.
10. **Control API, next minor version** (1.11 if the global sources work ships 1.10 first): `vcam.status` (`read`: installed state, sending, picture, size, rate, frame counters), `vcam.start`, `vcam.stop` (`control`, effect `live`: they change what other apps show to other people), `vcam.set_picture {picture}` (`control`, `live`), and the topic `vcam.changed`. Adding and removing the camera (`install`, `uninstall`) stay with the local user, like entering a stream key: they change the computer outside RBS and need OS approval (U20 exception, listed in the control API spec).

## Consequences

- Meeting apps can show RBS's program live; changing scenes in RBS changes what the meeting sees, with one camera frame of latency plus the platform's.
- New crates: `rbs-vcam` (port), `rbs-vcam-test` (in-process test adapter for node and studio tests), `rbs-vcam-cmio`, `rbs-vcam-cmio-extension`, `rbs-vcam-mf`, `rbs-vcam-mf-source`. The overview's layer table gains the port and adapters. The companion binaries (extension, source DLL) are not adapters: they depend on `rbs-vcam` (for the ring and the still picture) and their OS crates only, and never on the engine.
- macOS needs an app bundle and a paid Apple Developer team signature; until the owner has one, the macOS adapter is built and unit tested but cannot run, and the setting says it is not available. Notarization comes with distribution.
- Windows needs one elevated registration; a standard user without administrator rights cannot add the camera, and the setting says so.
- The Frame Server source runs RBS code inside a Windows service process. It must not panic across the COM boundary (P8: every entry point catches and returns `HRESULT`s), allocates its buffers when a stream starts, and is reviewed with the `risky-review` skill.
- The shared ring's access list lets any interactive user of the machine write frames to the camera while an app reads it. Accepted on single-user desktops; a per-user access list is a follow-up if multi-user machines matter.
- A camera that apps read while RBS is sending costs, per camera frame: the scale pass when sizes differ, one NV12 conversion, and on Windows one readback plus one copy into the ring (about 1.4 MB at 1280 x 720). Measured on the owner's Mac and SC-PC before merge (P15): render worker tick time (p50, p99), late program frames and dropped frames of a recording, and process CPU and GPU, camera off and on, at 1080p60 canvas with the camera at 720p30 and at 1080p30.
- Tests (ADR-0032): port conformance (send never blocks, newest-wins mailbox, counters, config refusal, threads back to their number after drop); the ring as property tests (a reader never sees a torn slot, the writer never waits, sequence numbers increase); the node with the test adapter on `TestClock` (cadence from 60 to 30 fps, drops when the ring is full, a session error never fails the tick, no allocation per tick after warm-up); the studio (start and stop leave outputs untouched, Preview follows studio mode, no node or thread while not sending). Hardware tests on both machines with a real meeting app.
- Specs: new virtual camera spec; io-nodes (the node), recording (Studio), control API (next minor), UI design system (Settings section, Live controls, live indicator), overview and hot paths.

## Alternatives considered

- **Pop-out window shared by the meeting app.** Simple, but has the problems the owner named (must stay full size and visible on screen, minimising freezes it). Possible later as a fallback; not chosen now.
- **Virtual display.** Each OS needs a driver (Windows IddCx, macOS private API); out of scope (owner).
- **DAL plug-in on macOS.** Deprecated, and current macOS apps refuse to load DAL plug-ins.
- **DirectShow filter on Windows (OBS's way).** Works without administrator rights per user, but Media Foundation apps (the Windows Camera app, newer Chromium paths) do not see DirectShow filters, and a filter runs inside every consumer process. `MFCreateVirtualCamera` reaches both kinds of app with one source.
- **Session lifetime on Windows** (the camera exists only while RBS runs it). Needs no persistent registration of the camera, but the user could not pick the camera in a meeting app before starting RBS, and macOS behaves the other way. Kept as the fallback if the persistent lifetime fails on hardware.
- **A camera as an encoder output (encode, then decode in the extension).** Saves bandwidth nobody needs on one machine and adds encoder latency and cost.
- **Send RGBA frames (reuse the preview publisher).** No new scaler, but four bytes per pixel instead of 1.5 and a conversion in every consumer; NV12 is what camera consumers expect.
- **Let the engine process write `Global\` objects.** Needs a privilege standard users lack; the source in the service creates them instead.
- **Start sending when the setting is turned on.** Simpler UI, but the picture would reach other people without a deliberate act each time.
