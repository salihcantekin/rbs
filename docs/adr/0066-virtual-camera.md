# ADR-0066: Virtual camera: the program as a camera for meeting apps, off by default

- Status: Proposed
- Date: 2026-11-07
- Deciders: Salih (owner)
- Builds on: ADR-0003 (ports and adapters), ADR-0013 (zero cost when unused), ADR-0025 (native surface export), ADR-0028 (non-blocking IPC exception), ADR-0031 (adapter support crates), ADR-0038 (graph nodes and the readback exception), ADR-0041 (studio on a running engine), ADR-0047 (several outputs per canvas), ADR-0050 (command registry), ADR-0052 (API parity and effects), ADR-0061 (studio mode)

## Context

The owner wants meeting apps (Google Meet in a browser, Zoom, Teams, FaceTime) to show what RBS produces, and to change what they show live from RBS, without the window-sharing trick: a pop-out window must stay on screen at full size (a minimised window stops being captured, a small one is shared small) and takes a screen of its own. He chose a virtual camera (2026-11-07): RBS appears as one more camera in every app's camera list. It must be off by default, and turning it on must tell the user what it does. A virtual display and a pop-out window are out of scope for now. The roadmap lists the virtual camera under phase 3; the glossary already names it as a kind of output.

What the platforms offer:

- **macOS 12.3+: CoreMediaIO Camera Extensions.** A system extension (`CMIOExtensionProvider`, one device, streams) embedded in an app bundle in `/Applications`, activated with `OSSystemExtensionRequest` and approved by the user in System Settings; activation can also finish only after a restart. Every app that uses AVFoundation sees the device; the extension runs in its own sandboxed process, started by the system when an app opens the camera. An app feeds it through a *sink stream* of the same device, through the public CoreMediaIO C API (`CMIOStreamCopyBufferQueue`, `CMIODeviceStartStream`); IOSurface-backed sample buffers cross the process boundary without a pixel copy. Opening the device is camera access, so the feeding app needs the user's camera permission (TCC, `NSCameraUsageDescription`). Loading a system extension needs a Developer ID (or development) signature with the `com.apple.developer.system-extension.install` entitlement, which needs a paid Apple Developer team. The older DAL plug-ins are deprecated and refused by current macOS apps.
- **Windows 11: `MFCreateVirtualCamera`** (Media Foundation, build 22000+). The app registers a camera backed by a COM media source (a DLL); the Windows Camera Frame Server service loads that DLL in its own process (session 0, LocalService) and every Media Foundation and DirectShow camera app sees the camera. The DLL's class must be registered machine-wide once (administrator rights); creating and removing the camera itself does not need them. The source runs in another session, so frames reach it through a named shared-memory section that the source creates in the `Global\` namespace (creating `Global\` objects needs a privilege the user's process does not have; opening one with the right access does not). A crash in the source takes Frame Server down, and with it every camera of every app until the service restarts.
- **In both, the consuming app picks the format** from the formats the source stream lists, and the extension or source is installed once and runs before RBS sends anything.
- **Linux:** `v4l2loopback` (a kernel module). Parked: there is no Linux machine (owner, 2026-11-04).

What exists in RBS: the studio composes the program (and in studio mode a preview scene, ADR-0061, only for the UI's picture) on the render partition; ADR-0025's `SurfaceExporter` exports a canvas into IOSurfaces on unified-memory Macs (used by tests only so far); ADR-0038's `YuvDownload` reads NV12 back to system memory without waiting (the P4 exception, Windows), with `DOWNLOAD_BUFFERS` (6) recycled buffers. The YUV converter loads canvas pixels one to one (`textureLoad`), so it cannot scale.

Forces:

- **P13:** off by default; a user who never turns it on pays nothing, and one who turned it on but is not sending pays nothing in RBS.
- **P6, P7:** the render thread never waits for a camera consumer, another process or the OS; a slow or stuck consumer drops camera frames, never program frames, recordings or the stream.
- **P1, P3:** the engine sees a port, not CoreMediaIO or Media Foundation; the node chooses native or system memory from what the adapter declares, not from the platform.
- **P4:** zero copy where the platform allows it (macOS); the Windows path inherits the readback exception until a native path exists.
- **Owner's settings rule (2026-11-03):** what affects the picture (size, frame rate) is a user setting.
- **Privacy and trust:** an installed system extension or a machine-wide camera outlives RBS's process; the user must know what is installed, how to remove it, and when RBS is sending. Code RBS puts into a Windows service must not widen what a user-level process can do, and must not take the user's real cameras down.

## Decision

1. **A new port, `rbs-vcam`** (Ports layer: depends on `rbs-core` only, no `unsafe`). A `VirtualCameraFactory` (registered in the adapter registry like other ports) reports the camera's state (`Unsupported { reason }`, `NotInstalled`, `NeedsApproval`, `NeedsRestart`, `NeedsPermission`, `NeedsUpdate { reason }`, `Installed`), installs and uninstalls it (`install`, `uninstall`: may show OS prompts and block, so they run on the control thread, never the UI thread), changes the format the camera announces (`set_format`), and opens a `VirtualCameraSession` for a `VirtualCameraConfig` (built with `VirtualCameraConfig::new`). A session takes frames with `send(frame)`, which never waits (decision 3). The adapter declares capabilities: `vcam.input.memory` (`metal`, `system`), `vcam.input.format` (`nv12`), `vcam.max_size`, `vcam.rates`, and `vcam.persistent` (the camera stays in the OS camera list while RBS is not sending). The crate holds the conformance suite. All of `rbs-vcam` is new and additive (semver: new crate, 0.x). Contract: [virtual camera spec](../specs/virtual-camera.md).
2. **A shared frame ring in an adapter support crate, `rbs-vcam-ring`** (ADR-0031; a marked low-level module, every `unsafe` block with a `// SAFETY:` comment; no OS or vendor code). It lays a header and three slots over a mapped byte slice, with slot states, sequence numbers, a writer heartbeat, a reader heartbeat and a generation in atomics. The writer never waits; the reader never sees a slot while it is written; a slot left `Reading` by a reader whose heartbeat is older than 1 s is taken back by the writer; the creator of the section writes a new generation, and a writer that sees the generation change starts over. Heartbeats use a system-wide monotonic clock (`GetTickCount64` on Windows). **The reader never trusts the shared header:** it keeps the layout (size, stride, slot count, offsets) it computed itself from the format it announced, bounds every index by its own values, and treats a header that disagrees as "no frames". The header carries a layout version; a mismatch on either side means "no frames", and the app reports `NeedsUpdate`. Property tests and a fuzz target for the reader live in the crate.
3. **The hand-off.** `send` puts the frame into a fixed triple buffer (pre-allocated slots, one atomic exchange) and rings the sender thread's doorbell: one non-blocking wake per camera frame, an accepted exception to "no system calls on hot paths" for the same reason as ADR-0028's non-blocking send. The sender thread, never the render thread, drops replaced frames (counted as `replaced`) and frames it has delivered. With the sender holding frames, the node's `YuvDownload` is created with enough buffers for the render slot, the triple buffer and the sender's frame (a constructor taking a buffer count; 6 stays the default), so recycling never falls back to allocating.
4. **A virtual camera node** (`org.rbs.virtual-camera`, kind `Output`, in `rbs-nodes`, on the `RENDER` partition, one input `canvas`). Each tick it takes the newest canvas frame only when the camera's cadence (`rbs_core::timing`, camera rate from canvas rate) says a camera frame is due, converts it to NV12 at the camera size, and sends it:
   - **Scaling** is folded into the YUV conversion: a sampler-based variant of `YuvConverter` (linear filtering, aspect ratio kept with black bars) used when the camera size differs from the canvas; the existing one-to-one path is unchanged for encoders. This is a change to a listed hot path (P15: measurements and the owner's sign-off before merge).
   - With `vcam.input.memory = metal`: through an ADR-0025 `SurfaceExporter` sized for the camera (decision 7 says how many surfaces); the native frame goes straight to `send` (the adapter is its single consumer; it never travels on a link). This is the exporter's first production use; hot-paths.md says so.
   - With `system`: through a `YuvDownload` (ADR-0038's readback, the same P4 exception and exit criteria, #83). On Windows this is two CPU copies per camera frame (staging buffer into the frame buffer on the render thread, frame buffer into a ring slot on the sender thread); a download that writes straight into a ring slot is a follow-up.
   - A full exporter or download ring drops the camera frame, counted; nothing waits. A frame `send` refuses is counted, never an error of the tick. Session failures (consumer gone, OS error) show in the node's stats and the adapter retries; the node is not essential, so the studio and its outputs never stop because of the camera.
5. **The camera shows the program.** What goes out never depends on studio mode (ADR-0061). Sending the studio-mode preview scene to the camera needs the preview compositor without a UI picture, which ADR-0061 decision 2 does not allow; it is left to a later decision that amends ADR-0061 (a picture node separate from the compositor's lifetime, and re-linking the camera to the program in the same apply that retires the preview compositor).
6. **Studio API** (additive, semver minor for `rbs-record`; `StudioSettings` unchanged). `Studio::start_virtual_camera(factory, VirtualCameraSettings) -> Result<(), VcamError>`, `stop_virtual_camera()`, `virtual_camera()` (state and stats). It is not one of the `MAX_OUTPUTS` outputs (ADR-0047): it has no encoder or output partition, and it runs alongside recording and streaming without touching them. `start` opens the session on the control thread, then adds the node with a plain swap. Stopping removes the node with a plain swap; the node comes back through the studio's pending takes (as every removed node does), and the session, whose drop joins the sender thread, is dropped on the control thread, never on `RENDER`. The canvas can change while the camera sends: the camera keeps its size and rate and the new canvas is scaled into it.
7. **Format.** The extension or source announces exactly one format, the one in the user's settings (size, frame rate, NV12), so the app picks what RBS sends and nothing rescales outside RBS. `set_format` hands it over: on macOS through the shared app-group preferences that the extension reads (it updates its stream's formats and tells CMIO the property changed); on Windows by removing and creating the camera again with the format as a camera property (no administrator rights). A format change applies when no app reads the camera; while one does, the setting says "Applies when no app is using the camera". RBS sends at the announced rate or at the canvas rate when that is lower; the extension or source repeats the last frame to keep the announced rate. A frame whose size differs from what the reader announced is not shown (the still picture is).
8. **macOS adapter: `rbs-vcam-cmio`** (adapter crate, `objc2` bindings) and **the extension: `rbs-vcam-cmio-extension`** (a separate binary built into `RBS.app/Contents/Library/SystemExtensions/org.rbs.app.camera.systemextension`; it depends on `rbs-vcam` and its OS crates only). The extension exposes one device "RBS Virtual Camera" with a source stream (what apps read) and a sink stream (what RBS writes). It forwards each sink buffer to the source stream, keeps the newest one to repeat it, and switches to a still "RBS Virtual Camera is off" picture after 1 s without frames (RBS stopped or crashed).
   - The adapter finds the device by its UID, starts the sink stream and, for each frame, creates a `CVPixelBuffer` over the exported IOSurface (`CVPixelBufferCreateWithIOSurface`) on the sender thread, wraps it in a `CMSampleBuffer`, enqueues it and releases its own references at once. It keeps the native frame (the exporter's lease) until the surface's use count (`IOSurfaceGetUseCount`) is back at the baseline RBS itself holds (the exporter's Metal aliases, measured when the ring is created), checking on every sender wake and at the camera rate while frames are held. Only then does the exporter write the surface again.
   - Ring size: 6 surfaces (one written, one in the sink queue, one the extension keeps to repeat, up to two held by an app, one spare), within `MAX_EXPORT_SURFACES`. A ring that stays held shows as dropped camera frames, not as memory growth.
   - A hardware test shows a surface coming back after a meeting app has shown it and released it; if use counts turn out not to cross the process boundary, the fallback is buffers from the sink queue's own `CVPixelBufferPool` with one GPU blit per frame, decided on hardware before the adapter merges.
   - `status` reports `Unsupported` for a build that is not signed for system extensions, for an app outside `/Applications` (unless system extension developer mode is on) and, for now, for Macs without unified memory (the exporter's limit; a `system` path for Intel Macs is a follow-up); `NeedsApproval` until the user allows it, `NeedsRestart` when activation completes after a restart, `NeedsPermission` until RBS has camera permission. Deactivation may also ask the user and may complete after a restart; `uninstall` reports it.
   - Packaging (an `RBS.app` bundle, its signing team, entitlements, `NSCameraUsageDescription`, app group, notarization) gets its own ADR before the adapter lands.
9. **Windows adapter: `rbs-vcam-mf`** (adapter crate, `windows` crate) and **the media source: `rbs-vcam-mf-source`** (a `cdylib`, an in-process COM server implementing a Media Foundation media source with one NV12 stream; depends on `rbs-vcam-ring` and `windows` only, as few crates as possible).
   - **Installation.** RBS is installed per machine for this feature: the DLL lives in `Program Files`, signed, and the machine-wide class registration points only there; a DLL in a user-writable folder is never registered (that would let any user-level process run code as LocalService). The registration is done by a separate elevated step (one UAC prompt), never by the engine process. Creating the camera (`MFCreateVirtualCamera`, software camera source, persistent lifetime, current-user access) and removing it need no elevation. Turning the setting off removes the camera; the DLL registration stays until RBS is uninstalled or the user picks "Remove completely" in the section (a second UAC prompt), and the dialog says so.
   - **Containment.** Every COM entry point catches panics (`catch_unwind`, the crate builds with `panic = "unwind"`) and returns an `HRESULT`; the source allocates its buffers when a stream starts and nothing per sample; it is reviewed with the `risky-review` skill.
   - **Frames.** The source creates the ring section `Global\org.rbs.vcam.<camera id>` when an app starts reading, writing a new generation even if RBS still holds the old section open, with an access list that grants write access only to the installing user's SID (stored with the registration at install). The adapter's sender thread opens it (retrying at most twice a second while sending and the ring is absent) and copies each NV12 frame into a slot. The source delivers the newest complete slot at the announced rate, repeats it when no new one came, and shows the still picture when the writer heartbeat is older than 1 s.
   - **Updates.** Frame Server keeps a DLL in use locked; an RBS update replaces it when no app reads the camera, and a version mismatch between app and DLL shows as `NeedsUpdate` with the reason, never as wrong pixels.
   - A zero-copy path (a shared D3D texture across sessions) is a follow-up with its own hardware check.
10. **Lifecycle (P13).**
    - **Off** (the default): no adapter call beyond a cheap status probe when Settings › Virtual camera is opened, nothing installed by RBS, no node, no thread.
    - **Turned on** (installed, not sending): the OS camera exists, so the user can pick "RBS Virtual Camera" in a meeting app before RBS sends; it shows the still picture, at its own cost in the extension's or Frame Server's process. RBS holds no session, thread, GPU resource or device handle.
    - **Sending** (Active): the node, its converter, exporter or download, and the adapter's sender thread. Stopping returns RBS to the turned-on state with the threads and GPU resources of before (rule 5).
    - **Turning it off** removes the camera (macOS: deactivates the extension, possibly after a restart; Windows: removes the camera; an app reading it sees the stream end).
11. **Settings and the warning (desktop app).** Settings gets a **Virtual camera** section: a Toggle "Virtual camera" (off by default). Turning it on first shows a dialog that says what happens before anything is installed: RBS adds a camera named "RBS Virtual Camera" that every app on this computer can list; an app you allow to use cameras sees what RBS sends while it sends; macOS asks you to allow the extension in System Settings and to let RBS use cameras, Windows asks for administrator approval once; sending costs one more GPU pass per camera frame (and on Windows two copies of each frame); it is video only (meeting apps keep using your microphone); turning the setting off removes the camera. Buttons: "Add the camera" and Cancel (focused). Then the section shows the state in words (Not added; Waiting for your approval in System Settings, with "Open System Settings"; Restart the computer to finish; RBS needs permission to use cameras; Update needed; Added; Not available on this computer, with the reason), **Size** (1920 x 1080, 1280 x 720 (default), 640 x 360) and **Frame rate** (15, 24, 30 (default), 60). Kept in the app settings file `vcam.toml` (`format_version = 1`, `enabled`, `width`, `height`, `rate`), not in an output profile: the camera belongs to the computer.
12. **Start and stop.** A registry command `vcam.toggle` ("Start virtual camera" / "Stop virtual camera", icon `camera`; ADR-0050), in the Live controls panel under Record and Go live and in the Controls menu; not in the default toolbar (the user can add it). It is enabled only while the camera is added. While sending, the button and the live indicator say "Virtual camera on" in words (U12, U4: an app may be showing it to other people); stopping asks nothing, because the camera then shows the still picture rather than a frozen frame. Quitting RBS stops sending. RBS never starts sending by itself.
13. **Control API, next minor version** (1.11 if the global sources work ships 1.10 first): `vcam.status` (`read`: state, sending, size, rate, frame counters), `vcam.start`, `vcam.stop` (`control`, effect `live`, so a token without the irreversible-actions permission is refused, ADR-0052), and the topic `vcam.changed`. A start by an API client shows in the app exactly like the button's, and the live indicator names it. Adding and removing the camera and its format stay with the local user, like entering a stream key: they change the computer outside RBS and need OS approval (U20 exception, listed in the control API spec).

## Consequences

- Meeting apps can show RBS's program live; changing scenes in RBS changes what the meeting sees, with one camera frame of latency plus the platform's.
- New crates: `rbs-vcam` (port), `rbs-vcam-ring` (adapter support), `rbs-vcam-test` (in-process test adapter), `rbs-vcam-cmio`, `rbs-vcam-cmio-extension`, `rbs-vcam-mf`, `rbs-vcam-mf-source`. The overview's layer table gains them. The companion binaries are not adapters and never depend on the engine.
- macOS needs an app bundle (own ADR) and a paid Apple Developer team signature; until the owner has one, the macOS adapter is built and unit tested but cannot run, and the setting says it is not available. Intel Macs are not supported at first.
- Windows needs a per-machine install with one elevated registration; a standard user without administrator rights cannot add the camera, and the setting says so.
- RBS code runs inside a Windows service. Its failure would take every camera down, so the source is kept minimal, panic-free across COM and fuzzed on its only input (the ring).
- A camera that apps read while RBS is sending costs, per camera frame: one scaled NV12 conversion, and on Windows one readback plus two CPU copies (about 1.4 MB each at 1280 x 720). Measured on the owner's Mac and SC-PC before merge (P15): render worker tick time (p50, p99), late program frames and dropped frames of a recording, and process CPU and GPU, camera off and on, at a 1080p60 canvas with the camera at 720p30 and at 1080p30. The converter's existing path is measured against main to show no change.
- Tests (ADR-0032): port conformance with a stalled test consumer (send returns under a hang guard, allocates nothing after warm-up, newest frame wins, replaced frames are dropped by the sender, refused configs, threads back to their number after drop); the ring as property tests and a fuzz target (no torn slot, the writer never waits, sequence numbers increase, a stale reader's slot is reclaimed, a new generation resets the writer, a corrupt header gives no frames) plus a two-process smoke test on the Windows and Linux CI runners; the node with the test adapter on `TestClock` (cadence 60 to 30 fps, drops when rings are full, a session error never fails the tick); the studio (start and stop leave outputs untouched; no node or thread while not sending; the session is dropped off `RENDER`). Hardware tests on both machines with a real meeting app.
- Specs: new virtual camera spec; io-nodes (the node), gpu-compositor (scaled conversion), recording (Studio), control API, UI design system (Settings section, Live controls, live indicator), overview and hot paths.

## Alternatives considered

- **Pop-out window shared by the meeting app.** Simple, but has the problems the owner named (must stay full size and visible on screen, minimising freezes it). Possible later as a fallback; not chosen now.
- **Virtual display.** Each OS needs a driver (Windows IddCx, macOS private API); out of scope (owner).
- **DAL plug-in on macOS.** Deprecated, and current macOS apps refuse to load DAL plug-ins.
- **DirectShow filter on Windows (OBS's way).** Works without administrator rights per user, but Media Foundation apps (the Windows Camera app, newer Chromium paths) do not see DirectShow filters, and a filter runs inside every consumer process. `MFCreateVirtualCamera` reaches both kinds of app with one source.
- **Session lifetime on Windows** (the camera exists only while RBS runs it). The user could not pick the camera in a meeting app before sending, and macOS behaves the other way. Kept as the fallback if the persistent lifetime fails on hardware.
- **The extension or source lists several formats and scales on the CPU.** Lets the app pick, but costs a CPU scale per frame in another process, outside RBS's measurements. One announced format, chosen by the user, keeps all scaling on RBS's GPU.
- **Preview as a camera picture now.** Needs ADR-0061's preview compositor without a UI and a re-link on leaving studio mode; deferred to its own decision (decision 5).
- **A camera as an encoder output (encode, then decode in the extension).** Saves bandwidth nobody needs on one machine and adds encoder latency and cost.
- **Send RGBA frames (reuse the preview publisher).** No change to the converter, but four bytes per pixel instead of 1.5 and a conversion in every consumer; NV12 is what camera consumers expect.
- **A separate scale pass before the converter.** No change to the encoder converter's shader, but an intermediate texture and a second pass per frame; folding the sampler into the converter is one pass.
- **Let the engine process write `Global\` objects.** Needs a privilege standard users lack; the source in the service creates them instead.
- **Start sending when the setting is turned on.** Simpler UI, but the picture would reach other people without a deliberate act each time.

## Review

- 2026-11-07, independent AI session (ADR-0014, `architecture-review` skill; given only the proposal, principles, specs and code). Verdict: changes requested (2 blockers, 5 major, 7 minor). All addressed in this revision:
  1. (blocker) The consuming app, not RBS, picks the format from what the extension or source lists. Resolved: one announced format from the user's settings, handed over with `set_format` (decision 7).
  2. (blocker) `IOSurfaceIsInUse` with a cached `CVPixelBuffer` per surface would read "in use" for ever. Resolved: a `CVPixelBuffer` per send, released after enqueue; reuse when the use count is back at RBS's own baseline; ring of 6 with the reasons; check frequency stated; hardware test and fallback before merge (decision 8).
  3. (major) Windows service security and containment. Resolved: DLL only in `Program Files`, signed; the reader keeps its own layout and bounds every index, fuzzed; `catch_unwind` on every COM entry, no per-sample allocation, minimal dependencies; access list for the installing user's SID only (decisions 2 and 9).
  4. (major) Ring recovery and lifetime. Resolved: reader heartbeat and slot take-back, a generation written by the creator, a named system-wide clock, layout version and `NeedsUpdate` (decisions 2 and 9).
  5. (major) Preview picture conflicts with ADR-0061 decision 2. Resolved by taking it out: the camera shows the program; Preview needs a later decision that amends ADR-0061 (decision 5).
  6. (major) `send` contradictions. Resolved: fixed triple buffer, replaced frames dropped by the sender, the doorbell stated as an exception like ADR-0028, download buffers sized for the frames the sender may hold (decision 3).
  7. (major) Incomplete macOS states. Resolved: `NeedsRestart`, `NeedsPermission`, `Unsupported` for location and signature, deactivation outcomes, install off the UI thread (decisions 1 and 8).
  8. (minor) Intel Macs. `Unsupported` for now; the exporter's first production use is noted (decisions 4 and 8).
  9. (minor) Two CPU copies on Windows. Stated; scaling folded into the converter (decision 4).
  10. (minor) Contract and semver details: `VirtualCameraConfig::new`, `VcamStats` non-exhaustive with an encoded last error (spec), semver stated (decisions 1 and 6), related ADRs added.
  11. (minor) Second UAC prompt, uninstall while in use, rate below the setting. Stated (decisions 7, 9, 10, 11).
  12. (minor) Session drop on stop. Through pending takes; dropped on the control thread (decision 6).
  13. (minor) Testability. Stalled consumer, hang guard, allocation check; two-process ring smoke test (Consequences).
  14. (minor) `unsafe` in a port crate, packaging, remote start. The ring moved to an adapter support crate; packaging gets its own ADR (decision 8); `vcam.start` is `live`, so it needs the irreversible-actions permission, and the app shows a remote start like a local one (decision 13).
- Re-check by an independent session: pending.
