# ADR-0137: Context menus and drop-down lists are drawn by RBS; the macOS menu bar stays native

- Status: Proposed
- Date: 2026-11-17
- Deciders: Salih (owner)
- Amends: ADR-0050 decision 4 (context menus are Slint's `ContextMenuArea`), ADR-0054 decision 6 (native menus need no cover), ADR-0094 rule B1 (a short `Select` list is a native menu) and the Select decision of 2026-11-14 (only more than 20 options open `SelectList`); the ui-design-system spec, "Context menus" (toolkit bullet) and "Select"
- Keeps: ADR-0069 decision 4 (the system menu bar on macOS, the RBS menu on Windows and Linux)
- Builds on: ADR-0054 (covers of the native preview), ADR-0094 (overlay layers, keyboard rules E1), ADR-0013 (zero cost when unused), ADR-0115 (UI stop rule)

## Context

RBS has three kinds of menus ([ui-design-system spec](../specs/ui-design-system.md#menus-and-commands)):

- **The menu bar.** On macOS it is the system menu bar, built from the command registry by Slint's `MenuBar`. On Windows and Linux there is none; the RBS menu, drawn with design tokens, takes its place (ADR-0069).
- **Context menus.** `CommandMenu` (`ui/context_menu.slint`) is Slint's `ContextMenuArea`. On macOS and Windows the operating system draws it; on Linux Slint draws it in its widget style. About 30 elements use one: scene and source rows, the preview and program pictures, panel headers, the Mixer, the status bar pickers, the toolbar's Workspace and Add source items, the Add filter button, the projector.
- **Drop-down lists.** A `Select` with up to 20 options opens a native menu; a longer one opens `SelectList`, a layer of the window drawn with tokens (capped height, virtual rows, paging keys).

The native menus follow the operating system's look, not the RBS theme, so the same menu looks different on each platform and never matches Dark, Light or a user theme (rule U6 covers everything else in the window). They cannot show a disabled item's reason (ADR-0050 decision 4; the spec lists it as "Not yet") or shortcuts in context menus. On Windows, the click that closes a system menu reaches the picture as a stray press, which the app filters by the cursor's position (`menu_press`). On 2026-11-17 the owner chose a hybrid: the macOS menu bar stays native (users expect it; shortcuts and accessibility come with it), and every menu inside a window is drawn by RBS. The owner's conditions: menus behave as today's do, open upward near the bottom so they never run off, and close on a click elsewhere.

Constraints:

- A menu drawn in the window cannot leave the window; a native one can use the whole screen.
- The projector's window is shared in video calls; anything drawn in it is shared (ADR-0125).
- The native preview layer is cut out under every layer drawn over it (ADR-0054, at most `MAX_CUTOUTS` = 8 rectangles).
- Nothing may run while no menu is open (P13).
- Slint 1.18 has no public API to give the keyboard focus back to the element that had it, and no menu accessible role.

## Decision

1. **Where each kind of menu comes from.**
   - The macOS menu bar stays Slint's `MenuBar`, drawn by the system. The RBS menu stays as ADR-0069 has it.
   - Every context menu in every RBS window must be drawn by RBS as a layer of the window's `OverlayHost` (`MenuLayer`), from design tokens only, the same on every platform.
   - Every `Select` must open `SelectList`, whatever its number of options; the native short list and the 20-option threshold go away. `SelectList` keeps its rules (height cap `size.select.list-h`, virtual rows, Page Up and Page Down, at least the field's width, the result through `select-owner`/`select-serial`, the focus back to the field).
   - **Exception:** the projector's menu stays native, as `NativeCommandMenu` (Slint's `ContextMenuArea`), because the system draws it outside the shared picture (ADR-0125). The generated slots (`MAX_CONTEXT_ITEMS` of them) stay only for it; the projector menu gains neither reasons nor shortcuts.
2. **One menu layer.** `CommandMenu` keeps its properties (`context`, `target`) and `open(at)`, and gains `open-from(at, wide, above)`: `at` is the anchor's bottom-left corner, `wide` its width and `above` its height, so a menu opened from a button flips over the button, not over the point, and one with no room on the right ends at the button's right edge. A caller that only knows the button's left edge (toolbar callbacks that pass an x) passes a width of 0. Button-opened menus (toolbar, panel headers, status bar pickers, Add filter, Mixer group buttons) call `open-from`; right-clicks call `open`. The Menu key and Shift+F10 on a row open at the row's bottom-left as today (`open`); a menu with no room below then ends there, over the row. Both ask Rust for the rows (`ContextMenus.rows`), convert to window coordinates and open the layer. `CommandMenu` takes no room or input of its own. One drawn menu is open per window. Opening it closes the window's tooltip, info hint, colour popover, `SelectList` and the RBS menu; opening any of those closes the menu.
3. **Rows.** Rust gives each row its kind (command, separator, submenu), title, icon name, bound shortcut (as the RBS menu shows it), registry id, enabled, checkable, checked and the disabled reason (`MenuRow`); a submenu's rows come from `ContextMenus.submenu(index)` of the last menu made. Submenu rows are what the registry gives today (`MenuItem::Choices`: title, id, checked; a group drops its disabled commands, as the spec says); this ADR adds only their icons and bound shortcuts, looked up by id in `rbs-app`, and changes nothing in `rbs-ui`. Disabled rows and reasons inside submenus need a change of `MenuItem` and are left for later. A row is, from left, the icon (a `check` in its place on a picker's current choice), the title (elided), the shortcut in `text.secondary` caption size, then `chevron-right` on a submenu row or, on a checkable command (an on/off setting such as Visible, Locked or Flip), the library `Toggle` switch showing its state, drawn as everywhere else in RBS, with its own theme effects (owner, 2026-11-17). A click on such a row or its switch, or Return or Space on it, runs the command and flips the switch at once, and the menu stays open (when the command runner refuses it, decision 6, the switch keeps its state and the menu closes), so several settings can be changed in one visit; Escape or a click outside closes it. In a submenu, a choice whose registry entry is checkable and not a picker gets a switch too; a picker's choices keep the check. Separators are `border.subtle` lines. Rows are `size.control.md` high; the current row has the selected plate of a `ListRow` on an overlay (`accent.subtle` and an `accent` border; `surface.raised` with the border when disabled), as in the RBS menu. The surface is `MenuSurface` with `space.1` padding, as wide as its longest row within `size.menu.sm` and `size.menu.md`. The theme effects (ADR-0122) do not apply to the menu surface or its rows; the switch is the library `Toggle` and keeps its own.
4. **Disabled reasons.** A disabled row stays reachable by the pointer and keys and does nothing when clicked; a disabled submenu row (an empty group) does not open. When any row of a menu has a reason, the menu has a reason line under its rows (a `border.subtle` line, then one line of `type.caption` in `text.secondary`, elided), which shows the current row's reason, as the RBS menu does; the line keeps its height while the menu is open, so the menu never moves. The reason is also the row's accessible description.
5. **Placement**, one pure Rust function (`menu_layout::place` in `rbs-app`) that Slint calls, unit-tested; all in window coordinates, with `space.1` kept from every window edge:
   - A menu: below the anchor if it fits; else above it if it fits; else on the side with more room, shrunk to that room, scrolling. Horizontally it starts at the anchor's left; if it does not fit, its right edge is at the anchor's right (the point, for a right-click); then it is clamped into the window. A menu is never wider than the window's room.
   - A submenu: beside its row, its first row level with it, on the right, or on the left when the right has no room; if neither side has its width, on the side with more room, clamped. Vertically it is moved up until it fits, shrunk to the window's room if needed.
   - The order is always flip, then shrink and scroll, then clamp. The current row is scrolled into view.
6. **Closing.** A press of any button outside every level closes the whole menu and goes no further; a press inside a menu that misses a row (a separator, the padding, the reason line) does nothing. The wheel outside closes it and scrolls what is under the pointer. Escape or Left closes the submenu, then Escape the menu; Tab closes the menu. The menu closes when its window is resized or loses the activation, and when the RBS menu or another layer named in decision 2 opens. A pick closes it and then runs the row's id. The rows are a snapshot made when the menu opened: models that update behind it (meters, lists) do not close or change it; a pick whose target has gone is refused by the command runner with its usual error message (`run_command`), never a panic.
7. **Pointer and keyboard.** No row is current when a menu opens; Down makes the first row current and Up the last. Hover makes a row current. Resting on a submenu row for `delay.submenu` (new token, 250 ms) opens its submenu; resting on another row (a disabled submenu row too) for the same time closes it, so the pointer can cross rows on its way to the submenu; a click opens it at once; the pointer on the submenu keeps it. Return or Space runs the current command row (and closes the menu, except on a switch row); Right or Return opens a submenu with its first row current. Up and Down move and wrap over separators; Home and End jump; a letter moves to the next row whose title starts with it (`menu_layout::find`). The menu's `FocusScope` takes the keyboard focus while open and accepts every key, so nothing behind it moves; rows take no focus. Because Slint 1.18 has no active descendant, the scope's accessible value is the current row's title (and its reason when disabled), so a screen reader hears each move as a value change. When it closes, Rust gives the focus back to the item that had it when the menu opened, through `i-slint-core`'s `WindowInner::focus_item` and `set_focus_item` at the exact version `slint` is pinned to (as `popups.rs` does), with a test that fails if that API changes; if the item has gone, the focus is cleared.
8. **Accessibility.** Slint 1.18.1 has no menu role. The menu is a `list`; rows are `list-item`s with `accessible-checkable`, `accessible-checked`, `accessible-enabled`, `accessible-item-selected` (the current row), `accessible-item-index`, `accessible-item-count`, and `accessible-expandable`/`accessible-expanded` on submenu rows; `Select` sets `accessible-expanded` while its list shows. VoiceOver, Narrator and Orca are checked before merge.
9. **Zero cost when closed.** The layer exists only while open (an `if` in `OverlayHost`); rows are built when it opens, never while it is closed. The layer's `FocusScope` takes the focus when it is created (its `init`), so no timer runs for it; the submenu timer runs only while the pointer rests on a row. The menu, its submenu and its reason line are one or two covers of the native preview (ADR-0054): the menu with its reason line, and the submenu. Worst case while a menu shows over the preview: two toasts, the end-stream card, a slid-out panel, the menu and its submenu, six of the eight cut-outs (`MAX_CUTOUTS`); the modal layers (name prompt, picker, first run, vertical output, transition and live popovers) cover the preview, so no right-click reaches it while they show. Past eight the preview layer hides, as it does today.
10. **Every window that uses `CommandMenu` or `Select` has an `OverlayHost`**; a test checks it for every `Window` in `ui/` (the projector uses `NativeCommandMenu` and needs none; probe windows that hold a `Select` get one).
11. **Limits.** A context menu holds at most 16 top-level items (`MAX_CONTEXT_ITEMS`), checked by the existing `every_context_fits_its_slots` test for every context; ADR-0094 B2's seven-item guidance for top levels stays. The drawn layer takes any number of rows.

## Consequences

- One look on every platform, in every theme and user theme; disabled reasons and shortcuts appear in drawn context menus (two "Not yet" items of the spec): reasons on top-level rows, shortcuts on every row; not in the projector's native menu.
- A menu cannot leave its window. In a small floating window a long menu scrolls; the native menu used the whole screen.
- RBS owns behaviour the system gave for free: keyboard navigation, typeahead, submenu timing, screen-reader exposure, and the focus return through a private Slint API that must be checked on every Slint upgrade.
- A right-click outside an open menu closes it; a second right-click opens the menu there (native menus did both at once on Windows).
- The Windows stray-press workaround for the picture's menu (`menu_press`, `preview-menu-opened`) is removed: the layer takes the closing press itself.
- Every right-click on a picture now cuts the native preview for as long as the menu is open (one or two rectangles). Before merge, the cut-out cost is measured on Windows (RTX 4090 and the AMD iGPU when the owner allows) and Mac with a menu open over the preview, against today's (`measure-performance` skill): frame time of the preview layer and the compositor's overlay promotion. A regression is a merge blocker.
- `SelectList` handles every Select; the native short list goes.
- Spec updates in the same change: ui-design-system "Context menus" (toolkit, opening, not-yet list), "Select", the token tables (`delay.submenu`), the themes spec's not-themeable list.

## Alternatives considered

- **Keep native context menus and only theme the Linux one.** Keeps the platform differences and the missing reasons and shortcuts the owner wants gone.
- **Reuse `AppMenu` (the RBS menu) as the context menu.** It is a flyout with a search field, a category column, profile chips and a fixed width; a context menu is a plain list placed at a point with submenus. The menu layer uses the same row look and the same reason line, so they read as one family; a shared row component may follow when both settle.
- **Draw menus in borderless popup windows of their own, so they can leave the window.** Slint 1.18's `PopupWindow` takes no keyboard focus (ADR-0094 spike) and ADR-0094 B1 removed every `PopupWindow`; a separate OS window per menu also needs focus and placement handling per platform.
- **A `closed()` callback on every `CommandMenu` that each owner wires to refocus itself.** About 30 call sites, each easy to forget; the private API is one place, pinned and tested.
- **Draw the macOS menu bar too.** macOS users expect the system menu bar, and it carries the app menu, services and system shortcuts.

## Review

Independent review per ADR-0014.

- Round 1, independent AI session, 2026-11-17: changes requested (15 concerns). Resolved in this revision: focus return named (private `i-slint-core` API, pinned and tested; decision 7); anchored opening for buttons and one pure placement function with a stated order (decisions 2 and 5); the disabled reason is a reason line under the menu, not the tooltip (decision 4); the "content rebuilt" trigger replaced by snapshot rows and a refused stale pick (decision 6); Select keeps `SelectList` with its cap, paging and result path (decision 1); `AppMenu` reuse added as an alternative and the overlays' coexistence stated (decision 2); Tab, unhandled keys, the current row on open and clicks on disabled rows stated (decisions 4, 6, 7); the cut-out measurement plan and the removal of the stray-press workaround added (Consequences); the OverlayHost test (decision 10); `NativeCommandMenu` for the projector (decision 1); `MenuRow` fields listed (decision 3); accessibility properties (decision 8); the 16-item limit cited correctly (decision 11); the focus timer stated (decision 9); ADR-0054 decision 6 and the spec sections added to the amended list.
- Round 2, independent AI session, 2026-11-17: changes requested (1 major, 5 minor); round 1 resolutions confirmed against main. Resolved in this revision: submenu rows keep today's registry data (no disabled rows or reasons inside submenus; `rbs-ui` unchanged), only icons and shortcuts added (decision 3, Consequences); the focus stays on the layer's `FocusScope`, whose accessible value announces the current row (decision 7); the cut-out worst case counted (decision 9); keyboard opening from a row stated (decision 2); a disabled submenu row does not open (decision 4); the OverlayHost test's scope (decision 10).
- Round 3, independent AI session, 2026-11-17: approve (8 minor). Resolved in this revision: decision 9 says the focus is taken in `init`, not by a timer; `open-from` passes the button's width, so a menu near the right edge ends at the button's right edge (decisions 2 and 5); the placement and typeahead functions named as in the code (`menu_layout`); a switch row flips only when the command runner accepts the command, else the menu closes (decisions 3 and 6); the switch keeps the library `Toggle`'s theme effects, stated as such (decision 3); resting on a disabled submenu row closes an open submenu (decision 7); a press inside the menu that misses a row no longer closes it (decision 6); `menu_rows` has a unit test of switches against checks.
