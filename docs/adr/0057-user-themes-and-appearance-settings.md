# ADR-0057: User themes as checked token overrides in a theme library; Settings › Appearance picks and edits them

- Status: Accepted
- Date: 2026-11-06
- Deciders: Salih (owner)
- Builds on: ADR-0015 (UI design rules), ADR-0049 (main window), ADR-0051 (user data documents and libraries), ADR-0013 (zero cost when unused)
- Spec: [themes](../specs/themes.md)

## Context

The owner wants the look of RBS to be fully parametric: every colour, spacing, size and font a user can change, themes users make themselves, and themes the community can share (later bundled in `.rbspack` packs). Rule U12 already allows "custom themes": "A theme is a token file that must pass the contrast check and cannot change `color.state.live`."

What exists:

- `crates/rbs-ui/tokens.toml` (token file format 1) holds every token: fixed live colours, one colour set for each built-in theme (`dark`, `light`, `high-contrast`), and one shared set of lengths, durations and text styles. `rbs_ui::tokens::Tokens::parse` refuses a missing, unknown or invalid token, a changed fixed colour, a length under its minimum and any failed contrast or hue rule.
- Since PR #151 every token is a run-time value in the desktop shell: the build generates the `Theme` and `Tokens` Slint globals with the built-in values as defaults and `apply_tokens` to copy a parsed token file into them (`rbs-app` `look`). Each window gets the file when it opens. `RBS_TOKENS=<file>` names another complete token file as a development aid; `RBS_THEME` picks a theme, otherwise the OS scheme picks dark or light.
- There is no font family token; the shell uses the toolkit's default (the OS UI font).
- ADR-0051 gives versioned TOML documents (`format`, `kind`, `name`), libraries of named entries with stable ids, import, export, a writer lock and one writer thread, and reserves `themes/` under the config directory.

The forces: a theme file is a public format that strangers share, so it is untrusted input that must never break accessibility (U7, U12) or the layout (U11); themes made today must keep working when RBS adds tokens or a later release tunes built-in values; P13 wants nothing to run while the user does nothing; P1 keeps toolkits out of the model crates.

## Decision

1. **A user theme is a set of overrides on a built-in theme.** A theme document (`kind = "theme"`, format 1) names a `base` (`dark`, `light` or `high-contrast`) and sets only the tokens it changes; every other token takes the base's value from the built-in token file of the running build. The *resolved theme* is the base with the overrides applied. Consequences that are intended: a token added by a later RBS gets the base's value in old themes, so adding a token never needs a new theme format; a built-in value tuned in a later release reaches every theme that does not override it.
2. **What a theme may set.** Colours: every theme colour token (`THEME_COLORS`). Never the fixed colours (`color.state.live`, `color.text.on-live`): a theme that sets one is refused (U12). Look tokens: spacing (`space.*`), control heights, radii, lines, icon box and stroke, menu widths, durations (`motion.*`) and text styles (`type.*`, each style whole: size, line and weight). One new token, `font.family`: a list of font family names, the first one installed on the computer is used, and an empty list (the built-in value) means the OS UI font. Window sizes (`size.window.*`, `size.floating.*`) and keyboard steps (`step.*`) are behaviour, not look; a theme that sets them is refused. Themes name fonts only; they never carry font files (a font is a parser attack surface and has its own licence; whether packs may carry fonts is a later decision).
3. **Every resolved theme passes the built-in checks plus theme rules; a theme is untrusted input.** The checks of the built-in file run on the resolved theme (high-contrast thresholds when the base is `high-contrast`), together with rules that exist because a stranger's file, not a designer, chose the values. Each rule holds for the built-in themes today (checked when this ADR was written) and is enforced for the built-in file too, so the two can never drift:
   - **Contrast for every pair the components draw.** The rule list grows to cover the pairs the shell draws that the built-in rules did not: `border.focus` on `surface.overlay` and `.sunken`, `text.inverse` on `accent.hover`, `accent` on every surface (selection outline, 3:1), `text.secondary` on `accent.subtle`, `state.live` on `surface.sunken`. A test fails when a `.slint` file uses a colour token in a foreground/background pair no rule covers (the spec lists the pairs).
   - **Live red stays reserved (U12).** Every theme colour must differ from `color.state.live` by at least ΔE2000 15 (the closest built-in today is light `meter.high` at 16.2), on top of the existing 45 degree hue rule for error, destructive and clip. So a theme cannot make the accent, a warning, a meter zone or the focus ring look like live.
   - **Bounds per token** (spec): the focus ring stays visible, targets at least 24 px (U7, WCAG 2.5.8), text from 11 px with weight at least 300, motion 120 to 200 ms (U12; reduce motion turns it off, so a theme cannot set 0 or longer), lengths and menus within sane limits.
   - **Rules across tokens** so passing values still fit together (U11): `caption`, `body` and `label` line heights fit in `size.control.sm`; `size.icon.box` fits in `size.control.sm`; control heights, spacing steps, radii and text sizes grow monotonically (`sm <= md <= lg`, `space.1 <= ... <= space.8`, `caption <= body <= title <= heading`); `size.focus-ring` is at most `space.1`.
   - **Size.** A theme file is at most 64 KiB and holds at most 256 unknown token names (the user data limit of 16 MiB is for scene collections).
   A theme that fails any rule is not used; the Appearance page lists it with every problem. A token name the build does not know but that is a valid token name is kept on save and listed as "not used by this version", so a theme from a newer RBS still works with what this build knows; this is a deliberate exception to ADR-0051's "unknown keys are errors" for documents, like the unknown sections of output profiles, and the editor shows each one so a typo is visible. A known token with a value of the wrong type or out of bounds fails the theme.
4. **Themes are a library.** User themes live in `themes/<id>.toml` as a `Library<Theme>` (ADR-0051 decision 3): stable ids, unique names, rename, duplicate, delete to `deleted/`, import (with upgrades, newer formats refused) and export (one file, nothing to scrub: a theme holds nothing that belongs to one computer). Optional display fields `author` and `description` (single-line, at most 64 and 200 characters) help sharing. The three built-in themes are not files: they are read-only entries named Dark, Light and High contrast with the ids `builtin:dark`, `builtin:light` and `builtin:high-contrast` (`:` is never in a library id, so the two cannot clash). Editing starts from a copy: "Duplicate" on any theme makes a user theme whose base is the built-in theme it resolves from, with the same overrides.
5. **The appearance choice is per user, not per output profile.** `appearance.toml` (`kind = "appearance"`, format 1, under the config directory, written by the user data writer under the writer lock) holds `mode` (`system` or `fixed`), `dark` and `light` (the theme ids used when the OS scheme is dark or light, in `system` mode) and `theme` (the id used in `fixed` mode). Defaults: `system`, `builtin:dark`, `builtin:light`. An id that names no usable theme (missing, unreadable, newer, failing a check) falls back to `builtin:<base>` of that theme whenever its `base` can be read, so a user of a high-contrast based theme keeps high contrast; only when the base cannot be read does it fall back to `builtin:dark` (for `dark` and `theme`) or `builtin:light` (for `light`). The app shows a note and is kept in the file so the choice comes back when the theme is fixed. `RBS_TOKENS` and `RBS_THEME` stay as development aids and win over `appearance.toml`; the Appearance page says so while they are set.
   **A way back.** A theme can pass every check and still be unusable for one person (a symbol font, a font without the glyphs of the UI language, U8). So: a font family is used only if it covers the UI language's sample text (spec); choosing another theme or changing `font.family` asks "Keep this look?" and goes back to the previous look after 15 seconds without an answer (as display settings do; timed by the injected clock in tests); and `rbs-app --reset-appearance` moves `appearance.toml` aside and starts with the defaults.
6. **Settings › Appearance.** A new Settings section, beside the others (it does not touch General):
   - **Theme**: "Follow system" (mode `system`) with two pickers, "When the system is dark" and "When the system is light", or one picker (mode `fixed`). Each picker lists the built-in themes, then user themes by name, each with a small swatch preview (surface, text and accent).
   - **Themes list**: built-in and user themes with Use, Edit (user themes only), Duplicate, Rename, Delete, Import and Export. Unusable themes are listed with the reason and can be edited, exported or deleted but not used.
   - **Theme editor**: tokens grouped as Colours, Text, Font, Spacing and size, Shapes and Motion, each row showing the token's name in words, its value with the library control (ColorPicker, NumberField, a font family list) and a reset button that removes the override. An edit that fails a check stays in the editor with the rule it breaks shown beside the token, is not applied, and the theme cannot be saved while one fails. An edit that passes is applied at once to every open window, so the user sees it on the real app; Cancel returns to the saved theme. Saving is one write.
   - **Placement (owner's choice, 2026-11-06, with a mockup):** the editor lives inside Settings › Appearance: the themes list on the left, the editor of the selected user theme on the right, in the Settings window; no separate editor window.
7. **Applying a theme.** The generated globals hold two *slots*, one per OS scheme: slot 0 is used while the OS is dark, slot 1 while it is light. Each slot holds a complete resolved theme: its colours, every themeable length, duration and text style, and a `high-contrast` flag that is true when its base is `high-contrast`. `Theme.active` is the slot for the OS scheme; every `Theme.*` and `Tokens.*` property reads `slots[active]`, so an OS scheme change switches without Rust code or file reads, and a binding re-evaluates only when `active` or a slot changes. In `system` mode slot 0 gets the `dark` choice and slot 1 the `light` choice; in `fixed` mode both get `theme`. `RBS_THEME=<name>` puts `builtin:<name>` in both slots; `RBS_TOKENS=<file>` replaces the built-in token file the themes resolve on. `Theme.choice` is removed. On a change of choice or of a theme the shell sets the slots of every open window (main, floating, Settings, projectors) and gives native layers that draw with token colours (preview selection outline, ADR-0048; meters, ADR-0035) their new colours; each window gets the slots when it opens. The window's default font family is the first family of `font.family` that is installed and passes the glyph check (checked again when the UI language changes), found through a font catalogue the shell is given (the system font database in the app, a fake in tests); none: the OS UI font. Applying is a one-time property update: no polling, no file watching, no per-frame work (P13). Theme files are read at start (only the ones `appearance.toml` names), when the Appearance page opens (the list, envelopes only) and on "Reload themes"; a file edited by hand outside RBS takes effect on reload or restart.
8. **Layers.** The toolkit-neutral theme model (overrides, resolving on a base, the checks and bounds, the token metadata the editor shows) is in `rbs_ui::tokens`; `rbs-ui` keeps depending only on `serde` and `toml`. `rbs-user-data` gains a dependency on `rbs-ui` and implements `Document` for the theme and the appearance choice and `UserData::themes()`, `appearance()` and `set_appearance()`. Only `rbs-app` applies themes to Slint and queries fonts. No core or port crate changes. The new dependency `rbs-user-data -> rbs-ui` also reaches `rbs-cli`; `rbs-ui` stays toolkit-free, enforced by a `cargo-deny` ban that allows `slint` only under `rbs-app`. Public contract added: the theme and appearance documents, the token names and bounds in `THEMEABLE`, and the theme rules; the crates are not published, so the contract is versioned by the documents' `format` (rule 9), and generated Slint global names are internal to `rbs-app`.
9. **Token names are part of the theme contract.** Renaming or removing a token, or changing the meaning or unit of one, needs a new theme `format` with an upgrade step that maps old names and values (ADR-0051 decision 2); adding a token does not (decision 1). Tightening a check or a bound does not upgrade themes: a theme that fails the new rule is listed with the reason and the user fixes it in the editor.

## Consequences

- Users can change every look token, make, share and import themes, and use different themes for the OS's dark and light schemes, without a rebuild or a restart.
- Shared themes cannot break accessibility or the live colour rule: every resolved theme passes the same checks as the built-in file, with bounds on top.
- Overrides keep theme files small and readable and make old themes survive new tokens; the cost is that a theme can look different after an RBS update that changes a built-in value it did not override, and a tuned built-in value can, rarely, make an old theme fail a contrast rule. Both are visible in the editor, never silent.
- The token file format changes: `font.family` is added to the built-in file (format 2 of `tokens.toml`, an internal file, with `RBS_TOKENS` files of format 1 still read and given the default font). The generated Slint globals become two slots (decision 7); `Theme.choice` goes away.
- The added contrast pairs, the ΔE rule from live red and the cross-token rules also bind the built-in token file, so later tuning of built-in values is checked against them.
- New work: `rbs_ui::tokens` theme model, rules and bounds with property tests (any override set either resolves to a token set that passes every rule, including the cross-token ones, or is refused with a reason); the theme and appearance documents with library conformance tests; Appearance page, theme editor, keep-this-look prompt, `--reset-appearance` and live apply in `rbs-app` with light, dark and high-contrast screenshots and the `ui-review` skill; native layers reading colours on change; a "Reload themes" command in the registry (ADR-0050). Tests listed in the spec cover every generated setter, windows opened later, native layers, an OS scheme switch with two user themes, and each fallback.
- Follow-ups, each a change of its own: themes in `.rbspack` packs; the curated accent choice of rule U12 as a one-click shortcut that writes accent overrides; detecting the OS high-contrast setting; theme selection through the control API and MCP; a text size preference (U7, 200 %).

## Alternatives considered

- **A user theme as a complete token file** (what rule U12's wording and `RBS_TOKENS` do today): no base to resolve, but every token added later would break every shared theme or need a format bump, and files are long and hard to read. Overrides on a base avoid both.
- **One user theme holding all three colour sets** (like the built-in file): mirrors the file, but users make one look at a time, and "follow system" is better served by choosing a theme per OS scheme.
- **Unknown tokens as errors** (ADR-0051's default for documents): catches typos, but a theme from a newer RBS would be refused whole by an older one. Keeping and listing unknown names shows typos in the editor without refusing themes.
- **Fonts inside theme files or packs**: makes a theme look the same everywhere, but adds font parsing of untrusted files, licensing questions and size; names with fallbacks first.
- **Watching `themes/` for changes**: a hand edit would show at once, but a watcher is a running cost for a rare case (P13); "Reload themes" covers it.
- **The appearance choice inside output profiles**: profiles hold output settings only (glossary), and switching a profile for a stream should not change the app's look.

## Review

Independent AI session per ADR-0014, 2026-11-06 (given only the proposal, specs, principles and code). Verdict: changes requested, 12 concerns (7 blocking); all addressed in the same change:

1. Blocking: contrast rules missed pairs the UI draws. Added `border.focus` on overlay and sunken, `text.inverse` on `accent.hover`, `accent` on every surface, `text.secondary` on `accent.subtle`, `state.live` on sunken (all pass the built-in themes today), and a test that every drawn pair is covered (decision 3). `state.live` on raised was not added (nor on overlay): the dark theme measures 2.92 and 2.54 there, live is always shown as a badge with its fixed text (U12), and the fixed live colour is not the theme's to fix; it stays a check on `surface.base`.
2. Blocking: a theme could reuse live red. ΔE2000 of at least 15 from live for every theme colour (closest built-in 16.2) (decision 3).
3. Blocking: bounds alone did not keep the layout. Cross-token rules (line heights and icons in controls, monotonic scales, focus ring within spacing) and weight at least 300 (decision 3, spec).
4. Blocking: motion bounds contradicted U12. Motion is now 120 to 200 ms; no amendment to U12.
5. Blocking: no way back from a legal but unusable theme. Glyph coverage check for fonts, a 15 second "Keep this look?" revert, and `--reset-appearance` (decision 5).
6. Blocking: fallback could drop high contrast. Fallback is `builtin:<base>` when the base is readable (decision 5).
7. Blocking: the slot model was not specified. Two slots, per-slot flag, mapping of modes and `RBS_THEME`, `Theme.choice` removed (decision 7, spec).
8. Font enumeration: a font catalogue given to the shell, the system font database in the app and a fake in tests (decision 7).
9. Untrusted input bounds: 64 KiB per theme file, at most 256 unknown names, text direction marks refused in font names (decision 3, spec).
10. The unknown-token exception to ADR-0051 is now stated, with typos shown in the editor (decision 3).
11. Layering: semver and contract notes, and a `cargo-deny` ban that keeps `slint` out of everything but `rbs-app` (decision 8).
12. Tests: added to the spec (generated setters, later windows, native layers, OS scheme switch, fallbacks, cross-token property test).

Round 2, same independent AI session, 2026-11-06, reviewing commit 95ed611. Verdict: **approve**. All seven blocking concerns resolved; the built-in measurements were recomputed from `tokens.toml` and confirmed (tightest new contrast pairs 3.88 against 3.0 in light; closest colour to live ΔE2000 16.2, light `meter.high`). Non-blocking items, applied: `state.live` on `surface.sunken` added as a rule (3.37 / 4.80 / 3.66 in the built-ins); the font glyph check runs again when the UI language changes; item 1 above reworded (the concern named raised and sunken).
