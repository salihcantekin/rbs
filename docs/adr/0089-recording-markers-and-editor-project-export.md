# ADR-0089: Recording markers and an editor project (FCPXML) written from the recording manifest

- Status: Proposed
- Date: 2026-11-09
- Deciders: Salih (owner)
- Builds on: [ADR-0004](0004-single-master-clock.md), [ADR-0021](0021-scene-collection-model.md), [ADR-0050](0050-command-registry-menus-and-toolbar.md), [ADR-0051](0051-user-data-profiles-and-scene-collections.md), [ADR-0060](0060-shortcuts-in-app-and-global.md), [ADR-0086](0086-recording-sources-separately-iso.md)
- Spec: [recording](../specs/recording.md), [control-api](../specs/control-api.md), [user-data](../specs/user-data.md), [shortcuts](../specs/shortcuts.md)

## Context

After a long take the first job in an editor is finding the moments that mattered and putting the files on a timeline. With separate files (ADR-0086) the second job gets bigger: five files that must be imported, placed and aligned. RBS knows both things at record time: when the user pressed "this is good" and when the scene changed, and exactly how the files relate (same start, same clock, sizes, frame rates). The owner approved two ideas: markers placed during recording with a shortcut, and an editor-friendly project written together with separate recordings.

Constraints: the files are produced by hot-path code that must not gain work for this feature (P15); the project writer is a pure conversion from data we already have; the editor formats are external contracts that must be tested against real editors, not assumed; Windows and macOS only.

## Decision

1. **Markers.** While a recording runs, `marker.add` (a registry command with a shortcut, global shortcuts allowed by ADR-0060, a Live controls button, control API `marker.add {label?, color?, canvas?}`) adds a manual marker. The shortcut dispatcher already ignores key auto-repeat (shortcuts spec), so a held key adds one marker. `canvas` is `"main"`, `"vertical"` or `"all"` (the default): with `"all"` every running recording gets the marker at the same master-clock time, each relative to its own `t0`, so a control surface can mark one output or all (API parity). This default differs from `record.*`, whose `canvas` defaults to the main canvas; the control API lists `marker.add` and `marker.list` in its `canvas: "all"` section. A wrong marker is taken back with `marker.remove {canvas, index}`. Outside a recording the command is disabled with the reason, and the API answers `conflict`. A marker is a plain event on the control thread: no node, no per-frame work, no effect on the encoders (P13).
2. **The marker model** (one `[[markers]]` table per marker in the manifest, decision 4):
   - `index`: 1-based, stable, in the order the markers were added to that recording;
   - `t_ns`: position from `t0` in nanoseconds; for a manual marker `t_ns = pressed_ns - marker_lead`, clamped to 0;
   - `pressed_ns`: manual markers only, the press time from `t0` before the lead;
   - `kind`: `manual`, `scene`, `protection`, `stream_start` or `stream_end`;
   - `label`: one line of at most 200 Unicode scalar values (control characters refused, surrounding spaces trimmed); a blank or absent label of a manual marker becomes "Marker N", N counting manual markers;
   - `color`: one of a fixed semantic set, `blue` (default), `red`, `orange`, `yellow`, `green`, `purple`. The data stores the name; only `rbs-app` maps it to theme tokens (ADR-0057), so the manifest does not depend on a theme.
   - At most 10 000 markers per recording; one more is refused (`conflict`).
3. **Automatic markers (settings, each off or on, saved with the output profile in a `[markers]` section next to `marker_lead`).** *Scene changes*: kind `scene`, labelled with the new program scene's name, at the tick the transition to that scene starts on the main canvas (nested scene changes are not markers; the vertical canvas's own scene changes are marked in its recording only when it does not follow the main canvas). *Stream start and end* (`stream_start`, `stream_end`) when a stream runs during the recording. *Recording protection events* (`protection`, ADR-0090: encoder behind, disk low, with their text) ship only after ADR-0090 is Accepted. Default: scene changes on, the others off.
4. **Reaction-time offset (a user setting).** `marker_lead` moves manual markers earlier by 0 to 30 seconds (default 0), because a person presses the key after the moment. The marker keeps its real press time too (`pressed_ns`).
5. **Storage: the recording manifest, one owner.** Markers live in the recording manifest (`kind = "recording-manifest"`, `format = 1`, specified once in `recording.md`, "Recording manifest"). A recording folder (ADR-0086) has `recording.rbs.toml`; a plain recording that has markers or project export on writes `<file stem>.rbs.toml` next to its file. This narrows ADR-0086 decision 6, which says the manifest is "also written for plain recordings" without a condition: a plain recording with no marker and project export off writes no sidecar (an owner choice, listed in the Review). The manifest is not a profile document of `rbs-user-data` (it lives in the recordings folder, not the profile), but follows the same rules: `format` and `kind`, a temporary name and a rename, no secret and no absolute path. **One owner**, the recording's state on the control thread, holds the manifest in memory; the start write, the marker flushes and the stop rewrite are each an atomic whole-file rewrite through that owner. **Flushing:** the first marker not yet on disk arms a one-shot timer (5 seconds); when it fires the manifest is rewritten and the timer is not re-armed until another marker arrives; stop cancels it and writes the final manifest. No marker means no timer and no write (P13). A crash loses at most the last 5 seconds of markers and never the media.
6. **What the manifest carries for the project writer.** The writer reads only the manifest and never probes media, so the stop rewrite must add (normative; the one list of stop fields, specified in `recording.md`, "Recording manifest"): per file, `start_offset_ns` (its first sample from `t0`; ADR-0086's `first_real_ns`), `duration_ns` (its end, ADR-0086's "end time" and `ended_at` of a track that ended early, is `start_offset_ns + duration_ns`), and for a file with a picture `width`, `height`, `frame_duration` (`"num/den"` seconds), for a file with sound `sample_rate` and `channels`; at the top level `duration_ns` from `t0`, the master's `width`, `height` and the canvas `frame_duration` (ADR-0102), and `complete = true`. Every `name` is a file name with its extension; the rule in `recording.md` that a video `name` stays the plan's stem changes when video files are opened (ADR-0086 step 3). A manifest without `complete = true` (the stop rewrite never happened, for example after a crash) is refused by the writer with `ProjectError::Incomplete`; it never guesses. **The stop rewrite is step 0 of this ADR's work** and is shared with ADR-0086 step 1, which lists offsets and drop counters as written at stop.
7. **Crates.** The manifest model (the types above, markers, TOML read and write, the marker log) moves out of `rbs-record` into a new **model crate `rbs-manifest`** (depends on `rbs-core` and `toml`; no engine, adapter, GPU or UI crate). `rbs-record` uses it and re-exports its manifest types, so the engine does not own the format. The editor project writer is a new crate **`rbs-project`** (depends on `rbs-core` and `rbs-manifest` only), used by composition roots (`rbs-app`, `rbs-cli`). Both are in the layers table of `overview.md` (`rbs-manifest` as "Recording model"). The control API cannot depend on either (Control layer: Foundation only): its marker colour and kind enums mirror the manifest's, and `rbs-app` maps between them. These are layering additions and are part of this ADR's independent review.
8. **Editor project from the manifest.** `rbs_project::build(&RecordingManifest, &MediaFolder, Format) -> Result<String, ProjectError>` is pure. `MediaFolder` is the absolute folder of the files, given by the caller and turned into a file URL. `rbs_project::export(folder, manifest_name, format)` does the I/O: it reads the manifest, checks the files, builds the project and writes it next to the manifest under a fresh name (`<stem>.fcpxml`, then `<stem> 2.fcpxml`, ...; never overwriting).
   - **Timeline.** Sequence time 0 is `t0`. The sequence uses the canvas `frame_duration`. The primary storyline (lane 0) holds a `gap` from 0 to the master's first frame when that is one frame or more, then the master clip. Each separate video file is a connected clip on its own lane above (`lane` 1, 2, ...); ISO video files carry no sound (ADR-0086), so nothing is muted. Each separate audio file is a connected clip on its own lane below (`lane` -1, -2, ...).
   - **Coordinates.** In FCPXML a connected clip's `offset` and a marker's `start` are in its parent's local time (the parent's `start` plus the distance from the parent's `offset`). The writer places everything in sequence time first and then converts: an item that begins before the master's first frame is attached to the gap, every other item to the master clip. The gap and every asset start at `0s`.
   - **Rounding** (all deterministic; half a frame rounds up). The master's offset and every picture clip's offset and duration are rounded to the nearest frame of the sequence, at most half a frame. A sound clip is placed at the first frame boundary at or after its first sample, and the remainder (less than one frame) becomes the clip's in-point (`start`) in its own sample timebase, so the head loses less than a frame of sound and every later sample stays exactly where it was recorded; this keeps ADR-0086 decision 5's sample-exact promise without sub-frame offsets, which Final Cut edits only in 1/80-frame steps. Markers are rounded down to a frame. A marker after the end of the storyline is placed on its last frame; a connected clip that runs past the storyline's end is shortened to it. A golden-file test covers a 59.94 fps (1001/60000 s) sequence with 48 kHz sound clips.
   - **Markers.** `scene` markers become chapter markers; the others become standard markers with their label. FCPXML and FCP7 XML markers have no colour, so the colour is dropped (the label is kept).
   - **Missing files.** A missing master is an error (`ProjectError::MissingMaster`). A missing separate file is left out and the export report lists it; `rbs-cli project --strict` makes it an error.
   - **File URLs.** Absolute `file://` URLs: `file:///C:/Users/...` on Windows (the drive letter's colon stays literal and `\` becomes `/`), `file:///Users/...` on macOS, `file://server/share/...` for UNC paths (the host is not encoded). Every other byte of a path segment outside the RFC 3986 unreserved set is percent-encoded as UTF-8. One function in `rbs-project` does this, and the separate audio files' URLs (`recording.md`, which today encodes only space, `%`, `#` and `?`) move to it when the stop rewrite lands. The project therefore holds an absolute user path; the UI says so before a project is shared. Moving the folder needs a re-export (one command, same data).
9. **Formats, in order.** (1) **FCPXML 1.9**, a single `.fcpxml` file (not a `.fcpxmld` bundle), with the media URL in `media-rep` (Apple's FCPXML reference: 1.9 needs Final Cut Pro 10.4.9 or later, to be confirmed by the first manual import; DaVinci Resolve imports it on Windows and macOS; Final Cut is macOS-only, so a Windows-written project is for Resolve). One `format` resource per distinct picture size and frame duration. (2) **FCP7 XML (xmeml)**, which Premiere Pro and Resolve import. (3) Later, per demand: OpenTimelineIO, and a multicam clip for FCPXML so the separate video tracks become angles. **A format is not announced as supported until it has a golden-file test and has been imported in the real editor by hand**; the spec records which editor and version was tried and what was checked (clips placed, aligned, markers visible, and that the sound clips' offsets and in-points survived the import in Final Cut and in Resolve). Not promised: effects, transitions, the layout the compositor used, or rebuilding the on-air cut.
10. **When it runs.** Setting *Write editor project when recording stops* (off by default; a choice of format) and an on-demand command `project.export {recording, format}`. Both call the same function. Writing takes milliseconds and runs on the control thread after the media is closed; if it fails the recording and its manifest are untouched and the failure is reported. `rbs-cli project --manifest <path> --format fcpxml [--strict]` serves scripts and re-exports after a move.
11. **Control API** (minor numbers are assigned at merge; the first slice carries `marker.add` and `marker.remove`):
    - `marker.add {label?, color?, canvas?}`: scope `control`, effect `edit` (reversed by `marker.remove` with nothing lost, so a control-surface token needs no extra permission and no audit record). Answers `{markers: [{canvas, index, t_ns}]}`, one entry per recording that got it. Errors: `invalid_params` (label too long or not one line, unknown colour or canvas), `conflict` (no recording running on that canvas, or 10 000 markers). At most 2 per second per session, more is `rate_limited`: a per-session, per-method bucket in the session state machine on the API thread, tested on `TestClock`, which like the other protecting refusals may overtake earlier answers. It does not apply to the in-process UI or shortcut presses.
    - `marker.remove {canvas, index}`: scope `control`, effect `edit`. Removes one marker of the running recording on that canvas; the others keep their index. `not_found` for an unknown index, `conflict` when no recording runs there.
    - `marker.list {canvas?}`: scope `read`, effect `read`. The markers of the running recordings.
    - `project.export {recording, format}`: scope `control`. `recording` is the recording's folder or file name relative to the profile's recordings folder, a single path segment; `..`, separators and absolute paths are `invalid_params`. Errors: `not_found` (no such recording or manifest), `failed` (incomplete manifest, missing master, write error). Answers `{file, missing: [names]}`, `file` being the project's name inside the folder, never an absolute path. Its effect class is an owner choice, shared with `replay.save` (both only add a new file and never replace one, which neither `edit` nor `live` describes today): either `edit` with that sentence added to the definition, or a new class. It is settled before `project.export` ships.
    - Event topic `marker.changed`: scope `read`, a state topic with one state key per canvas, carrying that recording's whole marker state in short form: `{canvas, count, last: {index, t_ns, kind, label, color} | null}`; a client reads the full list with `marker.list`. There is no delta event.
12. **UI** (visual: proposal, then screenshots, rules 15 and 16): a Marker button in Live controls with a counter, a toast on each marker ("Marker 3 at 12:31"), and the settings in Settings › Recording › Markers and project, with plain-language help for each option.
13. **Order of work.** (a) `rbs-manifest` with the marker model and the manifest's stop fields, `rbs-project` with FCPXML and golden-file tests, and `marker.add` and `marker.remove` in the control API with the host keeping the markers of the running recordings (no UI); (b) the stop rewrite (step 0 above) and the manifest for plain recordings; (c) automatic markers and settings; (d) the UI; (e) `project.export`, `rbs-cli project`, xmeml; (f) markers in the media files (below).
14. **Markers in the media files (later).** Matroska chapters and a QuickTime/MP4 chapter text track are written at clean stop when the container allows (they need the final index), skipped for fragmented files that end uncleanly. The manifest stays the source of truth; embedding is a convenience for players and quick review. It needs muxer work (hot-path rules apply, P15) and is therefore its own step.

## Consequences

- The editor starts with the moments marked and, with separate files, a timeline with every track already aligned. No other tool in this class does this at record time.
- The feature adds no work to the encoders, muxers or any hot path in its first phases; embedding markers in containers (decision 14) is the only part that touches muxers and carries the P15 obligations.
- External formats drift; keeping the supported editor and version list in the spec, with a manual import checklist, is a standing cost.
- Two new crates: `rbs-manifest` (a model crate below `rbs-record`) and `rbs-project` (a leaf used only by composition roots). `recording.md` (the manifest), `control-api.md`, `shortcuts.md`, `user-data.md` (the output profile's `[markers]` section), `mcp-server.md` (the new methods' effects become tool annotations), `overview.md` (layers), `status.md` and the glossary change in the implementing PRs.
- A project file holds absolute paths of the user's machine; the UI must say this before sharing.

## Alternatives considered

- **Write the project by probing the media files (FFmpeg/OS).** Needs a probing dependency and can disagree with what RBS knows; the manifest is exact and free.
- **Only markers, no project.** Simple, but the main benefit of separate files (instant aligned timeline) would be left for the user to do by hand.
- **Embed everything in the media files only.** No sidecar to lose, but chapters need a clean close and cannot carry a multi-file project.
- **A platform stream marker (Twitch/YouTube) on the same key.** Platform-specific and network-dependent; a plugin concern (plugin SDK), not core.
- **Free-form colours and rich text for markers.** More to design, store and map to each editor; the small fixed set maps cleanly.
