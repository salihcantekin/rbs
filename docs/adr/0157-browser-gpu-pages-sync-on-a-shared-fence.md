# ADR-0157: Browser pages on the GPU sync on a shared fence; the helper never waits on the CPU

- Status: Proposed
- Date: 2026-11-20
- Deciders: Salih (owner)
- Supersedes: [ADR-0109](0109-browser-source.md) decision 8, only the Windows sync clause ("on Windows by releasing a keyed mutex") and the ring size clause ("enough textures to cover the sound delay plus one being written, at least two", replaced by decision 5) and the supervisor's "zero-timeout acquire on Windows", which the lease of decision 4 replaces; [ADR-0132](0132-browser-engine-css-interaction.md) decision 8, only "under a keyed mutex acquired with a 100 ms timeout" for Windows. The rest of both decisions stays: the studio owns the textures, the supervisor stamps pictures, a texture goes back only after the studio's GPU work that reads it has finished, a dead helper's unfinished copy is never published, and an adapter mismatch or a failed import uses the shared-memory path.

## Context

The Windows GPU path for browser pages (`rbs-browser-cef/src/gpu.rs`, `rbs-app/src/browser_gpu.rs`, `rbs-gpu/src/browser_pages.rs`) was built on branch `browser-gpu-texture` and is switched off on main: the studio names no adapter in `Configure`. With it on, the Interact window froze on SC-PC after the first busy second. The cause (static review, 2026-11-20):

- `Copier::copy` runs inside `OnAcceleratedPaint` on CEF's UI thread. Per frame it opens CEF's handle (`OpenSharedResource1`), guesses a keyed mutex (`AcquireSync(1, 16 ms)`, then `AcquireSync(0, 16 ms)`), copies, signals the shared fence and then waits on the CPU for that fence for up to 100 ms (`SetEventOnCompletion` + `WaitForSingleObject`). The same thread takes mouse and key input, so every move repaints and stalls input behind the GPU.
- A dropped frame (no free slot, mutex busy, wait timeout) is never asked for again. A page that stops changing keeps the stale picture.
- Three slots, and `claim_gpu` is check-then-use: the helper can pick a slot the supervisor is about to lease (TOCTOU), and it can overwrite the slot that was published last before the studio took it.
- The studio's frame carries `SurfaceSync::Ready`, because the helper already waited. The D3D12 importer can wait on the GPU instead (`interop::d3d12::Fences::wait`, `add_wait_fence` on the render queue, used by the zero-copy encode export, ADR-0147).
- CEF is not told which adapter to use. On SC-PC (RTX 4090 and an AMD iGPU) the GPU process can pick the other adapter, and the studio's textures do not open there. Naming a GPU vendor on the command line left the page black.

The owner decided (2026-11-20, stability plan D4, D5): a shared fence, the studio waits on the GPU, the helper never waits on the CPU; CEF is pinned to the studio's adapter by LUID; if that fails, the shared-memory path with a warning the user sees. No CPU copy on the normal path.

## Decision

1. **The helper never waits on the CPU in a CEF callback.** In `OnAcceleratedPaint` the helper must not call `WaitForSingleObject`, `SetEventOnCompletion`, `Sleep`, a keyed-mutex acquire with a timeout above zero, a blocking pipe or lock, or anything else that waits for the GPU or another process. The callback claims a slot, records the copy, signals, flushes and publishes, and returns. `rbs-browser-cef` enforces this with `clippy::disallowed_methods` for the waiting calls, and `Flush` time is measured on its own (decision 11), because a driver may throttle there.
2. **One shared timeline fence per page, owned by the studio; the supervisor gates on it.** The studio creates the fence with the textures (`D3D11_FENCE_FLAG_SHARED`), creates its NT handle with `GENERIC_ALL` (the only access `ID3D11Fence::CreateSharedHandle` takes; with the DXGI read and write rights every `Signal` in the helper fails, SC-PC check 3; the textures keep those rights) and duplicates it into the helper. The helper's copy is followed by `Signal(fence, v)` on its own immediate context and `Flush`, where `v` is the helper's next value (strictly increasing, starting at 1 for a new fence, decision 12). The helper writes `v` into the slot's header entry before it publishes the slot. A fence value is untrusted, and a GPU queue wait on a value that never arrives would stall every later submission on the render queue, not only this page. So the supervisor hands a picture to the render thread only after the fence's completed value (`GetCompletedValue`, a read that never waits) has reached `v`; a picture whose value has not arrived is checked again on the supervisor's next pass. At most two pictures wait, each holding its lease: the oldest, and the next one taken behind it. A waiting picture is never replaced; newer publishes stay unseen in the ring until the oldest goes out, so a GPU that finishes copies a frame or two late (a game on the same card) still shows the taken pictures in turn at the page rate. After the gate the copy has finished, so the picture carries `SurfaceSync::Ready`: the render queue never waits on a fence a helper can signal. A completed value of `u64::MAX` (device removed) or one more than 2^20 past the last published `v` is a failure and ends the GPU path for that tree (reason `fence`, decision 9). When the oldest waiting picture has not completed 30 page frames after the supervisor took it, measured on the supervisor's clock (so the same at the 5 ms sound poll, the half-frame poll and the 500 ms hidden poll), that is also fallback `fence`. A helper that keeps publishing cannot restart that timer, because nothing newer is taken while two wait: a helper device that was removed or hangs stops the value moving while its heartbeat goes on. The CPU observation followed by a later submission orders the studio's read after the helper's write as a queue wait would, under three rules this ADR requires: (a) both devices are on the same adapter (the import's LUID check); (b) a slot texture is in COMMON whenever it changes hands, because the importer creates it in COMMON and hands it back in COMMON (`Importer::retire`), and leaving COMMON on use invalidates the GPU caches; (c) the helper writes a slot only after the studio's hand-back submission has completed (the lease). A test checks that an imported slot starts and is handed back in COMMON. The render thread and CEF's callback never wait on the CPU for the fence. At worst a misbehaving helper shows a torn or stale picture of its own page; the heartbeat rule of ADR-0109 decision 8 ends a helper that stops.
3. **Keyed mutex only when the texture has one.** On the first accelerated paint the helper asks CEF's texture for `IDXGIKeyedMutex` and logs which case it found, once. Without one (expected for CEF 156) the copy uses no mutex. With one, the key is the one Chromium releases for the consumer, recorded from that first observation in the log and in this ADR's review before the path is turned on; it is acquired with a zero timeout and released after the copy is recorded. A busy mutex drops the frame (decision 6).
4. **Slots are claimed with a compare-and-swap, and the latest published slot is never overwritten.** Each slot has one 32-bit state word in the section: bit 31 is `WRITING`, bits 0..30 count studio leases.
   - Helper: claims a slot only by `compare_exchange(0, WRITING)` and only when it is not the slot published last. It writes the slot's fence value and paint time, then the latest slot index, then increments the publish sequence (release), then clears its bit with `fetch_and(!WRITING)`. It abandons a slot the same way, without publishing. It never stores the whole word.
   - Studio: load the publish sequence (acquire), then the latest slot index, then `fetch_add(1)` on that slot's word. If the old value had `WRITING` set, `fetch_sub(1)` and do not mark the sequence as seen, so the same publish is tried again on the next pass. Otherwise read the fence value and paint time, then load the sequence again; if it changed, release the lease and retry on the next pass (a newer picture exists). Only then mark the sequence as seen.
   - A clone of a held lease (`LeaseOwner::retain`) is a plain `fetch_add(1)`, legal only while the count is above zero, so it never meets `WRITING`.
   - Orderings: helper claim CAS Acquire; slot entry and index stores Relaxed; sequence increment Release; `fetch_and(!WRITING)` Release. Studio sequence loads Acquire; lease `fetch_add` AcqRel; lease release `fetch_sub` Release. The section's multi-thread tests run with these orderings, not SeqCst; `loom` tests of these orders are added before the path is turned on (round-4 review).
   - A page shown again without a new publish takes a new lease on the latest slot by the same steps, ignoring the seen mark.
   So a slot is never written while the studio holds it, the newest complete picture is always there to take, and a page that stops painting still shows its last published picture.
5. **Slot count from the holders, and too few costs frames, not correctness.** The holders at once are: the picture on air, the slots whose hand-back submission has not finished yet (at most the render queue's frames in flight, `Importer::retire`), the picture pending in the sink, the latest published slot (which the helper never claims, so a page shown again has a picture), and the slot the helper writes. The pictures that hold their leases while they wait at the fence gate (decision 2) are up to two more; with four slots a GPU that runs late therefore costs frames (no free slot) before it costs a fallback. With a fence two frames late and each picture held two frames, four slots show about four in five pictures and six show nearly all (`gpu_gate` tests); a copy that finishes within the frame loses none with four. Each slot is one page-size texture (about 8 MB at 1080p), so the default stays 4 until decision 11's drop rate says otherwise. Hand-backs are polled once per tick with a zero timeout, so their number is not strictly bounded by frames in flight. Other holders of the same leases (an Interact picture, an Unavailable source's last frame) are included. The sound delay no longer sets the count: a picture waits for its stamp in the sink, which holds one lease. The default is 4 and the section header has room for 8; `Configure` names the count. When no slot is free the helper drops the frame and decision 6 asks for it again, so a short count lowers the frame rate and never shows a slot that is being written. The default is set from the SC-PC drop rate (decision 11), and the metrics show how long a page has had no free slot, so a leaked lease is visible.
6. **A dropped frame is painted again, but not forever.** When the callback publishes nothing (no free slot, mutex busy, open or copy failed), the helper asks CEF for a new view paint once (`invalidate(PET_VIEW)`), posted to CEF's UI thread one page frame interval later, and not again until a paint arrives. A page that went still therefore ends on its latest state. Counting: a callback that published counts the failures back to 0; "no free slot" leaves the count unchanged; a busy mutex, a failed `CopyResource`/`Signal`, or a CEF texture smaller than the slot adds one, so a lasting size mismatch falls back too. At 60 the tree falls back with reason `copy` (decision 9). An `OpenSharedResource1` failure of CEF's texture is not counted here: it is reason `open` at once (decision 8).
7. **CEF opens are per callback.** CEF's handle is only valid during the callback and its value can be reused for another texture, so the helper must not cache an opened texture by handle value. The studio's own slot textures and the fence are opened once, at `Copier::open`. The cost of the per-callback open is measured (decision 11); a cache keyed on something CEF guarantees stable may be added later by a new decision.
8. **The helper runs on the studio's adapter.** The studio passes the adapter LUID in `Configure`, and the helper's browser process adds `--use-adapter-luid=<high>,<low>` for it, in decimal as Chromium parses it (signed 32-bit high, unsigned 32-bit low; `ui/gl/gl_display.cc`); `RBS_BROWSER_NO_ADAPTER_SWITCH` leaves it out for device checks. GPU and adapter switches are set in CEF's browser process only, never in a child process: `on_before_command_line_processing` runs in every process, a child cannot tell the GPU path from shared memory, and a renderer that turned GPU compositing off under a GPU-composited browser left CEF painting nothing (SC-PC check 3). Chromium hands the children what they need. A pure function of the process type and the LUID chooses the switches, and a unit test pins that a child gets none. Vendor and device switches are not used. "Another adapter" is detected when the helper cannot open the slot textures or the fence on its device for that LUID (reason `adapter`), or when `OpenSharedResource1` of CEF's texture fails on that device (reason `open`).
9. **Falling back is a restart, and it is visible.** A browser created with shared textures never gets software paint, so a tree cannot switch paths while it runs. A GPU failure found by the helper (`adapter`, `open`, `copy`) ends the helper with exit code 9 (`GPU_FALLBACK`), the reason written to its log (the status channel back is not built yet; when it is, it carries the reason), and the studio restarts that tree with no GPU block in `Configure`; this restart counts no back-off. A failure found by the studio (`fence`, or `import`: the render thread counts failed imports in an atomic the supervisor reads, it never talks to the helper; 10 failed imports in a row) causes the same restart. The source's last picture stays on air until the shared-memory tree paints. The choice is kept on the source's session in the studio (not in the scene), so a later heartbeat or ADR-0024 restart does not turn the GPU path back on; stopping the source clears it. `adapter` and `open` are found at the first paint, usually before the source is on air. The source then stays on shared memory until it is stopped. The studio shows a warning on that source in Properties; its text and placement are a visual change and follow CLAUDE.md rule 16. The metrics count fallback trees (ADR-0132 decision 8).
10. **The section and `Configure` are versioned.** The frame section takes layout version 2 when it has the GPU block (state words, fence values, paint times, latest slot, publish sequence, slot count). The studio and the runner ship together, so a section of another version is refused when the helper opens it (the helper exits before it paints, `helper_exit`); there is no shim for version 1. The `Configure` GPU block gets a version byte after its tag, then the LUID, the slot count and the handles; a block of an unknown version is ignored (shared memory). The current untagged-version block (`RBSg` with three handles) is replaced, not kept.
11. **Tests, reviews and numbers.** Tests without CEF (test-double runner and multi-thread or `loom` tests of the section): a texture is never handed back while the studio reads it (ADR-0109 decision 12); each order of decision 4 (claim before lease, lease before claim, publish between the studio's two sequence reads, a skipped `WRITING` lease retried); the latest published slot is never claimed; helper death while it holds `WRITING`; a section of another version is refused and an unknown `Configure` GPU block version gives shared memory; a completed value of `u64::MAX` gives fallback `fence`; repeated copy failure gives fallback `copy`; a value that never completes gives fallback `fence` after 30 frames even while the helper keeps publishing; ten failed imports give fallback `import`; a slot is in COMMON when imported and handed back; a restart with reused handle values matches no cached surface. The change gets `risky-review` and `hot-path-review`. Numbers on SC-PC for 1 to 2 minutes with Interact and a mouse sweep: callback time split into open, copy and signal (p50, p99, max), dropped and re-requested frames, `BrowserSourceNode::process` time before and after (CLAUDE.md rule 12).
12. **Every spawn is fresh.** Each helper spawn gets a new section, new textures and a new fence; nothing from an earlier spawn is reused. So a `WRITING` bit or a fence value a dead helper left behind can never be seen by the next one.
13. **A stopped tree's handles outlive every cached surface.** Importers cache opened surfaces by handle value and forget an idle one within 8 s (`SURFACE_IDLE`); the capture-port spec ("Native surface rules") asks a producer to keep a handle open until no importer can still match its value. So a stopped tree's `PageSlots` (textures, fence and their NT handles) go to a grave that drops them only once no frame references them and 10 s more have passed (`page_grave::HANDLE_HOLD`), and a restart can never get a handle value an importer still caches. A sweeper thread runs only while the grave holds a page, so a page that fell back to shared memory, or the last page of a removed source, is still released on time; the D3D release is never on the render thread. The page fence is never handed out in a frame (only the supervisor reads its completed value), so the importers' handle cache and its idle rule do not apply to it; it is kept and freed with the textures. A session dropped without a stop buries its slots too, and a poisoned grave lock is recovered, so a panic never keeps a page's textures. This uses the existing handle rule instead of a per-spawn identity, so `rbs-core` and the importer are unchanged. Test: `page_grave` (a held page stays, an unreferenced one goes after the hold, a page referenced again waits again).

## Consequences

- Input in Interact no longer waits behind the GPU; the callback's cost is the open, the copy record and the signal.
- A picture reaches the render thread up to one supervisor pass later than the copy finishes (at most half a page frame interval), instead of the CPU wait inside CEF.
- A misbehaving helper cannot stall the render queue (decision 2) or fault the studio: the studio still owns the textures and the fence, and the render queue never waits on a helper's fence.
- A GPU failure costs one restart of that page (decision 9): the page reloads, so its own state (timers, a chat overlay's scroll, Interact focus) starts again, while its last picture stays on air until the new tree paints. The page then stays on shared memory until the source stops.
- The section layout changes (version 2) and the `Configure` GPU block changes; the runner and the studio ship together, so no compatibility shim is kept beyond "unknown version means shared memory".
- Follow-up: scene-sources spec ("Frames cross ...") is rewritten when the code lands; the Properties warning is proposed to the owner first; WP-H adds fault injection for a fence value that never arrives.
- macOS (IOSurface) is unchanged by this decision and still paints in software.

## Alternatives considered

- **Keep the CPU wait but shorten it.** Any wait in the callback stalls input on CEF's UI thread; a short timeout only drops more frames.
- **Wait on the CPU in the studio's supervisor instead.** Moves the stall off CEF but adds a thread wake and latency per frame, and the D3D12 importer already waits on the GPU.
- **CPU copy of every frame (shared memory only).** Works everywhere but costs a full-frame copy and upload per paint; the owner rejected it for the normal path (D5 keeps it as the fallback).
- **A keyed mutex per slot.** Needs a timeout on one side and a CPU acquire; the fence gives the same ordering without either.
- **Three slots with a smarter claim.** Three cannot hold on-air, pending, latest and writing at once, so the helper would drop frames whenever the importer holds one for its hand-back.

## Review

Round 1: independent AI session (given only this ADR, the specs, the principles and the code), 2026-11-20. Verdict: changes requested. Concerns:
1. The CAS protocol missed the steps that make it correct: clearing `WRITING` with a store erases a lease in flight; the studio read the slot before its lease and marked a skipped publish as seen; `retain` was unspecified. -> Decision 4 now gives both orders step by step (`fetch_and`, sequence read twice, skipped publish not seen, `retain` only above zero); decision 11 names a test per order.
2. Helper death with `WRITING` set, and a fence restarting at 1, were safe only because the code makes everything new per spawn. -> Decision 12 makes that a rule.
3. A queue wait after the gate adds no ordering but lets a helper that lowers the fence stall the render queue; the importer's fence cache is keyed by handle value and grows on the render thread; a removed device reads `u64::MAX`. -> Decision 2: after the gate the picture is `Ready`; `u64::MAX` or an implausible value is fallback `fence`. The importer's fence cache is no longer used by this path.
4. Four slots do not bound every holder. -> Decision 5 states the holders, the default 4 with room for 8, and that a short count costs frames only; the default is set from the SC-PC drop rate.
5. "Shared memory for its life" cannot happen in a running tree created with shared textures; adapter detection and import failure reporting were undefined. -> Decision 9: fallback is a restart without the GPU block (no back-off); decision 8 defines detection; import failures reach the supervisor through an atomic.
6. A mutex that never frees loops forever, and the key was not named. -> Decision 3 records the observed key before the path is turned on; decision 6 falls back after 60 failed callbacks (`copy`).
7. Cached importer surfaces can outlive the page's handles and match a reused handle value. -> Decision 13.
8. The superseded text was understated. -> The header now also lists the supervisor's zero-timeout acquire; `risky-review` is kept explicit in decision 11.
9. The `Configure` GPU block has no version byte. -> Decision 10 adds it and replaces the current block; decision 11 lists the version, `u64::MAX` and `copy` tests.
