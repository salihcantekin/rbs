# ADR-0082: Audio filter chains on sources

- Status: Proposed
- Date: 2026-11-09
- Deciders: Salih (owner)
- Spec: [audio-filters](../specs/audio-filters.md) (new), [audio-graph](../specs/audio-graph.md), [scene-model](../specs/scene-model.md), [video-filters](../specs/video-filters.md), [control-api](../specs/control-api.md), [ui-design-system](../specs/ui-design-system.md)

## Context

Video sources have filter chains (ADR-0062): a `Filter { id, type_id, enabled, settings }` list on the source, a `FilterType` with a field schema, a `FilterNode` per filter that the binder wires between the source and the compositor, `filter.*` control API methods, one undo step per edit, and a Filters tab in Properties. Audio sources cannot have filters yet: the binder skips them (`BindProblem::FilterOnAudioSource`) and the audio graph spec lists audio filters as out of scope.

The owner's audio roadmap needs them: boost (a gain above 0 dB exists only as a filter, ADR-0059 and ADR-0081), a noise gate, later a compressor, limiter and equaliser, and the ducker (phase C). The owner also set a standing rule: a feature with parameters shows them in clear, polished controls and saves them as settings, with no hard-coded defaults where a parameter matters.

Facts that shape the decision:

- The scene model stores any filter as a type id string plus settings, and scene format 7 saves them, so audio filters need no model or format change.
- The field schema (`Field`, `FieldKind`, `Value`, `Values`, `FilterError`) lives in `rbs-filters`, which depends on `rbs-gpu`. An audio crate must not depend on a GPU crate (P1).
- The mixer matches strips by `producer` node id (`mixer.rs`, `apply_params`): a strip whose producer is new starts with `present = false` and fades in from silence, and the old producer's strip stops at once. If the chain tail becomes the producer, every change of the tail would cut the old strip and restart the new one.
- Filter nodes are created by the binder without a partition (default `RENDER`), and the binder's chain code works on video pins only. Disabled filters keep their node in the graph but are `Standby`, absent from the schedule.

## Decision

1. **Same model, no format change.** An audio filter is a `Filter` in the source's `filters` list with a type id `org.rbs.audio-filter.<name>`. `SceneCollection`, its undo records and the scene document (format 7) are unchanged. A build that lacks a type loads the file and reports `UnknownFilterType`; the source plays unfiltered and the filter list offers only Remove. This is a real behaviour difference for an older build (a gate or a boost is skipped); it is stated in the compatibility notes of `scene-model.md` and `user-data.md`.
2. **One parameter schema for every filter kind, in a new crate `rbs-params`.** `rbs-params` has no dependencies at all: `Field`, `FieldKind`, `Value`, `Values`, `ParamError` (the renamed `FilterError`), `MAX_FIELDS` (12). `FilterError` becomes `ParamError` and every user migrates to it (its `UnknownType(String)` variant, a filter-lookup concept, moves to a small `rbs-filters` lookup error). The crates that depend on `rbs-params` are `rbs-filters`, `rbs-sources`, `rbs-record` (`Values`), `rbs-app` (the filter editor and host) and `rbs-audio-filters`; `rbs-api` does not (its `FilterField` is its own wire type, mapped in `rbs-app`). `rbs-params` is added to `.github/CODEOWNERS` because `Values` is copied on the `ParamReceiver::update` path. A separate crate, not `rbs-graph`: `rbs-graph` is on the hot-path and CODEOWNERS list, and `NodeDescriptor` says settings schemas arrive with the plugin SDK, a design this ADR must not pre-empt. `rbs-params` is an internal stepping stone, not the SDK's schema; the SDK ADR may supersede it. It is a new crate and a layering addition, so the review below covers it.
   The schema grows what audio needs:
   - `Number` gains `curve: Curve` (`Linear` or `Log`; `Log` requires `min > 0`).
   - `Toggle { default }` and `Choice { options: &'static [(&'static str, &'static str)], default }` (stable key and label; `default` is a key that must be one of the options, at most 255 options, checked by the conformance suite).
   - `Value::Toggle(bool)` and `Value::Choice(u8)` (index into `options`), next to `Number` and `Color`.
   - `Field` gains `help: &'static str`, one plain sentence the UI shows with the control.
   `Field`, `FieldKind` and `Value` become `#[non_exhaustive]` and are built with constructors (`Field::number(key, label, ...)`, `.with_help(..)`, `.log()`), so adding a field later is not a break. Constructors do not panic (rule 8): they record what they are given, and the conformance suite rejects an invalid schema (for example `Log` with `min <= 0`); `Values` refuses invalid input at run time as before. The workspace is the only user today (the plugin SDK is unreleased), so P9 is not engaged, but the constructors are the contract the SDK inherits.
   All of `Values::defaults`, `from_pairs`, `with`, `to_pairs` and `rbs_sources::filter_values`, `filter_values_lenient`, `filter_settings` take `&[Field]` instead of `&dyn FilterType`.
   **Storage in `Settings`:** a number as `Float`, a colour as `Text` (`#rrggbb[aa]`) as today; a toggle as `Bool`; a choice as `Text` holding the option's key (stable if options are reordered or inserted). Strict conversion refuses a wrong kind or an unknown key (`WrongKind`, `UnknownChoice`); lenient conversion (used when loading) falls back to the field's default. API JSON uses the same forms. `video-filters.md` (the values and settings paragraphs) is updated in the same change.
   `MAX_FIELDS` 12 grows `Values` from 8 to 12 slots, which is copied under the latest-value lock in `ParamReceiver::update` for every video filter too; the first PR measures this (P15). `rbs-filters` gains its own conformance rule "at most 8 fields".
3. **Audio filter types and nodes.** A new crate `rbs-audio-filters` depends on `rbs-core`, `rbs-graph` and `rbs-params` only (no GPU, no OS API, no `rbs-audio`). It holds:
   - `trait AudioFilterType: Send + Sync + 'static { fn type_id; fn name; fn fields; fn make(&self, setup: DspSetup, values: &Values) -> Result<Box<dyn AudioDsp>, ParamError>; }` with `DspSetup { format: AudioFormat, block_frames: u32 }`.
   - `trait AudioDsp: Send { fn set(&mut self, values: &Values); fn reset(&mut self); fn process(&mut self, channels: &mut [&mut [f32]], frames: usize); fn meter(&self) -> Option<Arc<FilterMeter>>; }`. `meter` is called once, before the node is adopted (like `FilterNode::new` returning `Arc<FilterStats>`), so the studio keeps the `Arc` and the executor thread owns the DSP. `make`, `set` and `reset` run off the audio thread or at `prepare`; `process` never allocates, blocks, locks or does I/O (P6). All state is sized in `make` from `DspSetup`. The DSP sanitises its output (no NaN or infinity, denormals flushed).
   - `FilterMeter`: two `AtomicU32` holding `f32` bits, `input_peak_db` and `gain_reduction_db`, stored with `Relaxed` once per block by a gate (a gain filter has no meter); the UI reads them at its 30 Hz meter tick only while an editor that shows them is on screen.
   - `AudioFilterNode` (kind `AudioFilter`, one audio input `in`, one audio output `out`). In `process` it applies the latest values from its `ParamSender` (ADR-0023) at the start of the block, copies the input block to its output buffer, runs the DSP in place and commits with the input's timestamp. No input block: it publishes nothing and the consumer hears silence. An input block whose format or length is not the graph's is dropped and counted (as the mixer's `invalid_inputs`). `prepare` calls `reset` on every join of the schedule (a filter that comes back from Standby starts with a closed gate and no stale state); a parameter edit never resets it (tested). A filter makes no click on a parameter change (the Gain ramp above; the gate's gain only moves at the rates above).
   - `catalogue()`, and `conformance::check_type` (Tests).
   Filters here add no latency (no look-ahead, same-tick execution in one partition). A look-ahead limiter needs latency reporting in the node contract and is a later decision.
4. **Catalogue v1.**

   | Type id | Name | Fields (key: range, default; unit) |
   | --- | --- | --- |
   | `org.rbs.audio-filter.gain` | Gain | `gain` -30..+30, 0; dB, step 0.5 |
   | `org.rbs.audio-filter.noise-gate` | Noise gate | `open_threshold` -80..0, -40; dB. `close_threshold` -80..0, -46; dB. `attack` 0.1..100, 5; ms, log. `hold` 0..500, 100; ms. `release` 5..1000, 150; ms, log. `range` -80..0, -80; dB |

   Gain is the only boost in the product: the fader stops at 0 dB. **Gate semantics (testable):** the detector is a peak envelope follower over all channels (linked, so a stereo pair opens and closes together): per sample `env = max(|x|, env * decay)`, with `decay` for a fixed 40 ms time constant, so the level of a sine does not fall at every zero crossing. The ripple of the envelope on a sine of frequency `f` is `8.7 / (2 * f * 0.040)` dB (2.2 dB at 50 Hz, 3.6 dB at 30 Hz), so with `hold` 0 the gate does not chatter on a tone above the open threshold as long as the gap between the two thresholds is larger than that ripple; a smaller gap can chatter and the help text says so. The long constant also delays closing after a loud transient by about `0.040 * ln(level ratio)` seconds on top of `hold`; the digital-silence floor is -120 dB. The gate is *open* while `env >= open_threshold` and opens from closed at that moment; it stays open while `env >= close_threshold`; `hold` is the time since `env` was last at or above `close_threshold` (a level between the two thresholds keeps the hold timer reset); when `hold` has run out it closes. The gain moves linearly in dB at a rate of `|range| / attack` dB per ms when opening and `|range| / release` dB per ms when closing, so a partial transition (the level returns during the release) reverses from the current gain with no jump. `range` is clamped to at most 0 dB (0 dB means a gate with no effect); -80 dB is a gain of 0.0001, not exact zero. `close_threshold` above `open_threshold` is clamped to it inside `set`; the schema checks ranges per field only, an API patch that violates the order is accepted and clamped, and the UI constrains the two handles so they cannot cross. Thresholds and times take effect at once (they are not audio), and a change of `hold`, `attack` or `release` during a transition changes only the rate: the gain never jumps; the Gain filter's `gain` is ramped linearly in amplitude over 10 ms. The gate has no sidechain input.
5. **Binder.** With `with_audio`, a source with an audio output and no video output binds its filters like the video chain, with these specifics:
   - A filter node takes the **source's partition** (`set_partition`), so the chain stays inside the audio partition and no queue appears between the source and the filter (ADR-0026, ADR-0037).
   - The binder gets audio pin helpers (`audio_pins`, a kind-aware `tail`), and chain links and the mixer link use the audio output pin of the previous node. The mixer link comes from the **tail** of the chain (the source node when the chain is empty) and is rebuilt on every chain change; `BoundAudio::producer` is that tail, and `BoundMixer::inputs` still lists one entry per source.
   - The chain kind follows the source: an audio chain for a source with an audio output and no video output, where a filter's descriptor must be `NodeKind::AudioFilter` with an audio input and output; the video path is unchanged. The code that reads `bound.source.pins.output` for the video chain and `pins.audio` for the mixer link (the mixer link block and the `outs` map keyed by the source node) switches to the tail's audio pin. `rbs_sources::NodeTypeTable` also installs the audio catalogue's descriptors, next to the video ones. When a filter is removed its node is retired with its links; the mixer link is re-made from the new tail on the same sync, and the retire and `heal` tests cover a removed filter with a live mixer link.
   - Domain mismatches are reported by type kind: an audio filter type on a source with video, or a video type on an audio source, is `NoVideoPins` / the new `NoAudioPins`. `FilterOnAudioSource` is removed (audio sources accept filters now); the binder test and the `rbs-record` problem mapping that used it are updated. A source with video and audio outputs still binds only its video (`AudioOnVideoSource`).
   - A disabled filter keeps its node in the graph and is `Standby` (not in the schedule, no per-block cost); the node and its settings stay so re-enabling is instant, and `prepare` resets its state.
6. **Changing the chain tail costs a short dip; the mixer is not edited.** The mixer keys strips by producer, so adding, removing, enabling, disabling or reordering a filter that changes the tail gives the source a new strip: the old strip stops at once and the new one fades in from silence over 10 ms after the first block of the new tail, which arrives one tick late (a joining node has no output on its first tick, ADR-0020). Enabling a filter costs about 20 ms of reduced level (the silent first tick and the fade-in); disabling the last filter costs the fade-in and a cut of the old strip; a parameter edit never does this. This is accepted by the owner in this version (recorded in the review), described in `audio-filters.md`, and measured by the tests below. Making it seamless (a two-phase relink that moves the mixer link only after the new node has produced a block, or a crossfade state in the strip) is a later change with its own P15 review; the design leaves room for it because `BoundAudio::producer` is the only thing it touches.
7. **Position in the signal path.** Input node (with `sync_offset`) -> filter chain -> strip fader and mute -> post-fader meter -> mix. Filters run before the fader, so boost and gating come before volume. The ducker's pre-fader key tap (phase C) is out of scope here and needs a named tap in the graph, decided in its own ADR.
8. **Studio.** For every scheduled audio filter node `Studio` creates an `AudioFilterNode` (`adopt::<()>` in the audio partition, its own take path on retire, not the GPU render partition of video filters), keeps its `ParamSender` and meter, sends values on `changed_filters`, and drops the instance when the node is retired. `filter_of` looks in both catalogues. If `make` fails, the studio instantiates a pass-through DSP and reports the filter in `filter_problems`: the source stays audible and unfiltered rather than silent (a missing instance would drop the node from the plan, ADR-0020). `source.list` rows carry an audio source's filters; a client of 1.8 to 1.15 sees rows with filter types it does not know and cannot add them (what it shows is its own). `Studio::preview_filter` (live values while a control is dragged, no model edit) works for audio filters; the final value is one undo step through `set_filter_settings`. An audio filter that errors in `process` is bypassed by the executor, so its source is silent until it recovers; this is reported like any node failure (restart with back-off, ADR-0024), the user hears silence from that source until it recovers, and it is acceptable for a gate and a gain because the DSP cannot fail on valid input.
9. **Control API 1.16.** The `filter.*` methods work on audio sources. `filter.types` takes an optional `domain` (`"video"`, `"audio"`, `"all"`); the default is `"video"`, so a 1.8 to 1.15 client sees exactly what it saw before and never meets the new kinds. Each entry gains `domain`, per field `help` and `curve` (`"linear"` or `"log"`), and the kinds `"toggle"` and `"choice"` (with `options: [{key, label}]`). `filter.add` refuses the wrong domain in both directions (an audio type on a source with video, a video type on an audio source) with `invalid_params`. `apply_look` keeps refusing audio sources. A gain above 0 dB can push the mixer's sum above 0 dBFS (the mixer has no clip stage, ADR-0081); what an encoder does above 0 dBFS is the encoder's own (no clamp is guaranteed on the float path), so a gain filter must not be assumed safe; a limiter filter is the later answer and `audio-graph.md` notes this. The methods keep their class (`control`, one undo step each). `control-api.md` and its refusal text are updated.
10. **UI (visual, owner approval first).** The Audio tab of Properties gains a **Filters** section below Sound with the same list as the video Filters tab (add menu from the catalogue, reorder, enable, remove) and one parameter editor per filter generated from its schema with library components only: a `Slider` with typed value (linear or log) for a number, a `Toggle`, a `Select`, each with its `help` line, units and a reset to the default. The gate's editor also shows the live input level with its two thresholds on one bar and the current gain reduction, read from `FilterMeter` only while visible. The layout is proposed to the owner with screenshots before any UI code (CLAUDE.md rules 15 and 16). The tail-change dip is mentioned in the editor's help text as part of this visual proposal. A "filters" mark on a Mixer strip whose source has enabled filters is a separate visual proposal.
11. **Zero cost (P13).** A source without filters adds nothing. A disabled filter keeps its node in the graph (Standby: not scheduled, no per-block work) and holds its small DSP state until it is removed. An enabled filter adds one node to the audio partition, no thread and no allocation per block. The meter costs two relaxed stores per block per gate.
12. **Hot path (P15).** `rbs-audio-filters` and its nodes are on the audio hot path (`hot-paths.md`, first row, "audio filters"; the crate is added to that file, and CODEOWNERS already covers `/crates/rbs-audio*/`). Every PR that edits them has the benchmark (`cargo bench -p rbs-audio-filters`: block cost per filter at 48 kHz stereo, 480 frames, and a chain of four), the allocation guard test, the `hot-path-review` checklist and a human maintainer's approval. `MixerNode` is not edited. The schema PR measures `ParamReceiver::update` of a video filter with the larger `Values`.

## Tests

- **Layering**: a CI assertion (`cargo tree`) that `rbs-audio-filters` and `rbs-params` depend on neither `rbs-gpu` nor `wgpu`.
- **Schema conformance** (`rbs-params` and each catalogue): key charset and uniqueness, defaults inside range, `Log` only with `min > 0`, a choice default is one of its options, field count at most the limit (12; 8 for video), `Values` round trip through `Settings` for every kind, unknown choice key lenient fallback and strict refusal.
- **DSP** (`rbs-audio-filters`, driven by blocks and a `TestClock`, no sleeping): gain at 0 dB is bit-exact; gain follows its value with the 10 ms ramp; the gate opens at the open threshold, holds, closes after `hold`, attack and release timings measured in blocks, hysteresis respected, `close_threshold` above `open_threshold` clamped; no NaN, infinity or denormal for silence, full scale and NaN input; reset after Standby; allocation guard over `process` including `ParamReceiver::update`; a value change makes a step no larger than the ramp allows; the gate with `hold` 0 on 100 Hz and 50 Hz sines above the open threshold (thresholds further apart than the ripple) does not chatter; a change of `release` during a release does not jump the gain; a level between the two thresholds keeps the gate open and resets the hold timer; the three level transitions (open, hold, close) and a return of the level during the release reverse from the current gain; a parameter edit does not reset the DSP and a join does; the meter `Arc` seen by the studio changes with the audio.
- **Binder** (`rbs-scene`): filter nodes in the source's partition; mixer link and `BoundAudio::producer` are the tail and follow add, remove, enable, disable, reorder and a source settings rebind; domain mismatches give `NoVideoPins` / `NoAudioPins`; a disabled filter is in the graph and not in the plan; a source without filters binds as before.
- **Chain edits**: a sine through enable, disable, reorder and remove of a filter: the dip is at most two blocks plus the 10 ms fade, the output has no NaN, and the measured step and energy loss are recorded in the spec so a later seamless relink can be compared. A parameter edit alone makes no step beyond the ramp.
- **Studio** (`rbs-record`): instance created, previewed and retired for an audio filter; a failing `make` gives a pass-through and a `filter_problems` entry; a real-audio test with a gate.
- **API** (`rbs-api`, host): `filter.types` default (an old client sees only video types, never `toggle` or `choice`) and `domain` forms, domain refusals both ways, wire forms of the new kinds, `apply_look` refusal.
- **Scene document** (`rbs-user-data`): round trip of an audio filter; loading a file with an unknown audio filter type keeps it and reports `UnknownFilterType`.

## Consequences

- The owner's rule has a mechanism: a new filter is a schema; the UI, API, persistence and undo come from it with no per-filter UI code.
- Video and audio filters share one editor model, one API and one persistence path; a plugin `AudioFilter` can later implement the same traits through the SDK.
- `rbs-params` and `rbs-audio-filters` are new crates (a layering addition covered by this review); `MixerNode` is not edited.
- Scene files with audio filters play unfiltered in builds that lack the types.
- Enabling, disabling, adding, removing or reordering a filter that changes the chain tail costs about 20 ms of reduced level; parameter edits never do.
- Audio filters add no latency here.

## Alternatives considered

- **Gain and gate as fixed per-strip parameters inside `MixerNode`.** Edits the hottest node, cannot be reordered, extended or replaced by a plugin. Rejected.
- **A separate audio filter model** (own list, API, undo). Duplicates ADR-0062 and gives two editors. Rejected.
- **Audio crates depending on `rbs-filters` for the schema.** Pulls `wgpu` into the audio layer (P1). Rejected.
- **The schema in `rbs-graph` or `rbs-core`.** `rbs-graph` is a hot-path crate and its descriptor defers schemas to the SDK; `rbs-core` is time, clocks and capabilities. A small `rbs-params` crate is the least coupling. Chosen.
- **A stable pass-through tail node, created only for sources that have a filter.** Keeps the producer fixed while filters change behind it and costs nothing for unfiltered sources, but it adds a node and a block copy per filtered source, and the first filter and a joining node's silent first tick still leave a gap. Not chosen for this version; the seamless relink above is the preferred later fix.
- **A `continues` field on the mixer strip** (carry its state to a new producer). It cannot work alone: `present` is recomputed each tick and the new tail has no block for a tick, so the fade-in comes back. Rejected after review.
- **Linear-only number fields.** A frequency or time on a linear slider is unusable; `Curve` is the minimum.

Should-fix, all adopted: schema placement (new `rbs-params` crate), Studio audio partition and fallible `make` (item 8), failure modes (items 3 and 8), API 1.16 compatibility through a `domain` parameter defaulting to video (item 9), crate dependencies and `DspSetup` and `FilterMeter` definitions (item 3), spec list (Specs section), gate semantics and the threshold-order rule (item 4), signal path wording (item 7), implementation order. Round 2 (same reviewer, 2026-11-09): changes requested. Blocking: the mixer `continues` design cannot carry presence (the strip's `present` is recomputed every tick and a joining node has no output on its first tick), so it neither removed the dip nor avoided a pop (resolved: item 6 now accepts and documents the dip, drops `continues`, and does not edit the mixer; the seamless relink is a later change).
