# Spec: Control API

- Status: Draft
- Owner crate(s): `rbs-api` (first slice implemented, see "Implementation status"), `rbs-api-ws` (WebSocket adapter implemented: loopback, and TLS for network access), `rbs-api-ipc` (local IPC adapter implemented and served by `rbs-app`)
- Related ADRs: [0008](../adr/0008-ui-as-api-client.md), [0013](../adr/0013-zero-cost-when-unused.md), [0021](../adr/0021-scene-collection-model.md), [0035](../adr/0035-meters-as-native-layers.md), [0044](../adr/0044-control-api-protocol-and-security.md), [0052](../adr/0052-ai-agent-control-through-mcp.md), [0102](../adr/0102-output-size-distinct-from-canvas.md)

## Purpose

The single way to control and observe the engine, used by the desktop UI, remote clients, CLI, Stream Deck and other hardware panels, scripts, user-built apps and tests.

## Shape

- **Commands** change state (add source, set transform, start stream). Commands that edit the scene collection go through its operations and the one shared user undo stack. Live actions (program switch, record and stream start/stop) and client-scoped `ui.*` commands are not put on the undo stack (see below, ADR-0021).
- **Queries** read state (scene document, devices, adapter capabilities, settings).
- **Events** stream changes and metrics to subscribers.
- The Rust `serde` types in `rbs-api` are the schema; every request, response and event type is `Serialize + Deserialize`. A JSON Schema document is generated from them, checked in, served by `api.describe`, and used to generate client libraries (TypeScript first).
- All requests, from every client and from the desktop UI, are applied one at a time on the control thread, through a `ControlTarget` trait the composition root implements. That thread owns the studio, the scene collection, recording profiles, output destinations and canvas settings.

## Layers

| Part | Crate | Depends on |
| --- | --- | --- |

No engine, adapter, network, IPC, async-runtime or UI crate |

Framing is its own (RFC 6455 server side), so a message over the limit can be skipped without buffering it and the connection kept; no async runtime |
| Local IPC transport (Unix domain socket, named pipe) and its blocking client | `rbs-api-ipc` | `rbs-api`, `libc` (Unix), `windows` (Windows) |

| Which transports run; the `ControlTarget` implementation | `rbs-app`, `rbs-cli` | everything |
| Remote control settings file (`remote-control.toml`: on or off, port, token hashes), the config directory and the `tokens.*` answers on that file, shared by the composition roots | `rbs-remote-settings` | `rbs-api`, `serde`, `toml`; no toolkit, engine or adapter crate |

`ControlTransport` adapters accept connections, exchange whole UTF-8 messages and report the peer: transport kind, loopback or not, whether the channel is TLS (`PeerInfo::secure`), `Origin` and `Host` headers when present, OS user for IPC. The inbox refuses a WebSocket peer that is neither loopback nor TLS (`Refused::Insecure`), whatever the adapter did. They run their own I/O and push `Connected`, `Message` and `Closed` events into a bounded inbox owned by `rbs-api`; `rbs-api` sends through a per-connection handle. Every adapter passes the transport conformance suite (`rbs_api::conformance`, feature `conformance`).

## Threads

| Thread | Exists | Does |
| --- | --- | --- |
| Adapter I/O | While its transport is on | Accept, read, write; pushes into the API inbox |
| API thread | While remote control is on | Owns all sessions; handshake, auth, scopes, limits, queues; serializes each event once; sleeps on one wake primitive shared by the transport inbox, the response channel and the event slots, until the state machine's next deadline; no periodic wake-up |
| Sampling (on the API thread's deadline) | While a session subscribes to a latest-value topic | Reads levels and statistics at the requested rate from read-only, lock-free handles the composition root provides; never wakes the control thread |
| Control thread | Always (existing) | Applies requests from two queues (local UI, API) behind one wake-up, UI first; sends responses tagged with session and request ids, and fills per-state-key event slots; never blocks on API output |

- The session logic is a pure state machine, `handle(event, now)` and `next_deadline()`, that tests drive directly with `TestClock` (ADR-0032); the API thread only wraps it.
- Adapters apply back-pressure per connection: a connection that has used its queue quota is not read until it drains, so one client cannot fill the transport inbox.
- Each session has at most one request in flight to the control thread and a bounded queue behind it; the API thread forwards from sessions in round-robin order. Responses on one connection come in request order, so a long command (for example `canvas.set`, which restarts the studio) delays that connection's later requests; while it runs on the single control thread, other sessions' and the UI's requests also wait for it. A dispatched command is never cancelled.
- Output from the control thread never blocks it and never loses a response. Responses go into their own channel sized by the number of requests that can be in flight: one per connection under the connection cap. A closed session's in-flight request stays counted, and its connection slot stays taken, until its response is drained and discarded. So a send cannot fail, whatever fills the transport inbox. Events go into per-state-key latest-value slots; a newer event replaces the older one. A single `events pending` flag replaces one message per write: the API thread atomically swaps it to clear before it reads the slots, and a writer that changes it from clear to set signals the wake primitive. The wake primitive is permit-based, so a signal sent before the API thread sleeps is not lost; pushes to the transport inbox and the response channel signal it the same way.
- Every state key has a change counter `seq` that the control thread increments on every change of that state, subscribed or not. It builds event payloads only for topics in a subscriber mask. The in-process UI is a permanent subscriber registered on the control thread and gets the same event types and `seq`. The API thread sets its sessions' mask bits before it forwards `events.subscribe`; the control thread answers with the `seq` read after that.
- The desktop UI's level meters and preview do not go through `rbs-api`: the local UI gets the shared meters (ADR-0035) and the preview endpoint as local-only attachments.

## Wire protocol

JSON-RPC 2.0 over UTF-8 JSON text messages. WebSocket subprotocol: `rbs.v<major>` (version 1: `rbs.v1`). A client that offers subprotocols must offer `rbs.v1` (the upgrade is refused otherwise); a client that offers none speaks version 1. Binary messages close the connection with 1003.

WebSocket close codes: 1001 when the server stops, 1009 for a message before authentication over the limit, and in the private range `handshake_timeout` 4001, `auth_failed` 4002, `unsupported_protocol` 4003, `too_many_connections` 4004, `revoked` 4005, `too_slow` 4006. The close frame's reason text is that name. Protocol violations close with 1002 (1007 for text that is not UTF-8).

- **Request:** `{"jsonrpc":"2.0","id":7,"method":"record.start","params":{...}}`. Method names are `namespace.verb`.
- **Response:** `{"jsonrpc":"2.0","id":7,"result":{...}}` or `{"jsonrpc":"2.0","id":7,"error":{"code":-32010,"message":"...","data":{"kind":"scope_denied", ...}}}`. `data.kind` is the stable machine-readable error; `message` is for logs.
- **Event:** a notification `{"jsonrpc":"2.0","method":"event","params":{"topic":"record.state","seq":42,"data":{...}}}`.
- Batch requests are refused in version 1 (`batch_unsupported`).

### Local IPC

The same JSON-RPC messages over a local stream (`rbs-api-ipc`):

- **Endpoint.** Linux: `$XDG_RUNTIME_DIR/rbs/control.sock`, or `/tmp/rbs-<uid>/control.sock` without it; macOS: `$TMPDIR/rbs/control.sock`; Windows: the named pipe `\\.\pipe\rbs-control-<user SID>`. The Unix directory is made with mode 0700 and refused unless it is a real directory (not a symbolic link) owned by the current user that nobody else can enter; the socket is mode 0600. While serving, the server holds an advisory lock on `control.sock.lock` beside it: a second server is refused before it touches the socket file, and under the lock a socket file left by a process that ended is replaced. The pipe is created with a protected DACL that grants access to the current user's SID only, `PIPE_REJECT_REMOTE_CLIENTS`, and `FILE_FLAG_FIRST_PIPE_INSTANCE` for its first instance (a name someone else holds stops the server); one instance always waits, so the name stays the server's.
- **Peers.** The server asks the OS who the peer is (`SO_PEERCRED` on Linux, `getpeereid` on macOS and the BSDs; on Windows the user of the connection's own token, read while briefly impersonating the client at identification level, not looked up by process id) and closes the connection of any other user before it reaches the API. Every accepted peer is a same-user IPC peer, which `session.hello` authenticates with all scopes. The client checks the server the same way (Windows: the token user of the server process, found by `GetNamedPipeServerProcessId`; it opens the pipe with `SECURITY_IDENTIFICATION`, so the server can read its identity but not act as it). A Windows client whose pipe instances are all busy for a moment waits for one (`WaitNamedPipeW`) within its connect timeout and sends nothing to a server of another user.
- **Framing.** An accepted connection starts with the server's 4-byte preamble `RBS` `0x01` (framing version 1). Then each message in either direction is a 4-byte big-endian header, bit 31 clear and the low 31 bits the length, followed by that many bytes of UTF-8 text. A header with bit 31 set is a close frame: a big-endian `u16` code (the WebSocket close codes above; 1000 from a client closing normally) and up to 123 bytes of reason text. A connection refused at accept (connection cap) gets a close frame with 4004 instead of the preamble. A message over the connection's limit is skipped as it arrives and reported as `Oversized`; the connection keeps working. A message that is not UTF-8 ends the connection.
- **Threads.** One accept thread while serving, and a reader and a writer thread per connection, each blocked in the OS until there is work: no periodic wake-up. The reader stops reading a connection that used its inbox quota until the API thread drains it; output per connection is bounded (1 MiB, then `Full`, `Writable` when half has drained). A write that makes no progress for 10 s ends the connection, so a peer that stops reading cannot hold its slot. When the server closes a connection, what is queued and then the close frame are written, also while its reading is paused. On stop, the queued output is dropped, every connection gets its close frame (1001), and after one grace period for all of them (1 s) the streams are cut. The accept thread waits on the listener and a wake-up of its own, so stopping does not depend on the socket file.

### Handshake and authentication

1. Client: `session.hello {protocols: ["1.0"], client: {name, version}}`.
2. Server: `{protocol: "1.2", instance}`. Any `1.x` offer is accepted and the answer names the server's own minor version; a client checks it before calling methods added in a later minor (for example `stream.*`, added in 1.1, or the stream settings, added in 1.2). `instance` is a random id for this server run; `seq` counters restart with it.
3. Client: `session.authenticate {token}`.
4. Server: `{scopes, server: {name, version}}`, or `auth_failed` and close.

Until the `session.authenticate` answer arrives, the pre-authentication message limit (4 KiB) applies, so a client waits for it before sending larger requests. On IPC, a peer the OS identifies as the same user is authenticated by step 2, which then also returns its scopes. Since protocol 1.73 (ADR-0052): such a peer may still send `session.authenticate {token}` as its first request after `session.hello` (whose answer still reports all scopes); the session then has exactly the token's scopes for the rest of its life (narrowing, never widening), and the answer reports them (`scopes`; the token's permission, a new `irreversible` field, follows with the irreversible-actions permission). It is refused (`invalid_request`) once any other request was admitted, and a second time. A wrong token gets `auth_failed` and close; IPC has no back-off (the peer is the same user, the token has 256 bits). Revoking the token closes the session. Narrowing is voluntary: a peer that does not authenticate keeps all scopes. So an AI agent's `rbs-mcp` is limited by its own token on IPC too. Session tests on `TestClock` cover each case. Before authentication every other method returns `not_authenticated`. A connection that has not authenticated within the handshake timeout is closed. `auth_failed` is the same for an unknown and a wrong token.

**Tokens.** Text `rbs1_` followed by 64 lowercase hex digits (32 bytes of OS randomness). The server stores `SHA-256` of the token's UTF-8 bytes, as lowercase hex, and compares in constant time. Each token has a user-given name and scopes, is shown once at creation (UI or `rbs-cli token create`), and can be revoked; revoking closes its sessions.

Test vector: token `rbs1_000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f` is stored as `73aa00dce5b7afd18306d160c3de0e6e56db9ade3300340da67c2021c402f04b`.

**Channels.** A token is sent only over loopback, IPC, or TLS whose certificate the client verified (a CA or a pinned fingerprint). Client libraries must refuse to send it after a certificate mismatch. IPC peers are identified by the OS: a peer running as the same user is authenticated without a token.

### Scopes

| Scope | Allows | From |
| --- | --- | --- |
| `read` | Queries, `api.describe`, event subscriptions | Any authenticated peer |
| `control` | Scene and source changes, capture-target lists, mute and volume, transitions, program switch, record and stream start/stop with configured profiles and destinations, undo and redo, `ui.*` | Any authenticated peer |
| `admin` | Settings, explicit file paths and destinations (an explicit file is never overwritten; its path is logged) | Loopback and IPC; remote only with the separate "Allow remote admin" setting |
| `plugins` | Plugin management | Loopback and IPC only |
| `tokens` | Token management | Loopback and IPC only |

Every method declares one scope in the schema; where a parameter would need a different scope it is a separate method; a call outside the session's scopes returns `scope_denied`. A hardware panel token is `read` + `control`. The in-process UI and same-user IPC peers have all scopes.

Event topics declare a scope the same way: `settings.changed` carries recording folders, which only `admin` reads (`settings.get`), so subscribing to it needs `admin`; every other topic needs `read`.

### Subscriptions and events

- `events.subscribe {topics: [...], rates: {"audio.levels": 20}}` returns the current `seq` per state key; `events.unsubscribe`.
- State queries return `{seq: {state_key: n}, data}`, so a client knows which events its snapshot already includes and ignores events with an equal or lower `seq`.
- A state event carries the whole current state of its state key, never a delta, so a newer event replaces an older one without loss. Topics are kept small. A state key is a topic name plus an optional object id (for example one key per source); `seq`, coalescing and the `seq` maps in queries and `events.subscribe` use the state key, while subscriptions and the subscriber mask are per topic name. The first slice's topics have no object id: `source.changed` carries the whole program-scene source list. A client applies an event only when its `seq` is higher than what it holds; skipped `seq` values are normal and need no re-query.
- Sampling of a latest-value topic starts when `events.subscribe` is handled on the API thread, so a sample can arrive before the subscribe answer. Samples carry a per-server sample counter as `seq`, which has no entry in `seq` maps.
- State topics are sent when the state changes. Latest-value topics (`audio.levels`, `stats`) are sampled at the client's rate, capped (30 Hz levels, 1 Hz statistics in version 1), and coalesced per session.
- Each session's outgoing queue keeps only the latest event per state key, so it is bounded by the number of live state keys and cannot overflow. There is no `events.lost`.

### Versioning

Protocol version `major.minor`, independent of the `rbs-api` crate's semver. Minor: new methods, event topics, optional request fields, response fields, enum values in responses, error kinds. Major: removing or renaming anything, changing a type or meaning, a new required request field. Clients ignore unknown response fields and treat unknown enum values and error kinds generically. The server supports the current and the previous major for at least one release cycle (P9). A CI tool compares the generated schema with the checked-in one, classifies each difference, and fails unless the version bump matches. A new value of an existing request field, which an older server refuses with `invalid_params`, is minor too (ADR-0111): a client checks the protocol version before sending it. When such a value selects another answer shape, the method's answer schema becomes a `oneOf` of the shapes, selected by the request, and the classifier counts an added `oneOf` branch as minor. Exception (ADR-0098, owner-accepted): the preview outcome of `canvas.transition` is defined by the app's setting; protocol 1.31 documents its default change from swap to keep.

## Exposure and limits

- Off by default. When off, no server exists: no thread, socket, timer or event buffer (ADR-0013 rule 1).
- On: WebSocket binds to loopback. Network access is a separate setting; the app shows when RBS is reachable from the network. Non-loopback connections require TLS.
- Before the WebSocket upgrade completes: a request with an `Origin` header (including `Origin: null`) is refused unless the origin is on the user's allow list (`null` can never be added to it); the `Host` header must be a loopback name or address, a configured host name, an address the server is bound to, or the local address the connection was accepted on; an unspecified address (`0.0.0.0`, `[::]`) never matches.
- IPC endpoint: current user only. Unix: socket mode 0600 in a user-private directory. Windows: named pipe with a DACL for the current user's SID and `PIPE_REJECT_REMOTE_CLIENTS`.
- Caps: total connections, pending handshakes, connections per peer address (not applied on loopback, where every client shares one address). Pre-authentication messages are small (4 KiB). Repeated `auth_failed` delays further attempts with growing back-off: per connection on loopback, per peer address otherwise.
- Per session: maximum message size, request rate, queue length (`busy` when full).
- Responses come in request order, with one exception: refusals that protect the server are sent at once and can overtake the answer to an earlier request still in flight, because queueing them would make the queue unbounded. They are `busy`, `rate_limited`, `message_too_large`, and errors for messages whose request id cannot be read (answered with `"id": null`). Every other answer, including `scope_denied` and decoding errors that carry an id, waits its turn.
- Before authentication the server reveals only the handshake: a message naming any other method, known or not, gets `not_authenticated`, without the method list or parameter details.
- Transports read at most the connection's current message limit (4 KiB before authentication) and report a longer message instead of buffering it, so unauthenticated peers cannot make the server hold large messages.
- The pending-handshake cap counts and refuses only non-loopback peers, and the last slots of the connection cap are reserved for loopback and IPC peers, so remote clients, even a flood of connections the server refuses, cannot lock out local clients.
- Per-address caps and back-off group IPv6 addresses by their /64 prefix.
- Changing a token's name or scopes, or revoking it, closes its sessions; the client reconnects with what the token allows now.
- A peer that does not read its answers is closed once more than a limit of answers wait for it (events do not count: only the latest per state key waits).

Version 1 limits (from the first implementation, `rbs_api::Limits::default`):

| Limit | Value |
| --- | --- |
| Connections (including closed ones whose request is still in flight) | 64 |
| Pending handshakes (non-loopback peers) | 16 |
| Connection slots only loopback and IPC peers can take | 8 of the 64 |
| Connections per non-loopback address (IPv6: per /64) | 8 |
| Handshake timeout (connect to authenticated) | 10 s |
| Message size before / after authentication | 4 KiB / 1 MiB |
| Request rate per session | 50 per second, bursts of 100 |
| Requests queued behind the one in flight | 16 |
| Answers waiting for a peer that does not read | 64 |
| Unread messages per connection in the transport inbox | 8 |
| Authentication back-off per non-loopback address | 500 ms after the first failure, doubling, at most 30 s; forgotten 30 s after its delay ends; 1024 addresses remembered; an attempt released after its delay waits again if another attempt from the address failed meanwhile |
- Connections, authentication failures and `admin`, `plugins` and `tokens` calls are logged with the token name.

| --- | --- |

## API parity (ADR-0052)

Everything a user can do in the desktop app must be doable through this API, with the same validation and undo behaviour, except what is kept for the local user: entering the stream server and key, the remote control and network access settings, turning the irreversible-actions permission on for an existing token, and adding, removing and choosing the format of the virtual camera (protocol 1.12). The U20 test allows exactly these; a PR that adds a UI action adds its request. Planned additions, each a minor version with its own spec change:

- `profile.*` and `collection.*` for output profiles and scene collections (ADR-0051): list and switch are in protocol 1.4 (below); get, create, rename, duplicate, delete, import and export follow. None of them sets or reveals a stream server: `profile.import` drops the imported file's server and `profile.export` leaves it out. Exports to a path that exists are refused with `file_exists`; an import error gives the error kind, line and column, never text from the file.
- `scene.*`, `canvas.*` and the remaining `source.*` methods for the scene model's operations.
- `edit.apply {label, operations}` (`control`): a list of undoable scene operations only, validated as a whole, applied all or none, recorded as one undo step named `label`; waits for the serialisable scene operation type.
- An `effect` per method in the schema: `read`, `edit` (undoable, or reversed by another call with nothing lost, or only adds a new file and never replaces one: `project.export`, `replay.save`; owner 2026-11-15), `live` (record, stream and virtual camera start and stop, `profile.switch`) or `destructive` (removes something outside the undo history). Clients such as `rbs-mcp` ([MCP server spec](mcp-server.md)) turn it into tool annotations; a client treats a missing or unknown effect as `destructive`.
- A per-token permission, "Allow actions that cannot be undone". Without it, `live` and `destructive` methods, `edit` methods (undo, redo, program switch and `collection.switch` included) that change what is on air (for a canvas with any active output: its format, everything reachable from its program scene, nested scenes, shared sources and filters included, and its audio mix), adding or re-addressing a source of a type that opens network connections, and any location field (paths and URLs in source settings, recording folders, `record.start_to_file`, import and export paths; marked in the schema) whose value is not a local absolute file system path (URL schemes, UNC and `\\?\UNC` paths, device paths), are refused; a source type that does not declare itself local-only, with its location fields, counts as network with a new error kind `not_permitted` (code -32012, `data.reason` `irreversible`, `on_air` or `network`). A token store entry without the field has it, so existing tokens and same-user IPC peers keep today's behaviour; `tokens.create` takes an optional `irreversible` (default `true` when the caller holds the permission) and never gives more scopes or permission than the caller holds (`not_permitted`). `settings.set` is `edit`; its `canvas` field gets the on-air check. `ControlTarget::handle` receives the caller context (token name or a fixed label, and the permission).
- An audit record, with the caller label, for every `live` and `destructive` call and every `not_permitted` refusal, written on the API thread.
- The scopes and effects of `profile.*` and `collection.*` are listed in ADR-0052 decision 1.

### Item styles (protocol 1.3)

`source.list` rows, and the rows of `source.changed`, carry `item` (the source's item id in the program scene) and, for video sources, `layout`: `{position, size, rotation, crop: [left, top, right, bottom], opacity, style}`, the layout the studio's canvas shows, in the current canvas's pixels (ADR-0110). `style` is `{shape: "rectangle" | "circle" | "ellipse" | "triangle" | "arrow", radius, border?: {width, color}, shadow?: {offset, blur, color}}`; lengths are in the item's box units (canvas pixels for an item on the canvas), colours `#rrggbb` or `#rrggbbaa` (answers use `#rrggbbaa`), and `{}` is the plain picture. A 1.2 client ignores the new fields.

`item.set_style {item, style}` replaces the whole style of the item's layout on the studio's canvas: its override for that canvas when it has one, else its default layout, which every canvas without an override shows (as the app's Properties panel does). Refusals: `not_found` for an unknown item; `invalid_params` for an item that places a scene, a radius on a circle or ellipse, a colour in another form, a negative radius or blur, a border width of 0 or less, numbers that are not finite, or unknown keys. Each call is one undo step on the shared stack and publishes `source.changed`; setting the style an item already has changes nothing. The shadow is saved and returned but not drawn yet.

### Output profiles and scene collections (protocol 1.4)

The first part of the `profile.*` and `collection.*` methods of API parity (ADR-0051, ADR-0052 decision 1): listing and switching, what the File menu's Output profile and Scene collection pickers run. Creating, renaming, duplicating, deleting, importing and exporting follow as their own minor versions.

`profile.list` and `collection.list` answer `{entries: [{id, name}], current, pending}`: every entry of the library by name (ignoring case, as the app lists them), with its stable id (`EntryId`, user data spec), the id of the one in use, and whether a switch asked for through the API is still being made. They are `failed` while no user data is loaded (before the app read it, and in hosts without user data). Neither carries anything else from the entry (no folder, server or key).

`profile.switch {id}` and `collection.switch {id}` switch as the File menu does. The control thread answers `not_found` for an id the library does not have; `conflict` while recording or streaming on either canvas ("stop the recording before ..." and "end the stream before ...") and while another switch asked for through the API is still being made; nothing happens for the id in use. Otherwise the answer means the switch was handed to the app, which makes it with its own checks (a scene collection also needs the studio running and not restarting) and loads the entry. Until the app is done, `pending` is `true` and `record.start`, `record.start_to_file` and `stream.start` are refused with `conflict`, so no output starts with what the switch replaces. The app is done when the switch was made or refused: for an output profile after its recording and stream settings (main and vertical) and stream key account reached the control thread, for a scene collection after the studio restarted with it or kept the one before. Then `pending` is `false`, and `current` shows the outcome: still the old id means the app refused the switch or could not load the entry (a file that became unreadable or newer), and its error line says why. A collection switch restarts the studio as a canvas change does, so it publishes `canvas.changed` and `source.changed`; a profile switch publishes `settings.changed`. A `library.changed` topic, carrying the lists and the outcome, follows with the methods that change the libraries; until then a client reads `*.list` after those events.

Effects (ADR-0052 decision 4, when effects join the schema): the lists are `read`, `profile.switch` is `live` (it changes where the next stream goes), `collection.switch` is `edit` with the on-air check, which always passes here, because switching is refused while any output runs.

### Crop (protocol 1.5)

`source.list` rows, and the rows of `source.changed`, carry `picture_size: [width, height]` for a video source whose picture the studio has seen in this run (ADR-0058; absent before it ran, and for sound-only sources). `item.set_crop {item, crop: [left, top, right, bottom], keep_scale?}` sets the crop of the item's layout on the studio's canvas, with the `item.set_style` rule (its override for that canvas when it has one, else its default layout). With `keep_scale` (default `true`) the box changes too, so a source pixel keeps its size on the canvas and the part that stays keeps its place; `false` sets only the crop and what stays fills the box. Refusals: `not_found` for an unknown item; `invalid_params` for an item that places a scene, a crop that leaves less than one pixel of the known picture, or unknown keys; `failed` for `keep_scale` while the picture size was never seen. Each call is one undo step and publishes `source.changed`; the crop the item already has changes nothing. A 1.4 server answers `method_not_found`.

### Scenes, lock and source sound (protocol 1.6)

ADR-0059. `scene.list` answers `{scenes: [{id, name}], program, sources: [{id, name, kind}]}`: the scenes the studio's canvas may show, in the order the Scenes panel shows them (creation order for now; reordering is a later minor version), the scene on air, and every source of the collection (for `item.add`). The topic `scene.changed` carries the same answer whenever a scene is added, removed or renamed, a source is added, deleted or renamed, or the program changes. `source.list` rows and `source.changed` stay one row per source item of the program scene (a source placed twice has two rows, each with its own `item`) and gain the item's `visible` (absent when `true`) and `locked` (absent when `false`) and the source's `volume` and `muted`.

Refusals: `not_found` for an unknown scene, source or item; `invalid_params` for an empty name, a volume outside `0..=1` or not finite, or unknown keys; `conflict` for a taken name (as `tokens.create`) and for removing the last scene the studio's canvas may show. `scene.add` without a name is named "Scene", "Scene 2", ... and is shared (shown on any canvas), empty. `scene.remove` of the scene on air first switches the program, outside the undo stack, to the scene before it among those the canvas may show (else the one after it); `edit.undo` then puts the scene back but not on air. Undo and redo never change the program; an undo that would leave the canvas without a program (undoing the add of the scene on air) switches to the first scene the canvas may show. Switching to the program scene, or setting a flag, volume or name an object already has, changes nothing. `item.set_locked` is not enforced by the API: a client may still move a locked item, as Properties may. Effects (ADR-0052 decision 4, when effects join the schema): `scene.list` `read`; `scene.switch`, `source.set_volume` and `source.set_muted` `edit` with the on-air check; the undoable methods `edit`, with the on-air check when they touch the program scene (`scene.remove` of the scene on air always does). A 1.5 server answers `method_not_found`.

### Video filters and sync offset (protocol 1.8)

ADR-0062; filter types and their settings: [video-filters.md](video-filters.md). `filter.types` answers `{types: [{type, name, fields: [{key, label, kind, min?, max?, step?, unit?, default}]}]}`, `kind` being `"number"` or `"color"` (a color's `default` and every color value are `"#rrggbb"` or `"#rrggbbaa"` strings). `source.list` rows, and the rows of `source.changed`, carry the source's `filters: [{id, type, enabled, settings}]` in chain order (absent when empty), with every field of a built-in type in `settings` as the filter runs it on air (stored values read leniently: defaults filled in, out-of-range numbers clamped, unknown keys left out; ADR-0062 decision 8; a filter of an unknown type shows its stored settings as they are), and `sync_offset_ms` (absent when 0).

`filter.add {source, type, settings?}` adds an enabled filter at the end of the source's chain and answers `{filter}` (its id); missing settings take their defaults. `filter.remove {filter}`, `filter.move {filter, index}` (`index` the new position in the chain, from 0), `filter.set_enabled {filter, enabled}` and `filter.set_settings {filter, settings}` name a filter by its id alone (ids are unique in the collection). `filter.set_settings` is a patch on the settings as shown in the rows (the values on air): the given keys replace, the others stay, the result is checked as a whole and written in full, which also drops stored keys the type does not have. A patch is refused only for what it sends, never for a stored value the client did not send. Each of these is one undo step on the shared stack and publishes `source.changed`; a value or flag the filter already has changes nothing, except that a `filter.set_settings` on a filter whose stored settings were adjusted on load always writes the full set (ADR-0062 decision 8). `source.set_sync_offset {source, offset_ms}` sets the offset of a source's sound (positive delays it, negative advances it); like `source.set_volume` it is live, not undoable, and publishes `source.changed`.

Refusals: `not_found` for an unknown source or filter; `invalid_params` for a type the server does not have, an unknown key, a number for a colour or the reverse, a number outside its field's range or not finite, an index past the end of the chain, a filter on a source without a picture, an offset outside `-200..=200`, a sync offset on a source without sound, settings for a filter whose type the server does not have (it can still be moved, enabled, disabled and removed), or unknown keys. Effects (ADR-0052 decision 4, when effects join the schema): `filter.types` `read`; the filter methods and `source.set_sync_offset` `edit`, with the on-air check when the source is reachable from the program scene (nested scenes included). A 1.7 server answers `method_not_found`.

### Audio filters (protocol 1.16, ADR-0082)

The `filter.*` methods work on sources that have only sound: `filter.add` takes an audio filter type (`org.rbs.audio-filter.<name>`, spec [audio-filters.md](audio-filters.md)) on such a source and refuses the wrong domain in both directions with `invalid_params` (an audio type on a source with a picture, a video type on a source with only sound). `filter.types` takes an optional `domain`: `"video"` (the default, so a 1.8 to 1.15 client lists exactly what it listed before and never meets the audio kinds), `"audio"` or `"all"` (video types first). Each entry gains `domain`; each field gains `help` (one sentence, absent when none) and, for a number, `curve` (`"linear"` or `"log"`, a log number is meant for a log-scaled slider); the kinds `"toggle"` (a JSON boolean) and `"choice"` (the option's key as a string, with `options: [{key, label}]`) are new. `source.list` rows carry an audio source's `filters` like a video source's. A 1.15 server answers `invalid_params` to an audio type; `apply_look` still refuses audio sources. A gain above 0 dB can push the mix above 0 dBFS (the mixer has no clip stage, ADR-0081). Adding, removing, enabling, disabling or reordering a filter that changes the chain tail costs a 10 to 20 ms dip in that source (ADR-0082 decision 6); a settings edit never does. **Protocol 1.26 (ADR-0096).** `source.add` takes `with_audio` (default false): the picture and its companion sound are added as one undo step, and a refused companion adds nothing. `source.list` rows carry `companion_of` (the picture's source id) on a companion; 1.26 has everything of 1.23 (1.24 and 1.25 are other changes). **Protocol 1.19 (ADR-0095).** The audio filter type `org.rbs.audio-filter.ducker` (domain `audio`) has a field of the new kind `"source"`: its value is a source id (a JSON integer) or `null` for none, and its default is `null`. `filter.add` and `filter.set` refuse with `not_found` a source id that does not exist and with `invalid_params` a source with a picture or the filter's own source; setting `null` clears the key (the stored setting is removed). A key source that is later deleted or turned into an unusable key is not an error: the ducker then changes nothing. A 1.18 server does not list the ducker.

### Studio mode (protocol 1.9)

ADR-0061 (planned as 1.7; it shipped after the 1.8 filters, so it is 1.9 and 1.7 was never used). The studio's canvas is in studio mode while it has a preview scene. `scene.list` and `scene.changed` gain `preview`: the preview scene's id, absent outside studio mode; `scene.changed` is also published when the preview scene changes. `canvas.set_preview {scene}` with a scene id previews that scene (entering studio mode when it is off; the program stays on air) and with `null` leaves studio mode; `canvas.transition` puts the preview scene on air and, when "Swap scenes after a transition" is on, the old program scene in preview. A source that is in both scenes slides from its old box to its new one using the collection's glide (`duration_ms` and `easing`, default 400 ms and ease-in-out) or that source's `glide` override when set (ADR-0100, protocol 1.35); a source that is only in the scene coming on fades in with the collection **duration** and a linear ramp (easing does not apply to fade-ins). A source that leaves and is no longer drawn is not held on screen. `collection.set_glide` and `source.set_glide` are undoable `control` methods; `scene.list` / `scene.changed` carry `glide` on the collection snapshot and an optional `glide` on each source row when overridden. Both are live actions, not on the undo stack; undo and redo never change the program, the preview scene or the mode. Removing the preview scene keeps studio mode and previews the program scene.

`scene.sources {scene}` answers `{scene, sources}`: one row per source item of that scene, top first, in the `source.list` row form. `source.add` and `item.add` take an optional `scene` (default: the program scene, as before), so a client can build the preview scene before it goes on air. `source.list` and `source.changed` stay on the program scene in studio mode; the desktop app's Sources panel edits the preview scene and its Mixer plays the program's sound.

Refusals: `not_found` for an unknown scene (also as `source.add` and `item.add`'s `scene`); `conflict` for `canvas.transition` outside studio mode. Previewing the preview scene and leaving the mode when it is off change nothing. While preview and program are one scene, the desktop app holds the program as it was when that began (ADR-0063), and from protocol 1.31 the hold lasts while that scene stays on air, whatever is previewed after (ADR-0098): edits to the scene show in the preview and reach the program only with `canvas.transition`, which puts the scene as it is now on air and holds it again. A transition that keeps the preview scene (the default from 1.31) starts a hold too; a client learns the new program and preview from `scene.changed` or `scene.list`. Undo and redo never change program or preview, so the hold survives them. While the program is held, `source.list` and `source.changed` list the real scene, which may differ from what is on air until the next transition. The held copy is never listed: `scene.list`, `scene.changed`, `scene.sources`, `source.list` and `source.changed` name the real scene as the program. Source settings (filters, volume, mute, sync offset, capture target) are shared and are not held. Leaving studio mode ends the hold, so the program then shows the scene as it is. Effects (ADR-0052 decision 4, when effects join the schema): `scene.sources` `read`; `canvas.set_preview` `live`; `canvas.transition` `edit` with the on-air check. A 1.8 server answers `method_not_found`, ignores `scene` in `source.add` (adding to the program scene) and refuses it in `item.add` (`invalid_params`), so a client checks for protocol 1.9 first.

### Global sources and Remove from scene (protocol 1.10)

ADR-0065. A global source is drawn above and heard with every scene of its canvas; it is an item of the canvas's global scene, which no method lists: methods that take a scene id answer `not_found` for it. Nothing that 1.9 clients read changes shape or meaning (`session.hello` cannot tell them apart): `source.list`, `source.changed` and `scene.sources` keep their rows (items of the program or named scene only). `scene.list`'s and `scene.changed`'s `sources` rows gain `global: true` (absent when false), so a client knows which sources `item.add` refuses. `global.list` answers `{sources}`: one row per global source of the studio's canvas, top first, in the `source.list` row form.

`item.remove {item}` removes one item from its scene (Remove from scene); when that was the source's last placement in any scene, global sources included, the source is deleted in the same undo step; it answers `{source_deleted}`. `source.delete` keeps its meaning (Delete source: from every scene and the global sources). `global.add {source}` makes an existing source global: one item for it in the global scene, whose default layout is the source's layout on the canvas in the program scene (in studio mode the preview scene), else its first placement on the canvas, else the layout a new source of its kind gets, with no per-canvas overrides; its items are removed from the scenes the canvas may show; it answers `{item}`. `source.add` takes an optional `global: true`, which adds the new source as a global source in one undo step. `global.remove {source, keep?}` removes the global item (the last-placement rule applies; answers `{source_deleted}`) or, with `keep: true`, moves it into the program scene (in studio mode the preview scene) and answers `{item}`. Each of these is one undo step on the shared stack and publishes `scene.changed`, and `source.changed` when the program scene's rows change.

Refusals: `not_found` for an unknown source or item, and for the global scene's id as a scene; `conflict` for `global.add` of a source that is already global or whose scenes another canvas shows, and for `item.add` of a global source into a scene of its canvas; `invalid_params` for `global.remove` of a source that is not global, and unknown keys. A model `GlobalScene` refusal is `conflict`. Effects (ADR-0052 decision 4, when effects join the schema): `global.list` `read`; `item.remove`, `global.add`, `global.remove` and `source.add` with `global` `edit` with the on-air check (global items are on air while the canvas has a program; `item.remove` when the item is reachable from the program scene). The planned MCP server takes them from the same method table. A 1.9 server answers `method_not_found` and ignores `global` in `source.add` (adding to the program scene), so a client checks for protocol 1.10 first.

### Replay buffer (protocol 1.27)

ADR-0088. `replay.status` answers a snapshot (`seq` of `replay.changed`) of `{armed, held_secs, length_secs, bytes, memory_limit, memory_limited, saving, last_saved?, last_error?}`: `held_secs` is the usable past in whole seconds (`0` while disarmed), `length_secs` the wanted length, `memory_limited` says memory, not the length, is why the past is short, `saving` that a clip is being cut or written, `last_saved` the absolute file of the last clip saved since the app started and `last_error` why the last save failed (cleared by a successful save). `replay.changed` (state topic, `read`) carries the same object and is published when any of it changes; while armed it is published about once a second (`held_secs` and `bytes` move), and nothing is published while the buffer is disarmed and unchanged (ADR-0013). While armed, `length_secs` and `memory_limit` are the running buffer's; a setting changed meanwhile applies when it arms again. `last_saved` (an absolute path) and `last_error` are visible to `read` tokens. At most one clip is cut at a time and two are written at once (`conflict` otherwise). The settings (length, memory limit, audio, folder) are the desktop app's Replay buffer settings; this version has no API to change them. Scopes: `replay.status` is `read`, the others `control`.

### Recording protection (protocol 1.49)

ADR-0090 phase one. `protection.status` (scope `read`) answers a snapshot (`seq` of `protection.changed`) of `{guarded, level, disks: [{level, free_bytes?, seconds_left?, recordings: [canvas]}], outputs: [{canvas, output, level}], render, audio, memory: {level, available_bytes?}, alerts: [{kind, level, text, canvas?, output?}]}`; `protection.changed` (state topic, `read`) carries the same object when it changes. Levels are `unavailable`, `ok`, `notice`, `warning`, `critical` (an unknown level reads as `warning`); kinds are `disk`, `lag`, `render`, `audio`, `memory`. Values are rounded (0.1 GiB, whole minutes) so the state changes about once a minute. While no recording or stream runs, `guarded` is false and nothing is published. The rules, rounding and the guard's lifetime are in the [recording protection spec](recording-protection.md). No settings method in this version. A 1.48 server answers `method_not_found`; 1.48 was scene levels.

### Monitor output (protocol 1.30)

ADR-0097 F1. `monitor.status` answers a snapshot (`seq` of `monitor.changed`) of `{available, device, volume, wanted, playing, latency_ms?, solo?, error?}`: `available` says some audio adapter on the computer that runs the engine can play; `device` is the chosen playback device id from `monitor.devices`, `null` for System default (the OS default output); `volume` the monitor volume (linear, 0 to 1); `wanted` that a source of the program scene is monitored or soloed; `playing` that the device plays the monitor mix; `latency_ms` how far it plays behind real time while it plays (graph latency, output ring target and the device's latency); `solo` the soloed sources (absent when none); `error` why the device last failed to open or play, until it plays again. `monitor.changed` carries the same object whenever it changes.

- **Device.** The device opens only while `wanted` is true and closes when it turns false. A device that fails to open or play is closed and tried again after 1 s, the wait doubling up to 30 s; the stream and recordings never wait for it. `monitor.devices` enumerates (`{devices: [{device, name, is_default}]}`, best adapter first); clients call it when they show a picker, not on a timer.
- **Settings.** `monitor.set_device` and `monitor.set_volume` are this computer's settings, saved by the app (not in the scene collection); a host without a config folder keeps them in memory only, and a save that fails changes nothing and answers `failed`. `monitor.set_device` needs `admin`: it decides which speaker hears the program, including `"only"` sources kept off the stream. `monitor.set_volume` is `control` like a source's volume: it only changes how loud the chosen device plays. `monitor.set_device` answers `not_found` for an id `monitor.devices` does not list; a monitor that plays closes and opens on the new device. `monitor.set_volume` answers `invalid_params` outside 0 to 1; a playing monitor ramps.
- **Sources.** `source.set_monitor` saves the mode with the source (scene format 10). `"only"` takes the source off the stream and recordings only while the monitor plays; without a device it is heard in both (ADR-0097 decision 5). `monitor.set_solo {sources}` replaces the soloed sources (`not_found` for an unknown one, `[]` ends solo); while any soloed source has a strip in the program scene, the monitor plays only soloed strips; the mix is unchanged, solo is never saved, and a deleted source leaves it.

### Virtual camera (protocol 1.12)

ADR-0066 decision 13 (planned as "the next minor version"; 1.10 and 1.11 shipped first, so it is 1.12). The virtual camera is the platform's camera that meeting and streaming apps can pick (Windows only for now; the virtual camera spec). The API starts and stops sending the program to it; adding and removing the camera and its size and frame rate stay with the local user in the desktop app (Settings, Virtual camera), like entering a stream key: they change the computer outside RBS and need the operating system's approval. The U20 test lists them as local-only.

`vcam.status` answers a snapshot (`seq` of `vcam.changed`) of `{state, reason?, sending, width, height, rate, failure, frames}`:

- `state`: `"added"`, `"not_added"`, `"needs_update"` (the installed part is from another version of RBS; adding again updates it), `"unavailable"` (this computer cannot have the camera: no adapter on this platform, or the adapter says why), or `null` while the app has not read it (it reads it at start when the camera was added in RBS, and whenever Settings, Virtual camera is shown, since `rbs-cli vcam` can change it outside the app; until then `vcam.start` tries, and its error says when the camera is not added). A client treats a value it does not know as `null`. `reason` is the words for the user with `needs_update` and `unavailable`, absent otherwise.
- `sending`: RBS sends the program to the camera now.
- `width`, `height`, `rate` (frames per second, rounded): what is sent while sending, otherwise what Settings, Virtual camera has saved and `vcam.start` would use; all `0` before the app's camera settings reached the control thread and on a computer without a camera.
- `failure`: while sending, why the camera's node failed, until it runs again; otherwise `null`.
- `frames`: while sending and when the adapter shares its counters, `{sent, replaced, refused, consumer_busy, consumer_absent, format_pending, os_errors}` (the virtual camera spec, "Ring and stats"), counted since sending started; otherwise `null`.

`vcam.start` takes no parameters (unknown fields are ignored): it starts sending as the desktop app's Start virtual camera does, with the size and frame rate saved in Settings, Virtual camera, and answers `{}` once the camera's node runs. Refusals: `conflict` while it already sends, and while Settings is adding, removing or changing the format of the camera; `failed` while the app is still starting (before its camera settings reached the control thread), when the camera is not available on this computer, when it is not added or needs an update (the text says to add it in Settings, Virtual camera), and when it does not start (the adapter's error in words). `vcam.stop` stops sending (`conflict` when it does not send); apps that show the camera then get its still picture. Neither is undoable. A start or stop by an API client shows in the desktop app exactly as one of its own: Live controls, the Output menu's toggle, Settings, Virtual camera and the live indicator ("Virtual camera on"). Quitting RBS stops sending; RBS never starts sending by itself.

`vcam.changed` (state topic, `read`) carries the same object without `frames` (it is `null` there): it is published when `state`, `sending`, the size or rate, or `failure` change, not for the counters, which a client reads with `vcam.status`. A failure of the camera's node, or a stop because it could not start again after a studio restart, is seen at the next counters report (at most a second later while it sends; nothing runs while it does not); `vcam.status` publishes a change it finds first, so its data and `seq` always match. Until effects and the irreversible-actions permission ship, any `control` token can start sending, as with `stream.start`; the planned audit record covers both. Effects (ADR-0052 decision 4, when effects join the schema): `vcam.status` `read`; `vcam.start` and `vcam.stop` `live`, so a token without the irreversible-actions permission is refused. A 1.11 server answers `method_not_found` and has no `vcam.changed` topic (`events.subscribe` refuses it with `invalid_params`), so a client checks for protocol 1.12 first.

### Streaming (protocol 1.1)

`stream.start` takes no parameters (unknown fields are ignored, so a later minor version can add an optional destination): it goes live as the desktop app's Go live does, with the server and encoder settings saved in Settings, Stream, and the stream key read from the system's credential store at that moment. Neither the server nor the key is a parameter, so a `control` token cannot send the program elsewhere (an explicit destination would be an `admin` method, as `record.start_to_file` is). The answer comes once the stream's encoders and output are attached, before the connection is made: `{video_encoder, audio_encoder}`. Refusals: `conflict` while a stream runs; `failed` while the app is still starting (before its settings reached the control thread), when no server is saved, the saved settings cannot be used, no stream key is saved for a server that needs one (RTMP; nothing is opened), or this system has no video encoder. A saved encoder this system does not have falls back to the best one, as for recordings. Error texts never repeat the saved server. `stream.stop` ends the stream (`conflict` when none runs); it is the same as End stream in the app, which asks the local user first, while the API call does not: the caller is the one asking.

The stream settings are part of `settings.get`, `settings.set` and `settings.changed` from protocol 1.2, as `stream`: `{protocol: "rtmp" | "srt" | null, key_saved, reconnect, srt_latency_ms, encoding}` (and `auto_record` from protocol 1.11), where `protocol` is that of the saved server (`null` when none is saved; `rtmps` servers report `rtmp`, the protocol over TLS), `srt_latency_ms` is `null` for the transport's default, and `encoding` has the encoding fields of a recording profile (`encoder`, `rate_control`, `video_kbps`, `max_video_kbps`, `quality`, `keyframe_seconds`, `profile`, `preset`, `b_frames`, `cbr_padding`, `audio_kbps`, `delivery` from protocol 1.37, and `open_shadows` from protocol 1.38). Protocol 1.39 adds `output_size` on each recording profile and on `stream` (not inside `encoding`); see "Protocol 1.39". The server's address and the key are not among them, also not for `admin`: only the local user enters them, in the app, so no API client can read the address or send the program, and with it the key, to a server of its choosing. `settings.set` takes `stream: {reconnect, srt_latency_ms, encoding}` and, from protocol 1.39, `output_size`, and replaces those; the server and the key are ignored, so the `stream` that `settings.get` returned can be sent back changed. It is refused with `invalid_params` when the settings cannot be used (the same checks as Settings, Stream; an SRT latency of 0; a codec profile other than `high`, `main` or `baseline`; an encoder id that is empty, longer than 128 bytes or has control characters) or when the saved server itself cannot be used (the text does not repeat it), with `conflict` while a stream runs and the settings differ, and with `failed` while the app is still starting. `stream` is absent before the app's stream settings reached the control thread. A 1.1 server ignores `stream` in `settings.set`, so a client checks for protocol 1.2 first. The answer does not wait for the app to save the file: the change is in effect for this run when it comes, as for recording profiles. The change reaches the app's Settings, Stream, which saves it.

Protocol 1.11 adds `auto_record` (boolean) to `stream` in `settings.get` and `settings.changed`: the desktop app's "Record when the stream starts" (Settings, Stream). While it is on, a stream started by Go live or `stream.start` starts a recording with the saved recording settings when none runs (published on `record.state` as any recording; `stream.start`'s answer is unchanged and does not wait for or report it, so a client reads `record.state`); `stream.stop` and End stream stop that recording too, and a stream that fails leaves it running. `settings.set` takes an optional `auto_record` in `stream`: absent leaves it as it is, so a 1.2 client's patch never turns it off; like the other stream settings it is refused with `conflict` while a stream runs and it would change. An older server's `stream` has no `auto_record` (read as `false`) and ignores it in `settings.set`, so a client checks for protocol 1.11 first (1.10 is the global sources of ADR-0065).

`stream.state` (topic, state key without object id) and `stream.status` carry the whole stream state: `{"state": "idle", "last": null | {failure, frames, dropped, connects}}` or `{"state": "live", "protocol": "rtmp" | "srt", "connected", "connects", "reconnect_attempts", "video_encoder", "audio_encoder"}`. `last.failure` is `null` when the stream was asked to end; `dropped` counts video frames dropped at the export or the encoder and items the transport dropped while the connection was slow or down; `connects` is 0 when the stream never reached the server. The server's URL is a setting and is not part of the state, and the key never appears in any answer, event or log. A new event is published when a stream starts or ends and when its connection changes (connected, a reconnect attempt), never per frame; streams started from the app's own Go live button are published the same way. Starting and ending a stream are live actions and are not undoable.

A token change is in effect before its answer is sent: a new token authenticates, and a revoked token's sessions are closed, for any message sent after the answer arrived. Only loopback and IPC sessions can hold `tokens`, and no token the app makes has it, so in practice the callers are same-user IPC peers such as `rbs-cli token`.

### Outputs of the vertical canvas (protocol 1.29)

ADR-0093 decision 6: each canvas feeds its own recording and stream (at most two outputs per canvas, four in all). `record.start`, `record.start_to_file`, `record.stop`, `record.status`, `stream.start`, `stream.stop` and `stream.status` take an optional `canvas`: `"main"` (the default, also for `null`, so a 1.28 client's calls mean what they meant) or `"vertical"`. Each canvas has its own recording and its own stream, so `conflict` ("a recording is already running", "a stream is already running", "nothing records", "nothing streams") is per canvas: the vertical canvas can record and stream while the main one does.

- **Errors, in this order:** another `canvas` value is `invalid_params`; a start while an output profile or collection switch is pending is `conflict`, as before; an unknown `profile` is `not_found` as before; `"vertical"` while the studio has no vertical canvas (`canvas.add_vertical`) is `not_found` ("there is no vertical canvas"), also for `record.status` and `stream.status`; then the method's own refusals.
- **Settings.** With `canvas: "vertical"`, `profile` is still an id from `output.profiles` and is checked as before, but the encoding settings come from the output profile's vertical recording settings, or from the main recording settings until vertical ones are saved; a vertical stream uses the vertical stream settings. The desktop app keeps them beside the main ones (Settings, Recording and Stream, with a canvas selector; [UI design system](ui-design-system.md)). The vertical stream has its own server and its own key, read from the credential store at that moment (account in the UI design system). It is refused for the same reasons as the main one (no server saved, no key for an RTMP server, settings that cannot be used, no video encoder), each text naming the vertical stream and Settings, Stream; nothing is opened. `output.profiles`, `settings.get`, `settings.set` and `settings.changed` keep showing only the main canvas's settings in 1.29; the vertical ones follow in a later minor version.
- **Files.** A vertical recording into the profile's folder is named "RBS <local date> <time> vertical.<ext>".
- **Record when the stream starts** is per canvas: the vertical stream settings' `auto_record` starts and stops a vertical recording with the vertical stream, by the same rules as the main canvas's.
- **State.** `record.status` and `stream.status` answer the asked canvas's state; with `canvas: "vertical"` the answer is the vertical state object below and `seq` names its key. `record.state` and `stream.state` keep carrying the main canvas only, so a client of an earlier minor version never reads a vertical output as the main one. The vertical canvas's states go out on the topics `record.canvas_state` and `stream.canvas_state`: one state key per canvas, whose object id is the canvas's number in the studio's set (`1` for the vertical canvas; `seq` maps name `record.canvas_state:1`). The data is the `record.state` or `stream.state` object with a `canvas` field added at the same level, for example `{"canvas": "vertical", "state": "recording", "profile": "default", "video_encoder": "...", "audio_encoder": "..."}`. Events are published as for the main canvas (start, stop, connection changes; never per frame). Removing the vertical canvas publishes nothing on these topics, and a new vertical canvas starts at `idle` with `last: null`; the `seq` of its keys keeps counting up across canvases, so a client never drops a new canvas's events as old ones. The Stats panel and `settings.set`'s checks are the main canvas's, except that changing the main recording settings is `conflict` while a vertical recording without settings of its own uses them.
- **Older servers.** A 1.28 server answers `invalid_params` to `events.subscribe` with the new topics, and ignores `canvas` in these methods, so it would start, stop or report the **main** canvas's output instead: a client must check for protocol 1.29 before sending `canvas`.
- **Removing the canvas.** `canvas.remove_vertical` stays `conflict` while a vertical recording or stream runs; stop them first (`record.stop` and `stream.stop` with `canvas: "vertical"`). A collection switch, an output profile switch and a canvas change are refused while any output of either canvas runs.
- **Effects.** Unchanged: as for the main canvas, any `control` token can start the vertical stream until the irreversible-actions permission ships.

### Every canvas at once (protocol 1.42, ADR-0111)

While a vertical canvas exists, Record and Go live in the desktop app start and stop the vertical output of that kind too, unless the user picked "Main only". The API offers the same step as one call.

- **Methods.** `record.start`, `record.stop`, `stream.start` and `stream.stop` accept `canvas: "all"` (and, from protocol 1.61, `record.pause`, `record.resume` and `record.pause_toggle`). The value is a parameter type of these methods only: `record.start_to_file`, `record.status` and `stream.status` refuse it with `invalid_params`. The effect is `live`, as for the other values. `"all"` means the main canvas, then the vertical canvas when one exists; without one it is the main canvas alone. The control thread runs the call as one step, with no other request handled in between.
- **Errors, in this order.** `invalid_params`; `conflict` while an output profile or collection switch is pending (for the whole call); `not_found` for an unknown `profile`; then the main canvas's refusal at start, including a main recording that is still ending (`conflict`), fails the whole call: nothing else starts and the error answer has no `outputs`. A vertical refusal appears only in its entry. A later connection failure or reconnect give-up stays per canvas in `*.canvas_state`.
- **Result.** `{ "outputs": [ { "canvas": "main" | "vertical", "outcome": "started" | "running" | "stopped" | "not_running" | "not_configured" | "refused", "video_encoder"?, "audio_encoder"?, "error"?: { "code", "message", "data"? } } ] }`, one entry per canvas, main first. The encoder fields appear on `started`, and `error` on `refused`.
- **Outcomes.** For a start, an output that is starting or running is `running`, and a vertical recording that is still ending is `refused` with `conflict`. A vertical stream with no server saved is skipped as `not_configured`: not an error, so Go live does not fail for someone who never set up a vertical stream. A start is `conflict` when no entry is `started`, as a single-canvas start of a running output is. For a stop, an output that is starting or running is stopped (`stopped`), one that is ending or idle is `not_running`, and the call is `conflict` only when no entry is `stopped`.
- **Record when the stream starts** stays per canvas (1.29): the main stream's `auto_record` records the main canvas only.
- **The choice.** `settings.get` and `settings.changed` carry `vertical: { "record_with_main", "stream_with_main" }`, both `true` by default and present also with no vertical canvas. `vertical` is an object so that the vertical recording and stream settings can join it in a later minor version. `output.set_with_vertical {kind, on}` (`control`, so a control-surface token can flip it) changes one flag and publishes `settings.changed`; `settings.set` does not write the flags in 1.42. The flags live in the output profile's `[outputs-vertical]` section ([recording spec](recording.md#further-canvases-adr-0093-first-step)).
- **Commands.** `ui.command.run` of `record.toggle` and `stream.toggle` runs the start or stop with `canvas: "all"` while the kind's flag is on and a vertical canvas exists, and `canvas: "main"` otherwise. Their checked state is the main canvas's. `record.main.toggle` and `stream.main.toggle` always act on the main canvas, `record.vertical.toggle` and `stream.vertical.toggle` on the vertical one, and `output.with_vertical?kind=record|stream&on=on|off` runs `output.set_with_vertical` ([UI design system](ui-design-system.md)).
- **Markers.** `marker.add` also takes `canvas: "all"`, and it is its default (protocol 1.50, unlike `record.*`): see "Protocol 1.50".
- **Older servers.** 1.29 to 1.41 refuse `"all"` with `invalid_params` and answer `method_not_found` to `output.set_with_vertical`; a 1.28 server ignores `canvas` and acts on the main canvas. A client checks for 1.42 before sending `"all"`, and a client of an older server, whose `settings.get` has no `vertical`, assumes main only.

### Vertical canvas layouts (protocol 1.44, ADR-0093 decisions 4 and 8)

A source item has a default layout and, per canvas, a layout of its own (scene model, U15). 1.44 lets a client arrange the vertical canvas after it was added, change its size, and place an item there, as the desktop app's Vertical panel and Properties' "Main | Vertical" switch do.

- **`canvas.auto_layout {canvas, mode, scene?}`.** `canvas` must be `"vertical"` (`"main"` is `invalid_params` in 1.44; arranging the main canvas is a later minor). `mode` is `fit`, `fill` or `stack` (ADR-0093 decision 4, the same as `canvas.add_vertical`'s `layout`). `scene` defaults to the scene the vertical canvas shows now (while it follows, the main program scene); it may be any scene the vertical canvas may show, not only the one on air, and studio mode does not refuse it. Every visible source item of that scene gets its own layout on the vertical canvas; hidden items, nested scenes and items whose picture size is not known yet keep theirs. Locked items are arranged too (the lock stops pointer edits, scene model). One undo step (`edit.undo`). The effect is `edit`. Answers `{ "items": n }`, the number of layouts written; 0 is not an error. Errors, in this order: `invalid_params` (`canvas`, `mode`); `not_found` without a vertical canvas or for an unknown `scene`; `conflict` for a scene the vertical canvas cannot show (scoped to the main canvas, U15) or the global scene.
- **`canvas.set_vertical_size {width, height}`.** The vertical canvas's size in pixels, under the same rules as `canvas.add_vertical` (even, 64 to 8192). Layouts stay in the canvas's layout space and are fitted to the new size when drawn (ADR-0110, which 1.44 depends on), so no item is rewritten. A size whose aspect differs from the layout space shows the layout fitted and centred, with empty bars; `canvas.auto_layout` arranges it for the new shape. The vertical canvas's compositor and its picture restart; the main canvas does not. The size is saved with the collection. The same size changes nothing. Not undoable, and it does not clear the undo history (layouts are unchanged); the effect is `edit` (another `canvas.set_vertical_size` restores it with nothing lost). Answers `{}`. Errors: `invalid_params` (size); `not_found` without a vertical canvas; `conflict` while a vertical recording or stream runs (stop them first); `failed` when the canvas does not start at the new size (it runs again at the old size).
- **`canvas` on item edits.** `item.set_box`, `item.set_crop`, `item.set_style`, `item.flip`, `item.rotate`, `item.fit`, `item.align` and `item.reset_transform` take an optional `canvas`: `"main"` (the default, as before) or `"vertical"`. With `"vertical"` the change writes the item's own layout on the vertical canvas, starting from the layout that canvas shows (its own layout if it has one, else the default), so the main canvas does not change. `item.fit` and `item.align` use the vertical canvas's size, and `item.set_box` takes the vertical canvas's pixels. Undo and the `gesture` rules are unchanged. Errors, in this order: `invalid_params` for another `canvas` value; `not_found` without a vertical canvas; `conflict` while the vertical canvas shows another scene than the edited one (studio mode, a canvas that does not follow, or its fallback); then the method's own checks (an unknown item `not_found`, a locked item `conflict`, ...); `conflict` for a global source (global sources are not on the vertical canvas yet). The same rule makes the desktop app's Vertical panel read-only in those cases.
- **Undo and removal.** `canvas.remove_vertical` clears the undo history, as a main canvas change does, so no step can write a layout for a canvas that is gone. This also drops steps that touched only the main canvas.
- **Not in 1.44.** Per-canvas visibility and layer order (both stay per item and scene, by the owner's decision of 2026-11-13); arranging the main canvas; a read side for the vertical canvas (its size and an item's vertical layout in `scene.list`, `source.list` and their events), which a later minor adds.
- **Older servers.** A server before 1.44 answers `method_not_found` to the two new methods and refuses `canvas` on the item methods with `invalid_params` (their parameters deny unknown fields; `item.set_style` ignores it and acts on the main canvas). A client checks for 1.44 before sending `canvas`.

### Projectors (ADR-0125)

Client-scoped like every `ui.*` method, scope `control`; routed, so not in the schema, and the routing is not built yet (see [status](../status.md)). The desktop window runs the same commands from its menus through the registry: `ui.projector.open?canvas=main|vertical` (opens the projector, or brings an open one to the front), `ui.projector.size?canvas=...&size=window|exact|display:<name>` and `ui.projector.close?canvas=...`.

- `ui.projector.open {content, size?, display?}` → `{id}`. `content` is a workspace content string (`program`, `program?canvas=vertical`); `size` is `window`, `exact` or `fullscreen`; `display` is a display's EDID fingerprint as in the workspace file, needed for `fullscreen`. Opening a content that is already open answers its id and brings it to the front.
- `ui.projector.set_size {id, size, display?}`, `ui.projector.close {id}`, `ui.projector.displays` → `[{fingerprint, name, size: [w, h], scale}]` (physical pixels), `ui.projector.list` → `[{id, content, state, size, display, shared: [w, h]}]` (`state` is `open` or `suspended`; `shared` in physical pixels, absent while suspended).
- Topic `ui.projector.changed` with the same list, sent when a projector opens, closes, is suspended or comes back, or changes size, with `reason` on a close or suspension the user did not ask for (`canvas_removed`, `display_missing`, `picture_failed`).
- `invalid_params` for an unknown content or size, or `fullscreen` without `display`; `not_found` for an unknown id or display; `conflict` past the limits (four projectors, and a surface budget that lets two 2160p projectors open but not a third). Protocol version: the next free one when the routing is built.

## Undo

One user undo stack for the scene collection, shared by all clients. `edit.undo` from a panel can undo the desktop user's last edit, as in a shared document. An undo record used out of order returns `undo_conflict`. `edit.undo` with nothing to undo returns `conflict`, and so does `edit.redo` with nothing to redo. A step is one user action (in `rbs-app`: adding, deleting, a layer move, a source box, a style, a crop, showing or hiding, locking or unlocking an item, renaming a source, adding, removing or renaming a scene; all the boxes of one drag on the picture panel are one step); a new edit clears what is left to redo. `rbs-app` keeps at least 100 steps and clears the history when the canvas changes. Switching the program scene and a source's volume and mute are live actions and never on the stack (ADR-0059), and the history is kept across scene switches. The serialisable operation type joins the schema as a minor addition with the scene document format ADR.

## Compatibility

An OBS WebSocket (v5) compatibility layer (subset) is a separate optional adapter crate that speaks that protocol on its own endpoint and turns its calls into `rbs-api` requests in process, so existing Stream Deck and remote tools can work with RBS. It follows the same channel rules. obs-websocket authenticates with a salted password challenge, which the token store cannot answer, so the adapter keeps its own secret store, decided in its own review; each entry carries scopes applied the same way, and the remote limits on `admin`, `plugins` and `tokens` apply unchanged. Packaging it as a plugin waits for a plugin SDK host call that submits requests (plugin SDK spec, own review).

## Implementation status

- `rbs-api` implements the types and JSON codec of the first slice, tokens and the token store, scopes, the session state machine (`Server`), the control-thread side (`ControlTarget`, `ControlEndpoint`, `EventPublisher` with `seq` per state key and the event slots), the `ControlTransport` port with the bounded `TransportInbox`, the shared `Origin`/`Host` check for WebSocket adapters (`UpgradePolicy`), and the API thread (`ApiServer`).
- `rbs-app` serves the API from its control thread (`StudioHost`): an `ApiTarget` implements `ControlTarget` for studio, source, edit, output, record and settings commands and publishes `source.changed`, `scene.changed`, `canvas.changed`, `settings.changed` and `record.state` events through one `EventPublisher`. API requests are drained after the UI's own commands. The control thread holds the authoritative copy of the recording profile; the UI sends it each change, and an API `settings.set` comes back to the UI, which still writes the settings files. The control thread serves it once remote control is on (below).
- Scene levels (protocol 1.48, ADR-0091 Accepted, first stage): `rbs-api` has the five `scene.audio.*` methods and the `own_audio` and `heard` fields; `rbs-app` serves them on its control thread, and `crates/rbs-app/tests/studio_scenes.rs` covers them through the API. The Mixer and Properties do not show or edit scene levels yet (a visual change that waits for the owner's approval), so a fader in the Mixer still edits the source's own level.
- `rbs-api-ws` serves the API over WebSocket on loopback: one I/O thread on the OS readiness poller (no periodic wake-up), the HTTP upgrade completed only after the `Origin`/`Host` check, its own RFC 6455 framing that skips a message over the connection's limit as it arrives, bounded output per connection (`Full`, then `Writable`; a connection whose output is backed up is not read, so pings from a peer that never reads cannot grow it), an upgrade deadline (10 s), a cap on connections still sending their upgrade (16) and on sockets in any state (128), refusals answered before the socket closes, and accepting paused briefly after an accept error such as running out of file descriptors. A non-loopback address is refused at start without TLS. It passes the transport conformance suite in `rbs_api::conformance`, over plain WebSocket and over TLS 1.2 and 1.3.
- With network access (`WsConfig::network`, ADR-0046) it listens on one dual-stack `[::]` socket (`0.0.0.0` where IPv6 is off) and serves TLS (rustls, sans-IO, in the same I/O thread) and plain WebSocket on one port: a connection whose first byte is `0x16` is TLS; plain HTTP is served only to loopback peers (IPv4-mapped loopback included), others get `426` naming `wss://`. Remote peers have their own caps so they cannot lock out local clients: 16 connections still in their TLS handshake or upgrade, 8 sockets per address (IPv6: per /64), and the last 32 of the 128 sockets are for loopback only. Until a connection authenticates, it is no longer read once 16 KiB of its output is queued (so its output stays below about 16 KiB plus one read pass of pongs, plus rustls' own 16 KiB buffer). Plaintext rustls has decrypted but not yet handed over raises no readiness event, so the I/O thread does not sleep while a connection that may read still has some. No TLS 1.3 tickets and no session cache. Clients pin the key (`sha256//<base64>` of its SubjectPublicKeyInfo); the certificate's SHA-256 fingerprint is shown too (`rbs_api_ws::tls`).
- `rbs-app` has a Remote control section in the Settings window: "Allow remote control" (off by default), the port (4456 by default, not obs-websocket's 4455; 1024 to 65535), and access tokens. Turning it on starts the API thread and `rbs-api-ws` on `127.0.0.1` and `::1` at that port and attaches the endpoint to the control thread; turning it off, or a port change, stops both (connected apps get 1001), so while off nothing of the API exists. A token is made with a name and one of three access levels: View only (`read`), Control (`read` + `control`, the default, for panels) and Full control (`read` + `control` + `admin`); `plugins` and `tokens` are not offered. The token is shown once with a Copy button; revoking it closes its sessions (Undo puts it back). Connections, authentication and privileged calls go to the developer log (stderr). The settings live in `remote-control.toml` in the app's config directory: only token hashes, and on Unix the file is mode 0600 (on Windows the per-user application data folder is user-only already). A file that cannot be read, or that other users can write, leaves remote control off and says why. `rbs-cli` does not serve the API yet.
- `rbs-api-ipc` implements the local IPC transport above (Unix domain socket, Windows named pipe) and a blocking client (`IpcClient`), and passes the transport conformance suite. `rbs-app` serves it, at the current user's endpoint, while remote control is on, next to the loopback WebSocket; not serving it (another RBS serves the endpoint, or its directory cannot be used) is logged and leaves the WebSocket running. While remote control is off nothing of it exists.
- `rbs-app` answers `tokens.list`, `tokens.create` and `tokens.revoke` on its control thread from `remote-control.toml` (`rbs_remote_settings::token_command`), also after the studio failed: under the settings lock, which it never waits for (`failed` with "try again" while another program holds it), it reads the file, makes the change and saves it, then gives the server the saved tokens (`rbs_api::TokenHandle`) before the lock is released and the answer is sent. The Settings window is told and shows the list as saved.
- `rbs-cli token list`, `rbs-cli token create <name> [--access view|control|full] [--agent]` (`--agent`, protocol 1.80: without "Allow actions that cannot be undone") and `rbs-cli token revoke <name>` manage the same tokens in the same file, through the same code (`rbs-remote-settings`). `create` prints the token once, alone on standard output; `list` shows names and access levels, never tokens. A settings file that cannot be used is reported and left untouched. Names with control characters are refused. A change holds an advisory lock on `remote-control.lock` from reading the file to saving it, in the app too, and each save writes its own temporary file, so changes made at the same time are applied one after the other. If the token cannot be printed, it is revoked again. A deleted settings file means no tokens. The app reads the token list from the file again before each change it makes, when remote control starts and when its Settings window opens, so a change from `rbs-cli` is not undone by the app. While RBS runs with remote control on, `create` and `revoke` are sent to it over local IPC (`tokens.create`, `tokens.revoke`) and are in effect at once; `rbs-cli` changes the file itself only when nothing serves the IPC endpoint, or says why the running RBS could not be used and then changes the file. A change made in the file reaches a running app the next time its Settings window opens or remote control starts. A `revoke` is refused (non-zero exit, nothing changed) when RBS is running but could not be used, since a token revoked only in the file would keep working there. When `tokens.create` gets no answer (timeout, connection lost), `rbs-cli` revokes the name on a new connection, or says to check and revoke it. With `RBS_CONFIG_DIR` set, `rbs-cli` changes that directory's file and does not use IPC, since a running app may use another directory; an app started with `RBS_CONFIG_DIR` is reached over IPC by an `rbs-cli` without it, which then changes the app's file while `list` reads the default one. `list` always reads the file. The control thread answers `tokens.*` with file I/O (read, write, `fsync`), which can hold it for tens of milliseconds on a slow disk; token changes are rare.
- `rbs-remote-settings` keeps the network access settings (ADR-0046) in `remote-control.toml` as fields with defaults, so older files still load: `network` and `remote_admin` (off), `certificate_expires` (seconds since the Unix epoch, so renewal needs no certificate parser) and `own_certificate` (`certificate` and `key` paths, absolute). The generated key and certificate are PEM files beside it, `remote-control-key.pem` and `remote-control-cert.pem`, saved under the settings lock key first, each by an atomic rename of a file created mode 0600; only one of the two is reported as missing, and a key file (generated or the user's own) that other users can read is refused on Unix. The crate has no crypto dependency; `rbs_api_ws::tls` makes and checks them.
- `rbs-cli remote fingerprint` prints the key pin and the certificate fingerprint from the stored certificate (or the user's own) and opens no connection; it fails, saying why, when there is none yet or the key is not the certificate's.
- `rbs-app` serves network access when "Allow access from other computers" is on (Settings, Remote control; ADR-0046 decision 7): at each start of the server it makes the key and certificate the first time (`localhost`, the computer's name and `<name>.local`, loopback and the default-route address), renews the certificate with the same key when fewer than 30 days are left, or reads the user's own files (`rbs_app::network_access`), all under the settings lock; a stored key that is missing or does not match its certificate is never replaced silently: other computers cannot connect, the section says why, and "New key" makes a new one. It then listens on `[::]` with TLS (`RemoteServer::start_network`), with the computer's name and `<name>.local` as `Host` names and "Allow remote admin" as `ServerConfig::allow_remote_admin`. Creation, renewal, a new key and the key pin are logged. A change to these settings restarts the server.
- `rbs-app` answers `stream.start`, `stream.stop` and `stream.status` (protocol 1.1) on its control thread and publishes `stream.state`. The UI sends the stream settings it uses (those of the output profile's `stream` section, also when saving it failed) to the control thread at start and after each change, as it does the recording profile, so `stream.start` uses exactly what Go live would; one function builds the stream request for both. A stream started or ended through the API shows in the app's live controls as if its own buttons were used; a Go live that loses the race to an API client's `stream.start` keeps showing the stream that runs.
- `rbs-app` serves the stream settings in `settings.get`, `settings.set` and `settings.changed` (protocol 1.2) from the control thread's copy; a change from the UI publishes `settings.changed` too, and a change through the API is sent to the UI (`Update::StreamProfile`), which keeps a server being typed and the key state, and saves it to the output profile's `stream` section.

## Open questions

- Preview transport for remote clients: UI rule U5 requires a reduced-rate encoded preview for remote panels; WebRTC from the engine is the candidate.
- Stable addressing for layout commands. `rbs_ui::LayoutCommand` addresses windows and tab stacks by index, which shifts after each change; it is internal to the desktop shell. The `ui.*` commands for remote callers address panels by panel id (open, close, float, dock, move to an edge) and need stable window ids before they can target a window or stack.
- TLS certificates for network access: decided in [ADR-0046](../adr/0046-network-access-over-tls.md) (a generated key the client pins, or the user's own certificate; one port with TLS detected per connection); channel binding (RFC 9266) if pinning proves insufficient.

### Protocol 1.34: looks, samples and source boxes (ADR-0075)

`look.list`, `look.apply`, `source.add_sample` and `item.set_box` are what the Library and the picture-panel drag run. `look.list` returns only the built-in looks (`id`, `name`, `group`). `look.apply` is one undo step: the item's style when the look has one, and each of the look's filters replacing the source's filter of that type or added at the end, enabled, with the look's values. The step is checked before anything is written, and a refusal rolls back what was written. `source.add_sample` adds one image source over the whole canvas, stretched. A background is placed below the other items and a frame above them. The new source and its item are one undo step. `item.set_box` is the picture drag: the same source, position, size and gesture the window sends, answered with the request's `seq`. Calls with the same `gesture` other than 0 that follow each other are one undo step; `gesture` 0 is a step of its own. The window and a remote client call the same host functions.

Source rows carry `kind` `image` and `color` for those picture sources. A client treats a `kind` or a look `group` it does not know the way it treats a missing kind. A 1.33 server answers `method_not_found` to all four methods and leaves `kind` null for an image or colour source.

### Protocol 1.35: configurable glide (ADR-0100)

`collection.set_glide { duration_ms, easing }` sets the collection morph defaults (`duration_ms` in `0..=5000`, `easing` `"linear"` or `"ease-in-out"`). `source.set_glide { source, glide }` sets a per-source slide override (`glide` is `{ duration_ms, easing }` or `null` to clear). Each is one undo step. Fade-ins always use the collection duration and a linear ramp. `scene.list` and `scene.changed` carry the collection `glide` (absent when 400 ms and ease-in-out) and each `sources` entry may carry `glide` when overridden. `source.list` / `source.changed` rows carry the same optional `glide`. A 1.34 server answers `method_not_found` and omits the fields.

### Protocol 1.47: loudness meter (ADR-0092 stage 1)

- **`loudness.status`** (`read`, effect `none`) answers `{enabled, momentary?, short_term?, integrated?, range?, true_peak_max?, momentary_max?, short_term_max?}` for the main canvas's mix: `enabled` says the meter runs; `momentary` (400 ms) and `short_term` (3 s) in LUFS, ungated, updated every 10 ms of audio; `integrated` (LUFS, BS.1770-4 gating), `range` (LU, EBU Tech 3342), `true_peak_max` (dBTP, oversampled), `momentary_max` and `short_term_max` (LUFS) since the meter started or was last reset. A value without data is absent, never `null`, NaN or infinite: the meter is off, its window has not filled, or everything measured so far is below -70 LUFS. Values are not rounded; a display shows one decimal (Tech 3341). There is no event yet; a client polls (at most a few times a second is plenty, the values move every 10 ms of audio).
- **`loudness.set_enabled {on}`** (`control`) starts (`true`) or stops the meter and answers `{}`. Not undoable; session state in 1.47, saved from protocol 1.57 (the app starts with it as it was left). Starting it while it runs keeps the measurement; while it runs, a new studio (another collection, a canvas change) starts it again with a fresh measurement. A collection without audio has nothing to measure: `failed`. Off, nothing of the meter runs (ADR-0013).
- **`loudness.reset`** (`control`) restarts the measurement: integrated loudness, range, maxima and the windows, so momentary and short-term read again after 400 ms and 3 s. Answers `{}`; `conflict` while the meter is off.
- **Not yet.** Per-recording measurement and the leveler are later stages of ADR-0092; protocol 1.57 adds the target and the true-peak limit and saves Show loudness.
- **Older servers.** A 1.46 server answers `method_not_found` to the three methods. 1.46 was separate files.

### Protocol 1.48: scene levels (ADR-0091)

- **Modes.** A scene is in Shared levels (the sources' own volume and mute apply, as before) or Own levels (the scene keeps an entry per source it chooses: `volume?`, `muted?`, an absent field using the source's own value). Only the program scene of the studio's canvas sets what is heard; a following canvas hears the main mix (ADR-0093 decision 5).
- **`scene.audio.get {scene}`** (`read`) answers `{scene, own, levels: [{source, volume?, muted?}]}`; `levels` is empty in Shared levels.
- **`scene.audio.own {scene}`** (`control`) turns Own levels on, copying for every source the scene places (directly, through nested scenes, as a global source of the canvas, hidden items included) the level the scene makes heard in Shared levels, the source's own, so nothing jumps. **`scene.audio.shared {scene}`** turns it off and discards the entries. Each is one undo step on the shared stack and publishes `scene.changed` (and `source.changed` when the scene is on air); asking for the mode a scene is in changes nothing. Answers `{}`.
- **`scene.audio.set {scene, source, volume?, muted?}`** (`control`) sets the scene's entry for the source; a field left out keeps what the entry has. Live, not undoable, like `source.set_volume`; on the scene on air it reaches the mixer at once. On a scene in Shared levels it first turns Own levels on as `scene.audio.own` does (that part is one undo step) and answers `{turned_own: true}`; otherwise `{turned_own: false}`. A level edit on the program scene publishes `source.changed`; one on a scene that is not on air publishes nothing (a client reads `scene.audio.get`).
- **`scene.audio.reset_source {scene, source}`** (`control`) removes the scene's entry for the source, so the source's own level applies there again: one undo step; no entry changes nothing. Answers `{}`.
- **Rows.** `scene.list` and `scene.changed` scene rows add `own_audio: true` for a scene in Own levels (absent otherwise). `source.list`, `source.changed` and `scene.sources` rows keep `volume` and `muted` as the source's own values and add `heard: {volume, muted}` while the program scene has an entry for the source (absent otherwise, when `volume` and `muted` are what is heard). `source.set_volume` and `source.set_muted` still change the source's own values; while the program scene has an entry for the source, `heard` shows that the entry is still in force.
- **Refusals.** `not_found` for an unknown scene (the canvas's global scene included, which no method lists) or source; `invalid_params` for `scene.audio.set` with neither `volume` nor `muted`, a volume outside `0..=1` or not finite, or unknown keys.
- **Older clients and servers.** A 1.47 client sees the same objects as before for a collection without Own levels; on a scene in Own levels its `volume` and `muted` remain the source's own values, which may differ from what is heard. A 1.47 server answers `method_not_found` and omits the fields. 1.47 was the loudness meter. A collection that uses Own levels is saved as scene format 17, which older builds refuse to open.

### Protocol 1.63: pauses and markers (ADR-0124 decision 10)

- **Marker times are file times.** Once a recording has been paused, `marker.add`'s `t_ns` (and the manifest's times) leave out the pauses before it, so they are positions in the files. A marker added while the recording is paused sits on that pause's join (the lead does not apply) and its answer entry has `while_paused: true` (absent otherwise).
- **`pause_markers`** in a recording profile's `markers` (default `true`): the editor project written at stop has one marker per pause on its join ("Paused 2:10"). The server omits it with the other defaults; a partial object takes it as `true`. A change applies to the next recording.
- **Older clients and servers.** A 1.62 client ignores `while_paused`; the `rbs-api` crate before 1.63 refuses a `markers` object that carries `pause_markers` (unknown key), so a client checks for 1.63 before setting it. A 1.62 server refuses it in `settings.set`.
- **Rust crate.** `RecordingMarkers::pause_markers` and `MarkerPlaced::while_paused`; struct literals must add them.

### Protocol 1.62: marker settings (ADR-0089 decisions 3 and 4)

- **`markers`** on a recording profile (`settings.get`, `settings.changed`, `settings.set`): `{lead_ms, scene_changes, stream_events}`. `lead_ms` (0 to 30 000, default 0) moves manual markers earlier (`pressed_ns` keeps the press); `scene_changes` (default `true`) adds a `scene` marker when the program scene changes; `stream_events` (default `false`) adds `stream_start` and `stream_end` markers when a stream of that canvas starts or ends during the recording (recording spec, "Automatic markers"). The server omits `markers` while every value is the default; a set may give a partial object, the rest take defaults. `invalid_params` for `lead_ms` above 30 000 or an unknown key. A change applies to the next recording.
- **Older clients and servers.** A server older than 1.62 refuses `markers` in `settings.set` (unknown key) and never adds automatic markers. A client older than 1.62 reads a profile without `markers` as before; the `rbs-api` crate before 1.62 refuses a profile that carries it, so a client checks for 1.62 before changing the settings.
- **Rust crate.** `RecordingProfile::markers: RecordingMarkers`; a struct literal of `RecordingProfile` must add it.

### Protocol 1.61: pause a recording (ADR-0124)

- **Methods** (`control`, live class): `record.pause {canvas?}`, `record.resume {canvas?}`, `record.pause_toggle {canvas?}` (`canvas` as in 1.29, `all` as in 1.42). One canvas answers `{}`; `conflict` when nothing records there (or it is ending), it is already in the asked state, separate files run that do not belong to it, or the pause is refused because a video encoder it shares with another output cannot make a keyframe on request (the message says so). A toggle pauses a running recording and resumes a paused one. With `all` the answer is `{outputs: [{canvas, outcome, error?}]}` as in 1.42, main first, with the outcomes `paused`, `resumed`, `not_running` (no recording on that canvas) and `refused` (with `error` as a single-canvas call would answer); a toggle with `all` pauses every running recording when any of them is not paused, else resumes them all. When no canvas changed, the call answers that canvas's error (or `conflict` "nothing records") instead.
- **Timing.** A pause or resume takes effect on a render tick at least two render periods after the call (`recording.md`, "Pause and hold"); a resume before the pause began cancels it. Every recording the desktop app starts can be paused, its separate files with it.
- **State.** `record.state` and `record.canvas_state` add `paused` (bool), `paused_ms` and `recorded_ms`; `state` stays `recording` while paused. `paused` is set from the call on, including the ticks before the pause begins. `paused_ms` (time left out so far) and `recorded_ms` (time since the start less `paused_ms`) are as of the change; they are published on each pause and resume, never per frame, so a client counts on from them while not paused.
- **Older clients and servers.** A 1.60 client ignores the new fields; a 1.60 server answers the methods `method_not_found` and omits the fields, which read as not paused.

### Protocol 1.84: live text (ADR-0129 decision 11)

- **`text.timer {source, action}`** (`control`, effect `edit`, live class: not an undo step and not in the scene collection) starts, pauses or resets a countdown (one without `target`) or a stopwatch text source. `action` is `start` (runs it from its value; a countdown that reached zero starts over), `pause` (stops it at its value) or `reset` (zero, stopped). It answers the timer now: `{source, kind, running, value_ms}`, where `kind` is `countdown` or `stopwatch` and `value_ms` is the time counted (for a countdown the time gone, not the time left). A source that does not exist is `not_found`; any other source, a clock or a countdown to a time of day included, is `invalid_params`. Starting a running timer or pausing a stopped one changes nothing. Timers survive a studio restart and are saved per collection in `text-timers.toml` (user-data spec); they load stopped.
- **Live kinds drawn.** The text settings `kind`, `fields`, `format`, `target`, `duration_ms` and `end_text` (writable since 1.75 through `source.set_settings`) are now drawn: clocks, countdowns, stopwatches, recording and stream time, and `{...}` fields (scene-sources spec, "Live kinds"). `target` is checked as `HH:mm` or `HH:mm:ss` (`invalid_params` otherwise). `recording_time` and `stream_time` follow the main canvas's main recording and stream.
- **Older clients and servers.** A 1.83 server answers `text.timer` with `method_not_found` and draws a live kind as its `text`.
- **As built.** `rbs-api` `Command::TextTimer`, `request::{TextTimer, TimerAction}`, `types::TextTimerState`, `Response::TextTimerState`; `rbs-app` `studio_host/text_live.rs`, `text_timers`, `text_clock`; `rbs-record` `Studio::{text_timer, text_timers, set_text_timers, set_text_outputs}`. Tests: `rbs-api/tests/json.rs` (`text_timers_decode_as_protocol_1_84`), `rbs-app/tests/studio_api.rs` (`a_control_api_client_adds_and_edits_a_text_source`).
### Protocol 1.83: media playback controls (ADR-0108 decision 10)

- `media.play {source}`, `media.pause {source}`, `media.seek {source, position_ms}` and `media.restart {source}` (scope `control`, effect `edit`: reversed by another call), and `media.state {source}` (scope `read`, effect `read`). Each answers `{source, state, cursor_ms, duration_ms?}` after the command: `state` is `playing`, `paused`, `cued`, `ended`, `standby` or `unavailable` (a client treats a value it does not know as unknown; the `rbs-api` decoder maps it to `MediaPlayState::Unknown`), `cursor_ms` is where a pause stopped or the picture shown last, and `duration_ms` is the file's stated duration once it was opened.
- They are the source's control handle (`MediaControl`, scene sources spec): live actions that do not write the document, are not undo steps, do not replace the source, and act on every canvas and on preview and program together. `media.seek` past the stated duration is clamped to it. A source that only a preview scene draws is `cued`: `media.play` and `media.restart` do not play it in the preview; it plays on the take.
- Refusals: `not_found` for an unknown source; `invalid_params` for a source that is not a media file; `conflict` for a command on a media source that has no instance yet (it is in no scene the studio runs; `media.state` then answers `standby`); `failed` when the file cannot be opened again (the state is then `unavailable`). After the pause release a command that needs the decoder waits for the open on the control thread (the async open is not built yet).
- No topic yet: a client reads the state from each answer or with `media.state`. A 1.82 server answers `method_not_found`.

### Protocol 1.82: importing from OBS (ADR-0131 decision 12)

- **`import.obs.scan`** (`admin`, effect `read`) answers `{collections: [name], profiles: [name]}`: the scene collections and profiles in OBS's settings folders on the server's computer (`rbs_import_obs::discover::default_config_dirs`), by name only, sorted and deduplicated. Never a path.
- **`import.obs.check {collection, profile?, choose?}`** (`admin`, effect `read`) plans the import and writes nothing. It answers `{name, exact: {scenes, sources, items, filters}, entries: [{outcome, area, obs_name, obs_type?, scenes?, reason, hint?}]}`, the report of `obs-import.md`. `collection` and `profile` are names that `scan` returned; a name that `scan` does not find is `not_found`, and a path is only a name, so it finds nothing. The first OBS folder that has the name wins. Every file read is resolved with its links followed and must stay inside that OBS folder: a link leading out of it, or a file that cannot be read, is `failed`. `choose` holds the wizard's parts: `scenes` (OBS names; absent means all), `global_audio`, `audio_filters`, `video_filters`, `canvas`, `recording`, `stream_server`, `stream_key`, `hotkeys`. An absent part is on. Without a profile, the parts that need one are off. A file that is not a collection is `invalid_params`.
- **`import.obs.run`** (same parameters; `admin`, effect `destructive`) writes as the wizard's Import does (decision 9): a new scene collection and output profile with free names, the stream key in this computer's credential store under the new profile's account, the hotkeys added to `shortcuts.toml` (never replacing a shortcut of the user's), and the report file `imports/<collection id>.report.toml`. It switches to nothing. It answers `{collection: {id, name}, profile?: {id, name}, shortcuts_added, report, notes?}`, where `notes` are what writing left out. It is `destructive` because the added shortcuts and the saved key have no undo step, so it needs the irreversible-actions permission. It is `failed` when no user data is loaded (a second RBS holds the writer lock, or the host has no user data). The UI reloads its scene collection and output profile lists, and its shortcuts when some were added.
- **Older clients and servers.** A 1.81 server answers `method_not_found`.
- **As built.** `rbs-api` `Command::ImportObsScan`, `ImportObsCheck`, `ImportObsRun`, `request::{ObsImport, ObsImportChoice}`, `types::{ObsScan, ObsCheck, ObsCounts, ObsReportEntry, ObsRun}`; `rbs-app` `studio_host/obs_import_api.rs`, `obs_import::{api_scan, api_source, api_options, api_check, plan_api}`, `CollectionSaver::import_obs`, `Update::ObsImported`. Tests: `rbs-api/tests/json.rs` (`obs_import_calls_name_sources_only_and_answers_round_trip`), `rbs-api/tests/effect.rs`, and the `rbs-app` `obs_import` tests `the_api_reads_only_what_scan_found_by_name`, `a_link_out_of_the_obs_folder_is_refused` and `api_choices_map_to_options_and_need_a_profile`.

### Protocol 1.81: transitions (ADR-0128 decision 13)

- **`collection.set_transition {kind?, fade?, swipe?, slide?}`** (`control`, one undo step) merges the given parts into the collection's transition and answers `{}`. `kind` is `cut`, `fade`, `move` (the default: the collection glide of 1.35), `swipe` or `slide`. `fade` is `{duration_ms, easing, via?}`, default 300 ms linear; `via` is an opaque colour `"#rrggbb"` to fade through, absent for a crossfade. `swipe` and `slide` are `{duration_ms, easing, direction}`, default 500 ms ease-in-out `left`; `direction` is `left`, `right`, `up` or `down`. Durations are in `0..=5000`; `0` cuts. Setting what is already set changes nothing. Move's settings stay in `collection.set_glide`.
- **One-off transitions.** `canvas.transition` and `scene.switch` take optional `kind` and `duration_ms` that replace the collection's for that change only. With `fade`, `duration_ms` replaces the fade's duration; with `move`, `swipe` or `slide`, the glide's duration and every per-source override for that change. When the call changes nothing, they are dropped. A 1.80 server refuses both fields with `invalid_params`.
- **`scene.list` and `scene.changed`** carry `transition` `{kind, fade, swipe, slide}` on the collection snapshot, absent while every part is the default.
- **Topic `transition.state`** (`read`, state, one key per canvas): `{canvas, state, kind, duration_ms, from, to, at}`, published when a program change's transition starts (`state` `started`) and when it ends (`ended`), never per frame. `from` and `to` are scene ids, `at` the engine time in nanoseconds. A Fade starts when the incoming picture is ready (or after 250 ms) and ends when the blend is over; Move starts at the change and ends after its glide; a Cut, or a duration of 0, starts and ends at once. Like every state topic the latest event wins: a client that reads late may see only `ended`, with a `seq` that skipped `started`. `kind` is the kind that ran: `swipe` and `slide` are reported as `move` while they are not drawn yet (ADR-0128 phase 2).
- **Refusals.** `invalid_params` for a duration above 5000, a `via` that is not `#rrggbb`, or unknown keys.
- **Older clients and servers.** A 1.80 client ignores `transition` and the topic. A 1.80 server answers `collection.set_transition` with `method_not_found`.
- **As built (2026-11-16).** `rbs-record` `Studio::{set_transition_once, take_transition_events}`; `rbs-app` `studio_host` (`set_transition`, `publish_transitions`). `crates/rbs-record/tests/studio.rs` and `crates/rbs-app/tests/studio_scenes.rs` cover them.

### Protocol 1.80: tokens without the permission (ADR-0052 decision 4, last part)

- **`tokens.create {name, scopes, irreversible?}`.** `irreversible` (absent: `true`, as tokens behave today) sets "Allow actions that cannot be undone" on the new token. Only a caller that holds the permission reaches `tokens.create` (it is `destructive`), so it may give either. `scopes` beyond the caller's own are answered `not_permitted` with `data.reason: "scopes"` on the API thread, audited, and nothing is made.
- **Answers.** `tokens.create` answers and `tokens.list` rows add `irreversible`. An older server omits it, which reads as `true`.
- **`rbs-cli token create --agent`** makes a token without the permission, through the app (`irreversible: false`) or in the settings file (`RemoteProfile::create_token_with`).
- **Older clients and servers.** A 1.79 client leaves `irreversible` out and gets tokens as before. A 1.79 server ignores the field and makes a token with the permission, so a client that needs a token without it checks the answer's `irreversible`.
- **As built.** Tests: `crates/rbs-api/tests/effect.rs` (`tokens_create_never_gives_more_scopes_than_the_caller_holds`), `rbs-remote-settings` `api::tests::a_token_can_be_made_without_the_irreversible_permission`, `rbs-cli` `token::tests::an_agent_token_is_made_without_the_irreversible_permission`.

### Protocol 1.79: the network check (ADR-0052 decision 4, third part)

- **Locations.** A location value is a local absolute file system path when it starts with one `/`, or with a drive letter, a colon and `\` or `/` (`rbs_api::location::is_local_path`, the same on every platform). URL schemes (`file:` included), UNC paths (`\\host\x`, `//host/x`), verbatim and device paths (`\\?\`, `\\.\`), relative paths and values with control characters are not.
- **The check on the API thread** (`rbs_api::Command::reaches_network`), after the scope and irreversible checks, for a session without the permission: `source.add` of `kind: "browser"`, a `settings.set` whose `profiles` name a non-empty `folder` that is not a local absolute path, and a `record.start_to_file` whose `path` is not one (already refused as `live`) are answered `not_permitted` with `data.reason: "network"`, audited, and nothing reaches the control thread. An unchanged recording folder that is not local also fails: the check reads values, not differences.
- **The check on the control thread** (`rbs-app` `studio_host/network.rs`), where a source's kind is known: `source.set_settings` of a browser source's `url`, of an image or media source's `path` that is not a local absolute path, or of any setting of a source whose type this build does not know (a plugin type counts as network; it fails closed), and `source.retarget` of such an unknown type, are answered `not_permitted` with `data.reason: "network"` and audited when the answer is forwarded. Capture sources' targets come from their adapters' lists; colour and text sources name no location the API can write (a text source's `file` stays `forbidden`).
- **Not yet** (in 1.79; `tokens.create {irreversible}` is in 1.80). `tokens.create {irreversible}`, the media protocol allow list (scene sources spec) and `openWorldHint` in `rbs-mcp`.
- **As built.** Tests: `crates/rbs-api/src/location.rs`, `crates/rbs-api/tests/effect.rs` (`a_browser_source_reaches_the_network_and_is_refused_without_the_permission`, `a_recording_folder_on_another_computer_is_refused_without_the_permission`), `rbs-app` `studio_host::network` unit tests and `crates/rbs-app/tests/studio_record.rs` (`a_token_without_the_permission_cannot_point_a_source_at_another_computer`).

### Protocol 1.78: the on-air check (ADR-0052 decision 4, second part)

- **What is on air.** While any output runs (a recording or stream of either canvas, the virtual camera, or the armed replay buffer), every canvas counts as on air: stricter than ADR-0052's per-canvas rule, and simple. On air is each canvas's program scene, the followed canvas's program scene for a follower, a fallback scene, the canvas's global scene, and everything reachable from them: nested scenes, their items and the sources those items show (`rbs_scene::SceneCollection::on_air`, a pure function tested directly).
- **The check.** The server passes the caller (token name and permission) with each forwarded command (`rbs_api::Caller`, `ControlTarget::handle_as`). For a caller without the permission, an `edit` that changes what is on air is answered `not_permitted` with `data.reason: "on_air"`, and the refusal is audited when the answer is forwarded. It fails closed: an `edit` passes only when it is known never to touch the picture or sound on air (`settings.set` without `canvas`, `monitor.*`, `output.set_with_vertical`, `replay.save`, `project.export`, `marker.add`, `canvas.set_preview`, `scene.add`, `source.copy_attributes`), or when it acts only on what it names (the `item.*`, `source.*`, `filter.*` and `scene.*` edits) and every scene, item, source and filter it names is off air; a method that places into a scene and names none (it would use the program scene) is refused. Every other `edit` (program switch, transitions, undo and redo, master levels, global sources, looks, layouts) is refused while an output runs.
- **Not yet** (in 1.78; the network check is in 1.79). The network and location checks (`network`) and `tokens.create {irreversible}`.

### Protocol 1.77: filter latency (ADR-0130 decision 9)

- **`filter.types`.** Each audio type adds `latency_ms`: the delay an instance adds at the running audio graph's format and block size (`AudioFilterType::latency_frames`, `audio-filters.md`, "Latency"), in milliseconds to the microsecond. 0 for a type with no delay (gain, noise gate, ducker, compressor, equaliser); 2 for the limiter at 48 kHz; 10 for noise suppression with 480-frame blocks. Video types omit it.
- **Source rows** (`source.list`, `source.changed`, `scene.sources`, the global source list) add, each omitted when 0:
  - `filter_latency_ms`: `L`, the summed latency of the source's running audio filters (a disabled filter is Standby and counts 0);
  - `effective_offset_ms`: `h`, the offset the program hears the source's sound at: the input's effective offset plus `L` (ADR-0130 decision 4). It equals `sync_offset_ms` while neither the input's limits nor the compensation bite;
  - `uncompensated_ms`: the part of `L` the input's advance limit could not take back (`L - (clamp(stored) - a)`); for a source without an audio input (media, browser audio), all of `L`.
  These change only when the chain, the offset or the graph changes, so they ride on the row's change events.
- **Input counters.** `source.list` answers add, for a source with a running audio input, `input_late_frames` (output frames that were silence because the input's audio had not arrived) and `input_resyncs` (times its resampler resynchronised). Both only grow. They show how much of the input's jitter headroom the compensation spends. They are absent from events and other lists, so a growing count does not publish a change.
- **Meaning change.** `effective_offset_ms` in `sync.measure.changed` (1.66) is now `h`. While no latent filter runs (`L = 0`) it equals what the input applies, as before, so existing setups see the same value.
- **Older clients and servers.** A 1.76 client ignores the new fields. A 1.76 server omits them, which reads as no latency and no counters.
- **As built (2026-11-16).** `rbs-api` `FilterTypeInfo::latency_ms`, `SourceInfo::{filter_latency_ms, effective_offset_ms, uncompensated_ms, input_late_frames, input_resyncs}`; `rbs-record` `Studio::audio_latency` and `Studio::input_counters`; `rbs-app` `SourceRow::latency`, `api_source`, `with_input_counters` and `filters::api_types(domains, setup)`. Tests: `rbs-api/tests/json.rs` (`filter_latency_fields_are_optional_and_round_trip`), `rbs-app/tests/studio_filters.rs` (`filter_latency_and_input_counters_are_reported`).

### Protocol 1.76: method effects and the irreversible-actions permission (ADR-0052 decisions 4 and 5, first part)

- **Effects.** Every method declares an `effect`, listed by `api.describe` beside its scope: `read`, `edit`, `live` or `destructive` (definitions in "API parity" above; the table is `rbs_api::request::METHODS`). Every method with scope `read` has effect `read`. `live`: `record.*` start, stop, pause and resume (`record.start_to_file` included), `stream.start`, `stream.stop`, `stream.hold`, `stream.resume`, `stream.hold_toggle`, `output.break_toggle`, `vcam.start`, `vcam.stop`, `replay.arm`, `replay.disarm`, `calibration.run`, `calibration.cancel`, `profile.switch`, `collection.switch`. `destructive`: `tokens.create`, `tokens.revoke`, `settings.clear_recent_targets`, `sync.forget_device`, `sync.apply_to_device_sources`, `source.set_sync_offset` (writes the device memory with no undo record; 0 forgets it), `source.paste_attributes` and `source.reset` (their Sound and Sync offset groups are written outside the undo step), `loudness.set_enabled` (turning off drops the integrated measurement), `canvas.remove_vertical` (drops the items' vertical layouts and clears the undo history), `marker.remove`, `loudness.reset`. Every other method is `edit` or `read`. Stricter than ADR-0052's table, from a review of the handlers: `collection.switch` is `live` (it clears the undo history and restarts the studio, which re-arms the replay buffer empty and restarts the virtual camera), and `settings.set` with a `canvas` is `live` for the same reason (`rbs_api::Command::effect`); a superseding ADR or the owner can relax them. A client treats a missing or unknown effect as `destructive`.
- **The permission.** A token entry has `irreversible` ("Allow actions that cannot be undone"); an entry saved without it has it, so existing tokens keep their behaviour, and an entry that has it saves as before. A same-user IPC session without a token has it. `session.authenticate` answers `irreversible` beside `scopes`.
- **The check.** After the scope check, a `live` or `destructive` method from a session without the permission is answered `not_permitted` (code -32012; ADR-0052 planned -32011, which `forbidden` took in 1.75) with `data.reason: "irreversible"`, in its turn behind the request in flight, and nothing reaches the control thread. Changing a token's permission closes its sessions, as a scope change does.
- **Audit.** Every admitted `live` or `destructive` call and every `not_permitted` refusal is an audit record with the token name (`AuditEvent::Irreversible`, `AuditEvent::NotPermitted`).
- **Not yet** (in 1.76; the on-air check is in 1.78). The on-air and network checks (`on_air`, `network`), the caller context of `ControlTarget`, `tokens.create {irreversible}` and making tokens without the permission in the app follow in later minor versions. Until a token without the permission can be made, every token keeps it, so behaviour is unchanged.
- **Older servers** list no `effect` and answer no `irreversible`; a client treats them as `destructive` and `false`.

### Protocol 1.75: text sources (ADR-0129 decision 8)

- **`source.add {kind: "text", text?, name?, scene?, global?}`** (`control`; effect `edit` with the on-air check, as any `source.add`) adds a text source showing `text` (absent: "Text"), named `name` (absent: "Text", made unique). It has no target: `adapter` and `target` may be left out and are ignored. The box (`width`, `height`) fits the text with its padding, measured by the server's text renderer within 200 ms, else 640 x 160; the item has the same size, centred on the canvas, so it draws 1:1. One undo step; answers `{source}`. `text` on any other kind is `invalid_params`; `with_audio` is ignored. `source.list` rows carry `kind: "text"`.
- **Settings.** `source.get_settings` and `source.set_settings` read and write the text keys of `scene-sources.md`, "Text", with the strict checks of an edit (`invalid_params` naming the key). **`file` cannot be written through the API** (`forbidden`, whatever the scope) until token scopes exist: a path would put any readable file on air. Error texts never include a path or file contents.
- **`source.set_text {source, text}`** (`control`; `edit`) replaces only `text`; one undo step. `not_found` for an unknown source, `invalid_params` for a source that is not a text or a text over 10 000 characters.
- **`text.fonts {}`** (`read`) answers `{families}`: the installed font families, sorted, from the text worker's cache (refreshed at most once a minute). It never waits: the first call starts the worker and answers `not_ready` until the first list exists. `failed` when the server has no text renderer.
- **Not yet.** `text.timer` comes with the live kinds (phase (d)).
- **Older clients and servers.** A 1.74 server answers the new methods `method_not_found` and refuses `kind: "text"` with `invalid_params`; a client reads unknown error kinds generically.
- **As built.** `rbs-api` `SourceKind::Text`, `AddSource::text`, `SetText`, `TextFonts`, `ErrorKind::{Forbidden, NotReady}`; `rbs-app` `Host::{add_text, set_source_text}` and `Studio::text_fonts`; the desktop app registers `rbs-text-parley` on the system's fonts. Tests: `crates/rbs-api/tests/json.rs` (`text_sources_decode_as_protocol_1_75`), `crates/rbs-app/tests/studio_api.rs` (`a_control_api_client_adds_and_edits_a_text_source`), `crates/rbs-app/tests/studio_record.rs` (`a_text_box_is_locked_while_a_take_records_its_picture_separately`).

### Protocol 1.74: stream destinations (ADR-0127 decision 16)

ADR-0127 planned these as 1.68; other changes took 1.68 to 1.73 first, so they are 1.74. A stream goes to one or more destinations of its canvas (the output profile's `[stream-destinations]` section, `recording.md`, "Stream destinations"): the first one from the stream settings, the others from that section.

- **`stream.destinations {canvas?}`** (`read`): `{destinations: [{id, name, service, canvas, enabled, configured, encoding}]}`, the asked canvas's (`main` or `vertical`; `not_found` for a vertical canvas that does not exist), or both canvases' without `canvas` (the vertical one's while it exists), each canvas's first destination first (ids 0 and 1). `service` is a preset id or `custom` (data only); `configured` is true when a server is saved and, for RTMP, a key flag; `encoding` is `shared` or `own`. Never the server or the key.
- **`stream.destination.start {id}`** (`control`, effect `live`): starts one destination. While its canvas does not stream, that canvas's stream goes live with this destination alone (as `stream.start`: same answer `{video_encoder, audio_encoder}`, same refusals, "Record when the stream starts" honoured, the with-main flag of ADR-0111 not used); while it streams, the destination joins: sharing the stream's encoder at its next keyframe, or on its own encoder chain; the answer is `{}`. Refusals: `not_found` for an id the profile does not have; `conflict` when it is turned off (turning it on stays a separate, visible step), has no server, or is already on air; `failed` when its key is missing or cannot be read, or its output does not start (the text never repeats a server).
- **`stream.destination.stop {id}`** (`control`, effect `live`): stops one destination while the others go on: its output drains and its transport finishes; the shared encoder runs on, and when it was the stream's anchor (the output that carries the stream's hold and counters) the next running destination becomes the anchor. Stopping the last running destination ends the stream as `stream.stop` does. `conflict` when it is not on air.
- **`stream.destination.set_enabled {id, enabled}`** (`control`, not undoable): whether Go live sends to it; the desktop app saves the section. It changes nothing while live. `not_found` for an unknown id. A section written by a newer RBS is not overwritten: the call then changes nothing.
- **State.** A live stream's state (`stream.state`, `stream.canvas_state`) adds `destinations: [{id, name, service, state, connects, reconnect_attempts, dropped, on_air_ms, error?}]` in the order they started: `state` is `connecting`, `live`, `reconnecting`, `failed` or `stopped`; `dropped` counts items its transport dropped; `on_air_ms` is the time since it first connected, as of the change (a change of time alone is never published); `error` says why it failed. The top-level fields keep their meaning: `connected` while one destination is, `connects` and `reconnect_attempts` sums over the running ones, `protocol` the anchor's at the start, and `last.failure` the stream's (every destination failed). A destination that fails alone is only in its row. A stream the host tracks as one (from before 1.74) has no `destinations` field.
- **Deviations from ADR-0127 decision 16.** The rows carry `dropped` (transport drops) instead of `kbps` and `dropped_gops`: the output counters have no byte count yet. A destination with its own encoding that joins while the stream is on hold is not held until the next hold. The registry commands ("Start / stop destination <name>", "Use destination <name>", rule U20) come with the destinations UI (step e), since the desktop app has no destination command yet; adding and removing destinations, and their servers and keys, stay local-user only.
- **Older clients and servers.** A 1.73 server answers the new methods `method_not_found` and sends no `destinations`; an older client ignores the field.
- **As built (2026-11-16).** `rbs-api` `StreamDestination`, `LiveDestination`, `DestinationsOf`, `DestinationRef`, `SetDestinationEnabled`; `rbs-app` `studio_host` (`api_destinations`, `start_destination`, `stop_destination`, `start_stream_to`), `Update::StreamDestinations`; `crates/rbs-app/tests/studio_stream.rs` `a_control_api_client_lists_starts_and_stops_destinations` and `crates/rbs-api/tests/json.rs` `stream_destinations_have_a_stable_wire_form` cover them.

### Protocol 1.73: narrowing a same-user IPC session to a token (ADR-0052 decision 3)

- **`session.authenticate` after `session.hello` on IPC.** A same-user IPC peer, authenticated by `session.hello` with all scopes, may send `session.authenticate {token}` as its first request. On success the session has the token's scopes (channel limits applied as for any local peer) for the rest of its life, is shown and audited under the token's name, and is closed when the token is revoked or changed. A wrong or unknown token gets `auth_failed` and close, the same answer as on any channel; IPC has no back-off.
- **Refused** with `invalid_request` ("the session is already authenticated") once any other request was admitted, and for a second `session.authenticate`.
- **Voluntary.** A peer that does not send it keeps all scopes, as `rbs-cli` does.
- **Older servers.** A 1.72 server answers `invalid_request` to it on IPC: a client that relies on narrowing (`rbs-mcp`) treats that as a failure and stops.

### Protocol 1.68: duplicate, reset and paste attributes of sources (ADR-0133)

- **Attribute groups** (ids): `transform`, `crop`, `opacity`, `style` (on the item), `video_filters`, `audio_filters`, `options`, `region`, `glide`, `record_separately` (on the source; undoable), `sound` and `sync_offset` (live: written outside the undo step, never chosen by default). The table, defaults and applicability are ADR-0133 decision 1 and `scene-model.md`, "Copies, resets and attribute groups".
- **Addressing.** `source.duplicate`, `source.reset` and `source.copy_attributes` take `{source, scene?}`: the source's first item in `scene`, by default the scene being edited (the preview in studio mode, else the program); a global source uses its global item and takes no `scene` (`invalid_params`). `canvas?` (`main`, `vertical`) picks the layout read or written.
- **`source.duplicate {source, scene?}`** (`control`; effect `edit` with the on-air check, as `source.add`) makes an independent copy directly above the item, named like "Camera 2", with every filter (new ids), sound, glide, region, chrome and Record separately. A picture's companions are copied too, muted, pointing at the copy. A camera copy starts in standby. Answers `{source, item, active, companions: [{source, item}]}`; one undo step.
- **`scene.duplicate {scene, sources?}`**: `sources` is `shared` (default, as before) or `copied`: the copy places copies of the scene's own sources and their companions (global sources and nested scenes stay references), its own levels re-keyed and key links remapped inside the copied set. The answer adds `sources: [{from, to}]` when copied. A server before 1.68 refuses `sources` with `invalid_params`.
- **`source.reset {source, scene?, canvas?, groups?}`** (`control`; `edit` with the on-air check) sets each group to its default; without `groups`, every non-live group. Identity keys (device, window, file, URL) are kept.
- **`source.copy_attributes {source, scene?, canvas?}`** (`control`) takes a snapshot of every group into the server's one attribute clipboard (shared by the window and every API session, cleared by a scene collection switch) and answers the clipboard. **`source.attributes_clipboard {}`** (`read`) answers `{source, name, type, groups}` or `null`; `groups` are those whose copied value is not the default.
- **`source.paste_attributes {items, groups, filters?, canvas?}`** (`control`; `edit` with the on-air check) applies the chosen groups of the snapshot to every item, in any scene, as one undo step. `filters` is `replace` (default; the same type sequence keeps the target's filter ids and writes only settings and `enabled`) or `append`. `conflict` while the clipboard is empty.
- **Answers** of reset and paste: `{targets: [{source, item?, changed: [group], live: [group], skipped: [{group, reason}]}]}`, reasons `not_applicable`, `unchanged`, `locked`, `no_picture_size`, `out_of_picture`. `invalid_params` for an empty or unknown group or an empty `items`; `not_found` for an unknown source, item or scene.
- **Topic `source.attributes_clipboard.changed`** (`read`, state): `{clipboard}`, the `source.attributes_clipboard` answer or `null`, published on copy and on clear.
- **Older clients and servers.** A 1.67 server answers the new methods `method_not_found`.
- **As built (2026-11-16).** `rbs-scene` `SceneCollection::{duplicate_source, duplicate_scene_with_copies}`, `SourceCopy`, `AttributeGroup`; `rbs-sources` `option_keys`; `rbs-app` `studio_host::attributes` (host compositions, clipboard, API); `crates/rbs-app/tests/studio_attributes.rs` and `crates/rbs-scene/tests/copies.rs` cover them.

### Protocol 1.67: holding a stream with a scene (ADR-0124 phase 2b)

- **`stream.hold` and `stream.hold_toggle`** take `picture: "scene"` with `scene?` (a scene id) and `sound?` (`silence`, `scene`). Absent `picture`, `scene` or `sound`: the stream settings' `hold_picture`, `hold_scene` and `hold_sound`. Errors: `not_found` for a scene not in the collection; `invalid_params` for a scene the canvas cannot show, and for `scene` or `sound` with `freeze` or `black`; `conflict` when no scene is named or set ("no hold scene is set"), and when the stream is already on hold with another scene or sound (resume it first). Holding with `freeze` or `black` while held with a scene changes the picture and lets the scene go. Without `sound`, and with `silence`, the hold sends silence; with `scene`, the scene's own sources at its levels, also on an encoder a recording shares (`recording.md`, "Hold scene").
- **Settings.** `stream` in `settings.get`, `settings.set` and `settings.changed` adds `hold_scene` (scene id or `null`) and `hold_sound` (`silence` by default); `hold_picture` takes `scene`. In a `settings.set` patch `hold_scene` absent leaves it, `null` clears it; `hold_sound` absent leaves it. Saved in the output profile's stream section, omitted while unset or `silence`.
- **State.** A live stream's state (`stream.state`, `stream.canvas_state`) adds `hold_picture` (`null` while not held; `freeze` for a scene hold that fell back), `hold_scene`, `hold_sound`, `hold_fallback` (the scene hold fell back to the last frame and silence), `hold_sound_fallback` (its sound alone fell back to silence) and `hold_fallback_reason`. A hold waiting for a sharing recording's pause reports what it will send. A fallback is published as a change when the studio notices it (`Studio::take_hold_fallback`).
- **Older clients and servers.** A 1.66 client ignores the new fields; a 1.66 server refuses `picture: "scene"` with `invalid_params` and omits the fields, which read as not set, `silence` and no fallback.
- **As built (2026-11-16).** `rbs-api` `HoldPicture::Scene`, `HoldSound`, `StreamHold::{scene, sound}`, the settings and state fields; `rbs-app` `StudioHost::hold_ask` (defaults and checks), `hold_engine` (`Studio::hold_output_scene`, or `hold_output` then `settle_hold_scenes`), releases through `release_hold_scene`, and the service loop's `take_hold_fallback`. Tests: `rbs-api/tests/json.rs` (`hold_methods_take_a_canvas_and_a_picture`, `stream_settings_are_a_minor_addition`), `rbs-app` `stream_profile` (`the_hold_picture_is_saved_only_when_black`), `tests/studio_stream.rs` (`a_control_api_client_holds_a_stream_with_a_scene`).

### Protocol 1.66: sync offset measurement and device offsets (ADR-0126 decisions 7 to 10)

- **`sync.measure_start {source, reference?}`** (`control`) starts measuring `source`'s sync offset: the user claps in view of `reference`, a picture source, several times with pauses of at least half a second. Absent `reference`: the camera of a camera microphone (ADR-0096), else the only camera in the program scene. Answer `{measurement, reference}`: the id (a string) and the reference used. It lasts at most 10 s and ends early after 5 usable claps. Nothing is applied: a client applies the suggestion with `source.set_sync_offset`.
- **Refusals** carry `error.data.reason`: `not_audio` (`invalid_params`, the source has no sound), `no_reference` (`invalid_params`, none named and none found), `not_picture` (`invalid_params`, the reference has no picture), `busy` (`conflict`, one runs already; one per studio), `not_heard` (`failed`, the program mix does not hear the source), `source_closed` (`failed`, the reference shows no picture now, for example while no output takes the canvas). `not_found` for an unknown source or reference, without a reason. A client reads an unknown reason as `other`.
- **`sync.measure_cancel {measurement}`** (`control`) answers `{}`; `not_found` when that measurement is not running.
- **Topic `sync.measure.changed`** (`read`, state): `{measurement, source, reference, state, ...}`, published when a measurement starts, when its pair count changes, and when it ends, never per poll:
  - `{"state": "running", "pairs"}`;
  - `{"state": "done", "suggested_offset_ms", "measured_offset_ms", "effective_offset_ms", "clamped", "pairs", "spread_ms"}`: `suggested_offset_ms` is within `-200..=200` and the input's advance limit; `measured_offset_ms` is before that clamp, `clamped` says they differ; `effective_offset_ms` is the offset the input applied while measuring (from 1.77: the heard offset `h`, which adds the source's filter latency);
  - `{"state": "failed", "reason"}` with `too_few_claps`, `no_picture_motion`, `inconsistent`, `not_heard`, `source_closed`, `offset_changed`, `chain_changed`, `studio_restarted` or `cancelled` (ADR-0126 decision 5). An unknown state or reason reads as `other`.
  The last state stays until the next start. While a measurement runs the control thread reads its probes every 100 ms; without one nothing is read (P13).
- **Device offsets.** The app keeps one offset per audio device of this computer in `device-sync.toml` ([user-data.md](user-data.md)). A device is `key: {type, adapter, target}`: the source type (`org.rbs.source.audio-input` or `org.rbs.source.audio-output`) and its `adapter` and `target` settings. `source.set_sync_offset` on such a source updates its device: 0 removes the entry; the value of the last `done` suggestion for that source is recorded as `measured` with its reference, any other as `manual`. A source added on a device, or retargeted to one (`source.retarget`, `source.set_settings`), takes the device's value (0 without an entry) inside the same undo step, unless it was retargeted with a value that was not its old device's; that fill never updates an entry. Undo and redo restore the value.
- **Desktop window (ADR-0126 step 6).** Properties › Sync offset has Measure, which opens the Measure sync offset window for that source (`studio_host::Command::OpenSyncMeasure`). The window lists the picture sources under "Clap in view of" with the default reference chosen, and Start runs the same measurement as `sync.measure_start` (`StartSyncMeasure`): one runs at a time, whoever started it, and a refusal shows as text with the same reasons. While it runs, the window shows the claps paired, whether a clap-loud sound and a moving picture arrived (`rbs_record::SyncMeasureSignals`), and the time gone; then the result with Apply (`source.set_sync_offset`, recorded as `measured`) and Measure again, or why there is none. Nothing changes until Apply; Cancel, Escape or closing the window cancels a measurement it started (`CloseSyncMeasure`). After a committed change, when other sources use the same device with another offset, the row offers "Apply to N sources" (`ApplySyncToDeviceSources`, as `sync.apply_to_device_sources`).
- **`sync.devices {}`** (`read`): `{devices: [{key, offset_ms, origin, reference?, set_at}]}`, newest first; `origin` is `measured` or `manual` (unknown reads as `other`), `reference` is `{key?, name}` for a measured value, `set_at` seconds since the Unix epoch.
- **`sync.forget_device {key}`** (`control`) answers `{}`; `not_found` when the device has no entry. Sources keep their values.
- **`sync.apply_to_device_sources {source}`** (`control`) gives every other source of the collection on `source`'s device `source`'s offset (live, not undoable, as `source.set_sync_offset`). Answer `{changed: [source ids]}`; `invalid_params` when `source` is not an audio device source; `not_found` for an unknown source.
- **Permissions.** As `source.set_sync_offset` until scopes split them; the on-air check applies to each source once on-air checks land.
- **Older clients and servers.** A 1.65 client ignores the topic; its `source.set_sync_offset` now also updates the device's entry. A 1.65 server answers the methods `method_not_found`.
- **Rust crate.** `Command::{SyncMeasureStart, SyncMeasureCancel, SyncDevices, SyncForgetDevice, SyncApplyToDeviceSources}`, `Response::{SyncMeasureStarted, SyncDevices, SyncAppliedToDeviceSources}`, `Topic::SyncMeasureChanged`, `EventPayload::SyncMeasureChanged` and the types `SyncMeasureChanged`, `SyncMeasureState`, `SyncMeasureFailure`, `DeviceKey`, `DeviceSyncEntry`, `DeviceSyncOrigin`, `DeviceSyncReference`; exhaustive matches must add them.

The desktop app's Settings, Stream, "While on hold" (Last frame, Black). Absent in a `settings.set` patch: unchanged, so a 1.64 client's patch never resets it. Saved in the output profile's stream section, omitted while `freeze`.

### Protocol 1.64: hold a stream, Break (ADR-0124 decisions 12 to 15)

- **Methods** (`control`, live class): `stream.hold {canvas?, picture?}` (`freeze` by default, `black`; `scene` with phase 2b), `stream.resume {canvas?}`, `stream.hold_toggle {canvas?, picture?}` (`canvas` as in 1.29, `all` as in 1.42). One canvas answers `{}`; `conflict` when nothing streams there, the stream is already on hold with that picture (a hold with the other picture changes it), a resume finds it not on hold, or the hold is refused (the message says why); `invalid_params` for an unknown `picture`. With `all` the answer is `{outputs: [{canvas, outcome, error?}]}` as in 1.42, main first, with the outcomes `held`, `resumed`, `not_running` and `refused`; a toggle with `all` holds every live stream when any is not on hold, else resumes them all.
- **A recording sharing the stream's encoder** (decision 14). Holding pauses that recording first (as `record.pause` does, published on `record.state`) and the stream holds once the pause has begun, within two render periods, so the hold picture never reaches the file; `held` is `true` from the call on. `stream.resume` resumes the recording only when the hold paused it, never a recording paused before the hold. While the hold is on or waits, `record.resume` of that recording is `conflict` ("a stream sharing the recording's encoder is on hold"): resume the stream first.
- **`output.break_toggle {}`** (decision 15). When every live stream is on hold and every running recording is paused, it resumes them all, streams first; otherwise it holds the streams that are not held (with their `hold_picture`, `freeze` before 1.65) and pauses the recordings that are not paused. The answer is `{outputs: [...]}` listing only the outputs it changed or that refused, main first, each entry with `kind` (`stream` or `record`); a recording a hold paused or resumed is listed as `paused` or `resumed`. `conflict` when nothing records or streams, or when nothing changed (the first refusal then).
- **State.** `stream.state` and `stream.canvas_state` add `held` (bool) and `held_ms` (time on hold so far, as of the change) to a live stream; published on each hold and resume, never per frame.
- **What a held stream sends.** The connection stays up; the picture (the program's last frame, or black) goes out once per frame with silence, and timestamps keep running (`recording.md`, "Pause and hold"). The program, the preview and the scenes stay free to edit.
- **Permissions.** As `stream.start` and `stream.stop`: any `control` token, until the irreversible-actions permission ships (see `vcam.start`).
- **Older clients and servers.** A 1.63 client ignores the new fields and outcome; a 1.63 server answers the methods `method_not_found` and omits the fields, which read as not held.

### Planned with ADR-0124

- **Markers.** `marker.add` while paused is accepted; the marker sits on that pause's join with `while_paused: true`.
- **Registry.** Each 1.61 and 1.64 method is a command, so shortcuts, the RBS menu, Stream Deck and MCP get it (`record.pause_toggle`, `stream.hold_toggle` and `output.break_toggle` are built; the window runs them with `canvas: all`).

### Protocol 1.60: FCP7 XML editor projects (ADR-0089 decision 9, format 2)

- **`format: "xmeml"`** for `project.export` and for a recording profile's `editor_project`: an FCP7 XML (`xmeml` version 5) project, `<stem>.xml` (then `<stem> 2.xml`, ...), the format DaVinci Resolve reads markers from (recording spec, "Editor project"). `failed` also when the recording's frame rate is neither whole nor NTSC (`N*1000/1001`), which xmeml cannot hold. `"fcpxml"` is unchanged and stays the Final Cut Pro format.

### Protocol 1.59: loudness target and limit, Show loudness saved (ADR-0092 decisions 5 and 7)

- **`settings.get`, `settings.changed`** carry `loudness: {target, true_peak_limit}`: the target in LUFS (from -40 to -5; default -14) and the true-peak limit in dBTP (from -10 to 0; default -1), the user's settings of the desktop app on this computer (`loudness.toml`, [user data](user-data.md)). Each is kept to one decimal.
- **`settings.set`** takes an optional `loudness` with both fields and replaces them; absent leaves them as they are. Either value outside its range is `invalid_params`, checked before anything of the patch is applied. The file is written before anything of the patch is applied: a failed write is `failed` and changes nothing, and a canvas change of the same patch that then fails puts the file back. A change publishes `settings.changed` and shows in Settings › Audio › Loudness and on the Mixer's loudness bar at once. Fields added to `loudness` later are optional, so a client that sends only these two keeps working (the section still replaces what it names).
- **`loudness.status`** adds `target` and `true_peak_limit` (always present, also while the meter is off), so a control surface that only reads loudness needs no `admin` token.
- **`loudness.set_enabled`** is the API twin of Show loudness and is now saved: the app starts with the meter running when it was on. The choice is written first; a failed write is `failed` and the meter stays as it was. It stays `control`, unlike other saved settings of the computer (`settings.set`, `monitor.set_device`: `admin`): Show loudness is a display choice that a control surface (a Stream Deck key) toggles like the Mixer's own menu, it changes no output, and the meter costs nothing while off. The target and the limit stay `admin` (`settings.set`). Everything else of 1.47 holds.
- **Not added: a master row in `audio.levels`.** ADR-0092 decision 8 planned an optional `master: {short_term}` object there, but the topic's payload is an array of source rows, so a sibling field would change its shape for every client. A client reads the master's loudness from `loudness.status` (polled), as in 1.47; a loudness event topic, if wanted, is a later minor version.
- **Older clients and servers.** A 1.58 client ignores the new fields; a 1.58 server ignores `loudness` in `settings.set` (it answers the settings without it, so a client checks for 1.59 first) and keeps Show loudness for the session only.

### Protocol 1.58: editor projects (ADR-0089 decisions 8 to 11)

- **`project.export {recording, format}`** (scope `control`, effect `edit`: it only adds a new file and never replaces one, owner 2026-11-15). `recording` is one name inside the recording profile's folder: a recording folder's name (its `recording.rbs.toml`), a plain recording's file name (its `<stem>.rbs.toml`) or a manifest's name; a separator, `..`, a drive colon or an empty name is `invalid_params`. `format` is `"fcpxml"` (FCPXML 1.9); another name is `invalid_params`. Answers `{file, missing}`: the project's file name next to the manifest (`<stem>.fcpxml`, then `<stem> 2.fcpxml`, ...; never an absolute path) and the separate files the manifest names that are not in the folder, left out. Errors: `not_found` when there is no such manifest (a plain recording without markers or the setting writes none); `failed` when the manifest is not complete (the take kept no timing: no separate files and no `editor_project`, or it did not stop cleanly), the master file is missing or the project cannot be written. It runs on the control thread and takes milliseconds.
- **`editor_project`** on a recording profile (`settings.get`, `settings.set`): `"fcpxml"` writes the project when the recording stops and makes the master keep its timing; absent or `null` is off and the server omits it, so a 1.57 client still reads the profile. Off adds no work to the recording (P13). Protocol 1.62 adds `markers` beside it (see "Protocol 1.62").

### Protocol 1.57: *Test this computer* measures the export (ADR-0087 step D2)

- **`calibration.state`** while `running`: `part` gains `export`, the first part of a run whose plan has separate video files; `adapter` is `null` during it, and `steps` counts each export class as one step. What it measures is in [output-estimate.md](output-estimate.md#calibration-run) ("The export part").
- **`done`** gains `exports: [{size, format, time_us, gpu_us, kept_up}]`, one per measured (size class, format) (`format` is `nv12` or `p010`; `gpu_us` is absent or `null` when too few conversions ran), and `exports_skipped: [{size, format, code}]`. Both are absent or empty from older servers. `skipped` keeps its 1.55 meaning (encoder series and the write). The codes of `exports_skipped` are their own closed list: `gpu_unavailable` (no throwaway GPU context), `export_failed`, `device_lost` (the throwaway device; the run went on), `time_limit` and `cancelled`; 1.55's `code` list is unchanged. A lost live device still ends the run `failed` with `device_lost`. `partial` is also true when an export class was skipped for time or cancel.
- **`record.estimate`** rows (and the `estimate` of a `record.start` refusal) gain `calibrate: bool`: true when *Test this computer* would make the row known ([output-estimate.md](output-estimate.md#reasons)). A client shows the test's advice from it instead of from the resource.
- **Rust crate.** `CalibrationPart::Export`, `CalibrationExport`, `CalibrationExportFormat`, `CalibrationExportSkip`, `CalibrationExportCode` (the enums read unknown values as `Other`), `Done` gains `exports` and `exports_skipped`, `EstimateRow` gains `calibrate` (all `#[serde(default)]`). Struct literals and exhaustive matches on `CalibrationPart` must add them (a breaking change of the crate, not of the protocol).
- **Older clients and servers.** A 1.56 client ignores the new members and reads `part: "export"` as an unknown part. A 1.55 or 1.56 server never sends them; a client checks for 1.57 before relying on them.

### Protocol 1.56: open Settings at one setting (settings search step 1)

- **`ui.settings.open {section?, setting?, command?}`** gains two optional strings ([settings-search.md](settings-search.md)). `setting` is a key of the settings index (`rbs_ui::settings_index::SETTINGS`): a card id such as `settings.recording.replay`, or a row key such as `encoding.video-encoder`. With `section`, the key must show in that section; without one, Settings opens in the key's first section (`encoding.*` keys show in `recording` and `stream`). `command` is a registry command id without parameters; Settings opens at Shortcuts and shows that command's row (`section` absent or `shortcuts`). Scope and routing are unchanged (`control`; routed, so not in the schema).
- **Refusals.** `invalid_params` for an unknown key, a key the given section does not show, an unknown or parameterised command id, `command` with a section other than `shortcuts`, and `setting` with `command`.
- **What it shows.** The section, then the card opened, the row scrolled into view and marked (settings search step 2). The answer is `{}`.
- **Registry.** The entry `ui.settings.open` declares `setting` and `command` (text, optional) beside `section`; `ui.command.run {id: "ui.settings.open?section=stream&setting=encoding.b-frames"}` runs it. The RBS menu's search lists cards and settings as such ids.
- **Not served yet.** Routing of `ui.*` methods is not built ([status](../status.md)), so over the API this version is a contract only; the registry path (menus, toolbar, shortcuts) is built. When routing comes, a server older than 1.56 ignores the unknown optional parameters and opens at the section only, and a 1.55 client never sends them.
- **Keys** are stable once released; a removed setting's key becomes `invalid_params`.

### Protocol 1.55: *Test this computer* (ADR-0087 step D1)

- **`calibration.run {profile, canvas?}`** (`admin`, effect live: it writes a large file into a recording folder). `profile` is a recording profile id, as for `record.start`; `canvas` is `main` (absent or `null`) or `vertical`; `"all"` is `invalid_params`, since a run measures one canvas. It answers `{}` at once; the run goes on in the background and reports on `calibration.state`. What it measures and how (the late-frame rule, the stop reasons, the time budget, the folder write) is in [output-estimate.md](output-estimate.md#calibration-run). The results are merged into this computer's `calibration.toml` and used by the next `record.estimate` and start at once.
- **Refusals.** `conflict` while any recording, stream, virtual camera or armed replay buffer runs on any canvas, while a canvas change or collection switch is restarting the studio, and while a run is active; `not_found` for an unknown profile and for `vertical` without a vertical canvas; `invalid_params` for `canvas: "all"`; `failed` when the run's thread cannot be created. Collection, scene, source and canvas edits, `profile.switch` and settings changes are allowed during a run; the run keeps the plan it took at its start.
- **While a run is active** every start is refused with `conflict`, message "Test this computer is running": `record.start`, `record.start_to_file`, `stream.start`, `vcam.start`, `replay.arm`, the desktop Record, Go live and virtual camera buttons, "Record when the stream starts", and the replay buffer's arm at app start or after a studio restart (which then stays disarmed and says so). Preview and monitoring may stutter while it runs.
- **`calibration.cancel {}`** (`admin`, effect live) asks the run to stop and answers `{}` at once, also when nothing runs. The run stops between rounds and between write chunks; the state stays `running` with `cancelling: true` until it ends, at most 5 s.
- **`calibration.status {}`** (`read`): `{seq, data}` with the state below (`seq` of `calibration.state`).
- **Topic `calibration.state`** (`read`): the same object. It changes when a run starts, once per finished step and series, and when it ends, never per round.
- **State** (`state` tag; a client reads one it does not know as `other`):
  - `{"state": "idle"}`: no run in this app run, also when `calibration.toml` holds older measurements (clients read those through `record.estimate`, whose rows say `measured`).
  - `{"state": "running", "step", "steps", "part", "adapter", "cancelling"}`: `step` counts the steps started, `steps` is an upper bound (series × 20, plus 1 for the write); `part` is `encoder` or `write`; `adapter` is the adapter measured now, `null` during the write.
  - `{"state": "done", "partial", "cancelled", "saved", "encoders", "write_speed", "write_partial", "skipped"}`, kept until the next run. `encoders[]`: `{adapter, codec, size, fps, rate, sessions, pixels_per_second, stopped_by}`, one per series with a result. `write_speed`: the folder's synced write speed in bytes per second, or `null`; `write_partial`: the write stopped early. `skipped[]`: `{code, adapter?, class?}` for each series or write with no full result; `class` is `{codec, size, fps, rate}`, and both are absent for the write. `partial` is true when a series or the write stopped early (time, cancel, an error after step 1) or a series was skipped for time. `saved` is false when `calibration.toml` could not be written; the results are then used for this app run only.
  - `{"state": "failed", "code", "message"}`, kept until the next run; nothing was written.
  - `code` (closed list, an unknown one reads as `other`): `unsupported`, `busy`, `open_failed`, `encode_failed`, `no_room`, `write_failed`, `time_limit`, `cancelled`, `device_lost`, `panicked`, `ended`, `hung`. `stopped_by`: `refused`, `late`, `ceiling`, `limit`, `cancelled`, `error` (an unknown one reads as `other`); what each means for `sessions` is the table in `output-estimate.md`.
  - No member or message carries a path.
- **The run's end.** A run that has not ended 65 s after its start (60 s and a 5 s grace), or 5 s after a cancel, is ended by the server with what it received (`done` with `partial: true`, or `failed` with `hung` when nothing came). Encoder sessions a run that does not answer still holds stay open until the app restarts, so a later start on that encoder may be refused for lack of sessions.
- **`record.estimate`**: `max_video` and `max_audio` gain `known_count: n | null` (additive): the most tracks of the kind for which the encoder session and CPU load rows are known (`output-estimate.md#at-most-n`). No new reason code.
- **Older clients and servers.** A 1.54 client ignores the topic and `known_count`. Its starts may get `conflict` "Test this computer is running", only while an admin client's run is active. After a run, a start opens the number of separate video files the measurement allows, which may be more or fewer than 3, and an older request is trimmed while a growing row is `heavy` (`output-estimate.md#separate-video-limit`). A 1.54 server answers `method_not_found`.
- **Rust crate.** `Command::{CalibrationRun(CalibrationRun), CalibrationCancel, CalibrationStatus}`, `Response::CalibrationStatus(Snapshot<CalibrationState>)`, `Topic::CalibrationState`, `EventPayload::CalibrationState` and the types `CalibrationState`, `CalibrationEncoder`, `CalibrationClass`, `CalibrationSkip`, `CalibrationCode`, `CalibrationPart`, `CalibrationStop`. `MaxTracks` gains `known_count`, so its struct literals must add it; exhaustive matches on `Command`, `Response`, `Topic` and `EventPayload` must add the new variants (a breaking change of the crate, not of the protocol).

### Protocol 1.54: the start gate (ADR-0087 step C2b)

- **`record.start`** takes `acknowledge_heavy: bool?` and `on_hardware_limit: "ask" | "skip" | "cpu"?`; `null` is the same as absent. A request with either one (*new request*) may be refused by the gate; one with neither (*older request*: 1.53 and older clients, the desktop Record and Go live buttons, hotkeys, Stream Deck, "Record when the stream starts") is never refused because of separate video files. `on_hardware_limit` absent uses the profile's `recording.iso.on_hardware_limit` (`ask` by default; a value this build does not know behaves as `ask`). `cpu` is refused with `invalid_params` until the CPU encoder for separate files exists (ADR-0119 step (c), owner record on ADR-0087); any other value is `invalid_params`. An explicit `ask` lets a script be told even when the profile says `skip`.
- **When the gate applies.** Only to a start that writes separate files on the main canvas, whose profile records a picture and whose collection has a source marked for video. Otherwise the parameters are accepted and ignored. `record.start_to_file`, `stream.start` and `audio_record.start` are never gated. The gate judges the plan of `record.estimate` once, **before the take folder is made and before any file opens**, so a gate refusal leaves nothing on disk; it is never re-estimated after the master starts.
- **Gate level.** `gate_level` of the estimate: its level without the `disk_space` row (ADR-0087 decision 2: disk space is planned against a guessed duration and never gates).
- **The bound.** The files that fit are `max_tracks.video.at_most_now` (at most 3 while the encoder's capacity is unknown); the marked sources past it, in source id order, are the *extra* files. Its cause is `encoder` (encoder capacity: the cap of 3, or `encoder_sessions`, `encoder_throughput`, `cpu_load`), `resource` (another resource that grows with the files: `iso_workers`, `iso_render_share`, `disk_speed`) or `no_encoder` (no encoder can take a separate video file).
- **New request.** Extra files with cause `encoder`: `skip` skips them (`limit`), `ask` refuses with `reason: "hardware_limit"`. Cause `resource`: `skip` skips them, `ask` refuses with `over_limit`. Cause `no_encoder`: refused with `over_limit` under both. Then the plan with the kept files: a gate level of `over` refuses (`over_limit`); `heavy` without `acknowledge_heavy: true` refuses (`heavy`). Exactly the kept sources may open a file: one with no picture when the master runs is skipped (`no_picture`) and no other takes its place.
- **Older request.** Extra files are skipped (`limit`); with cause `no_encoder` every video file is skipped (`open_failed`). Then, per resource row that grows with the files, while it is `heavy` or `over` with the kept files and was not with none, the last kept file is skipped too (`limit`); with no calibration every such resource is unknown and nothing is trimmed. The number is a count, as in 1.52: a source with no picture leaves its slot to the next marked one, so the answer's `estimate` describes the plan the gate decided, and `skipped` the final list.
- **Opening the files.** A file whose hardware encoder refuses a session is skipped (`open_failed`) instead of falling to a software encoder, and the other files open; the start answer's `estimate.reasons` carries `software_fallback` for it. Under a new request with `ask` it refuses the start (`hardware_limit`, the same reason in `data.estimate.reasons`); a picture set that fails as a whole refuses with `open_failed`. Such a refusal comes after the master ran: the video files that opened, the master (an encoder it shares with a running stream keeps running for the stream, ADR-0047) and the sound files are stopped, the take folder is removed (a file that cannot be removed is named in the message), and no `record.state` of `recording` is published. Sound files that cannot open refuse the start as in 1.46, except under `skip`, where each is skipped (`open_failed`) and the take goes on.
- **One file.** When the gate skips every video file and no source is marked for images or for sound, the take is one file, as in 1.46 (ADR-0087 decision 7); its skipped files are in the answer and `record.status` only. Skips found while files open still leave the folder.
- **The refusal.** The existing `failed` code (-32040) with `error.data = {kind: "failed", reason, estimate, tracks?}`: `reason` is `hardware_limit`, `over_limit`, `heavy` or `open_failed` (a client reads an unknown one as `other`); `estimate` is the `record.estimate` answer of the plan that was judged; `tracks` (`[{source, role}]`, absent when empty) the files concerned: the extra files, every video file for `no_encoder`, the files that failed while opening. A client recognises a refusal by `error.data.reason`. With `canvas: "all"` a main-canvas refusal fails the whole call; a refused vertical entry's `error.data` carries the same members.
- **Manifest.** `recording.rbs.toml` gains `[[skipped]]` tables (recording spec, "Recording manifest").
- **Older clients and servers.** A 1.53 client ignores the new `data` members. Its `record.start` is an older request: never refused because of separate video files; two things change as ADR-0087 decisions 5 and 7 intend: a file whose hardware encoder refuses is skipped (`open_failed`) instead of falling to a software encoder, and a take whose video files the gate skips, with no image or sound mark, is one file. A 1.53 server ignores the two parameters, so a client checks for 1.54 before relying on the gate.
- **Rust crate.** `RecordStart` gains `acknowledge_heavy` and `on_hardware_limit` (`request::HardwareLimitPolicy`) and `RecordStart::new`; `ApiError` gains `data` (members merged into `error.data` beside `kind`, never overriding it) with `ApiError::with_data` and `wire_data`; `OutputErrorData` gains `more`; `types::StartRefusal` (with `from_error` and `into_error`) and `types::RefusalReason`. Struct literals of these must add the fields.

### Protocol 1.53: the output cost estimate (ADR-0087 step C2a)

- **`record.estimate {profile, canvas?, iso?}`** (`read`, effect none). The parameters are `record.start`'s, with the same errors (`not_found` for an unknown profile and for an explicit `"vertical"` without a vertical canvas; `canvas: "all"` without one is the main canvas alone, as in 1.42). It is answered while a recording runs and while a switch is pending, since it only reads. No path is accepted: the profile's recording folder is the only folder probed.
- **The plan** is built by the studio, never from the caller (`output-estimate.md#the-plan-of-a-start`): every encoder chain that runs on any canvas (shared chains once) and the running separate files, plus what the start adds: the recording of each asked canvas with the profile's settings (on the encoder the profile picks, else the one the selection would most likely use; nothing when it would share a running encoder, ADR-0047), and on the main canvas, when the start writes separate files (`iso` true, or absent with the profile's switch on), one video file per source marked for video, one 24-bit WAV per source marked for sound and the image tracks. A recording that runs on an asked canvas is left out with its separate files, as if it had stopped. The limits are the adapters' declared capabilities, this computer's `calibration.toml` and the cached free space of the profile's recording folder (a folder with no fresh reading is unknown, and is read for the next request; the request never waits).
- **Answer:** `{level, gate_level, unknown, resources, reasons, max_tracks, tracks}`.
  - `level`: `fits`, `heavy` or `over` (ADR-0087 decision 2). `gate_level`: the same without the `disk_space` row, which is planned against a guessed duration and never gates a start. `unknown`: the resources whose limit is unknown, beside the level.
  - `resources[]`: `{resource, scope?, need, limit, unit, level?, measured}`, one row per resource of `output-estimate.md#rows`. `scope` is the adapter id for `encoder_sessions` and `encoder_throughput`, `video` or `audio` for `iso_ceiling`. `need` and `limit` are finite JSON numbers, whole for counts and bytes; `limit` is `null` when unknown or unlimited, and `level` says which (`unknown`, or `fits` on a software adapter with no session limit). `memory` and `active_sources` are informational, with no `level`. `measured` is true when the limit comes from `calibration.toml`.
  - `reasons[]`: `{code, resource?, track?}` with `code` from the closed list of `output-estimate.md#reasons` and `track` `{source, role}`.
  - `max_tracks.video` and `max_tracks.audio`: `{count, limit, partial, unknown}` (ADR-0087 decision 3; `count` and `limit` `null` when no growing resource is known). `video.at_most_now`: the most separate video files a start with these settings opens now, however many are marked: `count`, and at most 3 while the encoder's session limit (hardware) or load (software) is unknown (`output-estimate.md#separate-video-limit`). Absent with no picture (vertical canvas, WAV or FLAC profile, `iso: false`).
  - `tracks[]`: `{source, role, cost}` per separate video and sound file of the plan; `cost` maps resource names to what the file adds. Image tracks cost no encoder and are not listed.
  - A client reads an enum value it does not know (level, resource, unit, code, role) as `other`, and skips a `cost` key it does not know.
- **`record.start`'s answer** gains `estimate: {level, unknown, reasons}`, the estimate of what runs once the recording started (the plan the start opened), and `skipped`, the list `record.status` shows (absent when empty). With `canvas: "all"` each started entry gains them.
- **Nothing else changes.** The number of separate video files a start opens comes from the same estimate, now with the calibration and the probe of the profile's folder; with no calibration and no declared session count it stays 3 on every computer. No start is refused that 1.52 accepts.
- **Older clients and servers.** A 1.52 client ignores the new fields. A 1.52 server answers `method_not_found` to `record.estimate`.
- **Rust crate.** `Command::RecordEstimate(RecordStart)`, `Response::RecordEstimate(types::EstimateAnswer)` and the types `EstimateLevel`, `EstimateResource`, `EstimateUnit`, `EstimateCode`, `EstimateRow`, `EstimateReason`, `EstimateTrack`, `MaxTracks`, `MaxTracksByKind`, `TrackCost`, `EstimateSummary`. `RecordStarted` and `OutputEntry` gain `estimate` and `skipped`, so struct literals must add them (a breaking change of the crate, not of the protocol).

### Protocol 1.52: separate picture files (ADR-0086 step 3.5, ADR-0117)

- **`source.set_record_separately {source, enabled?, video?, audio?, video_as?}`** (`control`, effect `edit`) is now a patch: an absent field, or `null`, keeps the source's value (`video_as: "auto"` resets the form). The call is one undo step, and records none when nothing changes. `enabled` keeps its 1.46 meaning for a sound source and for a source with both (a media file, or a type this server does not classify): their sound. On a picture source (display, window, camera, image, colour, browser) it now marks the picture instead of being refused. `video` and `audio` set each feed. `video_as` is `auto` (images for a still source, a video file otherwise, decided when each recording starts), `video` or `image`, and is kept only while the picture is marked (clearing `video` resets it to `auto`). Refused with `invalid_params`: `enabled` together with the feed it stands for (`video` on a picture source, `audio` otherwise), `video: true` on a sound source, `audio: true` on a picture source, `video_as: "image"` on a source that is not still (image or colour), a `video_as` other than `auto` when the picture is not marked after the call (it would not be saved), an unknown `video_as`, a mark the start plan cannot take (more than 16 video or 32 image marks), and any other field (the per-track options of ADR-0086 decision 2 are later minors).
- **Sources.** `source.list` rows and `source.changed` keep `record_separately: true` for the feed `enabled` stands for (a picture source's picture, anything else's sound), so an older client's switch shows and clears that feed, and add `record_tracks: {video?, audio?, video_as?}` for every feed (each absent when false or `auto`; the object absent when nothing is marked; a `video_as` this client does not know reads as `other`).
- **What a start writes.** With `iso` absent, `null` or `true` on the main canvas's recording, a marked picture source is written beside the master in the recording's folder: a video file `<name>.<ext>` in the recording's container with its video settings, or, for a still source, PNG images `<name>.png`, `<name>-2.png`, ... (ADR-0117), the source's own picture without its filters (ADR-0119 decision 1). They open once the master runs (sources draw only while something takes the canvas) and are added to `recording.rbs.toml`, which is written again; image entries (`[[files.images]]`) are written when the recording stops. The number of video files is the ADR-0087 estimate's "at most N" for this computer, and at most 3 while the encoder's session limit (hardware) or load (software) is neither measured nor declared, the owner's choice of 2026-11-14 ([output-estimate.md](output-estimate.md#separate-video-limit)); image and sound files are not counted; the marked sources past it, in source id order, are skipped. A request without new start parameters is never refused because of picture files the plan accepts (ADR-0087 decision 7; a collection whose marks the plan refuses, which only a file edited by hand or written by another build can hold, refuses the start with the reason, as in 1.46): a source with no picture yet, a recording with no picture (WAV or FLAC), and files that cannot open are skipped. When every picture file is skipped and no source is marked for sound, the take is still a folder with `master.<ext>` and the manifest (ADR-0087 decision 7 asks for one file there; it would need the picture check before the master starts). Protocol 1.54 ends this for the skips its start gate decides before the folder is made.
- **State.** `tracks` rows gain roles `video` (the file name with its extension) and `image` (the first image's name). `skipped` gains the reasons `limit`, `no_picture`, `audio_only` and `open_failed`; `role` names the feed (`video` or `image`).
- **Older clients and servers.** A 1.51 client reads the new roles and reasons as unknown (`other`), and its `{source, enabled}` call does what it did for sound sources; on a picture source it now marks the picture instead of failing. A 1.51 server refuses `video`, `audio` and `video_as` with `invalid_params` and a picture source's `enabled` too. A collection with a picture form other than automatic is saved as scene format 18, which older builds refuse to open.
- **Rust crate.** `SetRecordSeparately::enabled` becomes `Option<bool>` and the struct gains `video`, `audio`, `video_as` (`request::VideoAs`) and `Default`; `SourceInfo` gains `record_tracks` (`types::RecordTracks`); `TrackRole` gains `Image`; `SkipReason` gains `Limit`, `NoPicture`, `AudioOnly` and `OpenFailed`. Code that builds them with struct literals or matches them exhaustively must change (a breaking change of the crate, not of the protocol).

### Protocol 1.51: MOV recording profiles (ADR-0085 step c)

A recording profile's `container` may be `"mov"`: QuickTime, written fragmented like `"mp4"` so a crash leaves a playable file, with the same video codecs and AAC audio. It needs a video encoder to start, like MKV and MP4. `output.profiles` rows and `settings.get` show it; `settings.set` takes it. A 1.50 client treats `"mov"` as an unknown container; a 1.50 server refuses it with `invalid_params`.

### Protocol 1.50: recording markers (ADR-0089, first slice)

- **`marker.add {label?, color?, canvas?}`** (scope `control`, effect `edit`: `marker.remove` takes it back with nothing lost). A manual marker in every running recording `canvas` names: `main`, `vertical` or `all`, the default. Each recording gets it at the same master-clock time, relative to its own start. `label` is one line of at most 200 Unicode scalar values (surrounding spaces trimmed); absent or blank is "Marker N", N counting that recording's manual markers. `color` is `blue` (default), `red`, `orange`, `yellow`, `green` or `purple`. Answers `{markers: [{canvas, index, t_ns}]}`, main first: `index` is 1-based and stable for the recording, `t_ns` the position from the recording's start in nanoseconds. Errors, in this order: `invalid_params` (label, colour, canvas or any other field); `not_found` for `vertical` without a vertical canvas; `conflict` when nothing records on the canvases asked for, or a recording has 10 000 markers (nothing is added then). At most 2 calls a second per session, refused or not; more is `rate_limited`, sent at once like the other protecting refusals. The limit is the API's: the desktop's Marker command and shortcut (a later step) will not have it.
- **`marker.remove {canvas, index}`** (scope `control`, effect `edit`). `canvas` is `main` or `vertical`. The other markers keep their index and a later marker never reuses it. Answers `{}`. Errors: `invalid_params`; `not_found` for `vertical` without a vertical canvas and for an index the recording does not have; `conflict` when nothing records on that canvas.
- **Where they go.** The recording's manifest (recording spec, "Recording manifest"), written when the recording stops: `recording.rbs.toml` in a recording folder, `<file stem>.rbs.toml` beside a plain recording that has markers. The reaction-time offset (`marker_lead`), the periodic flush, automatic markers, `marker.list` and the `marker.changed` topic are later minors; `project.export` is protocol 1.58.
- **Older servers.** A 1.49 server answers `method_not_found`; a client checks the protocol version first.

### Protocol 1.46: separate files (ADR-0086)

- **`source.set_record_separately {source, enabled}`** (`control`, effect `edit`). Marks the source to record its sound as a file of its own, or clears the mark. 1.46 writes sound only, so it marks a sound source, and a source with both (a media file, or a type this server does not classify) for its sound; a picture source (display, window, camera, image, colour, browser) is refused with `invalid_params` until the minor that writes picture files (ADR-0086 step 3). One undo step (`edit.undo`), saved with the collection (scene format 16 only in a file that has a mark). Marking a source while a recording runs changes nothing in that recording (decision 10). Setting the value it already has changes nothing and records no undo step. Answers `{}`; `source.changed` follows. Errors: `not_found` for an unknown source; `invalid_params` for a picture source and for any other field, including the per-track options of decision 2 (`exclude_filters`, `size`, `max_height`, `frame_rate`, `raw`), which later minors add.
- **What a start writes.** When the main canvas's recording starts with `iso` absent, `null` or `true` (there is no profile setting for it yet; decision 11's profile default comes with the `recording.iso` section) and at least one source is marked for its sound, the recording is a folder named like the file would have been (the profile's file name without its extension), holding `master.<ext>` (the recording), one 24-bit PCM WAV per marked sound source named after the source (recording spec, "Separate files") and `recording.rbs.toml`, the manifest, which lists only the files written. The folder is made by the start and must not exist (`failed`, "... already exists"), so nothing outside it is written or removed. A marked source the program mix does not hear when the take starts (a microphone on no scene on air) gets no file and is listed in `skipped`; the take starts (keeping such sources running is decision 8, a later step). Any track that cannot open refuses the whole start and removes what it made (decision 5's default); the master never starts without its tracks. "Record when the stream starts" behaves like Record. `iso: false`, `record.start_to_file`, the vertical canvas's recording and a collection with no sound mark record one file as before. With `canvas: "all"` only the main recording has the files (decision 1). The tracks stop with the master. When every marked source is unheard, the take is still a folder, holding `master.<ext>` and the manifest, with `tracks` absent and every source in `skipped`. (1.52 adds picture files and skips the picture tracks that cannot open instead: see "Protocol 1.52".)
- **Timing.** The files share the master clock but start a little apart (the WAVs open before the master); offsets from `t0` are not written yet (`start_offset_ns`, decision 5 and 6, a later step), so 1.46 files are aligned by hand in an editor, to within the start-up time of the master's encoder.
- **State.** `record.status` and `record.state` add to a running recording `tracks: [{ "file": "Microphone.wav", "role": "audio", "source": 3 }]`, file names inside the folder with no directory, and `skipped: [{ "source": 4, "role": "audio", "reason": "not_heard" }]`. Each is absent when empty, so an object without separate files is unchanged. `role` is `"audio"` in 1.46 and `reason` is `"not_heard"`; a client reads a value it does not know as another role or reason, not as an error (the Rust types have an `other` variant).
- **Sources.** `source.list` rows and `source.changed` add `record_separately: true` for a source marked for its sound; absent means not marked. A picture mark that a later version saved in the collection is kept but not shown, since 1.46 writes nothing for it. The `scene.list` source rows do not carry the mark.
- **Older clients.** The objects a 1.45 client reads are unchanged. Its `record.start` on a collection where a 1.46 client marked a source writes the folder above, since `iso` defaults to true; a client that wants one file passes `iso: false` (ignored by a 1.45 server) or clears the marks. The new refusal is the existing `failed` code.
- **Older servers.** A 1.45 server answers `method_not_found` to `source.set_record_separately` and ignores `iso`, so a client checks for 1.46 before relying on either. 1.45 was WAV and FLAC profiles.
- **Rust crate.** `rbs_api::types::RecordState::Recording` gains `tracks` and `skipped`, `SourceInfo` gains `record_separately` and `RecordStart` gains `iso`, so code that builds them with struct literals must add them (a breaking change of the crate, not of the protocol).

### Protocol 1.45: WAV and FLAC recording profiles

A recording profile's `container` may be `"wav"` or `"flac"`. WAV is PCM of the mix with no picture. `bit_depth` is 16, 24 or 32 (32 is float). FLAC is a native FLAC stream of the mix, with no picture. `bit_depth` is 16 or 24 (integer). Omitted, and 16, are 16-bit, and the server omits 16 so a 1.44 client still reads a profile that stays MKV or MP4. A 1.44 client treats `"wav"` and `"flac"` as unknown containers. 32 is a WAV width and is refused for FLAC. A WAV or FLAC profile does not need a video encoder to start; MKV and MP4 still do. 1.42 and 1.43 were already `canvas: "all"` and `scene.duplicate`.

### Protocol 1.41: source region and display chrome (ADR-0103, ADR-0104)

`source.set_region { source, region }` sets or clears a source's region. `region` is `[left, top, right, bottom]` in full-picture pixels, or `null` for the whole picture. `source.get_region { source }` returns `{ source, region }`. Both need `control`. One undo step, an edit kind of its own, not `item.set_crop`. `not_found` for an unknown source. `invalid_params` for a sound-only source, or for a region that leaves no pixel after intersection with the picture size the source has already reported. When that size is not known yet, the region is stored.

`source.set_chrome { source, chrome }` writes display chrome and the region those insets describe. `chrome` is `{ top, right, bottom, left, fill }` (`fill` `"cover"` or `"fit"`, default cover) or `null` to clear chrome and the region. It does not move the item box and does not restart capture. Only `org.rbs.source.display` may store it (`invalid_params` otherwise). `source.get_chrome` returns the stored chrome or `null`. `source.fit_chrome { source }` is a separate undo step that places the item with the stored fill (cover fills the canvas, fit letterboxes) using the region size. `source.reset_chrome { source }` copies insets from the display's `work_rect` when the adapter reported one; when it did not, the call changes nothing and records no undo step.

The settings Region section, its 960-pixel grab, and the add-source region step are not in the desktop UI yet (rule 16). `region_grab` on the capture port is the method that preview will call. It is not `thumbnail`, and `THUMBNAIL_MAX` is unchanged.

A 1.40 server answers `method_not_found` to these methods.

### Protocol 1.40: AV1 in recording settings

A recording profile's `video_codec` may be `"av1"` (omitted still means H.264, `"hevc"` is unchanged). The server offers it when an encoder lists `av1`; a stream's `video_codec` stays H.264 because neither RTMP nor MPEG-TS carries AV1 yet, and a `settings.set` that stores `"av1"` on `stream` is kept but the desktop does not offer it for a stream. A 1.39 client treats an unknown `video_codec` the way it treats any unknown enum value. Old profile files without the field stay H.264.

### Protocol 1.39: output size (ADR-0102)

A recording profile and `stream` may carry `output_size`: `{ "width", "height" }`, both even, the canvas-aspect fit of an even long side, each side from 2 to 7680 (ADR-0102 decisions 4 and 7). Omitted, or `null`, means the same as that output's canvas, and the server omits it then, so a 1.38 client still reads the object. `settings.set` that omits it stores the same as canvas. A size that fails those checks is `invalid_params` and writes nothing. `settings.changed` carries the field the same way as `settings.get`.

The size is not a canvas change: storing it does not restart the studio and does not move scene items. An output that has already started keeps the size it started with. The next `record.start`, `stream.start`, Record or Go live reads the stored size. While a recording uses the profile, a `settings.set` that would change it (including only `output_size`) stays `conflict` ("stop the recording before changing its settings"). While a stream runs, a `settings.set` of `stream` that would change it stays `conflict` ("end the stream before changing its settings"). The resolved size must also lie in the encoder's declared `codec.video.width` and `codec.video.height` when the encoder chosen at start declares them; that refusal is the start's, not `settings.set`'s, because the encoder may be "Automatic".

Old profile files with no `output_size` read as the same as that canvas (`format_version` stays 1). Vertical recording and stream sections of the profile store the same field, each meaning that canvas when absent. They are not in `settings.get` or `settings.set` in 1.39 (protocol 1.29). While `recording-vertical` is absent, the vertical recording uses the main encoding settings but not the main `output_size`: it encodes at the vertical canvas. `rbs-app` serves `output_size` on the main recording profile and on `stream`.

### Protocol 1.38: open shadows

A recording profile and a stream `encoding` may carry `open_shadows`: a boolean. Absent means false, and the server omits it then, so a 1.37 client still reads the object. True lifts only the darkest tones of a Video encode; the file or stream stays Rec. 709 limited range, at 8-bit and at 10-bit. It does nothing while `delivery` is `"screen"`, and the value is still stored. Changing it does not restart an output that is already running.

### Protocol 1.37: output colour

A recording profile and a stream `encoding` may carry `delivery`: `"video"` or `"screen"`. Absent means `"video"` (Rec. 709 limited range), and the server omits it then, so a 1.36 client still reads the object. `"screen"` is sRGB full range, for a file that should match the desktop. A value other than those two is `invalid_params`. Changing it does not restart an output that is already running.

### Protocol 1.36: layer ends (ADR-0084 Arrange)

`item.move` and `scene.move` accept `direction` values `front` and `back` in addition to `up` and `down`. For an item, `front` / `back` move it to the top or bottom among sources with a picture. For a scene, they move it to the start or end of the canvas's scene list. Already at that end answers `{}`. A 1.35 server that only knows `up` / `down` answers `invalid_params` for `front` / `back`.

### Protocol 1.13: source retarget and reload (ADR-0077)

`source.retarget` and `source.reload` are what the Source tab of Properties runs. Refusals: `not_found` for an unknown source. `source.retarget` does not check that the adapter lists the target: like a stored document, a target that does not exist is reported by the source's status afterwards. Protocol 1.20 adds the source status `{"state": "unavailable", "fault": ..., "detail": ...}` to `source.list`, `source.changed` and `scene.sources`: `fault` is `target_gone`, `permission_denied`, `busy` or `other` (a client treats a value it does not know as `other`), `detail` is the adapter's own text. A server below 1.20 reports such a source as `failed` with `reason`; a client treats any `state` it does not know as `failed` and shows its `reason` or `detail` (the `rbs-api` decoder does; `rbs-api` 1.13 to 1.18 decoders are derived and refuse a whole `source.list` payload with an unknown `state`, so a client of that age should upgrade). The server sends `other` only for a fault it has no name for; `detail` is the adapter's text, as `failed.reason` always was, and may name a window or a path. 1.20 follows 1.19 (the audio ducker, ADR-0095): a 1.20 server has everything of 1.19. A 1.12 server answers `method_not_found`. Protocol 1.27 adds `replay.status`, `replay.arm`, `replay.disarm`, `replay.save` and the `replay.changed` topic (the instant replay buffer, ADR-0088); 1.27 follows 1.26 and has everything of it. Protocol 1.23 adds the client-scoped `ui.profile.*` and `ui.collection.*` methods (new, duplicate, rename, delete, import, export; the Output profile and Scene collection menus run them); 1.23 follows 1.22 and has everything of it. Protocol 1.22 adds the client-scoped `ui.workspace.save`, `ui.workspace.save_as`, `ui.layout.set_locked`, `ui.layout.undo` and `ui.layout.redo` (the workspace menu runs them; the shown workspace is the UI client's); 1.22 follows 1.21 and has everything of it. Protocol 1.21 adds the client-scoped `ui.panel.move`, `ui.panel.float` and `ui.panel.dock` (the panel menu runs them; a 1.20 server has everything else of 1.21).
