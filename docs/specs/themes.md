# Spec: Themes and appearance

- Status: Draft
- Owner crate(s): `rbs-ui` (`tokens`: theme model, resolving, checks, bounds, token metadata), `rbs-user-data` (theme and appearance documents, theme library), `rbs-app` (Settings › Appearance, theme editor, applying themes to windows and native layers)
- Related ADRs: [0015](../adr/0015-ui-design-rules.md), [0049](../adr/0049-main-window-areas-panel-states-and-sizes.md), [0051](../adr/0051-user-data-profiles-and-scene-collections.md), [0057](../adr/0057-user-themes-and-appearance-settings.md)
- Rules: [UI principles](../ui/principles.md) U7, U11, U12, U17

## Purpose

Users change the look of RBS with themes: files that override design tokens on top of a built-in theme, kept in a library, shared as single files, and chosen in Settings › Appearance. This spec defines the theme file, the appearance file, the checks every theme passes and how the app applies a theme.

## Scope

In scope: the theme document (format 1), resolving a theme on its base, checks and bounds, the theme library, the appearance document, the Appearance page's behaviour, applying a theme at run time.

Out of scope, later changes: themes in `.rbspack` packs; font files; a curated accent shortcut; detecting the OS high-contrast setting (RBS ships no high-contrast theme, [ADR-0123](../adr/0123-remove-the-high-contrast-theme.md)); theme methods in the control API other than `ui.theme.reload` and `ui.theme.switch {id}` (View › Theme; [control API](control-api.md#client-scoped-ui-commands)); a text size preference. The token names, groups and built-in values are in the [design system spec](ui-design-system.md#tokens).

### Theme rules

Run by `Tokens::resolve` on every resolved theme and by `Tokens::parse` on the built-in file (each theme in it), so built-in tuning is held to the same rules:

- **Contrast**: the rules of the design system plus `color.border.focus` on `color.surface.overlay` and `.sunken` (3:1), `color.text.inverse` on `color.accent.hover` (4.5:1), `color.accent` on every surface (3:1), `color.text.secondary` on `color.accent.subtle` (4.5:1), `color.state.live` on `color.surface.sunken` (3:1), and the pairs the desktop UI draws besides: `color.state.error` (error text) on every surface and on `color.accent.subtle` (4.5:1), `color.border.focus` on `color.accent.subtle`, `color.border.strong` on `color.surface.base`, `.sunken`, `.overlay` and `color.accent.subtle`, `color.brand` on `color.surface.raised` and `.overlay` (3:1; the RBS mark on its chip in the menu button), and `color.accent` on `color.accent.subtle` (3:1; the last three for a Checkbox on a hovered or selected row, ADR-0062), and `color.state.warning` on `color.surface.overlay` and `color.accent.subtle` (3:1; the mark of an unavailable source on a hovered or selected row, ADR-0077), `color.state.warning` on `color.surface.base` (4.5:1; the paused recording's chip and status text, ADR-0124; the light theme's warning is `#8f6000` for it, owner 2026-11-16), and the notice card: `color.text.primary`, `color.text.secondary` and `color.toast.edge` on `color.toast.surface`, and `color.toast.surface` (the seconds and the hourglass) on `color.toast.edge` (4.5:1), `color.border.focus`, `color.border.strong` and `color.accent` on `color.toast.surface` (3:1), and `color.toast.edge` on `color.surface.base`, `.raised`, `.overlay` and `.sunken` (3:1, so the outline stays visible on the window and on panels). Test `every_drawn_pair_has_a_contrast_rule` (in `rbs-app`, which owns the `.slint` files) reads them and fails when a text, border or icon colour is drawn on a theme colour no rule covers, or covers only with 3:1 when it is text (4.5:1). It expands components per instance (the instance's properties over the defaults, children at `@children`), takes the nearest ancestor `background` (through `transparent`; a popup or window starts afresh; a colour that is not a theme token ends the search), follows `if` conditions and ternaries with each condition as one atom shared by every expression of that instance (so a button's background and text take the same branch), and checks a `FocusRing` against what is around its control. Exempt: `color.text.disabled` (inactive controls, WCAG 1.4.3) and `color.border.subtle` (dividers and resting outlines that carry no meaning alone). The Tint buttons add `color.text.primary` and `.secondary` on `color.button.fill`, `.hover`, `.pressed` and `.chip`, `color.text.primary` on `color.accent.subtle.hover`, `color.text.inverse` on `color.accent.pressed` and `color.state.error` on `color.action.destructive.subtle` and `.subtle.hover` (4.5:1), `color.text.secondary` on `color.accent.subtle.hover`, `color.action.destructive.subtle` and `.subtle.hover` (a Button's caption and hint; 4.5:1), and `color.accent` on `color.button.chip` and `color.accent.subtle.hover`, and `color.border.focus` on `color.button.fill`, `.hover`, `.pressed`, `color.accent.subtle.hover` and both danger fills (3:1; the focus ring is drawn over the button's own fill). Accepted without a rule: `color.state.live` on `color.surface.raised` and `.overlay` (the fixed live colour is not a theme's to fix and live always shows its words, ADR-0057 review item 1), and on `color.accent.subtle` (the small live dot before "REC" on the selected scene row); the test lists them by name, so any other live pair fails. Record's dot and a running output's stop square on a button sit in a `color.surface.sunken` well, covered by the live rule (ADR-0118). A `ContextMenuArea`'s `Menu` is not read: its built-in items are a native menu in a window of its own (ADR-0125 decision 6). Not seen: a sibling drawn under a text and colours set from Rust (native layers).
- **Live red reserved**: every theme colour differs from `color.state.live` by at least ΔE2000 15 (`MIN_DELTA_E_FROM_LIVE`); the 45 degree hue rule for `color.state.error`, `color.action.destructive` and `color.meter.clip` stays.
- **Across tokens**: the `line` of `type.caption`, `type.body` and `type.label` and `size.icon.box` are at most `size.control.sm`; `size.control.sm <= .md <= .lg`; `space.1 <= space.2 <= space.3 <= space.4 <= space.6 <= space.8`; `radius.sm <= .md <= .lg`; text sizes `caption <= body <= title <= heading` and `body <= label <= title`; `size.focus-ring <= space.1`; `size.field.gap <= size.section.gap`; `size.icon.box <= size.button.chip <= size.control.sm` and `radius.button` at most half of `size.control.sm` (ADR-0118). A token below its floor (`MINIMUMS`: `size.focus-ring`, `size.icon.*`, `size.panel.pad` 8, `size.section.gap` 12, `size.field.gap` 6, `size.tab.indicator` 2, `size.toast.border` 2, `size.toast.rail` 4, `size.window.min-*`) makes the file refused with "<token> must be at least <floor> (<rule>)"; panel padding has a ceiling of 64 like the other spacing tokens. `size.tab.indicator` is not themeable.
- **Size**: a theme file over 64 KiB (`MAX_THEME_FILE`) is not read; more than 256 unknown token names (`MAX_UNKNOWN_TOKENS`) fails the theme.

### Effects ([ADR-0120](../adr/0120-theme-effects.md), [ADR-0122](../adr/0122-bold-theme-effects.md))

A theme chooses how lively its controls look: **Calm** (no key, the default), **Glow**, **Glass** or **Tactile**. Implemented in `rbs_ui::tokens` (`effects.rs`, `theme.rs`), `rbs_ui::tokens_slint` and the library components that draw effects (the design system's "Effects": the buttons, `Toggle`, `SegmentedControl` and, from 2026-11-17, the wells, `Checkbox`, `Slider`, cards, `ChoiceCard`, `ColorPicker` and `SettingsNavItem`).

- **Settings** (ADR-0122 decision 1): `"calm"`, `"glow"`, `"glass"`, `"tactile"`. `"vivid"`, ADR-0120's name for Glow, reads as Glow: `Effects::from_name("vivid")` gives `Effects::Glow`, and `Effects::name()` never returns it. A stored `"vivid"` is kept as stored until the user picks a segment of the Effects row, which writes `"glow"`.
- **Token file format 4** has `[effects.glow]`, `[effects.glass]` and `[effects.tactile]`; calm has no table (all zero). It still needs `[font]` and needs all three tables; an unknown table (`[effects.vivid]`) or an unknown token (`effects.sheen.*`, `effects.glow.*`) is refused.
  - **A format 3 file** (ADR-0120's tables) is still read: `[effects.vivid]` becomes Glow and `[effects.tactile]` Tactile, `effects.glow.*` becomes `effects.halo.*`, `effects.sheen.*` is dropped and every new token is 0. A table with both a glow and a key edge loses the glow, because a halo needs `effects.key.edge` 0. Such a file has no Glass: a theme that asks for it resolves to calm with the notice "This build's token file has no Glass effects".
  - **A format 1 or 2 file** has no effect tables: every theme resolves to calm, and a theme that asks for more gets the notice "This build's token file has no effects". A table in such a file is refused.
- **Effect tokens** (each table holds all of them; inclusive bounds; not themeable one by one; a fraction is a TOML number from 0 to 1):

  | Token | Bounds | Meaning |
  | --- | --- | --- |
  | `effects.shadow.blur` | 0 to 4 px | Blur of the drop shadow |
  | `effects.shadow.offset` | 0 to 2 px | Its offset downward |
  | `effects.shadow.alpha.dark`, `.light` | 0 to 0.6 | Its opacity on a dark and on a light base |
  | `effects.halo.blur` | 0 to 16 px | Blur of the primary's outer glow (the halo) |
  | `effects.halo.alpha` | 0 to 0.8 | Its opacity at the box edge |
  | `effects.key.edge` | 0 to 3 px | Height of the darker edge under the face |
  | `effects.key.shade` | 0 to 0.6 | The key edge is the rest fill mixed toward black by this |
  | `effects.press` | 0 to 3 px | How far the face moves down while pressed |
  | `effects.gloss` | 0 to 0.4 | The top of a face is its fill mixed toward white by this |
  | `effects.face.dark` | 0 to 0.3 | A ceiling: at most, the bottom of a face is its fill mixed toward black by this |
  | `effects.rim.mix` | 0 to 0.8 | The rim: the kind's rim colour mixed into `color.border.subtle` by this |
  | `effects.inner.blur` | 0 to 8 px | Blur of the inner glow (an inset shadow in the kind's rim colour) |
  | `effects.inner.alpha` | 0 to 0.4 | Its opacity |

  Rules: `effects.press <= effects.key.edge`; `effects.key.edge + effects.shadow.offset + effects.shadow.blur <= EFFECT_EXTENT_MAX` (4 px, a constant; the halo is outside this rule); `effects.key.edge = 0` while `effects.halo.alpha` is above 0.
- **Built-in tables** (ADR-0122 decision 11): Glow has a 12 px halo at 0.6, a rim at 0.55, an inner glow of 6 px at 0.25 and a 3 px shadow offset by 1; Glass has gloss 0.3, `face.dark` 0.3 and the same shadow; Tactile has edge 3, press 2, shade 0.55, gloss 0.12 and a 1 px shadow. The shadow alpha is 0.5 on Dark and 0.3 on Light in all three.
- **Derived colours** (ADR-0122 decision 4): every one is computed in Rust (`draw`, read by `slot()`), and Slint mixes nothing. Mixing is per channel in encoded sRGB, rounded to nearest: `toward_white(c, f) = c + (255 − c)·f`, `toward_black(c, f) = c·(1 − f)`, `mix(a, b, f) = a + (b − a)·f`. The colours are the shadow (black at the base's alpha), the halo (`color.accent` at the halo alpha), the key edge of each kind (its rest fill toward black), the top and bottom stop of each kind's face per state, the rim and the inner glow.
- **Kinds** (`FACE_KINDS`, the order of every per-kind array): primary (`color.accent`, `.hover`, `.pressed`; ink `color.text.inverse`; no ring pair), secondary and a framed ghost (`color.button.fill`, `.hover`, `.pressed`; inks `color.text.primary` and `.secondary`; rim `color.accent`), checked (`color.accent.subtle`, `.hover`; inks `color.text.primary`, `.secondary` and `color.accent`), danger with text (`color.action.destructive.subtle`, `.hover`; inks `color.state.error` and `color.text.secondary`; rim `color.action.destructive`). The chosen plate of a SegmentedControl (`surface.overlay` in every state; ink `color.text.primary`; ring pair; owner 2026-11-16) is an inset kind: its one height is `size.control.md − 2 · size.focus-ring` after density (`plate_height`), not the three button heights (`kind_heights`). Checked and danger have no pressed fill of their own and use their hover fill.
- **The face gradient** (ADR-0122 decision 5): a button that draws effects has a vertical gradient of three stops: the fill toward white by `gloss` at the top, the fill at the gloss stop, and the fill toward black by the kind's scaled `face.dark` at the bottom. A face whose stops all equal its fill is drawn flat.
  - **The ink band** of a button `height` tall starts at the band top, `(height − type.label line) / 2` (`band_top`): 4 of 28 px, 2 of 24 and 6 of 32.
  - **The gloss stop** of an instance is `max(band top / height, s)` of its own height (`gloss_stop`), where `s` is the kind's searched stop.
  - **The search**, per kind and in steps of 0.01: first `face.dark` is the largest value at which every pair of the kind holds for every state and for `size.control.sm`, `.md` and `.lg` after density; then `s` grows from 0 while every pair still holds, to at most 0.45 (`GLOSS_STOP_MAX`). A searched stop that is above every height's band top is stored as 0 (the band top).
  - **The pairs** are the existing rules (`CONTRAST_RULES`, `THEME_CONTRAST_RULES`) between the kind's inks and its fills, checked at both ends of the ink band and at the stop when it lies inside the band, plus `color.border.focus` on the bottom stop for a kind whose ring is drawn over its face. A pair must reach `min(rule + 0.05, its calm ratio)` (`FACE_MARGIN`, for Skia's rounding between stops). A pair whose calm ratio is under its rule is skipped: ADR-0072 already warns about it.
  - **The built-in colours resolve to** (regular density; "band top" is `s` = 0):

    | Kind | Dark Glass: `face.dark`, stop | Light Glass: `face.dark`, stop | Dark Tactile: stop | Light Tactile: stop |
    | --- | --- | --- | --- | --- |
    | primary | 0.09, 45 % | 0.30, band top | 45 % | 9 % (0.2 px under the band top of a 24 px button) |
    | secondary | 0.30, band top | 0.03, 45 % | band top | 45 % |
    | checked | 0.30, 10 % | 0.03, 45 % | 14 % | 45 % |
    | danger | 0.30, band top | 0.02, 45 % | band top | 45 % |
    | chosen plate | 0.30, 45 % | 0.06, 45 % | 45 % | 45 % |
- **The rim and the inner glow** (ADR-0122 decisions 6 and 7): the rim is `mix(color.border.subtle, the kind's rim colour, rim.mix)`, with `rim.mix` scaled down in steps of 0.01 until the rim differs from `color.accent` by ΔE2000 10 or more (`MIN_DELTA_E_RIM_FROM_ACCENT`), so it never reads as a checked button's outline. The inner glow is the kind's rim colour at `inner.alpha`; its residual (`residual`: `alpha · max(0, 1 − d / blur)`, evaluated half a pixel nearer the edge) is blended into the face at the ink band's ends before the pairs are checked, and `inner.alpha` scales down like `face.dark`. With the built-in colours the rim is the full 0.55 everywhere, and the inner glow is 0 in Dark, 0.19 for secondary and 0.05 for danger in Light.
- **The halo and its clear zone** (ADR-0122 decision 8): the halo is not scaled by the extent. `EffectDraw::halo_clear`, the slot field `halo-clear` and `Theme.halo-clear` are `halo.blur + 1` px when the setting draws a halo and 0 otherwise, in every density. A primary draws its halo only where its `Button` or `SplitButton` instance sets `halo-room: true`; the layout at that position keeps the zone free (design system, "Effects").
- **The chosen plate's room** (`EffectDraw::plate_*`, slot fields `effects-plate-*`): the plate's shadow blur and offset are the extent-scaled shadow scaled again so their sum fits one `size.focus-ring`; its glow blur is that room in a setting that draws a halo and 0 otherwise; its key edge is the extent-scaled key edge, at most the plate's band top (`plate_key_edge`: 2 px on a regular 24 px plate with the 20 px label line). Its key edge colour is the key colour of `surface.overlay`, checked against the live colour with the other key edges.
- **Extent** (per slot, on the lengths after density): `max(0, min(4, space.1, space.2 − size.focus-ring))`, 4 px regular and roomy, 2 px compact; shadow, key edge and press are scaled down together to fit it.
- **Checks that turn a setting off** (`checked`; ADR-0120 decision 9, ADR-0122 decision 6): every derived colour (key edges, halo, rims, inner glows and every gradient stop that differs from its fill) differs from `color.state.live` by ΔE2000 15 or more; `color.border.focus` on `color.surface.base` blended with a neighbour's strongest shadow at the outer edge of the extent keeps 3:1. A failure makes the setting calm with an effects notice naming the check; the theme's colours and colour warnings are unchanged. The face pairs never fail a setting: their searches scale the shading down instead.
- **Every density** (ADR-0122 decision 6): `Tokens::resolve` runs the checks for regular, roomy and compact steps 1 to 3 (`EFFECT_DENSITIES`, `effects_notice`). The notice is stored once and names the densities when it does not apply to all of them. A theme whose setting fails at every density resolves to calm; otherwise it keeps its setting and `ResolvedTheme::effect_draw()`, which works on the lengths as they are after density, gives calm at a density that fails. Glass gets the notice "This theme's colours leave no room for Glass shading" where no face is shaded; it keeps its shadow.
- **The built-in file is strict**: `Tokens::parse` refuses a file whose Dark or Light theme would get an effects notice in any setting and density.
- **Effects notice**: a `ThemeProblem` with `Severity::Notice`, `token: Some("effects")` and no rule, kept in `ResolvedTheme::warnings` beside the colour warnings. It never refuses a theme, Fix ignores it, and colour warning counts leave it out (`ThemeProblem::is_warning`, `ResolvedTheme::colour_warnings`). An unknown stored value reads as calm with "This theme uses effects this version does not have; it shows as Calm" and is kept unchanged on save.
- **Downgrade**: a theme saved as `"glow"` or `"glass"` reads as calm with the unknown-setting notice in a build that only knows ADR-0120's settings.
- `ResolvedTheme` carries `effects` (resolved) and `effect_values`; `ResolvedTheme::effect_draw()` gives what a slot draws.

### Theme document (`kind = "theme"`, format 1 or 2)

```toml
format = 1
kind = "theme"
name = "Midnight"
base = "dark"
author = "Salih"
description = "Deep blue surfaces with a warm accent"

[colors]
"color.surface.base" = "#0b1020"
"color.accent" = "#ff9f43"

[font]
"font.family" = ["Inter", "Segoe UI", "Helvetica Neue"]

[type]
"type.body" = { size = 14, line = 20, weight = 400 }

[length]
"radius.md" = 8

[duration]
"motion.fast" = 100
```

| Key | Meaning |
| --- | --- |
| `base` | Required: `dark` or `light`. The retired `high-contrast` reads as `dark` and is written back as `dark` on the next save (ADR-0123) |
| `author`, `description` | Optional display text: one line, no control characters or text direction marks, at most 64 and 200 characters |
| `effects` | Optional: `"calm"`, `"glow"`, `"glass"` or `"tactile"` (ADR-0122; `"vivid"` reads as Glow and is kept as stored). Missing or `"calm"` is calm and is written as no key. A value that is not a string, or not a valid name, is refused; a valid unknown name is kept and reads as calm with the effects notice |
| `colors`, `font`, `type`, `length`, `duration` | Optional tables of overrides, keyed by token name; a token belongs to its table's group (a colour under `[length]` is refused) |

**Format** (ADR-0120 decision 2): a theme whose stored `effects` is calm or missing is written as format 1, so older builds keep reading it; any other stored value (glow, glass, tactile, the older vivid or an unknown one) is written as format 2. The stored key decides, never the resolved effects. Format 1 reads as format 2 with no change, and a format 1 file with a hand-edited `effects` key is read and honoured. Older builds refuse format 2 and fall back to the theme's base. Writing format 2 over a format 1 file keeps the old file once as `<id>.toml.format1.bak`.

Other top-level keys are refused (ADR-0051 decision 2). Unknown token names inside the tables are the theme exception to ADR-0051's unknown-key rule (ADR-0057 decision 3): Inside the tables, a key that is a valid token name (lowercase words joined by `.` or `-`) but not known to this build is kept, rendered back on save in its table, not applied, and reported (`ResolvedTheme::unknown`); an invalid name is refused. Rendering is deterministic and writes overrides sorted by name.

### Resolving and checking

`Tokens::resolve(&self, theme: &ThemeOverrides) -> Result<ResolvedTheme, ThemeProblems>` on the built-in tokens of the running build:

- starts from `base`'s colour set and the shared lengths, durations, text styles and font family, then applies each override;
- runs every check of the design system and every theme rule above and returns all problems at once, each `ThemeProblem { token: Option<String>, reason, severity, rule }` naming the token it belongs to (the editor shows it beside the token). **Errors** (the theme is refused): a non-themeable token, a value of the wrong kind, a value out of bounds, each failed rule across tokens. **Warnings** (ADR-0072; the theme resolves and is used): each failed contrast rule (naming the foreground token, with the ratio found and needed), each failed hue rule, each colour too close to live. `Err` carries errors and warnings together; `Ok(ResolvedTheme)` carries `warnings`. Built-in token files (and `RBS_TOKENS`) treat every rule as an error. `suggest_colour(tokens, theme, token)` returns the nearest-lightness colour that clears the token's warnings;
- `ResolvedTheme` holds `base`, one colour set (plus the fixed colours), lengths, durations, text styles, the font family list and the unknown names.

Property test: for any set of overrides drawn from the themeable tokens with values in and out of bounds, `resolve` either returns a theme whose only problems are colour warnings or returns at least one error, and never panics.

### Theme library (`rbs-user-data`)

`UserData::themes() -> Library<Theme>` on `themes/` with every rule of the [user data spec](user-data.md#libraries-library). Export scrubs nothing. Built-in themes are not in the library; the app lists them first, as Dark and Light, with the ids `builtin:dark` and `builtin:light`. A stored `builtin:high-contrast` reads as `builtin:dark` (ADR-0123). Duplicating a built-in theme creates a user theme with that base and no overrides; duplicating a user theme copies its base and overrides.

### Appearance document (`appearance.toml`, `kind = "appearance"`, format 4)

| Key | Type | Default |
| --- | --- | --- |
| `mode` | `"system"` or `"fixed"` | `"system"` |
| `dark` | theme id | `"builtin:dark"` |
| `light` | theme id | `"builtin:light"` |
| `theme` | theme id | `"builtin:dark"` |
| `density` | `"regular"`, `"compact"` or `"roomy"` | `"regular"` |
| `compact_steps` | integer 1, 2 or 3 | 1 |

Format 1 is format 3 without `density` or `compact_steps` (read as `regular`, step 1). Format 2 is format 3 without `compact_steps` (read as step 1). Format 4 adds the value `"roomy"` (ADR-0112); a format 3 file reads unchanged, and an older build refuses a format 4 file and starts with its defaults. A `compact_steps` outside 1, 2 or 3 is refused. The step is kept while `density` is `regular`.

Compact spacing does not write the theme. While `density` is `compact`, each slot's freshly resolved length map is stepped `compact_steps` times (a second step on that same map would go further, so the app resolves again first). `space.*` and `size.control.*` each take the next smaller token's length, repeated; the smallest step is unchanged. `size.panel.pad`, `size.section.gap` and `size.field.gap` take the Nth smaller original `space.*` value that is still at or above that token's floor; when no such value remains, the token sits on its floor. `size.field.gap` is then kept at or below `size.section.gap`. No length is introduced except a token's floor. Text, radii, icons, menus and every non-themeable size stay as resolved. The same step applies to every theme the slots use. Off, the theme's own lengths are used.

Roomy spacing (ADR-0112 decision 9) does not write the theme either. While `density` is `roomy`, `size.control.md` takes the resolved `size.control.lg`, and `size.panel.pad`, `size.section.gap` and `size.field.gap` each take the next larger resolved `space.*` value (unchanged when none is larger). Nothing else changes: `space.*`, `size.control.sm`, `size.control.lg`, text and every non-themeable size stay as resolved, so the sizes built from the smallest steps (the Mixer strip, compact fields, the Transition panel) are the same in every density. Every value only grows or stays, so no "must not be smaller than" rule can fail. With the built-in lengths the default control is 32 px, the panel pad 16, the section gap 24 and the field gap 12.

**Panel outline** (ADR-0112 decision 3). Each slot also says whether docked panels and Settings cards draw their `color.border.subtle` outline (`Theme.panel-outline`): yes when the slot's `color.surface.raised` and `color.surface.base` differ by less than 1.15:1 (`rbs_ui::tokens::PANEL_OUTLINE_BELOW`), so colour alone would not separate a panel from the window ground. The built-in Dark (1.17) and Light (1.18) draw none; a user theme with close surfaces keeps it. It is computed once when the slot is filled.

**Button outline** (ADR-0118). Each slot also says whether secondary, danger and framed buttons draw their `color.border.subtle` outline (`Theme.button-outline`, `ResolvedTheme::button_outline`): yes when a resting fill (`color.button.fill` or `color.action.destructive.subtle`, `BUTTON_FILLS`) differs by less than 1.15:1 from any of `color.surface.base`, `.raised`, `.sunken` or `.overlay` (`BUTTON_SURFACES`). The built-in Dark draws none; Light keeps it. A user theme that recolours the surfaces but not the button colours keeps the base theme's fills, and the outline follows; a fill that fails a contrast rule is a colour warning (ADR-0072).

`UserData::appearance()` returns the defaults and the reason when the file cannot be read; `set_appearance(&WriterLock, ..)` writes it through the user data writer. A theme id is `builtin:<name>` or a library id. An id that names no usable theme falls back to `builtin:<base>` when the theme's `base` can be read (envelope and `base` key only), else to `builtin:dark` (for `dark` and `theme`) or `builtin:light` (for `light`); the app shows a note and does not rewrite the file. **Deleting:** an id whose theme file is gone (the theme was deleted) is not such a case: deleting a theme in use sets the slots that name it to `builtin:<base>` of the deleted theme and saves the choice, and at start (before the user data writer lock is taken) a slot naming a missing file is set to `builtin:dark` (`dark`, `theme`) or `builtin:light` (`light`) and saved, with no note. `rbs-app --reset-appearance` moves `appearance.toml` to `appearance.toml.reset.bak` (numbered when taken) and starts with the defaults.

### Applying (`rbs-app` `look`)

- **Slots.** The generated `Theme` global has `slots: [ThemeSlot; 2]`: slot 0 is used while the OS scheme is dark, slot 1 while it is light. `ThemeSlot` holds every theme colour, every themeable length, duration and text style, and the effect fields of ADR-0120 and ADR-0122 (`SLOT_EFFECTS`: `effects-on`, `effects-shadow-blur`, `-offset`, `effects-shadow`, `effects-halo-blur`, `effects-halo`, `effects-key-edge`, `effects-press`, `effects-rim-on`, `effects-inner-blur`, and per kind `effects-key-<kind>`, `effects-shade-<kind>` (the face is not flat), `effects-stop-<kind>` (the searched gloss stop) and `effects-top-<kind>-<state>` and `effects-bottom-<kind>-<state>` for rest, hover and, for primary and secondary, pressed; secondary and danger also have `effects-rim-<kind>` and `effects-inner-<kind>`) and the length `halo-clear`, all filled by `slot()` from `ResolvedTheme::effect_draw()` after density. Only library components read `Theme.effects-*` (`cargo xtask check-ui`); `Theme.halo-clear` is a length for layouts and is not counted. `Theme.active` is `Palette.color-scheme == light ? 1 : 0`, unless `Theme.os-scheme` is 0 or 1. On Windows the menus stay the system's and a dark theme asks for the dark menu, a light theme for the light one; that request changes what Palette reports, so the app sets `os-scheme` from the system setting (dark 0, light 1; the OS high-contrast mode counts as light) and updates it when that setting changes. Every `Theme.*` colour and `Tokens.*` themeable value reads `slots[active]`. The fixed colours and non-themeable tokens stay single values. `Theme.choice` is removed. Built-in defaults: slot 0 Dark, slot 1 Light.
- **Filling the slots.** `system` mode: slot 0 = resolved `dark`, slot 1 = resolved `light`. `fixed` mode: both = resolved `theme`. Compact spacing then steps those freshly resolved lengths (`compact_steps` while `density` is `compact`). `RBS_THEME=<dark|light>`: both = that built-in theme, and the appearance choice, including compact spacing, is not applied. `RBS_TOKENS=<file>`: the themes resolve on that file instead of the built-in one.
- **On a change** of choice or theme, the shell sets the slots of every open window (main, floating panels, Settings, source settings, Measure sync offset, Attributes, OBS import and projectors) and gives native layers their new colours (preview selection outline, meters); each new window gets the same slots when it opens.
- **Font.** `look` is given a `FontCatalog` (`fn has_family(&self, name: &str, sample: &str) -> bool`): in the app the system font database, in tests a fake. The window's `default-font-family` is the first name in `font.family` for which `has_family` is true with the UI language's sample text (its alphabet and digits); none: the OS UI font (empty string). The choice is made again when the UI language changes.
- **Reading.** Files are read at start (the themes `appearance.toml` names), when the Appearance page opens (envelopes) and on the `ui.theme.reload` command (View › Reload themes): it reads the token file (`RBS_TOKENS` when set), `appearance.toml` and the theme files again, resolves the two slots as at start (with `RBS_THEME`, that built-in theme of the new file), applies them to every open window and refreshes the Appearance page; an open draft in the editor stays open and is checked again against the new file, and what cannot be used is reported as at start. Opening the page also reads the files again. Nothing watches files or polls (P13).
- **View › Theme** (`ui.theme.select`): a picker of at most the first ten themes (built-in Dark and Light, then user themes by library name). Picking one runs the same Fixed-mode choice as Settings › Appearance › Use, without opening Settings. While Appearance follows the system, no choice is checked; picking still switches to Fixed.

## Errors and failure behaviour

Nothing panics. A theme that cannot be read or has an error is never applied (colour warnings do not count); the slot uses its built-in fallback and the Appearance page says why. Library errors are `DataError` (user data spec); check failures are `ThemeProblems`. A body that `ThemeBody::from_body` refuses gives a `ThemeBodyError` (a missing, wrong or unknown `base`, a key that must be a string, `author`/`description` that is not plain text (`LineError`), an invalid `effects` name, a table that is not a table, an unknown key, an invalid token name, a token in the wrong table); a failed effect check is an `EffectCheckError` (a derived colour like the live colour, or the focus ring under 3:1), shown as the effects notice; a token file of another build that lacks a token the app uses gives `MissingToken` from the generated `slot` and `apply_tokens`. The texts are unchanged. A new error rule (a bound or a rule across tokens) can refuse a saved theme that passed before; a new colour rule only adds a warning: it falls back the same way and the page names the failed rule, so the user can fix the colour in the editor.

## Performance requirements

User-paced; never on a hot path. Resolving and checking a theme takes well under 1 ms; applying sets each window's globals once per change. No cost while the user does nothing.
